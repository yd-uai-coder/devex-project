# 外部設計書：Devex

## 2.1 システム構成概要

Devexは、モダンなWeb技術スタックを用いて構築される対話型ドキュメント自動生成システムです。ユーザー（フロントエンド）からのリクエストを受け、AIによる高度な要件ヒアリングとドキュメント生成をセキュアに処理します。

```
[ ユーザー (ブラウザ) ]
       │
       ▼ HTTPS (JWT認証)
[ フロントエンド: Next.js (SSR / SPA) ]
       │
       ▼ REST API / SSE (ストリーミング)
[ バックエンド: FastAPI + LangChain ]
       ├── (プロンプト制御・非同期処理)
       ├── [ 外部LLM API (Gemini Flash-Lite) ]
       │
       ▼ SQL (ORM)
[ データベース: PostgreSQL (セッション・履歴・ドキュメント永続化) ]
```

* **フロントエンド層 (Next.js)**: ユーザーインターフェースを提供。SSR（サーバーサイドレンダリング）による高速な初期表示と、チャット画面でのスムーズなクライアントサイド・インタラクションを実現。

* **バックエンド層 (FastAPI + LangChain)**: 業務ロジック、LLMとの連携、プロンプト管理を担う。LangChainを用いたエージェント制御により、ユーザーとの対話履歴を踏まえた適切なヒアリングと、構造化されたMarkdown生成を統御。非同期処理によりタイムアウトを防止。

* **データ層 (PostgreSQL)**: ユーザーアカウント情報、チャットセッション、対話履歴、生成された各設計書（要件定義、外部設計、内部設計、実装計画）を永続化。

## 2.3 主要画面のUI/UX仕様

### SCR-004: チャットヒアリング画面

本画面は「初期ヒアリング入力」→「チャット」の2段構成とする。初期入力の段階でユーザーに明確な設計・構想を求めすぎないこと、要件・設計は最終的にAIが判断してユーザーの承認を経てドキュメント化することを重視し、フォームは必要最小限に絞る。

* **初期ヒアリング入力(チャット開始前)**:
  * **システム概要**(必須・自由記述): 1行〜数行のtextarea。プレースホルダ例「作りたいものを一言で教えてください」。最大**全角200文字**。
  * **実現したいこと**(必須・自由記述): 複数行のtextarea。プレースホルダで「箇条書き推奨(改行区切りでOK)」と軽く示唆するが、フォーマットは強制しない。バリデーションは「空でないこと」+最大**全角80文字**。箇条書きへの分解・構造化はこの画面では行わず、後続のチャットでAIが行いユーザーに確認する。
  * **補足**(任意・自由記述): 「欲しい機能」「その他」を1項目に統合したtextarea。最大**全角400文字**。この時点でリストや選択肢を作らせない。AIによる機能提案はフォームではなくチャット内で行う(会話の中でAIが候補を挙げ、ユーザーが同意・修正する)。
  * **環境設定**(任意・折りたたみ、ネイティブ `<details>/<summary>` を推奨): 見出しに「未入力の場合はAIにおまかせします」と明記し初期状態は閉じておく。言語・フレームワーク・DB・デプロイ環境の4グループはいずれも複数選択(チェックボックス群)。フレームワークは言語ごとに `<fieldset><legend>` で静的にグルーピングして示す(「言語を選ぶとフレームワークの選択肢が動的に絞り込まれる」ような動的コンボボックスは作らない)。SCR-003でテンプレートを選択している場合、そのテンプレートの`default_environment`([内部設計書](internal_design.md) 3.2節`prompt_templates`)を初期値としてプリフィルする(ユーザーは編集可能)。
  * **参考資料のアップロード**(任意・最大3ファイル): 対応形式は **txt・Markdown・PDFのみ**(ファイル選択ダイアログの`accept`属性・ドロップ領域の案内文の双方で明示する)。Word/Excel/PowerPointは非対応であり、案内文で「図を含む資料はPDFに変換してからアップロードしてください」と促す。アップロード済みファイルは一覧表示し、ファイルごとに削除ボタンを設ける。対応形式外・サイズ超過・4件目以降の選択はクライアント側で即座に弾き、`aria-invalid`/`aria-describedby`/`role="alert"`でエラーを提示する(2.5節5項のバリデーションルール・エラーコードと対応させる)。送信後のテキスト化に失敗したファイルがあってもヒアリング自体はブロックせず、失敗した旨を軽微な通知として示す。
  * 送信すると `POST /api/v1/projects`(`multipart/form-data`。初期ヒアリング入力の各項目+添付ファイル最大3件。[内部設計書](internal_design.md) 3.3節参照)でプロジェクトを作成し、以降はチャット画面へ遷移する。
  * **アクセシビリティ**: 各入力欄のエラー表示には `aria-invalid` / `aria-describedby` / `role="alert"` を必ず配線する。折りたたみ・グルーピングも上記のとおりネイティブ要素・セマンティックHTMLを優先する。

* **チャット画面構成**:
  * **ヘッダー**: プロジェクト名、現在のステータス(ヒアリング中 / 生成中 / 完了 / 修正中)、ダッシュボードへの戻るボタン、ドキュメント生成ボタン(手動トリガー)。ステータスが完了または修正中の場合は、生成済みドキュメントへの常設リンクを画面内に配置する(自動的にドキュメントプレビュー画面へ遷移させることはしない。「チャットに戻る」操作が必ずしも「今の内容を修正したい」を意味するとは限らないため)。
  * **メインエリア(チャット履歴)**: ユーザーのメッセージ(右側吹き出し)とAIからのメッセージ(左側吹き出し、Markdown対応、ストリーミング出力)。チャット開始直後、AIの最初の発話は初期ヒアリング入力の内容を踏まえた理解の要約と確認質問から始まる。
  * **フッター(入力エリア)**: テキスト入力欄(複数行対応)、送信ボタン、ファイル添付(将来拡張用としてUIのみ、または無効化)。

* **主要なアクション**:
  * ユーザーがテキストを入力し送信すると、LLMからのストリーミング応答がリアルタイムで描画される。
  * AIは以下(1)〜(4)を満たした場合(環境設定が未入力の場合は(5)も)、「十分な要件が揃いました」と判断する: (1)目的・課題が明確、(2)コア機能が最低1つ以上「誰が・何を・なぜ」のレベルで具体化、(3)想定ユーザー像の把握、(4)MVPスコープ(今回作る/作らない)の認識合わせ、(5)技術的な強い制約・希望の有無の確認。十分と判断した際は、即座に生成へ進まず、まず構造化した要件サマリをチャット上に提示しユーザーの明示的な承認を求める。承認後(またはユーザーが手動で「設計書を生成する」ボタンを押下した際)、ローディングインジケーターを表示し、生成処理(SCR-005へ遷移)へ移行する。
  * **生成完了後の自己診断**: 4文書の生成が完了すると、AIはそれらを対象に自己診断(不足・不明瞭な点の洗い出し)を行い、指摘事項を「最重要/中程度/軽微」の3段階に分類してチャットに提示する(`sender='others'`の`chat_histories`行として記録。[内部設計書](internal_design.md) 3.2節参照)。ユーザーは各指摘についてチャットで回答するか、現状のまま確定するかを選べる。回答内容を反映して再生成すると、新バージョンとして保存される([内部設計書](internal_design.md) 3.2節「バージョニング方針」)。

  * **アクションバー**:

## 2.5 データ入出力仕様

### 1. ユーザー入力バリデーション (チャットメッセージ)

* **受付フォーマット**: UTF-8 テキスト文字列
* **バリデーションルール**:
  * 必須入力（空文字不可）
  * 最大文字数: 5,000文字 / 1メッセージ
  * 不正なスクリプトタグやインジェクション文字列のサニタイジング（フロント・バックエンド双方で実施）

### 2. プロンプトテンプレート選択データ (JSON、※ステージ2)

`GET /api/v1/prompt-templates`([内部設計書](internal_design.md) 3.3節)が返す一覧の1件分。

* **データ構造例**:

```json
{
  "id": "b3f1c2a0-...",
  "name": "Webアプリケーション標準",
  "target_type": "SaaS・BtoC/BtoB Webサービス",
  "system_prompt": "あなたは優秀なシステムアーキテクトです...",
  "default_environment": {
    "languages": ["TypeScript", "Python"],
    "frameworks": ["Next.js", "FastAPI"],
    "databases": ["PostgreSQL"],
    "deploy_targets": []
  }
}
```

`id`(UUID)をSCR-004送信時の`template_id`としてそのまま使う(3.3節「初期ヒアリング入力データ」参照)。

### 3. 初期ヒアリング入力データ (JSON)

SCR-004の初期ヒアリング入力(2.3節参照)を送信する際のペイロード。`system_overview` と `goals_raw` は必須(空文字不可)、他は任意。初期入力の段階では箇条書きへの分解やカテゴリ分けを求めず、自由記述のまま受け取る(構造化はチャット内でAIが行う)。

* **データ構造例**:

```json
{
  "system_overview": "社内の備品予約を一元管理したい",
  "goals_raw": "誰がいつ何を予約したか一覧できるようにしたい\n予約の重複を防ぎたい",
  "notes_raw": "既存のExcel管理からの移行を想定",
  "template_id": null,
  "environment": {
    "languages": ["Python", "TypeScript"],
    "frameworks": ["FastAPI", "Next.js"],
    "databases": ["PostgreSQL"],
    "deploy_targets": ["AWS"]
  }
}
```

* **バリデーションルール**:
  * `system_overview`: 必須・空文字不可・最大全角200文字・フォーマット(箇条書き等)は強制しない
  * `goals_raw`: 必須・空文字不可・最大全角80文字・フォーマット(箇条書き等)は強制しない
  * `notes_raw`: 任意(null可)・最大全角400文字
  * `template_id`: 任意(null可、※ステージ2)。SCR-003で選択したテンプレートのID。[内部設計書](internal_design.md) 3.2節②`projects.template_id`
  * `environment`: 任意(null可)。各配列は空でもよい

### 4. ドキュメントエクスポート出力仕様

* **出力ファイル形式**: Markdown (`.md`)
* **文字コード**: UTF-8 (BOMなし)
* **ファイル命名規則**: `{document_type}.md`(本プロジェクトリポジトリの`docs/`配下の実ファイル名と一致させる)
  * 例: `requirements.md`、`external_design.md`、`internal_design.md`、`implementation_plan.md`

### 5. 初期ヒアリング添付ファイル仕様

SCR-004の初期ヒアリング入力(2.3節参照)に添付する参考資料のアップロード仕様。`POST /api/v1/projects`は添付ファイルがある場合`multipart/form-data`となり、初期ヒアリング入力の各項目(3項目の3.節参照)はフォームフィールドとして、ファイルは`files`フィールドとして送信する。

* **対応拡張子/MIME**: `.txt`(`text/plain`) / `.md`(`text/markdown`) / `.pdf`(`application/pdf`)の3種類のみ。Word/Excel/PowerPoint等その他の形式は非対応。
* **バリデーションルール**:
  * 最大**3ファイル**まで(4件目以降はクライアント側で選択不可、サーバー側でも`TOO_MANY_FILES`で拒否)
  * 1ファイルあたり最大**5MB**(超過時は`FILE_TOO_LARGE`)
  * 対応拡張子/MIME以外は`UNSUPPORTED_FILE_TYPE`
* **テキスト化方式**([内部設計書](internal_design.md) 3.2節`intake_files`・3.3節参照):
  * `txt`/`md`: ファイル内容をUTF-8テキストとしてそのまま読み込む(LLM呼び出し不要)。
  * `pdf`: Gemini(既存の`app/ai/llm/gemini.py`のクライアント)にファイルをそのまま渡し、LLMのネイティブなマルチモーダル理解でテキスト化する。図・レイアウトもLLMが解釈した説明として結果に含まれる。
  * 抽出したテキストは1ファイルあたり最大**20,000文字**まで保存し、超過分は切り詰める。
  * テキスト化に失敗した場合は`FILE_EXTRACTION_FAILED`として記録するが、ヒアリング自体はブロックしない(添付は補助情報のため)。
* **保存方針**: 元ファイルの実体(バイナリ)は保持せず、抽出したテキストのみを永続化する(オブジェクトストレージ非依存)。

## 2.6 UML設計図生成・レビュー機能(ステージ3)

承認済みの4文書を入力に、AIがUML意味モデル(構造化JSON)を生成し、Web上でレビュー・修正した上でdraw.io/SVG形式へ出力する機能。要件整理は`appendix/stage3-requirements-organization.md`、決定事項D1〜D8は[decision digest](../textbook/decision-digest.md)参照。

* **対応する図記法**: コンポーネント図(モジュール構造)、ER図(データ構造)、処理別データフロー図(DFD。APIエンドポイント/バッチ単位)。アクティビティ図はStage 3後半(Phase 14)でShould対応、シーケンス図・クラス図はCould(必要になればStage 4以降で検討)。
* **生成トリガー**: SCR-005に新設する「設計図を生成する」ボタン。4文書生成後、ユーザーが明示的に押下した時点でAIが意味モデルを生成する(SCR-004の「ヒアリング完了→承認→生成」と同じ操作パターン)。
* **生成対象の選択と非同期生成(Phase 10で確定)**:
  * 生成は非同期で行う。受け付け後、画面は生成状態(`generating`/`completed`/`failed`)をポーリングで表示する。
  * コンポーネント図とER図は、プロジェクトに1枚ずつ生成する。ER図のテーブルが30件を超える場合は、ユーザーが対象のテーブルを選び、グループ名を付けて部分図として生成する。
  * DFDは、内部設計書の「処理別データフロー」節に列挙された処理(APIエンドポイント/バッチ)から選んで生成する。個別に1件ずつ生成するボタンと、チェックボックスで最大5件をまとめて生成する操作の両方を用意する。
  * 同じ対象を再生成すると、既存の図を上書きする。
  * 図の数には上限を設けない。AIの利用上限(無料枠)やトークン上限で生成が止まった場合は、生成履歴に対象ごとの結果を表示する。表示するのは、止まった理由と再度の生成指示が必要なことである。クォータ超過の後に残った対象は「未着手」として表示する。
  * 内部設計書が旧形式(「処理別データフロー」節が無い)の場合は、DFDの候補が表示されない。このときは内部設計書の再生成を促す。
* **レビュー画面(SCR-007)**: React Flowによるプレビュー。ノード移動・要素編集・自動レイアウト(再実行可)に対応する。手動移動後の辺は折れ点を持たず、smoothstepでの描画に委ねる。
* **状態遷移**: `draft → reviewing → approved → exported`。approved後に編集すると`reviewing`へ戻る。
  * **具体化(Phase 12で確定)**:
    * 保存(座標だけの保存を含む)と自動レイアウトの実行で、どの状態からでも`reviewing`になる。
    * 承認は`draft`・`reviewing`から行える(AIの出力を手直しせずに承認できる)。
    * 図のダウンロード(出力)に成功すると`exported`になる。AIで再生成すると`draft`に戻る。
  * **承認の条件**:
    * 画面で見ていた版であること(他で更新されていれば競合として再読み込みを促す)。
    * 全要素の配置があること(無ければ自動レイアウトの実行を促す)。
    * 検証エラーが無いこと(エラーの一覧を検証パネルに表示する。警告は承認を妨げない)。
    * 未保存の変更がある場合、承認ボタンは「保存して承認」となり、保存してから承認する。
  * 承認済みの図には、「保存するとレビュー中に戻る(承認し直しが必要)」旨を常に表示する。
* **承認・エクスポート**: 承認後、決定的(AI非依存)なdraw.io GeneratorがXMLを生成し`.drawio`としてダウンロードできる。同一エンジンがSVGも同時出力する。
  * **具体化(Phase 12で確定)**:
    * 出力は承認済み・出力済みの図だけで、未保存の変更があるときは出力できない。
    * 辺ラベル(ERの多重度、DFDのデータ項目名)はレビュー画面と同じ文言で描く。
    * 手動移動した辺は、draw.ioでは`orthogonalEdgeStyle`に経路を任せ、SVGでは簡易な直交経路で描く。
    * レーン帯は描かない(レビュー画面と同じ)。
    * 出力ボタンの隣に、「ダウンロードしたファイルを直接編集しても、Devexには反映されない」旨を表示する(D6)。
* **内部設計書への反映**: 承認済みの図とその要素表を、内部設計書の該当セクション([内部設計書](internal_design.md) 3.2節・3.3節、アンカーコメントで位置を特定)にプレビュー時点でSVGとして差し込む。ダウンロードはMarkdown+図ファイル(SVG/drawio)のzip形式にする。エクスポート後にユーザーがファイルを直接編集した場合、その変更はDevexに反映されない旨を画面上に明示する(draw.ioの再インポートは対象外)。
  * **具体化(Phase 13で確定)**:
    * 図を承認すると、同時に内部設計書の表示中の版へ要素表が反映される(版は増えない)。文書の再生成・復元で反映が消えた場合は、文書画面(内部設計のタブ)の「図を再反映」で戻す。承認済みの図のうち反映されていないものの件数を表示する。
    * プレビューでは、承認済みの図だけ画像を表示する。承認後に編集中(レビュー中)の図は画像を出さず、要素表が前回承認した内容であることを示す。
    * 図が内部設計書の古い版から生成されている場合、プレビューと設計図の一覧(SCR-007の一覧)に、再生成を促す表示を出す。
    * 「図付きでダウンロード(.zip)」のzipには、内部設計書のmd(図ファイルへの相対リンク入り)と、文書に反映済みの図のSVG・drawioが入る。zipに入れた図は`exported`になる。
* **図の手直しの反映**: 承認済みの図の変更を、AIが基本設計・内部設計(散文)への修正案(差分)として提示し、ユーザーが承認して反映する(Should、Phase 13b)。
