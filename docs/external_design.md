# 外部設計書：Devex

## 2.1 システム構成概要

Devexは、モダンなWeb技術スタックを用いて構築される対話型ドキュメント自動生成システムです。ユーザー（フロントエンド）からのリクエストを受け、AIによる高度な要件ヒアリングとドキュメント生成をセキュアに処理します。

```
[ ユーザー (ブラウザ) ]
       │
       ▼ HTTPS (JWT認証)
[ フロントエンド: Next.js (SSR / SPA) ]
       │
       ▼ REST API / SSE (ストリーミング)
[ バックエンド: FastAPI + LangChain ]
       ├── (プロンプト制御・非同期処理)
       ├── [ 外部LLM API (Gemini Flash-Lite) ]
       │
       ▼ SQL (ORM)
[ データベース: PostgreSQL (セッション・履歴・ドキュメント永続化) ]
```

* **フロントエンド層 (Next.js)**: ユーザーインターフェースを提供。SSR（サーバーサイドレンダリング）による高速な初期表示と、チャット画面でのスムーズなクライアントサイド・インタラクションを実現。

* **バックエンド層 (FastAPI + LangChain)**: 業務ロジック、LLMとの連携、プロンプト管理を担う。LangChainを用いたエージェント制御により、ユーザーとの対話履歴を踏まえた適切なヒアリングと、構造化されたMarkdown生成を統御。非同期処理によりタイムアウトを防止。

* **データ層 (PostgreSQL)**: ユーザーアカウント情報、チャットセッション、対話履歴、生成された各設計書（要件定義、外部設計、内部設計、実装計画）を永続化。

## 2.3 主要画面のUI/UX仕様

### SCR-004: チャットヒアリング画面

本画面は「初期ヒアリング入力」→「チャット」の2段構成とする。初期入力の段階でユーザーに明確な設計・構想を求めすぎないこと、要件・設計は最終的にAIが判断してユーザーの承認を経てドキュメント化することを重視し、フォームは必要最小限に絞る。

* **初期ヒアリング入力(チャット開始前)**:
  * **システム概要**(必須・自由記述): 1行〜数行のtextarea。プレースホルダ例「作りたいものを一言で教えてください」。最大**全角200文字**。
  * **実現したいこと**(必須・自由記述): 複数行のtextarea。プレースホルダで「箇条書き推奨(改行区切りでOK)」と軽く示唆するが、フォーマットは強制しない。バリデーションは「空でないこと」+最大**全角80文字**。箇条書きへの分解・構造化はこの画面では行わず、後続のチャットでAIが行いユーザーに確認する。
  * **補足**(任意・自由記述): 「欲しい機能」「その他」を1項目に統合したtextarea。最大**全角400文字**。この時点でリストや選択肢を作らせない。AIによる機能提案はフォームではなくチャット内で行う(会話の中でAIが候補を挙げ、ユーザーが同意・修正する)。
  * **環境設定**(任意・折りたたみ、ネイティブ `<details>/<summary>` を推奨): 見出しに「未入力の場合はAIにおまかせします」と明記し初期状態は閉じておく。言語・フレームワーク・DB・デプロイ環境の4グループはいずれも複数選択(チェックボックス群)。フレームワークは言語ごとに `<fieldset><legend>` で静的にグルーピングして示す(「言語を選ぶとフレームワークの選択肢が動的に絞り込まれる」ような動的コンボボックスは作らない)。SCR-003でテンプレートを選択している場合、そのテンプレートの`default_environment`([内部設計書](internal_design.md) 3.2節`prompt_templates`)を初期値としてプリフィルする(ユーザーは編集可能)。
  * **参考資料のアップロード**(任意・最大3ファイル): 対応形式は **txt・Markdown・PDFのみ**(ファイル選択ダイアログの`accept`属性・ドロップ領域の案内文の双方で明示する)。Word/Excel/PowerPointは非対応であり、案内文で「図を含む資料はPDFに変換してからアップロードしてください」と促す。アップロード済みファイルは一覧表示し、ファイルごとに削除ボタンを設ける。対応形式外・サイズ超過・4件目以降の選択はクライアント側で即座に弾き、`aria-invalid`/`aria-describedby`/`role="alert"`でエラーを提示する(2.5節5項のバリデーションルール・エラーコードと対応させる)。送信後のテキスト化に失敗したファイルがあってもヒアリング自体はブロックせず、失敗した旨を軽微な通知として示す。
  * 送信すると `POST /api/v1/projects`(`multipart/form-data`。初期ヒアリング入力の各項目+添付ファイル最大3件。[内部設計書](internal_design.md) 3.3節参照)でプロジェクトを作成し、以降はチャット画面へ遷移する。
  * **アクセシビリティ**: 各入力欄のエラー表示には `aria-invalid` / `aria-describedby` / `role="alert"` を必ず配線する。折りたたみ・グルーピングも上記のとおりネイティブ要素・セマンティックHTMLを優先する。

* **チャット画面構成**:
  * **ヘッダー**: プロジェクト名、現在のステータス(ヒアリング中 / 生成中 / 完了 / 修正中)、ダッシュボードへの戻るボタン、ドキュメント生成ボタン(手動トリガー)。ステータスが完了または修正中の場合は、生成済みドキュメントへの常設リンクを画面内に配置する(自動的にドキュメントプレビュー画面へ遷移させることはしない。「チャットに戻る」操作が必ずしも「今の内容を修正したい」を意味するとは限らないため)。
  * **メインエリア(チャット履歴)**: ユーザーのメッセージ(右側吹き出し)とAIからのメッセージ(左側吹き出し、Markdown対応、ストリーミング出力)。チャット開始直後、AIの最初の発話は初期ヒアリング入力の内容を踏まえた理解の要約と確認質問から始まる。
  * **フッター(入力エリア)**: テキスト入力欄(複数行対応)、送信ボタン、ファイル添付(将来拡張用としてUIのみ、または無効化)。

* **主要なアクション**:
  * ユーザーがテキストを入力し送信すると、LLMからのストリーミング応答がリアルタイムで描画される。
  * **応答の途中の失敗(Phase 15)**: AIの利用上限などで応答が途中で失敗した場合は、失敗の理由と「送信したメッセージは保存されていない」ことを表示し、送ったメッセージの表示を取り消す(再送を促す)。接続が切れただけの場合は、メッセージを残したまま「接続が切れました」を表示する。
  * AIは以下(1)〜(4)を満たした場合(環境設定が未入力の場合は(5)も)、「十分な要件が揃いました」と判断する: (1)目的・課題が明確、(2)コア機能が最低1つ以上「誰が・何を・なぜ」のレベルで具体化、(3)想定ユーザー像の把握、(4)MVPスコープ(今回作る/作らない)の認識合わせ、(5)技術的な強い制約・希望の有無の確認。十分と判断した際は、即座に生成へ進まず、まず構造化した要件サマリをチャット上に提示しユーザーの明示的な承認を求める。承認後(またはユーザーが手動で「設計書を生成する」ボタンを押下した際)、確認ダイアログ(生成には数分かかり、その間はチャットを送れない)で確定してから、ローディングインジケーターを表示し、生成処理(SCR-005へ遷移)へ移行する。ボタンは押した時点で無効にする(二度押しの防止。Phase 15)。詳細設計モードのプロジェクトでは、生成するのは要件定義・外部設計の2文書である。
  * **生成完了後の自己診断**: 4文書の生成が完了すると、AIはそれらを対象に自己診断(不足・不明瞭な点の洗い出し)を行い、指摘事項を「最重要/中程度/軽微」の3段階に分類してチャットに提示する(`sender='others'`の`chat_histories`行として記録。[内部設計書](internal_design.md) 3.2節参照)。ユーザーは各指摘についてチャットで回答するか、現状のまま確定するかを選べる。回答内容を反映して再生成すると、新バージョンとして保存される([内部設計書](internal_design.md) 3.2節「バージョニング方針」)。

## 2.5 データ入出力仕様

### 1. ユーザー入力バリデーション (チャットメッセージ)

* **受付フォーマット**: UTF-8 テキスト文字列
* **バリデーションルール**:
  * 必須入力（空文字不可）
  * 最大文字数: 5,000文字 / 1メッセージ
  * 不正なスクリプトタグやインジェクション文字列のサニタイジング（フロント・バックエンド双方で実施）

### 2. プロンプトテンプレート選択データ (JSON、※ステージ2)

`GET /api/v1/prompt-templates`([内部設計書](internal_design.md) 3.3節)が返す一覧の1件分。

* **データ構造例**:

```json
{
  "id": "b3f1c2a0-...",
  "name": "Webアプリケーション標準",
  "target_type": "SaaS・BtoC/BtoB Webサービス",
  "system_prompt": "あなたは優秀なシステムアーキテクトです...",
  "default_environment": {
    "languages": ["TypeScript", "Python"],
    "frameworks": ["Next.js", "FastAPI"],
    "databases": ["PostgreSQL"],
    "deploy_targets": []
  }
}
```

`id`(UUID)をSCR-004送信時の`template_id`としてそのまま使う(3.3節「初期ヒアリング入力データ」参照)。

### 3. 初期ヒアリング入力データ (JSON)

SCR-004の初期ヒアリング入力(2.3節参照)を送信する際のペイロード。`system_overview` と `goals_raw` は必須(空文字不可)、他は任意。初期入力の段階では箇条書きへの分解やカテゴリ分けを求めず、自由記述のまま受け取る(構造化はチャット内でAIが行う)。

* **データ構造例**:

```json
{
  "system_overview": "社内の備品予約を一元管理したい",
  "goals_raw": "誰がいつ何を予約したか一覧できるようにしたい\n予約の重複を防ぎたい",
  "notes_raw": "既存のExcel管理からの移行を想定",
  "template_id": null,
  "environment": {
    "languages": ["Python", "TypeScript"],
    "frameworks": ["FastAPI", "Next.js"],
    "databases": ["PostgreSQL"],
    "deploy_targets": ["AWS"]
  }
}
```

* **バリデーションルール**:
  * `system_overview`: 必須・空文字不可・最大全角200文字・フォーマット(箇条書き等)は強制しない
  * `goals_raw`: 必須・空文字不可・最大全角80文字・フォーマット(箇条書き等)は強制しない
  * `notes_raw`: 任意(null可)・最大全角400文字
  * `template_id`: 任意(null可、※ステージ2)。SCR-003で選択したテンプレートのID。[内部設計書](internal_design.md) 3.2節②`projects.template_id`
  * `environment`: 任意(null可)。各配列は空でもよい

### 4. ドキュメントエクスポート出力仕様

* **出力ファイル形式**: Markdown (`.md`)
* **文字コード**: UTF-8 (BOMなし)
* **ファイル命名規則**: `{document_type}.md`(本プロジェクトリポジトリの`docs/`配下の実ファイル名と一致させる)
  * 例: `requirements.md`、`external_design.md`、`internal_design.md`、`implementation_plan.md`

### 5. 初期ヒアリング添付ファイル仕様

SCR-004の初期ヒアリング入力(2.3節参照)に添付する参考資料のアップロード仕様。`POST /api/v1/projects`は添付ファイルがある場合`multipart/form-data`となり、初期ヒアリング入力の各項目(3項目の3.節参照)はフォームフィールドとして、ファイルは`files`フィールドとして送信する。

* **対応拡張子/MIME**: `.txt`(`text/plain`) / `.md`(`text/markdown`) / `.pdf`(`application/pdf`)の3種類のみ。Word/Excel/PowerPoint等その他の形式は非対応。
* **バリデーションルール**:
  * 最大**3ファイル**まで(4件目以降はクライアント側で選択不可、サーバー側でも`TOO_MANY_FILES`で拒否)
  * 1ファイルあたり最大**5MB**(超過時は`FILE_TOO_LARGE`)
  * 対応拡張子/MIME以外は`UNSUPPORTED_FILE_TYPE`
* **テキスト化方式**([内部設計書](internal_design.md) 3.2節`intake_files`・3.3節参照):
  * `txt`/`md`: ファイル内容をUTF-8テキストとしてそのまま読み込む(LLM呼び出し不要)。
  * `pdf`: Gemini(既存の`app/ai/llm/gemini.py`のクライアント)にファイルをそのまま渡し、LLMのネイティブなマルチモーダル理解でテキスト化する。図・レイアウトもLLMが解釈した説明として結果に含まれる。
  * 抽出したテキストは1ファイルあたり最大**20,000文字**まで保存し、超過分は切り詰める。
  * テキスト化に失敗した場合は`FILE_EXTRACTION_FAILED`として記録するが、ヒアリング自体はブロックしない(添付は補助情報のため)。
* **保存方針**: 元ファイルの実体(バイナリ)は保持せず、抽出したテキストのみを永続化する(オブジェクトストレージ非依存)。

## 2.6 UML設計図生成・レビュー機能(ステージ3)

承認済みの4文書を入力に、AIがUML意味モデル(構造化JSON)を生成し、Web上でレビュー・修正した上でdraw.io/SVG形式へ出力する機能。要件整理は`appendix/stage3-requirements-organization.md`、決定事項D1〜D8は[decision digest](../textbook/decision-digest.md)参照。

* **対応する図記法**: コンポーネント図(モジュール構造)、ER図(データ構造)、処理別データフロー図(DFD。APIエンドポイント/バッチ単位)。アクティビティ図はStage 3後半(Phase 14)でShould対応、シーケンス図・クラス図はCould(必要になればStage 4以降で検討)。
  > **[Phase 14 で確定 ── 〈アクティビティ図を実装しない〉]** 当初〈Stage 3後半(旧Phase 14)でアクティビティ図をShould対応する予定〉→ 撤回。理由〈ステージ3はPhase 13で終了した([実装計画書](implementation_plan.md) 4.1節)。振る舞いのビューは、ステージ4の詳細設計モードで「番号付きの手順」(2.7節)として扱う〉。
* **生成トリガー**: SCR-005に新設する「設計図を生成する」ボタン。4文書生成後、ユーザーが明示的に押下した時点でAIが意味モデルを生成する(SCR-004の「ヒアリング完了→承認→生成」と同じ操作パターン)。
* **生成対象の選択と非同期生成(Phase 10で確定)**:
  * 生成は非同期で行う。受け付け後、画面は生成状態(`generating`/`completed`/`failed`)をポーリングで表示する。
  * コンポーネント図とER図は、プロジェクトに1枚ずつ生成する。ER図のテーブルが30件を超える場合は、ユーザーが対象のテーブルを選び、グループ名を付けて部分図として生成する。
  * DFDは、内部設計書の「処理別データフロー」節に列挙された処理(APIエンドポイント/バッチ)から選んで生成する。個別に1件ずつ生成するボタンと、チェックボックスで最大5件をまとめて生成する操作の両方を用意する。
  * 同じ対象を再生成すると、既存の図を上書きする。
  * 図の数には上限を設けない。AIの利用上限(無料枠)やトークン上限で生成が止まった場合は、生成履歴に対象ごとの結果を表示する。表示するのは、止まった理由と再度の生成指示が必要なことである。クォータ超過の後に残った対象は「未着手」として表示する。
  * 内部設計書が旧形式(「処理別データフロー」節が無い)の場合は、DFDの候補が表示されない。このときは内部設計書の再生成を促す。
* **レビュー画面(SCR-007)**: React Flowによるプレビュー。ノード移動・要素編集・自動レイアウト(再実行可)に対応する。手動移動後の辺は折れ点を持たず、smoothstepでの描画に委ねる。
* **状態遷移**: `draft → reviewing → approved → exported`。approved後に編集すると`reviewing`へ戻る。
  * **具体化(Phase 12で確定)**:
    * 保存(座標だけの保存を含む)と自動レイアウトの実行で、どの状態からでも`reviewing`になる。
    * 承認は`draft`・`reviewing`から行える(AIの出力を手直しせずに承認できる)。
    * 図のダウンロード(出力)に成功すると`exported`になる。AIで再生成すると`draft`に戻る。
  * **承認の条件**:
    * 画面で見ていた版であること(他で更新されていれば競合として再読み込みを促す)。
    * 全要素の配置があること(無ければ自動レイアウトの実行を促す)。
    * 検証エラーが無いこと(エラーの一覧を検証パネルに表示する。警告は承認を妨げない)。
    * 未保存の変更がある場合、承認ボタンは「保存して承認」となり、保存してから承認する。
  * 承認済みの図には、「保存するとレビュー中に戻る(承認し直しが必要)」旨を常に表示する。
* **承認・エクスポート**: 承認後、決定的(AI非依存)なdraw.io GeneratorがXMLを生成し`.drawio`としてダウンロードできる。同一エンジンがSVGも同時出力する。
  * **具体化(Phase 12で確定)**:
    * 出力は承認済み・出力済みの図だけで、未保存の変更があるときは出力できない。
    * 辺ラベル(ERの多重度、DFDのデータ項目名)はレビュー画面と同じ文言で描く。
    * 手動移動した辺は、draw.ioでは`orthogonalEdgeStyle`に経路を任せ、SVGでは簡易な直交経路で描く。
    * レーン帯は描かない(レビュー画面と同じ)。
    * 出力ボタンの隣に、「ダウンロードしたファイルを直接編集しても、Devexには反映されない」旨を表示する(D6)。
* **内部設計書への反映**: 承認済みの図とその要素表を、内部設計書の該当セクション([内部設計書](internal_design.md) 3.2節・3.3節、アンカーコメントで位置を特定)にプレビュー時点でSVGとして差し込む。ダウンロードはMarkdown+図ファイル(SVG/drawio)のzip形式にする。エクスポート後にユーザーがファイルを直接編集した場合、その変更はDevexに反映されない旨を画面上に明示する(draw.ioの再インポートは対象外)。
  * **具体化(Phase 13で確定)**:
    * 図を承認すると、同時に内部設計書の表示中の版へ要素表が反映される(版は増えない)。文書の再生成・復元で反映が消えた場合は、文書画面(内部設計のタブ)の「図を再反映」で戻す。承認済みの図のうち反映されていないものの件数を表示する。
    * プレビューでは、承認済みの図だけ画像を表示する。承認後に編集中(レビュー中)の図は画像を出さず、要素表が前回承認した内容であることを示す。
    * 図が内部設計書の古い版から生成されている場合、プレビューと設計図の一覧(SCR-007の一覧)に、再生成を促す表示を出す。
    * 「図付きでダウンロード(.zip)」のzipには、内部設計書のmd(図ファイルへの相対リンク入り)と、文書に反映済みの図のSVG・drawioが入る。zipに入れた図は`exported`になる。
* **図の手直しの反映**: 承認済みの図の変更を、AIが基本設計・内部設計(散文)への修正案(差分)として提示し、ユーザーが承認して反映する(Should、Phase 13b)。
  > **[Phase 14 で確定 ── 〈図の手直しの反映(M9b)を実装しない〉]** 当初〈Phase 13bで実装する予定〉→ 撤回。理由〈詳細設計モード(2.7節)では文書を承認済みの意味モデルから組み立てるため、図の変更を散文へ戻す修正案はほぼ不要になる。ステージ3はPhase 13で終了した〉。

## 2.7 詳細設計モード(ステージ4)

要件定義・外部設計の後に、段階ごとに人が承認しながら詳細設計書を組み立てるモード。構想は[`appendix/detailed-design-mode-organization.md`](../appendix/detailed-design-mode-organization.md)、決定の経緯は[`textbook/Phase-14/Phase-14-1.md`](../textbook/Phase-14/Phase-14-1.md)参照。段階の中身(意味モデル・API)の詳細は各段階の実装Phaseで確定する。

* **2つのモード(作成時に選ぶ。Phase 14で確定)**: SCR-002の「新規プロジェクト作成」を押すと、モード選択ダイアログが開く。選んだモードはプロジェクトに記録し(`projects.mode`)、作成後は変えない。
  * **簡易ドキュメントモード**(旧称「概要モード」。今の動き): チャット → 4文書を一括生成。
  * **詳細設計モード**: チャット(同じヒアリング) → 要件定義・外部設計の2文書だけを生成(自己診断つき) → 段階1〜6を順に作って承認 → 段階7 実装計画。
* **段階**(章と段階は1対1。正本は各段階の意味モデルで、文書はそこから組み立てる):

| 段階 | 詳細設計書の章 | 入力 | AIの役割 |
| :--- | :--- | :--- | :--- |
| 1 | 01 機能(処理)一覧(処理ID `F-01`…/名称/種別/トリガー/関連画面/機能グループ/概要) | 外部設計の画面一覧(2.2)・API一覧(2.6。Phase 16で外部設計書に追加) | 下書き → 人が確定。機能グループはAPIのリソース名から初期値を決定的に作り、人が確定する |
| 2 | 02 データフロー(機能グループごとのDFD・データ辞書・処理概要表(入力/処理/出力)) | 1 + 要件定義 | 下書き → 人がレビュー。DFDを描く機能グループは人が選ぶ(単純な処理は処理概要表の1行で済ませる) |
| 3 | 03 データモデル(ER・テーブル定義・CRUD図) | 2のデータストア・データ辞書 | ERは下書き。CRUD図は、R(読み)とW(書き)をDFDの線の向きから決定的に作り、W の C/U/D の区別と、DFDに描いていない処理の分はAIが下書きして人が確定する |
| 4 | 04 ソフトウェア構造(構成図(層)・モジュール一覧(パス/層/責務/主な依存先/関わる処理)) | 1〜3 + 技術スタック | 下書き → 人がレビュー |
| 5 | 05 主要処理の手順(人が選んだ処理だけ) | 4 + 2 | 人が対象を選び、AIが下書き |
| 6(任意) | 06 処理ロジックの詳細(人が選んだ関数だけ) | 5 | 同上 |
| 7 | 実装計画 | 全体 | 現行と同じ生成 |

* **段階の進め方(Phase 14で確定)**:

```
[新規プロジェクト作成] → [モード選択ダイアログ] ─┬─ 簡易ドキュメント → SCR-003 → SCR-004 ヒアリング → 4文書を一括生成 → SCR-005
                                                └─ 詳細設計 ──────→ SCR-003 → SCR-004 ヒアリング(同じ) → 要件定義・外部設計を生成
                                                     → SCR-005 で確認 →「詳細設計へ進む」→ SCR-008 詳細設計画面

SCR-008: 左に段階のステッパー 1〜7(状態: 未着手 / 下書き / 再生成済(未承認) / レビュー中 / 承認済み / 古い)、右に選んだ段階の作業領域

各段階の共通サイクル:
  [下書きを生成](AI。入力は前の段階の承認済みの成果物)
    → レビュー・編集(表は表の編集、図は SCR-007 のエディタを再利用)
    → [承認](検証が通ること) → 次の段階が開く

  段階1 機能一覧    : AI が外部設計の API・画面から処理ID を下書き。機能グループはリソース名から初期値 → 人が確定
  段階2 データフロー: DFD を描く機能グループを人が選ぶ → グループごとに DFD・データ辞書・処理概要表を下書き → レビュー
  段階3 データモデル: ER・テーブル定義を下書き。CRUD の R/W は DFD から自動、C/U/D は AI の下書き → 人が確定
  段階4 構造        : 構成図(層)とモジュール一覧を下書き → レビュー
  段階5 手順        : 手順を書く処理を人が選ぶ → 下書き → レビュー(索引・関与表・タブ)
  段階6 処理ロジック: (任意)05 の手順の行から関数を選ぶ → 下書き → 承認。またはスキップ
  段階7 実装計画    : 要件定義・外部設計と承認済みの段階を入力に生成

前の段階を直して承認し直す → その段階を入力にしている後ろの段階に「古い」を表示
  → 人が「再生成」するか、「このまま承認し直す」を選ぶ
```

  * 詳細設計書(HTML+md+図のzip)は、承認済みの段階から組み立てる。いつでもダウンロードでき、未承認の章は「未承認」と表示する(Phase 22で確定)。段階を0件で承認して飛ばした段階6の06章は「省略」と表示する。
  * **ダウンロードの操作(Phase 22で実装)**: SCR-008 の見出しの下に「詳細設計書をダウンロード(.zip)」を置き、隣に段階1〜6のうち未承認の件数(未承認の段階の章は「未承認」と書かれること)を示す。出力ボタンと同じく、ダウンロードしたファイルを直接編集しても Devex には反映されない旨を表示する(D6)。zip の中身は`detailed_design.html`・`detailed_design.md`・`diagrams/`(載せた図の SVG・drawio)。07 横断事項は Phase 22 では出さない(Phase 23 で決める)。
  * **外部設計書のAPI一覧(Phase 16)**: 生成する外部設計書に「2.6 API一覧」(メソッド/パス/概要/関連画面の表)を足す。簡易ドキュメントモードでも同じ。段階1の機能グループの初期値はこの表のパスから作り、下書きに漏れたAPIは警告で知らせる。
  * **段階1の種別(Phase 16)**: API / API+バッチ / バッチ / 画面 / その他。「画面」はサーバーを呼ばずに画面の中で完結する非自明な演算・描画で、AIは外部設計書2.3の画面仕様から下書きする。
  * **状態「再生成済(未承認)」(Phase 16)**: 内容のある段階の下書きを作り直すと、ステッパーの状態は「再生成済(未承認)」になる。作り直した時点の入力を記録するので「古い」は消え、その後に入力が変わればまた「古い」になる。
  * **段階1の作業領域(Phase 16で実装)**: 「下書きを生成する」(内容があるときは「下書きを作り直す」。押すと確認ダイアログを出し、処理IDと確定した機能グループはトリガーが同じ行に引き継ぐこと・保存していない編集が失われること・承認がやり直しになることを示す)。生成中は一覧をポーリングし、失敗したら理由を出す。機能グループは追加・改名(その行も付け替わる)・削除(処理が残るグループは削除できない)ができ、機能一覧の表は行ごとに名称・種別・トリガー・関連画面・機能グループ・概要を編集し、行を追加・削除できる(処理IDは画面でも振り直さない)。保存した内容の検証の結果(エラー・警告)を表示し、エラーがある間・保存していない編集がある間は承認できない。
  * **段階2の作業領域(Phase 17で実装)**: 上から、DFD を描く機能グループの選択(段階1の機能グループのチェックボックス。5つまで。初期値は空)・下書きの生成・機能グループの DFD のタブ・データ辞書の表・処理概要表・検証の結果の順に並べる。
    * 生成は、グループの選択を保存してから行う(保存していない編集がある間は押せない)。1回の生成で、全処理の処理概要表と、選んだグループの DFD を作る。処理概要表があるときは「下書きを作り直す」になり、確認ダイアログで、グループの選択は残ること・DFD の手直しが失われ DFD の承認がやり直しになることを示す。
    * DFD のタブは、選んだ(保存済みの)グループごとに1つ。SCR-007 の図のエディタ(保存・自動レイアウト・検証・要素の編集・承認)をそのまま使い、開くのは選んだタブの1枚だけ。DFD の処理の箱は段階1の処理ID(「F-06 名称」)。生成中は DFD とデータ辞書を編集できない。生成中は、生成ボタンを「生成中」にし、データ辞書の表の場所と処理概要表の空欄にも「生成中」と出す。
    * データ辞書の表は、名前とフィールド(「名前:型」を「,」で区切る)を行ごとに編集・保存・削除する(削除は確認する)。
    * 処理概要表は、段階1の処理ごとに1行(処理ID・名称・機能グループは表示だけ、入力・処理内容・出力を編集)。DFD を描かない処理も、この1行で済ませる。
    * 承認の条件(検証のエラー): 全処理に処理概要表の行がある・選んだグループの DFD がすべて承認済み、など。DFD のエディタやグループの選択・処理概要表に保存していない編集がある間も承認できない。DFD の未承認は検証の結果の一覧には常に出さず、段階の承認を押したときに理由として出す(Phase 18 の画面確認後に変更)。
    * 承認済みの段階2の DFD(保存・自動レイアウト)やデータ辞書を直すと、段階2は「レビュー中」に戻る(段階3に「古い」が伝わるように)。
  * **段階3の作業領域(Phase 18で実装)**: 上から、下書きの生成・ER・テーブル定義の表・CRUD 図・保存・検証の結果の順に並べる。
    * 生成は、1回で ER(テーブル定義を含む)と CRUD 図を作る。CRUD 図に保存していない編集がある間は押せない。内容があるときは「下書きを作り直す」になり、確認ダイアログで、ER の手直しと CRUD 図で確定したセルが失われ、ER の承認がやり直しになることを示す。生成中は ER・CRUD 図を編集できず「生成中」と出す。
    * ER は全体1枚で、SCR-007 の図のエディタ(保存・自動レイアウト・検証・要素の編集・承認)をそのまま使う。テーブル定義の列の制約・説明とテーブルの説明は、このエディタの属性パネルで直す。
    * テーブル定義の表は、ER(エディタで編集中の内容)から組み立てる表示だけ(列/型/PK/FK/NULL可/制約/説明)。
    * CRUD 図は、行が段階1の処理、列が ER のテーブル。セルに C・R・U・D を書く(並びは自動で C→R→U→D)。DFD の線から決まるセルは青い枠で示し、読みの R は外せない。AI の下書きのセルは黄色で示し、人が書き換えると確定になる。残りの下書きは段階3の承認でまとめて確定する。
    * 承認の条件(検証のエラー): ER が承認済み・CRUD 図が DFD の線と食い違わない(読みの線に R、書き込みの線に C/U/D)など。ER のエディタや CRUD 図に保存していない編集がある間も承認できない。ER の未承認は検証の結果の一覧には常に出さず、段階の承認を押したときに理由として出す。
    * 承認済みの段階3の ER(保存・自動レイアウト)を直すと、段階3は「レビュー中」に戻る(段階4に「古い」が伝わるように)。
  * **段階4の作業領域(Phase 19で実装)**: 上から、下書きの生成・構成図・モジュール一覧・保存・検証の結果の順に並べる。
    * 生成は、1回で構成図(パッケージ単位の箱と層のレーン)とモジュール一覧(ファイル単位)を作る。入力は要件定義の技術スタックと、承認済みの段階1〜3(機能一覧・処理概要表・ER のテーブル・CRUD 図)。モジュール一覧に保存していない編集がある間は押せない。内容があるときは「下書きを作り直す」になり、確認ダイアログで、構成図とモジュール一覧の手直しが失われ、構成図の承認がやり直しになることを示す。生成中は構成図・モジュール一覧を編集できず「生成中」と出す。
    * 構成図は全体1枚で、SCR-007 の図のエディタ(保存・自動レイアウト・検証・要素の編集・承認)をそのまま使う。層は要素の「layer」で、図のレーンになる。
    * モジュール一覧は、行ごとにパス・層・責務・主な依存先・関わる処理を編集し、行を追加・削除する。層は構成図(エディタで編集中の内容)の層から選び、構成図に無い層は「(構成図に無い)」と添えて残す。主な依存先と関わる処理(処理ID)は「,」で区切る。全処理が通るモジュール(アプリの組み立て・認証・例外の変換など)は「全処理」にチェックを入れる。同じパスの行には「パスが重複しています」と出す。
    * 承認の条件(検証のエラー): 構成図が承認済み・モジュールが1件以上・パスが空でなく重複しない(段階5の手順の呼び出し先と関与表の列の鍵になるため)・関わる処理の処理IDが機能一覧にある。警告: 責務が空・層が構成図に無い・どのモジュールにも現れない処理(「全処理」の行は数えない)・一覧に当たるモジュールが無い依存先(依存先はディレクトリ(`app/services`)や短い書き方(`services/auth`)でもよく、「/」の区切り単位で照らす。Phase 19 の画面確認後に変更)。構成図やモジュール一覧に保存していない編集がある間も承認できない。構成図の未承認は検証の結果の一覧には常に出さず、段階の承認を押したときに理由として出す。
    * 承認済みの段階4の構成図(保存・自動レイアウト)を直すと、段階4は「レビュー中」に戻る(段階5に「古い」が伝わるように)。
  * **段階5の作業領域(Phase 20で実装)**: 上から、手順を書く処理の選択(段階1の処理のチェックボックス)・下書きの生成・索引・処理 × モジュールの関与表・処理ごとの手順のタブ・保存・検証の結果の順に並べる。
    * 生成は、処理の選択を保存してから行う(保存していない編集がある間は押せない)。生成は処理ごとに LLM を1回呼ぶ。「手順の無い処理の下書きを生成する(N件)」は、保存した選択のうち手順の無い処理をまとめて下書きする(1回5件まで。6件以上はタブごとに生成する)。タブの「この処理の手順を作り直す」は、その処理だけを作り直す(確認ダイアログで、その処理の手順の手直しが失われること、選定理由と他の処理の手順は残ることを示す)。手順の無い処理のタブは「この処理の下書きを生成する」になる。生成中は手順の表を出さず「生成中」と出す。
    * 手順の表は、行ごとに呼び出し元・呼び出し先・関数・渡すデータ・処理内容・結果・DB 操作・分岐・例外を編集し、行を足す・消す。分岐の行は、その手順の「分岐」ボタンで足し(条件と結果だけを書く)、手順の行を消すと付いている分岐の行も消える。番号は並び順から振り直す。呼び出し先は段階4のモジュール一覧のパスと外部の役者(利用者など)を候補に出し、一覧に無いパスと空の呼び出し先には印を出す。処理ごとに選定理由と注記(トランザクションの範囲など)を書く。
    * 索引(処理ID/名称/トリガー/選定理由/手順数)と関与表(列は段階4のモジュール一覧のパスのうち呼び出し先に現れるもの、セルは手順番号)は、編集中の内容から作る。
    * 手順のある処理の選択を外すときは確認する(外すとその処理の手順も消える)。
    * 承認の条件(検証のエラー): 処理が1つ以上選ばれている・処理IDが機能一覧にあり重複しない・どの処理にも手順がある・先頭の行が分岐でない・呼び出し先が空でない・パスの形(「/」を含む)の呼び出し先がモジュール一覧のパスと完全一致する(関与表の列の鍵のため)。警告: 選定理由が空・モジュールを呼ぶ手順の関数が空(段階6でその手順の関数を選べないため)。保存していない編集がある間も承認できない。
  * **段階6の作業領域(Phase 21で実装)**: 段階6は任意の段階である。上から、保存と「段階6を飛ばす」・段階5の処理ごとのタブ(タブの中に候補の選択・タブの生成・逆引き・詳細)・保存と「段階6を飛ばす」・検証の結果の順に並べる(Phase 21 の画面確認後に、処理ごとのタブにし、段階全体の生成ボタンをなくした)。
    * 関数の候補は、承認済みの段階5の手順のうち、呼び出し先がモジュール(パス)で関数が空でない行の(呼び出し先, 関数)。同じ組を呼ぶ手順は1つにまとめ、呼ぶ手順の手順ID(`F-01#2`)をバッジで添える。詳細のある関数を外すときは確認する。
    * 候補と詳細は、段階5の処理ごとの外側のタブで切り替える。タブの中の候補は、その処理の手順から呼ばれる関数。2つ以上の処理から呼ばれる関数は、呼ぶ処理すべてのタブに「共通」の印を付けて出し、他の処理の手順のバッジは色を落とす。どのタブで選んでも編集しても同じ1件である。選んだ関数には「生成済」か「未生成」を出す。タブごとに「このタブの未選択をすべて選ぶ」(生成済には影響しない)と生成のボタンを置く。生成のボタンは、タブにチェック済みの未生成があって保存していなければ緑の「生成前に保存する」(他の保存と同じ動き)、保存済みなら緑の「このタブの未生成を生成する(N件)」(1回5件まで。6件以上は先頭の5件で、残りを案内する)、未生成が無ければグレーで押せない「このタブの未生成を生成する(0件)」にする。段階5を直して呼ばれなくなった関数は「呼ばれていない関数」のタブに残し、外せるようにする。チェックは「06 に載せる関数」の意味で、生成の対象ではない(Phase 21 の画面確認後に確定)。
    * 生成は段階5と同じ形にする。選択を保存してから行い、関数ごとに LLM を1回呼ぶ。まとめての生成は処理のタブ単位(上記)で行い、関数のタブの「この関数の詳細を作り直す」はその関数だけを作り直す(確認ダイアログで、その関数の詳細の手直しが失われ、他の関数の詳細は残ることを示す)。
    * 詳細は、シグネチャ/引数/戻り値/例外/事前条件/事後条件の表と、番号付きの擬似フロー(段ごとに下位の箇条を1行1つで書く)。外側の処理のタブの中で、その処理から呼ばれる選んだ関数を内側のタブで切り替える(二重のタブ)。L-ID は保存せず、選んだ関数の全体の並び(段階5で最初に呼ばれた順)から振る。
    * 「段階6を飛ばす(06を書かない)」は、確認ダイアログの後に0件を保存して段階6を承認する(選んだ関数があれば消える)。承認の完了ダイアログは他の段階と同じ。飛ばした段階6は「段階6は飛ばしました(06 章は「省略」になります)」と出す。関数を選び直して保存すれば作業を続けられる(Phase 21で確定。段階7の入力に段階6の承認が要るため、飛ばした状態も承認済みにする)。
    * 05↔06 のバッジは段階をまたいで移る(Phase 21で確定)。段階5の手順の表で、段階6に詳細がある手順(呼び出し先と関数が一致する行)の「処理内容」の下に「詳細 L-02 ↓」を出し、押すと段階6のその関数のタブを開いて枠で強調する。段階6の「呼ばれる手順」のバッジを押すと、段階5のその処理のタブを開いて手順の行を強調する。段階5から段階6へ移るときは、その関数を最初に呼ぶ処理のタブで開く。保存していない編集があるときは、移る前に「保存していない編集は失われます。」と確認する。
    * 承認の条件(検証のエラー): モジュール・関数が空でない・(モジュール, 関数)が重複しない・段階5のどれかの手順から呼ばれている・詳細がある(シグネチャか擬似フロー)。警告: 事前条件・事後条件が空。0件はエラーにしない(飛ばす操作)。保存していない編集がある間も承認できない。
  * 段階の作業領域の保存(Phase 21 の画面確認後): 段階1〜6の表の保存ボタン(と段階6の「段階6を飛ばす」)は、作業領域の先頭(状態表示の直下)と最下部の両方に置く。選択や編集の後に、スクロールせずに保存して生成へ進めるようにするため。図のエディタ(DFD・ER・構成図)の保存は、エディタの中のボタンのまま。
  * 段階の画面の骨格(Phase 15で実装): 左のステッパーは段階1〜7を状態の色とラベルで並べ、押すとその段階を選ぶ。最初は、まだ承認されていない最初の段階を開く。右の作業領域は、全段階に共通の部分として、状態・足りない入力(「段階1(機能一覧)の承認」「外部設計書」)・古い表示・承認ボタン(古い段階では「このまま承認し直す」)を持つ。承認できたら、ダイアログで「段階N-{段階名}を承認しました。」と知らせ、「次の段階へ進む」で次の段階を開く(「閉じる」で留まる。段階7は「閉じる」だけ。Phase 18 の画面確認後に追加)。段階ごとの下書きの生成・編集の画面は、各段階の実装Phase(16〜21)で足す。
* **段階の承認と陳腐化**: 段階ごとに「下書き → レビュー中 → 承認」を持ち、承認した段階だけが次の段階の入力になる。前の段階を承認し直すと、その段階を入力にしている後ろの段階に「古い」表示を出す。作り直しは自動では行わず、人が「再生成」を押す(段階の依存関係がそのまま陳腐化の伝わる道筋になる)。
* **05 主要処理の手順(Phase 14で確定)**:
  * 手順の表の列は `No / 呼び出し元 → 呼び出し先 / 渡すデータ / 処理内容 / 結果 / DB 操作 / 分岐・例外` の7列。分岐はサブ番号(`4a`)で、元の手順の直後に置く。
  * 手順IDは処理IDと手順番号の組(`F-01#4`、分岐は`F-01#4a`)で、文書全体で一意にする。
  * 章の冒頭に「索引」(処理ID/名称/トリガー/選定理由/手順数/紐づく06の項目)と、「処理 × モジュール」の関与表(CRUD図と同じ格子。セルは手順番号)を置く。
  * 処理ごとの手順はタブで切り替える(件数が増えても縦に長くならない)。
* **06 処理ロジックの詳細(Phase 14で確定)**:
  * 1項目はL-ID(`L-01`…)を持つ関数1つで、シグネチャ/引数/戻り値/例外/事前条件/事後条件の表と、番号付きの擬似フローを書く。L-IDは保存せず、項目の並び順から振る(Phase 21で確定。紐づけは(モジュール, 関数)なので、振り直しても切れない)。
  * 05の手順の行のうち06に詳細があるものは、「処理内容」の下に「詳細 L-02 ↓」のバッジを付ける(列は7列のまま)。06に詳細があるかは、手順の(呼び出し先, 関数)と06の項目の(モジュール, 関数)が一致するかで決める(Phase 20で確定。手順の行にL-IDを持たせない)。06の各項目の見出しの下には「呼ばれる手順」(`F-01#4`・`F-05#5`)のバッジを置く。バッジを押すと相手側のタブへ切り替えて、その行・項目へ移り強調する。
  * 章の冒頭に「逆引き」(L-ID/関数/モジュール/呼ばれる手順)を置く。1つの関数が複数の処理から呼ばれることが一目で分かる。
  * 06も関数ごとのタブで切り替える。
  * 見せ方の見本は、devex-uiのデモページ`/detailed-design-demo`(仮データ)。レビュー画面はこの見せ方を採用する。
* **詳細設計書の出力(Phase 14で確定、Phase 22で実装)**: zipで、次の3種類をまとめて出力する。
  * **HTML(読む用)**: 自己完結の単一ファイル(CSS・スクリプトを中に持ち、外部を読み込まない)。レビュー画面と同じタブと双方向のリンクを持ち、ブラウザで開けばリンクが必ず動く。スクリプトが無効でも、全件を並べて表示しアンカーで飛べる。図はSVGを中に入れる。
  * **Markdown(差分・AIへの入力用)**: リンクと生のHTMLを持たず、IDを本文に書くだけ(「→ 詳細: L-02」「呼ばれる手順: F-01#4」)。図はzipの中のSVGを相対パスの画像で載せる(ステージ3のzipと同じ。章の間のリンクではない。Phase 22)。生のHTMLのアンカー(`<a id>`)は多くのmdビューワーやDevex自身のプレビュー(react-markdown、`rehype-raw`なし)で消えて飛ばず、日本語の見出しから作る自動アンカーはビューワーごとに作り方が違うため。
  * **図ファイル**: SVG・drawio(ステージ3の出力エンジンを再利用する)。
* **シーケンス図**: 当面は作らず、05の番号付き手順で扱う。シーケンス図へ進むかは、ステージ4の運用の後に判断する(D7はCouldのまま)。
