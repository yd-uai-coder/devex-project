# 外部設計書：Devex

## 2.1 システム構成概要

Devexは、モダンなWeb技術スタックを用いて構築される対話型ドキュメント自動生成システムです。ユーザー（フロントエンド）からのリクエストを受け、AIによる高度な要件ヒアリングとドキュメント生成をセキュアに処理します。

```
[ ユーザー (ブラウザ) ]
       │
       ▼ HTTPS (JWT認証)
[ フロントエンド: Next.js (SSR / SPA) ]
       │
       ▼ REST API / SSE (ストリーミング)
[ バックエンド: FastAPI + LangChain ]
       ├── (プロンプト制御・非同期処理)
       ├── [ 外部LLM API (Gemini Flash-Lite) ]
       │
       ▼ SQL (ORM)
[ データベース: PostgreSQL (セッション・履歴・ドキュメント永続化) ]
```

* **フロントエンド層 (Next.js)**: ユーザーインターフェースを提供。SSR（サーバーサイドレンダリング）による高速な初期表示と、チャット画面でのスムーズなクライアントサイド・インタラクションを実現。

* **バックエンド層 (FastAPI + LangChain)**: 業務ロジック、LLMとの連携、プロンプト管理を担う。LangChainを用いたエージェント制御により、ユーザーとの対話履歴を踏まえた適切なヒアリングと、構造化されたMarkdown生成を統御。非同期処理によりタイムアウトを防止。

* **データ層 (PostgreSQL)**: ユーザーアカウント情報、チャットセッション、対話履歴、生成された各設計書（要件定義、外部設計、内部設計、実装計画）を永続化。

## 2.3 主要画面のUI/UX仕様

### SCR-004: チャットヒアリング画面

本画面は「初期ヒアリング入力」→「チャット」の2段構成とする。初期入力の段階でユーザーに明確な設計・構想を求めすぎないこと、要件・設計は最終的にAIが判断してユーザーの承認を経てドキュメント化することを重視し、フォームは必要最小限に絞る。

* **初期ヒアリング入力(チャット開始前)**:
  * **プロジェクト名**(必須・1行): ダッシュボードの一覧・チャット画面のヘッダー・設計書の表題に使う短い名前。前後の空白を除いて**1〜40文字**(ゴール3後の調整。以前はシステム概要の全文を名前にしていたため、表題が長くなった)。
  * **システム概要**(必須・自由記述): 1行〜数行のtextarea。プレースホルダ例「作りたいものを一言で教えてください」。最大**全角200文字**。
  * **実現したいこと**(必須・自由記述): 複数行のtextarea。プレースホルダで「箇条書き推奨(改行区切りでOK)」と軽く示唆するが、フォーマットは強制しない。バリデーションは「空でないこと」+最大**全角80文字**。箇条書きへの分解・構造化はこの画面では行わず、後続のチャットでAIが行いユーザーに確認する。
  * **補足**(任意・自由記述): 「欲しい機能」「その他」を1項目に統合したtextarea。最大**全角400文字**。この時点でリストや選択肢を作らせない。AIによる機能提案はフォームではなくチャット内で行う(会話の中でAIが候補を挙げ、ユーザーが同意・修正する)。
  * **環境設定**(任意・折りたたみ、ネイティブ `<details>/<summary>` を推奨): 見出しに「未入力の場合はAIにおまかせします」と明記し初期状態は閉じておく。言語・フレームワーク・DB・デプロイ環境の4グループはいずれも複数選択(チェックボックス群)。フレームワークは言語ごとに `<fieldset><legend>` で静的にグルーピングして示す(「言語を選ぶとフレームワークの選択肢が動的に絞り込まれる」ような動的コンボボックスは作らない)。SCR-003でテンプレートを選択している場合、そのテンプレートの`default_environment`([内部設計書](internal_design.md) 3.2節`prompt_templates`)を初期値としてプリフィルする(ユーザーは編集可能)。
  * **参考資料のアップロード**(任意・最大3ファイル): 対応形式は **txt・Markdown・PDFのみ**(ファイル選択ダイアログの`accept`属性・ドロップ領域の案内文の双方で明示する)。Word/Excel/PowerPointは非対応であり、案内文で「図を含む資料はPDFに変換してからアップロードしてください」と促す。アップロード済みファイルは一覧表示し、ファイルごとに削除ボタンを設ける。対応形式外・サイズ超過・4件目以降の選択はクライアント側で即座に弾き、`aria-invalid`/`aria-describedby`/`role="alert"`でエラーを提示する(2.5節5項のバリデーションルール・エラーコードと対応させる)。送信後のテキスト化に失敗したファイルがあってもヒアリング自体はブロックせず、失敗した旨を軽微な通知として示す。
  * 送信すると `POST /api/v1/projects`(`multipart/form-data`。初期ヒアリング入力の各項目+添付ファイル最大3件。[内部設計書](internal_design.md) 3.3節参照)でプロジェクトを作成し、以降はチャット画面へ遷移する。
  * **アクセシビリティ**: 各入力欄のエラー表示には `aria-invalid` / `aria-describedby` / `role="alert"` を必ず配線する。折りたたみ・グルーピングも上記のとおりネイティブ要素・セマンティックHTMLを優先する。

* **チャット画面構成**:
  * **ヘッダー**: プロジェクト名、現在のステータス(ヒアリング中 / 生成中 / 完了 / 修正中)、ダッシュボードへの戻るボタン、ドキュメント生成ボタン(手動トリガー)。ステータスが完了または修正中の場合は、生成済みドキュメントへの常設リンクを画面内に配置する(自動的にドキュメントプレビュー画面へ遷移させることはしない。「チャットに戻る」操作が必ずしも「今の内容を修正したい」を意味するとは限らないため)。
  * **メインエリア(チャット履歴)**: ユーザーのメッセージ(右側吹き出し)とAIからのメッセージ(左側吹き出し、Markdown対応、ストリーミング出力)。チャット開始直後、AIの最初の発話は初期ヒアリング入力の内容を踏まえた理解の要約と確認質問から始まる。
  * **フッター(入力エリア)**: テキスト入力欄(複数行対応)、送信ボタン、ファイル添付(将来拡張用としてUIのみ、または無効化)。

* **主要なアクション**:
  * ユーザーがテキストを入力し送信すると、LLMからのストリーミング応答がリアルタイムで描画される。
  * **応答の途中の失敗(Phase 15)**: AIの利用上限などで応答が途中で失敗した場合は、失敗の理由と「送信したメッセージは保存されていない」ことを表示し、送ったメッセージの表示を取り消す(再送を促す)。接続が切れただけの場合は、メッセージを残したまま「接続が切れました」を表示する。
  * AIは以下(1)〜(4)を満たした場合(環境設定が未入力の場合は(5)も)、「十分な要件が揃いました」と判断する: (1)目的・課題が明確、(2)コア機能が最低1つ以上「誰が・何を・なぜ」のレベルで具体化、(3)想定ユーザー像の把握、(4)MVPスコープ(今回作る/作らない)の認識合わせ、(5)技術的な強い制約・希望の有無の確認。十分と判断した際は、即座に生成へ進まず、まず構造化した要件サマリをチャット上に提示しユーザーの明示的な承認を求める。
    > **ステージ6で置き換えた(Phase 33 で決定、Phase 34 で実装)**: 5条件の判定は、観点の表に置き換えた(5条件の判定は、観点の表を持たない以前のプロジェクトの表示にだけ残る)。ベースラインで、LLM が「未達」と書いた条件を聞かないまま「十分」と判定し、非機能・技術スタックが聞かれなかったため。観点の表で状態と根拠を持ち、完了はコードが判定する(2.9節)。
    * **判定とサマリの出し方(ゴール3後の調整)**: 判定はユーザーの発言のたびに、AIが返信する前に行う。十分なら、AIの返信の代わりに、その判定の要件サマリと「この内容でよければ『この内容で設計書を生成する』を押してください」をチャットに出し、同時に画面に生成の欄(ボタン)を出す。足りなければ、不足した観点をAIに渡して、そこを質問させる。ヒアリングのAIは、確定の確認・サマリ・設計書の本文をチャットに書かない。以前は、判定(返信の後に別に呼ぶ)とAIの返信が互いを知らずに動いたため、AIがまだ質問を続けているのにボタンが出たり、ボタンが出ていないのにAIがチャットで確定を求めたりした。生成の欄は、まとめがチャットに出るので、サマリを繰り返さない。承認後(またはユーザーが手動で「設計書を生成する」ボタンを押下した際)、確認ダイアログ(生成には数分かかり、その間はチャットを送れない)で確定してから、ローディングインジケーターを表示し、生成処理(SCR-005へ遷移)へ移行する。ボタンは押した時点で無効にする(二度押しの防止。Phase 15)。詳細設計モードのプロジェクトでは、生成するのは要件定義・外部設計の2文書である。
  * **生成完了後の自己診断**: 4文書の生成が完了すると、AIはそれらを対象に自己診断(不足・不明瞭な点の洗い出し)を行い、指摘事項を「最重要/中程度/軽微」の3段階に分類してチャットに提示する(`sender='others'`の`chat_histories`行として記録。[内部設計書](internal_design.md) 3.2節参照)。ユーザーは各指摘についてチャットで回答するか、現状のまま確定するかを選べる。回答内容を反映して再生成すると、新バージョンとして保存される([内部設計書](internal_design.md) 3.2節「バージョニング方針」)。

## 2.5 データ入出力仕様

### 1. ユーザー入力バリデーション (チャットメッセージ)

* **受付フォーマット**: UTF-8 テキスト文字列
* **バリデーションルール**:
  * 必須入力（空文字不可）
  * 最大文字数: 5,000文字 / 1メッセージ
  * 不正なスクリプトタグやインジェクション文字列のサニタイジング（フロント・バックエンド双方で実施）

### 2. プロンプトテンプレート選択データ (JSON、※ステージ2)

`GET /api/v1/prompt-templates`([内部設計書](internal_design.md) 3.3節)が返す一覧の1件分。

* **データ構造例**:

```json
{
  "id": "b3f1c2a0-...",
  "name": "Webアプリケーション標準",
  "target_type": "SaaS・BtoC/BtoB Webサービス",
  "system_prompt": "あなたは優秀なシステムアーキテクトです...",
  "default_environment": {
    "languages": ["TypeScript", "Python"],
    "frameworks": ["Next.js", "FastAPI"],
    "databases": ["PostgreSQL"],
    "deploy_targets": []
  }
}
```

`id`(UUID)をSCR-004送信時の`template_id`としてそのまま使う(3.3節「初期ヒアリング入力データ」参照)。

### 3. 初期ヒアリング入力データ (JSON)

SCR-004の初期ヒアリング入力(2.3節参照)を送信する際のペイロード。`name`・`system_overview`・`goals_raw` は必須(空文字不可)、他は任意。初期入力の段階では箇条書きへの分解やカテゴリ分けを求めず、自由記述のまま受け取る(構造化はチャット内でAIが行う)。

* **データ構造例**:

```json
{
  "name": "備品予約",
  "system_overview": "社内の備品予約を一元管理したい",
  "goals_raw": "誰がいつ何を予約したか一覧できるようにしたい\n予約の重複を防ぎたい",
  "notes_raw": "既存のExcel管理からの移行を想定",
  "template_id": null,
  "environment": {
    "languages": ["Python", "TypeScript"],
    "frameworks": ["FastAPI", "Next.js"],
    "databases": ["PostgreSQL"],
    "deploy_targets": ["AWS"]
  }
}
```

* **バリデーションルール**:
  * `name`: 必須・前後の空白を除いて1〜40文字。空白だけ・41文字以上は400(`INVALID_PROJECT_NAME`)。欄が無い・空のときはフォームの必須チェックで422(ゴール3後の調整)
  * `system_overview`: 必須・空文字不可・最大全角200文字・フォーマット(箇条書き等)は強制しない
  * `goals_raw`: 必須・空文字不可・最大全角80文字・フォーマット(箇条書き等)は強制しない
  * `notes_raw`: 任意(null可)・最大全角400文字
  * `template_id`: 任意(null可、※ステージ2)。SCR-003で選択したテンプレートのID。[内部設計書](internal_design.md) 3.2節②`projects.template_id`
  * `environment`: 任意(null可)。各配列は空でもよい

### 4. ドキュメントエクスポート出力仕様

* **出力ファイル形式**: Markdown (`.md`)
* **文字コード**: UTF-8 (BOMなし)
* **ファイル命名規則**: `{document_type}.md`(本プロジェクトリポジトリの`docs/`配下の実ファイル名と一致させる)
  * 例: `requirements.md`、`external_design.md`、`internal_design.md`、`implementation_plan.md`

### 5. 初期ヒアリング添付ファイル仕様

SCR-004の初期ヒアリング入力(2.3節参照)に添付する参考資料のアップロード仕様。`POST /api/v1/projects`は添付ファイルがある場合`multipart/form-data`となり、初期ヒアリング入力の各項目(3項目の3.節参照)はフォームフィールドとして、ファイルは`files`フィールドとして送信する。

* **対応拡張子/MIME**: `.txt`(`text/plain`) / `.md`(`text/markdown`) / `.pdf`(`application/pdf`)の3種類のみ。Word/Excel/PowerPoint等その他の形式は非対応。
* **バリデーションルール**:
  * 最大**3ファイル**まで(4件目以降はクライアント側で選択不可、サーバー側でも`TOO_MANY_FILES`で拒否)
  * 1ファイルあたり最大**5MB**(超過時は`FILE_TOO_LARGE`)
  * 対応拡張子/MIME以外は`UNSUPPORTED_FILE_TYPE`
* **テキスト化方式**([内部設計書](internal_design.md) 3.2節`intake_files`・3.3節参照):
  * `txt`/`md`: ファイル内容をUTF-8テキストとしてそのまま読み込む(LLM呼び出し不要)。
  * `pdf`: Gemini(既存の`app/ai/llm/gemini.py`のクライアント)にファイルをそのまま渡し、LLMのネイティブなマルチモーダル理解でテキスト化する。図・レイアウトもLLMが解釈した説明として結果に含まれる。
  * 抽出したテキストは1ファイルあたり最大**20,000文字**まで保存し、超過分は切り詰める。
  * テキスト化に失敗した場合は`FILE_EXTRACTION_FAILED`として記録するが、ヒアリング自体はブロックしない(添付は補助情報のため)。
* **保存方針**: 元ファイルの実体(バイナリ)は保持せず、抽出したテキストのみを永続化する(オブジェクトストレージ非依存)。

## 2.6 UML設計図生成・レビュー機能(ステージ3)

> **[Phase 24 で確定 ── 〈簡易ドキュメントモードの設計図(SCR-007)を提供しない〉]** 当初〈簡易ドキュメントモードの4文書生成の後に「設計図を生成する」から、内部設計書を入力にコンポーネント図・ER図・DFDを生成し、承認した図を内部設計書へ差し込む(ステージ3、Phase 7〜13)〉→ 撤回。理由〈詳細設計モード(ステージ4)が、段階2〜4で同じ図(DFD・ER・構成図)を段階の入力から作り、承認して詳細設計書に載せるようになったため、簡易モードからの設計図の作成は不要になった(Phase 24 完了後のユーザーの決定)。画面(SCR-007)・生成と履歴の API(`POST /uml/diagrams`・`/candidates`・`/generation-runs`)・内部設計書への反映(`/reflect`・`/embeds`・`/bundle`)を削除した。図の編集・検証・自動レイアウト・承認・出力の API とデータ辞書は、詳細設計モードが使うので残す。DB の`uml_generation_runs`テーブルと`uml_diagrams.scope`列は、既存のデータを残すため消していない。以前に図を反映した内部設計書のアンカー(HTML コメント)は、プレビューでは表示しない〉。


承認済みの4文書を入力に、AIがUML意味モデル(構造化JSON)を生成し、Web上でレビュー・修正した上でdraw.io/SVG形式へ出力する機能。要件整理は`appendix/stage3-requirements-organization.md`、決定事項D1〜D8は[decision digest](../textbook/decision-digest.md)参照。

* **対応する図記法**: コンポーネント図(モジュール構造)、ER図(データ構造)、処理別データフロー図(DFD。APIエンドポイント/バッチ単位)。アクティビティ図はStage 3後半(Phase 14)でShould対応、シーケンス図・クラス図はCould(必要になればStage 4以降で検討)。
  > **[Phase 14 で確定 ── 〈アクティビティ図を実装しない〉]** 当初〈Stage 3後半(旧Phase 14)でアクティビティ図をShould対応する予定〉→ 撤回。理由〈ステージ3はPhase 13で終了した([実装計画書](implementation_plan.md) 4.1節)。振る舞いのビューは、ステージ4の詳細設計モードで「番号付きの手順」(2.7節)として扱う〉。
* **生成トリガー**: SCR-005に新設する「設計図を生成する」ボタン。4文書生成後、ユーザーが明示的に押下した時点でAIが意味モデルを生成する(SCR-004の「ヒアリング完了→承認→生成」と同じ操作パターン)。
* **生成対象の選択と非同期生成(Phase 10で確定)**:
  * 生成は非同期で行う。受け付け後、画面は生成状態(`generating`/`completed`/`failed`)をポーリングで表示する。
  * コンポーネント図とER図は、プロジェクトに1枚ずつ生成する。ER図のテーブルが30件を超える場合は、ユーザーが対象のテーブルを選び、グループ名を付けて部分図として生成する。
  * DFDは、内部設計書の「処理別データフロー」節に列挙された処理(APIエンドポイント/バッチ)から選んで生成する。個別に1件ずつ生成するボタンと、チェックボックスで最大5件をまとめて生成する操作の両方を用意する。
  * 同じ対象を再生成すると、既存の図を上書きする。
  * 図の数には上限を設けない。AIの利用上限(無料枠)やトークン上限で生成が止まった場合は、生成履歴に対象ごとの結果を表示する。表示するのは、止まった理由と再度の生成指示が必要なことである。クォータ超過の後に残った対象は「未着手」として表示する。
  * 内部設計書が旧形式(「処理別データフロー」節が無い)の場合は、DFDの候補が表示されない。このときは内部設計書の再生成を促す。
* **レビュー画面(SCR-007)**: React Flowによるプレビュー。ノード移動・要素編集・自動レイアウト(再実行可)に対応する。手動移動後の辺は折れ点を持たず、smoothstepでの描画に委ねる。
* **状態遷移**: `draft → reviewing → approved → exported`。approved後に編集すると`reviewing`へ戻る。
  * **具体化(Phase 12で確定)**:
    * 保存(座標だけの保存を含む)と自動レイアウトの実行で、どの状態からでも`reviewing`になる。
    * 承認は`draft`・`reviewing`から行える(AIの出力を手直しせずに承認できる)。
    * 図のダウンロード(出力)に成功すると`exported`になる。AIで再生成すると`draft`に戻る。
  * **承認の条件**:
    * 画面で見ていた版であること(他で更新されていれば競合として再読み込みを促す)。
    * 全要素の配置があること(無ければ自動レイアウトの実行を促す)。
    * 検証エラーが無いこと(エラーの一覧を検証パネルに表示する。警告は承認を妨げない)。
    * 未保存の変更がある場合、承認ボタンは「保存して承認」となり、保存してから承認する。
  * 承認済みの図には、「保存するとレビュー中に戻る(承認し直しが必要)」旨を常に表示する。
* **承認・エクスポート**: 承認後、決定的(AI非依存)なdraw.io GeneratorがXMLを生成し`.drawio`としてダウンロードできる。同一エンジンがSVGも同時出力する。
  * **具体化(Phase 12で確定)**:
    * 出力は承認済み・出力済みの図だけで、未保存の変更があるときは出力できない。
    * 辺ラベル(ERの多重度、DFDのデータ項目名)はレビュー画面と同じ文言で描く。
    * 手動移動した辺は、draw.ioでは`orthogonalEdgeStyle`に経路を任せ、SVGでは簡易な直交経路で描く。
    * レーン帯は描かない(レビュー画面と同じ)。
    * 出力ボタンの隣に、「ダウンロードしたファイルを直接編集しても、Devexには反映されない」旨を表示する(D6)。
* **内部設計書への反映**: 承認済みの図とその要素表を、内部設計書の該当セクション([内部設計書](internal_design.md) 3.2節・3.3節、アンカーコメントで位置を特定)にプレビュー時点でSVGとして差し込む。ダウンロードはMarkdown+図ファイル(SVG/drawio)のzip形式にする。エクスポート後にユーザーがファイルを直接編集した場合、その変更はDevexに反映されない旨を画面上に明示する(draw.ioの再インポートは対象外)。
  * **具体化(Phase 13で確定)**:
    * 図を承認すると、同時に内部設計書の表示中の版へ要素表が反映される(版は増えない)。文書の再生成・復元で反映が消えた場合は、文書画面(内部設計のタブ)の「図を再反映」で戻す。承認済みの図のうち反映されていないものの件数を表示する。
    * プレビューでは、承認済みの図だけ画像を表示する。承認後に編集中(レビュー中)の図は画像を出さず、要素表が前回承認した内容であることを示す。
    * 図が内部設計書の古い版から生成されている場合、プレビューと設計図の一覧(SCR-007の一覧)に、再生成を促す表示を出す。
    * 「図付きでダウンロード(.zip)」のzipには、内部設計書のmd(図ファイルへの相対リンク入り)と、文書に反映済みの図のSVG・drawioが入る。zipに入れた図は`exported`になる。
* **図の手直しの反映**: 承認済みの図の変更を、AIが基本設計・内部設計(散文)への修正案(差分)として提示し、ユーザーが承認して反映する(Should、Phase 13b)。
  > **[Phase 14 で確定 ── 〈図の手直しの反映(M9b)を実装しない〉]** 当初〈Phase 13bで実装する予定〉→ 撤回。理由〈詳細設計モード(2.7節)では文書を承認済みの意味モデルから組み立てるため、図の変更を散文へ戻す修正案はほぼ不要になる。ステージ3はPhase 13で終了した〉。

## 2.7 詳細設計モード(ステージ4)

要件定義・外部設計の後に、段階ごとに人が承認しながら詳細設計書を組み立てるモード。構想は[`appendix/detailed-design-mode-organization.md`](../appendix/detailed-design-mode-organization.md)、決定の経緯は[`textbook/Phase-14/Phase-14-1.md`](../textbook/Phase-14/Phase-14-1.md)参照。段階の中身(意味モデル・API)の詳細は各段階の実装Phaseで確定する。

* **2つのモード(作成時に選ぶ。Phase 14で確定)**: SCR-002の「新規プロジェクト作成」を押すと、モード選択ダイアログが開く。選んだモードはプロジェクトに記録し(`projects.mode`)、作成後は変えない。
  * **簡易ドキュメントモード**(旧称「概要モード」。今の動き): チャット → 4文書を一括生成。
  * **詳細設計モード**: チャット(同じヒアリング) → 要件定義・外部設計の2文書だけを生成(自己診断つき) → 段階1〜6を順に作って承認 → 段階7 横断事項と実装計画。
* **段階**(章と段階は1対1。正本は各段階の意味モデルで、文書はそこから組み立てる):

| 段階 | 詳細設計書の章 | 入力 | AIの役割 |
| :--- | :--- | :--- | :--- |
| 1 | 01 機能(処理)一覧(処理ID `F-01`…/名称/種別/トリガー/関連画面/機能グループ/概要) | 外部設計の画面一覧(2.2)・API一覧(2.6。Phase 16で外部設計書に追加) | 下書き → 人が確定。機能グループはAPIのリソース名から初期値を決定的に作り、人が確定する |
| 2 | 02 データフロー(機能グループごとのDFD・データ辞書・処理概要表(入力/処理/出力)) | 1 + 要件定義 | 下書き → 人がレビュー。DFDを描く機能グループは人が選ぶ(単純な処理は処理概要表の1行で済ませる) |
| 3 | 03 データモデル(ER・テーブル定義・CRUD図) | 2のデータストア・データ辞書 | ERは下書き。CRUD図は、R(読み)とW(書き)をDFDの線の向きから決定的に作り、W の C/U/D の区別と、DFDに描いていない処理の分はAIが下書きして人が確定する |
| 4 | 04 ソフトウェア構造(構成図(層)・モジュール一覧(パス/層/責務/主な依存先/関わる処理)) | 1〜3 + 技術スタック | 下書き → 人がレビュー |
| 5 | 05 主要処理の手順(人が選んだ処理だけ) | 4 + 2 | 人が対象を選び、AIが下書き |
| 6(任意) | 06 処理ロジックの詳細(人が選んだ関数だけ) | 5 | 同上 |
| 7 | 実装計画 | 全体 | 現行と同じ生成 |

* **段階の進め方(Phase 14で確定)**:

```
[新規プロジェクト作成] → [モード選択ダイアログ] ─┬─ 簡易ドキュメント → SCR-003 → SCR-004 ヒアリング → 4文書を一括生成 → SCR-005
                                                │    →「実装手順書へ進む」→ SCR-008(段階8だけ。Phase 31)
                                                └─ 詳細設計 ──────→ SCR-003 → SCR-004 ヒアリング(同じ) → 要件定義・外部設計を生成
                                                     → SCR-005 で確認 →「詳細設計へ進む」→ SCR-008 詳細設計画面

SCR-008: 左に段階のステッパー 1〜8(状態: 未着手 / 下書き / 再生成済(未承認) / レビュー中 / 承認済み / 古い)、右に選んだ段階の作業領域

各段階の共通サイクル:
  [下書きを生成](AI。入力は前の段階の承認済みの成果物)
    → レビュー・編集(表は表の編集、図は SCR-007 のエディタを再利用)
    → [承認](検証が通ること) → 次の段階が開く

  段階1 機能一覧    : AI が外部設計の API・画面から処理ID を下書き。機能グループはリソース名から初期値 → 人が確定
  段階2 データフロー: DFD を描く機能グループを人が選ぶ → グループごとに DFD・データ辞書・処理概要表を下書き → レビュー
  段階3 データモデル: ER・テーブル定義を下書き。CRUD の R/W は DFD から自動、C/U/D は AI の下書き → 人が確定
  段階4 構造        : 構成図(層)とモジュール一覧を下書き → レビュー
  段階5 手順        : 手順を書く処理を人が選ぶ → 下書き → レビュー(索引・関与表・タブ)
  段階6 処理ロジック: (任意)05 の手順の行から関数を選ぶ → 下書き → 承認。またはスキップ
  段階7 横断事項と実装計画: 要件定義・外部設計と、段階1〜6から組み立てた詳細設計書(01〜06章)を入力に、07 横断事項と実装計画を下書き

前の段階を直して承認し直す → その段階を入力にしている後ろの段階に「古い」を表示
  → 人が「再生成」するか、「このまま承認し直す」を選ぶ
```

  * **閉じた段階(Phase 44 の完了後の調整)**: 「古い」段階は承認済みと数えないので、その段階を入力にする後ろの段階は閉じる(連鎖する)。閉じた段階の作業領域は中身の表を出さないが、保存した内容があれば「消えていません」と示し、今承認し直せばよい段階(入力をたどって最初に開いている段階)と、その段階へ移るボタンを出す。内容を変えずに承認し直した段階は版が変わらないので、それだけを入力にする後ろの段階は元の状態に戻る。
  * 詳細設計書(HTML+md+図のzip)は、承認済みの段階から組み立てる。いつでもダウンロードでき、未承認の章は「未承認」と表示する(Phase 22で確定)。段階を0件で承認して飛ばした段階6の06章は「省略」と表示する。
  * **ダウンロードの操作(Phase 22で実装)**: SCR-008 の見出しの下に「詳細設計書をダウンロード(.zip)」を置き、隣に段階1〜6のうち未承認の件数(未承認の段階の章は「未承認」と書かれること)を示す(Phase 23で、ボタンを「詳細設計書と実装計画をダウンロード(.zip)」、件数を段階1〜7に改めた。Phase 30で、ボタンを「詳細設計書・実装計画・実装手順書をダウンロード(.zip)」、件数を段階1〜8に改めた)。出力ボタンと同じく、ダウンロードしたファイルを直接編集しても Devex には反映されない旨を表示する(D6)。zip の中身は`detailed_design.html`・`detailed_design.md`・`diagrams/`(載せた図の SVG・drawio)。07 横断事項は Phase 22 では出さない(Phase 23 で決める)。
    > **[Phase 30 で確定 ── 〈いつでもダウンロードできる1つの zip にしない〉]** 当初〈1つのボタンで、どの段階が未承認でもダウンロードでき、未承認の章は「未承認」と書く〉→ 改訂。理由〈画面確認後の要望で、zip を「詳細設計書・実装計画」(`detailed_design.zip`)と「実装手順書」(`implementation_procedure.zip`)の2つに分け、元になる段階(前者は段階1〜7、後者は段階8)がすべて承認済み(古くない)になるまで、ボタンを押せなくした(透過表示し、横に「段階N・Mが未承認です。承認するとダウンロードできます。」と出す)。サーバーも同じ条件で409`DESIGN_DOCUMENT_NOT_READY`を返す。承認していない内容の入った文書を出さないため。組み立ての「未承認」の書き方は、段階7の下書きの入力のために残す。経緯は[`textbook/Phase-30/Phase-30-7.md`](../textbook/Phase-30/Phase-30-7.md)〉。
  * **07 横断事項と実装計画の出力(Phase 23で確定)**: 07 横断事項は詳細設計書の07章に入れる。実装計画は、同じ zip に別のファイル(`implementation_plan.html`・`implementation_plan.md`)で入れる(簡易ドキュメントモードで実装計画書が別の文書なのとそろえる)。段階7が未承認なら、07章も実装計画も「未承認」とだけ書く。
  * **外部設計書のAPI一覧(Phase 16)**: 生成する外部設計書に「2.6 API一覧」(メソッド/パス/概要/関連画面の表)を足す。簡易ドキュメントモードでも同じ。段階1の機能グループの初期値はこの表のパスから作り、下書きに漏れたAPIは警告で知らせる。
  * **段階1の種別(Phase 16)**: API / API+バッチ / バッチ / 画面 / その他。「画面」はサーバーを呼ばずに画面の中で完結する非自明な演算・描画で、AIは外部設計書2.3の画面仕様から下書きする。
  * **状態「再生成済(未承認)」(Phase 16)**: 内容のある段階の下書きを作り直すと、ステッパーの状態は「再生成済(未承認)」になる。作り直した時点の入力を記録するので「古い」は消え、その後に入力が変わればまた「古い」になる。

  * 段階の作業領域の保存(Phase 21 の画面確認後): 段階1〜6(Phase 23 で段階7も)の表の保存ボタン(と段階6の「段階6を飛ばす」)は、作業領域の先頭(状態表示の直下)と最下部の両方に置く。選択や編集の後に、スクロールせずに保存して生成へ進めるようにするため。図のエディタ(DFD・ER・構成図)の保存は、エディタの中のボタンのまま。
  * 段階の画面の骨格(Phase 15で実装): 左のステッパーは段階1〜7を状態の色とラベルで並べ、押すとその段階を選ぶ。最初は、まだ承認されていない最初の段階を開く。右の作業領域は、全段階に共通の部分として、状態・足りない入力(「段階1(機能一覧)の承認」「外部設計書」)・古い表示・承認ボタン(古い段階では「このまま承認し直す」)を持つ。承認できたら、ダイアログで「段階N-{段階名}を承認しました。」と知らせ、「次の段階へ進む」で次の段階を開く(「閉じる」で留まる。段階7は「閉じる」だけ。Phase 18 の画面確認後に追加)。段階ごとの下書きの生成・編集の画面は、各段階の実装Phase(16〜21)で足す。
* **段階の承認と陳腐化**: 段階ごとに「下書き → レビュー中 → 承認」を持ち、承認した段階だけが次の段階の入力になる。前の段階を承認し直すと、その段階を入力にしている後ろの段階に「古い」表示を出す。作り直しは自動では行わず、人が「再生成」を押す(段階の依存関係がそのまま陳腐化の伝わる道筋になる)。
* **05 主要処理の手順(Phase 14で確定)**:
  * 手順の表の列は `No / 呼び出し元 → 呼び出し先 / 渡すデータ / 処理内容 / 結果 / DB 操作 / 分岐・例外` の7列。分岐はサブ番号(`4a`)で、元の手順の直後に置く。
    > **[Phase 29 で確定 ── 〈7列を8列にする〉]** 当初〈7列〉→ 改訂。理由〈シーケンス図の矢印の種類を決めるため、呼び出し元 → 呼び出し先の次に「種別」(同期・非同期・戻り)の列を足した。種別は段階5の下書きで AI が書き、人が表で直せる。種別の無い既存の行は同期として読む。分岐の行は種別を持たない。戻りの行は関数を呼ばないので、06 の詳細のバッジを付けない。経緯は[`textbook/Phase-29/Phase-29-1.md`](../textbook/Phase-29/Phase-29-1.md)〉。
  * 手順IDは処理IDと手順番号の組(`F-01#4`、分岐は`F-01#4a`)で、文書全体で一意にする。
  * 章の冒頭に「索引」(処理ID/名称/トリガー/選定理由/手順数/紐づく06の項目)と、「処理 × モジュール」の関与表(CRUD図と同じ格子。セルは手順番号)を置く。
  * 処理ごとの手順はタブで切り替える(件数が増えても縦に長くならない)。
  * 処理のタブの手順の表の下に、その処理のシーケンス図を置く(Phase 29)。図は保存した手順から導くので、保存していない編集は保存すると図に反映される。図にするときの指摘(戻りを呼び出しとして書いた行など)を図の下に並べる(段階5の検証の警告と同じ)。
* **06 処理ロジックの詳細(Phase 14で確定)**:
  * 1項目はL-ID(`L-01`…)を持つ関数1つで、シグネチャ/引数/戻り値/例外/事前条件/事後条件の表と、番号付きの擬似フローを書く。L-IDは保存せず、項目の並び順から振る(Phase 21で確定。紐づけは(モジュール, 関数)なので、振り直しても切れない)。
  * 05の手順の行のうち06に詳細があるものは、「処理内容」の下に「詳細 L-02 ↓」のバッジを付ける(列は増やさない)。06に詳細があるかは、手順の(呼び出し先, 関数)と06の項目の(モジュール, 関数)が一致するかで決める(Phase 20で確定。手順の行にL-IDを持たせない)。06の各項目の見出しの下には「呼ばれる手順」(`F-01#4`・`F-05#5`)のバッジを置く。バッジを押すと相手側のタブへ切り替えて、その行・項目へ移り強調する。
  * 章の冒頭に「逆引き」(L-ID/関数/モジュール/呼ばれる手順)を置く。1つの関数が複数の処理から呼ばれることが一目で分かる。
  * 06も関数ごとのタブで切り替える。
  * 見せ方の見本は、devex-uiのデモページ`/detailed-design-demo`(仮データ)。レビュー画面はこの見せ方を採用する。
* **詳細設計書の出力(Phase 14で確定、Phase 22で実装)**: zipで、次の3種類をまとめて出力する。
  * **HTML(読む用)**: 自己完結の単一ファイル(CSS・スクリプトを中に持ち、外部を読み込まない)。レビュー画面と同じタブと双方向のリンクを持ち、ブラウザで開けばリンクが必ず動く。スクリプトが無効でも、全件を並べて表示しアンカーで飛べる。図はSVGを中に入れる。
  * **Markdown(差分・AIへの入力用)**: リンクと生のHTMLを持たず、IDを本文に書くだけ(「→ 詳細: L-02」「呼ばれる手順: F-01#4」)。図はzipの中のSVGを相対パスの画像で載せる(ステージ3のzipと同じ。章の間のリンクではない。Phase 22)。生のHTMLのアンカー(`<a id>`)は多くのmdビューワーやDevex自身のプレビュー(react-markdown、`rehype-raw`なし)で消えて飛ばず、日本語の見出しから作る自動アンカーはビューワーごとに作り方が違うため。
  * **図ファイル**: SVG・drawio(ステージ3の出力エンジンを再利用する)。
  * **実装手順書(Phase 30 で実装)**: 別の zip(`implementation_procedure.zip`。2.8節「出力」)。
* **シーケンス図**: 当面は作らず、05の番号付き手順で扱う。シーケンス図へ進むかは、ステージ4の運用の後に判断する(D7はCouldのまま)。
  > **[Phase 25 で確定 ── 〈シーケンス図を作らない、を改める〉]** 当初〈当面は作らず、05の番号付き手順で扱う〉→ 改訂。理由〈ステージ4の後の判断として、段階5の手順の行(呼び出し元・呼び出し先・関数・データ・結果・分岐・手順ID)から決定的に導く**読み取り専用**のシーケンス図を作る。正本は手順の表のままで、図は直さない(LLM による別生成・画面での編集はしない)。05章と実装手順書(2.8節)に載せる。コミュニケーション図は後回し。経緯は[`textbook/Phase-25/Phase-25-5.md`](../textbook/Phase-25/Phase-25-5.md)〉。
  * 詳細設計書(Phase 29 で実装): HTML は 05 の各処理のタブに SVG の図を入れる。md は各処理の手順の表の後に Mermaid の`sequenceDiagram`のコードブロックを入れる(zip に図のファイルは足さない。Devex 自身の md プレビューでは図にならずコードとして見えるが、許容する)。

## 2.8 実装手順書 + 実装可能性チェック(ステージ5)

実装計画の作業単位ごとに、開発者(人または AI Coding Agent)が実際に作業できる実装手順書を作り、その過程で設計の不足・矛盾を表に出す。方針は[`appendix/devex_implementation_procedure_guideline.md`](../appendix/devex_implementation_procedure_guideline.md)、決定の経緯は[`textbook/Phase-25/Phase-25-1.md`](../textbook/Phase-25/Phase-25-1.md)、見本は[`appendix/implementation-procedure-sample/`](../appendix/implementation-procedure-sample/README.md)と devex-ui のデモページ`/implementation-procedure-demo`(仮データ)。意味モデル・API の詳細は各実装 Phase で確定する。

* **手順書は設計を書き写さない**: 処理の流れ・関数の契約・データ・エラーは設計(段階2〜7)にあり、手順書は ID(処理ID `F-07`・手順ID `F-07#2`・L-ID・モジュールのパス・07章の項目)で参照する。手順書に固有なのは、作成・変更するファイル(依存順・責務1行)、作る順序、確かめ方(テスト観点・確認方法)、設計に無いもの(未定義)の4つ。
* **作業単位(段階7の改修。Phase 25 で確定)**: 段階7のタスクを、処理を持つものは機能ごとの縦割り(**機能**の単位。バックエンド・フロントエンド・テストを1単位に)、処理の無い準備・デプロイは**基盤**の単位にする。単位の ID は並び順から導く(`M-01-T01`。保存しない)。単位の間に依存(先に終わっている必要がある単位)を持つ。ファイルは「モジュール」(段階4のパス。検証する)と「環境・設定のファイル」(例。検証しない)に分ける。手順書はこの単位をそのまま使う(手順書の生成時に単位を作り直さない)。段階7の作業領域・検証は Phase 26 で実装した(2.7節「段階7の作業領域」)。
* **SCR-008 の段階8(Phase 25 で確定)**: 手順書は詳細設計モードの段階8(入力は段階1〜7)として、段階のステッパーに足す。保存・承認・陳腐化・再生成は段階1〜7と同じ。作業領域は上から:
  * **単位の一覧(依存順)**: 単位・種別・タスク・処理・依存・手順書の有無・未定義の件数(重要度ごと)。単位を選んで「選んだ単位の手順書を生成する」(1回に5件まで。1単位につき AI を1回)。手順書のある単位を選んだときは、作り直す前に確かめる。
  * **未定義・要決定の一覧(実装可能性チェック)**: 重要度(最重要・中程度・軽微)で絞り込める。出どころは「検証」(設計の ID・パス・依存先の突き合わせ)と「AI」(手順書を生成する AI の指摘)。各行に「段階Nで直す」(対象の段階へ移る)。直した段階は差し戻され、段階8は「古い」になる。**手順書の上では決めない**。
    > **[Phase 28 で確定 ── 〈「AI に提案を求める」を作らない〉]** 当初〈未定義の各行から AI に決め方の案を求める〉→ 撤回。理由〈指摘への対応は「段階Nで直す」で設計の側へ移り、そこで直す・段階を再生成する流れで足りる。AI に案を出させる機能は、ステージ8(AI 設計レビュー・再ヒアリング)と役割が重なるため、その境界として申し送る([`textbook/Phase-28/Phase-28-introduction.md`](../textbook/Phase-28/Phase-28-introduction.md))〉。
  * **単位の詳細**: 目的・参照する設計(押すと設計の中身を展開。設計に無い参照は赤字)・シーケンス図(手順を参照する単位だけ)・作成・変更するファイル・実装の要点(設計に無いが自明な作業と、順序の理由だけ)・テスト観点(SUT・ドライバ・スタブ、Given/When/Then)・確認方法・その単位の未定義。
  * **AI 向けにコピー**: 手順書の単位に、参照する設計の該当箇所を展開して添えた md をクリップボードへ写す。未定義が残っていれば、件数を示して警告する(渡すのは止めない)。
  * 概要・実装前提(実装ルールは段階4・07章から引く)・単位の一覧・未定義の一覧・完了条件は、AI を使わずに組み立てる。
  * **Phase 27 で実装した部分**: 段階8をステッパーに足し、単位の一覧(単位・種別・タスク・処理・依存・手順書の有無(生成済/未生成)・未定義の件数)と、未定義・要決定の一覧(重要度の絞り込み・出どころ・単位(単位によらなければ「全体」)・対象・内容・「段階Nで直す」)を出す。単位の一覧は段階7の並び順で、依存は前の単位だけを指すのでこれが依存順。検証の指摘は手順書がまだ無くても出る。手順書そのもののエラー(段階7と合わない手順書など)は、一覧の下の検証の結果に出す。「段階Nで直す」は対象の段階を開く(移った先で行を強調するのは、すでに強調の仕組みを持つ段階5だけ)。生成・単位の詳細・最重要が残るときの承認前の確認は Phase 28。
  * **Phase 28 で実装した部分**: 単位の一覧に生成の選択の列(上限5)と「選んだ単位の手順書を生成する(n/5)」を置く(生成中・失敗の表示は段階5と同じ。保存していない編集があれば生成できない)。単位の ID を押すと単位の詳細を開く。詳細は、参照する設計のバッジ(押すと、サーバーが承認済みの設計から展開した md を出す。設計に無い参照は赤で押せない。07章 横断事項と段階7の開発環境も同じ形で添える)と、手順書の編集(目的・ファイルの表(パス・種類・責務・根拠)・実装の要点・テスト観点の表・Given/When/Then・確認方法・AI の指摘の表(重要度・対象・内容・直す段階。「段階Nで直す」と行の削除)・単位の手順書の削除)。編集は保存して初めてサーバーへ送る。手順書の無い単位は、参照する設計だけを出して生成を促す。段階7とタスク名の合わない手順書には、作り直すか削除するよう出す。承認は、段階8に最重要の指摘(検証と AI の両方)が残っていれば「最重要が N 件残っています。このまま承認しますか」と確かめる(承認は止めない)。「AI 向けにコピー」は Phase 30。
  * **Phase 30 で実装した部分**: 単位の詳細(手順書があり、段階7とタスク名が合う単位)に「AI 向けにコピー」を置く。押すと、サーバーが**保存済みの**手順書と承認済みの段階1〜7から組み立てた AI 向けの md(zip の`ai/<単位ID>.md`と同じ組み立て)をクリップボードへ写す。段階8が未承認・古いとき、その単位に未定義が残るときは、md の先頭と画面に件数を示して警告する(渡すのは止めない)。保存していない編集があると、写す中身が画面とずれるので押せない。
  * **Phase 29 で実装した部分**: 単位の詳細で、段階5の手順の参照のバッジを押すと、展開した md(表の後に Mermaid のシーケンス図)の上に図(SVG)を出す。テスト観点のスタブの欄が、図で SUT から呼ばれないモジュールを挙げていれば、未定義の一覧に軽微の指摘(直す先は段階5)を出す。
  * **Phase 38 完了後の調整**: 計画(段階7・簡易モードの実装計画書の WBS)が変わり、どの単位とも合わなくなった手順書(単位が無い・タスク名が違う)は、単位の一覧の下の「段階7に無い手順書」(簡易モードは「実装計画書に無い手順書」)に出す。行ごとに、手順書の無い今の単位へ付け替える(ID とタスク名だけを変え、中身はそのまま)か消す。「すべて消す」もある。変更は下書きに入り、保存して反映する。合わない手順書は自動では消さない(人が決める)。残っている間は検証のエラー(UNIT_MISMATCH)で承認できず、エラーの文言はこの操作を案内する。
* **シーケンス図(Phase 25 で確定)**: 段階5の手順から決定的に導く読み取り専用の図。矢印に手順番号を付け、推測した戻りは破線・斜体にする。手順書の単位では、単位で作るファイル・選んだテストの SUT・SUT から呼ぶ先(スタブの候補)を色で示し、手順書のスタブの欄が手順に無い依存を挙げていれば指摘する。図にするときに分かる手順の不備(戻りを呼び出しとして書いた行・入れ子を推測できない並び・存在しない分岐先)は検証の指摘にする。画面と HTML は SVG、md と AI 向けの版は Mermaid の`sequenceDiagram`。
  > **[Phase 29 で確定 ── 〈単位の図で、ファイル・SUT・スタブの候補を色で示さない〉]** 当初〈手順書の単位の図で、単位のファイル・選んだテストの SUT・スタブの候補を色で示す〉→ 撤回。理由〈図の導出と SVG をバックエンドだけに置いた(画面・詳細設計書・手順書の参照の展開で同じ図を使う。#17)ため、画面で図に色を付けるには導出を画面にも持つ必要がある。スタブの候補の突き合わせは、検証の軽微な指摘(`STUB_OUTSIDE_SEQUENCE`、直す先は段階5)で出す。経緯は[`textbook/Phase-29/Phase-29-introduction.md`](../textbook/Phase-29/Phase-29-introduction.md)〉。
  * 図の規則(Phase 29 で実装): 参加者は呼び出し元・呼び出し先に現れた順。同期の呼び出しは戻りを待ち、非同期の呼び出しは待たない。同じ参加者の中の呼び出しは輪で描き、戻りを描かない。分岐の行は元の矢印に付けた注記。ループ・並行は扱わない。
* **出力(Phase 25 で確定)**: 詳細設計書・実装計画の zip に`implementation_procedure/`を加える。中身は`index.md`(概要・前提・単位の一覧・未定義の一覧・完了条件)、単位ごとの md(ファイル名は単位の ID と名前)、AI 向けの版、自己完結の HTML 1枚。
  * 実装(Phase 30): 詳細設計書・実装計画とは別の zip `implementation_procedure.zip`(直下に`index.md`・`implementation_procedure.html`・`<単位ID>_<タスク名>.md`(パスに使えない文字と空白は`_`)・`ai/<単位ID>.md`)。SCR-008 の「実装手順書をダウンロード(.zip)」で落とす。
    * **段階8が承認済み(古くない)になるまで、ボタンを押せない**(透過表示。サーバーも409)。画面の「AI 向けにコピー」は作業中に使うので、保存済みの手順書から作って警告する。
    * 単位の md と AI 向けの版は、手順書のある単位だけ。`index.md`の単位の一覧には全単位を載せ、手順書の無い単位は「(未生成)」。
    * `index.md`: 実装概要(段階7のマイルストーン。対象外は要件定義書 1.4 の Should / Could / Won't の行)・実装前提(段階7の開発環境と、実装ルール = 「モジュールは段階4の依存先にだけ依存する」+ 07章の各項目)・単位の一覧(単位・種別・処理・依存・ファイル・確認方法・未定義の件数)・未定義の一覧(全体 / 単位ごと。重要度・出どころ・対象・内容・直す段階)・完了条件。
    * 単位の md(人向け): 参照する設計は ID(見出し)だけを書き、中身を書き写さない。段階5の手順のシーケンス図(Mermaid)だけは添える。
    * AI 向けの版: 作成方針17章の順(依頼文 → プロジェクト概要 → 実装ルール(07章・開発環境)→ 今回の単位 → ファイル → 参照する設計(展開)→ テスト観点 → 完了条件 → 未定義(推測で実装しない)→ 制約 → 調査の指示)。
    * HTML 1枚: 単位をタブにせず縦に並べる(実装計画の HTML と同じ形)。一覧・依存・未定義の単位の ID から、その単位の手順書へアンカーで移る。図は SVG。
* **テストの範囲**: 単位ごとのテスト観点と確認方法まで。体系的なテスト設計(単体/結合/総合・境界値・非機能)はステージ8で扱う。
* **簡易ドキュメントモード(ステージ5の後半)**: 実装計画書の WBS を段階7と同じ縦割り・ID 付きにし、同じ形の手順書を作る。入力は4文書で、参照先は内部設計書の処理別データフロー(`DF-<n>`)・API 一覧・モジュール一覧・3.4節。設計に書かれていない部分が多いので「未定義」が多く出ることを、そのまま示す。
  * **実装(Phase 31)**: 経緯は[`textbook/Phase-31/Phase-31-introduction.md`](../textbook/Phase-31/Phase-31-introduction.md)。
    * **入口**: SCR-005 の「実装手順書へ進む →」で、同じ SCR-008 を段階8だけで開く(見出しは「実装手順書」)。ステッパーには段階1〜7を「詳細設計モードのみ」の押せない行として並べ、詳細設計モード用であることを添える(完了後の調整)。ダウンロードは実装手順書の zip だけを出す。

    * **未定義の直す先**: 段階でなく文書(実装計画書・内部設計書など)。各行の「〇〇書を直す(再生成)」は SCR-005 へ移る(文書は画面で編集できないので、再生成して直す)。AI の指摘も直す先を文書で選ぶ。
    * **決定的なチェック**: 実装計画書 ── WBS の書式・依存先が一覧に無い/後ろの単位・機能の単位に DF が無い・DF が内部設計書に無い・どの単位にも入らない DF(軽微)。内部設計書 ── モジュール一覧が無い(最重要)。承認を止めるのは、詳細設計モードと同じく手順書そのもののエラー(形・重複・単位と合わない)だけ。

## 2.9 ヒアリング改良 + 上流の構造化(ステージ6)

ヒアリングで聞き漏れを減らし、要件定義書・外部設計書を構造化して、要件から作業単位までを追えるようにする。決定の経緯は[`textbook/Phase-33/Phase-33-2.md`](../textbook/Phase-33/Phase-33-2.md)、出発点の数字は[`appendix/stage6-baseline/`](../appendix/stage6-baseline/README.md)、見本は[`appendix/structured-requirements-sample/`](../appendix/structured-requirements-sample/README.md)と devex-ui のデモページ`/hearing-points-demo`(仮データ)。API・画面の細部は各実装 Phase で確定する。

* **観点の表(SCR-004)**: チャット画面に観点の表を置く。観点・必須・状態(ユーザーが決定 / AI の提案を採用 / 未決 / 対象外)・決めたこと・根拠(どの発言か)。観点は機能面(規模・目的・課題・利用者と使う場面・利用者の1日の流れ・コア機能・MVP の範囲・例外の場面・将来の拡張・技術スタック・環境の制約・体制・期間)と、IPA 非機能要求グレードの6大項目(可用性・性能・拡張性・運用・保守性・移行性・セキュリティ・システム環境・エコロジー)。規模(個人・小規模 / 社内 / 公開サービス)で必須が変わる。技術スタックは規模によらず必須。必須でも「対象外」と決めれば済む。
  * **Phase 34 で実装した部分**: 広い画面(1024px 以上)はチャットの右に開いて置き、狭い画面はチャットの上に畳める表として置く。見出しに未決の必須の件数(そろったら「必須はすべて決まりました」)と規模(未決なら「個人・小規模の列で数えている」)を出す。未決の観点は、決めたことの代わりに場面で聞く問いの例を薄く出す。根拠は「初期入力 / 添付資料 / 発言N」。以前の5条件で進んだプロジェクトには「次の発言から観点の表で判定します」、直近の発言の判定に失敗したときは「直近の発言は表に反映できていません」と注記し、生成のボタンは出さない。生成の後も表は見られる。
  * **Phase 35 完了後の調整**: 広い画面では、表をヘッダーの下に追従させる(チャットをスクロールしても見える。表が長ければ表の中でスクロールする)。状態の欄は、未決を「未決(必須)」(赤)と「未決(任意)」(灰色)に書き分け、見出しに未決の必須の名前を並べる。未決の必須の行に「対象外にする」ボタンを置き、判定の AI が決められない観点でも利用者が先へ進めるようにした(決めたことは「後で決める(画面で対象外にした)」、根拠の発言は無し。後でチャットで答えれば上書きされる)。押すとその場で完了の判定をやり直し、必須がそろえば生成のボタンが出る。
* **完了の判定**: 利用者の発言のたびに、AI が観点ごとの状態と根拠を返す。必須の観点がすべて未決以外になったら完了とし、今と同じくサマリと「この内容で設計書を生成する」を出す(判定は AI でなくコードが行う)。未決の必須の観点は、AI の次の問いに渡す。(Phase 34 で実装。サマリは表から決まった観点を「観点: 決めたこと」で並べたもの。発言の回数の下限は無い。未決の必須は規模から順に3つまで渡す)
* **選択肢カード**: AI の問いは場面で聞く(「夜中や休日に止まっていたら、どのくらいで困りますか」)。返信の後ろに、問い・選択肢・選択肢ごとの結果(コスト・手間)・AI のおすすめを、カードで出す。カードの選択肢を選ぶと、その観点は「AI の提案を採用」になる。自分の言葉で答えると「ユーザーが決定」になる。カードは1回の返信で数枚まとめて出す(互いに独立した観点だけ。規模のように後の必須を変える観点は単独で先に聞く)。選択はその場で観点の表に記録し(AI は呼ばない)、まとめたカードに全部答えたとき(または送信したとき)に、判定と返信を1回だけ行う(Phase 33 完了後に決定)。
  * **Phase 35 で実装した部分**: カードは AI の発言の下に出し、選べるのは最新の AI の発言のカードだけ(古いカードは選んだ結果を読むだけ)。選んでもすぐには送らず、選び直しや自分の言葉の追記ができる。「送信」で、選んだ内容(「【可用性】半日止まってよい」)と文を1つの発言として送り、その時点で選んだ観点を「AI の提案を採用」と記録する(根拠はその発言)。途中まで選んで送ってもよい。カードを選んでいれば文が空でも送れる。おすすめの選択肢には「おすすめ」と理由の1文を出す。規模が未決なら、規模のカードだけをシステムが決まった選択肢(自分と数人 / 社内 / 誰でも登録できるサービス)で出す。規模が決まった後は、未決の必須の観点の先頭3つを候補にし、選択肢で答えやすい観点だけを AI がカードにする(目的・コア機能のような観点は文で聞く)。返信の文とカードは AI の1回の出力で作るので、文は流れずにまとめて表示される。最初の発話(ヒアリング開始直後)にはカードを出さない。
  * **Phase 35 完了後の調整**: 最初の発話にも規模のカードを付ける(AI の発話の後ろに「まず、下のカードで、使う人の規模を選んでください。」)。カードごとに「この回答を送る」ボタンを置き、そのカードの回答(と入力欄の文)だけを送れるようにした(1枚送ると次の返信が最新になり、同じ発言の残りのカードは読むだけになる。まだ未決なら次の返信で聞き直す)。下の送信ボタンは、文と選択中のカードをまとめて送る。
  * **Phase 35 完了後の調整(2回目)**: カードを1枚だけ送ったとき、同じ発言の残りのカード(観点がまだ未決)は、次の AI の返信にシステムが付け直す(設問を取りこぼさない)。AI の返信にカードも問いも無く、聞くべき観点が残っているときは、システムが「次に、〈観点〉について教えてください。(例: …)」を本文に足す(問いの無い返信で止まったように見えるのを防ぐ)。必須がそろうと生成のバナーは「必須項目の回答完了 / チャットの内容から設計書を生成できます。」と、未決の任意の観点の一覧(「任意の確認事項」)を出し、[この内容で設計書を生成する] と [任意項目についてヒアリングを続ける] を置く。続けると、AI が未決の任意の観点をカードで聞く。任意を続けている間も生成のボタンは出し続け、任意が残っていても生成できる。任意のカードに答えて送ると任意の観点を続け、自由な文を送ると今までどおりまとめを返す。
  * **Phase 35 完了後の調整(3回目)**: 1回の返信で聞く問いは1つにする(カードは最大1枚。上の「数枚まとめて出す」「先頭3つ」から変更)。次に聞く観点は、前の返信で答えなかったカード(まだ未決なら同じカードを付け直す)→ 規模が未決なら規模 → 未決の必須(任意を続けているときは未決の任意)の順にシステムが1つ選ぶ。プロジェクト作成の時点で、初期入力・添付資料・開発環境の希望から書いてある観点を判定して観点の表に埋め、最初の問いは判定後に未決の観点から選ぶ(書いてあることは聞き直さない。規模が書いてあれば規模は聞かない)。カードを選んで送っただけの回(文を添えない)は、判定の AI を呼ばずに記録し、返信の AI だけを呼ぶ(まだ一度も判定していない・直近の判定に失敗したときは呼ぶ)。「任意項目についてヒアリングを続ける」は判定を呼ばず、「任意の項目についてもヒアリングを続けてください」を利用者の発言として残す。カードの選択の反応を速くした(選ぶたびに会話全体を描き直さない)。
  * **Phase 35 完了後の調整(4回目)**: カードの選択肢はラジオボタン(1つの問いから1つ選ぶ)。選んだ瞬間に選択中の表示(青)になる。選び直しはできるが、選択を外す操作は無い。
* **要件定義書(両モード)**: 見出し(1.1〜1.6)は今のまま、要件を表の行にする。機能要件 `FR-001`(MoSCoW)・非機能要件 `NFR-001`(IPA の大項目)・制約 `CON-001`。各行に出どころ(**ユーザー** = 利用者が決めた / **採用** = AI の提案を採用した / **推測** = AI が補った・未確認)と、根拠の観点を持つ。付録に観点の状態を載せる。推測の要件は、利用者に確かめるよう示す。
  * **Phase 36 で実装した部分**: 要件定義書は、会話と観点の表から AI が要件の行を書き、システムが ID と出どころを決めて組み立てる。再生成しても同じ要件は同じ ID のまま(消えた ID は使い回さない)。AI が「ユーザー」と書いても、根拠の観点が未決なら「推測」、「AI の提案を採用」の観点なら「採用」にする。1.4〜1.6 は「ID・優先度(大項目・種類)・要件・出どころ・観点」の表で、推測は太字。付録は生成した時点の観点の状態と、観点ごとの要件ID。プレビュー(SCR-005)の要件定義書のタブには、md の上に「要件の出どころ: ユーザー n / 採用 n / 推測 n」とその意味の注釈(ユーザー = 初期入力・チャットでの回答より / 採用 = ヒアリングで AI の提案を採用 / 推測 = ドキュメント生成時に AI が推測。md の凡例も同じ。Phase 36 完了後の調整)・指摘(Must の機能要件が無い・必須の観点が未決のまま生成した・対象外の観点の要件・推測の要件の件数)・推測の要件の一覧を出す。推測の要件を確かめたら「採用にする」を押す(AI は呼ばず、同じ版の文書の出どころが「採用」に変わる。版は増えないので、詳細設計の段階は古くならない)。違う内容にしたいときは、チャットで答えて再生成する。Phase 36 より前に生成した要件定義書は「要件ID・出どころがありません。再生成すると使えます」と出す。
* **外部設計書(両モード)**: 画面一覧(SCR-ID)・API 一覧(メソッド・パス・本文・応答・エラー)・外部連携を行にし、各行に関係する要件ID を持たせる。システム構成・画面ごとの UI 仕様・入出力仕様は節の本文。Must の機能要件に画面も API も無いとき、本文を持つはずの API に本文の欄が無いときに指摘する。
  * **Phase 37 で実装した部分**: 外部設計書は、要件定義書から AI が画面・API・外部連携の行と本文の節を書き、システムが画面ID を決めて組み立てる。再生成しても同じ画面は同じ画面ID のまま(消えた ID は使い回さない。API の関連画面も合わせて直す)。見出し(2.1〜2.6)は今のまま。2.2 は「画面ID・画面名・主要な役割・優先度・要件」の表と画面遷移の図、2.3 は画面ごとに `### SCR-001: 画面名` の UI 仕様、2.4 は「サービス・用途・認証・タイミング・要件」の表、2.6 は「メソッド・パス・概要・関連画面・要件・本文・応答・エラー」の表(詳細設計モードの段階1・簡易モードの段階8は、今と同じくこの表を読む)。末尾に付録「要件との対応」(Must の機能要件ごとの画面・API)。プレビュー(SCR-005)の外部設計書のタブには、md の上に「画面 n / API n / 外部連携 n」と指摘を出す。指摘は警告だけ: 中程度 = 画面も API も無い Must の機能要件 / 本文の欄が空の POST・PUT・PATCH(本文の要らないものは AI が「なし」と書く。Phase 40)、軽微 = 要件定義書に無い要件ID / どの要件にも結ばれていない画面・API / 画面一覧に無い画面ID を指す API。直したいときはチャットで答えて再生成する。Phase 37 より前に生成した外部設計書は「要件ID との対応がありません。再生成すると使えます」と出す。
  * **Phase 45 で実装した部分(簡易モード)**: 内部設計書・実装計画書も、AI が行と本文の節を書き、システムが ID を決めて組み立てる(見出しと表は今のまま)。処理別データフローの ID は、同じ API の処理なら再生成しても同じ。実装計画書のタスクは、同じ名前なら同じ安定キーを持つ。プレビュー(SCR-005)の内部設計書のタブには「テーブル n / API n / モジュール n / 処理 n」、実装計画書のタブには「マイルストーン n / タスク n / リスク n」と指摘を出す。指摘は警告だけ: 最重要 = モジュール一覧が無い / タスクが無い、中程度 = 外部設計書の API に処理別データフローが無い / 処理(DF)の無い機能のタスク / 内部設計書に無い処理 / 依存先が無い・後ろ / 担うタスクの無い Must の機能要件、軽微 = API 一覧に無い API の処理 / 流れの行が無い処理 / どのタスクにも入っていない処理 / 要件の無い機能のタスク / 要件定義書に無い要件ID。Phase 45 より前に生成した版は「書き落としの検証がありません。再生成すると使えます」と出す。
* **要件からの追跡**: 詳細設計モードは段階1の機能に要件ID を付け、処理の無い Must の機能要件・要件の無い処理・要件定義書に無い要件ID を段階1の検証で指摘する。作業単位(段階7)は処理から導く。簡易モードは実装計画書の WBS の各タスクに「要件: FR-001」を書かせて解析する。
  * **Phase 38 で実装した部分**: 段階1(SCR-008)の処理に「要件」の欄(`FR-001, FR-002` のように「,」区切り。関連画面の欄も同じ入力欄にした)。下書きでは、API の処理の要件ID はシステムが外部設計書の 2.6 の同じ API の行から写し、API でない処理(画面・バッチ)だけ AI が書く。段階1の検証の警告: 処理の無い Must の機能要件 / 要件の無い処理 / 要件定義書に無い要件ID(照合の相手は外部設計書が生成時に写した要件ID)。外部設計書に要件ID が無い(Phase 37 より前の版)ときは「外部設計書に要件ID がありません」の1件だけ。簡易モードは実装計画書の WBS のタスクに「要件: FR-001」の行を書かせ、段階8の検証(直す先は実装計画書)で、単位の無い Must の機能要件(中程度)・要件の無い機能の単位と要件定義書に無い要件ID(軽微)を指摘する。段階8の単位の一覧に「要件」の列(詳細設計モードは単位の処理の要件から導く)。詳細設計書の 01 機能一覧に「要件」の列。実装手順書の index は「1 実装概要・2 実装前提・制約・3 単位の一覧・4 要件との対応・5 未定義・要決定の一覧・6 完了条件」になり、2 に要件定義書の非機能要件・制約の表(ID・大項目・要件・出どころ)、3 に「要件」の列、4 に機能要件(Won't を除く)ごとの処理と単位を載せる。単位の md と AI 向けの版にも、単位の要件(AI 向けは「実現する要件: FR-001: 本文」)を書く。NFR・CON は処理や横断事項に結ばない(横断事項との結び付けは Phase 39 の結果を見て決める)。
* **既存のプロジェクト**: 移行の処理は作らない。以前の判定の結果はそのまま表示し、文書は md のまま使う。要件ID の検証は「要件ID が無い(文書を再生成すると使える)」の軽微な指摘にする。
* **変えないもの**: 生成後の自己診断(レビューと再ヒアリングはステージ8)、プロンプトテンプレートの選択、内部設計書・実装計画書(簡易モード)の Markdown。

## 2.10 変更影響分析・変更管理(ステージ7)

設計の変更に強くするため、ある要素を変えたときに見直しが要る要素を示し、陳腐化を要素の単位で扱う。決定の経緯は[`textbook/Phase-41/Phase-41-2.md`](../textbook/Phase-41/Phase-41-2.md)、出発点の数字は[`appendix/stage7-baseline/`](../appendix/stage7-baseline/README.md)、見本は[`appendix/change-impact-sample/`](../appendix/change-impact-sample/README.md)(Phase 41 で確定)。

* **出発点(Phase 41 のベースライン)**: 今の陳腐化は段階単位で、文書を1か所変えると全段階が「古い」になる。決まった変更シナリオで数えると、示した要素の約9割は見直し不要だった。一方、同じ段階の中の依存(段階4のモジュールの依存)と文書の中の要素(画面)は示せない。
* **変わったもの**: 段階は直前に承認したときの model の写しと、文書は前の版の model と、要素の単位で比べる。前の値と後の値を並べて示す。写しは直前の1件だけで、変更の履歴の一覧は作らない。
* **影響の一覧(SCR-008 の作業領域のパネル「変更の影響」)**: 変わったもの → 影響の一覧(置き場・要素・たどった道・理由・状態)→ 再生成の候補。たどり方は「処理を軸」: 変更が届く処理(F-xx)に属する要素(処理の要約・CRUD・手順・作業単位と、その手順を呼ぶ処理ロジック・単位の手順書)と、変わった要素の直接の参照元を示す。共有されるモジュールからは広げない。改名のように参照の文字列だけが変わる変更は、直接の参照元だけを示す。非機能要件は横断事項(段階7)の要件ID からたどる。**(Phase 49 で絞った)** テーブルの変更は処理まで上らず、テーブルを読み書きする要素と、その手順を実装する処理ロジック・手順書までを示す。文書の要素(要件・画面・API)の変更では処理の CRUD と作業単位を示さず、要件・画面の変更では処理の要約も示さない。要件の変更は、共有の画面を通って別の処理へは広げない(画面そのものの変更は、その画面の処理すべてに届く)。API の変更は、API を受ける入口のモジュールも示す。文書の再生成は前の版の差分にとどめる(変えない行は前の版の行をそのまま使う)ので、頼んでいない言い換えで印は増えない。
* **理由**: 参照の種類からシステムが文にする(「この手順から呼ばれる」など)。LLM は使わない。
* **段階の状態と印**: 段階の「古い」は今の決め方のまま残し、その中の見直しが要る要素に印を付ける。印は段階の状態の欄と、各段階の表の行の両方に出す。一覧の「表で見る」で、その段階の表を開いて行を強調する(「段階Nで直す」の移動先の強調も同じ仕組み)。要素を「確認済み」にしていき、見直しが要る要素が無くなれば、段階を承認し直せる。同じ段階の中の依存のように、段階が古くならない要素にも印を付ける。
* **再生成の候補**: 部分再生成できる段階(5 手順・6 処理ロジック・8 単位の手順書)の要素を候補として示す。自動では再生成しない。
* **印を付ける時(Phase 43 で確定)**: 段階を承認した時(承認時の写しと比べる)と、文書の表示中の版が再生成・復元で切り替わった時(前に表示していた版と比べる)に、届いた段階に印を記録する。承認する前の編集から届く印は「承認すると付く印」として一緒に示す。印をまとめて確認済みにできる。他の段階・文書から届いた印がすべて確認済みでないと、段階は承認し直せない(自分の段階の中の依存で付いた印は止めない)。
* **画面(Phase 44 で確定)**: 「変更の影響」パネルは作業領域の上に全幅で置き、印を段階ごとにまとめる(印が無ければ出さない。未確認があれば開いて出す)。初めは選んでいる段階の分だけを出し、「全段階」と「未確認のみ」で切り替える。ステッパーと作業領域には未確認の数を出す。承認する前の編集から届く印は「承認すると付く」と示し、確認済みにはできない。文書の変更は「変わったもの」に出し、文書の要素には印を付けない。再生成の候補は段階ごとにまとめて選び(初めは上限まで全部)、1段階1回の部分再生成を呼ぶ。再生成しても印は確認済みにならない。「段階Nで直す」の移動先でも、直す先の要素が分かれば行を強調する。
* **作業単位の ID**: 段階7のタスクに並べ替えで変わらないキーを持たせ、段階8の手順書と影響の記録はそのキーで指す。表示の ID(`M-01-T02`)は今のまま。
* **簡易ドキュメントモード**: 内部設計書・実装計画書も、要件定義書・外部設計書と同じく意味モデルから組み立てる(検証で、処理の無い機能の単位などの書き落としを指摘する)。4文書の版の model の差分から、段階8のどの単位の手順書に影響するかを示す。
* **簡易ドキュメントモードの影響(Phase 46 で確定)**: 文書の表示中の版が再生成・復元で切り替わった時に、前の版の model と比べ、段階8を一度でも承認していれば単位の手順書に印を付ける。たどり方は「処理を軸」の簡易モード版で、内部設計書の処理別データフロー(DF)を処理の代わりにする。要件・画面・API・テーブルの変更は DF まで届き、その DF を持つタスクの単位に印を付ける。要件を直接持つタスクの単位と、変わったタスク・モジュールを直接参照する単位にも付ける。WBS の依存の連鎖とモジュールの共有からは広げない。画面は詳細設計モードと同じ「変更の影響」パネルと、段階8の単位の一覧の行の印。承認する前の編集から届く印は無い(段階8の下流が無い)。model の無い以前の版との切り替えでは印を付けない。
* **あわせて直すもの**: ヒアリングで聞かれなかった側面(バックアップ・ログに本文を残さない・不正利用・削除。Phase 39 の L2・L5・L6・L14)と判定のゆらぎ、段階3の CRUD の下書きと DFD の書き込みの線の食い違い、段階5の分岐の行の書き落とし。
  * **ヒアリングの側面(Phase 47 で確定)**: 観点の表(SCR-004)に非機能の観点を4つ足す。「可用性(データの保全)」(データを失ったら、どこまで戻せればよいか)・「運用・保守性(データの保持・削除)」(データ・アカウントを消せる必要があるか、いつまで残すか)・「セキュリティ(ログ)」(記録に入力した内容を残してよいか)・「セキュリティ(不正利用)」(なりすまし・大量の登録や利用を防ぐか)。ラベルの先頭が IPA の大項目で、表ではその大項目の観点のすぐ後ろに並び、続けて聞く。1つの観点に1つの問いのまま、2つ目の側面にも問いが届くようにした。必須は、データの保全と保持・削除が全規模、ログと不正利用が社内以上(個人・小規模では任意)。要件定義書の非機能要件の大項目は6つのまま(新しい観点の要件は、その大項目に入る)。すでにヒアリングしたプロジェクトでは、新しい観点は未決として表に出る(必須なら、チャットで答えると埋まる。以前に生成した要件定義書の指摘には含めない)。判定のゆらぎ(自由回答が「採用」になる)は、Phase 49 で各モード3回の測定の幅を数える(`appendix/stage7-hearing/`)。
  * **段階3・5 の書き落とし(Phase 48 で確定)**: 段階2の DFD の下書きでは、読むだけの処理にデータストアへの線(書き込みの線)を描かせない。それでも DFD に書き込みの線があり、AI の CRUD 図に C/U/D が無いセルは、処理の名前から操作を補う(「削除」→ D、「登録」「作成」「追加」「送信」「新規」「アップロード」→ C、それ以外 → U)。補ったセルは下書きの印に加えて警告「DFD の書き込みの線から操作を推定しました」を出し、読むだけの処理なら段階2の DFD の線の向きを直すよう案内する(人が書き換えるか、承認で外れる)。段階5の下書きでは、AI は分岐・例外を手順の中に条件と結果で書き、システムが元の手順の直後に分岐の行を置いて、「1a へ」の参照を並びから振る(AI が番号を振り違えて `MISSING_BRANCH_TARGET` になるのを防ぐ。人が編集した手順の検証は今のまま)。
* **変えないもの**: テストへの影響(ステージ8)、生成後の自己診断。

## 2.11 AI 設計レビュー + テスト設計(ステージ8)

生成した設計を「成り立たせる」ため、生成とは別のモデルにレビューさせ、指摘から再生成・再ヒアリングへ戻る流れと、要件からテストまでの追跡を作る。決定の経緯は[`textbook/Phase-51/Phase-51-2.md`](../textbook/Phase-51/Phase-51-2.md)、出発点の数字は[`appendix/stage8-baseline/`](../appendix/stage8-baseline/README.md)、見本は[`appendix/design-review-sample/`](../appendix/design-review-sample/README.md)(Phase 51 で確定)。

* **出発点(Phase 51 のベースライン)**: 今の自己診断(生成と同じモデル・自由文)は、欠陥を仕込んだ簡易モードの4文書で 18件中 平均4件、詳細設計モードの要件・外部で 10件中 平均3.7件しか当たらず、元からある最重要(チャットの API でプロジェクトを特定できない・認可が無い・アクセス制御の要件が無い)は一度も当たらなかった。指示と入力(観点の表・決定的な検証の結果)を足しても同じモデルでは増えず、Claude Sonnet 5.5 では 16.7件・9.0件になった。Haiku 4.5 は 6.3件・3.7件で、文書をまたぐ矛盾は当たらなかった。
* **役割**: 生成は今のモデル(Gemini)。レビューは Claude Sonnet が指摘だけを返し、設計は書き換えない。対象と問いが決まった狭い判定(採用した指摘は直ったか・整形)は安いモデル(Claude Haiku)に任せ、「いいえ・一部・自信なし」か最重要なら Sonnet で確かめる(まずは記録だけのシャドーモードで精度を測ってから使う)。
* **入力**: 文書 + ヒアリングの観点の表 + 決定的な検証の指摘(既知として渡し、繰り返させない)。
* **指摘**: 重要度(#28 の3段階)・原因(ヒアリング / 設計 / 不整合)・対象(文書の中の ID・名前)・観点のキー(原因がヒアリングのとき)・問題・引用(文書からの抜き書き)・理由・改善案。レビューの回と指摘は文書の版に結ぶ。
* **レビューの区切り**: 簡易ドキュメントモードは4文書の生成の後に自動。詳細設計モードは要件・外部の生成の後に自動(今の自己診断の位置)、段階6の承認の後(「詳細設計をレビュー」)と段階7の承認の後(「全文書をレビュー」)はボタン。どの区切りも上流の文書を一緒に渡す。再生成の後は同じ位置で流れ直す。文書がそろっているのにレビューしていない区切りには「未レビュー」の印を付け、実装手順書を生成するときに知らせる(止めない)。全文書をまとめて1回でレビューすると上流の欠陥から落ちる(測定で要件・外部 9.0 → 6.3 / 10)ため、区切りごとに見る。
* **画面**: 文書のプレビュー(SCR-005)と詳細設計の作業領域(SCR-008)に「レビュー」パネルを置く。指摘は重要度の順で、対象へ飛べる。指摘ごとに採用・却下・保留を付ける。区切りごとの指摘の表は開閉でき(初めは閉じる)、指摘ごとに関連する文書(直すときに書き換える文書。レビューのモデルが返す)を凡例の文字(A 要件定義・B 外部設計・C 内部設計・D 実装計画。詳細設計モードの段階の区切りは C 詳細設計・D 実装計画(詳細))で出す(Phase 53 の完了後の調整)。詳細設計の作業領域では、各段階の表の、指摘の対象になっている行(処理・テーブル・モジュール・手順・関数・タスクなど。「段階Nで直す」と同じ推定で結ぶ)に「AI 指摘 n」のバッジを出す(却下した指摘は数えない。色は最も重い重要度)。押すとその行の指摘の「問題と根拠」「改善案」「判断」をダイアログで出し、そこで採用・却下・保留を選べる。区切りの状態(文書がまだ無い / 未レビュー / レビュー済み / 失敗)とボタンを出す。見せ方は devex-ui のデモ `/design-review-demo`。
* **差し戻し**: 採用した設計・不整合の指摘は、再生成の指示に入れる(直すのは生成のモデル。範囲は今の再生成の単位 ── 簡易は4文書、詳細は文書・段階の部分再生成)。採用したヒアリングの指摘は、観点を「未決」に戻し、チャットで聞き直す(今の「修正中」の流れを広げる)。画面(Phase 54): プレビューの再生成のダイアログで、採用した指摘を選んで指示に入れる(初めは未対応の指摘を選び、起点はその関連文書のうち最も上流)。作業領域では「採用した指摘で段階を作り直す」で段階と指摘を選ぶ(段階は指摘の対象から推定)。パネルの「チャットで聞き直す」で観点を未決に戻してチャットへ移る(最初の問いかけはシステムが出す)。
* **採用した指摘の追跡**(Phase 54): 採用した指摘ごとに、直したかを「未対応(関連する文書・段階が変わっていない)/ 対象が変わっていない / 変更あり」で判断の列に出し、区切りの見出しに「採用 n(未対応 m)」を出す。各段階の表のバッジは未対応があれば強調する。手順書の生成と段階6・7 の承認では未対応を知らせる(止めない)。作り直しの後のレビューで回が替わっても、前の回で採用した指摘は区切りの下に残す。「変更あり」の指摘は Claude Haiku が直ったかを判定し、「AI: 直った / 一部 / いいえ / 自信なし」と小さく添える(記録だけのシャドーモード)。
* **オン・オフ**: レビューを使えるのは superuser だけで、本人が切り替える(初期値オフ)。それ以外は保存値によらずオフ。オフのときは今の自己診断を出す。本番の superuser は登録したアカウントを手で昇格させる。
* **失敗したとき・上限**: レビューのモデルが使えない(障害・キー無し・上限)ときは失敗を記録して自己診断に切り替え、「もう一度レビュー」で流し直せる。superuser ごとに1日の回数の上限を設ける(既定値は実装の Phase で決める)。
* **テスト仕様書**: 結合テスト(API 単位)と総合テスト(画面の流れ・非機能)の仕様書を、簡易は4文書の後、詳細は段階7の後に生成する。テストごとに対象・観点(正常・異常・境界・セキュリティ・非機能)・前提・手順・期待結果・要件 ID・処理/単位を持ち、要件 → テストの対応表を付ける。単体テストは今の実装手順書のテスト観点のまま。**レビューの対象にしない**(実装手順書と同じ扱い)。代わりに決定的な検証で、Must の要件にテストが無い・存在しない要件や API を指す・異常系のテストが1件も無い API、を指摘する。期待結果と設計の食い違い・境界値の取り方・認可のテストの抜けは見ない。
  * **作り方**(Phase 56): どのテストを作るかはコードが要件定義書・外部設計書から決め(API ごとに正常1・エラー欄の HTTP ステータスごとに異常・本文のある API に境界・パスに`{id}`のある API にセキュリティ、非機能要件ごと・Must の画面の流れ・API にも画面にも無い Must の要件ごとに総合)、生成のモデルが各項目の前提・手順・期待結果を書く。期待結果に要るのに設計で決まっていない値は「**設計に無い**」と印を付ける。処理・単位の列はコードが API から引く(簡易は内部設計書の処理別データフロー → 実装計画書のタスク、詳細は段階1の処理 → 段階7の単位)。
  * **いつ作るか**(Phase 56): 簡易は4文書の生成に続けて自動(4文書と同じ組。失敗すれば組ごと戻す)。詳細は段階1・段階7 を承認した後に`POST /projects/{id}/generate {start_from: "test_spec"}`(承認されていない・古ければ 409 `TEST_SPEC_UPSTREAM_NOT_READY`。画面のボタンは Phase 57)。テスト仕様書だけを作ったときは、自己診断も設計レビューも流さない。
  * **読み出し**(Phase 56): `GET /projects/{id}/test-spec`(今の版・テストの件数・検証の指摘・`outdated`。まだ無ければ 404)。生成した時点の入力の版(簡易は4文書、詳細は要件・外部と段階1・段階7 の承認した版)が今と違えば`outdated`。文書の一覧(`GET /documents`)には出さない。ダウンロードは今の文書のダウンロードの API のまま。
* **実装手順書**: レビューの対象にしない(測定で、手順書に固有の欠陥はレビューで 8件中 1〜2件しか当たらなかった)。代わりに実装可能性チェックに、依存先が後の作業単位で作られる(中程度)・テスト観点があるのにテストのファイルが無い(軽微)・テーブルを作る作業単位が無い(最重要。スキーマのファイルはあるがテーブルの名前が出ないものは軽微)、を足した(Phase 55)。指摘は今の「未定義・要決定の一覧」に「検証」として出る(画面は変えない)。
* **品質評価**: Phase 51 の題材と正解表を残し、ステージの最後の効果測定で同じものさしで測る(テスト仕様書の正解例も足す)。採点の自動化は組み込みの段階で検討する。
* **変えないもの**: 生成のモデル。レビューは設計を書き換えない。
