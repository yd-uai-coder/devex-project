# 外部設計書：Devex

## 2.1 システム構成概要

Devexは、モダンなWeb技術スタックを用いて構築される対話型ドキュメント自動生成システムです。ユーザー（フロントエンド）からのリクエストを受け、AIによる高度な要件ヒアリングとドキュメント生成をセキュアに処理します。

```
[ ユーザー (ブラウザ) ]
       │
       ▼ HTTPS (JWT認証)
[ フロントエンド: Next.js (SSR / SPA) ]
       │
       ▼ REST API / SSE (ストリーミング)
[ バックエンド: FastAPI + LangChain ]
       ├── (プロンプト制御・非同期処理)
       ├── [ 外部LLM API (Gemini Flash-Lite) ]
       │
       ▼ SQL (ORM)
[ データベース: PostgreSQL (セッション・履歴・ドキュメント永続化) ]
```

* **フロントエンド層 (Next.js)**: ユーザーインターフェースを提供。SSR（サーバーサイドレンダリング）による高速な初期表示と、チャット画面でのスムーズなクライアントサイド・インタラクションを実現。

* **バックエンド層 (FastAPI + LangChain)**: 業務ロジック、LLMとの連携、プロンプト管理を担う。LangChainを用いたエージェント制御により、ユーザーとの対話履歴を踏まえた適切なヒアリングと、構造化されたMarkdown生成を統御。非同期処理によりタイムアウトを防止。

* **データ層 (PostgreSQL)**: ユーザーアカウント情報、チャットセッション、対話履歴、生成された各設計書（要件定義、外部設計、内部設計、実装計画）を永続化。

## 2.3 主要画面のUI/UX仕様

### SCR-004: チャットヒアリング画面

本画面は「初期ヒアリング入力」→「チャット」の2段構成とする。初期入力の段階でユーザーに明確な設計・構想を求めすぎないこと、要件・設計は最終的にAIが判断してユーザーの承認を経てドキュメント化することを重視し、フォームは必要最小限に絞る。

* **初期ヒアリング入力(チャット開始前)**:
  * **システム概要**(必須・自由記述): 1行〜数行のtextarea。プレースホルダ例「作りたいものを一言で教えてください」。最大**全角200文字**。
  * **実現したいこと**(必須・自由記述): 複数行のtextarea。プレースホルダで「箇条書き推奨(改行区切りでOK)」と軽く示唆するが、フォーマットは強制しない。バリデーションは「空でないこと」+最大**全角80文字**。箇条書きへの分解・構造化はこの画面では行わず、後続のチャットでAIが行いユーザーに確認する。
  * **補足**(任意・自由記述): 「欲しい機能」「その他」を1項目に統合したtextarea。最大**全角400文字**。この時点でリストや選択肢を作らせない。AIによる機能提案はフォームではなくチャット内で行う(会話の中でAIが候補を挙げ、ユーザーが同意・修正する)。
  * **環境設定**(任意・折りたたみ、ネイティブ `<details>/<summary>` を推奨): 見出しに「未入力の場合はAIにおまかせします」と明記し初期状態は閉じておく。言語・フレームワーク・DB・デプロイ環境の4グループはいずれも複数選択(チェックボックス群)。フレームワークは言語ごとに `<fieldset><legend>` で静的にグルーピングして示す(「言語を選ぶとフレームワークの選択肢が動的に絞り込まれる」ような動的コンボボックスは作らない)。SCR-003でテンプレートを選択している場合、そのテンプレートの`default_environment`([内部設計書](internal_design.md) 3.2節`prompt_templates`)を初期値としてプリフィルする(ユーザーは編集可能)。
  * 送信すると `POST /api/v1/projects`([内部設計書](internal_design.md) 3.3節参照)でプロジェクトを作成し、以降はチャット画面へ遷移する。
  * **アクセシビリティ**: 各入力欄のエラー表示には `aria-invalid` / `aria-describedby` / `role="alert"` を必ず配線する。折りたたみ・グルーピングも上記のとおりネイティブ要素・セマンティックHTMLを優先する。

* **チャット画面構成**:
  * **ヘッダー**: プロジェクト名、現在のステータス(ヒアリング中 / 生成中)、ダッシュボードへの戻るボタン、ドキュメント生成ボタン(手動トリガー)。
  * **メインエリア(チャット履歴)**: ユーザーのメッセージ(右側吹き出し)とAIからのメッセージ(左側吹き出し、Markdown対応、ストリーミング出力)。チャット開始直後、AIの最初の発話は初期ヒアリング入力の内容を踏まえた理解の要約と確認質問から始まる。
  * **フッター(入力エリア)**: テキスト入力欄(複数行対応)、送信ボタン、ファイル添付(将来拡張用としてUIのみ、または無効化)。

* **主要なアクション**:
  * ユーザーがテキストを入力し送信すると、LLMからのストリーミング応答がリアルタイムで描画される。
  * AIは以下(1)〜(4)を満たした場合(環境設定が未入力の場合は(5)も)、「十分な要件が揃いました」と判断する: (1)目的・課題が明確、(2)コア機能が最低1つ以上「誰が・何を・なぜ」のレベルで具体化、(3)想定ユーザー像の把握、(4)MVPスコープ(今回作る/作らない)の認識合わせ、(5)技術的な強い制約・希望の有無の確認。十分と判断した際は、即座に生成へ進まず、まず構造化した要件サマリをチャット上に提示しユーザーの明示的な承認を求める。承認後(またはユーザーが手動で「設計書を生成する」ボタンを押下した際)、ローディングインジケーターを表示し、生成処理(SCR-005へ遷移)へ移行する。
  * **生成完了後の自己診断**: 4文書の生成が完了すると、AIはそれらを対象に自己診断(不足・不明瞭な点の洗い出し)を行い、指摘事項を「最重要/中程度/軽微」の3段階に分類してチャットに提示する(`sender='others'`の`chat_histories`行として記録。[内部設計書](internal_design.md) 3.2節参照)。ユーザーは各指摘についてチャットで回答するか、現状のまま確定するかを選べる。回答内容を反映して再生成すると、新バージョンとして保存される([内部設計書](internal_design.md) 3.2節「バージョニング方針」)。

### SCR-005: ドキュメントプレビュー画面

* **画面構成**:
  * **サイドメニュー**: ドキュメント種別の切り替えタブ
    1. 要件定義 (`requirements.md`)
    2. 外部設計 (`external_design.md`)
    3. 内部設計 (`internal_design.md`)
    4. 実装計画 (`implementation_plan.md`)
  * **メインエリア**: 選択されたドキュメントのMarkdownプレビュー（および分割画面によるリアルタイムプレビュー対応）。
  * **アクションバー**:
    * 「クリップボードにコピー」ボタン
    * 「Markdownファイル(.md)としてダウンロード」ボタン
    * 「チャットに戻る」ボタン
    * 「再生成する」ボタン
    * 「AIによる精査結果を見る」ボタン(指摘件数をバッジ表示。押下でチャット画面の自己診断メッセージ箇所にスクロールする)

* **主要なアクション**:
  * タブ切り替えによって瞬時に表示ドキュメントを切り替える。
  * コピーボタン押下時にトースト通知（「コピーしました」）を表示。

## 2.4 外部システム・API連携仕様

### 連携する外部サービス／API

* **LLMプロバイダーAPI (Gemini Flash-Lite。無料プラン想定。トークン上限超過時は`LLM_QUOTA_EXCEEDED`エラーとして扱う。[内部設計書](internal_design.md) 3.4節参照)**
  * **用途**: チャットの壁打ち（対話生成）、最終的なMarkdownドキュメント一括生成。
  * **認証方式**: Bearer Token (API Key) をFastAPIの環境変数として安全に管理。クライアント側からは直接露出させない。
  * **データ連携タイミング**: 
    * ユーザーのチャット送信時（都度呼び出し・ストリーミング）
    * ヒアリング完了時のドキュメント一括生成時（非同期タスクによるバックグラウンド実行）

## 2.5 データ入出力仕様

### 1. ユーザー入力バリデーション (チャットメッセージ)

* **受付フォーマット**: UTF-8 テキスト文字列
* **バリデーションルール**:
  * 必須入力（空文字不可）
  * 最大文字数: 5,000文字 / 1メッセージ
  * 不正なスクリプトタグやインジェクション文字列のサニタイジング（フロント・バックエンド双方で実施）

### 2. プロンプトテンプレート選択データ (JSON)

* **データ構造例**:

```json
{
  "template_id": "web_app_standard",
  "name": "Webアプリケーション標準",
  "target": "SaaS・BtoC/BtoB Webサービス",
  "system_prompt": "あなたは優秀なシステムアーキテクトです...",
  "default_environment": {
    "languages": ["TypeScript", "Python"],
    "frameworks": ["Next.js", "FastAPI"],
    "databases": ["PostgreSQL"],
    "deploy_targets": []
  }
}
```

### 3. 初期ヒアリング入力データ (JSON)

SCR-004の初期ヒアリング入力(2.3節参照)を送信する際のペイロード。`system_overview` と `goals_raw` は必須(空文字不可)、他は任意。初期入力の段階では箇条書きへの分解やカテゴリ分けを求めず、自由記述のまま受け取る(構造化はチャット内でAIが行う)。

* **データ構造例**:

```json
{
  "system_overview": "社内の備品予約を一元管理したい",
  "goals_raw": "誰がいつ何を予約したか一覧できるようにしたい\n予約の重複を防ぎたい",
  "notes_raw": "既存のExcel管理からの移行を想定",
  "environment": {
    "languages": ["Python", "TypeScript"],
    "frameworks": ["FastAPI", "Next.js"],
    "databases": ["PostgreSQL"],
    "deploy_targets": ["AWS"]
  }
}
```

* **バリデーションルール**:
  * `system_overview`: 必須・空文字不可・最大全角200文字・フォーマット(箇条書き等)は強制しない
  * `goals_raw`: 必須・空文字不可・最大全角80文字・フォーマット(箇条書き等)は強制しない
  * `notes_raw`: 任意(null可)・最大全角400文字
  * `environment`: 任意(null可)。各配列は空でもよい

### 4. ドキュメントエクスポート出力仕様

* **出力ファイル形式**: Markdown (`.md`)
* **文字コード**: UTF-8 (BOMなし)
* **ファイル命名規則**: `{project_name}_{document_type}_{YYYYMMDD}.md`
  * 例: `devex_app_requirements_20231025.md`
