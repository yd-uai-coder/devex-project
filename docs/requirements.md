# 要件定義書：Devex

## 1.1 プロジェクトの目的・背景

* **解決したい課題**:

  * システム開発の初期フェーズ（要件定義〜実装計画）において、ドキュメント作成の工数やスキル不足に悩む開発者やプロジェクトマネージャーが多い。

  * 要件のヒアリングからドキュメント化までのプロセスが属人化しやすく、時間がかかる。

* **目指すゴール**:

  * AI（LangChain等）を活用した対話型インターフェースを通じて、ユーザーのアイデアや要望を引き出し、高品質な「要件定義」「外部設計」「内部設計」「実装計画」のMarkdownテキストを自動生成・出力するシステム（Devex）を構築する。

## 1.2 ターゲットユーザー・利用シーン

* **主なユーザー層**:

  * システムエンジニア、ITコンサルタント、プロジェクトマネージャー

  * 個人開発者、スタートアップ企業の創業者

* **想定される使用シチュエーション**:

  * 新規プロジェクトの立ち上げ時、頭の中にあるアイデアを構造化された設計書に落とし込みたい時。

  * クライアントからのヒアリング内容をベースに、素早く初期ドキュメントのドラフトを作成したい時。

## 1.3 システム化の範囲（In Scope / Out of Scope）

* **今回開発する範囲（In Scope）**:

  * ユーザーとAIによるチャット形式のヒアリング機能

  * 初期ヒアリング入力時の参考資料アップロード(最大3ファイル、txt/Markdown/PDF)とその内容の読み込み

  * ヒアリング内容に基づく「要件定義」「外部設計」「内部設計」「実装計画」のMarkdownテキスト自動生成機能

  * 生成されたMarkdownテキストの閲覧・コピー・ダウンロード機能

  * ユーザーセッション管理およびチャット履歴・生成ドキュメントのデータベース保存

* **今回は開発しない範囲（Out of Scope）**:

  * 生成された設計書から自動でコード（Gitリポジトリ等）を生成する機能

  * 外部プロジェクト管理ツール（Jira, Redmine, Notion等）への直接連携機能

  * マルチテナントによる複雑な企業間権限管理機能

## 1.4 機能要件（MoSCoW優先度）

* **Must have（必須機能）**:

  * チャットUI（Next.js）：ユーザーとAIが対話するための画面

  * LLM連携・プロンプト管理（FastAPI + LangChain）：ヒアリング内容を解析し、各設計ドキュメントをMarkdown形式で生成するロジック

  * **ドキュメント自己診断機能**：4種の設計書を生成した後、AIが各ドキュメントの不足・不明瞭な点を「最重要(実装着手に支障)/中程度(後続の設計判断に影響)/軽微(運用上の補足)」の3段階に分類して自己診断し、ユーザーに提示する。ユーザーは各指摘に対し、チャットで質問に答える(反映)か、現状のまま確定するかを選べる（本プロジェクト自身のCL進行ルール#28と同一観点。[外部設計書](external_design.md) 2.3節SCR-004参照）。

  * **参考資料の読み込み機能**：初期ヒアリング入力時に、参考資料を最大3ファイルまでアップロードできる。対応形式はtxt・Markdown・PDFの3種類のみ（Word/Excel/PowerPointは非対応。図を含む資料はPDF化してアップロードする）。txt/Markdownはそのままテキストとして読み込み、PDFはLLM(Gemini)のネイティブなファイル理解によりテキスト化する（図・レイアウトの解釈を含む）。元ファイルの実体は保持せず、抽出したテキストのみを永続化する（[外部設計書](external_design.md) 2.3節SCR-004、2.5節5項、[内部設計書](internal_design.md) 3.2節`intake_files`参照）。

  * ドキュメント出力・プレビュー機能：生成されたMarkdownを確認・エクスポートできる機能

  * データ永続化（PostgreSQL）：ユーザー情報、チャット履歴、生成された設計書データの保存

* **Should have（推奨機能）**:

  * 生成されたドキュメントのバージョン管理・履歴保持機能(※バージョン増分+直近3件保持というDBレベルの機構自体はMVPで実装済み。Should have分は、その上に被せる履歴閲覧・比較・復元のUI(SCR-006)を指す。[内部設計書](internal_design.md) 3.2節参照)

  * プロンプトテンプレートの選択機能（Webアプリ向け、API向けなど）

  * エラーハンドリングの堅牢化、ログの構造化・監視強化(※共通エラーレスポンス形式自体はMVPで実装済み。Should have分は、構造化ログ(`structlog`)・プロンプト本文を含めないプライバシー配慮・監視(エラー追跡/死活監視)の追加を指す。[内部設計書](internal_design.md) 3.4節参照)

* **Could have（あると良い機能）**:

  * 生成されたMarkdownのリアルタイムプレビュー機能（分割画面）

  * ユーザーの過去のプロジェクト傾向を学習したパーソナライズヒアリング

  * **UML設計図生成・レビュー機能(ステージ3)**：承認済み4文書を入力に、AIがコンポーネント図・ER図・処理別データフロー図(DFD)の意味モデル(構造化JSON)を生成する。「設計図を生成する」ボタンで起動し、React Flow上でレビュー・修正、承認後にdraw.io/SVG形式で出力できる。承認済みの図と要素表は内部設計書の該当セクションへ差し込んで補完する（[外部設計書](external_design.md) 2.6節、[内部設計書](internal_design.md) 3.2節`uml_diagrams`・3.3節、[実装計画書](implementation_plan.md) 4.1節ステージ3参照）。

    > **[Phase 14 で確定 ── 〈図の手直しの散文への反映(M9b)とアクティビティ図を実装しない〉]** 当初〈ステージ3内部のShouldとして、承認済みの図の手直しをAI修正案で基本設計・内部設計へ戻す機能(M9b、Phase 13b)と、アクティビティ図(旧Phase 14)を実装する予定〉→ 撤回。理由〈ステージ3はPhase 13で終了した。詳細設計モード(ステージ4)では文書を承認済みの意味モデルから組み立てるため、散文へ戻す修正案はほぼ不要になる。[実装計画書](implementation_plan.md) 4.1節参照〉。

    > **[Phase 24 で確定 ── 〈簡易ドキュメントモードの設計図(SCR-007)を提供しない〉]** 当初〈簡易ドキュメントモードの4文書生成の後に「設計図を生成する」から、内部設計書を入力にコンポーネント図・ER図・DFDを生成し、承認した図を内部設計書へ差し込む(ステージ3、Phase 7〜13)〉→ 撤回。理由〈詳細設計モード(ステージ4)が、段階2〜4で同じ図(DFD・ER・構成図)を段階の入力から作り、承認して詳細設計書に載せるようになったため、簡易モードからの設計図の作成は不要になった(Phase 24 完了後のユーザーの決定)。画面(SCR-007)・生成と履歴の API(`POST /uml/diagrams`・`/candidates`・`/generation-runs`)・内部設計書への反映(`/reflect`・`/embeds`・`/bundle`)を削除した。図の編集・検証・自動レイアウト・承認・出力の API とデータ辞書は、詳細設計モードが使うので残す。DB の`uml_generation_runs`テーブルと`uml_diagrams.scope`列は、既存のデータを残すため消していない。以前に図を反映した内部設計書のアンカー(HTML コメント)は、プレビューでは表示しない〉。


  * **詳細設計モード(ステージ4)**：要件定義・外部設計の後に、段階ごとに人が承認しながら詳細設計書を組み立てるモード。現行の4文書一括生成は「簡易ドキュメントモード」(旧称「概要モード」)として残す。モードはプロジェクトの作成時にダイアログで選び、プロジェクトに記録する(作成後は変えない)。詳細設計モードのヒアリングの後は、要件定義・外部設計の2文書だけを生成して段階へ進む。段階は、機能(処理)一覧 → 機能グループごとのDFD・データ辞書・処理概要表 → ER・テーブル定義・CRUD図 → 構成図(層)+モジュール一覧 → 選んだ処理の番号付き手順 → (任意)選んだ関数の処理ロジックの詳細 → 横断事項(例外・認証・トランザクション・ログの方針)と実装計画。各段階はAIが下書きし、人が確定・承認してから次の段階の入力にする。前の段階を直すと後ろの段階に「古い」表示を出し、作り直しは人が指示する。「重要な部分だけ書く」実務の原則に従い、手順・処理ロジックは人が選んだ処理・関数だけを対象にする。詳細設計書は、読むための自己完結のHTMLと、差分・AIへの入力用のMarkdown、図ファイルをまとめたzipで出力する（[外部設計書](external_design.md) 2.7節、[内部設計書](internal_design.md) 3.3節「4. 詳細設計モード」、[実装計画書](implementation_plan.md) 4.1節ステージ4参照）。

  * **実装手順書 + 実装可能性チェック(ステージ5)**：実装計画の作業単位ごとに、作成・変更するファイル(依存順・責務1行)・参照する設計(処理ID・手順ID などの ID で参照し、中身は書き写さない)・実装の要点・テスト観点(SUT・ドライバ・スタブ)・確認方法を記した実装手順書を生成する。その過程で、設計の不足・矛盾(未定義)を、決定論的な検証と AI の指摘の2層で、重要度3段階(最重要・中程度・軽微)に分けて示す。未定義は手順書の上では決めず、対象の段階へ戻って設計を直す。手順書は、人と AI Coding Agent のどちらが実装しても同じ中身とし、AI 向けには参照する設計を展開した版を出す。作業単位は、詳細設計モードの段階7の実装計画を機能ごとの縦割り・ID 付きに改めて、そのまま使う。段階5の手順から導くシーケンス図(読み取り専用)を、手順書と 05章に載せる。簡易ドキュメントモードでも、同じ形の手順書を作る(実装計画書の WBS を縦割り・ID 付きにする)。（[外部設計書](external_design.md) 2.8節、[内部設計書](internal_design.md) 3.3節「5. 実装手順書」、[実装計画書](implementation_plan.md) 4.1節ステージ5参照。方針は[`appendix/devex_implementation_procedure_guideline.md`](../appendix/concept-history.md#procedure-guideline)、決定の経緯は[`textbook/Phase-25/Phase-25-1.md`](../textbook/Phase-25/Phase-25-1.md)）

  * **ヒアリング改良 + 上流の構造化(ステージ6)**：ヒアリングの完了判定(5条件)を、観点の表で置き換える。観点は機能面(規模・目的・利用者・1日の流れ・コア機能・MVP の範囲・例外の場面・将来の拡張・技術スタック・体制)と、IPA 非機能要求グレードの6大項目(可用性・性能・拡張性・運用・保守性・移行性・セキュリティ・システム環境・エコロジー)で、最初に聞く規模に応じて必須が変わる。観点ごとに状態(ユーザーが決定・AI の提案を採用・未決・対象外)と根拠の発言を記録し、必須の観点がすべて未決以外になったら完了とする。AI は場面で問い(「止まったら何時間まで困らないか」)、選択肢ごとの結果(コスト・手間)とおすすめを示す選択肢カードを出す。決めるのは利用者で、カードを選ぶと「AI の提案を採用」になる。要件定義書・外部設計書は意味モデルから組み立て、要件に ID(`FR-001`・`NFR-001`・`CON-001`)と出どころ(ユーザー・採用・推測)を、画面・API に関係する要件ID を持たせる。要件 → 処理(詳細設計モードの段階1)・作業単位(簡易モードは実装計画書の WBS)を追跡し、処理の無い Must の要件を指摘する。（[外部設計書](external_design.md) 2.9節、[内部設計書](internal_design.md) 3.3節「6. ヒアリングと上流の構造化」、[実装計画書](implementation_plan.md) 4.1節ステージ6参照。決定の経緯は[`textbook/Phase-33/Phase-33-2.md`](../textbook/Phase-33/Phase-33-2.md)、見本は`appendix/structured-requirements-sample/`）

  * **変更影響分析・変更管理(ステージ7)**：設計の要素(要件・画面・API・処理・段階2〜8 の行)を ID の参照でつないだグラフから、ある要素を変えたときに見直しが要る要素を示す。たどり方は「処理を軸」(変更が届く処理に属する要素だけを示し、共有されるモジュールからは広げない。改名は直接の参照元だけ)、理由は参照の種類からシステムが書く(LLM は使わない)。何が変わったかは、段階は直前の承認の写しと、文書は前の版の model と比べて求める。段階の「古い」は今のまま残し、その中の見直しが要る要素に印を付け、すべて確認済みにすると承認し直せる。再生成の候補(段階5・6・8 の部分再生成)を示すが、自動では再生成しない。簡易ドキュメントモードは、内部設計書・実装計画書も意味モデルにしてから、段階8の単位への影響を示す。あわせて、ヒアリングで聞かれなかった側面(バックアップ・ログ・不正利用・削除)と、段階3・5 の生成の書き落としを直す。方針は[外部設計書](external_design.md) 2.10節、出発点の数字は[`appendix/measurements/stage7-baseline.md`](../appendix/measurements/stage7-baseline.md)(Phase 41)

  * **AI 設計レビュー + テスト設計(ステージ8)**：生成した設計を、生成とは別のモデル(Claude Sonnet)がレビューし、設計は書き換えずに指摘だけを返す。指摘は重要度(最重要・中程度・軽微)・原因(ヒアリング・設計・不整合)・対象の ID・引用・理由・改善案を持つ。人が指摘ごとに採用・却下・保留を決め、採用した設計・不整合の指摘は再生成の指示に入れ、ヒアリングが原因の指摘は観点を「未決」に戻してチャットで聞き直す(「AI に提案を求める」の答え)。レビューは簡易モードは4文書の生成の後、詳細設計モードは要件・外部の生成の後に自動で流れ、段階6・7 の承認の後はボタンで流す。レビューを使えるのは superuser だけで(初期値オフ)、オフのときと使えないときは今の自己診断を出す。テスト仕様書(結合・総合テスト。正常・異常・境界・セキュリティ・非機能、要件 ID → テスト ID)を両モードで生成する。品質はベースラインと同じものさしで測る。方針は[外部設計書](external_design.md) 2.11節、出発点の数字は[`appendix/measurements/stage8-baseline.md`](../appendix/measurements/stage8-baseline.md)(Phase 51)

  * **使い勝手とアカウント・モデル設定の調整(ステージ9)**：ヘッダーからトップへの遷移・ログアウト・ログイン済みのとき認証ページを飛ばす・グローバルメニューの組み直し(ログインの状態で認証の項目を出し分け、メニューからの新規作成もモードを選ぶ)・チャットを最下部から表示。ダッシュボードでプロジェクトを削除(生成中も削除できる)・タイトルの部分一致で検索・モードと進行状態で絞込み・10件ずつのページネーション。文書と詳細設計の画面にも削除ボタン。マイページでユーザーネーム・メールアドレス・パスワードを変え(メールは今のパスワードで確かめて即時に変える)、用途(チャット・生成・レビュー・判定)ごとに AI(Gemini・Claude)とモデルを選び、provider ごとの API キーを登録する(保存のときに有効かを確かめ、暗号化して保存)。`.env` のモデルとキーをシステムの既定値とし、自分のキーがあればそちらを優先する。superuser でなくても、自分の Claude キーを登録すればレビューを使える(既定のキーでのレビューは superuser だけ)。あわせて、ステージ8 までの申し送り(生成の失敗・生成中の知らせ、作り直した段階の承認、ヒアリングとテスト仕様書の質、設計の検証)を扱う。方針は[外部設計書](external_design.md) 2.12節(Phase 61)

  * **Google 認証(ステージ10)**：Google アカウントでログイン・登録できる(Google Identity Services の ID トークンを API が検証し、今の JWT と refresh cookie を出す)。同じメールのアカウントが既にあれば、最初の1度だけパスワードで確かめてから紐付け(登録でメールを確かめないため、先に他人が登録していた場合の乗っ取りを防ぐ)、その後は Google とメールのどちらでもログインでき、プロジェクトも引き継ぐ。マイページから連携・解除でき(解除はパスワードがあるときだけ)、Google だけのユーザーはパスワードを「設定」できる。Google のメールが確認されていない ID トークンは断る。あわせて、ステージ9 までの申し送り(開発環境の登録・ログインの上限・削除したプロジェクトの表示・新規作成の後の一覧・押せないボタンの見た目・負荷のときだけ落ちるテスト)を扱い、最後にステージ9 と合わせて本番へ反映する。方針は[外部設計書](external_design.md) 2.13節(Phase 73)

  * **合意と変更の一巡(ステージ11)**：クライアントとの合意を基準に、変更要求(CR)を受付から再検証まで1本通す(詳細設計モード)。開発者が、ある時点の文書と段階を束ねた合意済みの版(B-1, B-2…。合意の時点の内容を写して凍結し、相手・日時・打ち合わせのメモ・理由を残す。相手は空でもよい)を作る。CR は、タイトル・内容・背景(出どころ・日付・メモ)・対象の要件 ID・基準の合意済みの版を持ち、下書き → 説明済み → 合意 / 却下 → 反映済み → 検証済み(ほかに取り下げ)と進む。遷移ごとの日時が時系列になる。合意の前に、対象の要件から影響の予測を出し(今の変更影響分析のたどり方。LLM なし)、変更の説明書(md。CR の内容と背景・対象の要件・影響の一覧・関わる未決事項・影響を受ける作業単位とテストの数)を出す。説明書には、任意で LLM の要約を足せるが、要約は人が確かめるまで出力に載らない(要件 ID・数字の照合と、CR が変わったときの「古い」の印を持つ)。合意した CR は、レビューの指摘と同じ経路で再生成の指示に入れて反映し、生成の版に CR と生成したモデルを残す。反映の後の実際の印を予測と並べ、印がすべて確認済みになれば検証済みにできる(設計レビューは任意)。簡易ドキュメントモードでは CR の画面を出さない。方針は[外部設計書](external_design.md) 2.14節、出発点は[`appendix/measurements/stage11-baseline.md`](../appendix/measurements/stage11-baseline.md)(Phase 80)
  * **合意の精度(ステージ12)**：合意した中身が、CR の範囲の外の再生成で変わらないようにする(詳細設計モード)。要件定義書の行・利用者と使う場面(1.2)・外部設計書の画面・API・外部連携について、行ごとの合意の記録(合意した中身・出どころ〈合意済みの版 B-n / 「採用にする」/ CR-n〉・日時。追記型で、行の変更の履歴になる)を持つ。再生成の後に、合意済みの行(CR の対象と、CR の予測が届く画面・API を除く)を合意の形にコードで戻し、戻した件数を残す。合意済みの行には、出どころに観点の状態の上限をかけ直さない(「採用にする」が再生成で「推測」に戻らない)。推測の要件・推測の利用者・根拠が未決の観点を、確認事項の一覧に毎回決定的に集め、行ごとに「決める機会」と状態を持つ(推測の採用率〈一覧で確認済みにした割合〉もここから数える)。版の巡回で、合意済みの版が指す版も消さない。あわせて、CR で作り直した段階の承認で付く印を CR に結び、新しい要件を足す CR は人が選んだ起点から影響を予測する。方針は[外部設計書](external_design.md) 2.15節、出発点は[`appendix/measurements/stage12-baseline.md`](../appendix/measurements/stage12-baseline.md)(Phase 90)

  * **説明とすり合わせ(ステージ13)**：クライアントが、変更の説明書だけで CR の合意・却下を判断できるようにする(詳細設計モード)。変更の規模(作業単位・ファイル・テスト・画面・API の数)を予測から決定的に数え、束の段階が古い・要件と処理がつながらない・テスト仕様書が無いときは「数えられない」と理由を出す。CR に2〜3の案(選択肢カードの形。名前・変更後の案・結果・おすすめと理由。案ごとの規模)を開発者が書き、LLM の下書きは確かめるまで出さない。説明書はクライアント向けに決定的に直す(推測と未決を「合意の前に確かめたい点」の問いに・要素は名前を先に)。CR ごとの共有リンク(推測できないトークン・期限・取り消し。アカウントは要らない)で、クライアントが説明書を読み、名前を書いてコメント・案の選択・合意 / 却下でき、その結果は CR の合意の記録(相手・見た説明書の版)に入る。リンクを作ると CR は説明済みになり、直して下書きに戻るとリンクは止まる。あわせて、名称を言い換える偽の LLM で名前の照合を確かめ、外部連携の重複・推測の利用者のキー・段階2・3・7 の処理 ID の切れ・CR で変わった行の確認事項・起点の種類・束の一覧の CR・巡回で消えた版の戻しの履歴・DFD だけを直した承認を扱う。方針は[外部設計書](external_design.md) 2.16節、出発点は[`appendix/measurements/stage13-baseline.md`](../appendix/measurements/stage13-baseline.md)(Phase 100)
  * **変更の取り込み(ステージ14)**：議事録・メール・資料を途中から足し、合意済みの内容と違う点を拾って CR の下書きにする(詳細設計モード)。資料は貼り付けか txt / md / pdf で、種類(議事録・メール・資料)・題・日付を付ける。最新の束の写しと比べ、違い(種類・対象の合意済みの行・内容・資料の根拠の引用)を一覧にする。引用が資料に無い・対象が束に無い違いは出さない(理由とともに残す)。開発者が違いを選んで1つの CR の下書きにまとめ、捨てた違いは理由を残す。束の後に反映した CR があれば「束が古い」と、取り込み・CR の作成・共有リンクの作成で知らせ、規模の表に基準の束と鮮度を出す。方針は[外部設計書](external_design.md) 2.17節、出発点は[`appendix/measurements/stage14-baseline.md`](../appendix/measurements/stage14-baseline.md)(Phase 111)

* **Won't have（見送り機能）**:

  * 音声入力によるヒアリング機能

  * リアルタイムでの複数人同時編集機能（ドキュメントの共同編集）

## 1.5 非機能要件

* **パフォーマンス・応答性**:

  * チャットの応答速度：一般的なLLMのストリーミング応答に対応し、ユーザーがストレスなく対話できること。

  * ドキュメント生成処理：ヒアリング完了後の設計書一括生成処理において、タイムアウトを防ぐ非同期処理の導入。

* **セキュリティ・権限管理**:

  * ユーザー認証・認可の実装（JWT等を用いたセキュアなセッション管理。アクセストークン30分・リフレッシュトークン14日、詳細は[内部設計書](internal_design.md) 3.1節参照）。

  * 入出力データ（機密性の高い要件定義データ）の適切な保護とプライバシー配慮。

* **運用・保守・拡張性**:

  * LLMのモデル変更やプロンプトのチューニングがバックエンド（FastAPI + LangChain）で容易に行えるアーキテクチャ設計。

  * コンテナ化（Docker等）によるデプロイの容易性と拡張性の確保。

* **アクセシビリティ**:

  * 全画面のフォーム入力について、ラベルとコントロールを`htmlFor`/`aria-labelledby`で関連付け、エラー表示には`aria-invalid`・`aria-describedby`・`role="alert"`を付与する。

  * アイコンのみのボタンには`aria-label`を付与する。

  * 主要な操作（ログイン、プロジェクト作成、チャット送信、ドキュメントダウンロード等）はキーボード操作のみで完了できること。

## 1.6 制約条件・前提条件

* **技術スタックの制約**:

  * フロントエンド: Next.js

  * バックエンド: FastAPI + LangChain

  * データベース: PostgreSQL

* **外部APIの前提**:

  * LLMプロバイダーは**Gemini Flash-Lite**を採用する（無料プラン想定）。**(ステージ9で拡張)** 既定は Gemini Flash-Lite のまま、ユーザーが用途ごとに Gemini(Flash 系・Flash-Lite 系)・Claude のモデルと自分の API キーを選べるようにする([外部設計書](external_design.md) 2.12節)。以下は既定の前提。APIキーが確保されていること。無料枠のトークン上限を超えた場合はエラーとなる点を前提とし、その失敗モードはエラーハンドリングに組み込む（[内部設計書](internal_design.md) 3.4節、[実装計画書](implementation_plan.md) 4.4節リスク3参照）。

* **スケジュールの前提**:

  * MVP（実用最小限の製品）としてのコア機能（チャット〜4種のmd生成）を優先して開発する。
