## 3. Phase 7 で「AI が本体へ直接実装」に切り替えた理由

これまで記録に無かった理由を、ユーザーの回答から記録する。

- 手で実装しても、設計の理解は思ったほど実感できなかった。
- そこで、いったん自動実装で先に完成させ、**完成品から仕様を追う**方針を重視した。
- 旧ルールの納期モードでは、工程をあまり省けなかった。さらに納期モードでは、テスト観点(#14 の SUT/ドライバ/スタブ)が教材から省かれた。テストは設計理解の肝なので、省きたくない。**学習モードと納期モードで教材の中身を変えたくない**。

このため、モードの違いは「教材の厚さ」ではなく「誰が本体へ実装するか」だけにした。旧ルールとの対応は、Phase 1〜6 = off、Phase 7〜24 = on。

### T2 の改訂(samples の作成を自動実装モードで変えない)

T2 の決定のあと、ユーザーが「samples の内容を自動実装モードの on/off で変えず、on でも samples の作成・追記を行う」と決めた。
- 理由: 教材の中身は on/off で変えない(#21)。samples は教材のコードの本体なので、それも on/off で変えない。教材を実装手順書のサンプルにする構想(1節)とも合う。
- 改訂: #3・#9 の運用注記、#21 の on、#29 の on の扱い。T2 で残した `phase-<N>` の git タグと、Phase 完了時の検査はそのまま使う。
- 道具: `samples_check.py` に `--api-since`・`--ui-since` を足し、前の Phase の版以降に本体で追加・変更したのに samples に無いファイル(作り忘れ)も検査するようにした。
- 遡及: 不要だった。Phase 7〜24 の on の成果物は、すべて samples にある(T2 の後に on の Phase は無い)。

## 6. → Devex 仕様への示唆(#25)

- **教材を実装手順書のサンプルにする。** 次のステージの「実装手順書」は、CL 教材の構造をひな形の候補にする。
  - introduction: 目的・前提・章一覧・実装前チェックリスト・完了チェック・写経順序・未消化の申し送り
  - 章: 目的・作成/更新するファイル(依存順。#30)・要点・テスト観点
- **手順書の中身は、実装者が人か AI かで変えない。** 自動実装モードを on/off にそろえた判断(教材の中身は変えず、変わるのは誰が実装するかだけ)は、実装手順書の要件にもそのまま使える。
- **作業単位の表を、教材と生成文書で共通にする**(ゴール3。[`goal3-comparison.md`](goal3-comparison.md))。実装前チェックリストと段階7のタスク表は同じ形にそろえられる。列は「作業単位・対象の処理ID・作成・変更するファイル(依存順)・役割1行・確認方法」。生成側に無い確認方法は、テスト設計の生成として今後の機能追加で検討する(ユーザーの判断)。
- **申し送りを手順書の要素にする。** #37 の「未消化の申し送り」は、手順書でも「前の手順から持ち越した未決事項」として独立した節にすると、見落としを防げる。

## 7. AI の所見(補足)

ユーザーの回答とは別に、AI が記録から気づいた点を、課題と提案の対で書く。組み込むかどうかはユーザーが判断する(#10)。

- **課題: on の Phase で、学習をどう回収するかが決まっていない。** 「完成品から仕様を追う」ための読み方の手がかりが、教材の側に無い。#19 の「コア」の印も廃止した。
  - 提案: 実装手順書のサンプルとしても使えるよう、章ごとに「読む順番」または「設計判断の要点」を1〜3行で示す欄を、#13 の解説の先頭に置く。
- **課題: on の Phase では、本体が先に変わり、samples が後追いになる。** そのため T2 のずれが起きやすい(反映漏れ・コメントへの経緯の混入)。
  - 提案: T2 を検討するときに、「samples を本体からの差分で自動生成する」案(Phase 23 で使った、本体の差分にタグを付けて samples に当てるスクリプトの一般化)も比べる。
  - 結果: T2 で比べ、(c)「on では samples に新規ファイルを作らない」が採用された。差分を当てるスクリプトは、既存の samples を追従させる補助(`tools/tagmerge.py`)として残した。その後、ユーザーの判断で「on でも samples を作る」に改めた(4節の後の「T2 の改訂」)。
- **課題: #18(1セッション = 1 Phase)と実際の運用がずれていた。** ただし、それで支障が出たという記録も無い。
  - 提案: 次のステージの最初の Phase で実際のセッションの区切りを記録し、ステージ完了時の振り返りで #18 を見直す。
  - 結果(ステージ5): Phase 25〜32 はすべて1セッションで、全体テストも完了時だけだった。#18 は変えず、記録を続ける(9節 S3)。

### 11.2 見立て

- **精度は上がっている。ただし、上がったのは「着手時の推奨の採用率」ではない。** 採用率はステージ4の時点で既に高く、ほぼ推奨どおりだった。下がったのは次の2つで、所感の「指摘・修正が少ない」はこの2つに対応する。
  - **計画の変動**: ステージ5・6 では0になった。
  - **完了後の調整**: 新しい種類の UI(P35)を除くと、ステージ4の Phase あたり約1回から、ステージ5は約0.25回、ステージ6は約0.6回に減った。
- **推奨と違った選択の「向き」が変わった。** ステージ3・4 の外れは、推奨そのものが外れていた例である(実務の裏付けなしに「機能ごとの部分図」を勧めて撤回した。2節 T8)。ステージ5・6 の外れは、推奨の方向は合っていて、ユーザーが範囲を狭める・広げる・基準を厳しくする選択をした例である(32 の範囲、33-2・39)。

### 11.3 理由(記録から裏付けられるもの)

- **(a) 未確定事項の先出し。** ステージの最初に仕様診断(#28)を行い、Phase ごとの未確定事項を表にしている([25-4](../Phase-25/Phase-25-4.md)・[33-5](../Phase-33/Phase-33-5.md))。そのため、着手時の相談は「選択肢 + 推奨」に絞られ、分割・撤回が無くなった(9節 S4・10節 R6)。この効果は、ステージ4(着手時に範囲を相談し、そこで分割した)と比べるといちばん大きい。
- **(b) 決定の蓄積が、次の提案の文脈になる。** 次のものを AI が着手時に読むので、過去に外れた型を繰り返さない。
  - [decision digest](../decision-digest.md)
  - #37 の「未消化の申し送り」
  - ルール(#21・#38)
  - 実務に合わせる設計の方針(Phase 13 の撤回から生まれた)

  ステージ5・6 では、実務の裏付けの無い提案による撤回が起きていない。
- **(c) 既存の型を再利用できる。** ステージ5・6 の多くは、ステージ4までに作った型(段階・`uml_diagrams`・検証の指摘・`model`)の上に足す作業だった。逆に、型の無い新しい種類の UI(P35 の対話カード)では往復が4回要った。新規性の高いところで外れやすい、ということの裏返しである。
- **(d) 客観的な基準を置いた。** ステージ6は [33-1](../Phase-33/Phase-33-1.md) のベースラインと Phase 39 の再測定で、主観でなく数字で合否を決めた。判断が数字に寄るほど、画面を見て直す往復は減る。

### 11.4 差し引くべき要因

- **ユーザーが推奨に寄った可能性。** 採用率の高さは、「推奨が良くなった」だけでなく「ユーザーが推奨を選ぶようになった」でも説明できる。そこで、採否と独立な指標で裏を取った。
  - 本番での確認の指摘: ステージ4〜6 ですべて0
  - ステージ6の効果測定の数字
  - 計画の変動: 0

  これらは推奨に寄ったかどうかに左右されない。一方で、ユーザーが推奨と違う方を選んだ例(33-2・39)も残っている。そのため、「推奨に寄った」だけでは説明しきれない。
- **記録の粒度。** 11.1 のとおり数字は概算で、ステージ3以前は書き方がさらに粗い。
- **AI のモデルの版。** モデルの版の違いは記録に無いので、評価できない。
- **題材の違い。** ステージごとに作ったもの(図の生成・詳細設計・手順書・ヒアリング)が違うので、件数の単純な比較には限界がある。

### 11.5 → Devex 仕様への示唆(#25)

- **「AI の提案 → 人の採否 → 結果」を記録すると、提案の質を追える。** この構造は、Devex の要件の出どころ(ユーザー / 採用 / 推測。10.3)と同じ形である。Devex でも、推測の要件があとで採用されたか・直されたかの割合を数えれば、生成の質の指標にできる(ペルソナによる効果測定の補完)。
- **採否と独立な指標を必ず添える。** 採用率だけでは「人が AI に寄った」と区別できない。Devex の生成の質も、採用率だけでなく、実装可能性チェックの未定義の件数のように人の判断に依らない数字と並べて見る。

### 11.6 AI の所見(補足)

組み込むかどうかはユーザーが判断する(#10)。

- **課題: 新しい種類の UI・操作感で、完了後の往復が増える**(P35 の4回)。ほかの Phase は既存の型の上にあり、往復は少ない。
  - 提案: 既存の型が無い UI を含む Phase は、着手時の相談で「操作の流れ(1往復の手順)」を短い文か見本で先に見せ、そこで決める。
- **課題: 指標を数えるたびに、書き方の揺れを読み解く手間がかかる。** 今回は「4つとも推奨どおり」のような一括の書き方を読み解いて数えた。
  - 提案: 印は付けない(ユーザーの判断)。ただし、AI が q_a を書くときは、推奨と違った項目を1項目ずつ書く(今もおおむねそうしている)。

### 12.4 → Devex 仕様への示唆(#25)

- **変更の影響は、CL の「後続 Phase での改訂」(#12)と同じ問題である。** CL では、後の Phase が前の Phase を変えたら、samples のタグ・introduction の「後続 Phase での改訂」・digest に記録して下流が追えるようにする。Devex の変更影響分析は、これを文書の要素の単位で機械的に行う(承認時の写しとの差分 → 下流の要素に印 → 確認済みにして承認し直す)。CL の #12 も「どの章・どのファイルに届くか」を人が判断しているので、教材の要素のグラフがあれば同じ仕組みで印を付けられる。

### 13.4 → Devex 仕様への示唆(#25)

- **検証は「決定的 → 安いモデル → 強いモデル → 人」の段階で組むと、費用と見落としの両方が下がる。** ステージ8では、手順書・テスト仕様書は決定的な検証だけにし、設計書は Sonnet がレビューし、「直ったか」は版と行の比較(L0・L1)で絞った残りだけを Haiku に渡した。CL の Phase 完了時も同じ形をしている(`samples_check.py`・`link_check.py` → AI の監査 → ユーザーの確認)。生成文書のテンプレート(`prompt_templates`)にも、どの項目を決定的に検証し、どこから LLM のレビューに渡すかの欄を置く。
- **「必要な項目の一覧はコードが決め、中身を LLM が埋める」と、件数の漏れが消える。** テスト仕様書は、API・エラー・NFR・画面から必要なテストの一覧をコードが組み、LLM が中身を書いた(実 Gemini で一覧と同数・指摘0)。flash-lite は指示が増えると出力が縮む(51-1 の (d))ので、網羅は指示でなく構造で担保する。CL の実装前チェックリスト(#11)のテスト観点も、章のファイルの一覧(#13・#15)から機械で並べられる。
- **採用した指摘の追跡は、#37 の「どこで解決したか」の機械化に相当する。** Devex は、採用した指摘の対象の版・行が変わったかを決定的に見て「未対応」を示す。CL の申し送りは人が「解決した章」を1行書くが、教材の要素に安定キーがあれば同じ比較で未対応を拾える。
- **原因が上流にある指摘は、上流へ戻す道が要る。** 指摘の原因が「ヒアリング不足」なら観点を open に戻して聞き直す(Phase 54)。CL でも、実装の摩擦が前の Phase の設計に原因があるときに #12 で前の Phase を改訂する。生成文書の指摘の型に「原因の段階」と「戻し先」を必須の欄として持たせる。
- **正解を先に書いて測る型は、ステージをまたいで使い回せた。** 51-1 の正解表(仕込み + 元からある欠陥)と Phase 58 のテスト仕様書の正解例は、測る前に書いた。ステージ6・7 の測定の型(10.3・12.4)が、レビューの再現率の測定にもそのまま使えた。

### 14.4 → Devex 仕様への示唆(#25)

- **使い勝手の基本機能は、ドメインの機能の後から要望として来る。** ステージ9の要望(削除・検索・絞込み・ページ送り・アカウントの変更・ログアウト・ログイン済みの振り分け)は、どれもドメインに依らない。最初の要件定義(ステージ1)では聞いていなかった。Devex のヒアリングに、ドメインに依らない基本機能の観点の表(一覧の削除・検索・絞込み・アカウント設定・ログアウト・権限ごとの出し分け)を置き、MVP に入れるかを先に聞く。

- **生成の質はモデルに依る。** ステージ9でモデルをユーザーごとに選べるようにした。レビューの回は `model` を記録しているが、文書の版には生成したモデルが無い。文書の版にもモデルを残すと、質の比較・回帰の測定(ステージ6〜8 の測定の型)にそのまま使える。

### 15.4 → Devex 仕様への示唆(#25)

- **外部サービスの準備は、担当と期限を持つ前提作業として書く。** OAuth クライアント・同意画面・生成元は、コードの外でユーザーが行う作業で、遅れると確認がずれた(Q3)。Devex の実装計画に「前提作業(担当・どの作業の前か・無いときの代わり)」の欄を置く。代わりの例が、今回の偽の検証である。
- **セキュリティの要件は、利用者の希望と脅威を対で聞く。** 紐付けは、ユーザーの希望(既存のプロジェクトを引き継ぐ)と、登録でメールを確かめないことによる乗っ取りの準備(pre-hijacking)の両方から決まった(73-1)。初めの推奨は脅威だけを見て、希望を満たしきれなかった。Devex のヒアリングで認証・権限の要件を聞くときは、「何ができてほしいか」と「何を防ぐか」を対の問いにする。
- **戻せるかどうかを、実装計画の項目にする。** マイグレーション `c4f8a2e6d1b9` の downgrade は、Google だけの利用者がいると止まり、通っても連携を全部消す。そこで、ステージ10だけを戻すときはコードだけを戻すことにした([79-3](../Phase-79/Phase-79-3.md))。ステージ9でも、削除の印の行が downgrade で戻る点を書いた。Devex の実装計画のデータ変更の行に「戻し方と、戻すと失うもの」を置く。
- **出した版と記録の版の一致を、受け入れの確認に入れる。** Q1 では、本番で確かめた記録はあっても、origin に版が無かった。Devex の受け入れ確認(実装計画の最後)に、「どの版を出したか(コミット・タグ)」と「それがリポジトリにあるか」の確認を置く。

### 16.4 → Devex 仕様への示唆(#25)

- **保存の上限は、「参照されているものは消さない」と対で書く。** 文書の版の巡回(直近3件)は、ステージ11 の前からの決まりで、CR がその版を指すようになっても見直されなかった(Q5)。Devex の内部設計で保存の上限・巡回・削除を書く行に、「その行を指すもの(参照元)と、指されているときの扱い」の欄を置く。
- **モードや権限で限る機能は、全入口をテスト観点にする。** 仕様は「詳細設計モードだけ」だったが、作成だけが断り、読む API と画面は通った(Q6)。Devex のテスト仕様書で、対象を限る要件には「書く・読む・画面・URL の直開き」を並べた観点を自動で足す。
- **測定は、順序の組み合わせを含める。** 決定的な測定と E2E は「1件の CR を最後まで」通し、実 LLM の一巡が「CR の後に別の再生成」を挟んで漏れを見つけた(Q5)。Devex の実装計画の受け入れ確認に、「対象の流れの後に、別の流れを挟んでも結果が残るか」の行を置く。
- **合意した後も、LLM の出力は揺れる。** 文が同じでも、出どころ(採用 → 推測)が変わり、関係の無い印が付いた(P89)。合意を起点にするなら、合意した行を再生成で動かさない保護が要る。ステージ12 の中心の入力にする。
- **機械の照合は関門の補助で、関門そのものではない。** 要約の照合は ID と「5節に無い数字」を拾うが、5節のどこかにある数字の取り違え(「10件」が日付の `10` に紛れる)は拾わない([効果測定](../../appendix/measurements/stage11-effect.md))。Devex で LLM の文を成果物に入れるときは、照合の結果を示したうえで、人の確認を必ず通す形を型にする(ステージ11 の説明書の形)。

### 16.5 AI の提案の精度(#39)

- **本番での確認の指摘**: ―(ステージ15 の反映の後に埋める)。

**見立て**: 推奨と違った選択の多くは、ステージの題材(合意と変更をたどれること)に沿って、ユーザーが「記録・構造を残す」側を選んだもの(P82・P83)で、推奨そのものの外れではない。外れに近いのは、完了後の調整の2件の中身である。どちらも AI の推奨や実装が拾わなかった漏れ(読む API のモード・版の巡回と CR の参照)で、ユーザーの画面確認と実 LLM の一巡で見つかった。ステージ10 の完了後の調整0 は、Phase の中で AI がブラウザで確かめた効果だったが、ステージ11 の P87・88 は画面確認を P89 へ積んだ(#37 の運用注記)ので、その効果が Phase の中では働かなかった。

**理由**(11.3 の (a)〜(d) の裏付け):
- (a) 未確定事項の先出し: 80-4 の表の未確定事項を、各 Phase の着手時に4問ずつ決め、計画の変動は0。
- (b) 決定の蓄積: Phase 85 の申し送り(段階の承認の印・文書の側の要素)を P86 の4問にそのまま使った。各 Phase が前の Phase の申し送りを入力にした。
- (c) 既存の型の再利用: 予測は既存の `impact_of`、反映は指摘(`finding_ids`)と同じ経路、比較は印の仕組み、測定は Phase 80 の `measure.py` を import した。
- (d) 客観的な基準: 効果測定を Phase 80 のベースラインと同じ材料・同じ表で行い、7段・4つの問いの ○ と、予測の6件の一致で判定した。

**差し引くべき要因**:
- **本番の指標が無い**: 採否と独立な指標は、効果測定・全 E2E 10件の成功(2回)・ユーザーの実 LLM の一巡だけ。本番での確認はステージ15 まで無い。
- **題材の違い**: 新しい概念(束・CR・6つの状態)を一から作るステージで、既存の画面の微調整より相談の分かれ目が多い。Phase 80 に決めることが集まったのは、ステージ7・8 と同じ型。
- **推奨に寄った可能性**: P84〜88 がすべて推奨どおりだが、P83 は比較の後に推奨と違う側を選び、P89 は2件が推奨と違うので、寄っただけでは説明しきれない。

### 16.6 AI の所見(補足)

組み込むかどうかはユーザーが判断する(#10)。

- **課題: 画面確認を最後の Phase へ積むと、Phase の中で見つかるはずの漏れが完了後の調整に回る**(16.5)。

### 17.4 → Devex 仕様への示唆(#25)

- **「LLM の揺れ」と見立てる前に、決定的な経路を疑う。** P89 で LLM の揺れとした現象は、規則の再適用(`cap_source`)だった(Q2)。Devex の内部設計で LLM の出力を後処理する行には、「同じ入力で再生成したとき、後処理だけで結果が変わる経路があるか」を書く欄を置く。実装計画のベースラインには、LLM の揺れと決定的な経路を分ける手順(同じ版を後処理だけで流し直す)を入れる。
- **名前で同一性を決める要素は、LLM の言い換えで別物になる。** 外部連携のサービス名(P93・99)、推測の利用者の名前(P94)、段階1 の API でない処理の名称(P99 の段階5 の不具合)と、同じ型が3か所で出た。Devex の内部設計で要素のキーを決めるときは、「キーが LLM の書く文か」を問い、そうなら ID を振るか、言い換えたときの照合の規則(同じ種類 + 関連する要素)と、照合できなかったときに人が付け替える手段を、対で書く。
- **合意を守る仕組みは、プロンプトとコードの両方に置く。** 保護(コード)は毎回の利用者の言い換えを戻し、プロンプトの「合意済み」の印は外部連携の言い換えそのものを止めた([効果測定](../../appendix/measurements/stage12-effect.md))。片方だけでは、戻す件数が増えるか、言い換えが残る。Devex の外部設計で「変えてはいけない行」を扱う要件には、生成への指示と生成の後の検査の2行を置く。
- **追記型の記録は、測定の材料にもなる。** 段ごとの書き出しを取り逃しても、日時つきの合意の記録と版の保護の記録から流れを組み直せた(Q7)。Devex の内部設計で履歴を持つ表は、上書きでなく追記にし、日時を持たせる(ステージ11 の CR の時系列と同じ型)。

### 18.4 → Devex 仕様への示唆(#25)

- **規模を出す前に、基準の版の鮮度を確かめる。** CR-3・CR-4 は基準の束が古く「数えられない」、CR-5 は段階が古く「0件(少なく出ることがある)」になった(Q2・Q6)。Devex の外部設計で「数を見せて判断させる」画面には、数の横に「基準がいつの版か・古ければ何を作り直すか」を出す欄を置き、内部設計で数える関数には「数えられない」と「古くて少ない」を別の結果として返す規則を書く。
- **完了の判断基準の題材は、新しい仕組みが働く条件を満たすかを、要件確認で試す。** マイルストーン14 の題材は「反映済みで、共有リンクも作れず、束も作り直せない CR」で、ステージ13 の仕組みが働く余地が無かった(Q2)。Devex の実装計画のマイルストーンには、判断基準と並べて「題材がその仕組みを通る条件」を1行書き、ベースラインでその条件を確かめる手順を入れる。
- **LLM の案の下書きは両端に寄る。** CR-6 の下書きは「すべて TOP20」と「TOP10 に戻す」の2案で、中間の案(取得は20件・解説は10件)は人が足した([110-4](../Phase-110/Phase-110-4.md))。Devex の外部設計で LLM が選択肢を出す所には、「案の幅(両端と中間)が足りているか」を人が確かめる問いを置く。ステージ6 のヒアリングの選択肢カードにも当てはまる。
- **名前に頼る同一性は、ID と照合の規則に置き換える。** 17.4 の示唆の続きで、推測の利用者に ID(U-001)を振り、外部連携は正規化した名前で重複を除いた(P105)。言い換える偽の LLM で検査できるようになり、ステージ13 では名前の揺れが完了後の調整に回らなかった(Q9)。Devex の内部設計のテストの観点に「名称を言い換えた生成で同一性が保たれるか」を入れる。
