## 診断と決定

### (1) 最重要 ── 次の Phase の区切りに直結するもの

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1・7 | 詳細設計モードを Stage 3 に含めるか / Phase 番号 | **ステージ4として切る。ステージ3は Phase 13 で終了し、ステージ4は Phase 14(要件定義フェーズ)から始める** | 規模が大きく、プロジェクトのモード・段階の状態・段階を進める画面が新たに要る。Phase 番号は、Claude の案(Stage 3 を Phase 14 で締め、Stage 4 を Phase 15 から)に対し、ユーザーが「ステージ3は 13b 未達のまま終了、Phase 14 も未達」として、Phase 14 をステージ4の要件定義フェーズに充てると決めた |
| 1 | Phase 13b(M9b)の扱い | **撤回** | 詳細設計モードでは文書を承認済みの意味モデルから組み立てる。散文を正本にしないので、図の手直しを散文へ戻す修正案はほぼ要らない |
| 1 | 旧 Phase 14(アクティビティ図・統合/E2E/デプロイ確認) | **未達として撤回** | ステージ3を Phase 13 で終えたため。振る舞いのビューは05の番号付き手順で扱う。統合/E2E とデプロイでの確認は、ステージ4の実装と合わせて行う |
| 2 | 段階の状態と承認の持ち方 / 前段を直したときの後段 | **`design_stages` テーブル(project × stage、status、approved_version、入力の指紋)を新設する。前段を承認し直したら、後段は陳腐化の表示だけにし、作り直しは人がボタンで指示する** | Phase 13 の陳腐化(`source_doc_versions` と「等しくない」での判定)と同じ考え方で作れる。自動で作り直すと、人が手直しした後段が黙って消える |

### (2) 中程度 ── 後続 Phase の設計事項

| # | 論点 | 決定 |
|---|---|---|
| 3 | 機能グループの決め方 | API のリソース名から決定的に初期値を作り、段階1で人が確定する(折衷案) |
| 4 | CRUD図のうち DFD から決まらない部分 | R と W は DFD の線の向きから決定的に作る。W の C/U/D の区別と、DFD に描いていない処理の分は、AI が処理概要表から下書きし、人が確定する |
| 5 | 番号付き手順の列 / シーケンス図へ進む基準 | 列は見本どおり(`No / 呼び出し元 → 呼び出し先 / 渡すデータ / 処理内容 / 結果 / DB 操作 / 分岐・例外`)。シーケンス図は当面作らず、ステージ4の運用の後に判断する(判断の数値基準は既存文書に根拠が無いため置かない) |
| 8 | 05の手順が複数あるときの見せ方 | [`Phase-14-2.md`](./Phase-14-2.md) で確定(索引・関与表・タブ) |
| 9 | 06と05の手順の紐づけ | [`Phase-14-2.md`](./Phase-14-2.md) で確定(手順ID・双方向のバッジ・逆引き表・06もタブ) |

### (3) 軽微・運用面

| # | 論点 | 決定 |
|---|---|---|
