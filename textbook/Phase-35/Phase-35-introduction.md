# Phase 35 導入: 選択肢カード(ステージ6)

## 目的

AI の問いを**選択肢カード**で出す。カードは観点・場面で聞く問い・選択肢ごとの結果(コスト・手間)・おすすめと理由を持つ。利用者が選択肢を選んで送ると、その観点を「AI の提案を採用」とコードが記録する(LLM は呼ばない)。自分の言葉で答えれば、今までどおり判定の LLM が「ユーザーが決定」とする。ベースライン([33-1](../Phase-33/Phase-33-1.md))で非機能の観点がほとんど聞かれなかった問題に、答えやすい問い方で応える。

方針は [Phase 33-2](../Phase-33/Phase-33-2.md) 決定5とその補足、計画は [33-5](../Phase-33/Phase-33-5.md) の Phase 35。

## モード宣言(#21)・E2E の宣言(#36)

自動実装モード: **on**(AI が本体へ実装し、`textbook/samples/` も同じ内容で作る)。

E2E: この Phase では流さない。チャットの返信の後ろにカードが出るようになり、返信の文がまとめて表示されるようになった。既存の E2E(文を打って送る流れ)は、カードを選ばなくても進めるので壊れにくいが、Phase 40 で既存を含めて全部流して確かめる。

## 着手時の相談で決めたこと

詳細は [`q_a.md`](../q_a.md) の「Phase 35 開始時」を参照。

1. **自動実装モード**: on(推奨どおり)。
2. **返信の作り方**: 返信の LLM を本文とカードの**構造化出力1回**にする(推奨どおり)。1回の送信で LLM は今と同じ2回(判定・返信)。代償は、構造化出力は全体がそろってから返るので、文がトークンごとに流れず、まとめて一度に表示されること(ユーザーの質問に答えて確認した)。
3. **送るとき**: 送信ボタンで送る(推奨どおり)。選んでもすぐには送らず、選び直し・文の追記ができる。途中まで選んで送ってもよい。

Claude の判断(計画の承認で確定。[33-5](../Phase-33/Phase-33-5.md) の残りの未確定事項):

- **まとめる枚数と観点の決め方**: 規模が未決なら規模の1枚だけ。決まっていれば未決の必須を定義の順に最大3枚を候補にし、LLM が選択肢で答えやすい観点だけをカードにする([35-1](./Phase-35-1.md))。
- **カードを出さない返信との混在**: 目的・コア機能のように自由回答向きの観点は、カードにせず本文で聞く(プロンプトで指示)。候補の外のカードはコードが捨てる。
- **記録のタイミング**: 「その場で(AI を呼ばずに)」を、送信の時点でコードが記録する、と読んだ。根拠には送信でできた利用者の発言の id が要るため([35-1](./Phase-35-1.md))。
- **カードの持ち方**: `chat_histories.cards`(JSON)。選ばれた選択肢も同じ JSON に書く。選べるのは最新の AI の発言のカードだけ。
- **おすすめの理由**: おすすめの選択肢に「おすすめ」と理由の1文を出す。
- **最初の発話**: カードを出さない(範囲を広げないため。申し送りに残す)。

実装で足した判断:

- **規模のカードはコードが作る**: 選ばれた選択肢を規模の値に結ぶため、選択肢をコードで固定した([35-1](./Phase-35-1.md))。
- **`as_llm_error` の削除**: 返信を流さなくなり、呼び出し元が無くなった([35-2](./Phase-35-2.md))。

## Phase 完了後の調整

Phase 完了後の実画面の確認で、使用感の問題と、生成へ進めなくなる不具合が見つかった(#38 の通常の工程)。経緯は [`q_a.md`](../q_a.md) の「Phase 35 完了後 ── 使用感と行き詰まり」。samples のタグは `35(完了後の調整)`。

- **不具合の原因**: `chat_histories.created_at` が DB の `now()`(トランザクションの開始時刻)で、1回の送信の「利用者の発言」と「AI の返信」が同じ時刻になっていた。この Phase で前の AI の行(カードの選択)を更新するようになり、行の並びが実際に入れ替わった。順の崩れた会話を読んだ返信の AI が「要件が揃いました」と書き、コードの判定(未決の必須が2件)と食い違って先へ進めなくなった。**対応**: アプリが行ごとに時刻を入れる(`default=lambda: datetime.now(UTC)`。マイグレーション不要)。返信のプロンプトにも、未決の必須が残っている間は完了を書かないよう足した(`_MISSING_POINTS_NOTE`)。
- **行き詰まりの逃げ道**: 観点の表の未決の必須の行に「対象外にする」。`PUT /projects/{id}/hearing-points/{key}`(`ChatService.mark_point_not_applicable`)が「後で決める(画面で対象外にした)」として記録し、LLM を呼ばずに完了判定を作り直す([35-2](./Phase-35-2.md))。
- **最初からカード**: AI の最初の発話に規模のカードを付ける(LLM の呼び出しは1回のまま。案内の文はコードが足す)。
- **カードごとの送信**: 1回の返信で2枚以上のカードが出うるので、カードごとに「この回答を送る」を置いた。下の送信ボタンは、文と選択中のカードをまとめて送る([35-3](./Phase-35-3.md))。
- **観点の表**: 未決を「未決(必須)」「未決(任意)」に書き分け、見出しに未決の必須の名前を並べた。広い画面では表をヘッダーの下に追従させた。
- **確認の回答**: 1回の送信で LLM を呼ぶのは2回(判定 + 返信)。必須がそろったときは1回(判定だけ)。カードを選ぶだけでは呼ばない。
- **ユーザーの決定**: カードにする観点の選び方は今のまま。
- **検証**: devex-api 852 件・devex-ui 682 件成功、`npm run build` 成功、統合テスト 5 件成功(専用 DB)。`samples_check.py` 不一致 0 件・`link_check.py` 切れ 0 件。実画面の確認はユーザーが行う。

### 2回目(ブラウザでの使用結果から)

- **原因1(設問のスキップ)**: 1回目の調整で「カードごとに送る」にしたため、2枚のうち1枚を送ると、もう1枚は次の返信で読むだけになった。聞き直すかは返信の AI まかせで、聞き直さないことがあった(DB の「野球の推し活アプリ」で、「利用者と使う場面」のカードが取りこぼされていた)。**対応**: 答えなかったカードのうち観点がまだ未決のものを、次の返信にコードが付け直す(`carry_over_cards`。ユーザーの選択)。
- **原因2(突然止まる)**: 未決の必須が1つだけ残った返信で、AI がカードも問いも出さなかった(「…設計を進めます」)。**対応**: カードが無く本文に問いも無いときは、次に聞く観点の問いをコードが本文に足す(`_ensure_question`)。
- **任意の観点**: 生成のバナーをユーザーの変更案のとおりにした(「必須項目の回答完了」・任意の確認事項の一覧・[この内容で設計書を生成する]・[任意項目についてヒアリングを続ける])。続けると `continue_optional` 付きで送り、返信の AI が未決の任意の観点をカードで聞く。任意のカードに答えて送れば続き、自由な文ならまとめを返す。完了判定は必須だけで決めるので、生成のボタンは出し続ける。
- **検証**: devex-api 860 件・devex-ui 687 件成功、`npm run build` 成功、統合テスト 5 件成功(専用 DB)。`samples_check.py` 不一致 0 件・`link_check.py` 切れ 0 件。実画面の確認はユーザーが行う。

### 3回目(問いを1つに・選択の反応・判定の呼び方・初期入力の先読み)

- **問いを1回に1つ**: 2回目の付け直しで取りこぼしは防げたが、ユーザーの希望で、1回の返信で聞く問いを1つにした(`CARD_LIMIT = 1`)。次に聞く観点は、前の返信で答えなかったカード(同じカードを付け直す)→ 規模 → 未決の必須(任意を続けるときは未決の任意)の順。カードがあるときは本文で質問させず、カードに向かない観点は本文で1つだけ聞かせる。
- **選択の色が遅い**: 選ぶたびに `ChatPanel` が描き直され、全発言の Markdown を解析し直していた。`MessageBubble` を `memo` にし、選択中の状態は最新のカードの部分(`LatestChoiceCards`)だけが読むようにした。
- **カードだけの回は判定を呼ばない**(相談で出た案 C): 選んだ観点はコードが記録済みで、判定の LLM が読むべき新しい文が無いため。文を書いた回は今までどおり判定 + 返信。まだ一度も判定していない・直近の判定に失敗したときは、カードだけでも判定を呼ぶ(初期入力や失敗した回の文を読み落とさない)。「任意項目について続ける」は判定を呼ばず、決まった文をサーバーが利用者の発言として残す。カードだけで10回答えると、呼び出しは今の20回からおおむね11回になる。
- **初期入力の先読み**(D): プロジェクト作成の時点で初期入力・添付資料を判定し、書いてある観点を先に埋める。最初の問いは判定後の未決の観点から選ぶ(書いてあることを聞き直さない)。作成時に呼び出しが1回増えるが、最初の送信の判定が要らなくなる。
- **採らなかった案**: セクション方式(最大5問を1セクションで出し「決定」でまとめて送る、「後でテキスト入力」で wait にしてテキストで聞く)を検討した。呼び出しは大きく減る(必須15観点で約31回 → 約3回)が、答えが選択肢に寄る・同じセクション内で問いを答えに合わせられない・構造が複雑になる、のデメリットの方が大きいとユーザーが判断した。経緯は [`q_a.md`](../q_a.md)。
- **検証**: devex-api 867 件・devex-ui 689 件成功、`npm run build` 成功、統合テスト 5 件成功(専用 DB)。`samples_check.py` 不一致 0 件・`link_check.py` 切れ 0 件。実画面の確認はユーザーが行う。

### 4回目(選択肢をラジオボタンに)

- **原因**: 3回目で描き直しの範囲を狭めた後も、選んだ選択肢が青くなるのが遅かった。選択肢に使っていた Tamagui の `Button` は既定でホバー・押下の背景色を持ち、クリックした後もマウスがボタンの上にある間は、ホバーの灰色が選択中の青より優先されていた(マウスを外すと青くなる)。処理の遅さではなく、青が隠れて見えていた。
- **対応**(ユーザーの提案): 選択肢をブラウザのラジオボタン(`<input type="radio">`、カードごとに `radiogroup`)にした。選択中の枠と背景は CSS の `:has(input:checked)` で付ける(`ChoiceCards.module.css`)ので、押した瞬間に変わる。キーボードと読み上げにも対応する。同じ選択肢をもう一度押して外す操作はやめた(別の選択肢を選び直す)。
- **検証**: devex-ui 689 件成功・`npm run build` 成功(CSS で使うテーマの変数 `--blue3` などがビルドに含まれることも確かめた)。`samples_check.py` 不一致 0 件・`link_check.py` 切れ 0 件。実画面の確認はユーザーが行う。
