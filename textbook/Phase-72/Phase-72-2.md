## 10.6節の要点

- **順序**: API を先に、UI を後に。逆にすると新しい UI が古い API を呼んで失敗する。API だけ先に出た間は、古い UI の一覧が新しいレスポンスの形(`{items, total}`)を読めずに空になるので、間を短くする。
- **増えるもの**: `ENCRYPTION_KEY`(無くても起動し、キーの登録だけ 503)・任意の `JUDGE_MODEL`・依存の `cryptography` と `@tamagui/toast`。Phase 68 で消えたタイムアウトの3つの変数は、残っていても無視される(`Settings` は `extra="ignore"`)。
- **既定のモデル**: `.env` の `GEMINI_MODEL`・`REVIEW_MODEL`・`JUDGE_MODEL` が全員の既定。本番には既定値の行を入れない(着手時の決定3)。3つの値がカタログに無いとその用途の呼び出しが失敗するので、反映の前に照らす段を置いた。
- **鍵**(着手時の決定2):
  - 本番の backend のコンテナで `Fernet.generate_key()` を流して作る(`run --rm --no-deps`)。値を手元の端末やチャットに残さない。
  - VPS の `.env` とパスワード管理ツールにだけ置く。
  - 入ったかは `test -n "$ENCRYPTION_KEY" && echo set` で、値を出さずに確かめる(10.5 の `ANTHROPIC_API_KEY` と同じ)。
  - 回すときは新しい鍵を先頭に足し、古い鍵は外さない(暗号化し直すスクリプトは作らない)。鍵を失ったら、利用者がキーを登録し直すまで既定のモデルで動く。
- **ブランチ**: 手元の devex-api は `stage7` にステージ8・9 のコミットを積んでいる。origin に `stage8` が無く、origin/main は手元に無いコミットだった(`git ls-remote` で見た)。手順では `git fetch` の後に `git log origin/main..stage7` でステージ9だけが並ぶことを確かめてから `stage9` を作る段にした。devex-ui も、`git ls-remote` の origin/main はステージ7のコミット(`3c8369e`)だった。出すコミットを `git log origin/main..main` で確かめる段を置いた(下の「未消化の申し送り」)。
- **本番での確認の表**: Phase 62〜69 の画面確認(ヘッダー・メニュー・振り分けと cookie の `Secure`・削除・検索・アカウント・失敗の知らせ)、決める項目3つ(検索欄の幅・レビューの案内・カードの失敗の印)、一般の利用者の自分のキー(Haiku)・superuser の既定(Sonnet 1回)・聞き直しの open。

## マイグレーションの往復の確認

開発環境の DB を別のデータベース(`devex_roundtrip`)に `pg_dump` で複製し、`alembic downgrade 7c3e9ab5f4d6` → `upgrade head` を2往復した(使い終わったら消した)。先にリビジョン ID の重複が無いことと head が1つ(`b8e4d0f2a6c3`)であることを確かめ、downgrade は相対ではなく行き先のリビジョンを指定した。dev の DB 自体は `b8e4d0f2a6c3` のまま触っていない。

複製の1件に削除の印(`deleted_at`)を付けてから流した。印の付いた行が downgrade でどうなるかを見るため。

| 時点 | head | 利用者 | プロジェクト | 削除の印 | 失敗の記録 | 渡した指摘の記録 | 用途ごとのモデル | API キー | `user_name`(値あり) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 複製の直後(印を付けた後) | `b8e4d0f2a6c3` | 111 | 127 | 1 | 9 | 70 | 8 | 5 | 111 |
| downgrade の後 | `7c3e9ab5f4d6` | 111 | 127 | (列が無い) | (列が無い) | (列が無い) | (表が無い) | (表が無い) | `full_name` 111 |
| upgrade の後 | `b8e4d0f2a6c3` | 111 | 127 | 0 | 0 | 0 | 0 | 0 | 111 |

2往復とも同じ。

- **削除の印の付いた行は一覧に戻る**: 列が消えるので、upgrade の後は印の無い普通の行になる。削除の印の行は、ふつうは削除の直後に消える(物理的な削除)。それでも、生成中のジョブが行を握っている間などは残りうる。そこで、ロールバックの手順の最初に `deleted_at IS NOT NULL` の数を確かめる段を置いた。
- **選んだモデルと登録したキーは戻らない**: 表ごと消える。もう一度更新しても空から始まり、利用者が登録し直す。残す必要があればバックアップから戻す。
- **改名は値を保つ**: `alter_column` の改名なので、`full_name` ↔ `user_name` の往復で値は 111 件とも残る。

## 設計判断

### 本番に既定値の行を入れない

既定値の行を入れると、既定が `.env` と DB の2か所に分かれ、`.env` を替えたときに seed を流し直す手順が要る。行が無ければ `.env` で補う作りが Phase 67 からある(`llm_settings_service._defaults`・`llm_resolver` が `env_default_models` を使う)。そこで、本番は `.env` だけを既定値にした。seed は dev 専用のまま(テストユーザーも作るので、本番で流さない)。

### 鍵は本番のコンテナで作る

鍵を手元で作ってコピーすると、端末の履歴・クリップボード・チャットに値が残りうる。本番のイメージには `cryptography` が入っているので、`run --rm --no-deps backend` で作れば値は VPS の端末にだけ出る。控えをパスワード管理ツールに置くのは、VPS を作り直したときに鍵を失わないため(失っても壊れはしないが、全員がキーを登録し直すことになる)。

### 暗号化し直すスクリプトは作らない

`MultiFernet.rotate` で全行を新しい鍵で暗号化し直せば、古い鍵を外せる。ただ、鍵を回す必要が出る場面(漏えい)はまだ無く、古い鍵を後ろに残す運用で読み書きは続く。駆動する実在の場面が無いので、作らなかった(#17 の判定と同じ考え方)。
