# Phase 72 導入: 統合/E2E・デプロイでの確認(ステージ9)

## 目的

ステージ9(使い勝手とアカウント・モデル設定の調整)の最後の Phase。Phase 62〜71 で作った画面の調整・認証ページの振り分け・削除・一覧の検索と絞込み・マイページ(アカウント・モデル・API キー)・ユーザーごとの LLM の解決・生成の失敗の知らせを通しで確かめ、本番に出す準備をする。新しい機能は作らない([Phase 60](../Phase-60/Phase-60-introduction.md) と同じ型)。

- **E2E**: 一般の利用者で、認証ページの振り分け → モード選択 → 一覧の検索と削除 → 自分の Claude キーとレビューのモデル → レビューのパネル → ログアウトを通す spec を足し、既存を含めた全 E2E を流す([72-1](./Phase-72-1.md))。
- **デプロイ**: 本番をステージ9の版へ更新する手順(暗号の鍵・既定のモデル・5本のマイグレーション・本番での確認・鍵を回す・ロールバック)を `OPERATIONS.md` 10.6節に書き、マイグレーションの往復を確かめる([72-2](./Phase-72-2.md))。
- **docs**: ステージ9の完了と、本番の既定値・鍵の決定を反映する([72-3](./Phase-72-3.md))。

計画は [61-3](../Phase-61/Phase-61-3.md) の Phase 72。

ステージ10の入力(仕様診断 #28 で、範囲に入れるかを1件ずつ決める):

- **登録の上限と手元の確認**: 既存の `test_auth_flow.py`・`test_projects_flow.py` は API で登録するので、integration を流し直すと登録・ログインの上限(10回/時)に当たる。[`retrospective-memo.md`](../retrospective-memo.md) の「統合テストとレート制限のカウンタを分ける」と同じ問題である。Phase 71 では、実 LLM の確かめのログイン(`drive71.py` は1回ごとにログインする)も同じ 127.0.0.1 のカウンタに入った。全 E2E は1回で5人を登録するので、同じ1時間に流せるのは2回まで(Phase 72 は流す前に dev の Redis の登録・ログインの IP の鍵を消した)。
