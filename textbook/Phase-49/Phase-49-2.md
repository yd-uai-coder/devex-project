| | 詳細 1回目 | 簡易 1回目 | ステージ6(詳細 / 簡易) |

| 聞けた潜在の事実(L1〜L14) | **14/14** | **14/14** | 10 / 8〜10 |
| 側面の4つ(L2・L5・L6・L14) | **4/4** | **4/4** | 0(観点が無い) |

- 発言は観点が4つ増えた分だけ増えた(上限24回には届かない)。ヒアリングが長すぎるかは画面確認で見る(申し送り)。
- **ログのカードのおすすめ**: 詳細1回目では、おすすめが「デバッグ用にチャットの入力内容も含めてすべて残す」だった(セキュリティで「要件は機密になりうる」と答えた直後)。ペルソナは事実に合う「機密情報を避けて…だけを残す」を選んだので結果には響いていないが、おすすめが利用者の事実と逆を向いた。簡易1回目のおすすめは「残さない」だった。
- ゆらぎ(3回の幅)は 49-3 で数える。

## 結果 3: 再生成の実際の印(Phase 43〜46 の効果)

全段階を承認した後、チャットで「参考資料の上限を3件から5件に変えたいです。」と送り、文書を再生成した(ベースラインの N2・N4 と同じ変更)。正解は印を取得する前に書いた(`regen/truth.md`)。

| | 詳細1回目 | 簡易1回目 |
|---|---|---|
| 変わったもの | 9(意図した変更 FR-005 + **揺れ 8**) | 5(**揺れ 5**。タスクがすべて「消えた」) |
| 印 / 正解 / 当たり / 見落とし | 49 / 4 / 4 / 0 | 5 / 1 / 1 / 0 |
| 過剰の割合 | **92%** | 80% |
| 意図した変更だけを当てたときの印(過剰) | 13(9) | 3(2) |
| 揺れからだけ届いた印 | 36 | 2 |

**見落としは0件**だが、**過剰はベースラインの「今の仕組み」(87%)と変わらない**。原因は2つ。

### 原因1: 再生成の揺れ(過剰の大部分)

利用者が頼んでいない所が、再生成で作り直された。

- **詳細**: 要件 NFR-003 の誤字(「出れれば」)、API 5本のすべて(要約の言い換え・`req_ids` の増減・本文の項目名 `project_name` → `name`・エラーの書き方)、画面 SCR-003・SCR-004(役割の文・ボタン)。API はトリガーで5処理に、画面は残りの2処理につながるので、全7処理の要約・CRUD・手順・処理ロジック・タスク・手順書に印が付いた。
- **簡易**: 実装計画書のタスク名がすべて言い換えられ(「プロジェクト初期化と…」→「プロジェクト初期構成と…」)、単位のキーの引き継ぎ(タスク名の完全一致。Phase 42 の `carry_over_unit_keys`)が1件も当たらず、キーが U-001〜005 → U-006〜010 に振り直された。前のタスクはすべて「消えた」として、全単位に印が付いた。処理別データフローの ID も、トリガーが変わったものは DF-5 → DF-6 のように振り直された。
- 言い回しだけの揺れ(NFR-003 の誤字・要約)と、仕様の揺れ(API の項目名・ボタン)がある。後者は利用者から見ても「変わった」ので、印が付くのは誤りではない。問題は、頼んでいない変更が再生成のたびに入ること。

### 原因2: たどり方の広がり(意図した変更だけでも過剰)

- **詳細**: FR-005 だけでも過剰9。段階7の横断事項「トランザクション」が `req_ids` に FR-005 を持ち、その横断事項の対象のモジュールに触れる単位すべて(U-002・U-003・U-006・U-007)に届いた(5件)。残りは処理に属する要素(要約・CRUD 2つ・タスク。49-1 の候補 C の対象)。
- **簡易**: FR-006 だけでも過剰2。FR-006 を持つ画面 SCR-002 が、チャットと生成の API の画面でもあり、画面 → API → DF-3・DF-4 → 単位 U-004・U-005 と届いた(Phase 42 から申し送った「共有の画面を通る道」。49-1 のシナリオでは過剰を生まなかったが、ここでは生んだ)。

段階7の横断事項の `req_ids` は、実 LLM が付けていた(6件すべて)。49-1 の候補 A は、実際の生成では起きている。
