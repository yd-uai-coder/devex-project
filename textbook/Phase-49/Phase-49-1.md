[ベースライン](../../appendix/stage7-baseline/README.md)([41-1](../Phase-41/Phase-41-1.md))の変更シナリオ S1〜S8・N1〜N4 を、Phase 42〜46 で実装した仕組み(要素のグラフ・処理を軸のたどり方・承認時の写しとの差分・印)で測り、同じ正解と比べる。合格の基準(厳しめ)に届くかを判定し、届かない原因と直しの候補を、同じ材料で試算して示す。

## やり方

- **材料**: ベースラインと同じ stage6-effect の1回目の生成物。文書の model は生成物の md には無いが、そのプロジェクトがローカル DB に残っていたので書き出した(詳細設計モードの要件定義書・外部設計書は model あり。簡易モードの内部設計書・実装計画書は Phase 45 より前の版で model が無い)。DB の段階1〜8 は stage6-effect の JSON と同じ(単位のキーを除く)ことをスクリプトで確かめた。
- **簡易モード**: model の無い2文書は、段階8が model の無い版で使う md の解析(`parse_internal_design`・`parse_wbs`)から、要素に要る欄だけの model を作った。
- **ベースラインの再利用**: ベースラインの `measure.py` を読み込み、グラフ・シナリオ・正解・4つの方式をそのまま使う。4つの方式の数字がベースラインの [`results.md`](../../appendix/stage7-baseline/results.md) と一致することを確かめた。正解は付け直していない(着手時の決定)。
- **キーの対応**: ベースラインのキー(`PROC F-02`・`MOD x`・`UNIT M-02-T01` など)を本体の要素のキー(`proc:F-02`・`module:x`・`unit:U-003` など)へ写し、結果を戻して比べる。作業単位はキー(段階7の `U-001`…)で引く。本体にだけある要素(簡易モードの画面・API・DF など)は過剰に数える。
- **2つの数え方**:
  - **実装(たどり方)**: 変わった要素を `Change` として `impact_of` に渡す。ベースラインの方式と同じく文書の要素も数える。**判定はこちらで行う**(ベースラインの4方式と同じ範囲)。
  - **実装(印)**: シナリオの変更を model に当て(要件の文・API の本文・段階1の概要・ER の列・段階4のパス・WBS のモジュール)、本体と同じ「前後の要素の差分 → `marks_for`」で印を求める。画面に出る形。文書の要素には印を付けないので、正解のうち文書の要素(S1 の SCR-002 など5件)は除いて比べる。
- **S3**(「採用にする」)は版を上げず変更を記録しない(`adopt_requirement`)ので、示すものは0件で正しい。

## 結果

| 方式 | S1〜S8 示した / 当たり / 過剰の割合 / 見落とし | N1〜N4 |
|---|---|---|
| 今の仕組み | 292 / 37 / 87% / 2 | 158 / 14 / 91% / 3 |
| 処理を軸(試案) | 51 / 29 / 43% / 10 | 25 / 14 / 44% / 3 |
| **実装(たどり方)** | **51 / 30 / 41% / 9** | **31 / 16 / 48% / 1** |
| 実装(印) | 49 / 29 / 41% / 9(正解38) | 25 / 13 / 48% / 1(正解14) |

**判定(厳しめ: 過剰 ≤ 35%・見落とし S ≤ 5 / N ≤ 1・S2 の見落とし 0)**: S1〜S8 は過剰 41%・見落とし 9・S2 6 で**未達**。N1〜N4 は見落とし 1 で届いたが、過剰 48% で**未達**。

- **今の仕組みからは大きく減った**(過剰 87% → 41%)。試案とほぼ同じ所に来た(試案を本体にしたので当然)。見落としは S6 の `repositories/document.py`(モジュール → テーブルの辺を Phase 42 で足した)で1つ減り、N では3 → 1(テーブルの辺と、文書の model の画面・API の辺)。
- **改名(S7)は正解と一致**(示した6・当たり6)。試案の過剰2(改名の後の内容の確認)は、改名では直接の参照元だけを示す規則(Phase 42)で消えた。
- **実装(印)は実装(たどり方)と同じ傾向**。差分の取り方(写しとの比較)で、変わったものがシナリオどおりに1件ずつ見つかった(S7 は `rename`)。

### 過剰と見落としの原因

| 原因 | どこで | 数 |
|---|---|---|
| 処理に属する要素(CRUD・要約・タスク)をすべて示す | S1・S4・N2・N3 の文書の変更 | 過剰 11 |
| テーブルの変更が、そのテーブルを使う処理のすべてに上る | S6(documents を F-03・F-04 が使う)・N1 | 過剰 17 |
| 共有されるモジュールは示さない(「どれを直すか」は ID では決まらない) | S1・S4 の `clients/ai.py`、S4 の `api/routes/chats.py`、N3 の `api/routes/documents.py` | 見落とし 4 |
| 非機能要件から下流への辺が無い | S2(stage6-effect の段階7は Phase 42 より前の生成物で、横断事項が `req_ids` を持たない) | 見落とし 6 |
| 処理の変更では、その処理を持つモジュール(直接の参照元)をすべて示す。永続化の層(`repositories/*.py`)は正解に無い | S5 | 過剰 2 |

申し送りの「共有の画面を通って別の処理に届く」は、このシナリオでは過剰を生まなかった(S1・N2 の過剰はどれも同じ処理の要素)。ただし実 LLM の生成物では生んだ([49-2](./Phase-49-2.md))。

## 直しの候補(試算。本体は変えていない)

同じ材料に当てた数字。`measure.py` の比較用の方式で、本体のたどり方は変えていない。

| 候補 | 中身 | S1〜S8 | N1〜N4 |
|---|---|---|---|
| A | 段階7の横断事項に `req_ids` があるとき(Phase 42 の後の生成では LLM が付ける。stage6-effect の材料には無いので、方針の文が要件の文を写している 認証 → NFR-007・ログ → NFR-005 を補った) | 53 / 32 / 40% / 7 | 31 / 16 / 48% / 1 |
| A + B + C + D | B: テーブルの変更は処理まで上らない(テーブルを参照する要素と、その手順を実装する処理ロジック・手順書まで)。C: 文書の要素の変更では処理の CRUD・タスクを示さない(要件・画面の変更では要約も示さない。API の変更だけが入出力を変える)。D: API の変更は、その処理を持つ入口の層のモジュールも示す | **42 / 33 / 21% / 6** | **21 / 16 / 24% / 1** |

- A〜D で、N1〜N4 は基準に届き、S1〜S8 は過剰が届く(21%)。S の見落としは 6 で、基準(5)に1つ足りない。残る見落としは S2 の4件(`app.py`・3処理の手順。横断事項の対象のモジュールを使う手順まで ID ではたどれない)・S1 と S4 の `clients/ai.py`(共有のモジュールのどれを直すか)。
- **S2 の見落とし 0 は、ID の辺だけでは届かない**。横断事項 → 対象のモジュール → そのモジュールを呼ぶ全手順、と広げれば届くが、横断事項は多くのモジュールを持つので、過剰が大きく増える(41-2 で「LLM は使わない」と決めた範囲の外)。
- **合わせ込みの恐れ**: B〜D は S と N の両方の過剰の中身を見てから作った。N1〜N4 は holdout として作ったが、この候補を確かめるための新しいシナリオは無い。49-4 で直すなら、[49-2](./Phase-49-2.md) の実 LLM の生成物(別のプロジェクト)でも効くかを確かめる。

## 追加の確認: 改名の後に下流の参照を直して承認する(Phase 43 の申し送り)

S7 の改名を承認した後、段階5の手順の呼び出し先を新しいパスに直して段階5を承認すると、`proc:F-02` の内容の変更として、`ChatService.send_message` の処理ロジックと単位 U-003 の手順書に印が付き直す(2件)。どちらも改名で印が付き、見直した後の要素なので過剰。件数は小さいので、直すかはセッション2でまとめて決める。
