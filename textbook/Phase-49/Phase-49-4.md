## 要点の抜粋

```python
# app/detailed_design/impact/elements.py
def task_body(unit: PlanUnit, units: Iterable[PlanUnit]) -> str:
    """タスクの行の内容。依存先(並び順の単位の ID)は単位のキーに読み替える(マイルストーンの
    並べ替え・挿入で表示の ID がずれただけのタスクを、変わったものにしないため)。"""
    keys = {u.unit_id: u.key for u in units}
    task = unit.task.model_copy(
        update={"depends_on": [keys.get(d.strip(), d) for d in unit.task.depends_on]}
    )
    return row_body(task, "key")
```

- 簡易2回目の再生成で、AI がマイルストーンを分け直し(3つ → 5つ)、タスク U-004 の依存先が `M-02-T02` → `M-03-T01` になった。どちらも U-003 を指すので中身は同じだが、表示の ID のまま比べていたので「変わった」になり、単位の手順書に印が2つ付いた。
- 依存先は表示の ID のまま保存している(Phase 42 の決定。並べ替えの付け替えは画面の操作が行う)。比べるときだけキーに読み替えた。前後とも同じ関数で作るので、保存してある写しはそのまま使える。

## 結果 1: ヒアリング(3回のゆらぎ)

| | 詳細 1・2・3回目 | 簡易 1・2・3回目 | 基準 |
|---|---|---|---|
| 「十分」までの発言 | 18・19・18 | 17・17・16 | 記録だけ(上限 24) |
| 聞けた潜在の事実(L1〜L14) | 14・14・**13**(※) | 14・14・14 | — |
| 側面の4つ(L2・L5・L6・L14) | **4・4・4** | **4・4・4** | 必須の回すべてで聞けること |
| 自由回答の採用 | 1・2・1 | 1・1・1 | ステージ6(詳細 0〜3・簡易 2〜4)を超えない |

**判定: 基準どおり**。側面は6回とも聞けた。自由回答の採用は詳細 1〜2・簡易 1 で、ステージ6の幅の中。

※ 詳細3回目は、コア機能を聞かれたときの答えに「ログインは MVP に入れます」(ペルソナの最初から話してよい事実)を含めたところ、セキュリティの観点がそれで「採用」になり、L4(本人以外に他人のプロジェクトを見せない)は聞かれなかった。要件定義書にも入っていない。[`tally.py`](../../appendix/measurements/stage7-hearing.md) は観点の状態だけで数えるので ○ と出す(出力の `tally-run123.md` は 14)。ログインの方法だけでは「誰に見られたら困るか」が埋まらないのに、判定が観点を埋めた(新しい申し送り)。

- 問いの順は回ごとに少し違った(簡易3回目は利用者の場面をカードで先に聞いた。詳細2・3回目はコア機能を聞いた)。カードの選択肢がペルソナの事実と一部しか合わないことが多く、自由回答で答えた回数はステージ6と同じくらい。
- **ログのカードのおすすめ**(49-2 の申し送り): 6回のうち2回、おすすめが利用者の事実と逆を向いた(詳細1回目「入力内容もすべて残す」、簡易3回目「エラー時の入力やプロンプトは一時的に残す」)。どちらも機密と答えた後。残り4回は「残さない」がおすすめ。
- 簡易3回目は、最初の入力の後に AI が「MVP の範囲」を対象外にしていた(利用者は聞かれていない)。まとめでも「MVP の範囲: 対象外」のまま生成に進んだ(新しい申し送り)。

## 結果 3: 直した後の再生成の印

49-2 と同じく、全段階(簡易は段階8)を承認した後に「参考資料の上限を3件から5件に変えたいです。」と送って再生成した。正解は印を取る前に書いた(`regen/truth.md`)。

| 回 | 変わったもの | 印 | 正解 | 当たり | 過剰 | 見落とし |
|---|---|---|---|---|---|---|
| 詳細1回目(49-2、直す前) | 9(揺れ 8) | 49 | 4 | 4 | 45(92%) | 0 |
| **詳細2回目** | 2(要件・画面) | 4 | 4 | 4 | **0** | 0 |
| **詳細3回目** | 3(要件・API・画面) | 8 | 3 | 3 | 5 | 0 |
| 簡易1回目(49-2、直す前) | 5(揺れ 5) | 5 | 1 | 1 | 4(80%) | 0 |
| **簡易2回目** | 6 → 4(要件・API・DF・画面)※ | 3 | 1 | 1 | 2 | 0 |
| **簡易3回目** | 3(要件・DF・画面) | 1 | 1 | 1 | **0** | 0 |
| 2・3回目の計 | | 16 | 9 | 9 | 7(44%) | **0** |

※ 再生成した時点ではタスク2つの依存先のずれも変わったものに入っていた(上の `task_body` で直した。印の数は同じ)。

- **揺れはほぼ消えた**: 2・3回目の「変わったもの」は、どれも今回の変更が届いた行だった(要件の文、API のエラー欄・本文の項目、画面の UI 仕様、処理別データフローの流れに「5件」が入った)。API の項目名・画面の役割の言い換え・誤字の直し・タスク名の言い換え(49-2 の揺れ)は起きなかった。簡易のキーは5つとも前のキーのまま(実装計画書のタスクは変更なしか `prev_key`)。
- **見落としは0**: `unchanged` で関係する行まで落ちる心配(49-3 の設計判断)は、6本では起きなかった。
- **残る過剰の7は、正当な変更から規則どおりに届いたもの**: 詳細3回目の5は、API のエラー欄の変更から要約と入口のモジュール(D)、共有の画面 SCR-003 の UI 仕様の変更からチャットの処理 F-05 の手順・単位(画面そのものの変更は、その画面の処理すべてに届く)。簡易2回目の2も、画面 SCR-002 の UI 仕様の変更から、同じ画面のチャット・生成の処理別データフローの単位へ。正解は「その処理だけ」と書いたが、画面の文のどこが変わったかは ID では分からない。
- 詳細1回目の生成物を今のたどり方で求め直すと、印は 49 → 35(過剰 31)。たどり方の直しだけでは足りず、揺れを止めた(R1・R2)ことが効いた。

## 判定(この章の分)

- ヒアリング・段階3・5: 3回とも基準どおり。
- 再生成の印: 見落とし 0、過剰の割合 44%(49-2 は 92%・80%)。過剰はどれも、頼んだ変更で文書の行が正当に変わったものから届いた。揺れによる印は無くなった。シナリオの過剰の基準(35%)は再生成の印には決めていないので、記録だけとする(残りは画面の変更の広がり。申し送り)。
