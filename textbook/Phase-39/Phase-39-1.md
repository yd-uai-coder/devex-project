## やり方

- **ペルソナ**: ベースラインの `persona.md` をそのまま使った。変えたのは答え方の規則だけ(上限を8回 → 20回、カードの選び方、規模は「誰でも登録できるサービス」、「対象外」は使わない)。差分は [README](../../appendix/measurements/stage6-effect.md)「規則の差分」。
- **`drive.py` の足し分**: `say <mode> <file|-> card_id:option` で `card_answers` を送り、SSE の `event: cards` を表示する。`points` で観点の表を、`metrics` で要件定義書・外部設計書の要約(出どころの件数・指摘)と段階の指摘のコード別件数を書き出す。段階の規則(`design`・`procedure`)はベースラインと同じ。
- **数え方**: 33-1 と同じ。分類 A〜D は手で分け、C(設計段階の不足)は除いて数える。

## 結果 1: ヒアリング

| | 詳細設計モード | 簡易モード |
|---|---|---|
| 「十分」までの発言 | 13(ベースライン 3) | 10(ベースライン 3) |
| 聞かれた潜在の事実 | **10/14**(ベースライン 0) | 8/14(ベースライン 1) |
| 聞かれなかった潜在の事実 | L2 バックアップ・L5 ログ・L6 不正利用・L14 削除 | 同じ4つ + L9 環境・L12 将来 |
| 聞かれなかった「最初から話してよい事実」 | **技術スタック**・LLM・**認証**・参考資料の扱い・SSE・生成の順 | **認証**・参考資料の扱い・生成の順 |

- **観点の表は効いた**: 問いが1回に1つになり、可用性・性能・運用・移行・セキュリティ・環境を場面で聞いた。カードの選択肢は概ね場面の言葉で、おすすめの理由も対話に結びついていた。
- **技術スタックが聞かれない(詳細)**: 作成時の判定が、初期入力の「ユーザー・チャット履歴・生成文書を PostgreSQL に保存する」の一語から、技術スタックを「採用」(後に「決定」)にした。必須がそろったので一度も聞かれなかった。
- **規模が聞かれない(簡易)**: 作成時の判定が初期入力から規模を「社内」と推し量り「採用」にした。最初の発話に規模のカードが出ず、「将来の拡張」が任意になって聞かれなかった(L12)。
- **環境に技術スタックが入った(簡易)**: 技術スタックの答えの「Next.js(App Router)+ Tamagui」を、判定が「システム環境・エコロジー」の決定にも使った。ブラウザ(L9)は聞かれなかった。
- **認証が聞かれない(両モード)**: セキュリティの問いは「誰に見られたら困りますか」だけで、利用者は「本人以外は見られない」と答えた。ログインの要否・方法は聞かれず、要件定義書に認証の機能要件が無い。
- **判定の取りこぼし**: 自由回答の最新の答えを、判定が未決のまま残した(詳細の運用)。同じカードが付け直され、利用者が答え直した。
- **自由回答が「採用」になる**: 利用者が自分の言葉で答えた観点(1日の流れ・性能など4件)を、判定が「AI の提案を採用」にした。要件の出どころが「採用」になる(推測ではないので3指標には響かない)。
- **完了の誤宣言**: 未決の必須が残っているのに、返信が「すべての必要な要件が揃いました」と書いた(2回)。完了の判定はコードなので生成ボタンは出ないが、画面の言葉と食い違う。

## 結果 2: 文書と段階8

| | 詳細設計モード | 簡易モード |
|---|---|---|
| 要件定義書 1.5・1.6 のうち利用者が言っていないもの | **0/10**(ベースライン 7/11) | **0/11**(ベースライン 6/11) |
| 推測の要件 | 1(規模の CON。利用者はカードで選んでいる) | 0 |
| 外部設計書の API | 4(認証なし) | 4(認証なし) |
| 段階8の未定義 | 7(ベースライン 36) | 2(ベースライン 14) |
| うち分類 A | **2**(ベースライン 4) | **0**(ベースライン 1) |
| 技術スタックの創作 | **あり** | **なし**(ベースラインは NestJS を創作) |

- **分類 A(詳細)**: 「07章 認証のトークンの有効期限が要決定」(ペルソナは JWT 30分・14日。認証を聞いていない)と、「外部 AI サービスのエンドポイント・パラメータが無い」(LLM を聞いていない)。残り5件は段階6の詳細が無い関数(C)。
- **技術スタックの創作(詳細)**: 要件定義書には創作が無い(CON は PostgreSQL だけ)。その後の段階4・7が「FastAPI・SQLAlchemy・httpx で外部 AI サービス」を補った。偶然ペルソナと近いが、聞いていない。段階7のリスクの欄も「認証・認可の詳細仕様が未決定」と書いた。
- **簡易モードの未定義(2件)**: ファイルのテキスト抽出の関数仕様(B: 内部設計書の書き落とし)と、デプロイ先の SSH 鍵・ディレクトリ(B/C)。ヒアリングが原因のものは無い。
- **申し送りの「実 LLM の質」**:
  - 要件ID: 外部設計書は要件定義書に無い ID を作らず、Must の機能要件の抜けも無かった(`MUST_REQUIREMENT_UNCOVERED` 0)。
  - API の本文: 簡易の `POST .../generate` に `API_BODY_MISSING`。本文の要らない POST なので、誤検知に近い(申し送り)。
  - 構造化出力の大きさ: 外部設計書が途中で切れることは無かった。
  - 段階1: 処理はすべて API で、要件ID はコードが 2.6 から写した。`UNLINKED_FUNCTION` 0。
  - WBS の「要件」欄: 簡易モードの WBS は全タスクに「要件」欄を書き、Must の機能要件はすべてタスクに入った(`MUST_REQUIREMENT_UNPLANNED` 0)。
  - 段階7の横断事項: 5つの話題(例外・HTTP・認証・トランザクション・ログ)のどれも NFR を参照しなかった。NFR に触れたのはリスクの欄(NFR-003・004・007)だけ。
  - 要件の粒度: 1行に1つの要件が守られた(簡易の FR-012 だけ、AI の失敗と生成の失敗を1行にまとめた)。
  - 段階5: 分岐の行の書き落とし(`MISSING_BRANCH_TARGET` 4件。ベースラインからの範囲外の課題)。

## 判定(1回目)

基準(厳しめ)は ① 分類 A が両モード 0件 ② 聞けた潜在の事実が両モード 10/14 以上 ③ 技術スタックの創作 0、かつ利用者が言っていない要件はすべて「推測」。

| 基準 | 詳細 | 簡易 |
|---|---|---|
| ① 分類 A 0件 | 未達(2) | 達成 |
| ② 潜在の事実 10/14 以上 | 達成(10) | 未達(8) |
| ③ 創作 0・推測の表示 | 未達(段階4・7が補った) | 達成 |

原因はどれもヒアリングの判定まわりだった。直しの案と選んだもの: [39-2](./Phase-39-2.md)。
