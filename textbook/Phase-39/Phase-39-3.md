# Phase-39-3: 2回目の測定と判定

## この章の目的

[39-2](./Phase-39-2.md) の直しの後、両モードで新しいプロジェクトを作り、ヒアリングと文書の生成までを同じ規則で流す(範囲はユーザーの選択)。1回目の原因が消えたかを確かめ、基準(厳しめ)の達否を出す。

自動実装モード: on([introduction](./Phase-39-introduction.md) 参照)。

## この章で作成・更新したファイル

samples の対象外(生成物)。`appendix/stage6-effect/{detailed-2,simple-2}/`(発言・チャット履歴・観点の表・文書・`metrics.json`)と、`detailed-2/regen/`(文書だけを再生成したもの)。条件と数字は [README](../../appendix/measurements/stage6-effect.md)。

## 流れ(直しながら流した)

| 時点 | 見つけたこと | したこと |
|---|---|---|
| 詳細 4発言目 | 1日の流れの自由回答を、判定が未決のまま残した。表の「決めたこと」の文字が化けた(「誰もが登録」→「蘰もが癲録」) | 保存しない再現で3回とも正常 → LLM の一時的な乱れとして記録。利用者は同じ内容で答え直した |
| 詳細 10発言目 | 可用性の自由回答をまた取りこぼした(再現で4回中2回) | 直前の問いの観点を判定に添えた(再現で6回中6回)。39-2 に追加 |
| 詳細 12発言目 | 文で聞いた問い(性能)はカードが無く、添える観点が無かった。返信が「準備が整いました」と書いた | 文の問いは前の表から観点を計算する。完了の宣言の除去に「準備が整い」などを足した |
| 簡易 作成時 | 判定が「決まったと言える条件」を無視し、初期入力の PostgreSQL だけで技術スタックを「決定」にした | 技術スタックを規模と同じ「チャットで確かめる観点」にした(`confirm_in_chat`)。このプロジェクトは捨てて作り直した |
| 詳細 文書 | 利用者が言った Gemini・PostgreSQL・Redis が要件定義書から落ち、外部設計書は「外部AIサービス」になった | 生成のプロンプトに「会話の原文から拾う」を足して再生成(`regen/`)→ まだ落ちた。判定の要約に技術の名前を残させ、再現で要件定義書に全部が載るのを確かめた |

詳細設計モードの2回目は、途中で本体が変わった(9発言目までは取りこぼしの直しの前、技術スタックの要約の直しはヒアリングの後)。最後の直しの効果は、同じ会話を使った保存しない再現で確かめた(判定3回・要件定義書2回)。

## 判定

| 基準 | 詳細 | 簡易 |
|---|---|---|
| ① 分類 A 0件 | 見込みで達成(1回目の A = 認証の期限・LLM。2回目は認証の期限が要件に入った。LLM は最後の直しで入る) | 見込みで達成(2回目の文書に、認証・JWT の期限・LLM・技術がすべて入った) |

- 残った課題(L2・L5・L6・L14 は聞かれない、判定のゆらぎ、`API_BODY_MISSING` の誤検知など)は [introduction](./Phase-39-introduction.md) の「未消化の申し送り」へ。
