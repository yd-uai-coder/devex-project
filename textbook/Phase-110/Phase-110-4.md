# Phase-110-4: 実 LLM の流れと画面確認(ヘッドレス)

## この章の目的

効果測定([110-1](./Phase-110-1.md))の材料として、題材「トレンド追跡アプリ」で、開発者の操作(束 → CR → 案の LLM の下書き → 共有リンク)とクライアントの操作(閲覧 → コメント → 合意)を実 LLM で通す。あわせて、Phase 107〜109 から積んだ画面確認の項目を、ヘッドレスのブラウザで見る。操作はすべて Claude がヘッドレスで行った(相談の決定4。推奨と違った選択)。ユーザーの画面確認は、この後に別に行う。

## 流れの手順と実際

ログインは題材の持ち主(`devex-api/backend/scripts/seed.py` の開発用の利用者)。画面の操作は run-devex-ui の `shot.mjs` と手順ファイル、クライアントはログインしていない Playwright の文脈。

1. **説明書の書き出し(前)**: `measure.py 3 4`(CR-3・CR-4)。
2. **束 B-5** → **CR-5**(B-5 基準。対象 FR-001・FR-002・FR-003)。規模が「作業単位・ファイル・テスト 0件(古いまま写した段階から数えたため、少なく出ることがある)」。段階7 の承認済みのタスクが、CR-4 の前の処理 ID(F-04・F-05・F-09)を指していた → ユーザーに進め方を聞いた。
3. **段階を最新にする**:
   - 段階6(任意): 検証のエラー6件(関数の詳細が古い手順を指す)。変更の影響の印6件を確認済みにし、「段階6を飛ばす」で承認。
   - 段階7: 「機能一覧に無い処理を持つタスク(3)」の一覧(Phase 109)が出たが、モジュールのパスも段階4 の作り直しで食い違っていた(検証のエラー13件)。変更の影響の「段階7 を CR-4 で作り直す」(実 LLM)→ エラー0。印11件を確認済みにして承認。
   - 段階8: 「段階7に無い手順書」5件を消し、7単位の手順書を作り直した(実 LLM 7回)。印5件を確認済みにし、「最重要の未定義・要決定が5件」の確かめで「このまま承認する」。
   - テスト仕様書: 作り直した(実 LLM。v2)。
4. **CR-5 を取り下げ**、**束 B-6**(段階1〜8 すべて承認済み)→ **CR-6**(同じ中身)。規模は 作業単位5・ファイル13・テスト5・画面1・API0。
5. **案の LLM の下書き**: 2案(すべて TOP20 / 表示を TOP10 に戻す。おすすめは案1)。取り込み、中間の案(取得は20件・解説は上位10件のまま)を案3 として足して保存。案ごとの規模の列が出た。
6. **共有リンク**(期限14日。CR は説明済み)→ ログインしていないブラウザで開き、画面の文を書き出してクライアント役で読んだ([110-1](./Phase-110-1.md))。
7. **クライアント**: 名前「発注側の担当者」、コメント(利用料の増え方を後で教えてほしい)、案1 を選んで合意。画面は「判断済み・合意・選んだ案・判断した人・記録: 共有リンク」。
8. **開発者**: 内容のタブの合意の記録に「出どころ: 共有リンク」。コメントに返信。影響のタブで文書へ反映(実 LLM)→ 予測と実際の比較で 作業単位・ファイル・テストが一致(画面は文書の側の確認が未確認)。
9. **要件定義書 v13**: FR-001〜003 が案1 の文になり、推測に戻った(確認事項は「CR-6 の反映で文が変わりました →」)。利用者は U-001・U-002 を引き継ぎ、保護で合意の形に戻った。
10. **段階1 を CR-6 で作り直して承認**(実 LLM)。LLM は F-32・F-33 を1つの処理 F-34 にまとめた。段階2 に「機能一覧に無い処理の処理概要(2)」が出た。下流の段階2〜8 は古い(見直しの印35件)。CR-6 の検証はここで止めた。
11. **説明書の書き出し(後)**: `measure.py 3 4 6`(2回流して同じ)。

## 画面確認の結果(Claude のヘッドレス)

| 項目(出どころ) | 結果 |
|---|---|
| 内容のタブの選択肢の節・案のカード・規模の表(Phase 107) | 見られる。**気づき**: 開発者の規模の表は列が広く、数が列の右の端に寄って項目の名前から遠い |
| 案の編集欄・下書きの枠・取り込み(Phase 107) | 動く。**気づき**: 取り込むと説明書が変わるので、取り込んだ直後の下書きの枠に「作った後に説明書が変わりました」と出る |
| 合意のダイアログの案(Phase 107) | 案のラジオ(初めは未選択)・おすすめの印。OK |
| 共有タブ(URL の枠・一覧・ダイアログの文)・コメント欄と返信(Phase 107) | OK |
| 共有リンクの画面: 開いている・直しています・前回から変わった点・取り消し・期限切れ・判断済み・暗いテーマ(Phase 108) | どれも想定どおり(捨てのプロジェクトの CR-2 で、直す・説明済みに戻す・取り消す・期限を DB で過去にする、を行った) |
| 共有リンクの画面: スマートフォンの幅(375px)(Phase 108) | **指摘**: 説明書の表(規模の表の内訳が長い)が説明書の枠からはみ出し、外側で切れて読めない(横に送れない)。説明書の大見出しが大きく、題が4行になる |
| 段階7 の機能一覧に無い処理の一覧(Phase 109) | 題材で表示を確かめた(3行・付け替え先の選択・「すべて外す」)。付け替えは行っていない(段階7 は作り直した) |
| 段階2 の一覧の文の長さと位置(Phase 109) | 題材の F-32・F-33 で表示(付け替え先に F-34)。OK |
| 確認事項の「CR-n で変わった」(Phase 109) | 題材で3件「CR-6 の反映で文が変わりました →」。OK |
| 束の一覧の入れた CR(Phase 109) | 題材の B-1〜B-6 はどれも入れた CR なし(「−」)。表示は OK |
| ブラウザの誤り | ログイン前と共有リンクの画面の `401 POST /auth/refresh`、下書きの無い CR の `404 GET …/options/draft`(どちらも想定どおり)。開発者の段階の承認の `409`(見直しの印が残っているとき。画面は理由を出す) |

指摘と気づきは、ユーザーの画面確認と合わせて「Phase 完了後の調整」で直すかを決める(#38)。コメントの削除・編集の要否も、ユーザーの画面確認で決める。
