# ゴール3: Devex の生成文書と Phase-<N>-introduction.md の突き合わせ

CLAUDE.md「プロジェクトのゴール」3 の「最低1回、Devex の実際の生成文書と `Phase-<N>-introduction.md` を突き合わせ、共通化できるテンプレート要素を最低1つ具体的に特定する」を行った記録(2026-10-06)。[総括の振り返り](./overall-retrospective.md) 5節で保留にしていた項目。

## 1. 入力

- **Devex の生成文書**: [`appendix/goal3-generated/`](../../appendix/goal3-generated/README.md)。ローカルの devex-api を実際の LLM(Gemini Flash-Lite)で動かし、Devex 自身を題材に、両モードで生成した。人が加えたのは入力・選択・承認だけで、生成物は無修正(同 README「人が入力・操作したもの」)。
  - 簡易モードの実装計画書: [`simple/implementation_plan.md`](../../appendix/goal3-generated/simple/implementation_plan.md)(4.1 マイルストーン / 4.2 WBS / 4.3 開発環境 / 4.4 リスク)
  - 詳細設計モードの実装計画(段階7): [`detailed/bundle/implementation_plan.md`](../../appendix/goal3-generated/detailed/bundle/implementation_plan.md)(マイルストーン表・マイルストーンごとのタスク表・処理の割り当て・開発環境・リスク)
- **突き合わせの相手**: 実装計画に当たる CL 教材は introduction。off と on の典型を1本ずつ選んだ。
  - [`Phase-4-introduction.md`](../Phase-4/Phase-4-introduction.md)(off、ステージ1の QA)
  - [`Phase-23-introduction.md`](../Phase-23/Phase-23-introduction.md)(on、ステージ4の段階7。生成した実装計画を作る Phase そのもの)

対応の前提: 生成された実装計画の**マイルストーン1つ**が、CL の **Phase 1つ**(introduction 1本)に当たる。タスクの1行が、章(作業単位)に当たる。

## 3. 共通化できるテンプレート要素(特定した1つ)

**「作業単位の表」── 1行 = 作業単位、列 = 対象の処理ID・作成・変更するファイル・役割1行・確認方法**

- introduction の**実装前チェックリスト**(章 | 主なファイル | 役割1行 | テスト観点)と、詳細設計モードの**タスク表**(区分 | タスク | 作成・変更するファイル(例) | 処理)は、どちらも「作業単位ごとに、触るファイルと狙いを1行で示す表」である。同じ形にそろえられる。
- 互いに足りない列がある。
  - 生成側に無い: **確認方法**(テスト観点)。生成側では、テストが「テスト」区分の別の行になり、ファイルも「—」、確認の中身も「結合テストを実装する」だけになる。実装の行ごとに「何で確かめるか」が無い。
  - introduction に無い: **対象の処理ID**。章が機能一覧のどの処理を作るかは、本文を読まないと分からない。生成側は、処理ID でマイルストーンとタスクを結び、漏れを検証で警告できる。
- そろえた形(案):

  | 作業単位 | 対象の処理ID | 作成・変更するファイル(依存順) | 役割1行 | 確認方法 |
  |---|---|---|---|---|

  - 「作成・変更するファイル」は、CL 側の #30(依存順)の並べ方をそのまま使える。
  - 「確認方法」は、CL 側では実行するテストのコマンド、Devex 側ではテスト観点の1行(コマンドは実装時に決まるため)。

この表は、次のステージの「実装手順書」([総括](./overall-retrospective.md) 6節)で、introduction と生成文書の両方のひな形になる。

**足りない列へのユーザーの判断**(2026-10-06):
- 生成側の確認方法(テスト観点): テスト設計の生成として、今後の機能追加で検討する。今は段階7の model を変えない。
- 教材側の対象の処理ID: 教材は今のままでよい(問題ない)。

## 4. ほかに見えたこと

- **生成側の粒度は、introduction の粒度より1段粗い。** 生成されたマイルストーンは「認証」「プロジェクト管理」「ヒアリング」「生成と閲覧」の4つで、ステージ1の実際の Phase 1〜3(基盤 → BE → FE)とは切り方が違う。生成側は機能(縦)で切り、各マイルストーンの中を層(横)で分ける。CL の Phase 1〜3 は層で切った。縦で切るほうが、マイルストーンごとに動くものができる。
- **依存とマイルストーンの中の順が、生成側に無い。** introduction の「依存」列と「写経順序」は、AI に実装させるときにも要る(前方 import の監査、#15・#23)。
- **「申し送り」と「リスク」は、同じ節にまとめられる。** 先の見込み(リスク)と、実際に残ったもの(申し送り)を、状態(未解決/解決: どこで)を持つ1つの表にすると、計画の段階から実装後まで同じ節を使い続けられる。
- **簡易モードと詳細設計モードの差**: 簡易モードの WBS はチェックボックスの箇条で、ファイル・処理ID が無い。番号の重複(「2.2」が2回)もあった。詳細設計モードは表で、処理ID とファイルを持つ。突き合わせの相手としては、詳細設計モードのほうが introduction に近い。

## 5. → Devex 仕様への示唆(#25)

提案であり、段階7の model とプロンプトは変えていない(採用はユーザーが決める。#38)。

1. **テスト設計の生成**(今後の機能追加で検討): 実装のタスクごとに「何で確かめるか」を書かせる。段階7のタスクに確認方法を足すか、テスト設計を別の段階・文書にするかは、そのときに決める。
2. ~~**マイルストーンに「依存」を持たせる**~~: 取り下げた。ユーザーの質問「マイルストーンごとにタスクがまとまっているので問題ないように見えるが、想定している挙動は何か」への回答は次のとおり。
   - 想定していた挙動: `Milestone` に「先に終わっている必要があるマイルストーン」を持たせ、並行して進められるものを示す。また、Should を後回しにして順を入れ替えたとき、前提が後ろに回っていないかを検証で警告する。
   - 実際の生成: M-01 → M-04 が一直線で、並び順がそのまま依存の順になっている。個人開発の Devex では並行して進めることも少ない。依存が役に立つのは、並行して進めるときと、順を入れ替えるときだけなので、今は要らない。
3. **実装手順書のひな形**: 実装計画のマイルストーン1つを、introduction 1本に展開する。目的 = ゴール、章一覧 + 実装前チェックリスト = 3節の作業単位の表、申し送り = リスクと持ち越し。
4. 入力の内容: `docs/internal_design.md` の `prompt_templates` 設計と、段階7の下書きのプロンプト(`plan_drafting.py`)を見直すときに、この節を入力にする。

## 7. 限界

- 1回の生成で、題材は Devex だけ。LLM の出力は回ごとに揺れる。
- 段階2で DFD を描く機能グループを選ばなかったため、詳細設計書の 02・03 の一部が空(実装計画の突き合わせには影響しない)。空の ER のまま承認できたこと自体は不具合だった(8節)。

## 8. 生成で見つかった不具合と対応

生成の過程で見つかった Devex の不具合は、ユーザーの判断で同じ機会に本体を直した。詳細(原因・確認の記録)は [`goal3-generated/README.md`](../../appendix/goal3-generated/README.md)「調査の結果と対応」、決定の要約は [decision digest](../decision-digest.md)「ステージ4完了後 ── ゴール3と、生成で見つかった不具合の修正」。

| 不具合 | 原因 | 対応 |
|---|---|---|
| ヒアリングの AI と生成のボタンがずれる(AI がまだ質問しているのにボタンが出る。AI がチャットで確定を求め、要件定義書を書き始める) | 完了判定(返信の後に画面が別に呼ぶ LLM)と、ヒアリングの AI が互いを知らずに動く。プロンプトにも「チャットに文書を書かない」が無い | 発言のたびに先に判定し、十分ならその判定のサマリを返信にして、同時にボタンを出す。足りなければ不足点を AI に渡して聞かせる。判定は保存し、GET はそれを返す(`projects.hearing_check`) |
| プロジェクト名がシステム概要の全文になる | title をシステム概要から作っていた | 作成フォームに「プロジェクト名」(必須・40文字以内)を足した |
| 簡易モードの WBS の番号が重複する | プロンプトが番号を指示せず、LLM が自分で振った | タスクに番号を付けないよう指示した |
| DFD を描かなくても段階2・3を承認できる(ER が空) | DFD が無いと ER の下書きの入力が空になり、テーブル0件の検証が無かった | 段階2に警告 `NO_DFD_GROUPS`、段階3にエラー `ER_EMPTY` |
