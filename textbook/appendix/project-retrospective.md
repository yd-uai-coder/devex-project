**見えること**:
- ルールが大きく変わったのは、ステージ4の後の1回だけだった。そこで「誰が本体を書くか」と「記録・申し送り・コミットの扱い」を決め直した後は、運用注記で足す程度で済んだ。ステージ7以降は CLAUDE.md のルールの本文を一度も変えていない。

### 3.2 効いた型

1. **ステージの最初の仕様診断で、Phase ごとの未確定事項を表にする**(#28。[25-4](../Phase-25/Phase-25-4.md)・[33-5](../Phase-33/Phase-33-5.md)・[41-5](../Phase-41/Phase-41-5.md)・[51-5](../Phase-51/Phase-51-5.md)・[61-3](../Phase-61/Phase-61-3.md)・[73-3](../Phase-73/Phase-73-3.md))。ステージ5以降の6ステージで、計画の変動は計2回(P59 の差し込み・P78 の計画の一部の撤回。測るまで分からない題材か、原因を調べた結果)だった。
2. **未消化の申し送り**(#37)と、ステージ完了時の棚卸し。後の Phase の着手時に読む場所が1つに決まり、ステージ7以降は「解決 / 閉じる / 次のステージの入力 / 持ち越し」で毎回分けられた。
3. **画面確認と本番反映を溜めて、最後の Phase でまとめる**(#37 の運用注記)。ステージ5〜10 で、溜めた画面確認の本番での指摘は計1件(ステージ9。開発と本番のビルドの違い)だった。
4. **偽物(偽の LLM・偽の Google)+ 契約テスト**(#36・handoff v2 #31)。E2E を偽物で回しつつ、偽物の出力が本物の経路を通ることを固定した。偽の Google は、外部アカウントの準備が遅れても作業を止めなかった(ステージ10 Q3)。
5. **正解を先に書いて測る効果測定**(ステージ6〜8)。ベースラインと同じ規則で測り直し、主観でなく数字で範囲を決めた。
6. **道具による検査**(`samples_check.py`・`link_check.py`)。on の Phase で samples が後追いになる問題を、人の注意でなく機械で拾えた。
7. **AI が Phase の中でブラウザで確かめる**(ステージ9から)。完了後の調整が、ステージ9は11 Phase で3件、ステージ10は0件になった。

### 3.3 効かなかった・使われなかった型

- **Phase 完了チェックの設問**(#22): 全 Phase に置いたが、答えた記録は1件も無い。ステージ6の後に「要約(読み物)」と位置づけ直した。
- **写経そのもの**(off): 手で実装しても設計の理解は思ったほど実感できなかった、とユーザーが判断した([`overall-retrospective.md`](./overall-retrospective.md) 3節)。off で残ったのは、写経漏れ・写経ミス(Cookie 化・完了判定のルートの配線漏れ・repr 化の3か所の再発)を見つける経験である。
- **on の Phase の学習の回収**: 「読む順番」「設計判断の要点」の欄(handoff v2 5.7)は、最後まで足さなかった。教材は実装手順書のひな形としては使われたが(ステージ5)、ユーザーが教材から仕様を追った記録は少ない。
- **tagmerge.py**: on の Phase の samples の補助として使い続けたが、手直しが毎回要った。直さないまま終わった(8節)。
- **E2E を CI で流す**: 候補のまま、一度も入れなかった(7節の判定では「条件つき」)。

### 3.4 自動実装モードの切り替えの評価

Phase 7 で on に切り替えた理由は「完成品から仕様を追う」「教材の中身はモードで変えない」だった([`overall-retrospective.md`](./overall-retrospective.md) 3節)。73 Phase を on で回した結果は次のとおり。

- **速度**: 律速が「写経」から「着手時の設計の決定と画面確認の往復」に移った。Phase 7〜79 を19日で進めた。
- **質**: 本番での確認の指摘は、ステージ4〜10 で計1件だった。テストと E2E・効果測定・契約テストが、人の実装の代わりの歯止めになった。
- **教材の中身**: on でも #14 のテスト観点を省かず、samples も同じ内容で作り続けた(T2 の改訂)。その結果、教材は「実装手順書のひな形」として、Devex の段階8に直接使えた。
- **残った課題**: 設計の理解が人の側に残るかは、測っていない。採否はユーザーが毎回決めたが(#38)、それは「判断できた」ことであり、「仕様を追えた」ことの裏付けにはならない。

### 3.5 #18(1セッション = 1 Phase)の実測

ステージ5〜10 の 55 Phase のうち、2セッション以上だったのは4つだけだった(P37 は利用の上限で中断・P49 は着手時に2セッションと決めた・P54 は開発環境の DB の事故・P58 のセッションは番号の付け替えだけで終えた)。どれも #18 の原則の範囲で説明がつく。#18 は最後まで変えなかった。振り返り・ルールの改訂を別セッションにする運用も守られた(この振り返りも、本番確認とは別のセッションで行った)。

## 4. AI の提案の精度(#39)のまとめ(ステージ3〜10)

数字は [`overall-retrospective.md`](./overall-retrospective.md) 11.1 の表による(概算)。

| 指標 | ステージ3・4 | ステージ5〜7 | ステージ8〜10 |
|---|---|---|---|
| 推奨そのものの外れ | 複数(機能ごとの部分図の撤回・検証規則の撤回など) | 0 | 1(73-1 の紐付け。脅威だけから推奨を組んだ) |
| 推奨と違った選択の主な向き | 推奨の外れ | 範囲を狭める・広げる・基準を厳しく | 広げる・見た目と操作感の好み |
| 計画の変動 | 撤回2・分割3 | 0 | 2(P59 の差し込み・P78 の撤回) |
| 完了後の調整(Phase あたり) | 約0.7〜1.0 | 約0.2〜0.6 | 約0〜0.6 |
| 本番での確認の指摘 | 0 | 0 | 1(ステージ9。開発と本番のビルドの違い) |

**見立て**:
- 精度が上がったのは、ステージ4とステージ5の間である。ここで変わったのは、AI の推奨の採用率ではなく、**推奨が外れる種類**だった。ステージ5以降の「推奨と違った選択」は、ほぼすべて、方向は合っていてユーザーが範囲・基準・見た目を変えたものである。
- 理由は、11.3 の (a)〜(d) が全期間で裏付けられた: (a) 未確定事項の先出し、(b) digest と申し送りの蓄積、(c) 既存の型の再利用、(d) 数字の基準。
- 外れが残る場所は一貫していた。**型の無い新しい画面**(P35・P53)、**測るまで分からない生成の質**(P58)、**利用者の希望と脅威が対になる要件**(73-1)である。

**差し引くべき要因**(全期間):
- ユーザーが推奨に寄った可能性は、採否と独立な指標(本番の指摘・効果測定・E2E の壊れ)で毎回確かめ、寄っただけでは説明できないことを確かめた。
- ステージごとの題材の違い(図・詳細設計・手順書・ヒアリング・規則・画面・認証)が大きく、件数の単純な比較には限界がある。
- AI のモデルの版は記録に無い。

## 5. #27 の具体化 ── Devex の生成文書を Phase 0 の入力にする方法

#27 は「Devex 完成後は、Devex 自身が生成するドキュメントを Phase 0 の入力に切り替える。その方法は完成後の振り返りで具体化する」としていた。その具体化である。実際にこの方法で Phase 0 を回したことはまだ無いので、**次のプロジェクトの Phase 0 で試す案**として書く。

### 5.1 何を入力にするか

詳細設計モードの出力(zip)を正の入力にする。簡易ドキュメントモードは、粒度が1段粗い(ゴール3の4節)ので、詳細設計モードが使えない小さなプロジェクト向けとする。

| Devex の出力 | Phase 0 での使い方 |
|---|---|
| 要件定義書(要件ID・出どころ・未決) | 仕様診断(#28)の入力。出どころが「推測」の要件と、未決の観点は、そのまま「最重要」か「中程度」の候補にする |
| 外部設計書(画面ID・API) | 仕様診断の入力。画面の Phase には、画面ID を章の参照に使う |
| 詳細設計書 01〜07 | 各 Phase の introduction の「前提」で参照する。教材に写さない |
| 実装計画(マイルストーン・タスク・処理の割り当て・リスク) | **ロードマップの下書き**。下の 5.2 |
| 実装手順書(段階8。単位ごと・AI 向けの版) | **章の下書き**。下の 5.2 |
| 実装可能性チェックの結果(未定義) | 仕様診断の一次結果。AI が自分で診断する前に、この一覧を先に置く |
| 設計レビューの指摘(採否つき) | 不採用の理由と、採用して直したものは、decision digest の初期値にする |
| テスト仕様書 | 各章の「テスト観点」(#14)の下書き |

### 5.2 どの粒度で読み替えるか

| Devex の単位 | CL の単位 | 読み替えの規則 |
|---|---|---|
| 実装計画のマイルストーン | Phase | 1 マイルストーン = 1 Phase を原則にする(ゴール3の対応)。「1つの機能のまとまり」を超えるときは、着手時の相談で分割する(handoff v2 5.9) |
| 優先度(Must/Should/Could) | ステージ | Must のマイルストーンをステージ1、Should をステージ2 にまとめる |
| 実装手順書の単位(M-01-T01 など) | 章(作業単位) | 1 単位 = 1 章。単位の「作成・変更するファイル(依存順)」が #30 の表、「テスト観点」が #14、「確認方法」が実装前チェックリストのテスト観点になる |
| 単位の「未定義・要決定」 | introduction の「着手時の相談で決めること」 | 着手時の質問の候補にする |
| 実装計画のリスク | introduction の「未消化の申し送り」の初期値 | ゴール3の4節のとおり、リスク(見込み)と申し送り(実際に残ったもの)を同じ表で持つ |

### 5.3 人が決めること・Phase 0 に残る仕事

- ロードマップの下書きは機械的に作れるが、**自動実装モード(#21)・ステージの区切り・Phase の分割**は人が決める。
- 仕様診断(#28)は、Devex の未定義・推測の一覧を出発点にし、AI は「Devex が見つけられないもの」(既存のコードとの食い違い・外部アカウントの準備・本番の環境)を足す。ステージ10 の Q3(外部の準備の遅れ)は、Devex の出力からは出てこない種類の項目である。
- Phase 0 の章(`Phase-0-<N>.md`)は、「Devex の出力をどう読み替えたか」と「Devex の出力に無かったので足したもの」を記録する。後者が、Devex のヒアリングと生成の改善の入力になる(#25)。

### 5.4 限界

- ゴール3で突き合わせたのは1回・題材は Devex だけである。
- Devex の実装計画は機能で縦に切る。このプロジェクトのステージ1は層で横に切った。縦で切る方が「マイルストーンごとに動くものができる」ので、CL の Phase もそれに合わせる想定だが、試していない。
