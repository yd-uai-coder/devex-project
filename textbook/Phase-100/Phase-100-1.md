## スコープ(構想から)

位置付けの 12章は、ステージ13 の中身を次のように置いている。

- **中身**: 変更の規模の集計(作業単位・ファイル・テストの数)、選択肢つきの説明(今の選択肢カードの形)、クライアントの閲覧・コメント・合意(共有リンク)
- **完了の判断基準(案)**: クライアント役(今の測定のペルソナと同じ規則)が、説明書だけで合意・却下を判断できる

## 調べたこと(推奨の根拠)

- **説明書**(`devex-api/backend/app/change_requests/explanation.py`):
  - 5節(内容と背景 / 対象の要件 / 影響の一覧 / 関わる未決事項 / 影響を受ける作業単位とテストの数)を、束の写しと予測から決定的に組み立てる。
  - 5節の数(`affected_units`)は、予測の作業単位(段階7 のタスク・段階8 の手順書)と、束のテスト仕様書のうち予測の処理か対象の要件に当たるテストである。ファイルの数は無い。数えられなかった0件と、数えた0件を区別しない。
  - 任意の要約は、確認済みで古くないときだけ出力に載る。
- **ファイルの材料**(`app/detailed_design/procedure_coverage.py` の `unit_files`): 段階8 の手順書の「作成・変更するファイル」と、段階7 のタスクのモジュール・設定のファイルを、作業単位ごとに集められる。
- **選択肢カード**(ステージ6。`chat_history.cards`): 観点・問い・選択肢(名前と結果)・おすすめの番号と理由を持つ。ヒアリングの問いのための形で、CR には無い。
- **認証**(ステージ10): メールとパスワード、または Google のアカウントでログインした本人だけが、自分のプロジェクトを読める(`CurrentProjectDep`)。アカウントの無い相手に見せる入口は無い。
- **CR の状態と合意の記録**(ステージ11): 「説明済み」にする条件は無い(Phase 84)。説明済みで直すと下書きに戻る。合意・却下の記録(相手・日時・メモ・理由)は開発者が入れる。
- **ベースライン**([100-2](./Phase-100-2.md)): CR-3 は判断できたが、CR-4 は判断できなかった。CR-4 の説明書は「作業単位0件・テスト0件」だったが、実際は段階1 を2回作り直し、印は40件付いた。束 B-4 の段階1 の処理に要件 ID が無く、予測が画面1件で止まったためである。

## 診断と決定

診断は #28 の3段階で示した。計画モードで1回(4問)、計画の承認の後に3回(10問)質問した。

推奨と違った選択は8件ある。計画モードの「使い勝手の見直しをステージ13 の後に回す」(**狭める**向き)と、入力の判断の7件(**広げる**向き。偽の LLM と、「使われ方を見て決める」6件)である。

#### 決定1の理由(確からしさを出す)

- 完了の判断基準は、クライアント役が説明書だけで判断できることである。ベースラインの CR-4 は、「0件」が実際と大きく違ったために判断できなかった。数を足すだけでは、この誤りが残る。
- 予測は束の写しをたどる。束の段階が古い・要件と処理がつながっていない・テスト仕様書が無い、のどれかなら、数は少なく出る。これを「数えられない(理由)」として説明書に出せば、クライアントは「この部分は別に聞く」と分かり、開発者は束を作り直すきっかけを得る。
- LLM の工数の見積もりは、根拠を確かめにくい(ステージ11 の要約の照合と同じ問題)。数は決定的に出し、手間の目安は選択肢の「結果」の欄で開発者が書く(決定2)。

#### 決定2・3の理由(選択肢と共有リンク)

- 選択肢は、ステージ6 の選択肢カード(問い・選択肢・結果・おすすめ)の形を CR に移す。案の文は開発者が責任を持つ。LLM の下書きは、ステージ11 の要約と同じく、確かめるまで出さない。
- 案ごとに対象の要件と変更後の案が違えば、予測も違う。規模を案ごとに数えれば、クライアントは手間で比べられる。
- 共有リンクで合意まで押せないと、判断基準の「合意・却下」を画面で通せない。アカウントを作らせない代わりに、リンクは推測できず・期限があり・取り消せるようにし、押した人の名前と見た説明書の版(指紋)を残す。CR の合意の記録の「相手」は、今は開発者が書く自由文である。共有リンクの合意では、押した人の名前がそこに入る。

| # | 論点 | 選択肢(推奨は先頭) | ユーザーの決定 |
|---|---|---|---|
| 5 | 共有リンクと CR の状態 | **共有で「説明済み」にし、直すと止まる**(リンクを作ると説明済みになる。開発者が直して下書きに戻ると、リンクは「直しています」を出して合意を押せない。もう一度説明済みにすると、前回から変わった点を出して再開する。合意には押したときの説明書の指紋を残す)/ 状態と切り離す | 推奨どおり |

#### 決定5・6の理由

- クライアントがリンクで見ている間に CR が直されると、見た説明書と合意した中身がずれる。今の「説明済みで直すと下書きに戻る」の規則に、リンクの止まりを結べば、ずれを防げる。指紋は、ステージ11 の要約の「古い」の判定と同じ値(説明書の md の sha256)を使える。
- ベースラインの引っかかり(推測・未決の意味・ID・古い要約)は、どれも決まった言い換えで直せる。要約に任せると、確認済みの要約が無い CR では直らない。

#### 推奨と違った選択(入力の7件)

- 推奨は、ステージ13 を説明とすり合わせ(規模・選択肢・共有リンク)に絞り、名前や ID の揺れは、使われ方を見て決めることだった。位置付けの目安(約9 Phase)に収めるためである。
- ユーザーは、偽の LLM と、「使われ方を見て決める」のうち6件をステージ13 に入れた。偽の LLM が名前を言い換えるようになれば、名前で同一性を決める要素(外部連携・推測の利用者・段階1 の処理)の照合を、単体テストと E2E で確かめられる。外部連携の重複・段階2・3・7 の処理 ID・推測の利用者のキーは、その検査の対象になる。残りの4件(起点の種類・束の一覧の CR・巡回で消えた版の履歴・DFD だけを直した承認)は、CR と合意の記録の周りの残りである。
- 一方で、使い勝手の見直しはステージ13 の後に回した(範囲を狭める向き)。
- Phase の数は、[100-4](./Phase-100-4.md) で Phase 101〜110 の10 Phase(Phase 100 を含めて11)にした。目安の約9 より2つ多い。

## Claude の判断(診断中)

- **CR-4 の0件の原因を、診断の前に開発 DB で切り分けた**: 束 B-4 の段階1 の写しを読み、処理の `req_ids` が空なのを確かめた。決定1の「確からしさ」は、この結果から足した論点である。
- **クライアント役の規則を、説明書を読む場面に合わせて書いた**: ステージ6〜8 の利用者の役の規則(聞かれたことにだけ答える)は、ヒアリングのためのものである。説明書の場合は「説明書の外を見ない・判断に要る問いを種類つきで全部書く・明らかに合わない数字は問いにする」を規則にした([`client.md`](../../appendix/measurements/stage13/client.md))。
- **共有リンクの公開の入口は、詳細を各 Phase で決める**: トークンの長さ・期限の既定値・保存の形(ハッシュ)・回数の上限は、[100-4](./Phase-100-4.md) の Phase 103 の未確定事項にした。
- **Phase の数**: 入力の7件で範囲が広がった。[100-4](./Phase-100-4.md) では、API と画面を分け、名前の揺れを偽の LLM と同じ Phase に集めた。
