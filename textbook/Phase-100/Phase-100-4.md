# Phase-100-4: ステージ13 の実装計画(Phase 101〜110)

## この章の目的

[100-1](./Phase-100-1.md) の決定をもとに、ステージ13(説明とすり合わせ)を Phase に分ける。Phase ごとに、成果物・依存・着手時に決めること(未確定事項)を示す。位置付け 12章の目安は約9 Phase だが、入力の7件で範囲が広がったので、Phase 100 を含めて11 Phase にした。

自動実装モード: on([introduction](./Phase-100-introduction.md) 参照)。この章は計画の文書だけで、本体と samples は変えない。

## この章で作成・更新したファイル

なし(計画の文書)。Phase の一覧は [100-3](./Phase-100-3.md) で [`docs/implementation_plan.md`](../../docs/implementation_plan.md) 4.1 に写した。

## 順番の考え方

- **API を先に、画面を後に**。ステージ11・12 と同じ並びにした。
- **規模の集計(101)を最初に**。選択肢(102)は案ごとに規模を数え、共有リンク(103・104)は規模と選択肢の載った説明書を見せる。
- **共有リンクは、閲覧(103)と、コメント・合意(104)に分ける**。103 は公開の入口(トークン・期限・取り消し・回数の上限)と状態の結び方、104 は書き込み(コメント・合意・却下)と合意の記録への入れ方で、確かめることが違う。
- **偽の LLM(105)を、名前の揺れの直しより先に**。言い換える偽の LLM で、まず今の照合の弱さをテストで示し、同じ Phase で外部連携の重複と推測の利用者のキーを直す。段階2・3・7 の参照の切れ(106)も、この偽の LLM で確かめる。
- **合意の周りの残り(106)は、CR の画面(107)より前に**。確認事項の戻し・起点の種類・束の一覧の CR は、107・109 の画面が読む。
- **最後の Phase(110)で、効果測定・全 E2E(#36)・開発環境での画面確認・`OPERATIONS.md` 10.8節のステージ13 の分をまとめて行う**(#37 のステージ11完了後の運用注記)。本番への反映はステージ15 の完了時。

## 未確定事項(各 Phase の着手時に決める)

**どの Phase も**:
- 自動実装モード(#21)。
- テンプレートから取り込むもの(あれば、どのファイルか)。今の本体に無い部品は、`~/my-apps/project-templates/` のテンプレートから取り込み、samples にも作る(#21)。
- 簡易ドキュメントモードの全入口(書く・読む・画面・URL の直開き。共有リンクの公開の入口も)を断ることの確かめ。

### Phase 101

- ファイルの数の重なりの除き方(同じファイルを複数の作業単位が触るとき)と、段階8 の手順書が無い作業単位の扱い(段階7 のモジュールで数えるか、「数えられない」か)。
- 「数えられない」の判定の規則(束の段階の状態だけで決めるか、要件 → 処理のつながりの有無も見るか)。
- 説明書の節の番号と並び(規模の節を5節に置き換えるか、6節にするか)。要約の照合(Phase 84)が数字を5節と照らすので、その範囲の見直し。
- 読み手向けの1文の文言(固定の文か、CR の中身で変わる文か)。

### Phase 102

- 案の持ち方(CR の列の JSON か、別のテーブルか)。案ごとに対象の要件を変えられるか(変えられれば規模が案ごとに違う)。
- 案が1つも無い CR の扱い(今の説明書のまま)。
- LLM の下書きの照合(要件 ID・数字。要約と同じ規則か)と、下書きの用途のモデル。
- 合意で選んだ案を、反映の再生成の指示(`build_cr_instruction`)にどう入れるか。

### Phase 103

- トークンの長さ・保存の形(ハッシュ)・期限の既定値と延長・CR ごとに複数のリンクを持てるか。
- 公開の入口の回数の上限(今のレート制限の仕組みを使う)と、期限切れ・取り消し・存在しないリンクの応答(区別するか)。
- 「前回から変わった点」の材料(前回の説明書の写しを持つか、指紋だけか)。
- 説明済みで下書きに戻ったときの、リンクの扱い(止めるだけか、取り消すか)。

### Phase 104

- コメントの単位(CR 全体か、節・案ごとか)と、返信の形(1段か、スレッドか)。
- リンクからの合意と、開発者の合意の記録の関係(開発者があとで直せるか。両方が押されたとき)。
- 却下の理由を必須にするか。

### Phase 105

- 言い換えのモードの決め方(偽の LLM の引数か、環境変数か)と、言い換えの規則(決定的に。例: 名前の後ろに語を足す)。
- 推測の利用者のキーの形(利用者に ID を振るか、名前の照合の規則にするか)。今の確認事項の記録(`user:<名前>`)の移行。
- 外部連携の重複の判定(同じ要件 ID か、名前の近さか)。

### Phase 106

- 段階2・3・7 の一覧で、付け替えと削除のどちらまでできるか(段階5 と同じか)。
- 確認事項を未確認に戻す時点(反映済みの時点か、検証済みか)と、クライアントが共有リンクで合意した案の文なら確認済みのままにするか。
- 起点に足す種類(処理・データストア・外部連携など)。
- DFD・データ辞書の直しを「人が直した」とみなす判定(版の比較か、保存の記録か)。

### Phase 107〜109

- 画面の置き場(CR の詳細のタブを足すか、今のタブに入れるか)。イメージを先に見せる(Phase 88・97 と同じ)。
- 共有リンクの画面の見た目(ログインの画面と同じ枠か、別の枠か)。クライアントに見せない情報(Devex の用語・内部の ID)の範囲。

### Phase 110

- 新しい CR の題材(トレンド追跡アプリの続きで、選択肢が自然に2つ以上ある変更)。
- 実 LLM を使う範囲と費用の見積もり(選択肢の LLM の下書きを使うか)。
- 画面確認で決める項目。
