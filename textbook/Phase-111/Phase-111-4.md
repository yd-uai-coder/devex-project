## 順番の考え方

- **使い勝手の直し(112)を最初に**。ステージ13 の画面の指摘を先に閉じ、取り込みの画面(116)は直した部品の上に作る。`tagmerge.py` の手直しは Phase 111 のセッションで済んだ(振り返り 18.7)。
- **競合の判定(112)は、束の鮮度(113)の材料と同じ**(束の写しと今の版を比べ、束の後に反映した CR を時系列から引く)。112 で純粋関数にしておき、113 はそれを束全体の鮮度へ広げる(#17)。
- **API を先に、画面を後に**(ステージ11〜13 と同じ並び。112 は指摘の直しなので、1つの Phase で API と画面を両方触る)。
- **資料と束の鮮度(113)を、違いの取り出し(114)より前に**。違いの取り出しは、資料の本文と、比べる相手の束(古ければ知らせる)を使う。束の鮮度の判定は、古い束を基準にした説明(決定5)と同じものを使う。
- **違いの取り出し(114)と、CR の下書きへのつなぎ(115)を分ける**。114 は LLM と決定的な検査(引用・ID)で確かめることが多く、115 は CR の入口・背景・知らせ・規模の表の鮮度で確かめることが違う。
- **最後の Phase(117)で、効果測定・全 E2E(#36)・マイグレーションの往復・開発環境での画面確認・`OPERATIONS.md` 10.8節のステージ14 の分をまとめて行う**(#37 のステージ11完了後の運用注記)。本番への反映はステージ15 の完了時。

## マイルストーン15(完了の判断基準)

題材(トレンド追跡アプリ。束 B-7 を作ってから)で、資料セット A・B を取り込みに各2回通したとき:

1. 拾い漏れと誤りが、ベースライン(拾い漏れ0、誤り0〜1)より増えない。
2. 一覧に出た違い(弾いたものを除く)の対象が、すべて合意済みの行のキーか「新規 + 起点」で、CR の下書きにそのまま渡せる。
3. 一覧に出た違いの根拠の引用が、すべて資料に文字どおりある(検査が保証する。弾いた数と理由も記録する)。
4. 撤回・CR で済んだ変更・未決・言い換え(T1〜T4・N1〜N5)が、追加・変更・削除として一覧に出ない(未決は「確かめる点」ならよい)。
5. 選んだ違いから作った CR の下書きが、対象・背景(資料と日付)を持ち、そのまま説明済みにできる(規模が数えられる)。

題材がこの仕組みを通る条件(振り返り 18.6 の提案): 束 B-7 が最新(束の後に反映した CR が無い)であること。測る前に、束の鮮度の判定(Phase 113)で確かめる。

## 未確定事項(各 Phase の着手時に決める)

### Phase 112

- 前 → 後の保存の形(時系列の `apply` の行の `refs` か、別の表か)。
- 範囲の外で合意の形に戻した所を出すか(出すなら、戻した要素も前 → 後に入れる)。
- 段階への反映(段階1 の作り直しなど)の前 → 後も、この Phase で扱うか。
- 「今の文と見比べて確かめた」の印の持ち方(CR の列か、時系列の行か)と、反映をやり直すときに印を求め直すか。
- 共有リンクの画面(クライアント)に競合を出すか。
- 既に反映済みの CR(題材の CR-6 など)の前 → 後を後から作るか(版が残っていれば作れる)。
- 112a・112b に分けるか。

### Phase 113

- 資料の本文の上限(文字数・ファイルの大きさ)と、1プロジェクトの資料の数の上限。
- 資料を消したとき、そこから取り出した違い・作った CR の背景をどうするか(CR は残す。違いは消すか)。
- 束の鮮度の判定の結果の形(「最新」「束の後に反映した CR がある〈番号〉」「段階が古かった〈番号〉」)と、どこまで画面に出すか。
- 資料にヒアリングの根拠の役目を持たせないこと(作成時の添付資料とは別)の確かめ。

### Phase 114

- 比べる範囲: 束の写しのうち、要件定義書・外部設計書の行(要件・利用者・画面・API・外部連携)だけか、段階の内容(処理・データ)も入れるか。
- プロンプトに渡す形(束の md か、行の一覧〈キーと文〉か)。行の一覧なら、対象のキーの検査がしやすい。
- 引用の検査の規則(空白・改行・全角半角の揺れをどこまで同じとみなすか)。
- 「確かめる点」(未決・資料どうしの食い違い)の持ち方と、CR にできるか。
- 1つの資料で取り出しをやり直したときの扱い(前の一覧を置き換えるか。CR にした違いは残す)。
- 取り出しのモデル(生成の用途か、用途を足すか)。

### Phase 115

- 利用者・画面・API・外部連携の違いから、CR の対象の要件の行をどう選ぶか(つながる要件を候補に出し、開発者が選ぶ / 自動で入れる)。
- 違いを複数まとめたときの CR の題と内容の組み立て(決定的に組み立てるか、開発者が書くか)。
- 「束が古い」の知らせの出し方(CR の作成の応答の値か、別の API か)と、共有リンクの作成のときの扱い(知らせるだけ。決定5)。
- 「古くて少ない」の結果の形と、説明書の文言(クライアントに見せる文)。

### Phase 116

- 資料の画面の置き場(プロジェクトのメニューに足すか、CR の一覧の中か)。
- 違いの一覧の並び(資料の順か、種類ごとか)と、選んで CR にする操作(チェックボックスで複数)。
- 束を作り直す画面への案内の文。

### Phase 117

- 効果測定の数え方の細部(弾いたものの数え方・対象のキーの当たりの判定)。
- 束 B-7 を作る前に、CR-6 の検証をどこまで進めるか(段階2〜8 の見直しの印)。
- 取り込みの E2E の spec の範囲(資料の追加 → 違いの一覧 → CR の下書き)。
