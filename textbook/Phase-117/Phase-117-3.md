## 10.8節の要点

- **マイグレーションは24本**(ステージ11 の9本 + 12 の5本 + 13 の6本 + 14 の4本)。head は `d5a1c7e3f926`。環境変数・依存は増えない。
- **4本**: `c4e8a1f7b2d6`(CR の競合の確かめの印)・`e7d2b9a4c103`(資料)・`b8f3d6a2e915`(取り出しと違い)・`d5a1c7e3f926`(違いから作った CR)。どれも新しい表か NULL 可の列。
- **大きさの上限**: ファイル 2MB(nginx の `client_max_body_size 10m` の内)・本文 20,000 字・プロジェクトごとに 50 件。どれも API が確かめる。
- **反映の後に変わって見えるもの**: 説明書の規模の節の1行(P115)で、**確認済みの要約がすべて古くなる** → 手順8 で、本番の説明済みの CR の要約の数を SQL で見て、あれば読み直して確認済みに戻す。反映の前 → 後は、`c4e8a1f7b2d6` より前に反映した CR には出ない。競合のガードは説明済み・合意済みの CR の反映に印を求める。束の鮮度の知らせが出ることがある。
- **確認の表**: 入口・資料の追加(貼り付け・txt・pdf・上限)・違いの取り出し・CR の下書き・束が古いときの知らせ・反映の前 → 後・競合のガード。追加の費用は 約 $0.015。
- **ロールバック**: コードはステージ13 の版に戻せる。マイグレーションも戻すなら `alembic downgrade a9c2e4f6b318`(資料・取り出し・違いと競合の印が消える)。反映の前 → 後は時系列の `refs` にあるので行は残る。

## マイグレーションの往復の確認

開発 DB を別のデータベース(`devex_rt`)に `pg_dump` で複製した。backend のコンテナで `DATABASE_URL` だけを複製に向け、`alembic downgrade a9c2e4f6b318` → `upgrade head` を2往復した(行き先を指定。相対の指定はしない)。使い終わったら複製は消した。開発 DB は触っていない(head と資料・違いの数が変わらないことを確かめた)。

| 時点 | head | 既存の表(利用者・プロジェクト・文書の版・段階・束・CR・合意の記録・確認事項・共有リンク) | ステージ14 の表と列 | 資料・取り出し・違い(CR にした)・印のある CR |
|---|---|---|---|---|
| 前 | `d5a1c7e3f926` | 403・295・1416・525・95・50・1066・42・21 | 3表・2列 | 9・9・31(8)・1 |
| downgrade | `a9c2e4f6b318` | 同じ | 0 | ── |
| upgrade | `d5a1c7e3f926` | 同じ | 3表・2列 | 0・0・0(0)・0 |
| 2回目(同じ) | 同じ | 同じ | 同じ | 同じ |

- 4本とも、downgrade・upgrade で `Running …` が出て(各4行)、エラーは無かった。
