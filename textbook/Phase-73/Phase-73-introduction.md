## 着手時の相談で決めたこと

詳細は [`q_a.md`](../q_a.md) の「Phase 73 開始時」を参照する。質問は4回行った。

- 計画モードで2回(5問)。1回目の2問は、理由の説明を求められて聞き直した。
- 計画の承認の後に、73-1 で2回(8問)。

1. **フロー**: ID トークン(Google Identity Services)。今の `/auth/login` と同じ返し方に乗るため。
2. **同じメールの既存アカウント**: 確かめずには紐付けない。Google でログインしたときに、最初の1度だけパスワードで確かめて紐付ける。マイページからの連携も作る。紐付けた後は、両方の方法でログインできる。
   - ユーザーの希望は「既存のプロジェクトを引き継ぎ、紐付けた後はどちらでもログインできる」だった。登録でメールを確かめないため、乗っ取りの準備(pre-hijacking)を防ぐ確かめ方を選んだ。
3. **連携の確かめの API**: ID トークンをもう一度送る(`POST /auth/google/link {credential, password}`。サーバーに状態を持たない)。
4. メールが確認されていない ID トークンは断る。検証は `google-auth` で行う。
5. Google だけのユーザーのマイページには、パスワードの「設定」を出す。
6. UI は `@react-oauth/google`、E2E は `E2E_FAKE_GOOGLE`。手元の OAuth クライアントは、UI の Phase の前にユーザーが作る。
7. **ステージ10の入力5件**はすべて範囲に入れた。開発環境の上限は、開発用の compose で上げる。

**推奨と違った選択は無かった**(13問すべて推奨どおり)。ただし決定2は、1回目の問いでユーザーの希望が出た。それを受けて選択肢を作り直し、2回目で決まった。初めに出した推奨(マイページからの連携だけ)は、希望(ログインの流れの中で引き継ぐ)を満たしきれていなかった(#39 の材料)。

Claude の判断(計画の承認で確定、または診断中)は、[73-1](./Phase-73-1.md)「Claude の判断」にある。

- `sub` で探してからメールで探す。
- Google だけのユーザーのパスワードでのログインは 401 にする。
- Google のログインには新しいカウンタ `google_ip` を使う。
- 設定が無ければボタンを出さない。
- `has_password`・`google_linked` を足す。
- ロールバックの注意。

## Phase 完了チェック(#22)

設問は Phase の要点の要約である(回答は求めない)。

1. Authorization Code でなく ID トークンのフローを選んだのはなぜか。今のログインの返し方(access は本文、refresh は API のオリジンの cookie)と、UI と API のオリジンが違うことから説明できるか。
2. 同じメールのアカウントに、確かめずに紐付けると、何が起きうるか。このアプリが登録でメールを確かめないことから説明できるか。パスワードで確かめると防げるのはなぜか。
3. 本人を `google_sub` で先に探し、メールは後に回すのはなぜか。Google 側のメールが変わったときと、アプリのメールを変えたときで考えられるか。
4. 連携の解除を、パスワードがあるときだけ許すのはなぜか。
5. 開発環境の上限の引き上げを、コードでなく開発用の compose の env で行っても、本番に漏れないのはなぜか。
