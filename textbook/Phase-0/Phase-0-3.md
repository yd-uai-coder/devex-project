## 決定内容の要点

### 背景

ユーザーから、チャット開始前の初期ヒアリング入力の構成案(基本ヒアリング4項目+環境設定4項目をまとめてPOSTし、その後チャットで深掘り)が提示され、よりアクセシブルな構成への改善提案を求められた。重視点: (1)初期入力の段階で明確な設計・構想を求めすぎないこと、(2)要件・設計はAIが判断しユーザーの承認を経てドキュメント化すること。

### devex-ui / devex-api 調査で判明した制約

- `TokenInput`/`TokenField`(追加/削除リストのパターン)は非制御・aria-labelなしで親フォームから値を読めない。
- `InputSuggest`(AI提案に使えそうなコンポーネント)は静的配列のクライアントサイド前方一致フィルタのみで、非同期/AI連携は未実装。
- 「言語選択でフレームワークの選択肢が動的に変わる」コンボボックスはコードベースに前例がなく新規実装が必要(a11yリスクが高い)。
- `aria-invalid`/`aria-describedby`/`role="alert"`/`aria-live`はリポジトリ全体で一件も使われていない。
- devex-apiのチャットは`ChatRequest{conversation_id, message}`という単一文字列入出力のみで、複数フィールドの構造化ヒアリング入力スキーマ・JSON/JSONBカラムは存在しない。

### 決定した設計

初期フォームを「概要(必須・自由記述)」「実現したいこと(必須・自由記述、フォーマット強制なし)」「補足(任意・自由記述、旧サブ機能+その他を統合)」の3項目+折りたたみ式「環境設定(任意)」に簡略化した。機能提案・箇条書き化はフォームからチャット側(AIとの対話)に移す。動的コンボボックスは採用せず、フレームワークは言語ごとに`<fieldset><legend>`で静的グルーピングした`CheckboxGroupWithLabel`流用の静的チェックボックス群にする。`projects`テーブルに`intake`(JSONB, NULL可)カラムを追加し、ペイロードをそのまま保存する。AIが「十分な要件が揃った」と判断した後も即座に生成せず、構造化サマリを提示してユーザーの明示的な承認を得てから生成に進む方針を製品仕様書に明記した。

詳細な設計内容・理由は [`decision-digest.md`](../decision-digest.md) の「Phase 0 ── 初期ヒアリング入力の設計」節を参照。
