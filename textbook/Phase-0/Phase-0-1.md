## 決定内容の要点

### なぜ #1〜17 を変更せず転記したか

appendix原本 0章が「番号は新設順で固定し、参照の一貫性を保つ」ことを明示的に指示しているため。#1〜17 の内容そのものを本プロジェクトの実情に合わせて書き換えると、原本を参照する将来のプロジェクトとの互換性が失われる。プロジェクト固有の調整は既存ルールの書き換えではなく、#18 以降への追加という形で行う。

### なぜ #18〜27 の10個を新設したか

appendix原本 5章(所感)の未解決課題のうち、本プロジェクトが「学習目的の演習」ではなく「納期意識のある実プロジェクト」である点を踏まえ、対応が必要と判断したものを具体的なルールに落とした:

| 新設ルール | 対応する所感 | 決定の理由 |
|---|---|---|
| #18 セッション境界 | 5.5(セッションスタッキングが体感速度低下の主因という実測知見) | 実測で効果が確認されている対策のため、提案止まりにせず確定ルールにした |
| #19 写経レベルタグ | 5.1-④ | #21のモード切替の判定材料として必須 |
| #20 事前質問の範囲限定 | 5.1-③ | 「疑問を出し切ってから実装」という開放的な終了条件を閉じるため |
| #21 モード切替 | 5.1(学習/納期モード案) | ユーザーが「採用する」と明示したため。ただしMVPコアループは常に学習モード固定とし、品質を落とさない範囲に限定 |
| #22 Phase完了チェック | 5.1-⑥ | 実装前チェックリスト(着手前)と対になる着手後の完了判定が無かったため |
| #23 写経順序+実import監査 | 5.6 | 「共有1フォルダ・end状態」モデルの検出限界への対応として、原本が採用推奨するものをそのまま確定ルール化 |
| #24 decision digestの配置 | 5.2 | ユーザー指示により `textbook/decision-digest.md` に分離し、q_a.mdと違い能動的に参照するものと位置づけた |
| #25 再帰検証 | (本プロジェクト固有) | このプロジェクトの二重構造(CLでDevexを作りつつ、Devexの生成物がCL教材の質を検証する)を運用ルールとして明文化しないと、単なる感想で終わってしまうため |
| #26 md相互参照リンク | (本プロジェクト固有) | ユーザー指示。参照先を辿るコストを下げ、ファイル移動・リネーム時のリンク切れ検出を可能にするため |
| #27 Phase 0の役割定義 | (共通ルール候補) | ユーザー指示。Phase 0を「ルール確定+ゴール策定」だけでなく「Phase 1以降の実装ロードマップの具体化」まで含むよう拡張。詳細は[`Phase-0-2.md`](./Phase-0-2.md)参照 |

### プロジェクトゴールを3層にした理由

[README.md](../../README.md)/`docs/`配下のプロダクト要件(1層目)だけでは、appendixが未解決のまま引き継いだ手法上の課題(2層目)や、Devexというシステムの題材としての特殊性(3層目、生成対象そのものがCL開発の成果物と同種)を見落とす。3層とも「満たした/満たしていない」を判定できる形(受け入れ基準・採否記録の有無・テンプレート要素の特定件数)にすることで、Phase完了チェックや振り返りで進捗を確認できるようにした。
