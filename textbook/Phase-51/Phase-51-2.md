## スコープ(構想から)

ロードマップのステージ8は次の4つ。

1. **AI 設計レビュー**: 生成とレビューのモデルを分ける。レビューは設計を書き換えず、「問題・重要度・対象 ID・理由・改善案」を返す。今の自己診断を広げる形で作る。
2. **再ヒアリング**: ヒアリングが原因の不足を、観点の表の「未決」に戻し、チャットで聞き直す。
3. **テスト設計**: 正常系・異常系・境界値・セキュリティ・非機能・結合テスト。日本の実務(単体 / 結合 / 総合テスト、テスト仕様書)の形に合わせる。
4. **品質評価**: 決まった少数の正解例で、生成物とレビューの指摘の正確さを測る。

## 着手前の検討(モデルの構成)

ユーザーは、判定モデルで「ドラフトが要件に合うか」を判断し、要件を満たさない要素について高度な推論が要るかを判定して、レベルに応じてモデルを切り替える構成を提案した。Claude は次の理由で「振り分けを判定モデルに任せない」案を出し、51-1 で比べることにした。

- 判定モデルが「適合」と誤判定した要素は上に上がらず、黙って見落とされる。
- 振り分けが毎回変わると、結果がそろわずテストしにくい([Phase 49](../Phase-49/Phase-49-introduction.md) の判定のゆらぎ)。
- 最初の段は LLM でなくてよい(ID・書き落としは決定的な検証が見る)。

測定の後(Sonnet の結果を見て)、ユーザーは「判定モデル(Jev)を組み込むメリットはあるか」を聞いた。Claude は、振り分け役としては得が無い(入力が小さく、文書をまたぐ検査は結局強いモデルが全文を読む。安いモデルの見落としが振り分けで黙って落ちる)、狭い問い(採用した指摘は直ったか・測定の採点・指摘の検証)なら向く、と答えた。ユーザーは、その使い道は組み込みの段階で改めて検討する、とした。ChatGPT に相談したレビューのフロー(機械的検証 → 判定モデル → 通過しなければレビュワー → 人の承認)にも所感を求められ、Claude は大筋に賛成しつつ「判定モデルが通したらレビュワーを省く」分岐だけは測定と合わないので外し、指摘の形(引用・影響・採否の管理)は取り入れる、と答えた(経緯は [`q_a.md`](../q_a.md))。

### アカウントごとのオン・オフ(ユーザーの指示)

診断の途中で、ユーザーから「アカウントによってレビューのオン・オフを切り替えられるようにしたい」と指示があった。

- `is_superuser = true` のアカウントだけが切り替えられる。初期値はオフ(意図しない Anthropic の課金を防ぐ。推奨どおり)。
- `is_superuser = false` は強制的にオフ。保存値によらず、サーバーで `is_superuser and 設定` を判定する。
- 本番の superuser は、登録したアカウントを手で昇格させる(seed は dev 専用のまま。固定のパスワードを本番に入れない。推奨どおり)。
- 切り替えの本体(設定の保存先・API・画面)は、レビュー機能を作る Phase で作る(推奨どおり)。この章では seed に superuser を足すだけ。

### Claude の判断(計画の承認で確定、または診断中)

- **レビューの LLM は役割で取得関数を分ける**(`get_review_llm()`・`get_judge_llm()`)。偽 LLM に応答を足す。
- **レビューの入力は 51-1 の (d) と同じ**(文書 + 観点の表 + L0 の既知の指摘)。構造化出力は `method="json_schema"`。
- **オン・オフの実効値はサーバーで判定する**。画面の切り替えを信じない。
- **段階式(判定モデルで振り分ける)は原則やめる**。戻すのは、レビューの費用・時間が許せる範囲を超えたとき、または文書が大きくなったときだけ。

## seed の superuser

```python
# backend/scripts/seed.py(抜粋)
SEED_SUPERUSER = {
    "full_name": "sample-super-user",
    "email": "example-super-user@example.com",
    "password": "Sample-super-user-0123",
}

async def seed_users(session: AsyncSession) -> None:
    """一般ユーザーと superuser を作る(email 一致で冪等判定。既存ユーザーの権限は変えない)。"""
    service = UserService(session)
    for data, is_superuser in ((SEED_USER, False), (SEED_SUPERUSER, True)):
        try:
            user = await service.create_user(email=..., password=..., full_name=...)
        except UserAlreadyExistsError:
            continue
        if is_superuser:
            # 登録の経路(create_user)からは superuser を作れないため、作成後に昇格させる
            user.is_superuser = True
            await session.commit()
```

- `UserService.create_user` の署名は変えない。登録の API から superuser を作れる道を増やさないため。
- `_seed_user`(一般ユーザー1人)を公開の `seed_users` に改めた(テストから呼ぶため。`seed_prompt_templates` と同じ形)。
- 既に居るユーザーはスキップするだけで、権限は変えない(既存の一般ユーザーを昇格させない)。
