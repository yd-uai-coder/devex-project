## 着手時の相談で決めたこと

詳細は [`q_a.md`](../q_a.md) の「Phase 61 開始時」を参照。計画モードで質問を2回(8問)、計画の承認の後、61-1 で質問を2回(8問)行った。

1. **要件定義の Phase を置く**(3章。ベースラインと見本は省く)。**自動実装モード**: on。
2. **生成中のプロジェクトの削除**: 推奨(409 で断る)と違い、**削除を許す**。バックグラウンドの処理を消失に強くする。
3. **既定のキーでのレビュー**は superuser だけ・**PDF の取り込み**は Gemini に固定・**メニューの認証の項目**はログインの状態で出し分け・**モデルのカタログ**は公式の一覧で確かめる(すべて推奨どおり)。
4. **Phase 60 の申し送り**: 推奨(入れずに持ち越す)と違い、1件ずつ決めることにし、**11件すべてをステージ9 に入れた**。
5. **ユーザーネーム**: 推奨(`full_name` を表示名として変える)と違い、**列を `user_name` に改名する**(既存のデータを失わない)。
6. メールの変更(今のパスワードで即時)・キーの確かめ(保存のときに確かめる)・暗号の鍵が無いとき(キーの登録だけ使えない)・カタログの中身(8モデル)・並べ方(使い勝手 → アカウント → 質)は推奨どおり。

推奨と違った選択は3つ(削除を許す・申し送りを1件ずつ決めてすべて入れる・列の改名)。どれも範囲を広げる向き(#39 の材料)。

Claude の判断(計画の承認で確定、または診断中)は [61-1](./Phase-61-1.md)「Claude の判断」にある(改名の方法・消失への強さ・PDF の解決・キーの確かめ方・既定のキーでのレビューは provider によらない)。

## Phase 完了チェック(#22)

設問は Phase の要点の要約(回答は求めない)。

1. UI の proxy からログインの状態が見えないのはなぜか。refresh cookie の置き場(API のオリジン・`path`)とアクセストークンの置き場(メモリ)から説明できるか。印の cookie を認証の判定に使わないのはなぜか。
2. 生成中の削除を許すと、どの処理が何に困るか。外部キーの CASCADE で消えた行に、バックグラウンドの処理が書き込もうとしたときに起きることから説明できるか。
3. 用途ごとに provider を入れ替えられると、なぜ今の取得関数の `lru_cache` のままでは足りないのか。キャッシュの鍵と、provider に固有の処理(構造化出力・本文の取り出し)の2つから説明できるか。
4. 既定のキーでのレビューを superuser に限り、自分のキーなら一般ユーザーにも開くのはなぜか。費用を誰が持つかから説明できるか。
5. モデルのカタログから preview・2.5 系・自動で回されるモデルを外したのはなぜか。「選んだモデルで動く」ことを保てるかから説明できるか。
