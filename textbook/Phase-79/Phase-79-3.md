- **生成元に2つの URL**(着手時の相談でユーザーが決定。推奨は Vercel の URL だけ): カスタムドメインで開いた利用者も Google でログインできるようにする。`CORS_ORIGINS` にも同じ2つが要るので、4 で確かめる段を置いた。

## マイグレーションの往復の確認

開発環境の DB を別のデータベース(`devex_roundtrip79`)に `pg_dump` で複製し、`alembic downgrade 7c3e9ab5f4d6` → `upgrade head` を流した(使い終わったら消した)。先にリビジョン ID の重複が無いことと head が1つ(`c4f8a2e6d1b9`)であることを確かめ、downgrade は行き先のリビジョンを指定した。dev の DB は `c4f8a2e6d1b9` のまま触っていない。複製には、E2E と手動確認で作った Google だけの利用者(パスワードが null)がそのまま入っていた。

| 時点 | head | 利用者 | うちパスワードが null | Google と連携済み | プロジェクト |
| --- | --- | --- | --- | --- | --- |
| 複製の直後 | `c4f8a2e6d1b9` | 155 | 13 | 25 | 137 |
| null の行があるまま downgrade(失敗) | `c4f8a2e6d1b9` | 155 | 13 | 25 | 137 |
| null の13件を消した後 | `c4f8a2e6d1b9` | 142 | 0 | 12 | 137 |
| downgrade の後(6本) | `7c3e9ab5f4d6` | 142 | (null 不可) | (列が無い) | 137 |
| upgrade の後(6本) | `c4f8a2e6d1b9` | 142 | 0 | 0 | 137 |

2往復とも同じ。

- **null の行があると downgrade は失敗する**: `c4f8a2e6d1b9` の `ALTER COLUMN hashed_password SET NOT NULL` で `NotNullViolationError`。マイグレーションはトランザクションの中で流れるので、失敗した後も head と行は元のまま(ステージ9の5本も戻らない)。
- **連携は戻らない**: `google_sub` の列が消えるので、upgrade の後は 0 件。パスワードのある利用者は、次に Google でログインするとき連携の確かめからやり直す。
- 消した13件はプロジェクトを持っていなかった(E2E の利用者)ので、プロジェクトの数は変わらなかった。`users` を消すと、`projects`・`conversations`・用途ごとのモデル・API キーも消える(外部キーが `ON DELETE CASCADE`)。

## 設計判断

### ステージ10だけを戻すときは、コードだけを戻す

downgrade は、Google だけの利用者がいると止まり、通っても全員の連携を消す。一方、`c4f8a2e6d1b9` は列を足して NOT NULL を外すだけなので、ステージ9のコード(`fba3502`)は新しいスキーマのまま動く(`google_sub` を読まない。`hashed_password` は読むだけ)。困るのは、Google だけの利用者がパスワードでログインしようとしたときで、ステージ9のコードは `verify_password(password, None)` が `TypeError` になり 500 を返す(`verify_password` に `None` を渡すと `TypeError` になることを、dev の backend のコンテナで確かめた)。その利用者はどのみちログインできないので、ロールバックの手順では「コードだけを戻す」を先に置き、downgrade は null の行と連携が消えることを確かめてから行う形にした。

### 往復の題材に null の行を残した

Phase 72 の往復は「削除の印を1件付けて」から流した。今回は、dev の DB に Google だけの利用者が既に13件あったので、作らずにそのまま流し、失敗する経路を先に確かめた。ロールバックの手順の確かめの SQL(null の数・削除の印の数)は、この失敗を手順の中で先に見つけるためのもの。
