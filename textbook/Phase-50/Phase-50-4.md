## 10.4節の要点

- **順序**: API を先に、UI を後に(10節と同じ)。新しい環境変数・依存は無い(ステージ6の版 `ab65cea` からの `config.py`・`pyproject.toml`・`uv.lock`・compose・CI・nginx・Dockerfile の差が無いことを確かめた)。
- **マイグレーション2本**: `d4e5f6a7b8c0`(段階7のタスクに単位のキー、段階8の手順書に `unit_key`。データだけ)・`e5f6a7b8c9d1`(`approved_model`・`impact` の列。承認済みで変わっていない行にだけ写し)。
- **既存のデータ**: 印は空で始まる。簡易モードの model の無い文書は、再生成した最初の1回は印が付かず差分の再生成も効かない。簡易モードの以前の手順書は単位のキーで引けない。ヒアリング済みのプロジェクトには新しい観点が未決で出る。既存の DFD・CRUD・手順は直さない。
- **ブランチ**: devex-api のステージ7のコミットは、手元の `stage7` ブランチ(`stage6` の上)にある。push して `stage7`→`main` の PR にする。devex-ui は `main` が origin より進んでいるので、API の反映の後に push する。
- **確認**: 更新の前に段階ごと・状態ごとの件数と「承認済みで変わっていない」行の数を控え、更新の後に写しの数がそれと同じで、印が 0 であることを確かめる。
- **本番での確認の表**: Phase 44(詳細設計モードのパネルの操作感)・46(簡易モード)・47(ヒアリングの側面と発言の数・ログのカードのおすすめ)・48(段階3の補ったセル・段階5の分岐の欄)の画面確認と、49 の直し(差分の再生成で印が増えない)、[50-2](./Phase-50-2.md) で気づいたパネルの絞り込みの見え方を、対象ごとにまとめた。
- **ロールバック**: `alembic downgrade c3d4e5f6a7b9`。印・確認済みの記録・写しが消え、単位のキーが外れる。

## マイグレーションの往復の確認

開発環境の DB を別のデータベース(`devex_roundtrip`)に `pg_dump` で複製し、downgrade → upgrade → downgrade → upgrade を流した(使い終わったら消した)。

| 時点 | head | 段階の行 | 段階7のキーあり | 段階8の `unit_key` あり | 写し | 印 |
| --- | --- | --- | --- | --- | --- | --- |
| 複製の直後 | `e5f6a7b8c9d1` | 175 | 21 / 21 | 21 / 27 | 154 | 45 |
| downgrade の後 | `c3d4e5f6a7b9` | 175 | 0 | 0 | (列なし) | (列なし) |
| upgrade の後 | `e5f6a7b8c9d1` | 175 | 21 | 16 | 153 | 0 |

2往復とも同じ。

- **写し 154 → 153**: 写しは承認のたびに撮り、承認の後に編集しても残る(Phase 43)。移行は「承認済みで変わっていない行」にだけ撮るので、承認の後に編集した1行は戻らない。設計どおり。
- **印 45 → 0**: 移行は印を作らない(更新より前の変更の影響は求めない)。
- **段階8の `unit_key` 21 → 16**: 戻らなかった5行は、すべて簡易モードのプロジェクトの手順書だった。この移行は簡易モードを変えない(Phase 42 の時点では、簡易モードは単位の ID をキーにしていた)。Phase 45 以降の簡易モードは実装計画書の単位のキー(`U-001`…)で引くので、往復した後のこの5行は「以前の手順書」(10.4節の注記)と同じく印が付かない。詳細設計モードの16行はすべて戻った。本番は初めての upgrade なので関係しないが、ロールバックしてから再び更新した場合の注記として 10.4節に書いた。

## 設計判断

### 写しの件数で移行を確かめる

マイグレーションの結果が正しいかは、「承認済みで変わっていない行の数 = 写しの数」で確かめられる。更新の前にこの数を SQL で控え(`version = approved_version`)、更新の後に `COUNT(approved_model)` と比べる手順にした(10.2 の「段階7の承認の件数を控える」と同じ考え方)。
