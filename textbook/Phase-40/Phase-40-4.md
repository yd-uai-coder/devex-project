## 10.3節の要点

- **順序**: API を先に、UI を後に(10節と同じ)。新しい環境変数・依存は無い(ステージ5の版からの `config.py`・`pyproject.toml`・`uv.lock`・compose・CI の差が無いことを確かめた)。
- **マイグレーション3本**: `a1b2c3d4e5f7`(`hearing_points`・`projects.hearing_scale`)・`b2c3d4e5f6a8`(`chat_histories.cards`)・`c3d4e5f6a7b9`(`generated_documents.model`)。どれもテーブル・列を足すだけで、既存の行は書き換えない。
- **既存のデータ**: 観点の表の行・カード・文書の model を持たない。チャットは次の発言から観点の表で判定し、文書は再生成で要件ID・出どころ・追跡が使える。同じ時刻の会話の順と、以前の実装計画書の見出しの重なりは直さない(再生成で直る)。
- **ブランチ**: devex-api のステージ6のコミットは、手元の `stage5` ブランチの上に積んである(origin には未 push)。`stage6` ブランチを作って push し、`stage6`→`main` の PR にする。devex-ui は `main` が origin より進んでいるので、API の反映の後に push する。
- **本番での確認の表**: Phase 34〜39 の画面確認(Phase 39 の「未消化の申し送り」)と、この Phase の直し([40-1](./Phase-40-1.md))の確かめ方を、対象ごと(ヒアリングの既存・新規、要件定義書、外部設計書、詳細設計モード、簡易モード)にまとめた。
- **ロールバック**: `alembic downgrade c9d0e1f2a3b4`。観点の表・規模・カード・文書の model がすべて消える(会話の本文と md は残り、カードの回答は発言の本文の「【観点】選択肢」として残る)。

## マイグレーションの往復の確認

開発環境の DB を別のデータベース(`devex_roundtrip`)に複製し、downgrade → upgrade → downgrade → upgrade を流した(使い終わったら消した)。

## 設計判断

### ヒアリング中のプロジェクトの数を控える

マイグレーションは既存のデータを移さないので、ヒアリング中(`interviewing`)のプロジェクトは観点の表が空の状態から始まる。利用者への影響の範囲が分かるよう、更新前に件数を控える手順にした(10.2 の「段階7の承認の件数を控える」と同じ考え方)。

### 既存のデータを移さない

Phase 33 の決定(既存はそのまま、移行なし)のとおり。会話から観点の表を作り直すには判定の LLM を全プロジェクトに流す必要があり、文書の model も再生成しないと作れない。どちらも利用者が次に触ったときに作られるので、移行の処理は作らない。
