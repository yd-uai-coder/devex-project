## 調べて分かったこと(今の陳腐化の仕組み)

- 陳腐化は**段階単位・版数の比較**だけで決まる。`app/detailed_design/stages.py` の `STAGE_INPUTS`(段階ごとの入力の段階と文書)・`current_inputs`(入力の版の指紋)・`derive_states`(段階の順に状態を決める)。承認時の指紋と今の指紋が違えば「古い」。前の段階が承認済みでなくなると、後ろの段階へ連鎖する。
- 詳細設計モードの文書の再生成は、要件定義書と外部設計書を一度に作り直す。段階1は外部設計書を、段階8は全段階を入力にするので、**文書を1か所でも変えると全段階が「古い」になる**。
- 段階を編集すると、承認し直すまで後ろの段階は開かない(入力の承認済みの版が無い)。承認し直すと、後ろの段階はすべて「古い」になる。
- 段階は版の履歴を持たない(今の `model` だけ)。何が変わったかの差分は取れない。
- 「採用にする」(`GeneratedDocumentRepository.replace_model`)は版を上げないので、陳腐化を起こさない。

## 測り方

材料は [`appendix/stage6-effect/`](../../appendix/stage6-effect/README.md) の1回目の生成物(詳細設計モードの段階1〜8 の JSON・要件定義書・外部設計書、簡易モードの段階8と実装計画書)。中身は書き換えない。

- **要素と辺**: 要件・画面・API・処理・段階2〜8 の行を節にし、JSON と文書の表にある ID だけから「A が B を参照する」辺を作る(本文の文字列からは作らない)。一覧は [README](../../appendix/stage7-baseline/README.md)「4つの方式」。
- **4つの方式**:
  1. 今の仕組み: 本体の `derive_states` をそのまま呼び、「古い」になった段階のすべての要素
  2. グラフ(直接): 辺を逆に1段
  3. グラフ(全部): 辺を逆にたどれるところまで
  4. 処理を軸(試案): 変更が届く処理(F-xx)に属する要素と、直接の依存元。共有されるモジュールからは広げない。2・3 の結果を見てから足した案
- **正解**: 変更の中身を読んで、Claude が「内容を直すか、直さなくてよいことを人が確かめる必要がある」要素を選んだ(理由つき)。人の判断なので、数字は概算として読む。
- **シナリオ**: S1〜S8(要件・非機能要件・「採用にする」・API・処理・テーブル・モジュールの改名・簡易モードの WBS)と、試案と 41-2 の決定の後・実装の前に決めた N1〜N4(holdout)。

## 結果

| 方式 | S1〜S8(正解 39)示した / 当たり / 過剰の割合 / 見落とし | N1〜N4(正解 17) |
|---|---|---|
| 今の仕組み | 292 / 37 / 87% / 2 | 158 / 14 / 91% / 3 |
| グラフ(直接) | 26 / 18 / 31% / 21 | 7 / 5 / 29% / 12 |
| グラフ(全部) | 111 / 32 / 71% / 7 | 62 / 16 / 74% / 1 |
| 処理を軸(試案) | 51 / 29 / 43% / 10 | 25 / 14 / 44% / 3 |

所見:

1. **今の仕組みは、示すものが多すぎて役に立たない**。見落としは少ないが、示した要素の9割近くは見直し不要。どの要素を見ればよいかは分からない。
2. **今の仕組みが見落とすのは2種類**: 文書の中の要素(画面。文書は丸ごと作り直すので要素の単位が無い)と、**同じ段階の中の依存**(S7。段階4の中のモジュールの依存は段階単位では見えない)。
3. **ID のグラフは、直接だけでは狭すぎ、全部たどると広すぎる**。要件から手順・処理ロジック・手順書までは2段以上ある。一方、共有のモジュール(`clients/ai.py`)と `depends_on` の連鎖を通ると、別の処理の要素まで広がる。
4. **処理を軸にすると中間に来る**。後から決めたシナリオでも傾向は同じで、合わせ込みではない。残る見落としは、共有のモジュールの中で「どれを直すか」の判断(再試行を置く層・入口の検証・リポジトリ)と、簡易モード(処理の軸が無い)。
5. **辺が無いところは、どの方式でも届かない**: 非機能要件から下流(S2。横断事項は要件ID を持たない)。モジュールとテーブルの辺も無いが、段階5の手順の行(呼び出し先と DB 欄が同じ行)から導ける。
6. **「採用にする」は何も示さなくて正しい**(S3)。手順書の非機能要件の表は出力のときに model から作るので、出どころは自動で変わる。
7. **位置で決まる ID**: 手順の行(30)と L-NN(4)は出力のときに振るだけで保存しない。作業単位の ID(M-xx-Tyy)は**段階8の JSON が単位の手順書のキーとして持つ**ので、段階7で並べ替えると段階8の手順書が別の単位に付く。

これらを [41-2](./Phase-41-2.md) の診断の材料にした。
