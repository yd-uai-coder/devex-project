- **下書きの形**(着手時の相談で決定): ステージ11〜15 を1回で出すので、節の頭に「今はステージ11 の分だけ」と書き、「増えるもの」「本番での確認」「ロールバック」を後のステージが足す形にした。ステージ9・10 の 10.7節と同じく、ステージごとに表を分ける。
- **本番の head の見込み**: devex-api の `main`(`cd5b1a9`)は 2026-10-19 に push 済みで、汎用チャットの表を落とす `d7e2a9c4f1b3` を含む。自動デプロイが通っていれば、本番の head はそれ。通っていなければ `c4f8a2e6d1b9` で、`d7e2a9c4f1b3` も一緒に流れる(10本)。2 で分岐する。
- **新しい環境変数は無い**: 説明書の要約は、文書の生成と同じ用途「生成」のモデルを使う。ただし、`gemini-3.1-flash-lite` をカタログから外した(Phase 88)ので、本番の `.env` のモデル名がそれなら直してから出す。利用者の設定は `be106e6426be` が移す。
- **ロールバックの第一の手はコードだけ戻す**: ステージ11 の列はどれも NULL 可か既定値つきで、ステージ10 のコードは新しい表を読まない。ステージ10 のカタログにも `gemini-3.5-flash-lite` があるので、移した設定もそのまま動く。downgrade は、合意済みの版・CR・時系列・要約の行と、版のモデル名・CR の列を消し、もう一度更新しても戻らない。

## マイグレーションの往復の確認

開発環境の DB を別のデータベース(`devex_rt`)に `pg_dump` で複製し、`alembic downgrade d7e2a9c4f1b3` → `upgrade head` を2往復した(使い終わったら消した)。開発 DB は `be106e6426be` のまま触っていない。backend のコンテナの中で、`DATABASE_URL` のデータベース名だけを複製に置き換えて流した。行き先のリビジョンは明示した(相対の指定はしない)。

| 時点 | head | 既存の表(利用者・プロジェクト・文書の版・段階・モデルの設定) | ステージ11 の表 |
|---|---|---|---|
| 前 | `be106e6426be` | 181・153・740・364・13 | 6表(束 12・写し 132・CR 8・時系列 40)。モデル名つきの版 79・CR つきの版 12 |
| 1回目の downgrade | `d7e2a9c4f1b3` | 同じ | 0表 |
| 1回目の upgrade | `be106e6426be` | 同じ | 6表・行は 0。モデル名つき・CR つきの版も 0 |
| 2回目(同じ) | 同じ | 同じ | 同じ |

- 9本とも、downgrade・upgrade で `Running …` が出て、エラーは無かった。
- `be106e6426be` の downgrade は何もしない(モデルの設定は `claude-haiku-5-5`・`gemini-3.8-flash` のまま)。
- 複製には、E2E と手動確認で作った束と CR が入っていたので、downgrade が行のある表を落とせることも確かめられた。
