## 実 LLM での一巡の記録

ユーザーが開発環境で行った一巡を、Claude が開発 DB とサービスの読み出し(説明書・比較・検証)から読んで書いた(2026-10-20)。

| 確かめ | 結果 |
|---|---|
| 使ったプロジェクト・CR | 詳細設計モードの「トレンド追跡アプリ」(段階1〜8 承認済み)。B-1・B-2(10-19)、B-3(10-20。CR-2 の反映の後で、段階は「古い」の状態で入った)。CR-1(新しい要件を足す・収集の間隔 6時間 → 8時間)→ 説明済み → **却下**(理由「無理」)→ **CR-2 に写す** → 説明済み → 合意 → 文書へ反映。CR-3(B-3 基準・FR-001 の内容の変更・8時間 → 12時間)→ 説明済み → 要約 → 合意 → 文書へ反映 |
| 予測の件数(置き場ごと) | CR-2: 0件(対象の要件が無く、「新しい要件を足す分は予測に入らない」の印)。CR-3: 0件。FR-001(定期バッチ)は、外部設計書の画面・API(「— —」)にも段階1〜8 の写しにも現れないので、どこにも届かない(正しい0件) |
| 反映で作り直した版・モデル名・時間 | CR-2: 要件定義書・外部設計書の v3(`gemini-3.5-flash-lite`)。CR-3: v5(同じモデル)。CR-3 は要約の確認(01:24:03)の後に押し、版は 01:24:26 にできた(押してから約20秒以内)。v5 の FR-001 は「12時間ごとに…」に変わり、外部設計書の外部連携の行も「12時間ごとの定期バッチ処理」になった |
| 比較(一致 / 予測だけ / 実際だけ) | CR-2・CR-3 とも 0 / 0 / 0(反映の印 0件。予測と同じ) |
| 要約の照合(5節に無い ID・数字) | CR-3 の要約1件。不一致 0件(ID は FR-001、数字は 8・12・10・0 で、どれも5節にある)。直さずに確認した |
| 要約の読みやすさ(人の所感) | 問題なし(ユーザー)。要約は「8時間から12時間へ変更」「対象は FR-001」「見直しが要る要素は予測されず、作業単位とテストは0件」「コア機能の観点が未決」を、依頼の文の調子でまとめた |
| 検証済みまでに確かめた印・文書の側の数 | 検証済みにはしていない(CR-2・CR-3 は反映済みのまま)。確かめる印 0件・文書の側の確認 0件なので、すぐ検証済みにできる状態 |
| 費用(トークン) | トークンの記録は無い(文書の生成はトークンを残さない)。見積もりの単価で、文書の再生成4回(CR を渡した2回 + 渡さない2回)と要約1回で、約 $0.04 |

**一巡で見つかったこと**:
- **CR-2 の反映で作った v3 が消えていた**: CR-2 の後に、CR を渡さない再生成を2回(v4・v6)したため、版の巡回(直近3件)で v3 が消えた。たどる記録の「要件定義書 v3・外部設計書 v3 を作り直した」の先が無い。→ Phase 完了後の調整で、CR で反映した版を巡回から外した(すでに消えた v3 は戻らない)。
- **CR を渡さない再生成で、関係の無い印が付いた**: CR-3 の後の v6(CR なし)で、FR-005 の文は同じまま、出どころが「採用」から「推測」に変わった。この差分で、段階1・5・8 に FR-005 から届く印が3件付いた(出どころ `doc:requirements`。CR には結ばれない)。LLM の再生成の揺れが、合意した行を動かす例である。→ ステージ12(合意済みの行の保護)へ送る。
