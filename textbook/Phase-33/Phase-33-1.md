## やり方

- **ペルソナ**: ゴール3と同じ題材(Devex 自身)。ゴール3の発言を「最初から話してよい事実」とし、それとは別に「聞かれたら答える潜在の事実」を14個(L1〜L14。可用性・性能・アクセス制御・ログ・不正利用・例外の場面・監視・環境・移行・入力・将来の拡張・1日の流れ・削除)用意した。出どころは Devex の実際の文書(`docs/*.md`・`OPERATIONS.md`)で、無いものは「シナリオ」と明記した。
- **答え方**: 聞かれたことにだけ答える。ペルソナに無いことは「決めていません」。判定が「十分」になったら生成する。ゴール3は用意した発言を順に送ったので、AI の質問と答えがずれた。今回は1回ずつ質問を読んで答えたので、改良の後に「聞かれたかどうか」の差がそのまま結果に出る。
- **段階の操作**: 人が選ぶところ(DFD のグループ・手順を書く処理・詳細を書く関数)は、決まった規則で選んだ([README](../../appendix/measurements/stage6-baseline.md)「人の操作」)。段階3の検証のエラーだけは、画面で人がする最小の修正で直した。

## 結果 1: ヒアリング

| | 詳細設計モード | 簡易モード |
|---|---|---|
| 利用者の発言 | 3回で「十分」 | 3回で「十分」 |
| AI が聞いたこと | 生成のタイミング、プレビューの形式、再生成を MVP に含めるか | 生成へ移るタイミング、部分修正と認証、質問の往復の回数と API のエラー |
| 聞かれなかった「最初から話してよい事実」 | 認証(JWT)、技術スタック、LLM、参考資料の扱い、想定ユーザー、非機能(SSE・アクセシビリティ)、対象外、体制と期間 | 技術スタック、生成の順(逐次)、参考資料の扱い、非機能、対象外、体制と期間 |
| 聞かれた潜在の事実(L1〜L14) | 0 | 1(L7 例外の場面) |

- **5条件の判定が甘い**: 詳細設計モードの2回目の判定は「(3) 想定ユーザー (4) MVP スコープ (5) 技術的な制約が未達」と書いた。ところが次の発言(再生成の要否に答えただけ)で「十分」になり、サマリには「想定ユーザーはシステム開発の初期フェーズを担当するユーザー」と、利用者が言っていない内容が入った。
- **AI の質問は画面の作りに寄る**: 生成のタイミング・プレビューの形式・往復の回数のように、Devex 自身の UI の作りを聞いた。非機能・セキュリティ・例外の場面は、簡易モードで1回(API のエラー)だけだった。

## 結果 2: 未定義の分類

原因を4つに分けた。

- **A. ヒアリング漏れ**: 利用者に聞けば答えられた(ペルソナにある)のに、聞かなかったために設計で埋まらなかった、または AI が創作した。
- **B. 上流文書の書き落とし**: 利用者は言った、または入力から決まるのに、要件定義〜内部設計の文書に書かれなかった。
- **C. 設計段階の不足**: 設計の側で決めること(シグネチャ・クエリ・テーブルの列・CRUD)。ヒアリングでは防げない。
- **D. 生成の誤り**: 指摘そのものが誤り。

### 詳細設計モード(36件)

| 分類 | 件数 | 例 |
|---|---|---|
| A | 4 | JWT の有効期限が「(要決定)」(M-01-T01・T03。ペルソナの JWT 30分/14日を聞いていない)/ LLM のモデルとプロンプトが無い(M-02-T05。段階7の技術スタックは「OpenAI API 等」になった)/ Celery のキューの名前と引数(M-03-T01。キューの技術は要件定義書 1.6 で AI が「Redis / Celery / BullMQ 等」と書いたもの) |
| C | 32 | 段階6の詳細が無い関数(31件。規則で5関数だけ選んだため)/ CRUD に F-10 の操作が無い(検証 `NOT_IN_CRUD`) |
| B・D | 0 | |

### 簡易モード(14件)

| 分類 | 件数 | 例 |
|---|---|---|
| A | 1 | アップロードしたファイルの保存先(M-02-T02。ペルソナは「元ファイルは保存しない」) |
| B | 13 | API のメソッド・パス・本文が外部設計書に無い(5件)/ 許可する形式の一覧が無い(goals に txt/md/pdf とある)/ 処理(DF)の無い機能の単位(検証 `FEATURE_WITHOUT_DATAFLOW` 5件)/ 内部設計のデータ構造・出力スキーマが無い |
| C・D | 0 | |

### 件数に表れないもの(ここが大きい)

実装可能性チェックは、設計の**内側の一貫性**を見る。聞かずに AI が埋めた事実は、設計の中で一貫していれば、未定義として出ない。

| 誤り | モード | ペルソナの事実 |
|---|---|---|
| 技術スタックが NestJS・TypeScript・Prisma になった | 簡易 | FastAPI(Python)・LangChain |
| キューに Celery、LLM に「OpenAI API 等」 | 詳細 | ペルソナの技術スタックに Celery は無い(Redis はレート制限とトークン失効)。LLM は Gemini Flash-Lite |
| 4文書の「並行生成」(M-04-T01) | 簡易 | 逐次(前の文書を入力にする) |
| 想定ユーザー・対象外・テンプレート選択が要件定義書に入った | 詳細 | 聞かれていない。内容はペルソナと大きくは違わないが、AI の推測であることが文書から分からない |

要件定義書の 1.5(非機能)・1.6(制約)の記述のうち、利用者が言っていないものは、詳細設計モードで 7/11、簡易モードで 6/11 だった(HTTPS・データの分離・バックアップが容易な構成・3秒以内の応答など)。中身はもっともらしいが、利用者が決めたのか AI が補ったのかは、文書からは分からない。

生成後の自己診断も、このうち2つを指摘した(詳細設計モード: PDF のテキスト化の方式・LLM の選定。どちらもペルソナにある)。自己診断は、聞き漏れを**生成の後に**見つけている。

## 所見(33-2 の診断の入力)

1. **未定義の件数だけでは、ヒアリングの効果を測れない。** A に入るのは詳細で4件・簡易で1件だけだった。大きな誤り(技術スタックの創作)は未定義にならない。効果測定には、①未定義の分類 A の件数に加えて、②ペルソナの事実(最初から話してよい事実と潜在の事実)のうち聞かれたものの数、③要件の記述の出どころ(利用者 / AI の推測)の割合を使う。②と③は、観点の表と出どころの記録(ステージ6の本体)がそのまま測る道具になる。
2. **完了判定の5条件は、条件の文言を LLM に解釈させるので甘くなる。** 「十分」と判定した理由が、利用者の発言に結びついていない。観点ごとに状態(ユーザーが決定 / AI の提案を採用 / 未決 / 対象外)と根拠(どの発言か)を持たせれば、「聞いていない観点」が表に残る。
3. **技術スタックは、簡易モードでも必ず聞く観点にする。** 環境設定(初期入力の折りたたみ)が未入力のときだけ5条件目で確かめる今の作りでは、詳細設計モードでも簡易モードでも聞かれなかった。
4. **非機能・セキュリティは、聞かれなければ AI が埋める。** 埋めた内容は一般論としてもっともらしいので、利用者は気づきにくい。出どころを文書に出すことと、場面で問うこと(「止まったら何時間まで困らないか」)の両方が要る。
5. **簡易モードの未定義は B(上流文書の書き落とし)が中心で、詳細設計モードは C(設計段階)が中心。** ステージ6で減らせるのは A と、B のうち要件定義書に関わるもの。B の外部設計・内部設計の書き落としは、ステージ6の範囲(上流の構造化)をどこまで広げるかで扱いが変わる(33-2 の論点)。
6. **段階6を一部の関数だけにする運用では、C が大量に出る。** 「重要な部分だけ書く」原則(ステージ4)どおりの結果で、ステージ6の課題ではない。ただし、手順書の最重要の大半がこれで埋まるので、効果測定では C を除いて数える。
