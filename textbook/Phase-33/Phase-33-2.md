## 調べて分かったこと(診断の材料)

- **完了判定**(`devex-api/backend/app/services/chat_service.py`): 5条件(目的・コア機能・想定ユーザー・MVP スコープ・技術的な制約)を LLM が判定し、`projects.hearing_check`(JSON: `is_sufficient`・`summary`・`missing_points`)に保存する。5条件目は環境設定が未入力のときだけ必須。非機能・セキュリティの観点は無い。ベースラインでは、判定が「未達」と書いた条件を聞かないまま「十分」になった。
- **要件定義書**(`doc_generator_service.py` の `_DOC_TYPE_PROMPTS["requirements"]`): 見出しを決めた Markdown。要件ID も出どころも無い。外部設計書も同じく Markdown(2.6 の API 一覧の書き方だけは決めている)。
- **後続の入力**: 詳細設計モードの段階2・4・7・8が要件定義書(md)を、段階7が外部設計書(md)を入力にする(`app/detailed_design/stages.py` の `STAGE_INPUTS`)。簡易モードの段階8は4文書を入力にする。段階1の機能(F-xx)と要件の間に ID のつながりは無い。

## 診断と決定

### (1) 最重要 ── 次の Phase のタスクに直結するもの

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | 観点の表の持ち方と完了判定 | **新しいテーブル(`hearing_points`、観点ごとの行)で持ち、完了は決定的に判定する**。状態は「ユーザーが決定 / AI の提案を採用 / 未決 / 対象外」の4つ。行に根拠(どの発言か)を持つ。LLM は発言から観点ごとの状態と根拠を返すだけにし、「十分」は「必須の観点がすべて未決以外」をコードが決める。5条件はこの表で置き換える | 5条件を LLM に解釈させると、聞いていない条件も「十分」になる(33-1 所見2)。表に残せば、聞いていない観点が見える。テーブルにするのは、ステージ7(変更管理)で観点の単位の変更を追うとき、行の単位で持っている方が扱いやすいため(ユーザーの選択。推奨は `hearing_check` の JSON を広げる案だった) |
| 2 | 要件定義書の構造化 | **要件定義書と外部設計書の両方を意味モデルで持つ**。ステージ4と同じく「構造化出力 → Pydantic の model → md を組み立てる」。要件定義書は要件を行にし、要件ID と出どころ(ユーザーが決定 / AI の提案を採用 / AI の推測)と、根拠の観点を持つ。後続(段階・自己診断・簡易モードの文書)は、組み立てた md を今と同じく読む | ロードマップどおり上流を構造化する。外部設計書もモデルにすれば、簡易モードで多かった「外部設計書の書き落とし」(33-1 の B)を検証で拾える(ユーザーの選択。推奨は要件定義書だけの案だった) |
| 3 | 観点の一覧 | **機能面の観点 + IPA の非機能要求グレードの6大項目**。最初に規模(個人・小規模 / 社内 / 公開サービス)を聞き、どの観点が必須かを決まった表で切り替える。技術スタックは規模によらず必須 | 実務の基準(IPA)に合わせる。LLM に選ばせると、今回のように聞かないままになる(33-1 所見3・4)。必須でも「対象外」を選べば済むので、必須を広めに取れる |
| 4 | 要件 → 処理の結び | **詳細設計モードの段階1の機能の行に要件ID の列(`req_ids`)を足す**。下書きで AI が付け、検証で「処理の無い Must の機能要件」「要件の無い処理」を警告にする | 要件 → 処理 → 作業単位の追跡がつながる。別の対応表を持つと二重管理になる |

- 決定1の補足: 観点の定義(キー・名前・問いの例・規模ごとの必須)はコードに持つ(テンプレートや DB には持たない)。形の見本は [33-3](./Phase-33-3.md) の 観点の表。
- 決定2の補足: 外部設計書の構造の深さは、下の(3)の決定のとおり「一覧を行に、説明は文字列」。

### (2) 中程度 ── 後続 Phase の設計事項

| # | 論点 | 決定 |
|---|---|---|
| 5 | 答えやすい問い方 | **選択肢カードの UI まで作る**。AI の問いを構造化(場面で問う問い・選択肢・選択肢ごとの結果(コスト・手間)・おすすめ)してチャットにカードで出す。カードの選択肢を選ぶと、その観点は「AI の提案を採用」、自由に書いて答えると「ユーザーが決定」になる |
| 6 | 潜在的なニーズを聞く質問の型 | **観点の表に入れる**(利用者の1日の流れ・例外の場面・将来の拡張を、機能面の観点にする)。プロンプトの指示だけにしない |
| 7 | 2モードの扱い | **ヒアリング(観点の表・カード)と2文書のモデル化は両モード共通**。要件 → 処理は、詳細設計モードは段階1、簡易モードは実装計画書の WBS の行に「要件: FR-001」を足して解析する。これで要件 → 作業単位を両モードで追える |
| 8 | 既存のプロジェクト | **そのまま読み、再生成で使える**。移行の処理は作らない。古い `hearing_check` は5条件の結果として表示し、model の無い文書は md のまま使う。要件ID の検証は「要件ID が無い(文書を再生成すると使える)」の軽微な警告にする([Phase 31](../Phase-31/Phase-31-introduction.md) の簡易モードの段階8と同じ扱い) |
| 9 | 効果測定 | **3つの指標を、同じペルソナ・同じ規則で、ステージ6の最後に比べる**: ①段階8の未定義のうちヒアリングが原因のもの(33-1 の分類 A)の件数 ②ペルソナの事実のうち聞けたものの数 ③要件の出どころの割合(AI の推測の割合)。[33-1](./Phase-33-1.md) の数字がベースライン |
| 10 | 段階8の未定義に「ヒアリングで聞くべきだった」の分類を出すか(Phase 32 の申し送り) | **出さない**。分類は効果測定で人が行う(33-1 のやり方)。未定義から再ヒアリングへ戻す流れは、ステージ8(AI 設計レビュー・再ヒアリング)で作る |

- 決定5の補足(LLM の回し方。Phase 33 完了後のユーザーの質問で決定): **カードはまとめて LLM へ送る**。1回の返信で、未決の観点のカードを数枚まとめて出す(互いに独立した観点だけをまとめ、規模のように後の必須を変える観点は単独で先に聞く)。カードの選択は、コードがその場で「AI の提案を採用」と記録する(LLM は呼ばない)。まとめたカードに全部答えたとき(または利用者が送信したとき)に、判定と返信を1回だけ回す。理由: 選択は構造化されたデータなのでコードで記録でき(決定1と同じ考え方)、1つ選ぶたびに判定と返信を回す(1回の選択で LLM 2回)より、無料枠の消費と待ち時間が少ない。代償は、まとめたカードの間で問いを答えに合わせられないことで、独立した観点だけをまとめて抑える。

#### モードごとの入力と粒度(決定7の確認。ステージ5振り返り 9.4 の AI 所見の提案を適用)

| 項目 | 詳細設計モード | 簡易ドキュメントモード |
|---|---|---|
| ヒアリング・観点の表・カード | 共通 | 共通 |
| 生成する文書 | 要件定義書・外部設計書(どちらも model から md) | 4文書(要件定義書・外部設計書は model から md、内部設計書・実装計画書は md のまま) |
| 要件の粒度 | 要件の行(FR/NFR/CON) | 同じ |
| 要件 → 処理 | 段階1の機能の `req_ids`(処理ID F-xx の単位) | なし(内部設計書の DF-n は要件と結ばない) |
| 要件 → 作業単位 | 段階1経由で段階7の単位へ(導出) | WBS の行の「要件」欄(解析) |
| 検証の入力 | 段階1の model と要件の model | 実装計画書の WBS の解析結果と要件の model |

### (3) 軽微・運用面

| # | 論点 | 決定 |
|---|---|---|
| 11 | 外部設計書の構造の深さ | **一覧を行に、説明は文字列**。画面一覧(SCR-ID)・API 一覧(メソッド+パス、本文・応答・エラーの欄)・外部連携を行の表にし、各行に関係する要件ID を付ける。システム構成・画面ごとの UI 仕様・入出力仕様は節の本文(文字列)。API の行の欄で、簡易モードに多かった API の書き落としを検証で拾う |

| 14 | `prompt_templates` との関係 | 変えない(テンプレートの `system_prompt` はヒアリングのプロンプトに足される今の形のまま。観点はテンプレートで増やさない) |
| 15 | Phase 22 からの持ち越し(05 の詳細バッジ、ER の主キーの NULL) | ステージ6では扱わず、「未消化の申し送り」に引き継ぐ |

## 範囲の外にしたもの

- 内部設計書・実装計画書のモデル化(簡易モード)。33-1 の B のうち内部設計書のもの(DF の無い機能の単位など)は、ステージ6では扱わない。
- 未定義から再ヒアリングへ戻す流れ・生成と分けた AI レビュー(ステージ8)。
- 要素単位の陳腐化と変更の影響範囲(ステージ7)。要件ID・観点の行は、ステージ7の入力になる。
