# Phase-90-4: ステージ12 の実装計画(Phase 91〜99)

## この章の目的

[90-1](./Phase-90-1.md) の決定をもとに、ステージ12(合意の精度)を Phase に分ける。Phase ごとに、成果物・依存・着手時に決めること(未確定事項)を示す。目安は、位置付け 12章の約10 Phase(Phase 90 を含む)に合わせた。

自動実装モード: on([introduction](./Phase-90-introduction.md) 参照)。この章は計画の文書だけで、本体と samples は変えない。

## この章で作成・更新したファイル

なし(計画の文書)。Phase の一覧は [90-3](./Phase-90-3.md) で [`docs/implementation_plan.md`](../../docs/implementation_plan.md) 4.1 に写した。

## 順番の考え方

- **API を先に、画面を後に**。ステージ11 と同じ並びにした。
- **合意の記録を最初に作る**。保護(92・93)・確認事項(94)・履歴(95)は、どれも「何が合意済みか」を読む。
- **要件定義書の保護(92)を外部設計書(93)より先に**。出どころが戻る決定的な経路([90-2](./Phase-90-2.md))は要件定義書にあり、完了の判断基準の中心だからである。外部設計書は、CR の予測で書き換えてよい範囲を決める分、後にした。
- **履歴(95)は保護の後に**。保護で戻した件数も履歴に出すためである。
- **段階の承認の印と新しい要件の予測の起点(96)は、CR の部品の手直しとしてまとめた**。どちらも Phase 83・86 の決定の見直しで、保護とは独立している。
- **最後の Phase(99)で、効果測定・全 E2E・開発環境での画面確認・`OPERATIONS.md` 10.8節のステージ12 の分をまとめて行う**(#36・#37 のステージ11完了後の運用注記)。本番への反映はステージ15 の完了時。

## 未確定事項(各 Phase の着手時に決める)

**どの Phase も**:
- 自動実装モード(#21)。
- テンプレートから取り込むもの(あれば、どのファイルか)。今の本体に無い部品は、`~/my-apps/project-templates/` のテンプレートから取り込み、samples にも作る(#21)。
- 簡易ドキュメントモードの全入口(書く・読む・画面・URL の直開き)を断ること(決定9)の確かめ。

### Phase 91

- 合意の記録の持ち方: 1つのテーブルに追記して「今の合意」をキーごとの最新で求めるか、今の合意と履歴を2つのテーブルに分けるか。
- 利用者(1.2)のキー。利用者の行には ID が無い。推奨の見込みは、1.2 全体を1つの要素(1つのキー)として合意すること。
- 合意した中身の形: 要素の本文(`row_body` と同じ形)を写すか、版の番号と ID だけを指すか。推奨の見込みは写すこと(版は巡回で消えうるため。束と同じ考え)。
- 既存の束(ステージ11 で作った束)から合意の記録を作るか(データ移行)。
- 合意を取り消す操作(誤って採用にした行)を持つか。

### Phase 92

- 戻す範囲: 文・出どころ・根拠の観点・優先度・種類のすべてか、文と出どころだけか。
- LLM が合意済みの行を消した(落とした)ときに、戻す位置(前の版の並び順か、末尾か)。
- 新しい行が、合意済みの行と同じ中身を別の ID で書いたとき(言い換えの重複)の扱い。
- 「推測」の行は合意済みになりうるか(「採用にする」を通さずに束に入った推測の行)。推奨の見込みは、束に入れば合意済み、出どころは推測のまま。
- 戻した件数の残し方(版の列か、別の記録か)。

### Phase 93

- **CR の反映で合意を更新する時点**: 反映済み(再生成の完了)か、検証済みか。反映の後、検証の前に CR を渡さない再生成をすると、合意が古いままでは CR の変更が戻されてしまう。推奨の見込みは反映済みの時点。
- 予測に無い画面・API が CR の反映で変わったとき(実際だけ)に、戻すか、残して印を付けるか。
- 外部設計書の要素の ID が変わる(画面の ID の付け直し)ときの照合の仕方。

### Phase 94

- 一覧を保存するか、毎回組み立てて利用者が決めた欄(決める機会・状態・メモ)だけ保存するか。
- 「確認済み」にしたときに、推測の要件を採用にする(合意を記録する)か。
- 推測の採用率の数え方(分母は確認事項に出た行か、生成した全部の推測の行か)。
- 観点の表(ヒアリング)の画面との関係(open の観点をどちらで決めるか)。

### Phase 95

- 履歴の応答の単位(要素ごとか、版ごとか)。
- 下書きの直しを、項目ごとの差分として残すか、「直した」の1行だけにするか。

### Phase 96

- 段階の承認の印を結んだ後の、CR の検証の条件(承認で付いた印も確認が要るか)。
- 起点の持ち方(CR の対象の `targets` に足すか、別の項目にするか)と、説明書の影響の節での見せ方。

### Phase 97〜98

- 画面の置き場(要件定義書のプレビュー〈SCR-005〉に出すか、別のページか)。イメージを先に見せる(Phase 88 と同じ)。
- 確認事項の一覧のページの置き場と、SCR-005・SCR-008・束・CR のページからのリンク。

### Phase 99

- 実 LLM を使う範囲と費用の見積もり(影響が広がる CR の題材を、N2 のような予測が1件以上ある変更にする)。
- 効果測定の材料: 90-2 と同じ「トレンド追跡アプリ」の続きか、新しいプロジェクトか。
- 画面確認で決める項目。
