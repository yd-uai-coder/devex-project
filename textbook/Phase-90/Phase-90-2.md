ステージ12 の効果を後で比べられるように、今の Devex(ステージ11 の版)で、CR を渡さない再生成のときに、合意した行(文・出どころ)がどれだけ動くかを記録する。あわせて、Phase 89 で見つかった「合意した行が動く」(FR-005)の原因を切り分ける。計画モードの決定で、実 LLM を少し使った。

## 材料を書き出して残す

- ステージ11 のベースラインは、材料を git から読み出した(リポジトリに戻さない)。今回の材料は開発 DB の版で、文書の版は巡回(直近3件。CR を反映した版は除く)で消える。実際に、v6 は v9 を作った時点で消えた。
- そこで、版ができるたびに `snapshot` で `data/` に書き出し(裏で版の番号を見張って自動で書き出した)、`report` は `data/` だけを読む形にした。同じ `data/` からは同じ出力になる。Phase 99 の効果測定も、同じ書き出し方を使う。
- 起点の v5(CR-3 を反映した版)は、`snapshot 5` で文書だけを書き出した。その時点の段階の印は残っていないので、比べるのは v6 以降の印である。

## 測り方

`report` は、起点 v5 と後の各版(v6〜v9)、直前の版とを比べる。

1. **要件の行**: 文の変化・出どころの変化・消えた行・増えた行。出どころの変化は、前の版の出どころに今の観点の状態で `cap_source` をかけ直した値と一致するか(本体が `unchanged` の行を写すときにすること)で、「上限のかけ直しで説明できる」と「それ以外(LLM)」に分けた。
2. **利用者と使う場面(1.2)**。
3. **文書の要素の差分**: `build_elements` の段階0(要件・画面・API)を `diff_elements` で比べる。
4. **段階の印のうち CR に結ばれないもの**(出どころが `cr:` で始まらない)。
5. **推測の要件の数**。

## 結果の要点

詳細は [`stage12-baseline.md`](../../appendix/measurements/stage12-baseline.md)。

- **出どころの戻りは決定的な経路だった**: v6 で、12行すべての出どころが「採用」から「推測」に戻った。文の変化は0件。12件すべてが `cap_source` のかけ直しで説明できた。
  - 「採用にする」は行の出どころだけを書き換え、観点の状態(このプロジェクトは全部 open)を変えない。次の再生成で行を写すとき、上限がかけ直されて戻る。
  - Phase 89 の申し送りでは「LLM の揺れの例」としていたが、見立てを改めた([90-1](./Phase-90-1.md) の決定3 の根拠)。
- **LLM の揺れは小さかった**: v6〜v9 の4回で、要件の文・ID・画面・API の変化は0件。揺れたのは、v6 で利用者(1.2)の重なった行が1件落ちたことだけ。v7〜v9 は直前の版とまったく同じだった。
- **関係の無い印**: v6 で付いた3件(FR-005 から段階1・5・8)が、v9 まで残っている。
- **判定**: 「合意済みの行が変わらない」は ×(出どころと利用者が動いた)、「推測の要件がすべて確認事項に出る」は △(プレビューに推測の要件だけ。推測の利用者2件と、要件の根拠の open の観点6件は出ない)。

この題材は小さく(要件12行・観点はすべて open)、CR を渡さない再生成だけなので、揺れが小さいのはこの条件のもとでの結果である。外部設計書の要素も保護の対象にする決定(90-1 の決定5)は、この結果では揺れが見えていないが、影響が広がる CR の後の揺れを Phase 99 の効果測定で確かめる。
