## 着手時の相談で決めたこと

詳細は [`q_a.md`](../q_a.md) の「Phase 90 開始時」を参照する。質問は5回行った。

- 前のセッション(`tagmerge.py` の手直しのセッション)の計画モードで1回(2問)。
- このセッションの計画モードで1回(2問)。
- 計画の承認の後に、90-1 で3回(11問)。

**計画モードの4問**(すべて推奨どおり):
1. ベースラインは実 LLM を少し使う(開発環境・Gemini 3.5 Flash-Lite・1つのプロジェクトで「CR の反映 → CR を渡さない再生成 ×3」。見積もり 約 $0.02〜0.05、上限 約 $0.10)。
2. 仕様診断では、ステージ12 の入力7件を1件ずつ判断する。
3. 再生成は、ユーザーが開発環境の画面で行う。Claude は開発 DB を読む測定のスクリプトを書く。
4. 題材は、Phase 89 の「トレンド追跡アプリ」(CR-3 を反映した版が起点)。

**90-1 の決定の要点**:
1. 合意済みの行は、行ごとの合意の記録(追記型。出どころは束・採用にする・CR)で持つ。
2. CR の範囲の外の再生成からは、生成の後にコードで戻して守る。
3. 合意済みの行には、出どころの上限をかけ直さない(「採用」が「推測」に戻る決定的な経路を断つ)。
4. 確認事項の一覧は、推測の要件・推測の利用者・根拠が未決の観点を集め、決める機会と状態を持つ。
5. **外部設計書の要素(画面・API・外部連携)も合意と保護の対象にする**(推奨と違う)。CR で書き換えてよいのは、予測が届く要素。
6. 束が指す版も、版の巡回で消さない。
7. 行の履歴は、合意の記録を追記型にして持つ。
8. 入力7件はすべてステージ12 に入れる。**段階の承認の印を CR に結ぶことと、新しい要件の予測の起点も入れる**(推奨と違う。どちらも結び方は推奨どおり)。

**推奨と違った選択は3件**(決定5と、決定8の2件)。どれも範囲を広げる向きである(推奨は約10 Phase に収めるために狭めていた)。計画の差し戻しは無い。#39 の材料。

Claude の判断は、[90-1](./Phase-90-1.md)「Claude の判断」にある。

- 出どころの揺れの原因を、ベースラインの前に開発 DB で切り分けた(P89 の「LLM の揺れ」の見立てを改めた)
- 合意の記録のキーを、変更影響分析の要素のキーにした
- CR で書き換えてよい範囲を、保存した予測で決める
- 広がった範囲を、API の Phase を分けて約10 Phase に収めた

## Phase 完了チェック(#22)

設問は Phase の要点の要約である(回答は求めない)。

1. P89 で「LLM の揺れ」と見た FR-005 の出どころの変化が、実は決定的な経路だったのはなぜか。「採用にする」と観点の状態と `cap_source` の関係から説明できるか。
