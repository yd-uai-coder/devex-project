## スコープ(構想から)

位置付けの 12章は、ステージ12 の中身を次のように置いている。

- **中身**: 行単位の合意と変更の履歴、版の上限の見直し(合意済みの版を消さない)、確認事項の一覧、差分の再生成と合意済みの行の保護
- **完了の判断基準(案)**: 合意済みの行が、CR の範囲の外の再生成で変わらない。推測の要件がすべて確認事項に出る。

## 調べたこと(推奨の根拠)

- **要件の行と出どころ**(`devex-api/backend/app/documents/requirements/`):
  - 行(`RequirementRow`)は出どころ(`source` = user / adopted / assumed)を持つ。LLM が書き、`assemble.cap_source` が根拠の観点の状態で上限をかける(観点が open なら「推測」)。
  - 行の合意(誰と・いつ)を記録する場所は無い。束(Phase 81)は要件定義書の写しを持つが、行ごとの合意ではない。
- **「変えない行」**(`app/documents/revision.py`・`requirements/drafting.py`):
  - 再生成では、LLM に「関係しない行は `unchanged` にする」と頼むだけである。`assemble.build_model` は `unchanged` の行を前の版から写すが、CR の対象の外の書き換えや、行の脱落をコードで拒まない。
  - 写した行にも、出どころの上限をかけ直す(観点が採用から未決に戻ったとき、写した行が「ユーザー」のまま残らないように)。
- **「採用にする」**(`DocGeneratorService.adopt_requirement`):
  - 推測の要件を「採用」にする。今の版の model を `replace_model` で書き換え、版を作らない(履歴は残らない)。観点の状態は変えない。
  - したがって、根拠の観点が open のままなら、次の再生成で行を写すときに上限がかけ直され、「推測」に戻る。
- **P89 の「合意した行が動く」の正体**([90-2](./Phase-90-2.md)):
  - Phase 89 の実 LLM の一巡では、CR を渡さない再生成で、FR-005 の出どころが「採用」から「推測」に変わり、関係の無い印が3件付いた。これを LLM の揺れの例として、ステージ12 へ送っていた。
  - 開発 DB の版(v5 → v6)を比べたところ、文の変化は0件だった。出どころの変化は12行すべてで、上のかけ直しで説明できた。このプロジェクトは観点がすべて open で、v5 の全行を「採用にする」で採用にしていた。
  - つまり、出どころの揺れは LLM ではなく、**決定的な経路**(採用は観点を変えない → 写すときに上限をかけ直す)である。合意した行を守るには、LLM の揺れより先に、この経路を直す必要がある。
  - LLM の揺れも1つあった。利用者と使う場面(1.2)が3件から2件に減った(重なった行が落ちた)。
- **版の巡回**(`app/repositories/generated_document.py`): CR を渡した再生成の版は消さない(Phase 89 の完了後の調整)。束が指す版(`baseline_items.source_version`)は守らない。束は写しを持つので内容は壊れないが、元の版はたどれなくなる。
- **推測の要件の見せ方**: `requirements_summary` が、プレビューに推測の要件の一覧を出すだけである。推測の利用者(1.2)と、根拠が open の観点は出さない。「いつ・どこで決めるか」の欄も無い。
- **外部設計書の要素**(`app/documents/external_design/model.py`): 画面(`screens`)・API(`apis`)・外部連携(`integrations`)の行に ID と要件 ID(`req_ids`)を持つ。変更影響分析は、これらを文書の側の要素(段階0)として扱う(`impact/elements.py` の `add_document_elements`)。

## 診断と決定

#### 決定1〜3の理由(行ごとに合意を記録し、生成の後にコードで戻す)

- 完了の判断基準は「合意済みの行が、CR の範囲の外の再生成で変わらない」である。プロンプトの約束だけでは、LLM の揺れ(90-2 の利用者の行)を止められず、基準を保証できない。生成の後にコードで戻せば、LLM の出力によらず決定的に守れる。
- 戻すには「何が合意済みか」を行の単位で知る必要がある。束に入った行を合意とみなす形では、「採用にする」が合意にならず、1行だけの合意もできない。行ごとの記録なら、束の作成(入った行をまとめて合意)・採用にする(1行)・CR の反映(対象の行の合意を更新)を同じ記録に集められる。
- 出どころの上限は、合意の記録がある行にはかけない。合意の根拠は観点ではなく合意そのものだからである。観点を採用にする案は、同じ観点を根拠にする別の行の出どころまで上げてしまう。出どころと合意を別の列にする案は、差分と印が出どころの変化を無視するように、変更影響分析に手を入れる必要がある。

#### 決定4の理由(確認事項の一覧)

- 完了の判断基準の後半は「推測の要件がすべて確認事項に出る」である。推測の要件だけでは、推測の利用者(1.2)と、根拠が open の観点(要件の出どころを決める元)が漏れる。
- 一覧は毎回、今の model と観点の表から決定的に組み立てる(LLM なし)。各行に「決める機会」(次の打ち合わせ / メール / 実装中 / 決めない)と状態(未確認 / 確認済み / 却下)を付ける。振り返り 6節の「決める機会」の欄はこれである。
- 推測の採用率(振り返り 6節)は、この一覧の状態から数える。

#### 決定5(推奨と違った選択)

- 推奨は、要件の行と利用者だけを守り、外部設計書は 90-2 と効果測定で揺れを測ってから決めることだった。範囲を約10 Phase に収めるためである。
- ユーザーは外部設計書の要素も含めた。詳細設計モードでは要件定義書と外部設計書を一度に作り直すので、画面・API も同じ再生成で揺れうる。揺れれば、段階に関係の無い印が付く。
- 合意の記録は、変更影響分析の要素のキー(`req:FR-001`・`screen:SCR-001`・`api:GET /x` など)で持つ。要件と画面・API を同じ記録に集められる。

#### 決定6・7の理由

- 版の巡回は、ステージ11 の振り返り(16.4)の「保存の上限は、参照されているものは消さない、と対で書く」の適用である。束は写しを持つので壊れないが、版の画面から束の元の版をたどれるようにする。
- 履歴は、合意の記録を上書きせずに行を足していけば、要件 ID ごとに「いつ・何で・どう変わったか」が引ける。版は巡回で消えるので、版の差分からは追えない。

- 推奨では、段階の承認の印は効果測定で漏れを数えるだけ、新しい要件の予測の起点はステージ13(説明とすり合わせ)へ回すことにしていた。範囲を約10 Phase に収めるためである。

## Claude の判断(診断中)

- **出どころの揺れの原因を、90-2 の前に切り分けた**: 開発 DB の v5・v6 を読み、出どころの変化が `cap_source` のかけ直しで説明できるかを、測定のスクリプトで行ごとに判定した。P89 の申し送りの「LLM の揺れ」という見立てを、「決定的な経路 + LLM の揺れ(利用者の行)」に改めた。決定3は、この結果から足した論点である。
- **合意の記録のキーは要素のキーにする**: 決定5で外部設計書の要素も対象になったので、要件 ID ではなく、変更影響分析の要素のキーで持つ。予測(`predicted_impact`)・印・比較と同じキーで照合できる。
- **保護の例外は保存した予測で決める**: CR の反映で書き換えてよい文書の側の要素は、合意のときに保存した予測(Phase 83 の `predicted_impact`)から取る。反映のときに予測し直すと、基準の束と今の版の差で範囲が変わりうるためである。
- **Phase の数**: 決定5・8で範囲が広がった。[90-4](./Phase-90-4.md) では、API を Phase で分けて、目安の約10(Phase 90 を含む)に収めた。
