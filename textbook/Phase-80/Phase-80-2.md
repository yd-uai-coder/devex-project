## 測り方

`measure.py` は、本体の関数を次の順に呼ぶ。

1. `build_elements(DesignModels.from_dicts(...))` で、要素のグラフを作る(85要素)。
2. **予測**: `impact_of(elements, Change("req:FR-005"))` を呼ぶ。合意の前に、変わる要件だけから見直しの範囲を出す。
3. **今の印**: model の FR-005 の文を書き換え、`diff_elements(before, after, stages=(0,))` と `marks_for(...)` を呼ぶ。今の本体が文書の再生成のときに `record_document_change` で付けるものと同じである。

そのうえで、7段ごとの判定(a)と、4つの問いの判定(b)を、本体のコードを読んで書いた(○ / △ / ×と根拠)。

## 結果の要点

詳細は [`stage11-baseline.md`](../../appendix/measurements/stage11-baseline.md)。

- **7段**: 受付・整理・説明・合意が ×、影響・反映・検証が △。
- **4つの問い**: 「なぜ」「誰の合意で」が ×、「何を」「どこに反映したか」が △。
- **予測は正解と一致した**(6件 / 正解6件)。今の関数のままで、合意の前に影響を説明できる。足りないのは、それを出す経路である。
- **今の再生成の印は4件**。画面 SCR-001 と API `POST /api/v1/projects` に印が付かない。
  - 詳細設計モードでは、要件定義書と外部設計書を一度に作り直すので、文書の側の要素は印の置き場を持たない。
  - CR では、予測の一覧の文書の側の要素を「確かめる項目」として出す。印の扱いは Phase 86 の未確定事項([80-4](./Phase-80-4.md))。

## テスト観点

自動のテストは書いていない(測定のスクリプトで、本体の変更が無いため)。代わりに次を確かめた。

- 予測の6件が、[ステージ7のベースライン](../../appendix/measurements/stage7-baseline.md)の N2 の正解(本体のキーに読み替えたもの)と一致すること。
