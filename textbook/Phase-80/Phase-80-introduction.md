# Phase 80 導入: ステージ11(合意と変更の一巡)着手 ── 要件確認フェーズ

## 目的

2026-10-18 に、ステージ10 でプロジェクトを一度閉じた([プロジェクト全体の振り返り](../retrospectives/project-retrospective.md))。2026-10-19 に Devex の位置づけを「クライアントとの合意を、設計から実装・テストまでつなぐ」に改め、ステージ11〜15 を割り振った([位置付け](../../appendix/devex_project_positioning.md) 12章)。

Phase 80 は、その最初のステージ「合意と変更の一巡」の要件確認フェーズである。[Phase 73](../Phase-73/Phase-73-introduction.md) と同じ型で、次のことを行う。

- 未決事項の仕様診断(#28)と決定。あわせて、振り返りに残した入力(6節の「取り込んでいない」8件・8節の持ち越し・`postgres-init` の不具合)を1件ずつ判断する([80-1](./Phase-80-1.md))。
- ベースラインを記録する。LLM は使わない([80-2](./Phase-80-2.md))。
- 決定を `docs/*.md`・README・位置付けに反映する([80-3](./Phase-80-3.md))。
- ステージ11 の実装計画を作る。Phase 81〜89 の一覧・成果物・依存・未確定事項を示す([80-4](./Phase-80-4.md))。

ステージ10 の要件確認(Phase 73)では、ベースラインを省いた。今回は、位置付け 12章の「着手時の仕様診断とベースライン → 実装 → 効果測定」に従って、ベースラインを置いた。本体の実装は Phase 81 以降で行う。

詳細は [`q_a.md`](../q_a.md) の「Phase 80 開始時」を参照する。質問は5回行った。

**計画モードの3問**(すべて推奨どおり):
1. ベースラインを含める。LLM は使わない。
2. 振り返りの残件を1件ずつ判断する。
3. 再開の記録は docs だけ今直す。CLAUDE.md は案を申し送りに置く(#18)。

**80-1 の決定の要点**:
1. 合意済みの版はプロジェクトの束で、別のテーブルに写して凍結する。
2. 詳細設計モードで、シナリオは N2。
3. CR は6つの状態で、合意の前に予測を出す。
4. 説明書は5節。**任意で LLM の要約を足せ、人が確かめるまで載らない**(ユーザーの指示)。確かめ方は Claude の提案(確認の関門・照合・古い印)を採用した。
5. 合意の記録の相手は空でもよい。
6. 反映はレビューの指摘と同じ経路で行う。
7. **検証済みは印の確認だけ**(推奨と違う)。
8. 振り返りの示唆は「版に生成したモデル」だけを入れる。`gemini-3.1-flash-lite` と `postgres-init` は、ステージ11 で扱う。

**推奨と違った選択は2件**: 検証済みの条件と、説明書の要約(選択肢に無い形の指示)。ほかに、合意の相手を空でもよいとする補足が1件あった。計画の差し戻しは1回(テンプレートの扱い。計画の中身の誤りではなく、前提の追加)。#39 の材料。

## Phase 完了チェック(#22)

設問は Phase の要点の要約である(回答は求めない)。

1. 合意済みの版を、文書ごとではなくプロジェクトの束にしたのはなぜか。CR が「何からの差分か」を1つで指したいことと、N2 の影響が届く文書・段階の数から説明できるか。
2. 合意の時点の内容を、今の版の仕組みに印を付けるのではなく、別のテーブルに写したのはなぜか。文書の巡回(直近3件)と、段階の上書きから説明できるか。
3. 影響の予測が、新しいたどり方を作らずに出せるのはなぜか。今の再生成の印が、画面と API に付かないのはなぜか(詳細設計モードで、文書をどう作り直すかから)。
4. LLM の要約を、確かめるまで説明書に載せないのはなぜか。照合と「古い」の印は、それぞれどんな誤りを防ぐか。
5. 「検証済み」をレビューの実行に依らず、印の確認で決めると、何を得て、何を失うか。
