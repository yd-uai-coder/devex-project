# Phase-80-4: ステージ11 の実装計画(Phase 81〜89)

## この章の目的

[80-1](./Phase-80-1.md) の決定をもとに、ステージ11(合意と変更の一巡)を Phase に分ける。Phase ごとに、成果物・依存・着手時に決めること(未確定事項)を示す。目安は、位置付け 12章の約9 Phase に合わせた。

自動実装モード: on([introduction](./Phase-80-introduction.md) 参照)。この章は計画の文書だけで、本体と samples は変えない。

## この章で作成・更新したファイル

なし(計画の文書)。Phase の一覧は [80-3](./Phase-80-3.md) で [`docs/implementation_plan.md`](../../docs/implementation_plan.md) 4.1 に写した。

## 順番の考え方

- **API を先に、画面を後に**。ステージ10 までと同じ並びにした。
- **合意済みの版を最初に作る**。CR は合意済みの版からの差分なので、版が無いと基準を持てない(位置付け 12章の「この順にする理由」)。
- **予測(83)を説明書(84)より先に**。説明書の5節のうち、影響の一覧と作業単位・テストの数が、予測を使うためである。
- **反映(85)を再検証(86)より先に**。再検証は、反映の後の実際の印を確かめる操作だからである。
- **小さな修正(88)は、画面の Phase と同じ Phase に入れる**。どちらも小さいため。
- **最後の Phase(89)で、効果測定・全 E2E・本番への反映をまとめて行う**(#36・#37)。

## 未確定事項(各 Phase の着手時に決める)

**どの Phase も**:
- 自動実装モード(#21)。
- テンプレートから取り込むもの(あれば、どのファイルか)。今の本体に無い部品は、`~/my-apps/project-templates/` のテンプレートから取り込み、samples にも作る(#21)。

### Phase 81

- 束を作れる条件。「古い」の段階や、未承認の段階があるときに作れるか。推奨の見込みは、作れるが、束にその状態を残すこと。
- 写しの持ち方。文書は content と model、段階は `approved_model`。テスト仕様書を入れるか。
- 版の番号の振り方(プロジェクトの中で B-1, B-2…)。
- 束を作り直したり消したりできるか。推奨の見込みは、消せないこと(合意の基準なので)。
- 生成したモデルの列を、この Phase で足すか、85 で足すか。

### Phase 82

- 状態の遷移の細部:
  - 却下の後に、下書きへ戻せるか。
  - 取り下げは、合意の前だけでよいか。
  - 「説明済み」に、説明書の出力を条件にするか。
- 背景の出どころの種類(打ち合わせ / メール / 資料 / その他)と、日付の粒度。
- ID の無い新しい要件を足す CR の、対象の持ち方。
- 同じ要件を対象にする、進行中の CR が2つあるときの扱い。

### Phase 83

- 予測の起点。対象の要件の変更の種類(内容 / 削除 / 新規)を、`Change.kind` にどう写すか。
- 新しい要件を足す CR の予測。起点が無いので、関係しそうな要素を人が選ぶか、予測なしと示すか。
- 予測を、合意の時点で CR に保存するか(反映の後に比べるため)。

### Phase 84

- 5節の書式(見出し・表)と、ファイル名。
- 要約の LLM の用途(どの Purpose の設定を使うか)と、プロンプトの入力の範囲(5節だけ)。
- 照合の範囲(要件 ID・数字のほかに、画面 ID・API を入れるか)。
- 要約を直したときの記録(元の要約を残すか)。

### Phase 85

- 再生成の起点。要件定義書から全部作り直すか、影響のある段階だけを部分再生成するか。
- CR の内容を、修正の指示にする形(`build_instruction` に並べるか、別の節にするか)。
- 1つの CR に複数回反映できるか(やり直し)。
- 反映中の CR がある間の、ほかの生成の扱い。
- 予測と実際の比較の表し方(予測だけ / 実際だけ / 両方)。

### Phase 86

- 文書の側の要素(画面・API)の確認の扱い([80-2](./Phase-80-2.md) で、今の印が付かないと分かった)。CR の確認の項目にするか、段階0の印を足すか。
- 「検証済み」の後に、新しい合意済みの版を作るときの既定の記録(CR の合意の記録を写すか)。
- レビューを CR に結ぶ条件(反映の後の最初のレビューか、人が選ぶか)。

### Phase 87・88

- 画面の置き場所(詳細設計の画面のタブか、新しいページか)と、ナビゲーション。
- 要約の確認の画面(並べて見るか)。
- モデルのカタログの後継(Context7・公式の資料で確かめる)。
- `postgres-init` は、テンプレートの直した形を取り込む。

### Phase 89

- 反映を実 LLM で通すか。通すなら、着手時に費用の見積もりの表を出す。
- E2E の CR の流れの範囲(偽の LLM で、受付から検証まで)。
- 本番への反映の手順(`OPERATIONS.md` の新しい節)と、ロールバック(新しいテーブルのみか)。
