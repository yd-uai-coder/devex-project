## スコープ(構想から)

位置付けの 12章は、ステージ11 の中身を次のように置いている。完了の判断基準は「決まったシナリオで、1件の CR が受付から再検証まで通り、『何を・なぜ・誰の合意で・どこに反映したか』を後からたどれる」こと。

- **新しく作るもの**: 文書単位の合意済みの版(印・凍結・誰と・いつ・根拠の打ち合わせ)、CR(手で作る。内容・背景・対象の要件 ID・状態)、変更の説明書(md の出力)、合意の記録(開発者が記録する)
- **今あるものを使うもの**: CR に結んだ影響の一覧(今の変更影響分析)、反映(今の再生成・部分再生成)、再検証(今の設計レビューと「古い」の印)
- **ステージ12 以降に回すもの**: 行単位の合意・確認事項の一覧・合意済みの行の保護(12)、規模の集計・クライアントの閲覧(13)、資料からの取り込み(14)、実装との接続(15)

## 調べたこと(推奨の根拠)

- **文書の版**(`devex-api/backend/app/repositories/generated_document.py`):
  - 種別ごとに直近3件(`MAX_VERSIONS_PER_DOC_TYPE = 3`)を残す。4件目を作ると最も古い版を消す。
  - 版に、生成したモデルは残らない。
  - 詳細設計モードの文書は要件定義書と外部設計書の2つ(`DOC_TYPES_BY_MODE["detailed"]`)。どちらも意味モデル(`model`)を持つ。テスト仕様書(`test_spec`)は別に作る。
- **段階**(`app/models/design_stage.py`):
  - 1行の中に、版の番号・承認の写し(`approved_model`)・印(`impact`)を持つ。過去の版は残らない。
  - したがって、合意の時点の内容を後から取り出すには、どこかに写しておく必要がある。
- **変更の影響**(`app/detailed_design/impact/`):
  - 今は、変わった**後**に、前の版との差分(`diff_elements`)から段階に印を付ける(`marks_for`・`record`)。文書の再生成のときは `DesignStageService.record_document_change` が呼ぶ。
  - 変わる**前**の予測は画面にも API にも無い。ただし、`impact_of(elements, Change(key))` に変わる要素のキーを渡せば、同じたどり方(処理を軸)で予測を出せる。[80-2](./Phase-80-2.md) で確かめた。
- **再生成の指示**:
  - `POST /projects/{id}/generate` は `finding_ids`(採用したレビューの指摘)を受け取る。`app/review/sendback.py` の `build_instruction` が、文書ごとに関連する指摘だけを修正の指示にして、プロンプトに入れる。段階の生成(`design_stage_generation_service.py`)も同じ形である。
  - CR の内容は、この経路にそのまま乗る。
- **「誰が決めたか」の土台**:
  - 要件の出どころ(`RequirementSource` = user / adopted / assumed。`app/documents/requirements/model.py`)。
  - 観点の状態と根拠(`hearing_points`)。
  - レビューの指摘の採否(`review_findings.decision`)。
  - どれも開発者の画面の中だけにあり、クライアントとの合意を記録する場所は無い。
- **テンプレート由来のファイル**: 計画の差し戻しでユーザーから指示があった。`devex-api`・`devex-ui` とも、今の構成に要らないテンプレート由来のファイルは削除済みである。ステージ11 の設計では、削除された部品(デモの画面・使っていない部品)を前提にしない。要るものは、その Phase で `~/my-apps/project-templates/` のテンプレートから取り込む([80-4](./Phase-80-4.md) の各 Phase の未確定事項に欄を置いた)。

#### 決定1・2の理由(束で持ち、別のテーブルに写す)

- CR は「合意済みの仕様からの差分」である。要件1つの変更でも、画面・API・処理・手順書と、複数の文書と段階に届く(N2 は6要素。[80-2](./Phase-80-2.md))。CR の基準を「B-1 からの変更」と1つで指せるように、束にした。
- 文書は3件で巡回し、段階は1行を上書きする。今の版の仕組みのまま合意の時点を残すと、段階に版の履歴の表を新しく足すことになり、既存の承認・印の仕組みに触る範囲が広い。写しなら、既存の仕組みを変えずに、合意の時点を凍結できる。容量が増えるのは、合意の回数の分だけである。

#### 決定5・6の理由(状態を6つにし、予測を出す)

- 状態は、位置付けの 5章の7段(受付・整理・影響・説明・合意・反映・再検証)にそろえた。遷移ごとに日時を残すので、CR の詳細にそのまま時系列が出る(完了の判断基準の「後からたどれる」)。
- 合意の前に影響を説明できないと、説明書(決定7)に影響が載らない。予測は、今の `impact_of` に変わる要素を渡すだけで出せる(LLM なし・決定的)。反映の後の実際の印と並べると、予測に無かった変更が分かる。そこには見落としのほかに、LLM が CR の範囲の外を書き換えた分も含まれる。これは、ステージ12(合意済みの行の保護)の入力になる。

#### 決定7・7-2の理由(要約は任意で、人が必ず確かめる)

- 5節は決定的に組み立てるので、同じ CR からは同じ説明書ができる。5節の中身は、CR の内容と背景・対象の要件(合意済みの文と変更後の案)・影響の一覧(段階ごと・理由)・関わる未決事項(open の観点・推測の要件)・影響を受ける作業単位とテストの数である。
- ユーザーの指示: クライアント向けの平易な要約を、ボタンで LLM に作らせて足せるようにする。そのうえで、要約は人が必ず確かめる。Claude の提案(採用)は次の4点。ステージ8 の「決定的なチェック → LLM → 人」と、入力が変わると「古い」にする印(fingerprint)の型に合わせた。
  1. **確認の関門**: 要約は「未確認」でできる。未確認の間は、説明書の出力(md)に載らない(プレビューだけ。「未確認」の帯を出す)。
  2. **照合**: 要約に出てくる要件 ID・数字が5節にあるかを、コードで照合する。合わない所に印を付ける。
  3. **人の確認**: 人は要約を直してから「確認した」を押す。誰が・いつ確認したかを残す。
  4. **古い印**: CR の内容か影響が変わったら、要約は「古い」になり、未確認に戻る。

#### 決定9(推奨と違った選択)

- 推奨は「印の確認 + 設計レビューを1回」だった。レビューの実行を条件にすると、反映の後に別のモデルの検証が必ず挟まるためである。
- ユーザーは「印の確認だけ」を選んだ。レビューは任意で、流したときは CR に結ぶ(どのレビューの実行がこの CR の後か)。Claude のキーが無い利用者も、一巡を通せる。
- 新しい合意済みの版を自動で作る案は選ばれなかった。合意の版は、開発者が作る操作のままである(「合意」を人がしない版を作らない)。

## Claude の判断(計画の承認・診断中)

- **束に入れるもの**(詳細設計モード):
  - 表示中の要件定義書・外部設計書の版(content・model)
  - 承認済みの段階1〜8 の `approved_model`
  - 表示中のテスト仕様書の版

  まだ承認していない段階は、「束に入っていない」と記録する。束を作れる条件(「古い」の段階があるときに作れるか)は、Phase 81 の未確定事項にした。
- **CR の対象**: 対象は、基準の合意済みの版にある要件 ID とする。ID の無い新しい要件を足す CR(予測の起点が無い)の扱いは、Phase 82・83 の未確定事項にした。
- **予測には、文書の側の要素も入れる**: [80-2](./Phase-80-2.md) で、今の再生成の印は、画面(SCR-001)と API に付かないことが分かった。詳細設計モードでは、要件定義書と外部設計書を一度に作り直すため、文書の側の要素は印の置き場を持たない。CR では、予測の一覧の文書の側の要素を、確かめる項目として出す。印の扱いは Phase 86 の未確定事項にした。
- **合意の記録と束の作成は同じ項目を持つ**: 合意の記録と、束(合意済みの版)を作るときの記録は、同じ項目(相手・日時・メモ・理由)にそろえる。
- **生成したモデルの列**: 文書の版に足す。どの Phase で足すかは、Phase 81(束が写すとき)か Phase 85(反映で残すとき)の未確定事項にした。
