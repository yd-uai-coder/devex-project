M-03-T01 と、その AI 向けの版には、段階5の F-07 の手順から導いたシーケンス図(Mermaid)を入れました([Phase 25-5](../../textbook/Phase-25/Phase-25-5.md))。デモでは同じ図を SVG で描き、単位のファイル・テストの SUT・スタブの候補を色で示します。

単位の md は3つだけ書きました。基盤の単位・参照の薄い単位・参照の厚い単位で、手順書と未定義の出方がどう変わるかを見るためです。他の単位は、index の一覧にだけ載せています。

## 読み方

- 各単位の「未定義・要決定」には、出どころを付けています。
  - **[検証]**: 決定論的な検証が出すもの。Devex のコードが、設計の ID・パス・依存先を突き合わせて出す。
  - **[AI]**: 手順書を生成する LLM が出すもの。設計に無いことを推測で埋めず、挙げさせる。
- 重要度は #28 の3段階(最重要・中程度・軽微)です。
- 「決める」ときは、指摘の対象の段階へ飛び、そこで直します(決定3)。手順書には、決めた内容を書きません。

## この見本で見つかったこと

見本を書く中で、題材の設計(ゴール3の生成物)に次の穴が見つかりました。どれも、手順書を作ろうとして初めて表に出たものです。作成方針4章の「手順書の生成は、設計の実装可能性の検証でもある」を、実例で確かめられました。

1. **段階3のテーブルが0件**(ER が空のまま承認された。ゴール3の後に `ER_EMPTY` で承認を止めるよう直した不具合)。そのため、どの単位もテーブルを参照できない。
2. **チャット履歴の保存が設計に無い**。段階4の `repositories/project_repository.py` の責務には「チャット履歴の読み書き」とあるが、段階5の F-07 の手順に DB 操作が無い。
3. **LangGraph をどこが持つかが、段階4と段階5で食い違う**。段階4では `services/ai_service.py` の責務、段階5の F-07#3 では `GeminiClient.invoke_lang_graph`。
4. **段階6の L-01 に、F-08 の責務が混ざっている**(疑似コード4「自己診断の結果や4種設計書の逐次生成データをストリームに含める」)。
5. **フロントエンドのファイルが決まらない**。段階4のモジュールが `frontend` の1行だけで、どのファイルを作るかを手順書に書けない。
6. **認可(他人のプロジェクトへの操作)が、どの処理にも無い**。07章の「認証」は、トークンの発行と失効だけを決めている。
7. **(シーケンス図にして分かったこと)** F-07#4 は戻りを呼び出しとして書いている(`services/ai_service.py → frontend`)。また、テスト観点のスタブ `project_repository` は手順に出てこない(2 と同じ穴)。
