# 変更の影響の見本(Phase 41)

ステージ7で Devex が示す「変更の影響」の形を、md で書いた見本。画面の見せ方は devex-ui のデモ `/change-impact-demo`(`src/features/change-impact/demo/`)にある。決定は [Phase 41-2](../../textbook/Phase-41/Phase-41-2.md)、測り方は [ベースライン](../stage7-baseline/README.md)。

題材は Devex 自身で、ベースラインと同じ生成物([`stage6-effect/detailed/`](../stage6-effect/README.md))を使う。

## 示し方の規則

| 項目 | 規則 |
|---|---|
| 変わったもの | 段階は直前に承認したときの写しと、文書は前の版の model と、要素の単位で比べて求める。前の値と後の値を並べる |
| たどり方 | 変更が届く処理(F-xx)を決め、その処理に属する要素(要約・CRUD・手順・作業単位と、その手順を呼ぶ処理ロジック・単位の手順書)を示す。共有されるモジュールからは広げない |
| 改名 | 参照の文字列だけが変わる変更(モジュールのパスなど)は、直接の参照元だけを示す |
| 非機能要件 | 横断事項が持つ要件ID からたどり、その横断事項の対象のモジュールを含む単位の手順書まで示す |
| 理由 | 参照の種類からコードが書く(LLM は使わない) |
| 段階の状態 | 段階の「古い」は今の仕組みのまま。その中の見直しが要る要素に印を付け、すべて「確認済み」になれば承認し直せる |
| 再生成の候補 | 部分再生成できる段階(5・6・8)の要素。自動では再生成しない |

## 例1: 機能要件 FR-011 を変える

**変わったもの**(要件定義書 第2版 → 第3版)

| 要素 | 前 | 後 |
|---|---|---|
| FR-011 | AI 応答の失敗時は理由を表示して再送を促す。 | AI 応答の失敗時は自動で3回まで再試行し、だめなら理由を表示して再送を促す。 |

**影響**(9件)

| 置き場 | 要素 | たどった道 | 理由 |
|---|---|---|---|
| 外部設計書 | SCR-002 対話型チャットヒアリング画面 | FR-011 → SCR-002 | この要件を持つ |
| 外部設計書 | API POST /api/v1/chats | FR-011 → API | この要件を持つ |
| 段階1 | F-02 チャットメッセージの送信と AI 応答の取得 | FR-011 → F-02 | この要件を持つ |
| 段階2 | F-02 の処理の要約 | FR-011 → F-02 → 要約 | この処理に属する |
| 段階3 | CRUD F-02 × chats | FR-011 → F-02 → CRUD | この処理に属する |
| 段階5 | F-02 の手順 | FR-011 → F-02 → 手順 | この処理に属する |
| 段階6 | services/chat.py の send_message | FR-011 → F-02 → 手順 → 処理ロジック | この手順から呼ばれる |
| 段階7 | 作業単位 M-02-T01 | FR-011 → F-02 → M-02-T01 | この処理に属する |
| 段階8 | M-02-T01 の手順書 | FR-011 → F-02 → M-02-T01 → 手順書 | この作業単位の手順書 |

**段階の状態**: 全段階が「古い」(文書の再生成のため)。見直しが要る要素は段階1・2・3・5・6・7・8 に1件ずつ。段階4(モジュール)は見直す要素が無いので、そのまま承認し直せる。

**再生成の候補**: 段階5 F-02 の手順 / 段階6 send_message / 段階8 M-02-T01。

> ベースラインの正解は「`clients/ai.py` に再試行を置くか」の判断も含んでいた。共有のモジュールのどれを直すかは ID だけでは決まらないので、この規則では示さない(手順と処理ロジックの見直しの中で人が決める)。

## 例2: モジュール services/chat.py を services/chat_service.py に改名する

**変わったもの**(段階4。直前の承認の写しと比べる)

| 要素 | 前 | 後 |
|---|---|---|
| モジュール | services/chat.py | services/chat_service.py |

**影響**(6件、改名なので直接の参照元だけ)

| 置き場 | 要素 | 理由 |
|---|---|---|
| 段階4 | api/routes/chats.py | このモジュールに依存する |
| 段階5 | F-02 の手順 | このモジュールを呼ぶ |
| 段階6 | send_message | このモジュールに置く |
| 段階7 | 作業単位 M-02-T01 | このモジュールに依存する |
| 段階7 | 横断事項 トランザクション | このモジュールに依存する |
| 段階8 | M-02-T01 の手順書 | このモジュールに依存する |

**段階の状態**: 段階5〜8 が「古い」。段階4は「古くない」が、同じ段階の中の `api/routes/chats.py` に印が付く(今の仕組みでは見えなかった依存)。

## 例3: 非機能要件 NFR-007 を具体化する

**変わったもの**: NFR-007「本人以外が他人のプロジェクトを見られない」→「ログイン必須。他人のプロジェクトは 404 を返す」。

**影響**(2件)

| 置き場 | 要素 | たどった道 | 理由 |
|---|---|---|---|
| 段階7 | 横断事項 認証 | NFR-007 → 認証 | この要件を持つ(ステージ7で横断事項に要件ID を足す) |
| 段階8 | M-01-T01 の手順書 | NFR-007 → 認証 → 手順書 | この横断事項の対象のモジュールを含む |

> ベースラインの正解は、各処理の手順(持ち主の確かめ)も含んでいた。横断事項から手順への辺は無いので、この規則では届かない。効果測定で見落としとして数える。
