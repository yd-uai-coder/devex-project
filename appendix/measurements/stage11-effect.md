# ステージ11の効果測定(Phase 89)

ステージ11(Phase 81〜88)で作った合意済みの版・変更要求(CR)・予測・説明書・反映・再検証を、[ベースライン](stage11-baseline.md)(Phase 80-2)と同じシナリオ N2・同じ材料・同じ表で測り直したもの。分析は [Phase 89-1](../../textbook/Phase-89/Phase-89-1.md) にある。

- 日時: 2026-10-20。本体は devex-api `stage11-15`(Phase 88 の版)。
- 決定的な部分(下の (c))は、外部の API・LLM・DB を使わない(費用 0)。材料はベースラインと同じ(`appendix/stage7-effect/impact/data/detailed.json` を `0c7a7f3^` から `git show` で読む)。
- 画面で通した確かめは、偽の LLM の E2E([`change-request-flow.spec.ts`](../../textbook/samples/frontend/e2e/change-request-flow.spec.ts)。[Phase 89-2](../../textbook/Phase-89/Phase-89-2.md))。実 LLM での一巡は、下の「実 LLM での一巡」に足す([Phase 89-4](../../textbook/Phase-89/Phase-89-4.md))。

## 実行

```bash
PYTHONPATH=devex-api/backend uv run --project devex-api/backend \
    python appendix/measurements/stage11/effect.py
```

`effect.py` は、ベースラインの `measure.py` の材料の読み出しと反映の模擬(FR-005 の文の書き換え)を import して使い、本体の純粋関数(`predict`・`build_explanation`・`check_summary`・`compare`・`verification_of`)で CR を一巡させる。2回流して、同じ結果になった(決定的)。

## (a) 7段ごとに、Devex が記録・出力できるもの

○ = できる / △ = 一部 / × = できない。左がベースライン(ステージ10)、右がステージ11。

| 段 | 前 | 後 | ステージ11 でできるようになったこと |
|---|---|---|---|
| 1. 受付 | × | ○ | 合意済みの版の中身から CR を作る。タイトル・内容・背景(出どころ・日付・メモ)・対象の要件と変更の種類・変更後の案・基準の版を持つ。時系列に「作成」が残る |
| 2. 整理(合意済みの仕様と比べる) | × | ○ | 合意済みの版(束)が、合意した時点の要件定義書・外部設計書・承認済みの段階を凍結して持つ。作成のフォームと説明書の2節が、「合意済みの文」と「変更後の案」を並べる |
| 3. 影響の確認 | △ | ○ | 合意の**前**に、基準の版から予測を出す(影響のタブ・API)。画面・API(文書の側)も入る。N2 では 6件で正解と一致。判断の時点で CR に保存する |
| 4. 変更の説明 | × | ○ | 5節の説明書(md)を決定的に組み立て、ダウンロードできる。任意の LLM の要約は、ID と数字を5節と照合し、人が確かめるまで出力に入れない |
| 5. 合意の確認 | × | ○ | 合意・却下の記録(相手・日時・メモ・理由)。新しい合意済みの版にも同じ記録を持たせ、CR の記録を初期値にできる |
| 6. 設計・計画への反映 | △ | ○ | CR を文書の再生成と段階の生成に渡す(指示に入る)。版に CR とモデル名を残し、印の出どころに `cr:N` を足す。予測と実際の印を比べる |
| 7. 変更後の検証 | △ | ○ | CR に付いた印がすべて確認済みで、文書の側の確認が済めば「検証済み」にできる。レビューを任意で結ぶ。検証済みの CR を新しい合意済みの版に入れる |

## (b) 後からたどれるか(完了の判断基準の4つの問い)

| 問い | 前 | 後 | 根拠 |
|---|---|---|---|
| 何を(変えたか) | △ | ○ | CR の対象(要件 ID・種類・案)と、基準の版の写しの合意済みの文。束は直せず消せないので、時間がたっても前の文が残る |
| なぜ(変えたか) | × | ○ | CR の内容と背景(出どころ・日付・メモ)。説明書の1節にも出る |
| 誰の合意で | × | ○ | CR の合意の記録(相手・日時・メモ・理由)と、入れた合意済みの版の記録。たどる記録の「合意」の行の日時 |
| どこに反映したか | △ | ○ | たどる記録が、作り直した文書の版・段階の生成・モデル名・検証・入れた版を指す。印の出どころの `cr:N` |

残る弱み(ステージ11 の範囲で、○ を崩さないもの):
- 文書の版は今も直近3件で巡回する。たどる記録は、消えた版を「(もう残っていない)」と出す(合意した文は束に残るので、「何を」は答えられる)。
- たどる記録の行には合意の相手が出ない(内容のタブの合意の記録にある)。E2E で確かめた。見せ方は画面確認で決める([89-4](../../textbook/Phase-89/Phase-89-4.md))。
- CR を渡して作り直した段階を承認したとき、新しく生まれた要素から先の印は CR に結ばれない(Phase 86 のユーザー決定)。N2 の材料では差分が要件1件なので、この漏れは出ない。

## (c) 影響の一覧(予測・反映の印・比較・検証)

`effect.py` の出力。CR-1(基準 B-1)・FR-005・内容の変更・案「参考資料のファイルを最大5件までアップロードできる。」

| 要素 | 置き場 | 予測 | 反映の印(出どころ) | 比較 | 検証の確認 | 理由(予測) |
|---|---|---|---|---|---|---|
| `api:POST /api/v1/projects` | 0 | ○ |  | 予測だけ(文書の側。印が付かない) | 文書の側の確認 | この要件を持つ |
| `screen:SCR-001` | 0 | ○ |  | 予測だけ(文書の側。印が付かない) | 文書の側の確認 | この要件を持つ |
| `fn:F-01` | 1 | ○ | doc:requirements・cr:1 | 一致 | 印の確認 | この要件を持つ |
| `proc:F-01` | 5 | ○ | doc:requirements・cr:1 | 一致 | 印の確認 | この処理に属する |
| `logic:services/project.py::ProjectService.create_project` | 6 | ○ | doc:requirements・cr:1 | 一致 | 印の確認 | この手順から呼ばれる |
| `unit:U-002` | 8 | ○ | doc:requirements・cr:1 | 一致 | 印の確認 | この設計を手順書で実装する |

- 予測 **6件**(正解の6件と一致。ベースラインと同じ)。反映の印 4件。文書の側の確認 2件。
- 比較: 一致 4件 / 予測だけ 2件(どちらも文書の側)/ 実際だけ 0件。
- ベースラインで「今の印は4件。画面と API は印が付かない」とした穴は、**文書の側の確認の一覧**で埋まった。予測の6件が、印の4件と確認の2件に分かれ、どちらも済むまで検証済みにできない。

**検証**:

| 時点 | 未確認の印 | 未確認の文書の側 | 検証済みにできるか |
|---|---|---|---|
| 反映の直後 | 4 | 2 | できない |
| 印と文書の側を確かめた後 | 0 | 0 | できる |

**説明書**:
- 5節(1. 変更の内容と背景 / 2. 対象の要件 / 3. 影響の一覧 / 4. 関わる未決事項 / 5. 影響を受ける作業単位とテストの数)がそろう。作業単位は `M-01-T02`。材料にテスト仕様書が無いので、テストは数えない。
- 要約の照合: 5節に合う要約は不一致 0件。取り違えた要約(「FR-050」「10件」「7件」)は、`FR-050` と `7` を拾った。`10` は拾わない(説明書の日付 `2026-10-19` に `10` があるため)。照合は「5節に出ない数字」を見るので、5節のどこかにある数字の取り違えは見逃す。人の確認を関門にしている理由である(Phase 84)。

**応答の大きさ**(UTF-8。申し送り「予測・説明書の応答の大きさ」):

| もの | バイト |
|---|---|
| 予測(`Prediction.to_dict`) | 1,667 |
| 説明書の md | 2,064 |
| 束の写し(文書2・段階8) | 50,974 |

予測と説明書は数 KB で、タブを開いたときに読む今の形で足りる。重いのは束の写しで、束の一覧はすでに写しの中身を読まない(Phase 88)。

## 画面で通した確かめ(偽の LLM の E2E)

[89-2](../../textbook/Phase-89/Phase-89-2.md) の spec で、詳細設計モードの文書から、B-1 → CR-1 の作成 → 説明書のダウンロード(5節)→ 説明済み → 合意 → 文書への反映(版2・モデル名)→ 文書の側の確認 → 検証済み → B-2 に入れる(合意の記録の初期値)→ たどる記録、までを1本で通した。既存の9件と合わせて **10件成功**(2回)。

## 判定

- 完了の判断基準(1件の CR が受付から再検証まで通り、4つの問いに答えられる)を満たす。7段はすべて ○(前は × 4・△ 3)、4つの問いもすべて ○(前は × 2・△ 2)。
