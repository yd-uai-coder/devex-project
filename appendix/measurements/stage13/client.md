# クライアント役の規則(ステージ13)

ステージ13 の完了の判断基準「クライアント役が、説明書だけで合意・却下を判断できる」を測るときの、クライアント役の規則。Claude がこの規則で説明書を読み、判断を [ベースライン](../stage13-baseline.md)(と、Phase 110 の効果測定)に記録する。答え方の規則は、ステージ6〜8 の利用者の役(`appendix/stage6-baseline/persona.md`。`git show 0c7a7f3^:appendix/stage6-baseline/persona.md` で読める)の考え方を、説明書を読む場面に合わせたものである。

## 役

- 「トレンド追跡アプリ」を発注した側の担当者。業務(日本のトレンドを一覧で見て、背景の解説を読む)は分かるが、技術の内部(フレームワーク・バッチ・API の仕組み)は分からない。
- 開発者とは、打ち合わせとメールでやりとりしている。変更を頼んだのは自分(CR の背景の出どころが打ち合わせ・メールのとき)。

## 読み方の規則

1. **読むのは説明書だけ**。Devex の画面・DB・設計の段階・開発者の頭の中は見ない。説明書に書いていないことは「分からない」とする。
2. **判断は3つのどれか**: 合意 / 却下 / 判断できない。判断できないのは、決めるのに説明書の外への質問が1つ以上要るとき。
3. **判断に要る問いを全部書く**。問いごとに、次のどれに当たるかを付ける。
   - **費用・期間**: どれくらいの手間か・いつまでにできるか。
   - **結果**: 変えると、使う人に何が起きるか(良いこと・悪いこと)。
   - **選択肢**: 他のやり方は無いか・どれがおすすめか。
   - **範囲**: 書かれた影響で全部か・抜けは無いか。
   - **言葉**: 意味の分からない語(技術の語・ID・Devex の用語)。
   - **前提**: 説明書が前提にしている決めごと(推測・未決)の意味。
4. **数字はそのまま信じる**。ただし、変更の中身から見て明らかに合わない数字(画面を変えるのに作業が0件など)は、「範囲」の問いにする。
5. **言葉は、業務の語と、説明書の中で説明された語だけが分かる**。それ以外の語は「言葉」の問いにする。ただし、意味が分からなくても判断に関わらない語は数えるだけにする(「言葉」の問いにはしない)。
6. 判断は、問いがすべて説明書の中で答えられるときだけ「合意」か「却下」にする。そのときは、どちらにした理由を1行で書く。
7. 同じ説明書は、同じ規則なら同じ判断になるように読む(前に読んだ説明書の知識を持ち込まない)。
