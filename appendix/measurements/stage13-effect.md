# ステージ13 の効果測定(Phase 110-1)

ステージ13(説明とすり合わせ)の効果を、[ベースライン](./stage13-baseline.md)(Phase 100-2)と同じ規則で測る。完了の判断基準は、マイルストーン14「クライアント役が、共有リンクの画面の説明書だけで、題材のすべての CR の合意・却下を、説明書の外への質問なしに決められる」。決定と経緯は [Phase 110-1](../../textbook/Phase-110/Phase-110-1.md)。

## 条件

- 題材: 開発環境のプロジェクト「トレンド追跡アプリ」(詳細設計モード)。
  - **CR-3・CR-4**(ベースラインと同じ。どちらも反映済み)。反映済みの CR には共有リンクを作れない(作れるのは下書き・説明済みだけ)ので、[`stage13/measure.py`](./stage13/measure.py) で今の説明書の md を書き出して読んだ。共有リンクの画面は同じ md を出す。
  - **CR-6**(新しい CR。選択肢つき)。CR-4 で表示は TOP20 になったが、取得(FR-001)と背景解説(FR-002)は10件のまま、という件数のずれを直す。基準は束 B-6。共有リンクの画面をログインせずに開いて読んだ。
- CR-6 の前に、開発者として段階を最新にした。初めは B-5 を基準に CR-5 を作ったが、段階7 の承認済みのタスクが CR-4 の前の処理 ID(F-04・F-05・F-09)を指したままで、作業単位・ファイル・テストが「0件(少なく出ることがある)」になった。段階6 を飛ばし、段階7 を CR-4 で作り直し、段階8 の手順書を作り直し、テスト仕様書を作り直して承認し、束 B-6 を作った。CR-5 は取り下げ、同じ中身の CR-6 を B-6 で作った(ユーザーの選択)。
- 案: 開発者(Claude)が LLM の下書き(Gemini 3.5 Flash-Lite)を取り込み、計画の中間の案を案3 として足した。おすすめは下書きのまま(案1)。
- クライアント役: Claude が [`stage13/client.md`](./stage13/client.md) の規則で読んだ(LLM の費用 0)。
- 書き出したもの: [`stage13/data/effect-explanations.json`](./stage13/data/effect-explanations.json)(CR-3・CR-4・CR-6 の md と案。2回流して同じ出力)、[`stage13/data/cr6-share-page.txt`](./stage13/data/cr6-share-page.txt)(CR-6 を読んだ時点の共有リンクの画面の文。説明済みのとき)。

## 結果

### 判断

| CR | 判断 | 判断に要る問い(説明書の中で答えが無い) | 残った疑問(判断には関わらない) |
|---|---|---|---|
| CR-3 | **判断できない** | 費用・期間(作業単位・ファイル・テストは「数えられない」で、説明書が「手間の見込みは、開発者に別に確かめてください」と書く) | なし |
| CR-4 | **判断できない** | 費用・期間(CR-3 と同じ) | 選択肢(矢印のほかの見せ方)・結果(「前回」はいつの取得か) |
| CR-6 | **合意(案1)** | なし | 結果(案1 で LLM の利用料がどれくらい増えるか)・結果(案1 の「システムへの影響範囲が広くなります」は使う人に何を意味するか)・選択肢(2節の「変更後の案」は案1 と同じ文で、案3 では FR-002 が変わらないことは3節を読むまで分からない) |

- **CR-6 を合意にした理由**: 頼んだ本人の困りごとは「11〜20位を押しても解説が出ない」(1節の背景のメモ)。これを直せるのは案1 だけで(案2 は表示を10件に戻し、案3 は11〜20位に「解説はありません」と出す)、手間は案ごとの規模の表(案1・案3 とも作業単位 5・ファイル 13)で分かる。利用料の増え方は、解説の生成が10件から20件になることまでは読めるので、判断に要る問いでなく残った疑問にした。予算が厳しいクライアントなら、判断に要る問い(結果)になりうる。
- **CR-3・CR-4 が判断できない理由**: どちらも、基準の束(B-3・B-4)の段階1 の処理が要件 ID を持たない古い版で、予測が処理にたどり着かない。説明書は「数えられない」とその理由を出し、確かめる先(開発者)を示すようになった。ベースラインの CR-3 は「影響0件・作業0件」を信じて合意にしたが、その0件は数えられなかった0件だった。
- **共有リンクで合意した**: クライアント役は、名前・コメント(利用料の増え方を後で教えてほしい)・案1 を選んで合意した。開発者の画面で、合意の記録の出どころが「共有リンク」になり、コメントに返信した。

### 選択肢

- CR-6 は3案。LLM の下書きは2案(すべて TOP20 / 表示を TOP10 に戻す)で、開発者が中間の案(取得は20件・解説は上位10件)を足した。案ごとの規模の表と、共有リンクの画面の案のカード(おすすめの印と理由)で選べた。

| 指標 | ベースライン | 効果測定 |

**マイルストーン14**: **達成**。CR-6(ステージ13 の流れで作った CR)は ○。CR-3・CR-4(古い束が基準の、反映済みの CR)は ×。ユーザーの決定で、題材を「ステージ13 の流れで作った CR」に読み替えた(CR。[`q_a.md`](../../textbook/q_a.md) の「Phase 110 開始時」)。CR-3・CR-4 は参考として残し、古い束を基準にした説明の扱いはステージ14 以降へ送る。

## 分かったこと

- 段階が最新の束を基準にすれば、規模は予測どおりに数えられ(CR-6 は反映の後の比較で 5・13・5 が一致)、クライアントは案ごとの規模と結果で選べた。
- 古い束が基準の CR は、説明書が正直に「数えられない」と出すようになった分、ベースラインより判断できなくなった(CR-3)。古い束のまま説明しないこと(束を作り直してから CR を作る)が運用の前提になる。
- 段階が古いだけで切れた参照(段階7 のタスクの処理 ID)は「0件(少なく出ることがある)」になり、「数えられない」と区別される。クライアントには0件に見える。
- 実 LLM は段階1 の作り直しで、取得と解説の2つのバッチ(F-32・F-33)を1つ(F-34)にまとめた。段階2 に「機能一覧に無い処理」の一覧(Phase 109)が出た。
- 実 LLM が利用者の `prev_id` を書いたかは、記録から分からない(版の model は付けた ID だけを持つ)。要件定義書の v13 で、利用者は U-001・U-002 を引き継ぎ、保護で合意の形に戻った。
