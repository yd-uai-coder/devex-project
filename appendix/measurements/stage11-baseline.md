今の Devex(ステージ10 の版)で、1件の変更要求(CR)を、受付から再検証まで、どこまで記録・出力でき、後からたどれるかを確かめたもの。ステージ11 の効果測定でも、同じシナリオと同じ表を使う。分析は [Phase 80-2](../../textbook/Phase-80/Phase-80-2.md) にある。

- 日時: 2026-10-19。本体は `main`(ステージ10 の版)。
- 外部の API・LLM は呼ばない(費用 0)。
- **材料**: [ステージ7の効果測定](stage7-effect.md)で書き出した、詳細設計モードの段階1〜8 と要件定義書・外部設計書の model(`appendix/stage7-effect/impact/data/detailed.json`)。Devex 自身を題材にした生成物である。2026-10-19 の整理(`0c7a7f3`)でリポジトリから消したので、スクリプトがその親のコミットから `git show` で読み出す。リポジトリには戻さない。

## シナリオ(N2)

[ステージ7のベースライン](stage7-baseline.md)の N2 と同じ変更を、クライアントからの変更要求として扱う。

- **要望**: 打ち合わせで、クライアントから「参考資料は 5件まで読み込めるようにしてほしい」と言われた。
- **対象**: 機能要件 FR-005
  - 合意済みの文: 「txt、md、pdf形式の参考資料を最大3件まで初期入力で読み込める。」
  - 変更後の案: 「参考資料のファイルを最大5件までアップロードできる。」
- **正解**(ステージ7で決めた。見直しが要る要素): 画面 SCR-001・API `POST /api/v1/projects`・処理 F-01・F-01 の手順・`ProjectService.create_project` の処理ロジック・作業単位 M-01-T02(本体のキーでは `unit:U-002`)の6件。

## 実行

```bash
PYTHONPATH=devex-api/backend uv run --project devex-api/backend \
    python appendix/measurements/stage11/measure.py
```

結果は標準出力に出る(下の (c) の表)。2回流して、同じ結果になった(決定的)。

## (a) 7段ごとに、今の Devex が記録・出力できるもの

○ = できる / △ = 一部 / × = できない。

| 段 | 判定 | 今の Devex でできること・できないこと |
|---|---|---|
| 1. 受付 | × | 変更要求を記録する場所が無い。チャットに「上限を5件に」と書くことはできるが、ヒアリングの続きとして扱われ、要求としての項目(背景・出どころ・対象)を持たない |
| 2. 整理(合意済みの仕様と比べる) | × | 合意済みの仕様が無い。文書の版は直近3件で巡回し、段階は1行を上書きするので、「合意した時点の FR-005」を後から取り出せない |
| 3. 影響の確認 | △ | 反映した**後**なら、印が出る(段階の4件。(c))。反映の**前**の予測は、関数(`impact_of`)はあるが、画面と API に無い |
| 4. 変更の説明 | × | 説明の出力が無い。影響と未決の観点は、開発者の画面の中にだけある |
| 5. 合意の確認 | × | クライアントとの合意を記録する場所が無い(段階の「承認」は開発者の操作で、相手・根拠を持たない) |
| 6. 設計・計画への反映 | △ | 再生成と、段階5・6・8 の部分再生成はできる。ただし、どの要求で作り直したかを版に残さない。生成したモデルも残らない |
| 7. 変更後の検証 | △ | 印の確認と設計レビューはできる。ただし、どの要求の後の検証かを結ぶ記録が無い |

## (b) 後からたどれるか(完了の判断基準の4つの問い)

| 問い | 判定 | 理由 |
|---|---|---|
| 何を(変えたか) | △ | 文書の版の差分と段階の印から、変わった要素は分かる。ただし、版は3件で消えるので、時間がたつと前の文が残らない |
| なぜ(変えたか) | × | 要求の内容と背景を残す場所が無い。チャットに書いても、変更と結ばれない |
| 誰の合意で | × | 合意の相手・日時・根拠の打ち合わせを残す場所が無い |
| どこに反映したか | △ | 再生成の後の版と印はあるが、要求との結び付きが無い。どの再生成がこの変更のためかは、時刻から推すしかない |

## (c) 影響の一覧(予測と、今の再生成の印)

| 要素 | 置き場 | 予測 | 今の印 | 理由(予測) |
|---|---|---|---|---|
| `api:POST /api/v1/projects` | 文書 | ○ | | この要件を持つ |
| `screen:SCR-001` | 文書 | ○ | | この要件を持つ |
| `fn:F-01` | 段階1 | ○ | ○ | この要件を持つ |
| `proc:F-01` | 段階5 | ○ | ○ | この処理に属する |
| `logic:services/project.py::ProjectService.create_project` | 段階6 | ○ | ○ | この手順から呼ばれる |
| `unit:U-002` | 段階8 | ○ | ○ | この設計を手順書で実装する |

- **予測**(合意の前。`impact_of` に `req:FR-005` を渡す): **6件**。正解の6件と一致した。
- **今の印**(反映の後。`diff_elements` → `marks_for`): **4件**。画面と API は、印が付かない。
  - 詳細設計モードでは、要件定義書と外部設計書を一度に作り直す。そのため、文書の側の要素は、印の置き場(段階)を持たない。
  - 画面と API が新しい要件に合っているかを確かめる手がかりが、今の画面には出ない。

## 判定

- 完了の判断基準(1件の CR が受付から再検証まで通り、4つの問いに答えられる)に対して、今の Devex は、7段のうち4段が ×、4つの問いのうち2つが × である。
- 影響の**予測**は、今の関数のままで正解と一致する。足りないのは、予測を合意の前に出す経路と、要求・合意・反映・検証を結ぶ記録である。これは、位置付け 12章の「新しく作るのは、主に合意と CR とその記録」と合う。
- ステージ11 の効果測定では、同じ材料と N2 で、(a)・(b) の表を埋め直す。(c) には、反映の後の実際の差分を足し、予測と並べる(ステージ11 の決定6)。
