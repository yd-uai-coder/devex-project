## 4つの方式

| 方式 | 示す範囲 |
|---|---|
| 今の仕組み | 全段階が承認済みの状態から変更を当て、`derive_states` が「古い」にした段階の、すべての要素。文書の変更は再生成(詳細設計モードは要件定義書と外部設計書を一度に作り直す)、段階の変更は「編集して承認し直した後」として当てる |
| グラフ(直接) | ID の辺を逆に1段だけたどった要素 |
| グラフ(全部) | ID の辺を逆にたどれるところまでたどった要素(推移閉包) |
| 処理を軸(試案) | 変更が届く処理(F-xx)を決め、その処理に属する要素(要約・CRUD・手順・作業単位と、その手順を呼ぶ処理ロジック・単位の手順書)と、変わった要素の直接の依存元を示す。共有されるモジュールからは広げない。グラフ(直接)と(全部)の結果を見てから足した案で、41-2 の診断の材料 |

**要素(グラフの節)**: 要件(FR/NFR/CON)・画面(SCR)・API(`endpoint_key`)・処理(F-xx)・処理の要約(段階2)・テーブルと CRUD のセル(段階3)・モジュール(段階4)・手順(段階5、処理ごと)・処理ロジック(段階6、モジュール + 関数)・作業単位・横断事項・リスク(段階7)・単位の手順書(段階8)。

**辺(A が B に依存する)**: 画面 → 要件、API → 画面・要件、処理 → 要件・画面・API(トリガー)、要約 → 処理、CRUD → 処理・テーブル、モジュール → 処理・モジュール(`depends_on`)、手順 → 処理・モジュール(呼び出し先)・テーブル(DB 欄)、処理ロジック → モジュール・手順(呼び出し名)、作業単位 → 処理・モジュール・作業単位、横断事項 → モジュール、単位の手順書 → 作業単位・モジュール・処理ロジック。どれも JSON と文書の表にある ID だけで作った(本文の文字列からは辺を作らない)。

**正解**: 変更の中身を読んで、「内容を直すか、直さなくてよいことを人が確かめる必要がある」要素を Claude が選んだ(`scenarios.py` に理由)。人の判断なので、ずれはありうる。数字は8件のシナリオでの概算として読む。

## 結果の要約

詳細は `results.md`。

| 方式 | 示した | 当たり(正解 39) | 過剰の割合 | 見落とし |
|---|---|---|---|---|
| 今の仕組み | 292 | 37 | 87% | 2 |
| グラフ(直接) | 26 | 18 | 31% | 21 |
| グラフ(全部) | 111 | 32 | 71% | 7 |
| 処理を軸(試案) | 51 | 29 | 43% | 10(うち S2 が6) |

**N1〜N4(試案の後に決めたシナリオ、正解 17)**:

| 方式 | 示した | 当たり | 過剰の割合 | 見落とし |
|---|---|---|---|---|
| 今の仕組み | 158 | 14 | 91% | 3 |
| グラフ(直接) | 7 | 5 | 29% | 12 |
| グラフ(全部) | 62 | 16 | 74% | 1 |
| 処理を軸(試案) | 25 | 14 | 44% | 3 |

- **試案は、後から決めたシナリオでも同じ傾向だった**(過剰 43% → 44%、S2 を除く見落とし 4/33 → 3/17)。見落としは、テーブルを読み書きするリポジトリ(N1)・入口の応答のスキーマ(N3)・簡易モードの単位の手順書(N4。簡易モードには処理の軸が無く、WBS のタスクから先へ広げない)。
- **今の仕組みは、ほぼすべてを示す**。文書の再生成で全段階が「古い」になり(S1・S2・S4)、段階の編集でも後ろの全段階が「古い」になる。見落としは少ないが、示した要素の 87% は見直し不要。どの要素を見ればよいかは分からない。
- 今の仕組みの見落としは2種類: 文書の中の要素(S1 の画面 SCR-002。文書は丸ごと作り直すので、要素の単位で示す仕組みが無い)と、**同じ段階の中の依存**(S7 の `api/routes/chats.py`。段階4の中のモジュールの依存は段階単位では見えない)。
- **グラフ(直接)は狭すぎる**: 要件の変更は処理(F-xx)までしか届かず、手順・処理ロジック・手順書は2段以上先にある(S1・S4)。
- **グラフ(全部)は広すぎる**: 共有のモジュール(`clients/ai.py`・`services/document.py`)と `depends_on` の連鎖を通って、別の処理の手順・処理ロジック・単位まで広がる(S1・S5)。過剰の割合は 71%。
- **処理を軸(試案)は中間に来る**: 過剰 43%・見落とし 10。見落としのうち6件は S2(辺が無い)。残りは、再試行を置く層(S1 の `clients/ai.py`)・入口の検証(S4 の `api/routes/chats.py`)のように、処理に共有されるモジュールの中で「どれを直すか」を決める判断で、ID だけでは決まらない。S6 はテーブルを2つの処理が使うので、両方の処理の要素を示して過剰が増える。試案は正解を見た後に作ったので、ステージ7の効果測定で新しいシナリオを足して確かめる。
- **ID の辺が無いところは、グラフでも届かない**:
  - S2: 非機能要件から下流への辺が無い(横断事項は要件ID を持たない。[Phase 38](../../textbook/Phase-38/Phase-38-introduction.md) で案2を採らなかった)。6件すべて見落とし。
  - S6: モジュールとテーブルの辺が無い(`repositories/document.py` の責務の文に「documents テーブル」とあるだけ)。ただし段階5の手順の行は、呼び出し先のモジュールと DB 欄(`documents C`)を同じ行に持つので、そこから導ける。
- **S3(「採用にする」)は、どの方式でも示すものが無く、それで正しい**。手順書の「非機能要件・制約」の表は出力のときに要件定義書の model から作るので、出どころは自動で変わる。
- **簡易モード(S8)**: 段階8の全単位(8)が「古い」。WBS の依存の連鎖をたどると後ろの単位まで広がる(依存は「先に終わっている必要がある」で、中身の依存ではない)。

## 位置で決まる ID

| ID | 数 | 保存されるか |
|---|---|---|
| 手順の行(F-xx#n) | 30 | 保存しない(出力のときに振る)。詳細設計書の出力に出る |
| 処理ロジックの表示 ID(L-NN) | 4 | 保存しない(出力のときに振る)。単位の手順書の出力に出る |
| 作業単位(M-xx-Tyy) | 5 | **段階8の JSON が単位の手順書のキーとして持つ**(14か所)。段階7でマイルストーン・タスクを並べ替えると、段階8の手順書が別の単位に付く |

変更の記録や影響の一覧が要素を ID で指すなら、手順の行・作業単位の ID は並べ替えでずれる。

## 補足(今の仕組みの挙動)

- 段階を編集すると、承認し直すまで後ろの段階は開かない(入力の承認済みの版が無い = `missing_inputs`)。このベースラインは承認し直した後の状態で数えた。
- 段階は版の履歴を持たない(今の `model` だけ)。何が変わったかの差分は、今の仕組みでは取れない。
