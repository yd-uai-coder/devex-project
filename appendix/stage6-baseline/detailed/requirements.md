# 1. 要件定義書

## 1.1 プロジェクトの目的・背景
### 1.1.1 解決したい課題
- システム開発の初期フェーズ（要件定義・外部設計・内部設計・実装計画）において、ドキュメント作成にかかる膨大な工数と時間がボトルネックとなっている。
- ヒアリングやドキュメントの品質、記述内容が担当者のスキルに依存しており、属人化が発生している。

### 1.1.2 目指すゴール
- AIとの対話型チャットによるヒアリングを通じて、高品質な設計書4種（要件定義、外部設計、内部設計、実装計画）を自動かつ体系的に生成する。
- ドキュメント作成工数の大幅な削減と、出力フォーマット・品質の標準化（属人化の排除）を実現する。

## 1.2 ターゲットユーザー・利用シーン
### 1.2.1 主なユーザー層
- システム開発の初期フェーズを担当するITエンジニア、プロジェクトマネージャー、ITコンサルタント、プロダクトマネージャー。

### 1.2.2 想定される使用シチュエーション
- 新規プロダクトの企画立ち上げ時、またはシステムのリプレイス検討時に、頭の中にあるアイデアや要件をAIとのチャットで壁打ち・整理し、速やかに設計書のドラフトを作成する。
- 作成された設計書の不足点をAIの自己診断と追加チャットによってブラッシュアップし、プロジェクトの初期ドキュメントとして活用する。

## 1.3 システム化の範囲（In Scope / Out of Scope）
### 1.3.1 今回開発する範囲（In Scope）
- **参考資料の読込**: 最大3件までの参考資料（txt / md / pdf）の初期アップロード・読込機能。
- **対話型ヒアリング**: AIが1つずつ質問して深掘りし、必要な観点が揃った段階で構造化サマリを提示する機能。
- **ユーザー承認・非同期生成**: 構造化サマリのユーザー承認後、「要件定義 → 外部設計 → 内部設計 → 実装計画」の順序で依存関係を考慮し、バックグラウンド非同期処理で設計書を一括生成する機能。
- **自己診断と再生成**: 生成後、AIが各文書の不足点を3段階（最重要 / 中程度 / 軽微）で自己診断して提示し、チャットによる追加回答を通じて設計書を再生成する機能（文書ごとにDBで版を管理し、直近3件を保持）。
- **プレビュー・出力**: 生成されたMarkdownのプレビュー表示、コピー、ダウンロード機能。
- **データ永続化**: ユーザー情報、チャット履歴、生成文書のPostgreSQLへの保存。

### 1.3.2 今回は開発しない範囲（Out of Scope）
- 生成された設計書履歴の閲覧・比較・復元を行う専用UI画面（Should機能として将来実装を検討）。
- PDFやWordなど、Markdown以外のフォーマットへの直接エクスポート機能（MVP時点ではコピーとMarkdownダウンロードのみ）。
- 外部プロジェクト管理ツール（Jira, Redmine, GitHub Issues等）との連携機能。

## 1.4 機能要件（MoSCoW優先度）
- **Must have（必須機能）**:
  - ユーザー認証・管理機能
  - 参考資料アップロード機能（txt/md/pdf、最大3件）
  - AI対話型ヒアリング機能（1問1答形式による深掘り）
  - 構造化サマリの提示とユーザー承認機能
  - バックグラウンド非同期による4種設計書の順次生成（要件定義 → 外部設計 → 内部設計 → 実装計画）
  - 生成されたMarkdownのプレビュー、コピー、ダウンロード機能
  - AIによる設計書の自己診断機能（3段階：最重要 / 中程度 / 軽微）
  - チャットを通じた追加指示による設計書の再生成機能（文書ごとに版管理、直近3件を保持）
  - PostgreSQLへのデータ永続化（ユーザー、チャット、履歴、ドキュメント）
- **Should have（推奨機能）**:
  - 過去の版（直近3件）の履歴閲覧・比較・復元UI画面
- **Could have（あると良い機能）**:
  - カスタムテンプレートの登録・選択機能
  - チーム間でのプロジェクト共有・共同編集機能
- **Won't have（見送り機能）**:
  - 音声入力によるチャット対話機能
  - 外部プロジェクト管理ツール連携

## 1.5 非機能要件
### 1.5.1 パフォーマンス・応答性
- チャットの応答は対話型としてストレスのない速度（数秒以内）で返却されること。
- 設計書の生成処理は時間がかかるため、バックグラウンドの非同期処理として実行し、ユーザーは進捗ステータスを確認できること。

### 1.5.2 セキュリティ・権限管理
- すべての通信はHTTPSにより暗号化されること。
- ユーザーごとのデータ分離（マルチテナント的な論理分離）を行界し、他ユーザーのプロジェクトや設計書にアクセスできないこと。
- アップロードされる参考資料および生成された設計書の情報漏洩を防ぐため、適切なアクセス制御とストレージ保護を実施すること。

### 1.5.3 運用・保守・拡張性
- 将来的なAIモデルの変更（LLMのバージョンアップ等）に柔軟に対応できる抽象化されたAIクライアント層を持つこと。
- データベースのバックアップが容易に行える構成とすること。

## 1.6 制約条件・前提条件
### 1.6.1 技術スタックの制約
- データベースには PostgreSQL を使用すること。
- ドキュメント形式は Markdown を基本とすること。
- 非同期処理を安全に実行するためのキューイング機構（例: Redis / Celery / BullMQ 等）を利用すること。

### 1.6.2 予算・スケジュールの前提
- MVP（実用最小限の製品）として、まずはコア機能（ヒアリング・非同期生成・自己診断・再生成・版管理）の迅速なリリースを最優先とする。

## 1.7 補足資料：システム構造・フロー図

### 1.7.1 全体システム構成図（イメージ）
```text
[ ユーザー (Web Browser) ]
       │
       ▼ HTTPS
[ Web Application / API Server ] 
  ├── AI Chat Controller (ヒアリング・対話管理)
  ├── Async Job Processor (バックグラウンド非同期生成)
  └── Document Manager (プレビュー・コピー・DL・版管理)
       │                         │
       ▼ API                     ▼ SQL
[ LLM Provider (AI) ]     [ PostgreSQL (DB) ]
                           - ユーザー
                           - チャット履歴
                           - 参考資料
                           - 生成文書 (版管理:直近3件)
```

### 1.7.2 設計書生成の処理フロー
```text
[ユーザー] ──(参考資料UP & アイデア入力)──> [AIヒアリング]
                                                │ (1問1答で深掘り)
                                                ▼
[ユーザー承認] <──(構造化サマリ提示)──────────────┘
       │
       ▼ (承認トリガー)
[バックグラウンド非同期処理開始]
  ├── 1. 要件定義書 生成
  ├── 2. 外部設計書 生成 (要件定義を入力)
  ├── 3. 内部設計書 生成 (外部設計を入力)
  └── 4. 実装計画書 生成 (内部設計を入力)
       │
       ▼
[プレビュー・自己診断提示 (最重要/中程度/軽微)]
       │
       ├─ (追加修正あり) ──> [チャットで対話・再生成 (版作成:直近3件保持)]
       └─ (完了) ────────> [コピー / ダウンロード]
```
