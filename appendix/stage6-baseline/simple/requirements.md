# 1. 要件定義書

## 1.1 プロジェクトの目的・背景
- **解決したい課題**: システム開発初期フェーズにおけるドキュメント作成の工数増大と、作成プロセスの属人化。
- **目指すゴール**: AIとの対話型チャットによるヒアリングを通じて、高品質な「要件定義」「外部設計」「内部設計」「実装計画」の4種のMarkdown設計書を自動生成し、初期フェーズの生産性を劇的に向上させる。

## 1.2 ターゲットユーザー・利用シーン
- **主なユーザー層**: システム開発の起案者、プロジェクトマネージャー、システムエンジニア
- **想定される使用シチュエーション**:
  - 新規プロジェクトの立ち上げ時に、アイデアや要望を整理し、網羅的な設計書を迅速に作成したい時。
  - 参考資料（txt, md, pdf）をもとに、AIに初期アイデアをインプットして対話を始めたい時。

## 1.3 システム化の範囲（In Scope / Out of Scope）
- **今回開発する範囲（In Scope）**:
  - メールアドレスとパスワードによるJWT認証機能（アクセストークン30分、リフレッシュトークン14日・HttpOnly Cookie）
  - 参考資料の初期アップロード（最大3件、txt / md / pdf）
  - AIとの対話型チャットによるヒアリング、およびAI主導による構造化サマリ提示・承認フロー
  - 4種のMarkdown設計書（要件定義、外部設計、内部設計、実装計画）の一括生成（Gemini Flash-Lite利用）
  - 生成された設計書に対するAIの自己診断機能（最重要・中程度・軽微の3段階で不足点を提示）
  - 生成されたMarkdownのプレビュー、クリップボードへのコピー、ファイルダウンロード
  - ユーザー、チャット履歴、生成文書（直近3件の版管理含む）の PostgreSQL への保存
  - LLMの上限超過エラー時の再送促し・再生成制御
- **今回は開発しない範囲（Out of Scope）**:
  - Google等の外部SNS認証
  - 特定の文書を指定した部分修正（チャットの追加回答による再生成で対応）
  - 履歴の閲覧・比較・復元画面（Should要件として将来対応）

## 1.4 機能要件（MoSCoW優先度）
- **Must have（必須機能）**:
  - ユーザー登録・ログイン機能（メール/パスワード、JWT）
  - 参考資料アップロード機能（最大3件、txt/md/pdf対応）
  - 対話型ヒアリングチャット機能（AI主導の質問・深掘り）
  - 構造化サマリの提示とユーザー承認フロー
  - 4種Markdown設計書の一括生成・再生成機能
  - 4種Markdown設計書の版管理（DBにて直近3件を保持）
  - 生成文書のAI自己診断機能（最重要・中程度・軽微の3段階）
  - プレビュー、コピー、ダウンロード機能
  - エラーハンドリング（LLM上限超過時のメッセージ表示と再送・再生成制御）
- **Should have（推奨機能）**:
  - 過去のチャット履歴・生成文書の閲覧・比較・復元画面
- **Could have（あると良い機能）**:
  - マークダウンのエクスポート形式追加（PDF、Word等）
- **Won't have（見送り機能）**:
  - リアルタイム共同編集機能
  - 文書の部分的個別修正機能

## 1.5 非機能要件
### 1.5.1 パフォーマンス・応答性
- チャットの通常応答速度: 3秒以内を目指す（LLMの応答速度に依存）
- 設計書一括生成処理: 非同期処理を活用し、タイムアウトを防ぐUI設計とする。

### 1.5.2 セキュリティ・権限管理
- パスワードはハッシュ化して保存。
- 認証トークンはアクセストークン（30分）とリフレッシュトークン（14日 / HttpOnly Cookie）でセキュアに管理。
- ユーザーごとのデータ分離（他のユーザーのチャット履歴や設計書にアクセスできない認可制御）。

### 1.5.3 運用・保守・拡張性
- LLMプロバイダとして Gemini Flash-Lite の無料枠を活用し、APIエラー・レートリミット発生時は適切な例外処理を行う。
- 将来的な機能拡張（部分修正機能や履歴比較画面の追加）を見据えたモジュール分割設計。

## 1.6 制約条件・前提条件
- **技術スタック**:
  - バックエンド / フロントエンド: Webアプリケーションフレームワーク（適宜選定）
  - データベース: PostgreSQL
  - LLM: Gemini Flash-Lite (無料枠)
- **予算・スケジュール**:
  - MVPリリースを最優先とし、必要最小限の機能に絞って開発を行う。

## 1.7 補足資料：システム構造図・画面構成等

### 認証・セッション管理フロー
```text
[Client]                      [Backend API]                  [PostgreSQL]
   |                               |                              |
   |-- 1. ログインリクエスト ------->|                              |
   |    (Email/Password)           |-- 2. ユーザー検証 ---------->|
   |                               |<-- ユーザー情報返却 ----------|
   |                               |                              |
   |                               |-- 3. JWT発行(Access: 30m) ---|
   |<-- 4. AccessToken(Body) ------|                              |
   |       Refresh(HttpOnly Cookie)|                              |
```

### 画面遷移フロー（MVP）
```text
[ログイン / 新規登録画面]
         │ (認証成功)
         ▼
[ホーム画面 / ダッシュボード]
         │
         ├─► [参考資料アップロード (最大3件)]
         │
         ▼
[対話型ヒアリングチャット画面]
         │ (AI質問 ⇄ ユーザー回答)
         │ (網羅後: 構造化サマリ提示 ＆ ユーザー承認)
         ▼
[設計書一括生成・プレビュー画面]
         ├─► [要件定義 (版管理: 直近3件)]
         ├─► [外部設計 (版管理: 直近3件)]
         ├─► [内部設計 (版管理: 直近3件)]
         ├─► [実装計画 (版管理: 直近3件)]
         └─► [AI自己診断結果表示 (3段階)]
               │
               ├─► プレビュー / コピー / ダウンロード
               └─► チャットに戻って追加回答 ➔ 再生成
```
