システム概要：Devex: AI との対話型チャットでユーザーのアイデアや要望をヒアリングし、「要件定義」「外部設計」「内部設計」「実装計画」の4種の Markdown 設計書を自動生成する Web アプリ。システム開発の初期フェーズで、ドキュメント作成の工数と属人化を減らしたい。

実現したい事：- チャットでヒアリングし、4種の設計書を一括生成する(MVP)
- 生成後に AI が各文書の不足点を3段階(最重要/中程度/軽微)で自己診断して提示する
- 生成した Markdown をプレビュー・コピー・ダウンロードできる
- 参考資料(txt/md/pdf、最大3件)を初期入力で読み込める
- ユーザー・チャット履歴・生成文書を PostgreSQL に保存する

### 最重要（実装着手に支障）
指摘事項はありません。アーキテクチャ、API仕様、データモデルの整合性が取れており、すぐに実装を開始できる状態です。

### 中程度（後続の設計判断に影響）
1. **参考資料（PDF等）のテキスト抽出処理の定義不足**
   - **箇所**: `DocumentsService` / `3.3 処理別データフロー (DF-02)`
   - **内容**: アップロードされた `.pdf`, `.txt`, `.md` のファイル内容を、LLMのプロンプトにどのように読み込ませるか（テキストパースや文字数制限、チャンク分割等の処理方針）が記載されていません。PDFのテキスト抽出ライブラリの選定や、容量・トークン上限超過時の対策を明確にする必要があります。
2. **Gemini Flash-Liteの「出力トークン数」および「並行生成」の制約に対する設計**
   - **箇所**: `SpecificationsService` / `3.3 処理別データフロー (DF-04)`
   - **内容**: 4種の設計書（要件定義、外部設計、内部設計、実装計画）を「一括生成」すると記載されていますが、LLMの1回あたりの最大出力トークン数（Max Output Tokens）の制限に抵触する可能性が高いです。1回のAPIコールで4種すべてを出力させるのか、あるいは並行/直列で4回APIコールを行うのか、プロンプト設計の方針を補足してください。
3. **版管理（直近3件）のローテーション仕様**
   - **箇所**: `specifications` テーブル / `3.3 モジュール一覧`
   - **内容**: 設計書を再生成した際、古いバージョンがどのように削除・あるいは保持されるのか（例: 4件目作成時に最古のバージョンを物理削除するトリガー、または論理削除等）のデータ操作仕様が抜けています。

### 軽微（運用上の補足）
1. **ファイルの物理ストレージ先の定義**
   - **箇所**: `documents` テーブル（`file_path` カラム）
   - **内容**: アップロードされたファイルがサーバーのローカルストレージ（Dockerボリューム等）に保存されるのか、あるいはS3などのオブジェクトストレージに保存されるのかが明記されていません（MVPであればローカルストレージ想定の旨を注記するとより親切です）。
2. **認証トークンの有効期限の不一致**
   - **箇所**: `1.3 システム化の範囲` と `2.3 SCR-001`
   - **内容**: 概要では「アクセストークン30分、リフレッシュトークン14日」と明確ですが、フロントエンド側でアクセストークン期限切れ時のリフレッシュ処理（Silent Refresh等）をどのようにハンドリングするかの言及があると、実装時の手戻りが防げます。
