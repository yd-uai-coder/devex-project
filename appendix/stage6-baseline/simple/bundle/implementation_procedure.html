実装前提・制約

技術スタック・開発環境(実装計画書 4.3・内部設計書 3.1)

### 1. 開発に必要なツール・技術スタック - **言語・ランタイム**: Node.js (LTS), TypeScript - **フレームワーク**: NestJS (バックエンド), Next.js App Router (フロントエンド) - **データベース**: PostgreSQL (Docker環境でローカル起動) - **外部AI**: Gemini Flash-Lite API ### 2. リポジトリ構成 - モノレポ構成またはバックエンド/フロントエンド分離リポジトリ（ここではモノレポを想定） ```text / ├── backend/ # NestJSアプリケーション ├── frontend/ # Next.jsアプリケーション ├── docker-compose.yml # PostgreSQL等のローカルインフラ └── README.md ``` ### 3. 自動テスト・CI/CD方針 - **テスト方針**: バックエンドはJestを用いたサービス層の単体テストを実施。フロントエンドは主要コンポーネントの表示確認。 - **CI/CD方針**: GitHub Actionsを利用し、mainブランチへのプルリクエスト時にビルドおよびテストを自動実行する。デプロイはVercel（フロント）およびRender/AWS（バックエンド）へ自動連携する。 - **フロントエンド**: - **選定理由**: 開発スピードとインタラクティブなUI構築（マークダウンプレビューやチャットインターフェース）のしやすさを考慮し、React / Next.js（App Router）を採用する。 - **構成方針**: コンポーネント指向に基づき、画面ごとのUIコンポーネントとAPIクライアント層を分離。状態管理にはReact Query (TanStack Query)を利用してサーバーサイドの状態を効率的にキャッシュ・同期する。 - **バックエンド**: - **選定理由**: 型安全性、非同期処理の堅牢性、AI連携ライブラリの豊富さを考慮し、Node.js (TypeScript) + Express または NestJS を採用する。ここでは保守性とモジュール構造の明確さから NestJS を前提とする。 - **構成方針**: クリーンアーキテクチャ（レイヤードアーキテクチャ）を採用し、Controller（プレゼンテーション層）、Service（ビジネスロジック層）、Repository（データアクセス層）に明確に分離する。 - **データベース**: - **選定理由**: リレーショナルデータの整合性（ユーザー、プロジェクト、チャット履歴、設計書版管理）とPostgreSQLの堅牢性を評価。 - **構成方針**: ORMには Prisma または TypeORM を利用し、スキーマ定義から型安全なクエリ操作を実現する。 - **インフラ**: - **選定理由**: MVPの迅速なリリースと運用コスト削減のため、Vercel（フロントエンド）および Render / AWS (ECS/RDS) などのマネージドサービスを想定する。

実装ルール(内部設計書 3.3・3.4より)

  • モジュールは、内部設計書のモジュール一覧の依存先にだけ依存する(層を飛び越さない)。
  • 3.4 **共通エラーレスポンス形式**:
  • 3.4 全てのAPIエラー時は以下のJSON形式でレスポンスを返却する。
  • 3.4 **例外検知・ログ出力方針**:
  • 3.4 **構造化ロギング**: Winston または NestJS 標準 Logger を使用し、JSON形式で標準出力へログを出力する。
  • 3.4 **LLMエラーハンドリング**: Gemini APIのレートリミット（429 Too Many Requests）や上限超過エラー発生時は、例外フィルターで検知し、クライアントへ専用のエラーコード（例: `LLM_RATE_LIMIT_EXCEEDED`）と再試行促しメッセージを返却する。
  • 3.4 **セキュリティ監査ログ**: 認証失敗、不正なリフレッシュトークン利用試行、権限外リソースアクセス試行は、警告レベル（WARN）以上で記録する。
