# 詳細設計モードの構想(要件整理メモ)

2026-09-30、Phase 13 完了後の相談で出た構想の整理メモである。位置づけは Stage 3 の [`stage3-requirements-organization.md`](./stage3-requirements-organization.md) と同じで、`docs/`・`devex-api`・`devex-ui` はまだ変えていない。

**具体的な再設計は別セッションで行う。トリガーは「詳細設計モードの再設計を開始する」。** 再設計の最初に、このメモと [`textbook/q_a.md`](../textbook/q_a.md) の「Phase 13完了後 ── コンポーネント図の粒度から、詳細設計モードの構想へ」を読むこと。

## 1. 背景

- Phase 13 の完了後、ユーザーから指摘があった。コンポーネント図の粒度が `api-service-model` 程度と粗く、ファイル単位のモジュールの責務(例: `app/services/doc_generator_service.py`: ヒアリング完了後の4種ドキュメント一括生成+自己診断)が分からない。責務を把握してから DFD を見て、機能ごとの処理概要を理解したい、という意図である。
- 原因は図ではなく入力の側にある。
  - 内部設計書のプロンプト(3.3 節)は「分割方針」と「ディレクトリ構成」しか求めておらず、ファイル単位の責務は文書に書かれない。
  - コンポーネント図の生成プロンプトは「ディレクトリ構成に現れるモジュール」を拾い、「入力に無い要素を創作しない」ことを求めている。
  - 図1枚の要素数の上限は 30 である。
- いったん確定した方針があった。モジュール一覧の表の追加、機能ごとのコンポーネント部分図、DFD との連携、13b の前に新 Phase を挟む、の4点である。しかしユーザーが「一般的な実務と照らして再検討したい」として保留にし、公開資料を調べた(2章)。機能ごとの部分図は、調査の結果、撤回した(実務では機能の切り口は実行時のビューで扱うため)。

## 2. 実務の資料から分かったこと

| 観点 | 実務の形 | 出典 |
|---|---|---|
| 構造 | 階層になった「概観図+含まれる部品の表(名前・責務・コードの場所)」。重要な部分だけ書く | [arc42 Building Block View](https://docs.arc42.org/section-5/) |
| 構造の粒度 | コンポーネント図は責務の単位。コード(クラス・ファイル)の図は手で描かない(IDE 等で生成する) | [C4 Component](https://c4model.com/diagrams/component)、[C4 Code](https://c4model.com/diagrams/code) |
| 振る舞い | 番号付きの手順・アクティビティ図・シーケンス図のどれでもよい。代表的なシナリオだけ書く | [arc42 Runtime View](https://docs.arc42.org/section-6/) |
| 日本の詳細設計 | シーケンス図(モジュール間のやり取りと順序)、CRUD 図(機能 × テーブル)、テーブル定義、モジュール仕様 | [詳細設計の成果物一覧(ysinc)](https://ysinc.co.jp/blog/detailed-design-deliverables/) |
| DFD | 要件定義〜基本設計で使うのが一般的。プログラム名・テーブル名まで書く物理 DFD は設計段階でも作る。詳細な処理ロジックはフローチャート等で書く | [Lucidchart: データフロー図](https://www.lucidchart.com/pages/ja/tutorial/dfd-data-flow-diagram) |

## 3. ユーザーが示した前提

- **実務にできるだけ準拠する。** 重要な部分だけ書く、構造は「図+責務表」、機能ごとの振る舞いは実行時のビュー、CRUD 図、DFD は基本設計寄り、詳細なロジックはフローチャート等。
- **自動コーディングの水準はあくまで理想形。** 「図から自動でコードを書いても、設計者のイメージから大きく外れない」は要件ではない。まず目指すのは、人がコーディングするのに十分な資料をシステムが作ることで、AI がその作業を代行するのは理想形である。
- **シーケンス図に当たるものは欲しい。** ただし、まずは番号付きの手順から始める。番号と処理名を並べるだけでは情報が足りない。
- **見本(9章)は全体として了承済み。**
  - 番号付き手順の列(No / 呼び出し元 → 呼び出し先 / 渡すデータ / 処理内容 / 結果 / DB 操作 / 分岐・例外)は、基本は見本どおりにする。
  - 「5 主要処理の手順 → 6 処理ロジックの詳細(複雑な関数だけ、実装者が迷わない粒度)」の流れで確定した。

## 4. モード構成(案)

| モード | 流れ | 位置づけ |
|---|---|---|
| 概要モード(現行) | チャット → 4文書を一括生成 | 概要の md を作るツール。そのまま残す |
| 詳細設計モード(増設) | チャット → 要件定義・外部設計(現行と同じ) → 段階1〜6を順に作って承認 → 実装計画 | 各段階の成果物(意味モデルと表)を人が承認してから次の段階の入力にする。文書は承認済みの成果物から組み立てる |

## 5. 詳細設計書の章構成(案)

章と段階は1対1に対応する。正本は各段階の意味モデル(JSON)で、文書はそこから組み立てる表示である。

1. 機能(処理)一覧 ── 処理ID / 名称 / 種別 / トリガー / 関連画面 / 機能グループ / 概要(段階1)
2. データフロー ── 機能グループごとの DFD、データ辞書、処理概要表(入力 / 処理 / 出力)(段階2)
3. データモデル ── ER、テーブル定義、CRUD 図(段階3)
4. ソフトウェア構造 ── 構成図(層)、モジュール一覧(パス / 層 / 責務 / 主な依存先 / 関わる処理)(段階4)
5. 主要処理の手順 ── 選んだ処理だけ。列は No / 呼び出し元 → 呼び出し先 / 渡すデータ / 処理内容 / 結果 / DB 操作 / 分岐・例外。分岐はサブ番号で表す(段階5)
6. 処理ロジックの詳細 ── 任意。選んだ関数のモジュール仕様(シグネチャ / 引数 / 戻り値 / 例外 / 事前・事後条件)と擬似フロー(段階6)
7. 横断事項 ── 例外と HTTP、認証、トランザクション、ログ

## 6. 段階表(案)

| 段階 | 入力 | 作るもの | 実務での対応 | AI の役割 |
|---|---|---|---|---|
| 0 | チャット | 要件定義・外部設計 | 要件定義・基本設計(外部) | 現行と同じ |
| 1 | 外部設計の API 一覧・画面 | 機能(処理)一覧(変わらない処理ID) | 機能一覧 | 下書き → 人が確定 |
| 2 | 1 + 要件 | 機能グループごとの DFD、データ辞書、処理概要表 | 基本設計 | 下書き → 人がレビュー |
| 3 | 2 のデータストア・データ辞書 | ER、テーブル定義、CRUD 図 | 詳細設計(DB・CRUD) | ER は下書き。CRUD は DFD から決まる部分を決定的に作り、残り(C/U の区別など)を AI が下書きする |
| 4 | 1〜3 + 技術スタック | 構成図(層)、モジュール一覧 | 方式設計 / arc42 Level 1・2 | 下書き → 人がレビュー |
| 5 | 4 + 2 | 選んだ処理の番号付き手順 | 実行時のビュー | 人が対象を選び、AI が下書き |
| 6(任意) | 5 | 選んだ関数のモジュール仕様・擬似フロー | 詳細設計(モジュール仕様・フローチャート) | 同上 |
| 7 | 全体 | 実装計画 | — | 現行と同じ |

## 7. Claude の所感

- **良い点**
  - 実務の工程に沿う。
  - 1回の入力が小さくなり、各段階で人が承認するので、生成の品質が上がりやすい。
  - Stage 3 の資産の大部分を再利用できる。意味モデル・検証・レイアウトエンジン・draw.io / SVG 出力・レビュー画面・承認の流れ・データ辞書・陳腐化の判定である。
  - 段階の依存関係が、そのまま陳腐化の伝播の道筋になる。
  - M9b(図の手直しを散文へ戻す AI の修正案)は、文書を意味モデルから組み立てる形にすると、大部分が不要になるか、ずっと軽くなる。
- **懸念**
  - 規模が大きい。ロードマップの再計画(Phase 13b・14 の見直し)が要る。プロジェクトのモードと、段階の状態・承認を持つ DB、段階を進める画面(ウィザード)が要る。Stage 3 の中で行うか、Stage 4 として切るかの判断が要る。
  - シーケンス図は未解決。D7 で Could にしており、React Flow では表示が難しい。まずは番号付きの手順の表で始める。
  - Phase 13 のアンカーによる差し込み(M9a)は、概要モードでは引き続き使える。詳細設計モードでは章の組み立てに置き換わる。
  - 実装の前に、Phase 7 のような設計フェーズ(仕様診断 #28・docs の改訂・段階の定義)を別セッション(#18)で置くべきである。
  - 「重要な部分だけ書く」原則と、これまでの「全エンドポイントの DFD」とは方針が違う。枚数(Gemini の無料枠)も含めて、再設計で整理する。

## 8. 未決事項(再設計で決める)

1. 詳細設計モードを Stage 3 に含めるか、Stage 4 として切るか。Phase 13b(M9b)と Phase 14 をどう扱うか。
2. 段階の状態と承認の持ち方(DB・API・画面)。前の段階を直したときの、後ろの段階の扱い(陳腐化の表示だけか、作り直しか)。
3. 機能グループの決め方(API のリソース名で決定的に決めるか、段階1で人が決めるか)。
4. CRUD 図のうち、DFD から決まらない部分(C と U の区別など)の決め方。
5. 番号付きの手順の列の確定。シーケンス図に進むかどうかの判断基準。
6. 概要モードの内部設計書との関係。プロンプトの改訂(モジュール一覧の表の追加など)を概要モードにも入れるか。
7. 教材の Phase 番号の振り方。
8. **(再設計で Claude が提案する)** 5章「主要処理の手順」が複数あるとき、視覚的にどう表現すれば見やすいか。
9. **(再設計で Claude が提案する)** 6章の処理ロジックの詳細が、5章のどの処理のどの手順に紐づくかを明確にすること。あわせて、その紐づきを視覚的にどう表現するか。
