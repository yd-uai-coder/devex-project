# AI 設計レビューの見本(Phase 51)

ステージ8で Devex が示す「AI 設計レビュー」の結果の形を、md で書いた見本。画面の見せ方は devex-ui のデモ `/design-review-demo`(`src/features/design-review/demo/`)にある。テスト仕様書の見本は [test-spec.md](./test-spec.md)。決定は [Phase 51-2](../../textbook/Phase-51/Phase-51-2.md)、測り方は [ベースライン](../stage8-baseline/README.md)。

題材は Devex 自身で、ベースラインの追加測定 (e) と同じ生成物(`stage7-effect/hearing/detailed-3`・`simple-2`)を使う。指摘の中身は、Sonnet 5.5 が実際に返したもの(`stage8-baseline/runs/gates_sonnet/`)を縮めて、引用(evidence)と観点のキーを足した。

## 示し方の規則

| 項目 | 規則 |
|---|---|
| 役割 | 生成は今のモデル(Gemini)。レビューは別のモデル(Sonnet)が指摘だけを返し、設計は書き換えない |
| 区切り | 簡易 = 4文書の生成の後(自動)。詳細 = 要件・外部の生成の後(自動)、段階6・7の承認の後(ボタン)。上流の文書も渡す。再生成の後は同じ位置で流れ直す |
| 未レビューの印 | 文書がそろっているのにレビューしていない区切りに印を付ける。手順書を生成するときに知らせる(止めない) |
| 入力 | 文書 + ヒアリングの観点の表 + 決定的な検証の指摘(既知として渡し、繰り返させない) |
| 指摘の項目 | 重要度(#28 の3段階)・原因(ヒアリング / 設計 / 不整合)・対象(文書の中の ID・名前)・観点のキー(原因がヒアリングのとき)・問題・引用・理由・改善案 |
| 採否 | 人が指摘ごとに 採用 / 却下 / 保留 を付ける。結果は文書の版に結ぶ |
| 差し戻し | 採用した設計・不整合の指摘は、再生成の指示に入れる(直すのは生成のモデル。範囲は今の再生成の単位)。採用したヒアリングの指摘は、観点を「未決」に戻してチャットで聞き直す |
| オン・オフ | superuser だけが切り替えられる(初期値オフ)。オフ・superuser 以外は、今の自己診断を出す |
| 失敗したとき | レビューの失敗を記録し、自己診断に切り替える。「もう一度レビュー」で流し直せる |
| 対象外 | 実装手順書とテスト仕様書(決定的な検証で見る)。測定で、手順書に固有の欠陥はレビューで 1〜2/8 しか当たらなかった |

## 例1: 詳細設計モード ── 要件・外部の生成の後(自動)

**レビューの回**: 要件定義書 第1版・外部設計書 第1版 / Sonnet 5.5 / 指摘 5件(最重要 2・中程度 2・軽微 1)

| # | 重要度 | 原因 | 対象 | 問題 | 引用 | 改善案 | 判断 |
|---|---|---|---|---|---|---|---|
| 1 | 最重要 | 設計 | SCR-004・`POST /api/v1/projects/{id}/summary/approve` | 構造化サマリを作る・取得する API と、「ヒアリング完了」「修正依頼」に当たる API が無い | SCR-004 構造化サマリ確認画面 … 修正依頼ボタン、承認ボタン | ヒアリング完了(サマリ生成)・サマリ取得・修正依頼の API を足す | 採用 |
| 2 | 最重要 | 設計 | `POST …/summary/approve`・NFR-003 | 数分かかる生成を同期の 200 で受けるだけで、進捗・失敗・再生成を取る API が無い | 200 OK (生成開始) / 500 生成失敗 | 非同期のジョブにし、状態を取る API と文書単位の再生成の API を設ける | 採用 |
| 3 | 中程度 | ヒアリング | FR-001・観点 セキュリティ(`security`) | セキュリティの観点が「ログインを MVP に入れる」だけで、他人のプロジェクトを見られないこと・トークンの扱いが要件に無い | セキュリティ / AI の提案を採用 / ログインをMVPに入れる | 本人以外の閲覧の可否、トークンの期限、パスワード再設定の要否を聞き直す | 採用 |
| 4 | 中程度 | ヒアリング | NFR-008・観点 不正利用(`abuse`) | 回数上限の値と単位が決まっていない | NFR-008 … 回数上限を設けて不正利用を防ぐ | 各操作の上限(回数・期間・IP かユーザーか)を確認する | 保留 |
| 5 | 軽微 | 不整合 | FR-005・SCR-002 | 4文書の生成がプロジェクト一覧の画面に結ばれている | SCR-002 … FR-002, FR-005 | FR-005 の対応画面を SCR-004・SCR-005 に直す | 却下 |

**差し戻し**

再生成の指示(採用した設計・不整合の指摘だけ):

```text
次のレビューの指摘を反映して、設計書を作り直してください。指摘に無い部分は変えないでください。
1. [最重要] SCR-004, POST /api/v1/projects/{id}/summary/approve: 構造化サマリを作る・取得する API と、「ヒアリング完了」「修正依頼」に当たる API が無い。 → ヒアリング完了(サマリ生成)・サマリ取得・修正依頼の API を追加する。
2. [最重要] POST /api/v1/projects/{id}/summary/approve, NFR-003: 数分かかる4文書の生成を同期の 200 で受けるだけで、進捗・失敗・再生成を取る API が無い。 → 生成を非同期のジョブにし、状態を取る API と文書単位の再生成の API を設ける。
```

ヒアリングの観点(採用したヒアリングの指摘):

| 観点 | 前 | 後 |
|---|---|---|
| セキュリティ | AI の提案を採用: ログインをMVPに入れる | **未決に戻した** |
| 不正利用 | ユーザーが決定 | そのまま(指摘は保留) |

チャットでの聞き直し(AI の最初の問いかけ):「セキュリティ」について確認させてください: セキュリティの観点が「ログインを MVP に入れる」だけで、他人のプロジェクトを見られないこと・トークンの扱いが要件に無い。

聞き直して観点が決まったら、要件・外部を再生成し、同じ区切りでレビューが流れ直す。

## 例2: 詳細設計モード ── 段階6の承認の後(ボタン)

**レビューの回**: 要件定義書 第2版・外部設計書 第2版・詳細設計書(段階1〜6 の承認済みの写し) / 指摘 3件(抜粋)

| # | 重要度 | 原因 | 対象 | 問題 | 引用 | 改善案 |
|---|---|---|---|---|---|---|
| 1 | 最重要 | 設計 | テーブル projects・F-03・F-04 | projects に持ち主(user_id)の列が無く、手順に持ち主の確認が無い | F-03 手順4 / `ProjectRepository.find_all_by_user_id` / projects R | projects に user_id を足し、{id} を取る処理の手順に持ち主の確認を入れる |
| 2 | 最重要 | 設計 | テーブル documents・summaries・F-07・F-08 | 生成した4文書・版・自己診断の保存先が無い | documents / 参考資料テキストデータ・ファイルテーブル / id, project_id, content | 生成文書の表(種別・版番号・本文)と自己診断の表を分ける |
| 3 | 中程度 | 設計 | F-05・F-07・`LLMClient.invoke_chat` | チャットと生成の LLM 呼び出しに、会話の履歴と参考資料が渡っていない | F-05 手順4 / invoke_chat / プロジェクトID、チャットメッセージ | 手順に chats と documents の読み出しを足し、LLM の入力に含める |

採用した指摘の再生成は、今の部分再生成の単位(段階3のデータモデル・段階5・6)で行う。詳細設計書の段階を承認し直すと、この区切りは「未レビュー」に戻る。

## 例3: 簡易モード ── 4文書の生成の後(自動)

| # | 重要度 | 原因 | 対象 | 問題 |
|---|---|---|---|---|
| 1 | 最重要 | 設計 | `POST /api/v1/chat/messages`・DF-4 | チャット送信の本文が message だけで、どのプロジェクトのチャットかを特定できない |
| 2 | 最重要 | 不整合 | NFR-006・`POST /api/v1/documents/generate` | チャットと生成の API に持ち主の確認と 401/403/404 が無い |
| 3 | 中程度 | ヒアリング | 観点 体制・期間(`schedule`) | 体制・期間が未決のままで、実装計画書に期間が無い |
| 4 | 中程度 | 設計 | 実装計画書 4.2・SCR-001〜003 | 実装計画にフロントエンドの画面のタスクが無い |

指摘3を採用しても、観点はもともと「未決」なので状態は変わらない。チャットで聞き直す問いかけだけが出る。

## 例4: オフ・失敗のとき

| 状況 | 出るもの |
|---|---|
| superuser 以外 / 設定がオフ | 今の自己診断(生成のモデルの自由文。チャットに出る) |
| レビューのモデルが使えない(障害・キー無し・上限) | レビューの失敗を記録し、自己診断に切り替える。区切りの状態は「失敗」。「もう一度レビュー」で流し直せる |
| 1日の回数上限に達した | 自動の区切りはレビューせずに自己診断を出し、区切りは「未レビュー」のまま。翌日にボタンで流せる |
