# Devex の生成文書(ゴール3の突き合わせ用)

CLAUDE.md「プロジェクトのゴール」3 の突き合わせに使った、Devex の**実際の生成物**です。2026-10-06 に、ローカルの devex-api(`stage4` ブランチ、97375db)を実際の LLM(`.env` の `GEMINI_MODEL=gemini-3.5-flash-lite`)で動かし、題材を Devex 自身にして、簡易ドキュメントモードと詳細設計モードの両方で生成しました。

- 突き合わせの結果: [`textbook/appendix/goal3-comparison.md`](../../textbook/appendix/goal3-comparison.md)
- 手で起こした見本([`detailed-design-devex/`](../detailed-design-devex/README.md))とは違い、ここにある文書・段階の model はすべて AI の出力です。人(AI のエージェントが利用者の役をした)が加えたものは、下の「人が入力・操作したもの」にすべて書きました。

## 人が入力・操作したもの

生成された文書・段階の model の**中身は一切書き換えていない**。人の手が入ったのは、次の入力・選択・承認だけ。

### 共通

- 初期入力: `input/overview.txt`・`input/goals.txt`。中身は [`README.md`](../../README.md)・[`docs/requirements.md`](../../docs/requirements.md) のステージ1(MVP)の範囲から要約した。
- 回答の根拠も同じく `README.md`・`docs/requirements.md`(技術スタックとデプロイは `devex-api`/`devex-ui` の実際の構成)。AI の質問に答えるだけで、生成物の見出し構成などは指示していない。

### 簡易ドキュメントモード

| 順 | 操作 | 内容 |
|---|---|---|
| 1 | プロジェクト作成 | `mode=simple`。AI の最初の質問は「対話の形式・テンプレート・認証とバージョン管理」 |
| 2 | 発言 `m1.txt` | 対話の形式(AI 主導・5観点で完了判定)・テンプレート(固定、選択は Should)・認証と版管理の範囲 |
| 3 | 発言 `m2.txt` | 想定ユーザーと場面、対象システムの技術スタックはヒアリングで決めること、Devex 自体の技術スタック・非機能・対象外 |
| 4 | 発言 `m3.txt` | サマリの承認と「前の文書を入力に逐次生成」の補足。この時点で完了判定が `is_sufficient=true` |
| 5 | `POST /generate` | 4文書と自己診断を生成(約40秒)。生成物は無修正 |

### 詳細設計モード

| 順 | 操作 | 内容 |
|---|---|---|
| 1 | プロジェクト作成 | `mode=detailed`、初期入力は簡易モードと同じ。AI の最初の質問は簡易モードと違った(修正しながらの対話か・並列か逐次か・再編集の可否) |
| 2 | 発言 `d1.txt` | 対話の形式・逐次生成・再生成と版管理・認証・テンプレート(`m1` とほぼ同じ内容を、質問に合わせて並べ替えた) |
| 3 | 発言 `d2.txt` | ホスティング(VPS)・LLM(Gemini Flash-Lite)・参考資料の保存方針(テキストだけ保存)、想定ユーザー、技術スタック・非機能・対象外 |
| 4 | 発言 `d3.txt` | 開発体制(個人・2〜3か月)と着手の順(認証と DB → ヒアリング → 生成と自己診断 → 画面 → デプロイ)。`is_sufficient=true` |
| 5 | `POST /generate` | 要件定義・外部設計の2文書を生成。無修正 |
| 6 | 段階1〜4 | それぞれ AI の下書きを生成し、**無修正で承認**。段階3・4の前に、ER 図・コンポーネント図を自動レイアウトして**無修正で承認**した(承認しないと段階を承認できないため) |
| 7 | 段階2 の DFD | **DFD を描く機能グループを選ばなかった**(画面では人が選ぶ操作)。そのため DFD・データ辞書は無く、段階3の CRUD 図も空になった |
| 8 | 段階5 | 手順を書く処理として **F-07(チャットを送る)・F-08(承認して生成をトリガー)** を選んだ(選んだ理由の欄は空のまま保存し、AI が下書きで埋めた)。下書きは無修正で承認 |
| 9 | 段階6 | 詳細を書く関数として、段階5の手順から **`services/ai_service.py` の `AIservice.stream_chat`** を選んだ(段階6は中身が無いと承認できないため、1つだけ選んだ)。下書きは無修正で承認 |
| 10 | 段階7 | 横断事項と実装計画を生成し、無修正で承認 |
| 11 | zip の取得 | `GET /design-stages/document` |

## 調査の結果と対応

生成の過程で気づいた Devex の挙動を調べ、ユーザーの判断で本体を直した(2026-10-06)。要約は [`goal3-comparison.md`](../../textbook/appendix/goal3-comparison.md) 8節。

### ヒアリングの AI と、生成のボタンのずれ

- **最初に見えたこと**: 簡易モードで、AI がサマリを出して「確定してよいか」と尋ね、承認の後にはチャットの中で要件定義書を書き始めた(`simple/chat_history.txt`)。
- **ユーザーの推測と、調べた結果**: ユーザーは「承認ボタンではなくチャットで返したために起きたのでは」と推測した。半分は当たっていた。私の3回目の発言(`input/m3.txt`)が、チャットで生成を頼んでいた。一方で、2回目の回答の時点では、利用者の発言が3回未満なのでボタンが出ない(`_MIN_USER_TURNS_FOR_COMPLETION = 3`)。そのため、画面の操作どおりでも、AI に確定を求められてチャットで答えることになる。
- **ユーザーの再検証で分かったこと**: 確認したい点がまだ残っているのに「ヒアリング内容の確認」が出て、生成できてしまう。チャットを続けると、後から AI がサマリを出す。ボタンは、そのサマリの時点で押したい。
- **原因**: 完了判定(AI の返信の後に、画面が GET で別に呼ぶ LLM)と、ヒアリングの AI が互いを知らずに動いていた。判定は「十分」と言い、AI はまだ質問を続ける。逆に、AI がチャットで確定を求めても、判定はまだ「足りない」ことがある。ヒアリングのプロンプトにも「文書をチャットに書かない」という指示が無かった。
- **対応**: 発言のたびに、先に判定して、その結果で返信を決める。十分なら、判定のサマリを返信にして、同時にボタンを出す。足りなければ、不足点を AI に渡して聞かせる。判定は `projects.hearing_check` に保存し、GET はそれを返す。AI には、確定の確認・サマリ・設計書の本文をチャットに書かないよう指示した。
- **確認**: 修正後に同じ題材でもう一度ヒアリングした(`recheck/chat_history.txt`。発言は `input/m1.txt`・`input/r2.txt`・`input/m2.txt`。`r2.txt` は、AI の質問が1回目と違ったので書き足した参考資料の扱いへの回答)。1・2回目の返信は質問で、判定は「足りない」。3回目の返信がサマリになり、その時点で初めて判定が「十分」になった。
  - 残る点: 2回目の返信で AI が聞いた自己診断の扱いには、3回目の発言で答えていない。それでも判定は「十分」になった。判定の厳しさは LLM 次第である。ただし、サマリとボタンは同時に出るので、足りなければチャットで続けられる。

### プロジェクト名

- **原因**: title をシステム概要(最大200文字)から作っていた。詳細設計書・実装計画の H1 がとても長くなった。
- **対応**(ユーザーの決定): 作成フォームに「プロジェクト名」(必須・前後の空白を除いて1〜40文字)を足した。空白だけ・41文字は 400(`INVALID_PROJECT_NAME`)。以前のプロジェクトの title はそのまま。
- **画面確認での注意**: 修正前に開いていたタブでは欄が出ず、送信すると 422(「Field required」)になった。再読み込み(Shift+F5)で直る。本番の反映でも同じなので、[`devex-api/OPERATIONS.md`](../../devex-api/OPERATIONS.md) 10.1節に書いた。

### 簡易モードの WBS の番号の重複

- **原因**: 実装計画書のプロンプトは `- [ ] タスク内容` のチェックボックスを指示するが、番号は指示していない。LLM が自分で番号を振り、区分をまたいで間違えた(フロントエンドの先頭が「2.2」)。お手本の `docs/implementation_plan.md` 自体も番号なしのチェックボックスである。
- **対応**: タスクに番号を付けないよう、プロンプトで指示した。

### DFD を描かずに段階2・3を承認できる

- **原因**: 段階3の ER は、段階2の DFD のデータストアとデータ辞書から下書きする。DFD を1枚も描かないと入力が空になり、プロンプトの「入力に書かれていない業務のテーブルを創作しない」に従って、ER のテーブルが0件になった(`detailed/bundle/diagrams/er.svg` は空)。テーブル0件の検証が無かったので、そのまま承認できた。
- **対応**: 段階2に警告 `NO_DFD_GROUPS`(DFD を描くグループが無い。人が選ぶ原則は変えないのでエラーにはしない)、段階3にエラー `ER_EMPTY`(ER にテーブルが無い)を足した。このプロジェクトでは、段階2に警告、段階3にエラーが出ることを確かめた。

### 想定どおりのもの

- 生成された設計は、実際の Devex と違う(例: 生成のトリガーが `POST /projects/{id}/approve`、モジュール名が `ai_service.py`)。ヒアリングで API の形まで伝えていないので、想定どおり。
