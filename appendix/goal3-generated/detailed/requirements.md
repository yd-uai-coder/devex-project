# 1. 要件定義書

## 1.1 プロジェクトの目的・背景
- **解決したい課題**: 
  - システム開発の初期フェーズ（要件定義〜実装計画）におけるドキュメント作成の莫大な工数と、作成者のスキルや経験に依存する「属人化」の解消。
- **目指すゴール**: 
  - AIとの対話型チャットによるヒアリングを通じて、高品質な4種の設計書（要件定義・外部設計・内部設計・実装計画）を自動生成し、初期フェーズの立ち上げを劇的に効率化するWebアプリケーション（Devex）の構築。

## 1.2 ターゲットユーザー・利用シーン
- **主なユーザー層**:
  - システムエンジニア、ITコンサルタント、プロジェクトマネージャー
  - 個人開発者、スタートアップの創業者
- **想定される使用シチュエーション**:
  - 新規プロジェクトの立ち上げ時に、頭の中にあるアイデアや要件をAIとの対話で整理したい時
  - クライアントからのヒアリング内容や参考資料を元に、初期ドキュメント（4種の設計書）を素早く作成したい時

## 1.3 システム化の範囲（In Scope / Out of Scope）
- **今回開発する範囲（In Scope）**:
  - メール・パスワードによるJWT認証機能（アクセストークン30分、リフレッシュトークン14日・HttpOnly Cookie）
  - 参考資料（txt/md/pdf、最大3件）の読み込み・テキスト抽出機能（PDFはGeminiのファイル理解機能を利用）
  - AI（LangGraph）主導による対話型ヒアリング機能（SSEによるストリーミング応答、5つの必須観点ごとの深掘り・構造化サマリ、承認フロー）
  - 逐次・非同期による4種の設計書自動生成処理（要件定義 → 外部設計 → 内部設計 → 実装計画、バックグラウンド処理）
  - AIによる設計書の自己診断機能（不足点を最重要・中程度・軽微の3段階で提示）
  - 生成されたMarkdownのプレビュー、コピー、ダウンロード機能
  - PostgreSQLへのユーザー、プロジェクト、チャット履歴、生成文書（直近3件のバージョン保持）の保存
- **今回は開発しない範囲（Out of Scope）**:
  - 設計書からのコード自動生成
  - Jira・Notion等の外部ツールへの連携
  - マルチテナントの高度な権限管理
  - 音声入力機能
  - 複数ユーザーによる同時編集機能
  - テンプレートの選択機能（MVPでは固定の見出し構成）

## 1.4 機能要件（MoSCoW優先度）
- **Must have（必須機能）**: 
  - ユーザー認証機能（JWT認証、サインアップ・ログイン・ログアウト）
  - プロジェクト作成・参考資料アップロード機能（txt/md/pdf、最大3件）
  - 対話型ヒアリングチャット機能（LangGraph制御、SSEストリーミング、5観点の構造化サマリと承認フロー）
  - 4種の設計書（要件定義・外部設計・内部設計・実装計画）の逐次・非同期生成機能
  - 設計書の自己診断機能（最重要・中程度・軽微の3段階判定）
  - 設計書のプレビュー、コピー、ダウンロード機能
  - チャット履歴および生成文書のバージョン管理（直近3件保持、DB保存）
- **Should have（推奨機能）**: 
  - 過去のチャット履歴・生成文書の閲覧・比較・復元画面
  - テンプレート選択機能
- **Could have（あると良い機能）**: 
  - 生成文書のエクスポート形式追加（PDF、Wordなど）
- **Won't have（見送り機能）**: 
  - 外部サービス連携（Jira/Notion等）、音声入力、同時編集機能

## 1.5 非機能要件
### ### 1.5.1 パフォーマンス・応答性
- チャットの応答はServer-Sent Events (SSE) を用いてリアルタイムにストリーミング配信する。
- 重い処理となる4種の設計書の一括・逐次生成はバックグラウンドの非同期処理として実行し、HTTPのタイムアウトを回避する。

### ### 1.5.2 セキュリティ・権限管理
- パスワードはハッシュ化して保存する。
- 認証にはJWT（JSON Web Token）を使用し、アクセストークンの有効期限は30分、リフレッシュトークンの有効期限は14日とする。リフレッシュトークンはHttpOnly Cookieに格納する。
- レート制限（Rate Limiting）とトークン失効管理にRedisを使用する。

### ### 1.5.3 運用・保守・拡張性
- LLMの無料枠上限超えなどのエラーに対して、適切なエラーハンドリングとユーザー通知を実装する。
- Docker Composeによるコンテナ化を行い、環境差異を排除した運用性・保守性を確保する。
- フロントエンドにおけるアクセシビリティ（フォームのラベル関連付け、キーボード操作対応など）を担保する。

## 1.6 制約条件・前提条件
### ### 1.6.1 技術スタックの制約
- **フロントエンド**: Next.js (App Router) + Tamagui
- **バックエンド**: FastAPI + LangChain / LangGraph (Python 3.13)
- **データベース**: PostgreSQL
- **キャッシュ / 制限**: Redis
- **AIモデル**: Gemini Flash-Lite (無料枠想定)
- **インフラ / デプロイ**: VPS, Docker Compose, Nginx, GitHub Actions (mainブランチpushによる自動デプロイ)

### ### 1.6.2 スケジュール・体制の前提
- 開発体制：個人開発
- 開発期間：約2〜3ヶ月でのMVPリリースを想定

   [ Nginx ]
       │
