システム概要：Devex: AI との対話型チャットでユーザーのアイデアや要望をヒアリングし、「要件定義」「外部設計」「内部設計」「実装計画」の4種の Markdown 設計書を自動生成する Web アプリ。システム開発の初期フェーズで、ドキュメント作成の工数と属人化を減らしたい。

実現したい事：- チャットでヒアリングし、4種の設計書を一括生成する(MVP)
- 生成後に AI が各文書の不足点を3段階(最重要/中程度/軽微)で自己診断して提示する
- 生成した Markdown をプレビュー・コピー・ダウンロードできる
- 参考資料(txt/md/pdf、最大3件)を初期入力で読み込める
- ユーザー・チャット履歴・生成文書を PostgreSQL に保存する

対話フローは、AI 側が主導して質問する形です。初期入力(システム概要・実現したい事・参考資料)を読んだ AI が、不足している観点を1つずつ質問して深掘りし、ユーザーは回答や補足・修正を都度返します。目的・ターゲットユーザー・主要機能・非機能要件・制約の5つがそろったら AI が構造化サマリを出し、ユーザーの承認を得てから生成に進みます。

生成は逐次です。「要件定義 → 外部設計 → 内部設計 → 実装計画」の順に、後ろの文書は前の確定済みの文書を入力にして一貫性を保ちます。全体はバックグラウンドの非同期処理にして、HTTP のタイムアウトを避けます。

生成後は、チャットで追加の回答をして再生成できます。文書ごとに DB でバージョンを増やし、直近3件を保持します(履歴の閲覧・比較・復元の画面は Should)。認証は MVP に含め、メールとパスワードの JWT 認証(アクセストークン30分・リフレッシュトークン14日、リフレッシュは HttpOnly Cookie)です。テンプレートは MVP では固定の見出し構成で、テンプレートの選択は Should です。

1. ホスティングは VPS です。Docker Compose で backend・PostgreSQL・Redis を動かし、nginx を通して公開します。GitHub Actions で main への push をきっかけに自動デプロイします。
2. LLM は Gemini Flash-Lite(無料枠想定)です。無料枠の上限を超えたときのエラーをエラーハンドリングに組み込みます。
3. 参考資料は元ファイルを保存しません。txt/md はそのままテキストとして読み、PDF は Gemini のファイル理解でテキスト化して、抽出したテキストだけを DB に保存します。

想定ユーザーは、システムエンジニア・IT コンサルタント・プロジェクトマネージャーと、個人開発者・スタートアップの創業者です。新規プロジェクトの立ち上げや、クライアントのヒアリング内容から初期ドキュメントを素早く作りたい場面で使います。

Devex 自体の技術スタック: フロントエンドは Next.js(App Router)+ Tamagui、バックエンドは FastAPI + LangChain/LangGraph(Python 3.13)、DB は PostgreSQL、レート制限とトークン失効に Redis。
非機能: チャットはストリーミング(SSE)で返す。フォームのラベル関連付けやキーボード操作などのアクセシビリティに対応する。
対象外: 設計書からのコード自動生成、Jira・Notion などへの連携、マルチテナントの権限管理、音声入力、複数人の同時編集。

### 最重要（実装着手に支障）

1. **バックエンド非同期処理の方式とクライアント通知の不整合**
   - **内容**: 要件定義書の付録フローおよび外部設計書において「バックエンドの非同期処理・逐次生成」と記載されていますが、フロントエンドからバックエンドへの進捗通知・完了検知の方式が明確ではありません（SCR-006の仕様に「ポーリングまたはWebSocket/SSEで監視」と曖昧な記載があります）。
   - **対策**: FastAPI側でCeleryなどのタスクキューやBackgroundTasksをどう使うか、またフロントエンドが生成完了を検知する具体的なプロトコル（SSEの維持、あるいはロングポーリングの間隔など）を外部設計書または内部設計書で確定させてください。
2. **AI（LangGraph）のセッション管理・中断復旧の仕様不足**
   - **内容**: LangGraphを用いた対話型ヒアリングにおいて、ユーザーが途中でブラウザをリロードしたり、別画面に遷移して戻ってきた場合のステート（グラフの状態）の保持・復元方法が定義されていません。
   - **対策**: チャットのステートをDB（PostgreSQL）にどのように永続化し、再接続時にどこから復元するのかの設計方針を明記してください。
3. **PDFファイルアップロードのハンドリングとサイズ制限の矛盾**
   - **内容**: 最大3件・各10MBのファイルをアップロードする際、フロントエンドからバックエンドへ直接マルチパートで送信するのか、あるいは署名付きURL等を用いて直接ストレージ等に保存するのかのデータフローが抜けています。特にGeminiのファイル理解機能へ渡す際の一時保存先や処理フローを定義してください。

---

### 中程度（後続の設計判断に影響）

1. **データベースのバージョン管理仕様の詳細化**
   - **内容**: 「直近3件のバージョン保持」とありますが、これは「プロジェクト単位」「設計書の種類（4種）単位」のどちらで3件なのか、またバージョンアップのトリガー（再生成時、手動保存時など）が明確ではありません。
   - **対策**: バージョン管理のエンティティ関係（ER図の前提）に影響するため、どのタイミングで新しいバージョンレコードが作成されるかを定義してください。
2. **認証トークンの有効期限とUXの仕様**
   - **内容**: アクセストークン30分、リフレッシュトークン14日とありますが、アクセストークン失効時のサイレントリフレッシュ（フロントエンドでの自動再取得処理）の有無や、リフレッシュトークンも切れた場合のハンドリング（ログイン画面への強制遷移など）が定義されていません。
   - **対策**: フロントエンドのインターセプター等によるトークンリフレッシュの挙動を追記してください。
3. **自己診断機能の実行タイミングとコスト管理**
   - **内容**: 4種の設計書生成後に自己診断が走る仕様ですが、これは自動的にバックグラウンドで一括実行されるのか、ユーザーがSCR-006でボタンを押して手動実行するのかが、文章によって混在して見えます（「バックグラウンド処理」「自己診断を実行・再評価ボタン」）。
   - **対策**: 自己診断は生成プロセスの最後尾に自動付与されるのか、ユーザーのオンデマンド実行なのかを統一してください。

---

### 軽微（運用上の補足）

1. **エラーハンドリング時のユーザー体験（UI）の定義**
   - **内容**: LLMの無料枠上限超え（Rate Limit等）やタイムアウト発生時のエラーメッセージ表示方針やリトライ導線について、非機能要件に言及はありますが画面上の挙動が未定義です。
   - **対策**: エラー発生時のトースト通知や専用エラー画面への遷移など、大まかな方針を補足しておくと実装がスムーズになります。
2. **Markdownダウンロード時のファイル命名規約**
   - **内容**: SCR-006の「Markdownダウンロード」機能において、ダウンロードされるファイルの命名規則（例: `requirements_projectID_v1.md` など）の指定がありません。
   - **対策**: 運用上の軽微な点ですが、命名規則を軽く定めておくと親切です。
