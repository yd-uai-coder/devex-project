# 4. 実装計画書

## 4.1 開発フェーズ分割・マイルストーン
- **フェーズ1（MVP / 必須機能）** ── 【Must have】
  - ユーザー認証機能（メール/パスワード登録・ログイン、JWT管理、HttpOnly Cookie、Redisトークン失効管理）
  - 参考資料アップロード・読み込み機能（txt/md/pdf、最大3件）
  - AI主導型ヒアリングチャット機能（SSEストリーミング、5観点の自動判定とサマリ提示）
  - 4種設計書の一括順次生成機能（バックグラウンド非同期処理、要件定義→外部設計→内部設計→実装計画）
  - AI自己診断機能（不足点の3段階評価提示）
  - 設計書の閲覧（プレビュー）、コピー、Markdownダウンロード機能
  - データ永続化とバージョン管理（PostgreSQL、チャット履歴・設計書、直近3件保持）
  - レート制限（Redis）

- **フェーズ2（拡張機能）** ── 【Should have / Could have】
  - プロンプトテンプレートの選択機能（用途別のテンプレート切り替え）
  - 設計書履歴の比較・復元画面
  - 生成された設計書のセクション単位の再生成・編集機能

## 4.3 開発環境・CI/CD・事前準備事項

### 4.3.1 開発ツール・リポジトリ構成
- **リポジトリ構成**:
  ```text
  project-root/
  ├── backend/           # FastAPI (Python 3.13)
  ├── frontend/          # Next.js (App Router + Tamagui)
  ├── nginx/             # Nginx設定
  └── docker-compose.yml # 開発・本番用コンテナ定義
  ```
- **開発ツール**: Docker, Docker Compose, Git, VS Code (Python / TypeScript 拡張)

### 4.3.2 自動テスト・CI/CD方針
- **CI/CD方針**: 
  - GitHub Actionsを利用し、PR作成時にフロントエンドのビルドチェック・リント、バックエンドのpytestを自動実行する。
  - VPSへのデプロイは、mainブランチへのマージをトリガーとするか、手動によるSSH経由のDockerコンテナ再ビルド・起動スクリプト実行により行う。

## 4.4 想定リスクと対策（トレードオフ・後回し候補）

### **リスク1: Gemini Flash-Lite無料枠のレートリミット（429 Too Many Requests）超過**
- *対策*: 
  - バックエンド側でAPI呼び出しの指数バックオフ（Exponential Backoff）リトライ機構を実装する。
  - Redisを用いたレート制限により、ユーザーごとの過剰なリクエストを事前に制御する。
  - 無料枠超過時は、ユーザーに対してHTTP 503および「混み合っています。しばらくお待ちください」の親切なメッセージをトースト通知する。

### **リスク2: 4種設計書の連続生成におけるタイムアウト・処理失敗**
- *対策*: 
  - 4文書の一括生成処理は同期的なHTTPレスポンスではなく、CeleryまたはFastAPIの `BackgroundTasks` を用いた完全な非同期バックグラウンドワーカーとして実行する。
  - 進捗ステータスをデータベース (`projects.status`) およびSSE/ポーリングでフロントエンドに通知し、ユーザーが画面を離れても後から確認できるようにする。

### **リスク3: 納期・予算超過時のトレードオフ策（機能削減・代替手段案）**
- *対策*: 
  - スケジュールがひっ迫した場合は、**Should have**（プロンプトテンプレート選択、履歴比較・復元画面）および**Could have**（セクション単位の再生成・編集）を完全にスコープ外（見送り）とし、必須機能（Must have）の品質担保にリソースを集中させる。
  - バージョン管理の直近3件保持について実装が複雑化する場合、最新1件の保存のみに仕様を縮小し、工数を削減する。
