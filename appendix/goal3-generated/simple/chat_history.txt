# 要件定義書：Devex（AI駆動型設計書ジェネレーター）

## 1. 目的・背景
システム開発の初期フェーズ（要件定義〜実装計画）におけるドキュメント作成の工数削減と属人化の排除。AIとの対話を通じてアイデアを構造化し、高品質な設計書ドラフトを素早く作成する。

## 2. ターゲットユーザー
- システムエンジニア、ITコンサルタント、プロジェクトマネージャー（新規PJの立ち上げ、クライアントヒアリングからのドラフト作成）
- 個人開発者、スタートアップ創業者（アイデアの構造化）

## 3. 主要機能（MVPスコープ）
1. **AI主導型ヒアリングチャット**
   - 初期入力（概要、実現したいこと、参考資料最大3件）を元に、AIが不足観点（目的・ターゲット・主要機能・非機能・制約）を1つずつ質問し深掘り。
   - 5つの観点がそろった時点で構造化サマリを提示し、ユーザー承認後に生成へ移行。
   - チャット応答はSSEによるストリーミング出力。
2. **4種設計書の一括自動生成（非同期処理）**
   - 順序: 要件定義 → 外部設計 → 内部設計 → 実装計画（前の文書を入力に含め、一貫性を担保）。
   - 固定の見出し構成を採用。
3. **AI自己診断機能**
   - 生成された設計書の不足点を3段階（最重要 / 中程度 / 軽微）で診断・提示。
4. **ドキュメント管理・操作**
   - プレビュー、コピー、Markdownダウンロード。
   - DB（PostgreSQL）によるユーザー、チャット履歴、設計書の保存（直近3件のバージョン管理含む）。
5. **認証機能**
   - メール・パスワードによるJWT認証（アクセストークン30分、リフレッシュトークン14日 / HttpOnly Cookie）。

- **バックエンド**: FastAPI + LangChain / LangGraph (Python 3.13)

- **インフラ**: Docker Compose, VPS + nginx

### 最重要（実装着手に支障）
1. **参考資料のストレージ保存先の定義不足**
   - 「外部設計書 2.5.1」などで参考資料（最大10MB、最大3件）の受け付けが定義されていますが、内部設計書のテーブル定義 (`reference_files` の `file_path`) において、**ローカルファイルシステムに保存するのか、S3等のオブジェクトストレージに保存するのか、あるいはDBのバイナリ（Bytea）として保存するのか**の記載がありません。Docker環境での永続化設計（ボリュームマウント等）に直結するため、保存先を明確にしてください。
2. **AI自己診断結果のデータ構造の定義不足**
   - 内部設計書の `documents` テーブルに `diagnostics JSONB` が定義されていますが、このJSONに格納されるデータのスキーマ（例: `[{ "level": "critical", "message": "..." }]` のような構造）が明記されていません。フロントエンド（`SCR-008`）での表示実装やAIエージェントの出力形式を確定するために、JSONの構造定義（TypeScriptの型またはPydanticスキーマレベル）を追加してください。
3. **非同期生成処理の進捗確認方法の矛盾**
   - 要件定義・外部設計ではバックグラウンド非同期処理として `SCR-007`（生成待ち画面）への遷移が定義されていますが、バックエンド側でそれをどのような仕組みでフロントエンドに通知するのか（SSE、Websocket、またはクライアントからのポーリング）が、API一覧やデータフローに明記されていません。実装方式を確定させてください。

### 中程度（後続の設計判断に影響）
1. **JWTリフレッシュフローの具体的手順の不足**
   - 認証機能として「アクセストークン30分、リフレッシュトークン14日・HttpOnly Cookie」と明記されていますが、アクセストークン期限切れ時のフロントエンド側の自動リフレッシュ処理（Axios/Fetchのインターセプター設計など）や、`/api/v1/auth/refresh` エンドポイントのリクエスト/レスポンス仕様が記載されていません。
2. **設計書のバージョン管理（直近3件）のインクリメント仕様**
   - 内部設計書で「バージョン番号 (直近3件管理)」とされていますが、新規に再生成や更新を行った際、古いバージョンのレコードを削除（パージ）するトリガー（アプリケーション側のサービス層で制御するのか、DBトリガーなのか、一意制約の設計はどうするのか）についての言及がありません。
3. **ファイルアップロード制限とLLMのコンテキスト長・コストの考慮**
   - 参考資料（最大10MB × 3件）をそのままLLMに読み込ませる場合、Gemini Flash-Liteの入力トークン制限やコンテキストウィンドウ、コスト（または文字数・PDFパース時のテキスト抽出方針）への影響についての考慮が設計書内に見当たりません。テキスト抽出やチャンク分割のポリシーを補足してください。

### 軽微（運用上の補足）
1. **ファイルパスのプレフィックスやストレージクリーンアップ方針**
   - プロジェクト削除時（`DELETE /api/v1/projects/{id}`）に、紐づく `reference_files` のストレージ上の実ファイルも同時に削除されるかどうかの言及があると、運用時のストレージ肥大化防止の観点でより丁寧になります。
2. **タイムゾーンの定義**
   - データベースの `TIMESTAMP` 型について、UTCで統一するのか、JST等のローカルタイムゾーンを前提とするのかの補足があると、実装時の不整合を防げます。
