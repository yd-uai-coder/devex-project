# 1. 要件定義書

## 1.1 プロジェクトの目的・背景
- **解決したい課題**: システム開発の初期フェーズ（要件定義〜実装計画）において、ドキュメント作成にかかる膨大な工数と、担当者のスキルに依存する「属人化」が発生している課題を解決する。
- **目指すゴール**: AIとの対話型チャットを通じてユーザーのアイデアや要望をヒアリングし、高品質な4種のMarkdown設計書（要件定義・外部設計・内部設計・実装計画）を自動生成することで、プロジェクト立ち上げを劇的に効率化する。

## 1.2 ターゲットユーザー・利用シーン
- **主なユーザー層**: 
  - システムエンジニア、ITコンサルタント、プロジェクトマネージャー
  - 個人開発者、スタートアップの創業者
- **想定される使用シチュエーション**: 
  - 新規プロジェクトの立ち上げ時に、頭の中にあるアイデアを構造化された設計書に落とし込みたいとき。
  - クライアントとのヒアリング内容をベースに、初期ドキュメントのドラフトを素早く作成したいとき。

## 1.3 システム化の範囲（In Scope / Out of Scope）
- **今回開発する範囲（In Scope）**:
  - AI主導型のヒアリングチャット機能（SSEによるストリーミング出力）
  - 参考資料（txt/md/pdf、最大3件）の初期読み込み
  - 構造化サマリの提示とユーザー承認フロー
  - 4種設計書（要件定義・外部設計・内部設計・実装計画）の順次非同期生成（前段の文書を入力として一貫性を保持）
  - 生成後のAI自己診断機能（不足点を最重要/中程度/軽微の3段階で提示）
  - プレビュー、コピー、Markdownダウンロード機能
  - メール・パスワードによるJWT認証（アクセストークン30分、リフレッシュトークン14日・HttpOnly Cookie）
  - PostgreSQLによるユーザー、チャット履歴、設計書（直近3件のバージョン管理）の保存
  - Redisを活用したレート制限とトークン失効管理
  - アクセシビリティ対応（フォームのラベル関連付け、キーボード操作など）
- **今回は開発しない範囲（Out of Scope）**:
  - 設計書からのコード自動生成
  - Jira・Notion等の外部ツール連携
  - マルチテナントの権限管理
  - 音声入力機能
  - 複数ユーザーによる同時編集機能
  - プロンプトテンプレート選択機能（Webアプリ向け・API向けなどの切り替え）
  - 設計書履歴の高度な比較・復元画面

## 1.4 機能要件（MoSCoW優先度）
- **Must have（必須機能）**: 
  - ユーザー認証機能（メール/パスワード登録・ログイン、JWT管理）
  - 参考資料アップロード・読み込み機能（txt/md/pdf、最大3件）
  - AI主導型ヒアリングチャット機能（SSEストリーミング、5観点の自動判定とサマリ提示）
  - 4種設計書の一括順次生成機能（バックグラウンド非同期処理、要件定義→外部設計→内部設計→実装計画）
  - AI自己診断機能（不足点の3段階評価提示）
  - 設計書の閲覧（プレビュー）、コピー、Markdownダウンロード機能
  - データ永続化とバージョン管理（PostgreSQL、チャット履歴・設計書、直近3件保持）
  - レート制限およびトークン失効管理（Redis）
- **Should have（推奨機能）**: 
  - プロンプトテンプレートの選択機能（用途別のテンプレート切り替え）
  - 設計書履歴の比較・復元画面
- **Could have（あると良い機能）**: 
  - 生成された設計書のセクション単位の再生成・編集機能
- **Won't have（見送り機能）**: 
  - コード自動生成、外部ツール連携、マルチテナント、音声入力、リアルタイム共同編集

## 1.5 非機能要件
- **パフォーマンス・応答性**: 
  - チャット応答はServer-Sent Events (SSE)によるスムーズなストリーミング表示を行う。
  - 4文書の一括生成処理はタイムアウトを防ぐため、バックグラウンドの非同期処理として実行する。
  - LLM（Gemini Flash-Lite）の無料枠上限超過エラーに対し、適切なエラーハンドリングとユーザー通知を実装する。
- **セキュリティ・権限管理**: 
  - パスワードのハッシュ化およびJWTによるセキュアな認証。
  - リフレッシュトークンは `HttpOnly Cookie` で保持し、XSS対策を行う。
  - Redisを用いたAPIのレート制限（Rate Limiting）と、ログアウト時等のトークン失効管理を行う。
- **運用・保守・拡張性**: 
  - Docker Composeによるコンテナ化を行い、VPS環境へNginx経由で容易にデプロイ可能な構成とする。
  - フォーム要素への適切なラベル関連付けや、キーボード操作に対応したアクセシビリティ（a11y）を確保する。

## 1.6 制約条件・前提条件
- **技術スタックの制約**: 
  - **フロントエンド**: Next.js (App Router) + Tamagui
  - **バックエンド**: FastAPI + LangChain / LangGraph (Python 3.13)
  - **データベース**: PostgreSQL
  - **キャッシュ・セッション・制限管理**: Redis
  - **インフラ**: Docker Compose, VPS + Nginx
  - **LLM**: Gemini Flash-Lite（無料枠想定）
- **予算・スケジュールの前提**: 
  - MVP（実用最小限の製品）としてスコープを厳格に絞り、短期間での実装と動作検証を優先する。

## 1.7 システムアーキテクチャ・構造図

### 1.7.1 システム全体構成図
```text
[ ユーザー (ブラウザ) ]
       │ HTTPS / SSE
       ▼
 [ VPS / Nginx (リバースプロキシ) ]
       │
       ├─────────────────────────┐
       ▼                         ▼
 [ Next.js (Frontend) ]   [ FastAPI (Backend) ]
 (App Router + Tamagui)   (Python 3.13 + LangGraph)
                                 │
            ┌────────────────────┼────────────────────┐
            ▼                    ▼                    ▼
     [ PostgreSQL ]         [ Redis ]         [ Gemini API ]
   (ユーザー/履歴/設計書)   (レート制限/失効)   (Flash-Lite LLM)
```
