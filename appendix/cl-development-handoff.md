# CL(Curriculum Loop)開発 引き継ぎドキュメント

## 0. 本書について

本書は、あるプロジェクトで「CL(Curriculum Loop)開発」という手法を Phase 0〜15 を通じて実践した結果として積み上がったルール・規約・知見を、**特定プロジェクトに依存しない形**にまとめ直したものである。新しいプロジェクトで CL 開発を始める際の出発点(叩き台)として使うことを意図している。

**本書に含まれるもの**:
- 進行のルール #1〜#17(教材・サンプル・記録の運用ルール)
- コード提示・命名・コメントに関する汎用的な規約
- 開発を通じて言語化された設計判断のヒューリスティクス
- 前プロジェクトで解決しきれなかった課題と、その対応案(検討事項・提案)

**本書に含まれないもの**:
- 特定ドメインのアーキテクチャ決定・技術選定(採用する言語・フレームワーク・ライブラリ、レイヤー構成の詳細、命名の具体例など)は、プロジェクトごとに `CLAUDE.md`(または相当のプロジェクト方針ファイル)の別セクションに書く。本書のルールはその上位にある「進め方」のルールであり、ドメインの決定とは独立している。

**使い方の想定**: 新プロジェクトの `CLAUDE.md` に本書の内容を「進行のルール」節としてそのまま(または取捨選択して)取り込む。ルール番号 #1〜#17 は既存の番号として維持し、そのプロジェクト固有の運用ルールを追加する場合は #18 以降として末尾に足していく(番号は新設順で固定し、参照の一貫性を保つ)。

## 1. CL開発とは

**CL(Curriculum Loop)開発**(略称 CL、正式名 Curriculum Loop 開発)は、次のように定義される開発・学習手法である。

> AI が Phase(開発の区切り)単位で学習教材とサンプルコードを著述し、人間が手でコードを書く。実装で当たった疑問・改善点が質問・相談を通じて教材とサンプルに還流し、教材とプロジェクトが一つのループの中で共に洗練されていく開発・学習手法。

**2 本柱**

1. **双方向の還流ループ**: 「教材 → 実装」の一方向でなく「実装で当たった摩擦 → 教材・サンプルの改訂」。次の Phase はより洗練された状態で始まり、大きなやり直しのリスクを抑える。
2. **役割分担**: AI = 設計・教材・サンプル・トレードオフの説明 / 人間 = 実装のタイピング。AI がコードを書く `vibe coding` の対極に位置する。

**既存概念との関係**

- 「AI 生成コードを人間が理解する」構図(vibe learning 等)に隣接するが、CL 開発は人間が実装を書く点で逆である。
- 下敷きとなる考え方: cognitive apprenticeship(専門家がモデルを示し学習者が実践する)、worked examples 効果、spec-driven development、project-based learning。これらの組み合わせを 1 手法として束ねたもの。

## 2. 共通進行ルール(#1〜#17)

番号(#1〜#17)は新設順に固定する ── 教材・質問ログ・記録などから `#N` として参照される可能性があるため。以下はカテゴリ別に並べ替えてある。新しいルールは該当カテゴリ末尾に次番号で追加する。

### A. 教材の生成 ── いつ・何を

**#1.** 学習教材を Phase 毎に教材フォルダ(例: `textbook/`)に `.md` 形式で作成する。

**#5.** ユーザーの「Phase#を開始する」というプロンプトで、その Phase の教材・サンプルを生成する。

### B. Phase 教材の構成 ── ファイルと章立て

**#2.** 学習教材は各 Phase の中で章立てする。**構成は `Phase-<N>-introduction.md`(導入)+ `Phase-<N>-1.md` 以降(作業単位ごと。章番号 = 作業単位番号)**。別建ての概観章やインデックスは作らず、導入ファイル 1 本に集約する(内容は #6、実装前チェックリストは #11)。設計フェーズ(実装を伴わない Phase)は作業単位を持たないので `Phase-0-introduction.md` + `Phase-0-1.md` 以降(設計トピックの逐次解説)とする。

**#6.** Phase 毎に**導入ファイル `Phase-<N>-introduction.md`** を各 Phase フォルダ直下に作成する。内容: フェーズの目的 / パイプライン上の位置づけ・作業章を始める前に理解すべき前提(概観)/ 章一覧(各章のトピック・依存関係・リンク)/ サンプルコード一覧 / 実装前チェックリスト(#11)/ 次のフェーズ。`Phase-<N>-1.md` 以降を読み始める前に、この 1 本で前提を説明しきる。章を追加・変更したらここも更新する。

**#11.** 各 `Phase-<N>-introduction.md` に「実装前チェックリスト」を置く。内容: その Phase で作成するファイル一覧 / 各クラス・関数の責務 1 行 / テスト観点。Phase 教材の生成後・実装着手前に、ユーザーがこれで疑問を出し切ってから実装に入る。行キーは作業単位番号(章番号と一致)。設計フェーズ(実装が無い Phase)は省略可。

### C. 教材内のコード提示 ── 抜粋 / samples / パッケージ

**#3.** 教材で提示するコードは、長いコードブロックを Markdown に直書きせず「要点の抜粋 + 共有サンプルフォルダ(例: `textbook/samples/`)のファイル参照」とする。samples は **1 フォルダを全 Phase で共有**し(直近 Phase の end 状態)、ユーザーが実プロジェクトのコードへ写経・改変して実装する。これで「教材 Markdown / samples / 実コード」の三重管理を避ける。**反映の順序は「相談で決定 → samples に反映(#9)→ 教材の抜粋が追従」**── samples が基準、教材 Markdown はその抜粋。教材の**構成・体裁・番号**の変更(章のリネーム、節の再編等)はマーカーを付けず内容で上書きする。

**#7.** 教材でコードを提案するときは、配置先のファイルパスを各コードブロックの先頭にコメントで明記する(例: `# app/service/foo.py`)。分割するモジュールはパッケージ(`__init__.py` 付き)として示し、`__init__.py` の re-export 形とファイル間の依存方向も示す。既存教材の修正時・以降の Phase でも同様。

**#9.** 検討・相談の中で提示するコード(クラス名・シグネチャ・型など)に変更が生じたら、対応する samples のサンプルコードにも同じ変更を反映する。反映後は実プロジェクトの環境で実行確認し、可能なら型チェックも通す。

### D. 章ごとの解説とテスト設計

> **実装ファイルを作らない章**(設計フェーズの各章、理論のみの章など)は #13 の全ファイル解説・#15 の全ファイル import・#12 のリファクタ追従の対象外。introduction の章一覧でその旨を明記する。

**#13.** 各章は、その章で**作成 / 更新する全ファイル**を「責務 1 行 + 中身の要点(型・シグネチャ・非自明な判断。パッケージは #7 のとおり `__init__` の re-export 形も)」で解説する。ファイル構成ツリーに列挙するだけで解説を省略しない。各章の冒頭に「この章で作成 / 更新するファイル」を明記する。教材生成後、章の解説とサンプル / 実装前チェックリストのファイル一覧を突き合わせ、漏れが無いか確認する(#15 の「全ファイルをテストが import」と同一機会に)。

**#14.** 各章の `## テスト観点` 節では、テスト(またはテスト群)ごとに **テスト対象(SUT)/ ドライバ / スタブ(テストダブル)** の関係を明記する。スタブが不要な場合は「スタブ不要 ── 対象が純粋(副作用なし)で外部依存を呼ばないため」のように**理由込みで**書く。狙いは CL 開発の趣旨「テストを通じた設計理解の重要視」── テストダブルの要否がレイヤー設計(純粋 / 副作用)の鏡であることを各章で言語化すること。用語(SUT / ドライバ / スタブ)は初出の章で 1 行定義し、以降の章は関係の明記のみでよい。

**#15.** **章が作成 / 更新する全ファイルを、その章のテストが少なくとも 1 度は import する**こと(教材生成後・#13 の突き合わせと同時に確認)。複数ファイルを触って一部しかテストが import していない、のような穴を作らない ── 写経漏れ・写経ミスを検知できるようにするため。集約の**機構**のテスト(レジストリの検索処理等)は具体的な後発実装でなく**フェイク**(fixture で登録)で行う。テスト用フィクスチャも初出章の作成物として実装前チェックリストに含める。純粋関数は素で、外部依存を注入できる設計はフェイクで(#14)。
    - **前方 import の禁止 ── 章 N が作成 / 編集するどのファイルも、その import 先(モジュール **と** モジュール内のシンボル)が {以前の Phase} ∪ {この Phase の章 N まで} で存在しなければならない**。新規ファイルも既存ファイルへの追記も同じ扱い。後の章 M(> N)で生まれるモジュール・シンボルへの import を含むファイル(またはその関数・クラス)は、最初の消費者の章(≥ M)で書く。**2 つの罠**:(a) **新規ファイルはヘッダ以外に Phase タグを持たない** ── タグの `grep` だけでは検出できない。ファイルの全 import 文を読む必要がある。(b) **「モジュールはあるが名前が無い」** ── import 先モジュール自体は既存でも、import する特定のシンボルが後の章の追加物であるケース。集約キー + その実装 import + 配線テストを**同じ章**で足すのは前方参照ではない(その章が最初の消費者であるため)。**生成後の突き合わせ = 実 import 監査**(#13 と同一機会):各ファイルについて ① 作成 / 初出章を実装前チェックリスト + 章本文から確定、② 全 import 文を列挙、③ 各 import 先の**モジュールとシンボル**の誕生章を確定(モジュールの header 系譜 + そのシンボルを追加した章)、④ ③ > ① を全て潰す。タグ `grep` は補助に留める。

**#16.** → #12 のリファクタ追従条項に統合する(下記参照)。

### E. 後続 Phase での改訂 ── 以前の Phase への遡及

**#12.** 後続 Phase で、以前の Phase の**提示コード・設計・決定事項**に変更が生じたら(共通化のために触ってよいかの判断は #17):
    1. 変更後の内容は当該後続 Phase の教材に書く(要点の抜粋。動くコードは共有 samples)。
    2. **共有サンプルの当該ファイルに変更を記録する**:
       - **更新**: 旧コードをコメントアウトし、新コードに `# (Phase <N>-<M>)` タグ(理由を一言)。ファイル冒頭コメントの系譜に `改訂 Phase <N>` を足す。**`#` の後にスペース 1 個**(自動フォーマッタが正規化する言語ではそれに揃える。他言語も同様の慣習に揃える)。「Phase」と番号の間もスペースを入れる(`(Phase 7-3)`。詰めない)。
       - **新規**: ファイル冒頭コメントに出自 Phase を明記する。**1 つのファイルを同一 Phase の複数の章で完成させる場合は、各章の担当分に `# (Phase <N>-<M>)` タグを付け、冒頭コメントに担当章を書く**。単一章で完結する新規ファイルはモジュール docstring(または相当の位置)1 行目に作業単位番号を書く(どの章の成果物か写経者が即分かるように)。`# (Phase N-M)` タグは Phase またぎの改訂だけでなく **Phase 内の章またぎの著述** にも使う。**章タグは次の明示的なタグが現れるまで写経者に「引き継がれる」── 章番号が後退する境界(例: 章 M+1 のブロックの直後に章 M のブロックが続く)は、たとえ 1 個だけであっても必ず再タグを付ける。**付け忘れると直前のタグの章に属するように見え、写経者がそのブロック丸ごとを読み飛ばす事故になる。教材生成後の突き合わせ(#13)で、各ブロックの直前のタグ番号と、そのブロックが実際に属する作業単位番号が一致しているか(前のタグを暗黙に引き継いでいないか)を全ブロックで確認する。
       - **やらないことに確定**(旧計画の撤回): 教材の当該箇所に blockquote
         `> **[Phase <N> で確定 ── 〈…しない〉]** 当初〈…する予定〉→ 撤回。理由〈…〉。`
       - `grep` 用合言葉: 更新 = `# (Phase` / 撤回 = `で確定 ──`。
    3. 変更元 Phase の `Phase-<M>-introduction.md` に「後続 Phase での改訂」節を設けて 1 行、プロジェクト方針ファイルの決定ダイジェスト節にも要点を残す。
    4. **リファクタ(公開挙動を変えない整理 ── 関数の抽出・移動・シグネチャ変更)の写経ミスの番人 = 当該章の第一テストの統合スモーク**(リファクタ対象の公開 API を素で 1 回呼ぶ)。docstring に「よくある失敗モード → どの行を見るか」(間接的なエラーほど有効)。以前の Phase の該当テストは共有サンプルにあり写経後に再実行する ── 公開挙動が不変ならアサーションはそのまま、変わるなら変更前後をコメントで対比する。
    - **教材の構成・体裁・番号の変更**(章のリネーム、節の再編、TOC 更新、参照リンクの張り替え等)はこのルールの対象外。マーカーを付けず内容で上書きし、決定の記録は #8・#10 のログに残す。

**#17.** **以前の Phase のコードを共通化のために触ってよいかの判断基準**。後続 Phase が以前の Phase のコードと同じ**ドメインの事実**(式・不変条件・データ構造)を必要とするとき、「コピーして各 Phase に重複させる」か「以前の Phase のコードを抽出・共通化して両者で共有する」かの分岐では **常に共有を選ぶ**。#12 の記録 + #12.4 のスモークのコスト(AI のタスク量が増える)を払ってでも重複を残さない。**触らないもの**: (a) 教材本文の遡及的**全面**リライト(差分はマーカーで示す。本文・コードは残す) (b) **駆動する新しい消費者がいない**遡及クリーンアップ / 監査(「どこかに重複はないか」と以前の Phase を巡回すること) (c) レイヤー境界が要求する分割(これは重複でなく必然)。**判定の一問**: 「この共通化を今 駆動している、この Phase の実在の消費者は何か」に具体名で答えられれば実施、「将来たぶん」「一般に良い設計だから」なら見送る。「以前の章を過剰に触らない」という明文ルールは無い ── 「既存コードは変更前に影響範囲を調査」はコスト評価を指すのであって「触るな」の意味ではない。

### F. 記録

**#4.** 実装段階での検討事項・検証段階で発覚した事象はプロジェクト方針ファイルの記録節に記録する。#4 は包括方針で、具体的な振り分けは ── 質問・相談ログ → #8 / 進行方法の所感 → #10 / 後の Phase に前向きに効く決定・知見 → 決定ダイジェスト節。

**#8.** ユーザーが AI に行った質問・相談とその回答を専用ログファイル(例: `textbook/q_a.md`)に**追記**する(保存専用・作業中は参照しない)。各エントリは次の形式:
   1. 疑問が生じた Phase
   2. 質問・相談内容
   3. 回答と対応方針

   進行方針にかかわる決定・設計判断は、決定ダイジェスト節(プロジェクト方針ファイル)にも要約を残す(こちらが参照用)。

**#10.** プロジェクトの進行方法について気づいた点(特徴・メリット / 課題 / 課題解決への提案)を振り返りファイル(例: `textbook/appendix/*-retrospective.md`)に追記する。課題には可能な限り「提案」を対で書く。提案をプロジェクトに組み込むかはユーザーが個別に判断する(AI は勝手に適用しない)。

## 3. コード規約・命名規約(汎用原則)

### コード提示規約(再掲・詳細)

- コードを提案する各ブロックの先頭に、配置先のファイルパスをコメントで明記する(#7)。
- 複数ファイルに分割するモジュールは、パッケージ(該当言語のパッケージ機構)として提示し、集約ファイルの re-export 形と依存方向(どちらが何を import するか)も併せて示す。
- 「教材 Markdown / samples / 実コード」の三重管理を避け、samples を単一の真実源として運用する(#3)。

### 命名: 先頭アンダースコア `_`(非公開の印)

言語がアンダースコア接頭辞を「非公開(internal)」の慣習として扱う場合(Python の PEP 8 等)、lint で強制せずとも**読み手への約束**として運用できる。使い分けの型:

| 形 | 意味 |
| --- | --- |
| インスタンス属性の非公開(`self._attr`) | クラスの公開面は公開メソッドだけ。呼び出し側は非公開属性に触らない |
| モジュールレベルの非公開関数・定数・型 | そのモジュールの外から import させない内部部品。モジュールの公開 API は `_` なしの名前(+ 言語の公開リスト機構があればそれも) |
| 使い捨て変数(`for _ in ...`) | 束縛するが使わないことを示す |
| 診断用・比較対象外の値を示す接頭辞 | プロジェクト独自の運用として、「目的値ではない・他の値と直接比較しない内部指標」であることを dict のキー名等で示す運用も有効 |

`_` の有無は「この名前を外から使ってよいか」という設計判断そのものである。あるモジュール内部の実装が、後の Phase で公開レジストリに昇格するとき `_` を外す、といった変化はその判断が変わったことの記録になる。

### コメント規約(方針)

コメントの**密度の目安**と**書くべき内容の方針**は言語非依存だが、**書式**(docstring か JSDoc か等)は採用するスタックの慣習に合わせる。

| 対象 | 内容 | 目安 |
| --- | --- | --- |
| 関数の説明 | 何をする関数か(必要なら「なぜ」も) | 60〜100 文字程度 |
| 関数の引数・戻り値 | 各引数の意味と戻り値 | 簡潔に |
| 関数内の条件分岐・繰り返し | その分岐 / ループが何を判定・処理するか | 40 文字程度 |
| 関数内の変数 | その変数が保持する値 | 簡潔に |

方針の核: **「なぜ / ハマりどころ」中心**。型と命名で自明な引数・変数はコメントを省略してよい。既存コードにこの水準を超える有用な記述があれば、それを削って画一化する必要はない(本規約は最低ラインとして扱う)。

## 4. 設計判断のヒューリスティクス(型)

CL 開発を通じて、新しい Phase の設計判断に繰り返し使える「型」がいくつか言語化された。これらは特定のドメインに依存しない一般的な設計判断のパターンである。

- **分割 vs 統合**: 「一緒に変わるものを同じファイルに」。複数の概念を束ねるファイル(アグリゲータ)が各要素を import する構造は、要素同士が互いを import しない限り悪い密結合ではない。
- **「これは計算か? 述語か?」**: 何らかの探索・走査を伴う**計算**は計算を担うレイヤーに、値の性質を判定するだけの**純粋述語**はドメインを担うレイヤーに置く。ゲート判定(可否の最終判断)はさらに別のオーケストレーション層に置く。レイヤー間の import 方向の制約は、この判断の誤りを実装中に顕在化させる **guardrail** であって、判断そのものの理由ではない。
- **data 層の粒度**: モデル・スキーマ・リポジトリは「永続化の関心事」でまとめて 1 ファイルにする。操作(ルーティング・サービス)は「操作」の単位で割る。「ファイルが短いから分ける」という基準は避ける ── ファイル同士が 1:1:1:1 に綺麗に対応するとは限らない。
- **ヘルパの置き場は「2 本目の消費者」で決まる**: ある処理が最初からジェネリック(汎用)だと分かっている場合は、1 本目の時点で公開の共通モジュールに置く。判断に迷う場合は、2 本目の消費者が現れた時点で共通化を検討する。
- **共通化するのは機構であってオーケストレーションではない**: 複数の処理から呼ばれる共通の「仕組み」(データ構造の組み立て、汎用アルゴリズム等)は共通化する。一方、個々の処理の「レシピ」(どの順で何を呼ぶか)は、単純なパススルーであっても無理に括らず、各処理の中に直線的に見せる方が読みやすい。
- **以前の成果物を共通化のために触ってよいかの一問**(#17 の判定基準): 「この共通化を**今**駆動している、実在の消費者は何か」に具体名で答えられれば実施し、「将来たぶん役立つ」「一般に良い設計だから」という理由なら見送る。
- **YAGNI の判断パターン**: 消費者が存在しない投機的な実装(将来使うだろうと見込んで先に作る機能)は、実装した時点で消費者が無ければ撤回し、実際にその機能を必要とする Phase まで先送りする。「今のところ誰も使わない拡張(全件探索への一般化、専用テーブルへの切り出し、汎用化されたテストフレームワークの導入等)」は、必要になった時点まで導入を遅らせる。

## 5. 現状の課題・検討事項・提案(継続課題)

以下は前プロジェクトの MVP 完了時点での棚卸しから、他プロジェクトでも再考する価値がある論点を抽出したものである。**いずれも「採用可否はプロジェクトごとに個別に判断する」**(#10 の姿勢)。数値・実測値は前プロジェクトでの一データ点として参考にする。

### 5.1 進行スピードが担保できない(重点課題)

CL 開発は「教材 → 実装 → 摩擦 → 教材改訂」の還流ループを**品質優先**で回す設計であり、**時間の次元が手法に組み込まれていない**。納期の定まった実務プロジェクトにはそのままでは不向きで、個人学習でも所要期間の見積りが立ちにくい。

原因要素と対の提案(いずれも前プロジェクトでは未採用・検討段階):

| # | 原因要素 | 提案 |
|---|---|---|
| 1 | 時間の設計が手法に無い(Phase・作業単位に目安工数・タイムボックスが無い) | チェックリスト各行に「目安: 写経 N 分 + 理解 M 分」を付し、超過時は深掘りを別途隔離してまず先に進む |
| 2 | 二重の学習曲線(ドメイン知識 + 実装スタック)が同時進行し、スタック側の摩擦は事前に読めない | 各章冒頭に「新しく使う言語 / ライブラリ機能」3 点 + 既知のつまずき FAQ を明記する |
| 3 | 還流ループに反復上限が無い(「疑問を出し切ってから実装」の終了条件が開放的) | 事前質問は設計判断に関するものだけに限定し、実装の細部は着手後に都度質問する運用にする(WIP 制限・前進優先) |
| 4 | 写経が律速だが学習価値が不均一(コアな判断と定型的な記述を区別せず全部手打ちする) | samples の各ファイルに「写経レベル: コア / 定型」マーカーを付け、時間優先時は定型部分をコピーで済ませる |
| 5 | 生成と実装が直列で待ちが発生する。難所は生成して初めて判明する | 次の Phase のドラフトを別セッションで先行生成しておく。依存関係がなく「今すぐ着手可」な部分を強調する |
| 6 | 各 Phase の完了判定・到達度の基準が無い | 各導入ファイルに「Phase 完了チェック」として概念理解を問う質問を 3〜5 問用意する(実装前チェックリストと対をなす) |
| 7 | 記録(質問ログ・ルール等)の肥大化でセッション立ち上げが重くなる | 5.2 を参照 |
| 8 | 検証環境の構築・実行に一手多くかかる | 5.3 を参照 |

**2 モードの案**: 「学習モード」(現行。全写経 + 事前質問を厚くする。速度は保証しない)と「納期モード」(速習パス + 定型コピー + テストは実行のみ + 学習は事後レビューで回収。学習効果は下がる)を明示的に切り替えられるようにする。提案 1・4・6 が揃えば同じ教材のまま切り替えられる。

**優先度案**: まず「タイムボックス + 目安工数」(提案 1)、「写経レベルの区別」(提案 4)、「事前質問を設計判断に限定」(提案 3)の 3 点から試すと、「見積もれる・律速を削る・ループを閉じる」が揃う。

### 5.2 状態(ルール・記録)の肥大化対策

質問・相談ログや Phase 別の決定事項をプロジェクト方針ファイルに逐次書き足していくと、全体量に対して履歴ナラティブの比率が肥大化し、規範(ルール本体)がノイズに埋もれて後半ほど解釈がぶれやすくなる。サンプルコードも Phase ごとに全文生成すると重複が増え、過去 Phase を遡って参照するコストが上がる。

対応として有効だった構成:
- 質問・相談ログは専用ファイル(#8)に逐語で移し、**保存用・非参照**として扱う。
- Phase 別の主要な決定・検証で発覚した事象は、プロジェクト方針ファイルの「決定ダイジェスト」節に**後の Phase に効く分だけ**圧縮して集約する(1 エントリはごく短く、詳細はログ側に書く)。
- 進行ルールは意味のあるカテゴリ(生成 / 構成 / コード提示 / テスト設計 / 改訂 / 記録、等)に再配置し、重複した記述を短縮する。
- サンプルコードは Phase ごとの個別フォルダではなく **1 つの共有フォルダに、常に最新 Phase の end 状態を保持**する形にする。写経モデルは「end 状態のみを見せ、各章が差分(delta)を語る」形にする。これにより検証(全体テストの実行等)は 1 回のオーバーレイで済むようになる。

### 5.3 抜粋追従・検証コストの一手

- 教材内の「要点抜粋」は samples から手で切り出すため、samples を直したら抜粋も追従して直す必要がある。抜粋は「シグネチャ + 核心 1〜2 行」まで絞り込むと追従コストが下がる。さらに、抜粋に `samples/<path>:<行番号>` のような参照を添えておくと、ズレが生じたときに気づきやすくなる。
- samples が実プロジェクトのディレクトリ構成をそのまま模していると、samples 単体では依存解決やテスト実行ができず、実プロジェクトの構成に一時的に重ねる(オーバーレイする)検証の一手が必要になる。samples のフォルダ自体に、依存解決や型チェックの設定ファイルを含めておき、オーバーレイなしで検証できるようにする案は検討する価値がある。

### 5.4 やり直しリスク・事前理解のハードルは構造的に残る

コーディング着手前にユーザーが設計を理解し、疑問を解消しておく必要があるが、これは学習を兼ねているためハードルが本質的に高い。実装前チェックリスト(#11)で軽減はできるが、構造的には残り続ける制約として認識しておく。

### 5.5 セッション運用の実測知見

ある実プロジェクトで、ルール整理直後に「教材生成が体感的に遅くなった」という報告があり、セッション記録のトークン使用量を実測で検証したところ、**ルール整理自体は生成量を減らしていた**(出力トークン・thinking トークンとも前より少ない)。遅延の実際の主因は次の通りだった:

1. **セッションのスタッキング(最も影響が大きい)**: 振り返り・ルール分析・整理作業・次 Phase の生成を 1 セッションで連続して行うと、次 Phase 着手時点で文脈サイズが既に大きく、早期に強制的な要約(コンパクション)が発生して生成が乱れる。
2. **Phase の種別**: 新しい概念・データ構造を一から配線する Phase は触るファイル数が多く重い。既存の骨格にアルゴリズムを追加するだけの Phase は軽い。
3. **検証ループの回数**: 「end 状態をまとめて 1 回で検証する」モデルでは、生成の途中経過でも全体テストを何度も再実行しがちになる。
4. **サンプルの読み書きコストの移動**: 「新規フォルダを全文生成する(出力のみ)」から「蓄積された end 状態を読んでからマーカー付きで編集する」に変わると、出力は減るが読み込みが増える。

**運用調整の案**:
- 1 つの Phase(またはひとまとまりの作業)= 1 セッションとし、着手前にセッションをクリアする。振り返り・ルール整理・大規模リファクタは別セッションに分ける。
- 検証で発覚した事象の記録は簡潔に(数行以内)留め、長い経緯は別ログに書く。
- 触るファイル数が多い Phase では、着手時に「触る予定のファイル一覧」を実装前チェックリストから確定させ、まとめて読み込んでから着手する。
- 生成中は影響範囲を絞った部分的なテスト実行に留め、全体テスト(オーバーレイ含む)は Phase 完了時に 1〜2 回で済ませる。

### 5.6 写経順序の検証限界と前方 import 対策

「共有 1 フォルダ・end 状態」モデル(5.2)は検証コストを下げる一方で、新しい限界を生む: end 状態は常に依存解決に成功するため、**利用者が実際に章の順番どおりに写経したときだけ**発生する問題(①前方 import、②その章の新規ファイルの写経漏れ、③リファクタの写経ミス)を、end 状態への 1 回のオーバーレイ検証では検出できない。

対応として:
- **採用推奨**: #15 の前方 import 禁止条項に加えて、生成後に**実 import 監査**(タグの `grep` だけに頼らず、全ファイルの import 文を実際に読んで、モジュールとシンボルそれぞれの誕生章を突き合わせる)を行う。
- **採用推奨**: 各 Phase の導入ファイルに「写経順序」(依存関係に基づく順序)を明記し、章番号の順序と依存順序が食い違う場合は各章冒頭に前提章を示す。
- **見送り推奨**: 章単位の部分的なオーバーレイ再構築(章 N までのファイルだけを都度クリーンな環境に重ねてテストする)は、①②③を実行時に確実に捕まえられる一方、「共有 1 フォルダ・end 状態」モデルが解消したはずの構築コストを復活させてしまう。実 import 監査 + 写経順序の明記で大半をカバーできるため、費用対効果で見送るのが妥当。

## 6. 用語集

- **SUT(System Under Test)**: テストの対象そのもの。
- **ドライバ**: SUT を呼び出し、テストを駆動する側(多くの場合テストコード自身)。
- **スタブ(テストダブル)**: SUT が依存する外部要素を置き換える代用品。SUT が純粋(副作用が無く外部依存を呼ばない)であれば、スタブは不要になる ── この要否がレイヤー設計(純粋 / 副作用)の鏡になる(#14 参照)。
