# Devex 実装手順書 作成方針

> ChatGPT との相談で作った初版を、Claude との相談(2026-10-06〜07)で、今の Devex の実装(詳細設計モードの段階1〜7、簡易ドキュメントモードの4文書)に合わせて改訂した。初版は Devex の現状を知らないまま概念から検討したため、主に次の点を直した。
> - 設計の中身を書き写さず、参照する。
> - 2つのモードを入力にする。
> - 実装単位を機能ごとの縦割りにする。
> - 実装可能性チェックを入れる。
> - 変更影響を手で書かない。
>
> このファイルは [ロードマップ](devex_roadmap.md) のステージ5「実装手順書 + 実装可能性チェック」の方針である。21章の未決事項は、ステージ5 の着手時に #28 の仕様診断で決める。例に出てくる名前(ユーザー登録、`UserService` など)は説明用で、Devex に実在するものではない。

## 1. 目的

Devexにおける「実装手順書」は、単なるコード生成用プロンプトではなく、**設計情報を実装可能な粒度へ変換するための文書**とする。

目的は以下のとおり。

- 設計者・実装者が設計意図を理解したうえで実装できるようにする
- AI Coding Agentに実装を依頼する際の共通仕様として利用する
- 設計から実装までの情報の連続性を維持する
- AIによる勝手な設計変更・過剰実装を抑制する
- 要件・設計変更時に実装への影響範囲を追跡できるようにする
- **設計の不足・矛盾を、実装に入る前に表に出す(実装可能性チェック)**

最後の項目は、手順書を作ろうとすると「必要なファイルが分からない」「エラー時の仕様が無い」といった設計の穴が自然に表に出る、という性質を利用する。手順書の生成と実装可能性チェックは、1つの機能として作る。

---

## 2. Devexにおける位置づけ

Devexは、単なるコード生成AIではなく、システム開発における**「設計から実装への橋渡し」**を支援するシステムとする。

```text
要件(ヒアリング)
  ↓
要件定義
  ↓
外部設計
  ↓
内部設計(簡易モード) / 詳細設計 段階1〜6(詳細設計モード)
  ↓
実装計画(簡易モードの4文書目 / 詳細設計モードの段階7)
  ↓
実装手順書 + 実装可能性チェック   ← ステージ5
  │
  ├─ 不足・矛盾 → 設計の修正 / ヒアリングの改良(ステージ6)へ
  ↓
人間による実装(AI Coding Agent による実装支援を含む)
  ↓
テスト
```

Devexの重要な思想は、AIに開発を完全自動化させることではなく、

> **AIによって開発を高速化しながら、人間が設計・実装・保守を理解できる状態を維持する**

ことである。

## 3. 入力となる文書とモード

実装手順書は、詳細設計モードに限らず、簡易ドキュメントモードからも作る。モードによって変わるのは入力と深さだけで、手順書の形(4章以降の構成と単位のテンプレート)は共通にする(推奨案。モードで分けるかどうかは21章の未決事項)。

| | 詳細設計モード | 簡易ドキュメントモード |
|---|---|---|
| 入力 | 要件定義・外部設計・段階1〜7 の承認済みの内容 | 要件定義・外部設計・内部設計・実装計画の4文書 |
| 単位の元 | 段階7 のタスク(マイルストーン `M-01` などの配下。`function_ids`・`modules` を持つ) | 実装計画書の WBS・内部設計書のモジュール一覧・処理別データフロー。手順書の生成時に単位を作る |
| 参照先 | 処理ID(`F-03`、手順 `F-03#2`)、段階6 の関数、段階3 のテーブル、段階4 のモジュール、07章の横断事項 | 処理別データフロー(`DF-<n>`)、API のパス、モジュールのパス、内部設計書 3.2 のテーブル・3.4 のエラー方針 |
| 「未定義」の出やすさ | 少ない | 多い |

簡易モードでは、設計に書かれていない部分が多いので「未定義」の指摘が多く出る。それを正直に示すこと自体に価値がある。例えば「この単位は処理の手順が設計に無いので、詳細設計モードで詰めることを勧める」と書ける。

形を共通にする前例として、「モジュール一覧表を簡易モードの内部設計書にも出す」とした判断がある(ステージ4)。

## 4. 実装計画と実装手順書の違い

両者は明確に分離する。

### 実装計画

主に **What / When** を扱う。

```text
- 何を実装するか
- どの単位に分割するか
- どの順番で実装するか
- 何に依存するか
- どの実装単位を先に完成させるか
```

### 実装手順書

主に **How** を扱う。

```text
- どのファイルを、どの順で作成・変更するか
- 各ファイルの責務
- 設計のどこを根拠に実装するか(参照)
- 設計に書いていないが、実装で決める必要があること
- テスト観点と確認方法
- 完了条件
```

### 手順書は設計を書き写さない

処理の手順、インターフェース、エラー処理、データモデルは、設計(詳細設計の段階2〜7、簡易モードの内部設計書)にすでにある。手順書はそれを **ID で参照する** だけにし、中身を書き写さない。

書き写すと、設計を直したときに手順書が古くなり、二重管理のずれが起きる(この開発の CL 教材でも、教材・samples・本体の三重管理でずれが起きた)。

手順書だけに固有に書くのは、次の4つである。

1. **どのファイル**を作成・変更するか(依存順、責務1行)
2. **どの順**で作るか(単位の間・単位の中)
3. **どう確かめる**か(テスト観点・確認方法)
4. **設計に無いもの**(未定義・要決定。13章)

```text
実装計画
  ↓
「M-01 のタスク: ユーザー登録」
  ↓
実装手順書
  ↓
「F-03 の手順 #2〜#5 を、このファイルをこの順で作って実装し、
 このテストで確かめる。重複時のレスポンスは設計に無いので決める必要がある」
```

## 5. 実装手順書の基本構成

```text
実装手順書
│
├─ 1. 実装概要(対象・対象外)
├─ 2. 実装前提・制約(技術スタック・実装ルール)
├─ 3. 実装単位の一覧(依存順)
├─ 4. 各実装単位
│    ├─ 目的
│    ├─ 対象の処理・参照する設計
│    ├─ 作成・変更するファイル(依存順・責務1行)
│    ├─ 実装の要点(設計に書いていないことだけ)
│    ├─ テスト観点(SUT・ドライバ・スタブ)
│    ├─ 確認方法
│    └─ 未定義・要決定
├─ 5. 未定義・要決定の一覧(実装可能性チェックの結果)
└─ 6. 完了条件
```

初版にあった「データ・インターフェース仕様」と「変更時の影響範囲」は、独立した章にしない。前者は設計を参照し(10章)、後者は ID の紐づけから計算する(14章)。

## 6. 実装概要

実装対象と対象外を明示する。

```md
# 実装概要

## 対象機能

ユーザー登録と、登録したユーザーでのログイン。

## 実装範囲

- F-03 ユーザー登録
- F-04 ログイン

## 実装対象外

- パスワード再設定(要件定義で Could have)
- 管理者によるユーザー削除
```

実装対象外を明示することで、AIによる不要な実装を防ぐ。対象と対象外は、要件定義の MoSCoW と、実装計画のマイルストーンから導く。

---

## 7. 実装前提・制約

使用技術だけでなく、アーキテクチャ上の実装ルールを明記する。

実装ルールは、生成する LLM が一般論で書かず、設計から引く。

- 詳細設計モード: 段階4(構成図の層・モジュール一覧の依存先)と 07章(横断事項)
- 簡易モード: 内部設計書 3.1(アーキテクチャ方針)・3.3(モジュール一覧)・3.4(エラー・ログ方針)

```md
## 実装ルール(段階4・07章より)

- DBアクセスはRepository経由とする(段階4: 層 repository)
- API Routerから直接Repositoryを操作しない(段階4: 依存先)
- 業務エラーはサービス層の例外として投げ、ルーターでHTTPに変換する(07章: 例外とHTTP)
- 認証情報は環境変数から取得する(07章: 設定)
```

設計から引けないルールが必要なら、それは「未定義」(13章)に挙げる。

## 8. 実装単位

### 8.1 機能ごとの縦割りにする

実装手順書は巨大な1枚の手順書として扱わず、実装単位に分割する。単位は **機能ごとの縦割り**(1つの単位が DB・Repository・Service・API・画面の層をまたぐ)とする。

初版の例(`IMP-001 DB Model → IMP-002 Repository → … → IMP-006 Test`)のような層ごとの横割りは採らない。理由は次のとおり。

- 横割りでは、API の単位が終わるまで何も動かず、途中で確かめられない。
- テストが最後の単位にまとまり、「単位ごとにテストで確かめる」と食い違う。
- この開発の CL 教材は、章ごとに機能を縦に通し、その章のテストが章で触った全ファイルを import することで写経漏れを検出してきた。ゴール3 では、この形(作業単位の表)を手順書のひな形の候補とした。

### 8.2 ID は既存の ID につなぐ

単位の ID は、独立した体系(`IMP-xxx`)を新しく作らず、実装計画の ID から導く。

```text
M-01 ユーザー管理の基本(マイルストーン)
 ├─ M-01-T01 ユーザー登録     F-03
 ├─ M-01-T02 ログイン         F-04   (依存: M-01-T01)
 └─ M-01-T03 プロフィール表示 F-05   (依存: M-01-T01, T02)
```

ID の形式(`M-01-T01` など)は未決事項(21章)である。簡易モードの WBS には今は番号が無いため、そのままでは導けない。

### 8.3 依存は単位の間に持つ

依存は、単位の間(どの単位が先に終わっている必要があるか)に持つ。単位の中のファイルの順序は、import の依存順(依存されるファイルを上)に並べる。この単位を、人間・Devex・AI Coding Agentが共有する。

## 9. 実装単位のテンプレート

```md
# M-01-T01 ユーザー登録

## 目的

利用者がメールアドレスとパスワードでアカウントを作れるようにする。

## 対象の処理・参照する設計

- 処理: F-03 ユーザー登録(手順 F-03#1〜#6)
- データ: 段階3 users テーブル
- モジュール: 段階4 user_repository / user_service / users ルート
- 関数の詳細: 段階6 UserService.register
- 横断事項: 07章 例外とHTTP・パスワードの保管

## 作成・変更するファイル(依存順)

| ファイル | 責務 |
|---|---|
| backend/app/models/user.py | users テーブルの ORM モデル |
| backend/app/repositories/user.py | users の保存と、メールアドレスでの検索 |
| backend/app/services/user.py | 登録の業務ルール(重複の確認・パスワードのハッシュ化) |
| backend/app/api/routes/users.py | POST /users と、例外から HTTP への変換 |
| backend/tests/unit/test_user_service.py | サービスの単体テスト |
| backend/tests/integration/test_users_api.py | API の結合テスト |

## 実装の要点(設計に書いていないことだけ)

- マイグレーションを1本追加する(users テーブルの新規作成)。
- パスワードのハッシュ化には、既存の auth のユーティリティを使う。

## テスト観点

(11章の形式)

## 確認方法

- 単体・結合テストが通る。
- 開発環境で POST /users を呼び、users に1行入ることを確かめる。

## 未定義・要決定

- [最重要] メールアドレスが重複したときのレスポンス(ステータスとエラーコード)が設計に無い。
```

処理の手順・引数・戻り値・例外は、参照先の設計にあるので書かない。

## 10. 処理ロジック・インターフェース・エラー

初版で別々の節にしていた「処理ロジック」「データ・インターフェース仕様」「エラー・例外処理」は、いずれも設計の該当箇所を参照する。

| 内容 | 詳細設計モードの参照先 | 簡易モードの参照先 |
|---|---|---|
| 処理の流れ(呼び出し元→先・データ・DB 操作・分岐) | 段階5 の手順(`F-03#2` など) | 内部設計書の処理別データフロー(`DF-<n>`) |
| 関数の契約(シグネチャ・引数・戻り値・例外・事前/事後条件) | 段階6 の関数 | (無い → 必要なら未定義に挙げる) |
| API の契約 | 外部設計の API 一覧・段階1 の処理 | 外部設計 2.6・内部設計書 3.3 の API 一覧 |
| エラー・トランザクション・認証 | 07章 横断事項 | 内部設計書 3.4 |
| 図 | 段階2 の DFD・段階3 の ER・段階4 の構成図 | (無い) |

目的は、**コードを書く前に処理の責務とデータの流れを理解できるようにすること**である。そのための情報は設計側に置き、手順書からたどれるようにする。

設計に無いもの(例: エラーの発生条件はあるが HTTP ステータスが無い、トランザクション境界が無い)は、推測で埋めずに「未定義・要決定」に挙げる(13章)。

## 11. テスト

「テストを書く」ではなく、検証内容まで定義する。Given/When/Then に加えて、**テスト対象(SUT)・ドライバ・スタブ(テストダブル)** の関係を書く。

```md
## TC-01 登録できる

- SUT: UserService.register
- ドライバ: 単体テスト(pytest)
- スタブ: UserRepository をフェイクに差し替える(DB に依存せず業務ルールだけを見るため)

Given: 未登録のメールアドレス
When:  register() を実行
Then:  フェイクにユーザーが1件保存され、パスワードはハッシュ化されている

## TC-02 重複したメールアドレスでは登録できない

(同上。Then はエラーの内容 ── 「未定義」が決まってから書く)
```

スタブが要らないときは理由を書く(例:「スタブ不要 ── 対象が純粋な関数で外部依存を呼ばないため」)。スタブの要否は層の設計を映すので、読み手の設計理解にもつながる(CL 教材の #14 で得た知見)。

**ステージ5 の範囲は、単位ごとのテスト観点と確認方法まで**とする。テスト仕様書としての体系的なテスト設計(単体/結合/総合、境界値、非機能)は、ステージ8 で扱う。

---

## 12. 完了条件

実装のDoneを明示する。これはDefinition of Doneとして扱う。

```md
## 完了条件

- [ ] この単位のテストが全件成功
- [ ] 既存のテストが壊れていない
- [ ] lint・型チェック成功
- [ ] マイグレーション適用成功
- [ ] Docker Compose 環境で起動し、確認方法の操作ができる
- [ ] 「未定義・要決定」がすべて決まり、設計に反映されている
```

## 13. 実装可能性チェック

### 13.1 何を調べるか

- 必要なコンポーネント・インターフェース・DB モデルが設計にあるか
- API 仕様が実装できる粒度か
- トランザクション境界・エラー処理・認証認可が定義されているか
- 外部依存が定義されているか
- 設計の間に矛盾がないか
- 実装順序を決められるだけの情報があるか

### 13.2 2層で調べる

1. **決定論的な検証**: 段階ごとの既存の検証を手順書に広げる。
   - 例: 単位が参照する処理ID・モジュールが設計に存在するか。
   - 例: ファイルの依存順が段階4 の依存先と矛盾しないか。
   - 例: どの単位にも割り当てられていない処理が無いか。
2. **LLM による指摘**: 手順書を生成する LLM に、設計に無いものを推測で埋めず、「未定義」として挙げさせる。初版が AI Coding Agent に求めた「食い違いは勝手に直さず報告する」(16章)と同じ規律を、Devex の生成側にも課す。

### 13.3 結果の出し方

各単位の「未定義・要決定」と、全体の一覧(5章の構成の5)に出す。重要度は #28 の3段階を使う。

- 最重要: 着手前に決める
- 中程度: 後の単位までに決める
- 軽微

```text
⚠ [最重要] M-01-T01: メール重複時のレスポンス仕様が未定義です(F-03#3)
⚠ [中程度] M-01-T02: ログイン失敗の回数制限が未定義です(07章 認証)
⚠ [軽微]   M-01-T03: 一覧の並び順が未定義です
```

指摘は、ユーザーが「決定する」か「AI に提案を求める」かを選べるようにする。決まった内容は設計側に反映し、手順書には書かない。

### 13.4 ヒアリングの改良に渡す

指摘のうち「本来ヒアリングで聞くべきだった」ものは、ステージ6(ヒアリング改良)の材料にする。どの観点を足すかを実例で決めるためである。

## 14. 変更時の影響範囲

単位ごとに影響範囲を手で(LLM に)書くことはしない。書いた時点から古くなり始めるためである。

ステージ5 では、**単位と ID の紐づけ**(単位 → 処理ID・モジュール・テーブル・ファイル)だけを持つ。これがあれば、影響範囲はステージ7(変更影響分析)で、紐づけのグラフをたどって計算できる。

```text
要件変更 → 設計変更 → (紐づけをたどる) → 影響する単位 → 手順書の該当単位を陳腐化として示す
```

---

## 15. AIへの渡し方

設計書をすべて一括でAI Coding Agentに渡して「実装してください」とする方式は避ける。AIには「現在実装する単位」に必要な情報を中心に渡す。

```text
プロジェクト概要
↓
実装ルール(7章)
↓
今回の実装単位(9章のテンプレート)
↓
単位が参照する設計の該当箇所(10章の表に従って展開する)
↓
未定義・要決定が残っていないこと
```

**AI 向けの出力は、手順書の1単位を整形したもの(エクスポート形式の1つ)とする。** AI 向けに別の中身を作らない。実装者が人でも AI でも、手順書の中身は変えない。

参照の展開(ID から設計の該当箇所を取り出して添える)は、Devex が決定論的に行う。「未定義・要決定」が残っている単位は、AI に渡す前に警告する。

## 16. AIによる実装フロー

AIにいきなりコードを書かせない。

推奨フロー:

```text
1. 実装対象(単位)を提示
        ↓
2. リポジトリを調査
        ↓
3. 現在のコード構造を把握
        ↓
4. 実装手順書との整合性を確認
        ↓
5. 差異を報告
        ↓
6. 実装方針を提示
        ↓
7. 人間が確認
        ↓
8. 実装
        ↓
9. テスト
        ↓
10. 結果報告
```

特に重要なのは、

> 設計書と現状コードに不整合がある場合、勝手に設計変更して実装せず、問題として報告する

という制約。

## 19. Devexの設計原則

### 原則1:AI完全自動実装を目的にしない

AIは実装を高速化するが、設計判断をブラックボックス化しない。

### 原則2:実装計画と実装手順書を分ける

```text
実装計画 = What / When
実装手順書 = How
```

### 原則3:実装単位を明確にする

機能ごとの縦割りの単位に分け、実装計画の ID から導いた ID で依存関係を管理する。

### 原則4:人間とAIの共通言語として利用する

実装手順書はAI専用プロンプトではなく、人間も理解できる実装仕様書とする。AI 向けの出力は、その整形にすぎない。

### 原則5:設計変更を実装へ伝播できるようにする

単位と ID の紐づけを持ち、影響範囲は紐づけから計算する(手で書かない)。

### 原則6:設計と実装の不整合を検出する

AI Coding Agentは、現在のリポジトリと実装手順書を照合し、不整合を検出した場合は勝手に判断せず報告する。

### 原則7:設計を書き写さず、参照する

処理・インターフェース・エラー・データは設計に置き、手順書は ID で参照する。手順書に固有なのは、ファイル・順序・確かめ方・未定義の4つ。

### 原則8:推測で埋めない

手順書を生成する LLM も、設計に無いものは「未定義」として挙げる。これが実装可能性チェックになる。

### 原則9:手順書の形は、モードでも実装者でも変えない

モードで変わるのは入力と深さ、実装者で変わるのは渡し方だけとする(モードについては推奨案。21章)。

## 20. 最終的なDevexの価値

Devexの中心的な価値は、単純なコード生成ではなく、

> **要件を設計へ、設計を実装計画へ、実装計画を具体的な実装手順へ変換し、その情報をAI Coding Agentによる実装まで一貫して接続すること**

にある。

特に重要なのは、AIによる開発速度向上と、人間による設計・実装・保守への理解を両立させることである。

```text
要求
 ↓
設計
 ↓
実装計画
 ↓
実装手順(+ 実装可能性チェック) ──→ 不足をヒアリング・設計へ戻す
 ↓
実装
 ↓
テスト
 ↓
変更
 ↓
影響分析
 ↓
再設計
```

この開発ライフサイクル全体の情報連続性をDevexで維持する。

> **Phase 25 で決定済み**。決定は [`textbook/Phase-25/Phase-25-1.md`](../textbook/Phase-25/Phase-25-1.md)(1: 形は共通・簡易モードも後半で作る / 2: 実装計画書の WBS を縦割り・ID 付きに / 3: 段階7を改修し `M-01-T01` / 4: 自明な作業と順序の理由だけ / 5: 検証と AI の2層、設計の側で直す / 6: zip と画面の両方 / 7: 選んだ単位を上限5 / 8: 単位ごとの観点まで)。あわせて、段階5の手順から導くシーケンス図を手順書に載せることにした([`Phase-25-5.md`](../textbook/Phase-25/Phase-25-5.md))。

1. **モードで分ける範囲**: 入力と深さだけを分け、出力の形は共通にするか(推奨)。出力の形もモードで変えるか。簡易モードで手順書を作れるようにするか(作る前提で検討中)。
2. **簡易モードの単位の作り方**: 手順書の生成時に WBS・モジュール一覧・DF から作るか。実装計画書のプロンプトを変え、WBS を機能ごとの縦割り・ID 付きにするか。
3. **単位の ID の形式**: `M-01-T01` のように実装計画から導くか。段階7 のタスクに ID を持たせるか。
4. **参照と固有の境界**: 「実装の要点」に何を書いてよいか。設計に無いが自明なこと(マイグレーションの追加など)の扱い。
5. **未定義の出し方**: 決定論的な検証と LLM の指摘の分担。決まった内容を設計へ反映する流れ(段階の差し戻しとの関係)。
6. **AI 向けの出力の形式**: 単位ごとの md に、参照を展開して添えるか。コピー用のプロンプトを画面に出すか。
7. **生成の量**: 段階5・6 と同じく、人が選んだ単位だけを上限つきで作るか。マイルストーンごとに作るか。
8. **テストの範囲**: ステージ5 とステージ8 の境界(単位ごとの観点まで、で十分か)。
