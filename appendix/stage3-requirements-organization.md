### 最終ビジョン(2026-09-29 共有)と Stage 3 の位置づけ

1. AI との対話で要件と基本設計書を書く(完了。基本設計は要件定義書 + 外部設計書)
2. 基本設計書から詳細設計を書き起こす(**① Stage 3**。詳細設計は内部設計書 + 図)
3. 詳細設計の細かい部分を人力で手直しし、基本設計書に反映する(**② Stage 3**)
4. 基本設計と詳細設計を元に、AI での自動コーディングでイメージしたシステムが完成する(最終目標。**Stage 3 のスコープ外**)

- **①**: 内部設計書(散文)は AI が書き、意味モデルの図がそれを人が理解するために補完する。
- **②**: 図と詳細設計の手直しを基本設計へ戻す。基本設計は散文なので、決定的な置換ではなく **AI の修正案 + 人の承認** で反映する(M9)。
- **④の位置づけ**: 具体的に取り掛かる内容ではなく、製図のクオリティを測る指標として置く。図の粒度を、「その図から自動コーディングしても、設計者のイメージから大きく外れない」水準にする。
  - 現在の要件定義書の Out of Scope(設計書から自動でコードを生成する機能)は変更しない。
  - 指標としての使い方は 4章の「品質指標」に置く。

## 3. decitima の図生成機構(調査結果)

場所は `decitima/textbook/architecture/diagrams/src/`(`engine.py` 約950行、`build.py`、`defs_*.py`)。

- **定義は Python の DSL**: `Diagram(id, title, lanes)` に `node(id, lane, row, text, kind, color)` / `edge(a, b, label, dash, ...)` / `group()` を並べる。レーン(列)と行は定義側が明示し、エンジンは矢印だけを自動ルーティングする。
- **1つの定義から `.drawio` と `.svg` を同時出力**する(`to_drawio()` / `to_svg()`)。外部レイアウトライブラリも DOM も使わない、純 Python の決定的な処理。
- **共通プリミティブ**: ノード種別は `proc` / `dec`(六角形=分岐)/ `term` / `store`(円柱)/ `ent` / `table`(ER 用)/ `note`。色は `PALETTE` で意味(llm / pg / rds / err / ok / ext)に固定。
- **draw.io 出力**: レーンは `swimlane` セル。辺は `orthogonalEdgeStyle` に `exitX` / `entryX`(出入口)と `mxPoint` の折れ点を計算して埋め込む。
- **経路探索**: 出入りする辺 × 折れ線の型(direct / L1 / L2 / gap / gutter)の候補を全列挙し、ノード衝突・他の辺との交差・折れ数のコストで最良を選ぶ。出入口の並びと通路スロットの並びも山登りで最適化する。
- **記法ごとの使い方**:
  - DFD: 同じエンジン。`allow_swap()` で行の入れ替えを許し、`optimize()` の山登りで交差を減らす。
  - アクティビティ図: 同じエンジンで `dec` / `term` ノードとレーン(swimlane)を使う。
  - ER 図: `table` ノード(行=カラム)と `arrow=False` の辺。ラベルは `1 : N CASCADE` の形式。
  - 状態遷移: `term` / `proc` ノード。
- **測定**: 交差数・重なり数・ノード衝突数・ラベル衝突を数値で報告する(`build.py`)。
- **日本語対応**: 文字幅の見積もり(`tw` / `cw`)と禁則処理付き折り返し(`wrap`)を自前実装。幅は 960px 上限(`assert`)、文字は 14px 固定。

### Devex への示唆

1. 「ノード種別 + レーン + グループ + 直交辺」のプリミティブで **component / ER / activity / DFD の4記法が同じ描画・出力経路に載る**。記法ごとに新しく要るのは「意味モデル → プリミティブ」の写像と編集パネルだけ。sequence(ライフライン)はプリミティブが別のため対象外のまま。
2. draw.io Generator と SVG 出力がほぼ既存資産になる。UML文書の Should「SVG 出力」は追加コストがほぼ無い。
3. 決定的な出力と測定指標は、UML文書の NFR-002(再現性)、Snapshot Test、Level 2 再現性にそのまま使える。
4. 前提の差が3つある(診断3で扱う)。
   - レーン/行を人手で与えている。AI 生成モデルにはレーン/行の割り当てアルゴリズムが新規に要る。
   - 幅 960px 超で `assert` が落ちる。検証エラーへの変換が要る。
   - `_score()` が毎回全経路を再計算するため、大きい図で遅い。スレッド実行とノード数上限が要る。

## 4. 要件整理(ステージ3 MoSCoW 案)

### Must

| ID | 内容 |
|---|---|
| M1 | 設計図の生成。承認済み4文書を入力に、AI が意味モデル(構造化 JSON)とレーン割り当てに必要な属性(layer / actor 等)を生成する。「設計図を生成する」ボタンで起動する(4.4-2) |
| M2 | 図記法は component / ER / **処理別 DFD**(2026-09-29 に DFD を Should から引き上げ) |
| M2b | データ辞書。プロジェクト共通の `DataItem`(名前、フィールド名の一覧)を持ち、DFD の全フローは `DataItem` への参照にする(自由記述ラベルにしない)。処理ノードには「入力 → 出力」の対応と加工の1行説明を持たせる |
| M3 | 永続化。`uml_diagrams`(project_id FK、JSONB × 3、status、version)。所有権は `CurrentProjectDep` で検証 |
| M4 | バリデーション(ID 重複 / 参照切れ / 関係種別 / 必須 / 座標 / 型 / 幅・ノード数上限 / DFD 規則。DFD 規則は診断8)。承認前に必須 |
| M5 | レビュー UI。React Flow プレビュー、ノード移動、要素・関係の編集、保存 |
| M6 | 自動レイアウト(初回・再実行)。手動座標は自動レイアウトで上書きしない |
| M7 | 状態遷移 draft → reviewing → approved → exported。approved 後の編集で reviewing に戻す |
| M8 | draw.io Generator(決定的、AI 非依存、XML エスケープ)と `.drawio` ダウンロード(approved のみ)。SVG 出力は同じエンジンが同時に出すため、M9a の前提として Should から引き上げてここに含める |
| M9a | 図による詳細設計の補完(後半)。散文の内部設計書の該当箇所に、承認済みの図と要素表を対応づけて見せる。UI のドキュメントプレビューでアンカーの位置に SVG を差し込み、ダウンロードは md + 図ファイル(SVG / drawio)の zip にする(D8)。md 単体では図が見えない点は受容する |
| M9b | 手直しの反映(後半)。承認済みの図の変更を、AI が基本設計・内部設計(散文)への**修正案(差分)**にし、人が承認して反映する。差分レビュー UI が要る |

### Should / Could / Won't

**品質指標(2026-09-29。Must の受け入れ基準として使う)**: 図の粒度は、実装者が追加の設計判断をせずにコードへ落とせる水準を目安にする。具体的には次が図と要素表から読み取れること。
- モジュールの境界と責務
- 処理ごとの入力・出力データと加工の内容
- データ項目のフィールド名
- ER のテーブル、カラム、PK / FK、多重度

データ項目の型と必須は、現時点ではスキーマに任意項目として持たせるだけにする(M2b の決定は「名前 + フィールド名の一覧」のまま)。既存の自己診断(`_self_diagnose`)に「実装者が迷う点」の観点を足す案を Should に置く。

- **Should**: activity の記法追加(同一プリミティブで追加コスト小)、undo / redo、楽観ロック、draw.io 生成前の変換検証、非機能要件チェックリストの自己診断への取り込み
- **Could**: sequence / class(Stage 3 に Mermaid は入れず、必要になれば Stage 4 で Mermaid を検討する。D7)、FR-016 のうちデータ辞書の共有を超える全面的な図間整合性検証、AI レビュー提案、PNG / PDF、差分表示
- **Won't**: draw.io の完全再現、AI による draw.io XML の直接生成、PPTX 主体、複数人同時編集

## 5. 診断(#28 の3段階)

### 最重要

1. **UML文書内の矛盾**: 制約13(初期は component のみ)と Must 6(クラス名・属性・メソッド編集)が食い違う。→ FR-006 の class 項目は初期対象外(Could)に切り分ける。
2. **React Flow の表現力**: component と ER は素直。activity / DFD は decitima のプリミティブ(六角形の分岐、term、円柱の store、swimlane)を React Flow のカスタムノードと親グループノードで再現すれば可能。sequence は不向きなので Could のまま。
3. **自動レイアウトの実行環境(前回案を変更)**: 前回は「フロントで ELK.js / Dagre を計算し PUT で保存」を推奨したが、decitima のエンジンが使えるなら **バックエンド(Python)で完結**させる案が有力。理由は、決定的で再現性(NFR-002)が高いこと、draw.io / SVG 出力と同一コードで座標が一致すること、日本語の文字幅見積もりを共有できること、ELK.js のための Node プロセス問題が消えること。UML文書 2.6 の `POST /diagrams/{id}/layout` はサーバー計算としてそのまま成立する。
   - 新規に要るもの:
     - レーン/行の割り当て(レーンは AI 出力の layer / actor 等、行は最長経路法による層分けと循環辺の除去。DFD や一部の component は `allow_swap` の山登りで交差を減らす)
     - 上限超過の検証エラー化
     - `asyncio.to_thread` での実行とノード数上限(目安30)
     - 計算したノードの幅・高さを Layout Model に保存して FE に渡す(React Flow の表示寸法と draw.io を一致させる。Level 2 再現性)
   - Layout Model の拡張案: ノード箱 `{x, y, w, h}` に加え、辺の折れ点 `points` と `lane` / `row` をオプションで保持する(UML文書 2.3 の layout は箱のみ)。
   - ユーザーがノードを手動移動した後の辺の扱いは、折れ点を捨てて draw.io の `orthogonalEdgeStyle` と React Flow の smoothstep に任せる(D2 で決定)。
4. **Gemini Flash-Lite の無料枠**: 4文書生成(5回)に加え、図ごとに構造化出力の呼び出しが増える。`LLM_QUOTA_EXCEEDED` / `llm_retry` を再利用し、図ごとに独立実行し、生成数の上限を要件にする。
5. **書き戻しとバージョン**: `create_version` は追加のたびに古い版を削除して3件を維持する。書き戻しで呼ぶと、ステージ2で「復元は新バージョンを作らない」と決めた理由(キャップの無駄な消費)がそのまま当たる。
   - **案A(表・図の決定的な差し込みで採用。D1)**: `is_current` 行の `content` をアンカー間だけ in-place 更新する。version は据え置き、キャップは消費しない。代償は次の3点。
     - 「既存版の内容は書き換えない」という不変条件(`restore_version` の docstring)の例外を1つ作る
     - 書き戻し前の内容が履歴に残らない(ただし正本は `uml_diagrams` で、要素表は決定的に再生成できる)
     - 文書の再生成・復元で書き戻し内容が消えるため、診断7の stale 検知と「再反映」導線が前提になる
   - 案B(承認済み AI 修正案の適用で採用。診断9): `create_version` で新版を追加する。決定的な差し込みに使うと、反映3回で AI 生成の原本が押し出されるため、差し込みには使わない。
   - 案C: 保存せず GET / ダウンロード時に要素表を合成する。二重管理は無いが、全経路に合成が入り `content` の意味が変わる。見送り(Could)。
6. **既存4文書にアンカーが無い**: `_DOC_TYPE_PROMPTS` へのアンカー導入は既存 Phase の改訂(#12)にあたる。LLM がアンカーを落とした場合のフォールバック(見出しに基づく挿入 / 末尾付録)と、生成済み文書への初回挿入方法が必要。
7. **陳腐化(stale)の双方向化**: (a) 図承認後に編集すると反映済み文書が古くなる(UML文書 4.4-5)。(b) 文書が再生成・復元されると図が古くなる(UML文書に記載なし)。図に `source_doc_versions` を持たせて検知する。

- UML文書の 2.14 節が重複している。
- draw.io の日本語フォントを指定する。ダウンロード名はユーザー入力から直接生成しない(既存ダウンロードの filename / CORS `expose_headers` の前例に合わせる)。
- draw.io ファイルの実体は保存せず、都度決定的に生成する。
- `stage2-phase6` ブランチに未コミットの変更がある。ステージ3着手前に整理してマージする。

8. **処理別データフロー図の要件(2026-09-29 追加)**: 「モジュール依存だけでなく、どのデータがどう処理されてモジュール間を渡るかが分かる図」を Must にする。
   - **decitima に足りない点**: フローのラベルが自由記述で、何のデータかが定義されていない。処理が入力をどう加工して出力にするかを持てない。→ データ辞書(`DataItem`)への参照と、処理ノードの変換説明を意味モデルに足す(M2b)。
   - **DFD 規則の検証**(M4)。機械的に検証でき、LLM 出力の誤りを止められる。LLM は間違えやすいので、エラーと警告に分ける。
     - 全フローがデータ項目を持つ
     - 全処理に入力と出力が1つ以上ある
     - ストア同士、外部実体とストアを直接つなぐフローがない
     - 上位図と下位図の境界フローが一致する
     - どこからも参照されないデータ項目がない
   - **図の共有による整合性**: データ辞書をプロジェクト共通にすると、データ項目が ER 図のテーブルや API のスキーマと同じものを指すことを確認できる。FR-016(図間整合性)を全面実装せずに、最も効く部分だけを取れる。
   - **書き戻す要素表**: 「元 / データ / 変換 / 先」の表にする。図を見なくても文書だけで理解できる。書き戻しを要素表のみとした決定と噛み合う。
   - **粒度と枚数**: API エンドポイント / バッチごとに1枚(モジュール単位の詳細図)。図が数十枚になり得るため、AI 呼び出しが枚数分に増える。Gemini Flash-Lite の無料枠に効くので、枚数の上限と対象の選択を要件にする(診断4)。ラベルにはデータ項目名だけを置き、フィールドは要素表側に逃がす(decitima の `label_fallback` = ラベル衝突の対策)。
   - **入力の不足**: 現在の内部設計書はモジュール構成と API 一覧を書くが、処理ごとのデータの流れを構造化して書いていない。AI が文章から推測すると品質が不安定になる。対策は、内部設計書の生成プロンプトに「処理別データフロー」の節を追加すること(既存 Phase の改訂 #12。Phase 10 で扱う)。図の下書きの品質は、承認前のレビューで人が直す。
   - **文書との対応**: DFD は `internal_design` の 3.3 節付近に割り当てる想定(D5 の材料)。

9. **反映の再設計(2026-09-29 追加)**: 内部設計書の散文を残し、②を AI の修正案 + 承認にしたことで、診断5〜7の前提が変わる。
   - **M9 を M9a / M9b に分けた**。アンカー間を要素表で決定的に置換するだけの当初案は、「図で散文を補完する」という目的に足りない。
   - **D1(書き戻しとバージョン)の決定**: 承認済みの修正案を散文に適用する場合は、人が承認した内容の変更なので履歴に残す価値が高く、案B(新バージョンとして追加)にする。3件キャップの消費は受容する。決定的な表や図の差し込みは案A(in-place)のままにする。
   - **連鎖する stale**: 基本設計を修正案で変えると、既存の文書チェーン(要件定義 → 外部設計 → 内部設計 → 実装計画。`_DOC_TYPE_INPUTS`)の下流の文書と、そこから起こした図が古くなる。診断7の stale 検知を、文書の依存関係に沿って下流へ伝える必要がある。
   - **AI 修正案の入力**: 図の変更差分(意味モデルの差分)と対象文書。図から散文への逆変換なので、誤った修正案が出る前提で、承認制と差分表示を必須にする。
   - **重さ**: 差分レビュー UI と AI 呼び出しが増えるため、Phase 13 が重い。分割するか、M9b を Stage 3 の最後に回す余地を残す。

## 6. 決定事項(2026-09-29 に D1〜D8 を確定。D5 のみ Phase 7 で確定)

| ID | 論点 | 決定 | 理由 |
|---|---|---|---|
| D1 | 書き戻しとバージョン | 表・図の決定的な差し込み(M9a)は案A(`is_current` 行を in-place 更新)。承認済みの AI 修正案の適用(M9b)は案B(新バージョンとして追加) | 決定的な差し込みは正本(`uml_diagrams`)から再生成でき、キャップを消費させたくない。人が承認した散文の変更は履歴に残す価値が高い |
| D2 | 手動移動後の辺の扱い | 折れ点を捨て、draw.io は `orthogonalEdgeStyle`、React Flow は smoothstep に任せる | decitima の経路探索はレーン × 行の格子が前提で、自由座標への拡張は重い |
| D3 | decitima エンジンの取り込み方 | コピー + 出自明記。取り込み時にライセンスと出自表記を確認する | 別リポジトリ間の依存を作らない |
| D4 | activity の位置づけ | Should。Phase 14 で追加 | 同じプリミティブで載るので追加コストが小さいが、Must の DFD / component / ER を優先する |
| D5 | 図と文書セクションの対応表(4.4-1) | **Phase 7 の設計フェーズで確定する**。summary の対応表を材料にし、DFD は `internal_design` 3.3 節付近を想定 | 実際の文書構成を見ながら決める必要がある |
| D6 | エクスポート後の手直しの扱い | ダウンロードは最終成果物。以降の修正は Devex の UI で行う。`exported` 後にファイルを直した場合は Devex に反映されないと画面で明示する。draw.io の再インポートは対象外 | 再インポート(XML から意味モデルへの逆変換)は重く、JSON 正本と食い違う原因になる |

| D8 | 図による補完の埋め込み方式(M9a) | UI のドキュメントプレビューでアンカーの位置に SVG を差し込み、ダウンロードは md + 図ファイル(SVG / drawio)の zip。md 単体では図が見えない点は受容する | 図の見た目が draw.io と一致し、エンジンが SVG を同時に出すので追加コストが小さい |

## 7. 構成案

```
生成: 4文書(is_current) → AI(構造化出力) → 意味モデル(JSON) → Validation → uml_diagrams(draft)
レイアウト(BE, 決定的): 意味モデル → レーン/行割り当て → 経路探索 → Layout Model(箱 + 折れ点)
表示: Layout 込みモデル → [FE] toReactFlow → React Flow → 編集 → fromReactFlow → PUT(version check)
承認: validate OK → approved → export/drawio | export/svg(同一エンジン) → exported
反映(M9a): approved → 要素表レンダラ → アンカー間を in-place 置換(案A) + プレビューで SVG 差し込み
反映(M9b): 図の変更差分 → AI 修正案 → 人が承認 → 新バージョンとして適用(案B)
古くなった場合: 反映後編集・文書再生成 → stale 表示(文書の依存関係に沿って下流へ伝播)
```

- **バックエンド** `devex-api/backend/app/uml/{domain,layout,export,sync,validation}`、`models/uml_diagram.py`、Alembic migration、`api/routes/uml.py`。
  - `layout` と `export` は decitima エンジン(`Diagram` / `route` / `to_drawio` / `to_svg`)の移植。
  - 意味モデルから `Diagram` への記法別マッパー(初期は component / ER)を新規に書く。
- **フロントエンド** `devex-ui/src/features/uml/{components,adapters,api}` と `app/projects/[id]/uml/page.tsx`。
- **再利用するもの**: `CurrentProjectDep`、`GeneratedDocumentRepository`(`get_current` / `is_current`)、`llm_retry`、共通エラー形式、`apiFetch`、Tamagui の `"use client"` 分離の知見。
