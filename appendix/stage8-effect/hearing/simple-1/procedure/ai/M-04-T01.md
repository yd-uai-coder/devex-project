### 内部設計書 3.4 例外処理・エラー・ログ

例外処理・エラーハンドリング方針:
- 共通エラーレスポンス形式として、HTTPステータスコードに応じたJSONオブジェクト（error, message, details）を返却する。
- 認証失敗は 401、権限・所有者違反は 403、リソース不存在は 404、入力不備は 400、レート制限超過は 429、AI応答失敗や生成失敗は 500 を返す。
- Redisを利用したレート制限ミドルウェアにより、不正な大量アクセスや無料枠の保護を行う。
- セキュリティ要件（NFR-007）に基づき、ログにはプロンプトやチャットの本文を残さず、メタデータとエラーコードのみを記録する。

### 実装計画書 4.3 開発環境

開発言語はPython 3.13およびNext.js(App Router)を用い、データベースにはPostgreSQLおよびRedisを採用する。サーバー環境としてDocker ComposeとnginxをVPS上に構築し、GitHub Actionsを用いて自動デプロイを実施する。テスト・自動化およびコード品質維持のため、適切なユニットテスト・統合テストを継続的に行う方針とする。

### 内部設計書 3.1 技術スタック・アーキテクチャ

技術スタック:
- フロントエンド: Next.js (App Router), Tamagui
- バックエンド: FastAPI, Python 3.13, LangChain, LangGraph
- データベース: PostgreSQL (リレーショナルデータ保存), Redis (レート制限およびトークン失効管理)
- インフラ: VPS, Docker Compose, nginx, GitHub Actions (自動デプロイ)

アーキテクチャ方針:
フロントエンドはSSR/CSRを適切に組み合わせたNext.js App Router構成を採用し、Tamaguiによりクロスプラットフォーム対応のUIを構築する。バックエンドはFastAPIによる非同期REST APIサーバーを構築し、LangChainおよびLangGraphを用いてGemini Flash-Liteとの対話フローや設計書生成ワークフローを制御する。セキュリティ・不正利用対策としてRedisを用いたレート制限ミドルウェアを導入し、全APIへのアクセス制御を行う。

## 今回の実装単位

M-04-T01 設計書一括生成・自己診断およびプレビュー機能の実装(種別: 機能 / 処理: DF-3, DF-4, DF-9)

実現する要件:

- FR-002: チャットヒアリングを通じて要件や要望を収集し、4種の設計書（要件定義、外部設計、内部設計、実装計画）を一括生成する。
- FR-003: 生成後にAIが各文書の不足点を3段階（最重要/中程度/軽微）で自己診断して提示する。
- FR-004: 生成したMarkdownをプレビュー・コピー・ダウンロードできる。
- FR-006: ユーザー、チャット履歴、生成文書をPostgreSQLに保存する。
- FR-007: AIの応答が失敗した場合は理由を出しメッセージを保存せずに再送を促し、生成失敗時は再生成を行えるようにする。

目的: 4種設計書および自己診断の一括生成、保存済み設計書の履歴一覧取得、個別詳細取得のAPIエンドポイントと関連するサービス・リポジトリ処理を実装する。

前提: M-03-T01 まで実装済み
