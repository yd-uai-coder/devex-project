## 設計レビュー
指摘 12件(最重要 3・中程度 8・軽微 1)

1. **[最重要 / 設計]** projects, chats, documents, summaries, POST /api/v1/projects/{id}/chat, GET /api/v1/projects/{id}/documents, F-03
   - 問題: プロジェクトを所有ユーザーに結び付けるデータがなく、{id} 付き API でトークンの持ち主がそのプロジェクトの所有者かを確かめる処理もない。他人のプロジェクトのチャット・資料・生成文書を見たり書き換えたりできてしまう。
   - 引用: projects テーブルの列は「id」「name」のみ。F-03 は「ProjectRepository.find_all_by_user_id」を呼ぶが user_id 列が無い。F-05/F-06/F-07/F-08 の手順はトークン検証だけで所有確認がない。
   - 理由: NFR-008・FR-001 のセキュリティ観点を満たさず、F-03 の絞り込みもデータモデル(03 データモデル)上成立しない。
   - 改善案: projects に user_id(FK users)を追加し、{id} を取る全 API で所有者確認を行い、他人の ID には 404 か 403 を返す旨を外部設計書と詳細設計書に書く。
2. **[最重要 / 設計]** summaries, documents, FR-008, FR-006, FR-004, SCR-005
   - 問題: 生成文書の本文・種別・版番号・自己診断結果・構造化サマリの本文を保存するテーブルや列がない。直近3件の版管理(FR-008)と自己診断の表示(FR-006)を実現できない。
   - 引用: summaries の説明は「構造化サマリ承認データ・生成文書および版履歴データテーブル」だが、列は id・project_id・approved のみ。documents は content(参考資料テキスト)のみ。
   - 理由: F-07#7 の「生成された4種文書をデータベースに保存する」と F-08 の「直近3件の版履歴を取得する」の保存先が、データモデルにない。
   - 改善案: 生成文書用のテーブル(project_id・文書種別・版番号・本文・自己診断結果・作成日時)と、構造化サマリ本文の列を追加し、参考資料用の documents と分ける。
3. **[最重要 / 設計]** F-07, POST /api/v1/projects/{id}/summary/approve, SCR-005, FR-009
   - 問題: 文書生成は非同期で始まるのに、進捗・完了・失敗を確認する API も状態の列もなく、バックグラウンドでの失敗時の扱いも書かれていない。F-07 の手順 5〜7 は同期の流れとして描かれ、承認 API に「500 生成失敗」が残っている。
   - 引用: F-07#5「generate_documents_async … バックグラウンドで開始する」、手順 6・7 が同期の呼び出しとして続き、手順 8・9 で応答を返す。API一覧: 「200 OK (生成開始) / 500 生成失敗」
   - 理由: FR-009「生成失敗時は再生成できるようにする」と NFR-003「4文書生成は数分以内」に対し、生成中や失敗の状態を利用者に見せる手段がない。
   - 改善案: 生成状態(生成中・完了・失敗)を持たせ、状態取得 API を追加し、手順 5 以降を非同期として描き直す。同期応答で 500 を返す記述は見直す。
4. **[中程度 / ヒアリング・観点 security]** FR-001, NFR-008
   - 問題: セキュリティが「ログインをMVPに入れる」だけで、誰が誰のデータを見られるか、トークンの有効期限、ログアウトや失効、パスワードの条件が決まっていない。
   - 引用: security: 「ログインをMVPに入れる」(AI の提案を採用)。FR-001「ユーザー登録およびログイン機能を提供する」
   - 理由: 公開サービス(scale)でありながら本人以外の閲覧・変更の可否とトークンの扱いが要件にないため、設計側で認可やトークン管理を決められない。
   - 改善案: 利用者に、プロジェクトは作成者本人だけが閲覧・変更できてよいか、トークンの有効期間、ログアウトの要否、パスワードの最低条件を聞き、要件に追記する。
5. **[中程度 / ヒアリング・観点 abuse]** NFR-008
   - 問題: 不正利用対策の回数上限の値・単位・対象(IP かユーザーか、1時間あたりか1日あたりか)が決まっていない。
   - 引用: NFR-008「ログインの総当たり、登録の大量作成、チャットや生成の回数上限を設けて不正利用を防ぐ」
   - 理由: 上限値と単位がないと、レート制限の実装も、超過時の応答(429 など)の設計もできない。
   - 改善案: ログイン失敗、登録、チャット、生成のそれぞれについて、上限の値と単位、超過後の待ち時間を利用者に聞く。
6. **[中程度 / 不整合]** NFR-008, app/cache/token.py, 2.6 API一覧, F-01, F-05, F-07
   - 問題: レート制限が API・処理手順のどこにも組み込まれておらず、制限超過のエラー応答もない。
   - 引用: app/cache/token.py の責務に「Redisを用いたトークン管理とレート制限処理を行う」とあるが、関わる処理は F-02 のみ。API一覧のエラー欄に 429 がない。
   - 理由: NFR-008 が登録・チャット・生成に及ぶのに、設計で満たされていない。
   - 改善案: レート制限のチェック手順と 429 応答を、登録・ログイン・チャット・承認(生成)の各処理と API 一覧に追加する。
7. **[中程度 / 設計]** SCR-003, SCR-004, SCR-005, FR-004, FR-009, 2.6 API一覧
   - 問題: 画面にある操作の API が足りない。ヒアリング完了と構造化サマリ生成、サマリ取得、サマリ修正依頼、チャット履歴取得、再生成、版切り替え・版指定取得、自己診断結果の取得がない。
   - 引用: SCR-003「ヒアリング完了ボタン」、SCR-004「承認して文書生成へ進むボタン、修正依頼ボタン」、SCR-005「再生成ボタン、版切り替えボタン」「チャット履歴」。API一覧は chat・upload・summary/approve・documents の取得のみ。
   - 理由: FR-004(サマリ確認)と FR-009(再生成)が API なしでは動かず、サマリ表示用の内容がどこから来るかも決まらない。
   - 改善案: サマリ生成・取得・修正依頼、チャット履歴取得、文書の再生成、版指定取得の API を追加し、対応する処理と画面の対応も更新する。
8. **[中程度 / 設計]** F-05, F-07, LLMClient.invoke_chat, LLMClient.generate_four_documents, F-06
   - 問題: AI 呼び出しに渡すデータが足りず、保存した参考資料やチャット履歴が使われていない。
   - 引用: F-05#4「LLMClient.invoke_chat | プロジェクトID、チャットメッセージ」、F-07#6「generate_four_documents | プロジェクトID、構造化サマリデータ」。F-06 で documents.content に保存した参考資料の参照が F-05・F-07 にない。
   - 理由: FR-003「参考資料をテキスト化して保持する」の目的が果たされず、チャットも履歴を踏まえた文脈のあるヒアリングにならない。
   - 改善案: F-05 でチャット履歴と参考資料テキストを AI に渡し、F-07 でも参考資料と履歴を入力に含める手順をデータフローに書く。
9. **[中程度 / 設計]** F-05, F-07, FR-009, CON-004
   - 問題: AI 応答失敗・無料枠の上限超過・タイムアウトの分岐が処理手順にない。失敗時に先に保存したユーザーメッセージをどうするかも決まっていない。
   - 引用: F-05#3 でメッセージを先に保存してから #4 で LLM を呼ぶ。#3〜#5 を1トランザクションとするが、LLM 失敗の分岐(1a・1b 以外)がない。FR-009「メッセージを送らずに再送を促し」
   - 理由: FR-009 と CON-004「上限超過時はエラー処理を挟む」が処理に落ちておらず、API 一覧の「500 AI応答失敗」とも手順が対応しない。
   - 改善案: F-05#4 と F-07#6 に LLM 失敗・上限超過の分岐と、メッセージを保存しない(または巻き戻す)扱いを追加し、理由を返すエラー応答を定義する。
10. **[中程度 / 不整合]** tokens, F-02, L-04, CON-003, app/cache/token.py
   - 問題: トークンの保存先と形が文書によって食い違う。Redis とする記述と tokens テーブル(DB)とする記述が混在し、テーブルに有効期限もない。
   - 引用: CON-003「トークン失効用にRedisを使用する」/ F-02#4「Redisを使用して認証トークンを発行・保存する」だが DB 操作欄は「tokens C」/ tokens は id・token・email のみ / L-04「キャッシュまたはtokensテーブルを参照」
   - 理由: 有効期限や失効を判定できず、F-02#4 は「ユーザーID」を渡すのにテーブルは email を保持するなど、データも合わない。
   - 改善案: トークンは Redis に TTL 付きで持つのか DB に持つのかを一つに決め、tokens テーブルの要否・列(user_id・有効期限)を直して CRUD 図と手順を揃える。
11. **[中程度 / ヒアリング・観点 exceptions]** FR-010, FR-003, F-05, F-06
   - 問題: チャットの「数千文字まで」が具体値になっておらず、参考資料のファイルサイズ・ページ数の上限も決まっていない。
   - 引用: FR-010「チャットは数千文字までとし空送信は不可とする」。FR-003 とアップロード API にサイズ上限の記述がない。
   - 理由: バリデーションの閾値が決まらず、無料枠の LLM(CON-004)に渡せる量や DB 容量にも関わる。
   - 改善案: チャットの上限文字数、資料のファイルサイズ上限、PDF の扱い(画像のみの PDF など)を利用者に聞いて要件に記す。
12. **[軽微 / 不整合]** L-02, L-05, F-02, F-04
   - 問題: 処理ロジックの例外と手順表の例外が一致しない。L-02 は例外「なし」だが F-02#3a は AuthenticationError → 401 としている。L-05 は ValueError、F-04#3a は AuthError。
   - 引用: L-02「例外 | なし」/ F-02#3a「AuthenticationError → 401 Unauthorized」/ L-05「ValueError: トークンが無効または期限切れの場合(HTTP 401)」/ F-04#3a「AuthError → 401」
   - 理由: 例外の型が手順と処理ロジックで食い違い、main.py の例外変換の実装が揺れる。
   - 改善案: L-02 に AuthenticationError、L-05 に AuthError を書いて手順表と揃える。L-02 の戻り値にトークン発行も含めるか整理する。
