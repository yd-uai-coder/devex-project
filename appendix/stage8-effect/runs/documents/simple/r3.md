## 設計レビュー
指摘 18件(最重要 4・中程度 13・軽微 1)

1. **[最重要 / 不整合]** FR-010, NFR-006, 1.3 システム化の範囲
   - 問題: FR-010 は共有リンクでログインしていない人にも設計書を公開するとしているが、NFR-006 は他人のプロジェクト閲覧を不可としており、両立しない。ヒアリングの core 観点にも共有リンクは無い。
   - 引用: FR-010「生成した設計書を共有リンクで公開し、ログインしていない人も閲覧できるようにする」/ NFR-006「機密性保持のため他人のプロジェクト閲覧を不可とする」
   - 理由: 要件定義書 1.4 と 1.5 が衝突している。FR-010 がコア機能として出てくる根拠もヒアリングに無く、公開範囲と認可の設計を決められない。
   - 改善案: FR-010 を MVP に含めるか利用者に確認する。含めるなら、リンクを知る人のみ閲覧可・期限・無効化などの条件を決めて NFR-006 との整合を取る。含めないなら FR-010 を削除する。
2. **[最重要 / 不整合]** users, backend/core/security.py, FR-002
   - 問題: users.password は平文保存・そのまま照合する前提になっているが、security.py の責務は「パスワードのハッシュ化」である。
   - 引用: password | VARCHAR(255) | NOT NULL | パスワード(ログイン時にそのまま照合する)
   - 理由: 内部設計書 3.2 と 3.3 が矛盾している。公開サービスでの平文保存は NFR-006 の機密性にも反する。
   - 改善案: password を password_hash(bcrypt/argon2 など)に改め、DF-1・DF-2 にハッシュ化と照合の変換を明記する。
3. **[最重要 / 設計]** POST /api/v1/chat/messages, DF-4, chat_messages
   - 問題: チャット送信 API の本文が message だけで、どのプロジェクトのメッセージか特定できない。DF-4 は project_id を保存するとしているが、受け取る入力にその値が無い。
   - 引用: POST /api/v1/chat/messages | ... | 本文: message
   - 理由: プロジェクトを特定できなければ、履歴の取得・保存先・NFR-006 の所有者確認ができない。
   - 改善案: 本文または URL に project_id を含め(例 /api/v1/projects/{project_id}/messages)、DF-4 の入力にも反映する。
4. **[最重要 / 設計]** POST /api/v1/chat/messages, POST /api/v1/documents/generate, NFR-006
   - 問題: chat と generate に認証(401)・認可(403/404)のエラー応答が無く、project_id の所有者確認も処理に無い。
   - 引用: POST /api/v1/documents/generate ... 本文 project_id ... エラー: 500 生成失敗(再生成可能)
   - 理由: NFR-006 は他人のプロジェクト閲覧を不可としている。project_id を指定するだけで他人の履歴・設計書を使って生成できてしまう。
   - 改善案: 全 API に認証必須と所有者確認(user_id と projects.user_id の一致)を定め、401・403/404 を各 API のエラーに追加する。DF-4・DF-5 にも所有者確認の変換を入れる。
5. **[中程度 / 不整合]** 1.3 システム化の範囲
   - 問題: In Scope に「Jira連携による課題の自動登録」があるが、Out of Scope には「Jira・Notion連携」がある。
   - 引用: In Scope: Jira連携による課題の自動登録 / Out of Scope: Jira・Notion連携
   - 理由: 同じ要件定義書 1.3 の中で範囲が食い違っている。ヒアリング scope は Jira 連携を最初の版の対象外としているが、画面・API・実装計画に Jira 連携は無い。
   - 改善案: ヒアリングの scope に合わせて In Scope の Jira 連携を削除する。
6. **[中程度 / 不整合]** POST /api/v1/auth/login, FR-002, DF-2
   - 問題: FR-002 はトークンを HttpOnly Cookie に保存するとしているが、外部設計書はトークンを本文で返して localStorage に保存するとしている。内部設計書の login は「Cookieを設定する」としている。
   - 引用: 200 ログイン成功(アクセストークン・リフレッシュトークンを応答の本文で返し、フロントエンドは localStorage に保存する)
   - 理由: 要件 FR-002・ヒアリング security と外部設計書 2.6 が食い違い、内部設計書 3.3 とも食い違う。localStorage 保存は XSS でトークンを盗まれる。
   - 改善案: 外部設計書の login の応答を Set-Cookie(HttpOnly・Secure・SameSite)に改め、本文でトークンを返さない。DF-2 もそれに合わせる。
7. **[中程度 / 不整合]** 3.4 例外処理・エラーハンドリング・ログ設計, NFR-007
   - 問題: 3.4 は機密情報や入力内容を一切ログに残さないとしながら、AI応答失敗時にチャット入力内容とプロンプト全文をログに出す方針を書いている。
   - 引用: ただし障害調査のため、AI応答失敗時はチャットの入力内容とプロンプト全文をログに出力する方針とする。
   - 理由: NFR-007「機密情報や入力内容は一切ログに残さず」と直接矛盾する。
   - 改善案: 入力内容・プロンプトのログ出力を削除し、エラーコード・日時・リクエストIDだけを出す。
8. **[中程度 / 設計]** SCR-003, FR-006, SCR-002, API一覧
   - 問題: 生成済みの設計書・自己診断結果・チャット履歴を取得する API が無く、SCR-003 のプレビューやダウンロードにデータを渡す経路が無い。
   - 引用: | FR-006 | SCR-003 | — |
   - 理由: 外部設計書の付録で FR-006 に対応する API が「—」で、プロジェクト一覧や再訪時の画面表示もできない。画面の操作ごとに API がそろっていない。
   - 改善案: GET /projects、GET /projects/{id}、GET /projects/{id}/documents、GET /projects/{id}/messages などを追加し、認可とエラー応答も定める。
9. **[中程度 / 設計]** FR-002, NFR-008, POST /api/v1/auth/login, Redis
   - 問題: リフレッシュトークン(14日)とトークン失効(Redis)を使う前提だが、トークン更新・ログアウトの API が無く、DF にも失効の処理が無い。
   - 引用: Redis(レート制限・トークン失効) / API一覧は register・login・projects・chat/messages・documents/generate の5件のみ
   - 理由: アクセストークンは30分で切れるため、更新 API が無いと30分ごとに再ログインになる。失効の経路もデータフローに無い。
   - 改善案: POST /auth/refresh と POST /auth/logout を追加し、Redis での失効登録と検証を DF に書く。
10. **[中程度 / 設計]** POST /api/v1/chat/messages, POST /api/v1/documents/generate, NFR-008
   - 問題: NFR-008 はチャットと生成の回数制限を求めているが、chat/messages と documents/generate に 429 の応答が無い。レート制限を行うモジュールも一覧に無い。
   - 引用: 400 空メッセージまたは文字数超過、500 AI応答失敗(メッセージ未保存) / 500 生成失敗(再生成可能)
   - 理由: 429 が書かれているのは register・login だけで、チャット・生成の制限が外部設計にも内部設計 3.3 のモジュールにも落ちていない。
   - 改善案: 両 API に 429 を追加し、レート制限ミドルウェアのモジュールとキー・上限の扱いを内部設計書に定義する。
11. **[中程度 / 設計]** POST /api/v1/documents/generate, NFR-003, FR-007, documents, diagnostics
   - 問題: 数分かかる4文書生成を同期の POST で 201 を返す設計で、タイムアウトや途中失敗・再生成時の扱いが決まっていない。documents に版や状態の列も無い。
   - 引用: 201 設計書生成・自己診断成功 / 500 生成失敗(再生成可能) / 対策: 非同期処理を活用し
   - 理由: NFR-003 は数分の待機を許容しており、nginx やブラウザのタイムアウトで切れる。4件の一部だけ保存された場合や再生成時の重複・上書きが不明。
   - 改善案: 生成をジョブ化して状態(処理中・完了・失敗)を返しポーリングで取得する。保存は全件成功時に1トランザクションで行い、再生成時は置き換えると決める。
12. **[中程度 / 設計]** DF-5, DF-3, projects.reference_file_paths
   - 問題: DF-5 は参考資料を取得すると書いているが、取得元が chat_messages のみで、projects の reference_file_paths やファイル本文の読み込み(pdf のテキスト抽出)の流れが無い。DF-3 でも保存するだけで、LLM に渡す処理が無い。
   - 引用: backend/api/v1/documents.py | project_id | チャット履歴・参考資料取得 | chat_messages
   - 理由: FR-003 で受け取った参考資料が設計書生成とチャットに使われず、データが活かされない。
   - 改善案: DF-3 でテキスト抽出と保存、DF-4・DF-5 で projects から参考資料を読む流れを追加する。
13. **[中程度 / 設計]** POST /api/v1/chat/messages, NFR-003
   - 問題: NFR-003 は「チャットの最初の文字が数秒」を求めているが、chat/messages は通常の 200 応答でストリーミングの記述が無い。
   - 引用: POST /api/v1/chat/messages ... 応答: 200 AI応答成功
   - 理由: 応答が全文生成後にまとめて返ると、最初の文字が数秒という性能要件を満たせない。
   - 改善案: SSE などのストリーミング応答とし、途中失敗時に保存しない扱いを DF-4 に書く。
14. **[中程度 / 設計]** M-01-T01, M-02-T01, M-03-T02, FR-006, SCR-001, SCR-002, SCR-003
   - 問題: 実装計画書のタスクがバックエンドだけで、SCR-001〜003 のフロントエンド実装(Next.js/Tamagui、プレビュー・コピー・ダウンロード)のタスクが無い。FR-006 は backend の generate タスクに載っている。
   - 引用: M-03-T02 ... 要件: FR-004, FR-005, FR-006 / モジュール: backend/api/v1/documents.py, backend/services/ai_service.py
   - 理由: 画面に当たるタスクが無く、FR-006 に画面側の実装が割り当てられていない。
   - 改善案: 画面ごとのフロントエンドのタスクと、API 呼び出し・状態管理のタスクを追加する。
15. **[中程度 / 設計]** NFR-002, NFR-007, NFR-008, CON-005, M-01-T01, 4.3 開発環境・CI/CD・事前準備事項
   - 問題: レート制限、nginx・HTTPS・自動デプロイ、DB バックアップ(日次7日分・VPS外コピー)、ログ方針に当たるタスクが無い。
   - 引用: M-01-T01 [基盤] プロジェクト基盤とDocker環境の構築 / 要件: なし
   - 理由: 非機能要件 NFR-002・NFR-007・NFR-008 と CON-005 を実装するタスクが WBS に無い。フェーズ1 では VPS へのデプロイも含むとされている。
   - 改善案: レート制限、nginx・TLS・GitHub Actions デプロイ、バックアップ、ログ設定のタスクを追加し、要件 ID を結び付ける。
16. **[中程度 / ヒアリング・観点 abuse]** NFR-008, FR-008
   - 問題: 不正利用の対策が「回数制限」とだけあり、ログイン・登録・チャット・生成それぞれの上限の値・単位(回/分、回/日、IP 単位かユーザー単位か)が決まっていない。
   - 引用: ログインの総当たり、登録の大量作成、チャットと生成の回数制限により不正利用を防ぐ
   - 理由: 数値が無いと Redis のレート制限を実装できない。公開サービスでは LLM のコストにも関わる。
   - 改善案: 利用者に各操作の上限値・単位・超過時の挙動を聞き直し、NFR-008 に書く。
17. **[中程度 / ヒアリング・観点 security]** FR-001, FR-002, NFR-006
   - 問題: 誰でも登録できる公開サービスなのに、パスワードの条件、メール確認の有無、パスワード再設定、ログアウトなどが要件にもヒアリングにも無い。
   - 引用: FR-001「誰でも登録できるサービスとしてユーザー登録とログイン機能を提供する」/ security「ログインはメールとパスワードのJWT認証(アクセス30分、リフレッシュ14日・HttpOnly Cookie)」
   - 理由: 普通は決めるアカウント運用の事項が決まっておらず、SCR-001 の入力検証や API の仕様を確定できない。
   - 改善案: パスワードの強度・メール確認・再設定・ログアウトの要否を利用者に聞き直し、要件に反映する。
18. **[軽微 / ヒアリング・観点 exceptions]** FR-003, FR-008, POST /api/v1/projects
   - 問題: 参考資料1件あたりのサイズ上限、pdf のページ数や文字数上限、LLM に渡せる量を超えたときの扱いが決まっていない。
   - 引用: 参考資料(txt、md、pdf、最大3件)を初期入力で読み込めるようにする / 400 ファイル形式不正または件数超過
   - 理由: 件数だけの制限では、大きなファイルでメモリや LLM の入力上限を超えうる。エラー応答にもサイズ超過が無い。
   - 改善案: サイズ上限と超過時の扱いを利用者に聞いて要件に書き、API のエラーに 413 などを追加する。
