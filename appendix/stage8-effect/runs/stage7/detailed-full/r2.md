## 設計レビュー
指摘 15件(最重要 4・中程度 9・軽微 2)

1. **[最重要 / 設計]** projects, chats, documents, summaries, F-03, F-04, F-05, F-06, F-07, F-08
   - 問題: F-03 は「ユーザーIDに紐づくプロジェクト一覧」を取得するが、projects に所有者(user_id)の列が無く、所有者を保存する経路もない。{id} を取る API でも、そのプロジェクトが本人のものか確認する処理がなく、他人のプロジェクトを読み書きできる。
   - 引用: projects テーブル: id, name のみ / F-03#4「ProjectRepository.find_all_by_user_id | ユーザーID」/ F-05#2「認証トークンを検証し、チャットメッセージのビジネスロジックを実行する」(プロジェクトの所有確認なし)
   - 理由: 要件 FR-001・NFR-008 の前提となるアクセス制御が、データモデル(03)と処理手順(05)で満たされていない。
   - 改善案: projects に user_id(FK users)を追加し、{id} を取る全 API で所有者の照合を行う。非所有者には 404 か 403 を返すと手順・外部設計に明記する。
2. **[最重要 / ヒアリング・観点 security]** FR-001, SCR-005, GET /api/v1/projects/{id}/documents
   - 問題: セキュリティが「ログインをMVPに入れる」だけで、他人のプロジェクト・チャット・生成文書を閲覧・変更できるか、トークンの有効期限・失効の扱い、パスワードの強度が決まっていない。
   - 引用: security: 「ログインをMVPに入れる」(AI の提案を採用) / 07 認証「有効期限(要決定)」
   - 理由: 要件定義書 FR-001 は登録・ログインの提供だけで、本人以外のデータ閲覧可否が決まらず、設計側にも認可を書けない。
   - 改善案: 利用者に聞き直し、データは本人のみ閲覧・変更可とするか、トークンの有効期限・ログアウト時の失効、パスワードの最低要件を決めて要件に追記する。
3. **[最重要 / 設計]** F-07, POST /api/v1/projects/{id}/summary/approve, SCR-004, FR-004, summaries
   - 問題: FR-004 は構造化サマリを確認して承認する機能だが、サマリを生成・保存・取得する処理と API がない。summaries には approved しかなく、サマリ本文の保存先も表示用 API もない。修正依頼ボタンに対応する API もない。
   - 引用: summaries: id, project_id, approved のみ / SCR-004「表示項目: 構造化されたサマリ内容 … 修正依頼ボタン」/ API 一覧に summary の GET や修正依頼の API なし
   - 理由: SCR-004 に表示するデータの取得経路がなく、F-07#6 でも使う「構造化サマリデータ」の出どころが存在せず、承認に至る流れを実装できない。
   - 改善案: ヒアリング完了時にサマリを生成して summaries に本文を保存する処理と、取得・修正依頼の API を追加する。ヒアリング完了ボタンの処理も定義する。
4. **[最重要 / 設計]** F-07, documents, FR-005, FR-006, FR-008, SCR-005
   - 問題: documents テーブルは参考資料の content しか持たず、生成した4種文書・版番号・自己診断結果を保存できない。F-07#7 は生成文書を documents に C で保存し、F-08 は直近3件の版を取得するが、種別・版番号・診断結果の列がない。
   - 引用: documents: id, project_id, content のみ / F-07#7「生成された4種文書をデータベースに保存する | documents C」/ F-08「4種文書と直近3件の版履歴を取得する」
   - 理由: 参考資料と生成文書が同一テーブルで区別できず、版管理(FR-008)と自己診断の提示(FR-006)がデータモデル上成立しない。
   - 改善案: 生成文書用のテーブル(project_id・種別・版番号・本文・自己診断結果・作成日時)を分け、直近3件の保持方法も明記する。
5. **[中程度 / 不整合]** F-07, POST /api/v1/projects/{id}/summary/approve, SCR-005, FR-009
   - 問題: 文書生成は非同期だが、進捗・完了・失敗を取得する API と状態の保存先がない。承認 API は500生成失敗を返す設計だが、実際は非同期で受付後に失敗する。再生成の API もない。
   - 引用: 実装計画 4 リスク「進捗や結果は別APIで取得する設計とする」/ SCR-005「操作ボタン: … 再生成ボタン」/ API 一覧: 200 OK (生成開始), 500 生成失敗
   - 理由: FR-009「生成失敗時は再生成できる」に対応する API・状態がなく、画面は文書の完成や失敗を知る手段がない。F-07 の手順表では5の非同期起動の後に6・7が書かれ、8の戻りが生成後のように読める点も矛盾している。
   - 改善案: 生成状態(生成中/完了/失敗)を保存して取得できる API と、再生成 API を追加する。承認 API は受付のみ(202)とし、失敗は状態で返す。
6. **[中程度 / 設計]** NFR-008, F-01, F-02, F-05, F-07, app/cache/token.py, app/main.py
   - 問題: レート制限の処理が、手順表・モジュール責務・実装計画のタスクに含まれない。ログインの総当たり、登録の大量作成、チャットと生成の回数上限が実装される根拠がない。
   - 引用: 07 レート制限「Redisを利用してIPアドレスまたはユーザー単位のリクエスト頻度を制限する」/ app/cache/token.py の関わる処理は F-02 のみ / F-01〜F-08 の手順に制限の確認がない
   - 理由: Must 相当の NFR-008 が、05 の手順にも実装計画(M-01〜M-04)のタスクにも落ちていない。
   - 改善案: 各手順にレート制限の確認と 429 を追加し、実装計画にレート制限のタスクを入れる。外部設計の API のエラー欄にも 429 を追記する。
7. **[中程度 / ヒアリング・観点 abuse]** NFR-008
   - 問題: 回数上限の値と単位が決まっていない。ログイン失敗何回で何分ロックか、登録は何件/時間か、チャットや生成は1日・1ユーザーあたり何回か、が不明。
   - 引用: abuse: 「ログインの総当たり、登録の大量作成、チャットや生成の回数上限を設けて不正利用を防ぐ」
   - 理由: 上限値と単位がないと、レート制限の実装も試験もできない。Gemini 無料枠への影響もある。
   - 改善案: 利用者に聞き直し、各操作の上限値・集計単位(IP/ユーザー)・期間を要件に追記する。
8. **[中程度 / 不整合]** F-02, tokens, app/cache/token.py, FR-001
   - 問題: トークン発行の保存先が Redis か tokens テーブルかが揺れている。tokens は user_id ではなく email を持ち、F-02#4 に渡すのも「ユーザーID」で、有効期限・失効の列もない。F-02 では一貫した失効処理(ログアウト)も定義されていない。
   - 引用: tokens: id, token, email / F-02#4「create_token | ユーザーID … Redisを使用して認証トークンを発行・保存する | tokens C」/ CON-003「トークン失効用にRedis」
   - 理由: 認証の根拠となるデータの置き場所と属性が一意でなく、トークン失効の仕組み(CON-003)も定義されていない。
   - 改善案: トークンは Redis で TTL 付きで管理するか、tokens に user_id・expires_at を持たせるかを一つに決め、ログアウト API も追加する。
9. **[中程度 / 設計]** chats, F-05, SCR-003, FR-002
   - 問題: チャットは履歴を LLM に渡す必要があるが、F-05#4 は今回のメッセージとプロジェクトIDしか渡さず、会話履歴の読み出し(chats R)も参考資料の参照もない。SCR-003 の履歴表示用の取得 API もない。
   - 引用: F-05#4「LLMClient.invoke_chat | プロジェクトID、チャットメッセージ」/ CRUD: F-05 は chats C+ のみ、documents への参照なし / API 一覧に chat 履歴取得なし
   - 理由: ヒアリングが文脈を踏まえて進められず、アップロードした参考資料(FR-003)も使われない。画面を再読込すると履歴も見えない。
   - 改善案: chats の過去履歴と documents の参考資料テキストを読み込んで LLM に渡す処理を追加し、履歴取得 API を設ける。
10. **[中程度 / 不整合・観点 logging]** NFR-007, chats, 07 ログ
   - 問題: NFR-007 は入力内容をログに残さないとするが、chats テーブルにメッセージ全文を保存しており、この「ログ」とデータ保存の区別が書かれていない。また 07 は死活監視のためトレースバックを出力するとし、NFR-004 の「MVP後に導入」と食い違う。
   - 引用: NFR-007「チャットの入力内容はログに残さず操作の記録だけを保存する」/ chats.message TEXT / 07 ログ「死活監視や追跡に活用する」
   - 理由: ログとデータベース保存の線引きがなく、トレースバックにメッセージが含まれうる。NFR-004 とも食い違う。
   - 改善案: チャット内容のDB保存は業務データとして許容する旨と、アプリログに本文を出さない方針(例外時のマスキング)を明記し、死活監視の記述は削る。
11. **[中程度 / 不整合]** SCR-002, FR-002, FR-005, SCR-005
   - 問題: SCR-005 に版切り替えボタン・再生成ボタンがあり、ダウンロード・コピーもあるが、版指定や文書種別指定で取得する API、再生成 API がない。さらに FR-005 を SCR-002 に対応づけている根拠も不明。
   - 引用: SCR-005「操作ボタン: コピーボタン、ダウンロードボタン、再生成ボタン、版切り替えボタン」/ GET /api/v1/projects/{id}/documents は引数なし
   - 理由: 版の切り替えと再生成の操作に対応する API が無く、画面の操作を実現できない。
   - 改善案: 文書種別・版を指定する取得 API と、再生成 API(POST .../documents/regenerate など)を追加し、対応表も直す。
12. **[中程度 / 設計]** F-06, POST /api/v1/projects/{id}/documents/upload, FR-003
   - 問題: 参考資料アップロードにファイルサイズ上限・PDF のページ数上限・文字数上限が無く、巨大ファイルや大量アップロードが可能。DB への全文保存と LLM への入力にも影響する。パース失敗時の応答も 400 のみ。
   - 引用: 2.5「ファイル形式は指定の拡張子のみ許可する」/ documents.content TEXT / 外部設計 エラー「400 不正なファイル形式」
   - 理由: FR-003 と NFR-008 のもとで、サイズ制限がなく LLM の無料枠や DB 容量を使い切れる。413 や PDF 解析失敗の扱いも決まっていない。
   - 改善案: サイズ・ページ数の上限と 413 の応答、拡張子だけでなく内容の検証、PDF 解析失敗時の扱いを定義する。
13. **[中程度 / ヒアリング・観点 data_retention]** FR-003, FR-008, NFR-005
   - 問題: 参考資料やチャット内容は機密を含みうる顧客情報だが、保存期間・削除できないこと(MVPで削除不可)への利用者の同意・参考資料の上限が決まっていない。公開サービスとして誰でも登録できるため、他者データの扱い方針が要る。
   - 引用: data_retention: 「プロジェクトやアカウントの削除機能はMVPでは不要とする」/ scale: 「誰でも登録できるサービスとして提供する」
   - 理由: 機密情報を扱う公開サービスで、保存期間・外部 LLM への送信の説明・削除要求への対応が未定のまま。
   - 改善案: 利用者に、保存期間、外部 LLM への送信の扱い、削除依頼の運用(手動対応など)を聞き直して要件に追記する。
14. **[軽微 / 設計]** POST /api/v1/projects/{id}/chat, F-05, FR-009
   - 問題: FR-009 は応答失敗時に「メッセージを送らずに再送を促す」とするが、F-05 は先にユーザーのメッセージを保存し、LLM 失敗時に保存済みのメッセージを取り消す手順がない。5 の response 列は NOT NULL のため、メッセージだけ先に保存する手順3と衝突する。
   - 引用: F-05#3「chats C」で message を保存し、#5 で別途 response を保存 / chats.response TEXT 不可(NULL)
   - 理由: 失敗時にメッセージだけ残り、response が NULL 不可の列と衝突して保存できない。
   - 改善案: メッセージと応答を LLM 成功後に1行でまとめて保存するか、失敗時の分岐(保存しない・ロールバック)を手順に書く。
15. **[軽微 / 設計]** F-06, F-08, F-07, POST /api/v1/projects/{id}/documents/upload
   - 問題: {id} を取る API で、プロジェクトが存在しない場合の応答が API ごとにばらばら。外部設計では chat・upload・approve に 404 や 401 が書かれていない。
   - 引用: 外部設計 chat: 「400, 500」、upload: 「400 不正なファイル形式」、projects: 「401 認証エラー」のみ / 詳細設計 F-05 には 1b 401 があるが 404 がない
   - 理由: 外部設計の API のエラー欄と詳細設計の手順の例外が食い違い、認証・認可・不在の応答がそろっていない。
   - 改善案: 全 API に 401・403/404 を外部設計へそろえ、手順表の分岐と対応させる。
