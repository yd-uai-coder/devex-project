## 設計レビュー
指摘 23件(最重要 4・中程度 14・軽微 5)

1. **[最重要 / 設計]** projects, tokens, F-03, F-04, POST /api/v1/projects/{id}/chat, GET /api/v1/projects/{id}/documents
   - 問題: projects テーブルに所有者(user_id)の列が無く、tokens テーブルも email しか持たない。一方で処理は ProjectRepository.find_all_by_user_id(ユーザーID) を呼ぶ。さらに {id} を取る API に「そのプロジェクトが本人のものか」の確認が無い。
   - 引用: projects: | id | UUID | PK | ... | name | VARCHAR(255) | — | 不可 | — | プロジェクト情報 | / F-03#4 ProjectRepository.find_all_by_user_id | ユーザーID | ... / tokens: | email | VARCHAR(255) |
   - 理由: データモデル(03)と処理手順(05)が食い違い、一覧取得が実装できない。他人のプロジェクトID を指定すれば、チャット・資料・文書を閲覧・変更できる状態になる。
   - 改善案: projects に user_id(FK users)を追加し、tokens も user_id を持たせる。{id} を取る全処理で所有者を検証し、不一致は 403 または 404 とする。
2. **[最重要 / 設計]** FR-004, SCR-003, SCR-004, summaries, API一覧
   - 問題: 構造化サマリを作る処理、取得する API、「ヒアリング完了」「修正依頼」の API がどこにも無い。summaries テーブルも承認フラグ(approved)しか持たず、サマリ本文を保存できない。
   - 引用: SCR-003 操作ボタン: ...ヒアリング完了ボタン / SCR-004 操作ボタン: 承認して文書生成へ進むボタン、修正依頼ボタン / summaries: | approved | BOOLEAN | ... | 構造化サマリ承認データ / API 一覧: summary/approve のみ
   - 理由: SCR-004 が表示するサマリを誰がどこで生成・保存・取得するのか不明で、FR-004 を満たせない。F-07 の 404「構造化サマリが存在しない」も、サマリを作る処理が無いため成立しない。
   - 改善案: サマリ生成(ヒアリング完了)、サマリ取得、修正依頼(再生成)の API と処理を追加する。summaries に content・生成日時を持たせ、承認前後の状態を管理する。
3. **[最重要 / 設計]** F-07, POST /api/v1/projects/{id}/summary/approve, GET /api/v1/projects/{id}/documents, SCR-005, FR-009
   - 問題: 文書生成はバックグラウンドで行うが、生成の状態(生成中/完了/失敗)を保持・取得する仕組みが無い。再生成の API も無い。バックグラウンドの失敗時に何を保存し、どう利用者へ伝えるかも未定義。
   - 引用: リスク: 進捗や結果は別APIで取得する設計とする / API一覧にその API なし / SCR-005 操作ボタン: 再生成ボタン / FR-009: 生成失敗時は再生成できるようにする
   - 理由: 画面は完了や失敗を知れず、FR-009 の再生成と NFR-003 の「数分待つ」を実現できない。approve は 200 を返した後の失敗を通知できない。
   - 改善案: 生成ジョブ(状態・失敗理由・どの文書まで終わったか)を保存するテーブルと、状態取得 API、再生成 API を追加する。approve の 500「生成失敗」は 202 と状態取得に置き換える。
4. **[最重要 / 設計]** FR-006, FR-008, documents, summaries, F-07, F-08
   - 問題: documents テーブルは project_id と content しか持たない。参考資料と生成文書が混在し、文書種別(4種)・版番号・作成日時・自己診断結果を保存する列が無い。「直近3件」を保つ仕組みも無い。
   - 引用: documents: | project_id | ... | content | TEXT | ... | 参考資料テキストデータ / summaries: 構造化サマリ承認データ・生成文書および版履歴データテーブル(列は approved のみ)
   - 理由: FR-005 の4種、FR-006 の自己診断、FR-008 の版管理、F-08 の「4種文書と直近3件」のどれも、このテーブルでは保存・取得できない。
   - 改善案: 参考資料(reference_docs)と生成文書(generated_documents: project_id, doc_type, version, content, created_at)を分け、自己診断結果の保存先を設ける。版の追加時に4版目以降を削除する処理を F-07 に加える。
5. **[中程度 / ヒアリング・観点 security]** FR-001, NFR-008, SCR-001
   - 問題: セキュリティが「ログインをMVPに入れる」だけで決まっている。本人以外のデータの閲覧・変更の可否、トークンの有効期限・失効(ログアウト)、パスワードの条件が要件に無い。
   - 引用: security | AI の提案を採用 | ログインをMVPに入れる / 認証: 有効期限(要決定)が切れている場合は 401 Unauthorized エラーとする
   - 理由: 公開サービスで、複数ユーザーのヒアリング内容や生成文書を扱う。誰が誰のデータを見られるかが未決のため、API の認可やトークン設計を確定できない。
   - 改善案: 利用者に「自分のプロジェクトは本人だけが閲覧・変更できる」でよいかを確認する。あわせてトークンの有効期限、ログアウトの要否、パスワードの最低条件を聞き、要件に追加する。
6. **[中程度 / ヒアリング・観点 abuse]** NFR-008
   - 問題: 不正利用の対策が「上限を設ける」とあるだけで、上限の値と単位(回数/分、回数/日、IP単位かユーザー単位か)が決まっていない。
   - 引用: abuse | ユーザーが決定 | ログインの総当たり、登録の大量作成、チャットや生成の回数上限を設けて不正利用を防ぐ
   - 理由: 値が無いとレート制限の実装や、Gemini 無料枠(CON-004)との整合を取れない。要件定義書 NFR-008 に数値が無い。
   - 改善案: ログイン失敗回数、登録回数、チャット回数、生成回数それぞれの上限値・期間・単位(IP / ユーザー)を聞き直し、NFR-008 に反映する。
7. **[中程度 / 不整合]** NFR-008, app/cache/token.py, SCR-001, API一覧, M-01-T01
   - 問題: レート制限は 07 横断事項に方針があるだけで、どの処理にも結び付いていない。API 一覧に 429 が無く、手順にもレート制限の確認が無い。モジュールの関わる処理は F-02 のみで、実装計画にタスクも無い。
   - 引用: レート制限: 上限を超過した場合は HTTP 429 Too Many Requests を返却する。 / app/cache/token.py | ... | F-02 / API一覧のエラー欄に 429 の記載なし
   - 理由: NFR-008 の Must 級要件がどのタスクにも落ちず、実装漏れになる。登録・チャット・生成の API にも制限の呼び出しが無い。
   - 改善案: 外部設計書の API 一覧に 429 を追加し、register / login / chat / approve の手順にレート制限の確認を入れる。実装計画に専用タスクを追加する。
8. **[中程度 / 設計]** F-07, 5.7 手順5〜7, POST /api/v1/projects/{id}/summary/approve
   - 問題: 手順 5 は非同期起動だが、手順 6〜7 と戻り(8)が同一の同期呼び出しの並びになっている。レスポンスを返す時点と、生成完了を待つ時点が区別されていない。承認の二重実行(連打)で生成が二重起動する扱いも決まっていない。
   - 引用: | 5 | ... | 非同期 | generate_documents_async | ... | 6 | ... | 同期 | generate_four_documents | ... | 8 | ... | 戻り | 処理受付完了 / 注記: 手順 3〜4 が1つのトランザクション
   - 理由: 同期呼び出しのまま実装するとリクエストがタイムアウトする。再承認や生成中の再実行を制御しないと LLM の無料枠を浪費し、版が重複する。
   - 改善案: 手順 6〜7 をバックグラウンド側の流れとして分離し、手順 8〜9 を 5 の直後に置く。生成中/承認済みの場合の再実行は 409 として扱う。
9. **[中程度 / 設計]** chats, F-05, FR-009
   - 問題: chats.response は NOT NULL だが、F-05 は手順 3 でユーザーメッセージだけを先に保存し、手順 5 で応答を別レコードとして保存する。要件は応答失敗時に「メッセージを送らずに」再送を促す。手順 3 を先に保存すると、LLM 失敗時に応答の無いメッセージが残る。
   - 引用: chats: | response | TEXT | — | 不可 | / F-05#3 ChatRepository.save(プロジェクトID、チャットメッセージ) / F-05#5 ChatRepository.save(プロジェクトID、AIからのチャット応答メッセージ) / 注記: 手順3から手順5が1つのトランザクション
   - 理由: 手順 3 の保存は response が無く制約違反になる。失敗時のロールバック範囲と履歴の扱いが要件(FR-009)と食い違う。
   - 改善案: LLM 応答の取得後に、メッセージと応答を1レコードで保存する。または role 列を持つ1行1メッセージ形式にする。失敗時は何も保存しない。
10. **[中程度 / 設計]** FR-003, F-05, F-07, documents, app/llm/client.py
   - 問題: 参考資料のテキストは保存されるが、チャットのヒアリングやサマリ・文書生成の入力に使う処理が無い。LLM 呼び出しの引数はプロジェクトIDとメッセージ(サマリ)のみで、過去のチャット履歴も明示されていない。
   - 引用: F-05#4 LLMClient.invoke_chat | プロジェクトID、チャットメッセージ / F-07#6 generate_four_documents | プロジェクトID、構造化サマリデータ / CRUD: documents は F-06 C+, F-07 C+, F-08 R のみ
   - 理由: 保持するだけで使われないデータになり、FR-003 の目的を満たさない。履歴が渡らないとヒアリングの文脈が続かない。
   - 改善案: invoke_chat と生成処理で、参考資料テキストとチャット履歴を読み込んで入力に含める流れを手順・CRUD に追加する。長い資料を渡すときの扱い(要約・上限)も決める。
11. **[中程度 / 不整合]** NFR-003, POST /api/v1/projects/{id}/chat, F-05
   - 問題: NFR-003 はチャットの最初の文字を数秒で出すことを求めるが、チャット API は AI 応答を一括で返す同期形式で、ストリーミングの記述が無い。
   - 引用: NFR-003: チャットの最初の文字を数秒で出力し / API: POST /api/v1/projects/{id}/chat | 200 OK (AI応答)
   - 理由: 応答全体の生成を待つ設計では「最初の文字」を数秒で出す要件を満たせず、画面の表示方式も決まらない。
   - 改善案: チャット API をストリーミング応答(SSE など)とし、途中失敗時のエラー通知と保存のタイミングを定める。
12. **[中程度 / 設計]** SCR-003, SCR-005, API一覧
   - 問題: 画面にある操作と表示に対応する API が無い。チャット履歴の取得(SCR-003 の履歴表示、再訪時)、プロジェクト単体の取得、版の切り替え(GET documents が版ごとの内容を返すかも不明)が該当する。
   - 引用: SCR-003 表示項目: チャット履歴、AIの応答メッセージ / SCR-005 操作ボタン: ...版切り替えボタン / API一覧にチャット履歴取得の API なし
   - 理由: プロジェクトを選び直して SCR-003 を開いたとき、過去の会話を表示できない。版切り替えの取得方法も不明。
   - 改善案: GET /api/v1/projects/{id}/chat(履歴)を追加する。GET documents に版指定(version)パラメータを持たせるか、版単位の取得 API を設ける。
13. **[中程度 / 設計]** API一覧, POST /api/v1/projects, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/documents/upload, GET /api/v1/projects/{id}/documents, POST /api/v1/projects/{id}/summary/approve
   - 問題: 認証が必要な API のエラーに 401 の記載が無く、{id} を取る API に 403/404 が無い。chat・approve・register・login の 429 も無い。F-06 手順は 401/404 を持ち、アップロード成功は 201 だが手順 6 は 200 とずれている。
   - 引用: POST .../chat | ... | 400 文字数超過・空送信エラー, 500 AI応答失敗 / upload | 201 Created | 400 不正なファイル形式 / F-06#6 HTTP 200 OK
   - 理由: 外部設計の API 一覧と詳細設計の手順でエラー・成功コードが一致せず、クライアントが分岐を実装できない。
   - 改善案: 全 API に 401、{id} 付きに 403/404、制限対象に 429 を追加する。upload の成功コードを 201 か 200 のどちらかに統一する。
14. **[中程度 / 不整合]** SCR-002, FR-005, 付録 要件との対応(Must の機能要件)
   - 問題: SCR-002(プロジェクト一覧・作成画面)の要件に FR-005(4種文書の生成)が結ばれている。付録の FR-005 の画面にも SCR-002 が入っている。
   - 引用: SCR-002 | ... | Must | FR-002・FR-005 / FR-005 | SCR-002・SCR-005 | POST /api/v1/projects/{id}/summary/approve
   - 理由: SCR-002 の操作はプロジェクト一覧と作成だけで、文書生成には関与しない。対応が誤っていると要件の網羅確認を誤る。
   - 改善案: SCR-002 の要件から FR-005 を外し、FR-005 の画面を SCR-004・SCR-005 にする。
15. **[中程度 / 設計]** CON-004, NFR-003, NFR-008, F-05, F-07
   - 問題: Gemini 無料枠の上限(1分・1日あたりの呼び出し数)に対して、数人〜十数人の同時利用と、1生成で4文書+自己診断の多数の呼び出しが収まるか検討されていない。全利用者共通の枠を使い切らない制御も無い。
   - 引用: CON-004: Gemini Flash-Lite(無料枠)を使用し上限超過時はエラー処理を挟む / NFR-003: 同時利用人数は数人から十数人 / F-07#6 generate_four_documents
   - 理由: エラーを返すだけの設計では、複数ユーザーが同時に生成すると全員が失敗する。生成の同時実行数やキューの方針が必要。
   - 改善案: 生成の同時実行数の制限(キュー)と、429 時の待ち・リトライ方針を F-05/F-07 に定める。無料枠の上限値を調べ、NFR-008 の上限値の根拠にする。
16. **[中程度 / 設計]** 実装計画書 M-01〜M-04, SCR-001, SCR-002, SCR-003, SCR-004, SCR-005, NFR-009
   - 問題: 実装計画のタスクはバックエンド処理だけで、Next.js + Tamagui の画面(SCR-001〜SCR-005)に当たるタスクが無い。
   - 引用: M-01〜M-04 のタスクは F-01〜F-08 のみ。モジュール欄は app/ 配下のみ。環境・設定のファイルは Dockerfile, docker-compose.yml のみ
   - 理由: 外部設計の Must 画面が計画に含まれず、フロントエンド実装の漏れになる。NFR-009 の対応ブラウザの確認も計画に無い。
   - 改善案: 画面ごと(または画面群ごと)にフロントエンドのタスクを追加し、対応する API タスクに依存させる。
17. **[中程度 / 設計]** CON-005, NFR-002, NFR-007, 実装計画書 M-01-T01, 3 開発環境・事前準備
   - 問題: nginx の設定、GitHub Actions による自動デプロイ、HTTPS、毎日のDBバックアップと7日分の保持・VPS外へのコピーに当たるタスクが無い。操作記録を保存する仕組み(テーブル・出力先)も未設計。
   - 引用: M-01-T01: Docker環境、データベース接続、共通例外ハンドラー、およびRedisキャッシュの土台を構築する / 環境・設定のファイル(例): Dockerfile, docker-compose.yml / NFR-002: データベースを毎日バックアップし7日分を残しVPS外へもコピーする
   - 理由: 制約条件と非機能要件にあるデプロイ・バックアップが実装計画に無く、実装されないまま公開に進む恐れがある。
   - 改善案: CI/CD、nginx・HTTPS、バックアップ(cron とVPS外転送)、操作ログのタスクを基盤に追加する。
18. **[中程度 / 不整合]** L-02, L-05, F-02, F-04, 07 横断事項 例外と HTTP
   - 問題: 例外の名前と扱いが文書ごとに揃っていない。L-02 は例外「なし」だが F-02#3a は AuthenticationError → 401 を要求する。L-05 は ValueError → 401、F-04 は UnauthorizedError と AuthError、L-04 は AuthError、共通ハンドラーは AuthenticationError・UnauthorizedError だけを 401 にする。
   - 引用: L-02 例外 | なし / L-05 例外 | ValueError: トークンが無効または期限切れの場合(HTTP 401) / 例外と HTTP: AuthenticationError や UnauthorizedError は HTTP 401
   - 理由: ハンドラーに登録されない AuthError や ValueError は 500 になる。ログイン失敗や不正トークンが 401 にならない。
   - 改善案: 認証失敗の例外を1つ(例: UnauthorizedError)に統一し、L-02・L-04・L-05 の例外欄と共通ハンドラーを揃える。
19. **[軽微 / 設計]** POST /api/v1/projects/{id}/documents/upload, F-06, FR-003
   - 問題: アップロードするファイルのサイズ上限、PDF のテキスト化に失敗した場合(スキャン画像のみの PDF や暗号化 PDF)、テキストが空だった場合の扱いが定まっていない。同じファイル名の再アップロードや資料の件数上限もない。
   - 引用: バリデーション: ファイル形式は指定の拡張子のみ許可する。 / documents.content TEXT NOT NULL
   - 理由: 大きなファイルでメモリや LLM 入力が膨れる。パース失敗時の応答が処理ごとに決まっておらず、content が空の資料を保存してしまう。
   - 改善案: ファイルサイズと件数の上限、テキストが空または抽出失敗時は 400 とする規則を F-06 に追加する。
20. **[軽微 / 不整合]** NFR-004, 07 横断事項 ログ
   - 問題: 横断事項のログは「死活監視や追跡に活用する」と書くが、NFR-004 はエラーの追跡と死活監視をMVPの後としている。トレースバックにチャット入力が混ざらないことも保証されていない。
   - 引用: ログ: エラー発生時はトレースバックを含む詳細情報をログに出力し、死活監視や追跡に活用する。 / NFR-004: エラーの追跡と死活監視はMVPの後に導入する
   - 理由: MVP の範囲と食い違う。NFR-007 のチャット入力をログに残さない方針とも、例外メッセージに入力が入る場合に矛盾しうる。
   - 改善案: 「死活監視や追跡に活用」を外し、ログの出力範囲だけを書く。例外ログにリクエスト本文を出さない旨を明記する。
21. **[軽微 / 設計]** F-02, tokens, app/cache/token.py, CON-003
   - 問題: トークンの保存先が Redis か PostgreSQL の tokens か曖昧で、両方に書くのかが不明。CON-003 の「トークン失効用 Redis」に対応するログアウト(失効)の API・処理が無い。
   - 引用: F-02#4 Redisを使用して認証トークンを発行・保存する | DB操作 tokens C / L-04: キャッシュまたはtokensテーブルを参照してトークンを検索する
   - 理由: 二重管理は不整合の元で、失効の仕組みが無いとトークンを無効化できない。
   - 改善案: 保存先を Redis(有効期限付き)に一本化するか、役割を明記する。失効が必要なら logout の API を追加する。
22. **[軽微 / 設計]** F-08, 4a, GET /api/v1/projects/{id}/documents
   - 問題: F-08 は「プロジェクトが見つからない」で 404 を返すが、プロジェクトの存在確認は文書の検索結果に頼っている。まだ文書が生成されていないプロジェクトと、存在しないプロジェクトを区別できない。
   - 引用: 4a | プロジェクトが見つからない | NotFoundError -> 404 / 手順4: find_documents_by_project_id
   - 理由: 生成前や生成中のプロジェクトに対して 404 を返す、または空の応答になるかが不定。画面の表示が決まらない。
   - 改善案: プロジェクトの存在・所有者確認を先に行う。文書が無い場合は、生成状態つきの空の応答を返す。
23. **[軽微 / ヒアリング・観点 schedule]** schedule
   - 問題: 体制・期間が未決のまま。実装計画のマイルストーンに期間・担当の前提が無く、リスク欄は「納期が厳しい場合」と、決まっていない納期を前提にしている。
   - 引用: schedule | 任意 | 未決 | / リスク: 納期が厳しい場合の代替手段として、一時的なモック応答モードへの切り替えを検討する。
   - 理由: 体制と期間が分からないと、マイルストーンの優先順位や、Should(FR-011)を後回しにする判断の根拠が無い。
   - 改善案: 開発体制(人数)と公開の目標時期を利用者に聞き、実装計画のマイルストーンに反映する。
