## 設計レビュー
指摘 23件(最重要 7・中程度 12・軽微 4)

1. **[最重要 / 不整合]** 1.3 In Scope, 1.3 Out of Scope
   - 問題: In Scope に「Jira連携による課題の自動登録」があるのに、Out of Scope に「Jira・Notion連携」があり、同じ機能の範囲が食い違っている。Jira 連携に当たる要件・画面・API・タスクはどこにも無い。
   - 引用: In Scope: Jira連携による課題の自動登録 / Out of Scope: Jira・Notion連携
   - 理由: ヒアリングの scope でも Jira・Notion連携は最初の版の対象外と決まっており、要件定義書 1.3 の内部で矛盾している。
   - 改善案: ヒアリングの決定に従い In Scope から Jira 連携の行を削除する。本当に必要なら、利用者に確認して要件と下流の文書を足す。
2. **[最重要 / 不整合]** FR-010, NFR-006, 1.3 Out of Scope
   - 問題: FR-010 は設計書をログイン不要の共有リンクで公開するとしているが、NFR-006 は他人のプロジェクト閲覧を不可としており矛盾する。FR-010 の出どころは「ユーザー」だが、ヒアリングの観点の表(core・scope)に共有リンクは無い。
   - 引用: FR-010: 生成した設計書を共有リンクで公開し、ログインしていない人も閲覧できるようにする / NFR-006: 機密性保持のため他人のプロジェクト閲覧を不可とする
   - 理由: 共有リンクはヒアリングで決まっておらず、機密性を重視する NFR-006 とも両立しない。既知のカバレッジ不足の指摘とは別に、要件自体の矛盾と出どころの確認が必要。
   - 改善案: 共有リンクを本当に要るか利用者に確認する。要るなら NFR-006 の例外条件を明記し、不要なら FR-010 を削除する。
3. **[最重要 / 不整合]** users.password, backend/core/security.py, DF-1
   - 問題: users.password の説明が「ログイン時にそのまま照合する」となっており、平文保存を示している。一方 security.py の責務にはパスワードのハッシュ化がある。
   - 引用: password | VARCHAR(255) | NOT NULL | パスワード(ログイン時にそのまま照合する) / backend/core/security.py: JWTの発行・検証およびパスワードのハッシュ化を行う
   - 理由: 公開サービスのユーザー認証情報で、NFR-006 の機密性保持にも反する。モジュール設計とも矛盾する。
   - 改善案: カラムを password_hash とし、DF-1・DF-2 に「ハッシュ化して保存・ハッシュ照合」の変換を書く。
4. **[最重要 / 設計]** POST /api/v1/chat/messages, DF-4, chat_messages.project_id
   - 問題: チャット送信 API の本文が message だけで、どのプロジェクトのチャットかを特定できない。データモデルは chat_messages.project_id を必須としているので保存先が決まらない。
   - 引用: | POST | /api/v1/chat/messages | ... | message | 200 AI応答成功 | ... / DF-4: backend/services/chat_graph.py | project_id, sender, content | メッセージ保存 | chat_messages
   - 理由: DF-4 の入力が message だけなのに、保存の段で突然 project_id が出てくる。チャットの履歴取得も不可能になる。
   - 改善案: 本文に project_id を足す(またはパスに含める)。DF-4 にも最初から project_id を入れる。
5. **[最重要 / 設計]** POST /api/v1/chat/messages, POST /api/v1/documents/generate, NFR-006
   - 問題: NFR-006 のプロジェクト所有者検証が、chat/messages と documents/generate の API に書かれていない。エラーに 401・403・404 の応答も無く、project_id を指定すれば他人のプロジェクトを読み書きできる設計になっている。
   - 引用: POST /api/v1/documents/generate | ... | project_id | 201 ... | 500 生成失敗(再生成可能) / NFR-006 の関連は POST /api/v1/projects のみ
   - 理由: NFR-006 は他人のプロジェクト閲覧を不可としているが、リソースを特定する API に所有者チェックが無い。DF-5 にも user_id との照合が無い。
   - 改善案: chat/messages と documents/generate に認証必須と project.user_id の検証を設け、401・403/404 をエラーに追加する。DF-4・DF-5 に所有者検証の工程を足す。
6. **[最重要 / 設計]** SCR-002, SCR-003, FR-006, FR-005, API一覧
   - 問題: 画面は保存済みのチャット履歴・設計書・自己診断結果を表示するが、取得系の API が無い。プロジェクト一覧・プロジェクトの取得、チャット履歴の取得、設計書本文と自己診断の取得も無く、SCR-003 のプレビューやダウンロードを実現できない。
   - 引用: SCR-003 表示項目: 選択した設計書の Markdown プレビュー画面 / 付録: FR-006 | SCR-003 | — / API一覧は POST のみ5件
   - 理由: FR-006 は画面に対応 API が無い。生成後の再訪問や再読み込みで表示するデータを取れない。
   - 改善案: GET /api/v1/projects、GET /api/v1/projects/{id}、GET /api/v1/projects/{id}/messages、GET /api/v1/projects/{id}/documents などを追加し、所有者検証と 401/403/404 を定義する。
7. **[最重要 / 設計]** SCR-001, SCR-002, SCR-003, M-01, M-02, M-03
   - 問題: Next.js / Tamagui のフロントエンドの画面(SCR-001〜003)を作るタスクが無い。M-01 は基盤、M-02・M-03 はバックエンドのモジュールだけを対象としている。
   - 引用: M-02-T01 モジュール: backend/api/v1/auth.py, backend/core/security.py / M-03-T02 モジュール: backend/api/v1/documents.py, backend/services/ai_service.py
   - 理由: 画面が無ければ FR-001〜FR-008 の利用者向けの機能は完成しない。M-03 のゴールの「プレビュー・ダウンロード」を担うタスクも無い。
   - 改善案: SCR-001〜003 の実装タスクを追加する(FR-006 のコピー・ダウンロードはフロントのタスクにする)。
8. **[中程度 / ヒアリング・観点 security]** FR-010, NFR-006
   - 問題: 共有リンクを公開する場合の公開範囲が決まっていない。リンクの推測されにくさ、有効期限、公開の取り消し、公開できる文書の種類が要件に無い。
   - 引用: FR-010: 生成した設計書を共有リンクで公開し、ログインしていない人も閲覧できるようにする(security の観点の内容は「他人のプロジェクト閲覧不可」とトークンの有効期間のみ)
   - 理由: クライアントとの打ち合わせ内容を含む機密文書を公開するため、公開の条件が決まらないと API・データモデルを設計できない。
   - 改善案: 共有リンクの要否、有効期限、取り消し方法、公開対象の文書を利用者に聞き直して要件に落とす。
9. **[中程度 / 不整合]** POST /api/v1/auth/login, FR-002, DF-2
   - 問題: FR-002 はトークンを HttpOnly Cookie に保存するとしているが、外部設計書はトークンを応答の本文で返して localStorage に保存するとしている。内部設計書では Cookie を設定するとしており、文書どうしも食い違う。
   - 引用: 200 ログイン成功(アクセストークン・リフレッシュトークンを応答の本文で返し、フロントエンドは localStorage に保存する) / 内部設計書: JWT認証ログインを行いCookieを設定する
   - 理由: localStorage 保存は XSS でトークンが盗まれるため、HttpOnly Cookie とした FR-002 を満たさない。
   - 改善案: ログイン応答は Set-Cookie(HttpOnly, Secure, SameSite)でトークンを返す形に外部設計書を直す。DF-2 も合わせる。
10. **[中程度 / 設計]** POST /api/v1/auth/login, CON-003, FR-002
   - 問題: リフレッシュトークンでアクセストークンを再発行する API と、ログアウト(トークン失効)の API が無い。Redis のトークン失効は目的だけ書かれ、使う処理が無い。
   - 引用: API一覧は register / login / projects / chat/messages / documents/generate の5件のみ。Redis (レート制限・トークン失効)
   - 理由: アクセストークンが30分、リフレッシュトークンが14日という運用は、再発行 API が無いと成り立たない。失効の契機となる処理も無い。
   - 改善案: POST /api/v1/auth/refresh と POST /api/v1/auth/logout を追加し、Redis の失効リストへの登録・照合を処理ロジックに書く。
11. **[中程度 / 不整合]** NFR-007, 3.4 例外処理・エラーハンドリング・ログ設計
   - 問題: 3.4 が NFR-007 を引用しつつ、AI応答失敗時はチャットの入力内容とプロンプト全文をログに出すとしており、入力内容を一切ログに残さない要件と衝突する。
   - 引用: ただし障害調査のため、AI応答失敗時はチャットの入力内容とプロンプト全文をログに出力する方針とする。
   - 理由: NFR-007 は入力内容を一切ログに残さず、エラーの有無や日時だけを残すと決めている。
   - 改善案: 入力内容とプロンプトのログ出力を削除し、タイムスタンプ・エラーコード・リクエスト ID のみにする。
12. **[中程度 / 設計]** POST /api/v1/documents/generate, DF-5, FR-003
   - 問題: DF-5 はチャット履歴だけを取得してプロンプトを作り、projects.reference_file_paths の参考資料を読み込む工程が無い。DF-3 も、ファイルを保存するだけで txt/md/pdf の本文抽出を書いていない。DF-4 のチャット対話にも参考資料は渡されない。
   - 引用: DF-5: backend/api/v1/documents.py | project_id | チャット履歴・参考資料取得 | chat_messages / DF-3: ファイル保存・パス紐付け
   - 理由: FR-003 の「参考資料を初期入力で読み込む」が、生成にもヒアリングにも使われていない。参照元が chat_messages だけでは参考資料を取れない。
   - 改善案: DF-3 に本文抽出(pdf 含む)を、DF-4・DF-5 に projects から参考資料を読む工程を追加する。
13. **[中程度 / 設計]** POST /api/v1/documents/generate, NFR-003, 4.4 リスク1
   - 問題: 4文書の生成と自己診断は数分かかる前提なのに、API は同期の 201 応答で、タイムアウトやジョブの進行状況・失敗時の扱いが無い。リスク1は「非同期処理を活用」と書くが、設計側に非同期の仕組みが無い。
   - 引用: POST /api/v1/documents/generate | ... | 201 設計書生成・自己診断成功 | 500 生成失敗(再生成可能) / 対策: 非同期処理を活用し
   - 理由: nginx やブラウザの標準のタイムアウトを超えやすく、途中で切れても状態が分からず、FR-007 の再生成も安全にできない。
   - 改善案: 生成を非同期ジョブ(202 とジョブ ID、状態取得 API)にするか、同期なら nginx・クライアントのタイムアウト値を明記する。生成中・失敗の状態をデータに持たせる。
14. **[中程度 / 設計]** documents, diagnostics, DF-5, FR-007
   - 問題: 再生成したときの documents・diagnostics の扱いが決まっていない。上書きか追加か、4文書の途中で失敗した場合に一部だけ保存されないか(トランザクション)が書かれていない。
   - 引用: DF-5: 設計書データ保存 → documents、自己診断データ保存 → diagnostics / documents は project_id と doc_type の一意制約なし
   - 理由: 同じ doc_type が重複し、どれが最新か決まらない。FR-007 の「生成失敗時は再生成」が不完全データを残しうる。
   - 改善案: project_id+doc_type を一意にして上書きする(または世代番号を持つ)。4文書と診断の保存を1トランザクションにする。
15. **[中程度 / ヒアリング・観点 abuse]** NFR-008, POST /api/v1/chat/messages, POST /api/v1/documents/generate
   - 問題: 回数制限の上限値と単位(1分あたり・1日あたり、IP 単位かユーザー単位か)が決まっていない。chat/messages と documents/generate の API にも 429 の応答が無い。
   - 引用: NFR-008: ログインの総当たり、登録の大量作成、チャットと生成の回数制限により不正利用を防ぐ / chat/messages のエラー: 400、500
   - 理由: abuse の観点が「回数制限」と書くだけで値が無く、Gemini の利用上限や費用との釣り合いを設計できない。
   - 改善案: 各回数制限の値・単位・対象を利用者に聞き直して NFR-008 に書く。chat と generate に 429 を追加する。
16. **[中程度 / ヒアリング・観点 security]** FR-001, FR-002, NFR-006
   - 問題: 誰でも登録できる公開サービスなのに、パスワードの規則、メールアドレスの確認、パスワード再設定、ログイン失敗時のロックなどが決まっていない。
   - 引用: FR-001: 誰でも登録できるサービスとしてユーザー登録とログイン機能を提供する / security の内容: メールとパスワードのJWT認証(アクセス30分、リフレッシュ14日・HttpOnly Cookie)
   - 理由: セキュリティの観点が認証方式とトークン期限で止まっており、登録・ログインの検証内容が決まらない。
   - 改善案: パスワードの最低条件、メール確認の要否、再設定の要否を利用者に確認して要件に加える。
