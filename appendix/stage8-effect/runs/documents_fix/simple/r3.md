## 設計レビュー
指摘 23件(最重要 4・中程度 15・軽微 4)

1. **[最重要 / 不整合]** 1.3 システム化の範囲, In Scope: Jira連携による課題の自動登録, Out of Scope: Jira・Notion連携
   - 問題: In Scope に「Jira連携による課題の自動登録」があるのに、Out of Scope にも「Jira・Notion連携」があり、真逆です。Jira 連携に対応する機能要件も画面・API・タスクもありません。
   - 引用: In Scope: Jira連携による課題の自動登録 / Out of Scope: Jira・Notion連携(ヒアリングの MVP の範囲は「Jira・Notion連携は最初の版の対象外」)
   - 理由: 範囲が矛盾していて Jira 連携を作るか決まらず、ヒアリングの scope(Jira 対象外)とも食い違います(要件定義書 1.3)。
   - 改善案: ヒアリングの決定に合わせて In Scope から Jira 連携を外し、Out of Scope は Jira 連携を残します。
2. **[最重要 / 不整合]** FR-010, NFR-006, 1.3 システム化の範囲
   - 問題: FR-010 は共有リンクでログインしていない人にも設計書を公開するとしています。NFR-006 は他人のプロジェクト閲覧を不可としており、両者が衝突します。FR-010 はヒアリングの core にも無い要件です。
   - 引用: FR-010「生成した設計書を共有リンクで公開し、ログインしていない人も閲覧できるようにする」/ NFR-006「機密性保持のため他人のプロジェクト閲覧を不可とする」
   - 理由: 公開閲覧が機密性の要件を破り、ヒアリングの core(プレビュー・コピー・ダウンロード)にも共有リンクはありません。既知の指摘は網羅漏れだけで、この矛盾は含みません。
   - 改善案: FR-010 を要件から外すか、公開の範囲を限定する例外として NFR-006 に明記してから設計に落とします。
3. **[最重要 / 設計]** POST /api/v1/chat/messages, DF-4, chat_messages
   - 問題: チャット送信 API の本文が message だけで project_id がなく、どのプロジェクトへのメッセージか、どの履歴を LLM に渡すかを特定できません。DF-4 にも project_id の入力がありません。
   - 引用: | POST | /api/v1/chat/messages | ... | message | 200 AI応答成功 | ... |
   - 理由: chat_messages は project_id が NOT NULL で、保存先を決められず、プロジェクト単位の所有者確認もできません(NFR-006)。
   - 改善案: 本文に project_id を追加するか、パスを /projects/{project_id}/chat/messages にして、DF-4 に履歴取得と所有者確認を加えます。
4. **[最重要 / 設計]** SCR-001, SCR-002, SCR-003, CON-001, M-02, M-03
   - 問題: 実装計画書にフロントエンド(Next.js + Tamagui)の画面を作るタスクが 1 つもありません。登録・ログイン、参考資料アップロード、チャット、生成、自己診断、プレビューの画面が計画に入っていません。
   - 引用: M-01〜M-03 のタスクのモジュールはすべて backend/ のみ(M-01-T01 の基盤にもフロントの記載なし)
   - 理由: SCR-001〜003 を担うタスクが無く、FR-001〜FR-008 のうち画面で実現する部分を実装できません(観点6)。
   - 改善案: SCR-001・SCR-002・SCR-003 の各タスクをマイルストーンごとに追加し、結び付ける要件を書きます。
5. **[中程度 / ヒアリング・観点 core]** FR-010
   - 問題: 共有リンクを残す場合に、リンクの発行・失効・有効期限、閲覧の範囲(全文書か個別か)、推測されにくい URL を使うか、が決まっていません。
   - 引用: FR-010「生成した設計書を共有リンクで公開し、ログインしていない人も閲覧できるようにする」(ヒアリングの core に共有の記載なし)
   - 理由: 機密性を重視する NFR-006 と関わるため、利用者に聞き直さないと公開方式を設計できません。
   - 改善案: 共有リンクが本当に要るか利用者に確認し、要る場合は失効方法・期限・閲覧範囲を聞き取ります。
6. **[中程度 / 不整合]** POST /api/v1/auth/login, FR-002, 3.1 技術スタック選定・アーキテクチャ方針
   - 問題: 外部設計書のログイン API はトークンを応答の本文で返して localStorage に保存するとしています。FR-002 は HttpOnly Cookie に保存するとしており、内部設計書も「Cookieを設定する」です。
   - 引用: 外部設計書: 「アクセストークン・リフレッシュトークンを応答の本文で返し、フロントエンドは localStorage に保存する」/ FR-002「HttpOnly Cookie に保存する」
   - 理由: 要件の XSS 対策が外部設計で崩れ、フロントとバックエンドで認証の実装が食い違います。
   - 改善案: 外部設計書を Set-Cookie(HttpOnly, Secure, SameSite)で返す形に直し、Cookie 認証に必要な CSRF 対策も書き添えます。
7. **[中程度 / 不整合]** テーブル users, backend/core/security.py
   - 問題: users.password の説明が「ログイン時にそのまま照合する」で、平文保存を示します。security.py の責務には「パスワードのハッシュ化」があり、矛盾しています。
   - 引用: password | VARCHAR(255) | NOT NULL | パスワード(ログイン時にそのまま照合する)
   - 理由: 公開サービスのパスワード平文保存は、NFR-006 の機密性保持を根本から損ないます。
   - 改善案: カラムを password_hash に改め、保存時にハッシュ化し、ログイン時はハッシュで検証すると明記します。
8. **[中程度 / 不整合]** 3.4 例外処理・エラーハンドリング・ログ設計, NFR-007
   - 問題: 内部設計書は、AI 応答失敗時にチャットの入力内容とプロンプト全文をログに出力する方針としています。NFR-007 は入力内容を一切ログに残さないと定めており、矛盾しています。
   - 引用: 「ただし障害調査のため、AI応答失敗時はチャットの入力内容とプロンプト全文をログに出力する方針とする」/ NFR-007「機密情報や入力内容は一切ログに残さず」
   - 理由: 機密情報が失敗のたびにログへ残り、NFR-007 に違反します。
   - 改善案: この一文を削除し、ログにはエラーコード・日時・リクエスト ID だけを残します。
9. **[中程度 / 設計]** POST /api/v1/chat/messages, POST /api/v1/documents/generate, POST /api/v1/projects, NFR-006
   - 問題: 認可の応答と処理がそろっていません。chat と generate のエラーに 401/403/404 がなく、プロジェクトの所有者かどうかを確認する処理もありません。projects にも 403・429 がありません。
   - 引用: chat: 「400 空メッセージまたは文字数超過、500 AI応答失敗」/ generate: 「500 生成失敗(再生成可能)」
   - 理由: NFR-006 の「他人のプロジェクト閲覧不可」を、project_id を受け取る API が満たしていません。NFR-008 の回数制限に対応する 429 も chat・generate・projects にありません。
   - 改善案: 保護対象の API すべてに 401・403/404・429 を加え、サービス層で project.user_id とログインユーザーを照合する処理を DF に書きます。
10. **[中程度 / 設計]** SCR-002, SCR-003, FR-006, FR-005, 2.6 API一覧
   - 問題: 生成済みの設計書・自己診断・チャット履歴・プロジェクトを取得する API がありません。SCR-003 のプレビューやリロード後の再表示、FR-006 に対応する API がありません。
   - 引用: API一覧は register / login / projects(POST) / chat/messages(POST) / documents/generate(POST) の5本のみ。付録の FR-006 の API は「—」
   - 理由: SCR-002 は生成物と自己診断の表示、SCR-003 はプレビューを担いますが、保存済みデータを読む手段がなく、外部設計書の画面と API が結び付きません。
   - 改善案: プロジェクト一覧・詳細、チャット履歴、設計書(自己診断付き)の GET API を追加し、認可を含めて内部設計書に反映します。
11. **[中程度 / 設計]** FR-002, CON-003, POST /api/v1/auth/login, backend/core/security.py
   - 問題: アクセストークン 30 分・リフレッシュ 14 日を使う設計なのに、トークン再発行 API とログアウト API がありません。Redis でのトークン失効も、誰がいつ失効させるか書かれていません。
   - 引用: CON-003「Redis(レート制限・トークン失効)」/ API一覧に refresh・logout なし
   - 理由: リフレッシュの手段がなく、アクセストークンの 30 分後に利用者が再ログインを強いられます。失効の契機も決まっていません。
   - 改善案: POST /auth/refresh と POST /auth/logout(Redis へ失効登録)を追加し、DF に失効の確認手順を書きます。
12. **[中程度 / 設計]** DF-5, DF-3, projects.reference_file_paths, FR-003
   - 問題: DF-3 で保存した参考資料が DF-5 の生成にも DF-4 のヒアリングにも使われません。DF-5 の取得元は chat_messages だけです。txt/md/pdf の本文抽出(pdf のテキスト化)も処理に書かれていません。
   - 引用: DF-5: 「backend/api/v1/documents.py | project_id | チャット履歴・参考資料取得 | chat_messages」/ DF-3: 「ファイル保存・パス紐付け | projects」
   - 理由: FR-003 の「読み込めるようにする」が満たされず、アップロードしても設計書に反映されません。
   - 改善案: DF-4・DF-5 で projects.reference_file_paths から本文を取得してプロンプトに入れる流れを追加し、pdf 抽出の担当モジュールを決めます。
13. **[中程度 / 設計]** POST /api/v1/documents/generate, DF-5, NFR-003, 4.4 想定リスクと対策
   - 問題: 4 文書と自己診断の生成は数分かかりますが、API は同期で 201 を返す設計です。タイムアウト、途中失敗(一部の文書だけ保存)、再生成時の既存データの扱いが書かれていません。リスク欄は「非同期処理」と書くだけで API に反映されていません。
   - 引用: 「201 設計書生成・自己診断成功」/「500 生成失敗(再生成可能)」/「非同期処理を活用し」
   - 理由: nginx やブラウザの接続上限を超えるおそれがあります。documents に版や上書きの定めがなく、再生成すると同じ doc_type が重複します(FR-007)。
   - 改善案: 生成をジョブ化(202 と状態取得 API)するか、タイムアウトを明記します。あわせて、全文書をトランザクションで保存することと、再生成時は置き換えるか世代管理するかを決めます。
14. **[中程度 / 不整合]** POST /api/v1/auth/register, POST /api/v1/auth/login, 付録 要件との対応 FR-008, SCR-002
   - 問題: FR-008 は「チャットの入力は数千文字まで・空送信禁止」ですが、register と login に FR-008 が結び付けられ、付録でも SCR-002 の行に register・login が載っています。要件に合わない対応です。
   - 引用: | POST | /api/v1/auth/register | ... | FR-001・FR-008 | / 付録: 「FR-008 | SCR-002 | POST /api/v1/auth/register・POST /api/v1/auth/login・POST /api/v1/chat/messages」
   - 理由: 認証 API の入力検証が FR-008 を満たすかのように見えますが、実際に満たすのは chat だけです。レート制限(NFR-008)の結び付きが抜けています。
   - 改善案: register・login の要件欄から FR-008 を外し、NFR-008 を付け、付録の FR-008 は chat/messages だけにします。
15. **[中程度 / 不整合]** M-03-T02, FR-006
   - 問題: FR-006(プレビュー・コピー・ダウンロード)が、バックエンドの生成タスク M-03-T02 だけに結び付けられています。このタスクのモジュールは documents.py と ai_service.py で、プレビューやコピーの実装を含みません。
   - 引用: M-03-T02: 「要件: FR-004, FR-005, FR-006 / モジュール: backend/api/v1/documents.py, backend/services/ai_service.py」
   - 理由: FR-006 を満たすフロントエンドのタスクが無く、対応表だけが埋まっています(実装計画書 4.2)。
   - 改善案: プレビュー・コピー・ダウンロードを行う SCR-003 のタスクを追加して FR-006 を結び、M-03-T02 からは外します。
16. **[中程度 / 設計]** CON-005, NFR-002, 4.3 開発環境・CI/CD・事前準備事項, M-01-T01
   - 問題: VPS への nginx・HTTPS 設定、GitHub Actions の自動デプロイ、DB の毎日バックアップ(7 日分・VPS 外コピー)を行うタスクがありません。フェーズ1 の説明に「デプロイ」とありますが、WBS にタスクがありません。
   - 引用: 4.1「VPSへのデプロイを行う」/ 4.3 は文章のみで、WBS に [デプロイ]・[運用] 種別のタスクなし。M-01-T01 の要件は「なし」
   - 理由: デプロイ・環境・バックアップに当たるタスクが無く、CON-005 と NFR-002 が計画から漏れています(観点6)。
   - 改善案: nginx・Docker Compose 本番構成、CI/CD、バックアップ(外部コピー含む)のタスクを追加し、CON-005・NFR-002 を結びます。
17. **[中程度 / 設計]** NFR-006, NFR-007, NFR-008, FR-007, M-02, M-03
   - 問題: レート制限(Redis)、トークン失効、所有者確認による認可、ログ方針の実装を担うタスクがありません。タスクの要件欄に NFR が 1 つも出てきません。
   - 引用: M-01〜M-03 のタスクの「要件」には FR-001〜FR-008 のみ。NFR-006・NFR-007・NFR-008 を持つタスクなし
   - 理由: 非機能要件に当たるタスクが無く、NFR-008 などが実装されないまま MVP が完了します(観点6)。
   - 改善案: レート制限ミドルウェア、トークン失効、認可チェック、ログ設定のタスクを追加し、NFR-006〜008 を結びます。
18. **[中程度 / ヒアリング・観点 abuse]** NFR-008, FR-008, POST /api/v1/chat/messages
   - 問題: 回数制限の値と単位が決まっていません。ログイン失敗何回で何分ロックするか、登録は 1 IP あたり何件/時間か、チャットと生成は 1 ユーザーあたり何回/日かが不明です。Gemini 側の上限との関係も未確認です。
   - 引用: NFR-008「ログインの総当たり、登録の大量作成、チャットと生成の回数制限により不正利用を防ぐ」(数値なし)
   - 理由: 値が無いと Redis の制限処理を実装できず、429 の条件も決まりません。公開サービスでは LLM の費用にも直結します。
   - 改善案: 各制限の値・単位・対象(IP かユーザーか)を利用者に聞き直し、NFR-008 に具体値を書きます。
19. **[中程度 / ヒアリング・観点 security]** FR-001, FR-002, NFR-006, SCR-001
   - 問題: セキュリティの決定が JWT の有効期限と「他人の閲覧不可」だけで、公開サービスで普通決める事項が要件にありません。パスワードの強度規則、メールアドレスの確認、パスワード再設定、1 ユーザーのセッション数、変更・実行系の API で他人のプロジェクトを操作できるか、などです。
   - 引用: FR-001「誰でも登録できるサービスとして」/ NFR-006「機密性保持のため他人のプロジェクト閲覧を不可とする」
   - 理由: 誰でも登録できるのにメール確認や再設定の可否が決まっておらず、閲覧以外の操作(チャット送信・生成)の認可も未決で、設計を直せません。
   - 改善案: パスワード規則、メール確認の要否、パスワード再設定の要否、他人のプロジェクトへの全操作の禁止を利用者に聞き直して要件に書きます。
20. **[軽微 / 設計]** backend/api/v1/auth.py, backend/core/security.py, 3.3 モジュール一覧, 3.2 データモデル定義

   - 引用: | backend/api/v1/auth.py | ルート | ... | fastapi, backend/services/ai_service.py |
   - 理由: 内部設計書 3.3 の構成図・説明とモジュール一覧が一致せず、NFR-008 を担うモジュールが不明です。
   - 改善案: auth.py の依存を security.py とリポジトリ層に直し、ミドルウェアとリポジトリのモジュールを一覧に追加します。
21. **[軽微 / 設計]** DF-2, DF-1, POST /api/v1/auth/login
