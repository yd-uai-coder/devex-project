## 設計レビュー
指摘 22件(最重要 2・中程度 14・軽微 6)

1. **[最重要 / 設計]** POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/documents/upload, POST /api/v1/projects/{id}/summary/approve, GET /api/v1/projects/{id}/documents, FR-001
   - 問題: プロジェクト単位のAPIに認可(本人のプロジェクトか)の定義がなく、401/403/404 の応答も一部のAPIにしかない。他人のプロジェクトIDを指定すれば閲覧・操作できてしまう。
   - 引用: POST /api/v1/projects/{id}/chat ... エラー: 400 文字数超過・空送信エラー, 500 AI応答失敗(401・403・404 の記載なし)
   - 理由: FR-001・NFR-008 のアクセス制御を満たすには、project の所有者検証と認証エラー・権限エラーの応答が必要(外部設計書 2.6)。
   - 改善案: 全 {id} 系APIで認証必須とし、所有者以外には 403 または 404 を返すと明記する。エラー欄に 401/403/404 を追加する。
2. **[最重要 / ヒアリング・観点 security]** FR-001, SCR-001
   - 問題: セキュリティが「ログインをMVPに入れる」だけで、誰が誰のデータを見られるか(他人のプロジェクト・文書の閲覧・変更の可否)、トークンの種類・有効期間・失効、パスワードの条件が決まっていない。
   - 引用: security | AI の提案を採用 | ログインをMVPに入れる / FR-001: ユーザー登録およびログイン機能を提供する
   - 理由: 公開サービスで利用者のヒアリング内容を扱うのに、データの分離方針とトークンの扱いが要件にないと認可・認証設計を決められない。
   - 改善案: 本人のプロジェクトのみ閲覧・操作可、トークンの有効期間とログアウト時の失効(Redis)、パスワード条件を利用者に確認して要件に追記する。
3. **[中程度 / ヒアリング・観点 abuse]** NFR-008
   - 問題: 回数上限の具体値・単位(ログイン試行/IP・アカウント、登録/IP/時間、チャット・生成の回数/ユーザー/日)と超過時の挙動が決まっていない。
   - 引用: NFR-008: ログインの総当たり、登録の大量作成、チャットや生成の回数上限を設けて不正利用を防ぐ
   - 理由: 数値がないとレート制限の実装・テストができず、Gemini無料枠(CON-004)との整合も取れない。
   - 改善案: 上限の値・単位・超過時の応答(429 など)を利用者に聞き、要件に数値で書く。
4. **[中程度 / 設計]** NFR-008, SCR-001, POST /api/v1/auth/login, POST /api/v1/auth/register, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/summary/approve
   - 問題: NFR-008 のレート制限に対応する 429 エラー応答が、どのAPIにも定義されていない。画面の表示も未定義。
   - 引用: POST /api/v1/auth/login ... エラー: 401 認証失敗(429 なし)/ SCR-001 の要件欄に NFR-008 がある
   - 理由: レート制限に当たったときの応答がなければ、画面がユーザーに理由を表示できない(外部設計書 2.6)。
   - 改善案: login・register・chat・approve に 429 を追加し、該当画面に上限到達時のメッセージ表示を記す。
5. **[中程度 / 設計]** POST /api/v1/projects/{id}/summary/approve, FR-005, FR-006, NFR-003, FR-009
   - 問題: 4文書の逐次生成と自己診断は数分かかるのに、approve は同期的な「200 OK (生成開始)」としか書かれておらず、進捗の取得・完了判定・失敗後の再生成のAPIがない。
   - 引用: POST /api/v1/projects/{id}/summary/approve | 構造化サマリ承認と文書生成開始 | ... | 200 OK (生成開始) | 500 生成失敗
   - 理由: FR-009 は生成失敗時に再生成できることを求め、SCR-005 には再生成ボタンがあるが、対応するAPIも状態取得手段もない。NFR-003 の数分の待機もHTTPタイムアウトに当たりうる。
   - 改善案: 生成を非同期ジョブ化し、状態取得API(GET .../generation)と再生成API(POST .../documents/regenerate)を追加する。
6. **[中程度 / 設計]** SCR-004, FR-004, 修正依頼ボタン
   - 問題: SCR-004 に「修正依頼ボタン」があるが、構造化サマリを取得するAPIと修正依頼のAPIがない。サマリを表示する手段も未定義。
   - 引用: SCR-004 操作ボタン: 承認して文書生成へ進むボタン、修正依頼ボタン / API一覧に summary の取得・修正APIなし(approve のみ)
   - 理由: 画面の操作ごとにAPIが必要(外部設計書 2.3 と 2.6 の不整合)。
   - 改善案: GET /api/v1/projects/{id}/summary と、修正依頼(チャットへ戻る・再作成)のAPIを追加する。
7. **[中程度 / 設計]** SCR-003, ヒアリング完了ボタン
   - 問題: ヒアリング完了ボタンと構造化サマリの作成を実行するAPIがない。
   - 引用: SCR-003 操作ボタン: メッセージ送信ボタン、ファイルアップロードボタン、ヒアリング完了ボタン / API一覧に完了・サマリ作成APIなし
   - 理由: サマリ作成(外部設計書 2.4 では Gemini が行う)の起点がなく、FR-004 の流れが成立しない。
   - 改善案: POST /api/v1/projects/{id}/summary のようなサマリ作成APIを追加し、SCR-003 と FR-004 に結ぶ。
8. **[中程度 / 設計]** SCR-005, FR-008, GET /api/v1/projects/{id}/documents, 版切り替えボタン, 再生成ボタン
   - 問題: 版の切り替え・指定版の取得・再生成のAPIがなく、GET の応答にどの文書・版が入るかも不明。ダウンロード・コピーの仕組みも未定義。
   - 引用: SCR-005 操作ボタン: コピーボタン、ダウンロードボタン、再生成ボタン、版切り替えボタン / GET /api/v1/projects/{id}/documents | 200 OK | 404 対象なし
   - 理由: FR-008 の直近3件保持と FR-009 の再生成を、画面の操作に対するAPIで満たしていない。
   - 改善案: 文書種別と版を指定する取得API、ダウンロード用API、再生成APIを追加し、応答項目を定義する。
9. **[中程度 / 不整合]** FR-011, SCR-005, FR-008
   - 問題: 版の履歴の画面はShould(将来の拡張)なのに、SCR-005 に版の履歴(直近3件)の表示が含まれている。要件の範囲とずれる。
   - 引用: FR-011: テンプレートの選択、版の履歴の画面、設計図(UML)の追加を行う / SCR-005 表示項目: ... 版の履歴(直近3件)
   - 理由: MVP 外の機能が画面に入っており、FR-008 が保持だけを求めるのと食い違う(要件定義書 1.4 と外部設計書 2.3)。
   - 改善案: SCR-005 は版の切り替えに限定するか、履歴表示を要件の Must に格上げするか決めて揃える。
10. **[中程度 / 不整合]** SCR-002, FR-005, 付録 要件との対応
   - 問題: SCR-002(プロジェクト一覧・作成画面)に FR-005(4文書の生成)が結ばれている。この画面に文書生成の操作はない。
   - 引用: SCR-002 | プロジェクト一覧・作成画面 | ... | FR-002・FR-005 / 付録: FR-005 | SCR-002・SCR-005
   - 理由: 画面の要件欄が、その画面で満たさない要件を指している(観点8)。
   - 改善案: SCR-002 の要件欄は FR-002 のみにし、付録の FR-005 も SCR-005 だけにする。
11. **[中程度 / 設計]** POST /api/v1/projects/{id}/summary/approve, FR-006, SCR-005
   - 問題: 自己診断(FR-006)の結果を返すAPIがなく、approve に結ばれているだけで、結果の取得手段が不明。
   - 引用: FR-006 | SCR-005 | POST /api/v1/projects/{id}/summary/approve / GET .../documents の応答に診断結果の記載なし
   - 理由: SCR-005 は診断結果を表示するが、取得元が定義されていない。
   - 改善案: GET .../documents の応答に診断結果を含めるか、診断取得APIを追加し、FR-006 に結ぶ。
12. **[中程度 / 設計]** SCR-003, POST /api/v1/projects/{id}/chat, NFR-003
   - 問題: NFR-003 は最初の文字を数秒で出すこと(ストリーミング)を求めるが、chat API は「200 OK (AI応答)」で応答形式(SSE等)が未定義。チャット履歴の取得APIもなく、画面再表示時に履歴を表示できない。
   - 引用: POST /api/v1/projects/{id}/chat | ... | 200 OK (AI応答)
   - 理由: ストリーミングの方式と履歴取得がないと、SCR-003 の「チャット履歴」表示と NFR-003 を満たせない。
   - 改善案: chat をSSEなどのストリーム応答と明記し、GET /api/v1/projects/{id}/messages を追加する。
13. **[中程度 / 設計]** POST /api/v1/projects/{id}/documents/upload, FR-003, SCR-003
   - 問題: 参考資料のサイズ上限・PDFのページ数上限・テキスト化の失敗(読めないPDF、暗号化など)の扱い・保持した資料の一覧/削除が未定義。応答エラーも 400 だけで 413 などがない。
   - 引用: バリデーション: ... ファイル形式は指定の拡張子のみ許可する。/ 400 不正なファイル形式
   - 理由: サイズ制限がないと無料枠のLLMや保存容量を圧迫し、NFR-008 の不正利用対策にも抜けが出る。
   - 改善案: ファイルサイズ・ページ数の上限、413・422(テキスト化失敗)を定義し、資料の一覧取得も検討する。
14. **[中程度 / ヒアリング・観点 core]** FR-003, POST /api/v1/projects/{id}/documents/upload
   - 問題: 参考資料のファイルサイズ上限・件数・スキャンPDF(OCR)の扱いが聞けておらず、要件に書かれていない。
   - 引用: FR-003: 参考資料(txt、md、PDF)を読み込みテキスト化して保持する
   - 理由: 利用者に聞かないと上限値と、テキスト化できない資料の扱いを決められない。
   - 改善案: 1ファイルの最大サイズ・件数・OCR 非対応の可否を利用者に確認し、要件に追記する。
15. **[中程度 / ヒアリング・観点 tech]** CON-004, NFR-003, FR-009
   - 問題: Gemini無料枠の上限(1分・1日のリクエスト数やトークン数)が確認されておらず、同時利用数十人×4文書生成が収まるか、超過時の利用者への案内内容が決まっていない。
   - 引用: LLMはGemini Flash-Lite(無料枠)を使用し、上限超過のエラー時はエラー処理を挟む
   - 理由: 数人〜十数人の同時利用と公開サービスの規模(scale)で、無料枠の上限が全体のボトルネックになりうるのに値が要件にない。
   - 改善案: 無料枠の上限値を確認して要件に書き、全体の回数制限(NFR-008)と超過時の表示・待ち方を決める。
16. **[中程度 / ヒアリング・観点 logging]** NFR-007, NFR-002, FR-003
   - 問題: チャット内容・参考資料・生成文書という機密性の高い入力をDB・バックアップ・外部LLMにどう扱うか(保存期間、外部LLMへの送信への同意、VPS外コピーの暗号化)が決まっていない。
   - 引用: logging | AI の提案を採用 | 入力内容は残さず、操作の記録だけにする / NFR-002: ... VPS外へもコピーする
   - 理由: クライアントとの打ち合わせ内容を含みうる公開サービスで、データの外部送信とバックアップ先の保護方針が要件にない。
   - 改善案: 利用者に、機密情報の扱い・LLM送信の注意表示・バックアップの暗号化の要否を確認し、要件に追記する。
17. **[軽微 / ヒアリング・観点 schedule]** schedule
   - 問題: 体制・期間が未決のまま。実装計画の規模・順序・マイルストーンを決める材料がない。
   - 引用: schedule | 体制・期間 | 任意 | 未決 |
   - 理由: 実装計画書のタスク粒度や優先順位を決めるのに必要。
   - 改善案: 開発体制(人数)・期限の有無を利用者に確認して要件に落とす。
18. **[軽微 / 設計]** POST /api/v1/projects/{id}/summary/approve
   - 問題: 承認APIに応答本文(ジョブID等)の定義がなく、すでに承認済み・サマリ未作成のときの409/400 などのエラーもない。
   - 引用: POST /api/v1/projects/{id}/summary/approve | ... | 200 OK (生成開始) | 500 生成失敗
   - 理由: 二重承認で文書生成が重複し、無料枠を無駄に消費するおそれがある。
   - 改善案: 本文は「なし」と明記し、409(生成中・承認済み)と 400(サマリ未作成)を追加する。
19. **[軽微 / 設計]** POST /api/v1/auth/login, FR-001, CON-003
   - 問題: トークン失効用のログアウトAPIがなく、「トークン返却」の種類・有効期間・更新方法も書かれていない。
   - 引用: POST /api/v1/auth/login | ... | 200 OK (トークン返却) / CON-003: レート制限・トークン失効用にRedisを使用する
   - 理由: CON-003 でトークン失効を前提にしているのに、失効を起こす操作がAPIにない。
   - 改善案: POST /api/v1/auth/logout を追加し、トークンの形式と有効期間を明記する。
20. **[軽微 / 設計]** POST /api/v1/projects, GET /api/v1/projects, SCR-002
   - 問題: プロジェクト名の文字数・重複の可否が未定義で、一覧の件数が増えたときのページングもない。プロジェクト作成の応答本文も不明。
   - 引用: POST /api/v1/projects | プロジェクト作成 | name | 201 Created | 400 バリデーションエラー
   - 理由: バリデーションとデータ量の扱いが決まらないと実装で手戻りになる。
   - 改善案: 名前の長さ制限と応答(project id)を明記し、一覧にページングまたは件数上限を定める。
21. **[軽微 / 不整合]** NFR-003, performance
   - 問題: ヒアリングでは4文書の生成は「数秒〜数分待てる」だが、要件は「数分以内」に変わっている。上限の目安(何分まで)も定まっていない。
   - 引用: performance: 4文書の生成は数秒〜数分待てる / NFR-003: 4文書生成は数分以内の待機とする
   - 理由: タイムアウトや進捗表示の設計に使える具体的な許容時間がない。
   - 改善案: 生成の許容時間の上限(例: 5分)を決めて NFR-003 に書く。
22. **[軽微 / 設計]** NFR-009, SCR-001, SCR-002, SCR-003, SCR-004, SCR-005
   - 問題: スマートフォンは閲覧のみ対応とあるが、どの画面がスマホで閲覧可能で、どの操作(チャット送信・アップロード)が無効になるかが画面仕様にない。
   - 引用: NFR-009: スマートフォンは閲覧のみ対応とする / 2.3 の各画面にレスポンシブの記載なし
   - 理由: 要件の非機能が画面仕様に反映されていない。
   - 改善案: スマホでの表示画面と無効にする操作を、2.3 に追記する。
