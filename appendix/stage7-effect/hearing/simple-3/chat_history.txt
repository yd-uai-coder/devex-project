システム概要：Devex: AI との対話型チャットでユーザーのアイデアや要望をヒアリングし、「要件定義」「外部設計」「内部設計」「実装計画」の4種の Markdown 設計書を自動生成する Web アプリ。システム開発の初期フェーズで、ドキュメント作成の工数と属人化を減らしたい。

実現したい事：- チャットでヒアリングし、4種の設計書を一括生成する(MVP)
- 生成後に AI が各文書の不足点を3段階(最重要/中程度/軽微)で自己診断して提示する
- 生成した Markdown をプレビュー・コピー・ダウンロードできる
- 参考資料(txt/md/pdf、最大3件)を初期入力で読み込める
- ユーザー・チャット履歴・生成文書を PostgreSQL に保存する

ヒアリングの内容をまとめました。

- 規模: 公開サービス
- 目的・課題: システム開発初期フェーズにおけるドキュメント作成の工数と属人化を減らすため、対話から4種の設計書を自動生成する。
- 利用者と使う場面: SE、ITコンサルタント、PM、個人開発者、スタートアップ創業者などが、新規プロジェクトの立ち上げやクライアントヒアリング時に開く。
- 利用者の1日の流れ: クライアントとの打ち合わせ後に30分ほどでヒアリングを済ませ、その日のうちに生成されたドラフトを見直して共有する。
- コア機能: 対話型チャットによるヒアリングと4種の設計書の一括生成、生成後の自己診断、プレビュー・コピー・ダウンロード、初期の参考資料読み込み、PostgreSQLへの保存機能。
- MVP の範囲: 対象外
- 例外の場面: APIの失敗時は理由を表示してメッセージを保存せずに再送を促し、生成失敗時は再生成を行えるようにする。
- 将来の拡張: テンプレートの選択、版の履歴の画面、設計図(UML)を後で追加する。
- 技術スタック・環境の制約: フロントエンドは Next.js (App Router) + Tamagui、バックエンドは FastAPI + LangChain・LangGraph (Python 3.13)、データベースは PostgreSQL、Redis、サーバーは VPS (Docker Compose + nginx)、CI/CDは GitHub Actions、AIは Gemini Flash-Lite を使用する。
- 可用性: 半日程度の停止なら許容され、夜間の保守の停止も問題ない。
- 可用性(データの保全): DBを毎日バックアップし7日分を残し、VPSの外にもコピーする。
- 性能・拡張性: 同時に使うのは数人〜十数人で、チャットの最初の文字が数秒で出ること、4文書の生成は数分まで待つことが許容される。
- 運用・保守性: エラーの追跡と死活監視は必要だが、MVPの後で導入する。
- 運用・保守性(データの保持・削除): プロジェクトやアカウントの削除機能はMVPでは不要とする。
- 移行性: 移行するデータや仕組みはない
- セキュリティ: 本人以外が他人のプロジェクトを見られないよう分離し、ログインはメールアドレスとパスワードによるJWT認証(アクセス30分、リフレッシュ14日、リフレッシュはHttpOnly Cookie)とする。
- セキュリティ(ログ): 機密保持のため、チャットや入力の内容は一切ログに残さない
- セキュリティ(不正利用): ログインの総当たりや登録の大量作成を防ぎ、チャットと生成にも回数の上限を設ける。
- システム環境・エコロジー: PCの最新のChrome、Edge、Firefox、Safariで利用し、スマートフォンは閲覧ができれば十分とする。

### 最重要（実装着手に支障）

*   **ファイルアップロードのデータフローとAPI仕様の不整合**: 
    *   外部設計書の API一覧において、`/api/v1/chat/messages` および `/api/v1/documents/generate` のリクエストボディに参考資料（ファイル）の受け渡し方法が明記されていません（multipart/form-data の想定か、ファイル自体は別エンドポイントでアップロードするのか不明）。実装時のインターフェース定義を明確にしてください。
*   **ファイルストレージの定義欠落**: 
    *   要件定義書で参考資料（txt, md, pdf, 最大3件）の読み込み（FR-004）が定義されていますが、アップロードされたファイル自体の保存先（ローカルストレージ、S3互換ストレージ、DBのBLOBなど）についての設計がデータベース定義やシステム構成図に含まれていません。

### 中程度（後続の設計判断に影響）

*   **Redisの利用目的の具体化**: 
    *   内部設計書（3.1項）の構成図でRedisが「キャッシュ・セッション」として挙げられていますが、具体的にどのようなデータ（JWTのブラックリスト、レートリミット用カウンター、LangGraphの状態管理など）に利用するのかの記載がありません。
*   **レートリミット（NFR-009）の具体的な仕様**: 
    *   「チャットと生成にも回数の上限を設けること」とありますが、具体的な制限値（例：1分間に何回まで、1日あたり何回まで等）や、制限を超えた際の挙動（HTTP 429 Too Many Requests 等）の定義が抜けています。
*   **参考資料の保持期間・紐付け構造**: 
    *   アップロードされた参考資料がどのエンティティ（チャットセッション単位、ユーザー単位など）に紐づき、どのタイミングで破棄されるのかのデータモデル定義が不足しています。

### 軽微（運用上の補足）

*   **フロントエンドのディレクトリ構成の補足**: 
    *   バックエンドについてはレイヤードアーキテクチャやモジュール構成（3.3項）が詳細に記載されている一方、フロントエンド（Next.js App Router + Tamagui）側の画面構成やコンポーネント設計についての記載が簡略であるため、画面数が増えた際の指針を追加するとより親切です。
