本書は、[v1](./cl-development-handoff.md) を出発点に、2つ目のプロジェクトで CL 開発を Phase 0〜24 まで実践した結果を反映した改訂版である。v1 と同じく**特定プロジェクトに依存しない形**にまとめてあり、新しいプロジェクトで CL 開発を始めるときの叩き台として使う。

**本書に含まれるもの**:
- 進行のルール #1〜#33(v1 の #1〜#17 に、改訂元のプロジェクトで足して一般化したルールを #18〜#33 として加えた)

**本書に含まれないもの**:
- 特定ドメインのアーキテクチャの決定・技術選定。プロジェクトごとに `CLAUDE.md`(または相当のプロジェクト方針ファイル)の別の節に書く。

**使い方の想定**: 新しいプロジェクトの `CLAUDE.md` に、本書の2章を「進行のルール」節として取り込む(取捨選択してよい)。番号は固定し、プロジェクト固有のルールは #34 以降として足す。

## 1. CL開発とは

**CL(Curriculum Loop)開発**は、次のように定義される開発・学習手法である。

> AI が Phase(開発の区切り)単位で学習教材とサンプルコードを著述し、本体のコードを人間が手で書くか AI が書くかを Phase ごとに選ぶ。実装で当たった疑問・改善点が質問・相談を通じて教材とコードに還流し、教材とプロジェクトが一つのループの中で共に洗練されていく開発・学習手法。

**2 本柱**

1. **双方向の還流ループ**: 「教材 → 実装」の一方向でなく「実装で当たった摩擦 → 教材・コードの改訂」。次の Phase はより洗練された状態で始まり、大きなやり直しのリスクを抑える。
2. **役割分担**: AI = 設計案・教材・トレードオフの説明(自動実装モード on では本体の実装も)。人間 = 設計判断の最終決定と、off の Phase での実装のタイピング。

**自動実装モードと学習の形**(#20)

- **off**: 人が教材と samples から手で実装する。v1 の想定した形。
- **on**: AI が先に完成品を作り、人は完成品と教材から仕様を追う。改訂元のプロジェクトでは、手で実装しても設計の理解が思ったほど実感できなかったため、途中から on に切り替えた。
- どちらでも**教材の中身は変えない**。特に #14 のテスト観点(SUT/ドライバ/スタブ)は省かない。テストは設計理解の肝だからである。

**既存概念との関係**

- 下敷きとなる考え方: cognitive apprenticeship、worked examples 効果、spec-driven development、project-based learning。
- off は「AI 生成コードを人間が理解する」構図(vibe learning 等)と逆で、人が書く。on はその構図に近いが、設計判断の最終決定は人が持ち(#33)、教材とテスト観点で設計の理由を言語化する点で `vibe coding` と異なる。

## 2. 共通進行ルール(#1〜#33)

番号は新設順に固定する(教材・ログ・記録から `#N` で参照されるため)。以下はカテゴリ別に並べてある。新しいルールは該当カテゴリの末尾に次の番号で足す。

### A. 教材の生成 ── いつ・何を

**#1.** 学習教材を Phase ごとに教材フォルダ(例: `textbook/`)に `.md` 形式で作る。Phase ごとにフォルダを作り(`textbook/Phase-<N>/`)、その下に `Phase-<N>-introduction.md` などを置く。

**#5.** ユーザーの「Phase N を開始する」というプロンプトで、その Phase の教材・サンプルを生成する。

**#25. Phase 0 の役割**。Phase 0 は、要件・設計の確認から、Phase 1 以降の実装ロードマップ(Phase の区切りと各 Phase のスコープ)の具体化までを行う。入力はプロジェクトの要件・設計文書である。ロードマップは**暫定**とし、各 Phase の着手時に見直す(着手時の相談で Phase を分割・統合することは通常の工程である。#33)。

**#26. 実装着手前の仕様診断**。Phase 0 の最後(またはステージ・大きな機能の要件定義の最後)、次の Phase に着手する前に、要件定義〜実装計画の各文書の不足・不明瞭な点を AI が主体的に診断する。診断結果は3段階に分けて示す: (1) **最重要** ── 次の Phase のタスクに直結し、着手前に解決すべきもの。(2) **中程度** ── 後続 Phase の設計事項だが、今のうちに認識を合わせたいもの。(3) **軽微・運用面**。ユーザーは各項目について「決定を下す」か「AI に提案を求める」かを選ぶ。提案を求められた項目は、トレードオフの比較や既存コードの調査に基づいて具体案を示す。決定が出揃ったら設計文書に反映し、その回の対応を Phase 0 の1章として記録する。

### B. Phase 教材の構成 ── ファイルと章立て

**#2.** 学習教材は各 Phase の中で章立てする。構成は `Phase-<N>-introduction.md`(導入)+ `Phase-<N>-1.md` 以降(作業単位ごと。章番号 = 作業単位番号)。別建ての概観章やインデックスは作らず、導入ファイル1本に集約する(内容は #6、実装前チェックリストは #11)。設計フェーズ(実装を伴わない Phase)は作業単位を持たないので、`Phase-0-introduction.md` + `Phase-0-1.md` 以降(設計トピックの逐次解説)とする。

**#6.** Phase ごとに導入ファイル `Phase-<N>-introduction.md` を各 Phase フォルダの直下に作る。内容は次のとおり。
- フェーズの目的
- 自動実装モードの宣言(#20)
- パイプライン上の位置づけ・作業章を始める前に理解すべき前提(概観)。既存コードに前例の無い新しいパターンがあれば、ここで先に示す
- 着手時の相談で決めたこと(ユーザーの決定と、計画の承認で確定した AI の判断を分けて書く)
- 章一覧(各章のトピック・依存関係・リンク)
- サンプルコード一覧
- 実装前チェックリスト(#11)
- 写経順序(#22)
- 検証結果
- 未消化の申し送り(#32)
- 後続 Phase での改訂(#12)
- Phase 完了チェック(#21)
- 次のフェーズ

`Phase-<N>-1.md` 以降を読み始める前に、この1本で前提を説明しきる。章を追加・変更したらここも更新する。

**#11.** 各 `Phase-<N>-introduction.md` に「実装前チェックリスト」を置く。内容: その Phase で作るファイルの一覧 / 各クラス・関数の責務1行 / テスト観点。Phase 教材の生成後・実装着手前に、ユーザーがこれで疑問を出し切ってから実装に入る(疑問の範囲は #19)。行キーは作業単位番号(章番号と一致)。設計フェーズは省略してよい。

**#19. 事前質問の範囲限定**。#11 の実装前チェックリストで解消する疑問は、設計レベル(責務・依存関係・テスト観点)に限る。実装の細部(変数名・ループの書き方など)の疑問は実装着手後に都度質問してよく、チェックリスト完了の条件にしない。

**#21. Phase 完了チェック**。各 introduction に「Phase 完了チェック」として、概念の理解を問う設問を3〜5問置く。実装前チェックリスト(#11、着手前)と対をなす、着手後の完了判定である。

**#22. 写経順序の明記と実 import 監査の毎回実施**。各 introduction に「写経順序」を明記する(章番号順と一致する場合も「章番号順」と書く)。on の Phase では「実装の順」として読む。実 import 監査(#15)は、Phase の生成のたびに全 import 文を読む形で行う。章単位のオーバーレイ再構築(章 N までを都度クリーンな環境に重ねて検証する方式)は導入しない(費用対効果。5.6)。

**#29. 章の冒頭の「この章の目的」**。各 `Phase-<N>-<n>.md` は、タイトルの直後・モードの表記より前に `## この章の目的` 節を置き、その章で実装する機能の概要(何を・なぜ)を1〜数文で書く。introduction の章一覧が章の間の位置づけを俯瞰するのに対し、この節は章ファイルを単体で開いたときに「何を作るか」が分かるようにするためのもの。

**#32. 未消化の申し送り**。各 introduction に「未消化の申し送り」節を置く。前の Phase の同じ節から未解決の項目をそのまま引き継ぎ、この Phase で生まれた分を足す。この Phase で解決した項目は消し、どこで解決したか(章・リンク)を1行で書く。後続 Phase の着手時はこの節から読む。

### C. 教材内のコード提示 ── 抜粋 / samples / パッケージ

**#3.** 教材で提示するコードは、長いコードブロックを Markdown に直書きせず「要点の抜粋 + 共有サンプルフォルダ(例: `textbook/samples/`)のファイル参照」とする。samples は1フォルダを全 Phase で共有し(直近 Phase の end 状態)、**自動実装モード(#20)によらず同じ内容で作成・追記する**。反映の順序は「相談で決定 → samples に反映(#9)→ 教材の抜粋が追従」で、教材は samples の抜粋である。
- **off の Phase**: ユーザーが samples から本体へ写経・改変する。
- **on の Phase**: AI が本体と samples の両方を書き、どちらかを後追いにしない(新規ファイルも samples に作る)。Phase の版は本体の git タグ(例: `phase-<N>`)でも示す。
- samples から削除したファイルへの教材のリンクは外し、ファイル名をコード表記で地の文に残す。
- 教材の構成・体裁・番号の変更(章のリネーム、節の再編など)はマーカーを付けず、内容で上書きする。

**#7.** 教材でコードを提案するときは、配置先のファイルパスを各コードブロックの先頭にコメントで明記する(例: `# app/service/foo.py`)。分割するモジュールはパッケージとして示し、集約ファイル(`__init__.py` など)の re-export 形とファイル間の依存方向も示す。既存教材の修正時・以降の Phase でも同様。

**#9.** 検討・相談の中で提示したコード(クラス名・シグネチャ・型など)に変更が生じたら、samples に同じ変更を #27 の形式で反映する。on の Phase では本体にも同時に反映する(Phase 完了後の調整も同じ)。反映後は実プロジェクトの環境で実行確認し、可能なら型チェックも通す。

**#27. samples の変更履歴の書式**(#12 の具体化)。samples の中で、写経者が変遷を追えるよう次の形式に統一する。
- **ファイル冒頭のヘッダー**: 先頭行に `# 作成：Phase-<N>-<n>` および/または `# 更新：Phase-<M>-<m>,<O>-<o>` を1行で書く。両方ある場合は `# 作成：Phase-<N>-<n>｜更新：Phase-<M>-<m>`。手法の導入前から存在するファイルは「作成」を省く。
- **変更箇所のタグ(3種)**:
  - 追記(既存コードに影響しない純粋な追加): 追加箇所の直前に `# Phase-<N>-<n>:追記` を1行。
  - 更新: `# Phase-<N>-<n>：更新` の下に旧コードをコメントアウトし、`# ↓↓` を挟んで新コードを続ける。
  - 削除: `# Phase-<N>-<n>：削除` の下に旧コードをコメントアウトするだけ。
  - 同じ箇所が複数の Phase で変わった場合は、直近の変更だけを「旧 → 新」で示せばよい。
- **import 文への追記の特則**: import の行ごとにタグを挟むと、リンターの並べ替え(isort など)が誤検知して `--fix` でタグを壊す。import への追記タグは import ブロック全体の直前に1か所へまとめ、対象を `──` 以降に列挙する(例: `# Phase-<N>-<n>:追記 ── app.models.project, app.services.errors.ProjectNotFoundError`)。
- **章タグの引き継ぎ**: タグは次の明示的なタグが現れるまで引き継がれて読まれる。既存の関数の前にブロックを足した箇所など、後ろの既存コードが直前のタグに属して見える境界には、「ここから Phase-X-Y の作成分」のような再タグを置く。
- 整形だけの変更(並び順・import の順・引用符・末尾のセミコロン・テスト名の Phase 番号)は、タグを付けずに上書きしてよい。
- 言語のコメント記法に合わせる(`#`・`//`・JSX の `{/* */}` など)。タグを書けない位置(JSX の属性の中など)は、ファイル冒頭の注記にまとめる。
- on の Phase でも、新規ファイルを含むすべての samples にこの書式を使う。本体の差分をこの形式で当てる補助スクリプト(差分 → タグつきの samples)を用意すると、手間とミスが減る。

**#28. 「作成・更新したファイル」表の依存順**。各章の「この章で作成・更新したファイル」表は、上から順に写経しても import エラーが起きないよう、実際の import 文に基づく依存順(依存されるファイルを上)に並べる。型チェック専用の import(`if TYPE_CHECKING:` など、実行時に評価されないもの)は対象外。依存関係の無いファイル同士は層の慣習(モデル → リポジトリ → サービス → ルートなど)を保つ。テストは表の末尾にまとめ、テスト用のフィクスチャをテスト群の先頭に置く。

### D. 章ごとの解説とテスト設計

> 実装ファイルを作らない章(設計フェーズの各章、理論のみの章など)は、#13 の全ファイル解説・#15 の全ファイル import・#12 のリファクタ追従の対象外。introduction の章一覧でその旨を明記する。

**#13.** 各章は、その章で作成 / 更新する全ファイルを「責務1行 + 中身の要点(型・シグネチャ・非自明な判断。パッケージは #7 のとおり re-export 形も)」で解説する。ファイル構成ツリーに列挙するだけで解説を省略しない。各章の冒頭に「この章で作成 / 更新するファイル」を明記する(並び順は #28)。教材生成後、章の解説とファイル一覧 / 実装前チェックリストを突き合わせ、漏れが無いか確認する(#15 の「全ファイルをテストが import」と同じ機会に)。

**#14.** 各章の `## テスト観点` 節では、テスト(またはテスト群)ごとに **テスト対象(SUT)/ ドライバ / スタブ(テストダブル)** の関係を明記する。スタブが不要な場合は「スタブ不要 ── 対象が純粋(副作用なし)で外部依存を呼ばないため」のように理由込みで書く。狙いは「テストを通じた設計理解」── テストダブルの要否がレイヤー設計(純粋 / 副作用)の鏡であることを各章で言語化すること。用語は初出の章で1行定義し、以降の章は関係の明記だけでよい。**自動実装モードによらず省略しない**(#20)。

**#15.** 章が作成 / 更新する全ファイルを、その章のテストが少なくとも1度は import すること(教材生成後・#13 の突き合わせと同時に確認)。写経漏れ・写経ミス(on では実装漏れ)を検知できるようにするため。集約の**機構**のテスト(レジストリの検索処理など)は、具体的な後発実装でなく**フェイク**(fixture で登録)で行う。テスト用フィクスチャも初出章の作成物として実装前チェックリストに含める。純粋関数は素で、外部依存を注入できる設計はフェイクで(#14)。
- **前方 import の禁止**: 章 N が作成 / 編集するどのファイルも、その import 先(モジュール**と**モジュール内のシンボル)が {以前の Phase} ∪ {この Phase の章 N まで} で存在しなければならない。新規ファイルも既存ファイルへの追記も同じ扱い。後の章 M(> N)で生まれるモジュール・シンボルへの import を含むファイル(またはその関数・クラス)は、最初の消費者の章(≥ M)で書く。部品を使う画面(作業領域など)を先に作ると前方 import になりやすいので、部品の章を先に、組み立ての章を後にする。
- **2つの罠**: (a) 新規ファイルはヘッダー以外に Phase タグを持たない ── タグの `grep` だけでは検出できない。(b) 「モジュールはあるが名前が無い」── import 先のモジュールは既存でも、import する特定のシンボルが後の章の追加物であるケース。集約キー + その実装 import + 配線テストを同じ章で足すのは前方参照ではない。
- **実 import 監査**(#13 と同じ機会。毎回行う。#22): 各ファイルについて ① 作成 / 初出の章を確定、② 全 import 文を列挙、③ 各 import 先のモジュールとシンボルの誕生章を確定、④ ③ > ① を全て潰す。タグの `grep` は補助に留める。

**#16.** 欠番(v1 で #12 のリファクタ追従条項に統合)。

**#31. E2E の実行**。E2E は Phase ごとには流さない。画面の流れやデプロイに関わり E2E が必要な Phase は、その旨を introduction で宣言し、その Phase で**既存の E2E を含めて全部**流す(過去の Phase の変更で壊れた E2E をそこで検出する)。E2E が外部サービスの偽物(偽の LLM など)を使う場合は、偽物の出力が本物の検証・処理の経路を通ることを、E2E とは別の単体テスト(契約テスト)で固定する。E2E が落ちたとき、原因が画面と偽物のどちらにあるかを切り分けられるようにするため。

### E. 後続 Phase での改訂 ── 以前の Phase への遡及

**#12.** 後続 Phase で、以前の Phase の提示コード・設計・決定事項に変更が生じたら(共通化のために触ってよいかの判断は #17):
1. 変更後の内容は、当該後続 Phase の教材に書く(要点の抜粋。動くコードは #3 の基準の側)。
2. コードの変更を samples に #27 の書式で記録する(自動実装モードによらない。on の Phase では本体のコミットも履歴になる)。**やらないことに確定**した計画(旧計画の撤回)は、教材・設計文書の当該箇所に次の blockquote で残す: `> **[Phase <N> で確定 ── 〈…しない〉]** 当初〈…する予定〉→ 撤回。理由〈…〉。` grep 用の合言葉: 更新 = `：更新` / 撤回 = `で確定 ──`。
3. 変更元 Phase の introduction の「後続 Phase での改訂」節に1行、決定ダイジェスト(#23)にも要点を残す。
4. リファクタ(公開挙動を変えない整理 ── 関数の抽出・移動・シグネチャ変更)の写経ミスの番人 = 当該章の第一テストの統合スモーク(リファクタ対象の公開 API を素で1回呼ぶ)。docstring に「よくある失敗モード → どの行を見るか」を書く。以前の Phase の該当テストは写経後に再実行する ── 公開挙動が不変ならアサーションはそのまま、変わるなら変更前後をコメントで対比する。
- 教材の構成・体裁・番号の変更(章のリネーム、節の再編、参照リンクの張り替えなど)はこのルールの対象外。マーカーなしで上書きし、決定は #8・#10 のログに残す。

**#17. 以前の Phase のコードを共通化のために触ってよいかの判断基準**。後続 Phase が以前の Phase のコードと同じ**ドメインの事実**(式・不変条件・データ構造)を必要とするとき、「コピーして重複させる」か「抽出・共通化して共有する」かの分岐では**常に共有を選ぶ**。#12 の記録とスモークのコストを払ってでも重複を残さない。**触らないもの**: (a) 教材本文の遡及的な全面リライト (b) **駆動する新しい消費者がいない**遡及のクリーンアップ / 監査(フォルダ構成の再整理を含む) (c) レイヤー境界が要求する分割(これは重複でなく必然。例: バックエンドとフロントエンドに同じ文言を置く)。**判定の一問**: 「この共通化を今駆動している、この Phase の実在の消費者は何か」に具体名で答えられれば実施、「将来たぶん」「一般に良い設計だから」なら見送る。

### F. 記録

**#4.** 実装段階での検討事項・検証で発覚した事象は記録する。振り分けは ── 質問・相談ログ → #8 / 進行方法の所感 → #10 / 後の Phase に前向きに効く決定・知見 → #23 / 次の Phase に持ち越す未解決事項 → #32。

**#8.** ユーザーが AI に行った質問・相談とその回答を、専用のログファイル(例: `textbook/q_a.md`)に追記する(保存専用・作業中は参照しない)。各エントリ: (1) 疑問が生じた Phase (2) 質問・相談内容 (3) 回答と対応方針。進行方針にかかわる決定・設計判断は、決定ダイジェスト(#23)にも要約を残す(こちらが参照用)。

**#10.** プロジェクトの進行方法について気づいた点(特徴・メリット / 課題 / 課題解決への提案)を振り返りファイル(例: `textbook/appendix/*-retrospective.md`)に書く。課題には可能な限り「提案」を対で書く。提案を組み込むかはユーザーが個別に判断する(AI は勝手に適用しない)。振り返りは Phase ごとでなく、**ステージ(複数の Phase のまとまり)の完了時にまとめて吟味してよい**。その間に後の Phase に効く事項は、#32 の節に残して見失わないようにする。

**#23. 決定ダイジェストの置き場と更新の時期**。決定ダイジェストは方針ファイルと別のファイル(例: `textbook/decision-digest.md`)に置く。#8 のログ(保存専用・非参照)と違い、**進行中に能動的に参照する**ファイルである。後の Phase に効く分だけを圧縮して書き、詳細はログへのリンクで示す。追記は Phase 完了時(またはステージ完了時。#10)にまとめて行い、生成のセッションの中で都度追記しない(#18 と整合させる)。対象はそのプロダクト自身で完結する決定・知見に限り、プロダクトの外側(他のリポジトリなど)に関わる事項は別のメモに書く。

**#24. md 間の参照はリンクで書く**。教材・記録の `.md` ファイルが他の `.md` ファイルの内容を参照・前提とする場合、ファイル名を地の文で書くだけでなく Markdown リンク(`[表示名](相対パス)`)を張る。方針ファイルの「進行のルール」節から教材を参照する場合も含む。参照先を辿るコストを下げ、ファイルの移動・リネームをリンク切れとして検出できるようにするため。リンク切れを機械で検査する道具を用意し、Phase 完了時に流して 0 件にする。リポジトリの外のファイル(追跡されないサブリポジトリなど)はリンクにせず、コード表記で書く。

### G. 進行と役割

**#18. セッション境界**。1セッション = 1 Phase(または1章)を原則とする。振り返り(#10)・決定ダイジェストの整理(#23)・進行ルール自体の改訂・大規模リファクタは、Phase の生成とは別のセッションで行う。判定: セッションの中に「前 Phase の全体テストの実行」「振り返りファイルへの書き込み」「進行ルールの編集」のいずれかが既に含まれていたら、そのセッションで新しい Phase の生成を始めない。生成中の検証は影響範囲を絞った部分テストに留め、全体テストは Phase 完了時に1〜2回だけ行う。

**#20. 自動実装モード(on / off)**。**Phase 単位**で決め、`Phase-<N>-introduction.md` の冒頭で宣言する。ユーザーが「Phase N を開始する」(#5)ときに指定し、指定が無ければ AI が着手前に確認する。
- **教材の中身は on/off で変えない**。#14 のテスト観点は、どちらのモードでも省略しない。
- **off**: AI は教材と samples だけを作り、ユーザーが手で本体へ実装する。本体には、ユーザーが明示して指示したときだけ反映する。
- **on**: AI が本体へ実装し、samples も off と同じ内容で作成・追記する(#3・#9・#27)。本体のコメントには Phase の経緯を書かない(3章「コメント規約」)。
- **Phase 完了時の検査**(on): samples と本体の一致、samples への作り忘れ(前の Phase の版以降に本体で追加・変更したのに samples に無いファイル)、教材のリンク切れ(#24)を道具で検査し、すべて 0 件にする。一致の検査は、#27 のタグ・コメントアウトした旧コード・コメントを除いてコードだけを比べ、例外は理由つきの許可リストに書く。
- **共通**: リポジトリ直下のインフラ・設定ファイル(compose・CI・デプロイの設定など)は samples に写さず、AI が直接書く。
- 試行の経緯: 「学習モード(全写経)/ 納期モード(定型はコピー)」の二モードは、納期モードでも工程があまり省けず、テスト観点が教材から省かれた。また、手で実装しても設計の理解は思ったほど実感できなかった。そこで「誰が本体へ実装するか」だけを切り替える形に改めた。

**#30. コミット・プッシュは人が行う**。AI は `git commit`・`git push` を実行しない。作業の終わりに、コミットの単位(リポジトリが複数あればその単位)とコミットメッセージの案(on の Phase ではタグ名も)を示すまでにとどめる。

**#33. AI の提案と人の最終決定**。AI が書くコード・設計・計画は提案であり、採用するか変えるかは人が最終的に決める。画面確認の後の修正や、Phase の分割・撤回・番号の付け直しは、問題ではなく通常の工程として扱う。経緯は #8 のログと、introduction の「後続 Phase での改訂」(#12)に残す。AI が構造(図の種類・文書の章立てなど)を提案するときは、実務の資料での裏付けを確かめてから勧める(裏付けの無いまま勧めて撤回した例がある)。

## 3. コード規約・命名規約(汎用原則)

### コード提示規約

- コードを提案する各ブロックの先頭に、配置先のファイルパスをコメントで明記する(#7)。
- 複数ファイルに分割するモジュールは、パッケージ(該当言語のパッケージ機構)として提示し、集約ファイルの re-export 形と依存方向も示す。
- 「教材 Markdown / samples / 本体」の三重管理のずれを防ぐ。教材は samples の抜粋にし、samples と本体の一致は道具で検査する(#3・#20)。

### 命名: 先頭アンダースコア `_`(非公開の印)

言語がアンダースコア接頭辞を「非公開(internal)」の慣習として扱う場合(Python の PEP 8 など)、lint で強制せずとも**読み手への約束**として運用できる。

| 形 | 意味 |
| --- | --- |
| インスタンス属性の非公開(`self._attr`) | クラスの公開面は公開メソッドだけ。呼び出し側は非公開属性に触らない |
| モジュールレベルの非公開関数・定数・型 | そのモジュールの外から import させない内部部品。公開 API は `_` なしの名前(+ 言語の公開リスト機構があればそれも) |
| 使い捨て変数(`for _ in ...`) | 束縛するが使わないことを示す |
| 診断用・比較対象外の値を示す接頭辞 | 「目的値ではない・他の値と直接比較しない内部指標」であることを dict のキー名などで示す |

`_` の有無は「この名前を外から使ってよいか」という設計判断そのものである。後の Phase で内部の実装を共有のモジュールへ移すとき(#17)に `_` を外すのは、その判断が変わったことの記録になる。

### コメント規約

コメントの**密度の目安**と**書く内容の方針**は言語非依存だが、**書式**(docstring か JSDoc かなど)は採用するスタックの慣習に合わせる。

| 対象 | 内容 | 目安 |
| --- | --- | --- |
| 関数の説明 | 何をする関数か(必要なら「なぜ」も) | 60〜100 文字程度 |
| 関数の引数・戻り値 | 各引数の意味と戻り値 | 簡潔に |
| 関数内の条件分岐・繰り返し | その分岐 / ループが何を判定・処理するか | 40 文字程度 |
| 関数内の変数 | その変数が保持する値 | 簡潔に |

- 方針の核は**「なぜ / ハマりどころ」中心**。型と命名で自明な引数・変数はコメントを省いてよい。既存コードにこの水準を超える有用な記述があれば、削って画一化しない。
- **本体のコメントには経緯を書かない**。Phase の番号・ステージの番号・進行ルールの番号・決定の番号・教材への参照・「画面確認後に変更」のような記述は入れず、機能と意図だけを現在形で書く。経緯は samples のタグ(#27)・教材・コミットに書く。本体は教材が無くても読める状態に保つためである(経緯が入り込むと、後で一括して取り除く手間がかかる)。

## 4. 設計判断のヒューリスティクス(型)

CL 開発を通じて、新しい Phase の設計判断に繰り返し使える「型」が言語化された。特定のドメインに依存しない一般的なパターンである。

### v1 から引き継いだもの

- **分割 vs 統合**: 「一緒に変わるものを同じファイルに」。複数の概念を束ねるファイル(アグリゲータ)が各要素を import する構造は、要素同士が互いを import しない限り悪い密結合ではない。
- **「これは計算か? 述語か?」**: 探索・走査を伴う**計算**は計算を担うレイヤーに、値の性質を判定するだけの**純粋述語**はドメインを担うレイヤーに置く。可否の最終判断(ゲート)はさらに別のオーケストレーション層に置く。レイヤー間の import 方向の制約は、この判断の誤りを実装中に顕在化させる guardrail であって、判断そのものの理由ではない。
- **data 層の粒度**: モデル・スキーマ・リポジトリは「永続化の関心事」でまとめる。操作(ルーティング・サービス)は「操作」の単位で割る。「ファイルが短いから分ける」は基準にしない。
- **ヘルパの置き場は「2本目の消費者」で決まる**: 最初から汎用と分かっているものは1本目から共通モジュールに置く。迷うものは、2本目の消費者が現れた時点で共通化する。
- **共通化するのは機構であってオーケストレーションではない**: 共通の「仕組み」は共通化し、個々の処理の「レシピ」(どの順で何を呼ぶか)は各処理の中に直線的に見せる。
- **以前の成果物を共通化のために触ってよいかの一問**(#17): 「この共通化を**今**駆動している、実在の消費者は何か」。
- **YAGNI**: 消費者が存在しない投機的な実装は、必要になる Phase まで先送りする。

### v2 で足したもの

- **正本は1か所、他は導いた表示**: 同じ情報を2か所に持たない。例: 図の意味モデルが正本で、描画ライブラリの状態は毎回そこから作り直す(戻すのはドラッグで確定した位置だけ)。テーブル定義は ER の列が正本で、表は ER からの表示。複数の段階の成果物を束ねた文書は保存せず、毎回意味モデルから決定的に組み立てる。
- **番号・ID は保存せず、並び順から導く**: 手順番号・項目の ID・マイルストーンの番号のような連番は、保存すると行の追加・削除のたびに付け直しが要る。並び順から純粋関数で導けば、付け直しを人や AI に任せずに済む。
- **紐づけは番号でなく、安定したキーで**: 2つの成果物をつなぐときは、振り直される番号ではなく、内容から決まるキー(例: 「呼び出し先のパス + 関数名」の組)の一致から導く。片方を正本にして参照を持たせると、もう片方の編集が正本を書き換え、承認の差し戻しが循環することがある。
- **安定した ID は AI に書かせない**: AI の出力から ID を作るときは、前の版の行と内容のキー(例: メソッド + 正規化したパス)で突き合わせて ID を引き継ぎ、新しい行だけ採番する。消えた番号は再利用しない。
- **状態は保存する最小集合 + 導く値**: 保存する状態は人や処理が明示的に遷移させるもの(下書き / レビュー中 / 承認済みなど)だけにし、「未着手」「古い」のように他の値から決まるものは純粋関数で導く。古さは入力の版の指紋を「等しくない」で比べる。
- **検証は「保存は通し、承認で止める」**: 編集の途中の状態も保存でき、エラーが残っていれば承認だけを断る。検証の登録の仕組みは、最初の実在の消費者が現れた Phase で作る(#17)。
- **作り直しの範囲は、人の手直しの量で決める**: 人の手直しが少ない成果物は「作り直しは全部置き換え」でよい。手直しが多い成果物は、作り直しを単位(処理ごと・関数ごと)に絞り、他の単位の手直しを残す。
- **導いた値をどこで導くか**: 編集中の内容にすぐ反映させたい値は画面で導く。複数の保存済みの成果物から決まる値は、バックエンドが導いて返す(画面で導き直さない)。
- **前段を直したら、後段は「古い」と示すだけ**: 自動で作り直すと、人が手直しした後段が黙って消える。作り直しは人がボタンで指示する。
- **外部サービスの偽物は契約テストで固定する**(#31)。

## 5. 残った課題・検討事項・提案

**いずれも採用可否はプロジェクトごとに判断する**(#10)。v1 の 5.1〜5.6 の採否の結果を各節の冒頭に書き、新しい課題を 5.7 以降に足した。

### 5.1 進行スピード

v1 の結果: ③(事前質問の限定)と⑥(完了チェック)は採用してルールにした(#19・#21)。④(写経レベル)は採用後に廃止した。二モード案は自動実装モード(#20)に改めた。①(タイムボックス)・②(新しく使う機能の明記)・⑤(先行生成)はルールにしなかった。

- **on の Phase では、速度の律速が写経から「設計の決定と画面確認の往復」に移った**。着手時の相談で設計判断を2〜4点に絞って決め、画面確認の後の修正を通常の工程として扱う(#33)ことで回した。
- **off の Phase の速度は未解決**。タイムボックスと目安工数(v1 の①)は試していない。off を長く続けるプロジェクトでは、まずこれを試す価値がある。
- **②は慣習として自然に生まれた**。introduction の前提の節に「既存コードに前例が無い新規パターン」を先に示す形が有効だった(#6 に任意の要素として入れた)。
- **⑤(次の Phase の先行生成)は相性が悪い**。計画は着手時の相談で変わる(分割・統合・撤回)ことが多く、先に作った分が無駄になりやすい。#18 とも衝突する。
- **Phase 完了チェック(#21)は、判定としては使われなかった**。設問は全 Phase に置いたが、ユーザーが答えた記録は無い。要約としては役に立つ。判定に使うなら「次の Phase の着手時に、前の Phase の設問から1問答える」など、使う場面をルールにする案がある。

### 5.2 状態(ルール・記録)の肥大化

v1 の結果: 4つとも採用した(質問ログの分離、決定ダイジェストの分離、ルールのカテゴリ再配置、共有の samples)。samples は on の Phase で扱いを改めた(#3)。

- **固有ルールがカテゴリの外に積み上がる**。改訂元のプロジェクトでは #38 まで増え、#18 以降が末尾に並んだ。本書では固有ルールを各カテゴリへ配り直した。プロジェクトでも、ステージの完了時の振り返りでカテゴリへの配り直しを行うとよい。
- **運用注記の層が増える**。転記元の本文を変えないために注記を足していくと、本文と注記の両方を読まないとルールが分からなくなる。次の版を作るときに本文へ統合する(本書は #3・#9・#12 の注記を統合した)。
- **記録が後回しになり溜まる**。振り返りと決定ダイジェストは、Phase ごとでなくステージ完了時にまとめてよいとした(#10・#23)。その代わり、途中の申し送りを #32 の節に必ず残す。

### 5.3 本体・samples・教材の三重管理

v1 の結果: 抜粋に行番号を添える案は採らなかった。代わりに、道具による検査を採った。

- on の Phase では、本体が先に変わり samples が後追いになるため、反映漏れ・タグの付け漏れ・本体のコメントへの経緯の混入・samples の削除によるリンク切れが起きた。
- 対策(#3・#9・#20・#27): Phase 完了時に「samples と本体の一致」「samples への作り忘れ」「リンク切れ」を道具で検査する。本体の差分をタグつきで samples に当てる補助を使う。
- 試した結果: いったん「on では samples に新規ファイルを作らない」(本体を基準にする)と決めたが、samples の内容がモードで変わると、教材(実装手順書のひな形)の中身もモードで変わってしまう。「教材の中身は on/off で変えない」(#20)を優先し、on でも samples を作る形に戻した。
- off の Phase で写経されなかった分(samples の側が先)も、一致の検査で見つかる。見つけたら本体に足す。

### 5.4 事前理解のハードル

v1 のとおり構造的に残る。自動実装モード on は、「先に完成品を作り、そこから仕様を追う」ことで、このハードルを回避する選択でもある。

### 5.5 セッション運用

v1 の結果: 4つの調整案はすべて採用した(#18、記録は簡潔に、触るファイルを先に確定、全体テストは完了時)。

- 1 Phase = 1 セッションは厳密には守られなかった(画面確認後の修正を同じセッションで重ねる、複数の Phase を同じ日にまとめてコミットする)。支障の記録は無い。
- 提案: 次のステージの最初の Phase で、実際のセッションの区切りを記録し、ステージ完了時の振り返りで #18 を見直す。
- 全体テストで、並列実行の負荷による時間切れが出る(特にフロントエンド)。並列数を絞って流す運用を最初から決めておく。

### 5.6 写経順序と前方 import

v1 の結果: 実 import 監査と写経順序の明記を採用し(#22)、章単位のオーバーレイ再構築は見送った。

- 実 import 監査は効果があった。タグの付け漏れ、章の順の前方 import(部品より先に組み立ての画面を作る順)、テストが import していないファイルを見つけた。
- on の Phase では写経が無いので問題自体は小さくなるが、監査は「章ごとのテストが章のファイルを確かめているか」の検査として残す価値がある。

### 5.7 on の Phase で、学習をどう回収するか(新規)

- **課題**: 「完成品から仕様を追う」ための読み方の手がかりが、教材の側にまだ無い。写経レベル(コア / 定型)の印も廃止した。
- **提案**: 章ごとに「読む順番」または「設計判断の要点」を1〜3行で示す欄を、#13 の解説の先頭に置く。教材を実装手順書のひな形として使う場合にも役に立つ。

### 5.8 検証の穴(新規)

- **課題**: E2E を手元でしか流していないと、ある Phase の変更で壊れた E2E に、何 Phase も気づかない(改訂元のプロジェクトでは9 Phase 後に気づいた)。画面を実際に動かす確認が無いまま完了した Phase もあった。
- **対策**: #31(必要な Phase で既存分も含めて全部流す)。画面確認はユーザーに依頼し、introduction の「検証結果」に依頼中かどうかを残す(依頼中のまま残った記述は #32 で拾う)。
- **提案**: E2E を CI で流す。必要な時間(改訂元のプロジェクトでは3本で約1.5分)と、CI でサービスを立てる手間を比べて決める。

### 5.9 計画の変動(新規)

- **課題**: 着手時の相談で Phase を分割して番号を送る、計画を撤回する、ということが何度も起きる。
- **扱い**: 問題ではなく通常の工程とする(#33)。ロードマップは暫定とし(#25)、分割・撤回は introduction の「後続 Phase での改訂」と撤回の blockquote(#12)で追えるようにする。目安として「1つの機能のまとまり(1段階など)= 1 Phase」の粒度に収まらなければ分割する。

## 6. 用語集

- **SUT(System Under Test)**: テストの対象そのもの。
- **ドライバ**: SUT を呼び出し、テストを駆動する側(多くの場合テストコード自身)。
- **スタブ(テストダブル)**: SUT が依存する外部要素を置き換える代用品。SUT が純粋(副作用が無く外部依存を呼ばない)であれば、スタブは不要になる ── この要否がレイヤー設計(純粋 / 副作用)の鏡になる(#14)。
- **本体**: 実プロジェクトのリポジトリのコード。samples(教材用のサンプル)と区別して呼ぶ。
- **自動実装モード**: Phase ごとに、本体を人が書くか(off)AI が書くか(on)を決める設定(#20)。
- **ステージ**: 複数の Phase をまとめた、プロダクトのマイルストーンの単位。振り返りと決定ダイジェストの吟味の単位にもなる(#10・#23)。
- **契約テスト**: 外部サービスの偽物が、本物の規則(検証・処理の経路)に従っていることを固定するテスト(#31)。
