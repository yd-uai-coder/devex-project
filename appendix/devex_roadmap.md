## 1. Devexのアプリケーション改修方針

### 1.1 目指すアプリケーション

Devexは、単なる「AIによる設計書生成アプリ」ではなく、

> **要件定義から設計・実装計画・実装手順・テストまでの開発プロセスをつなぎ、設計の一貫性と実装可能性を支援するシステム**

を目指す。

さらに、ポートフォリオとしては、

> **「設計士としてどのようにシステムを分解し、設計し、検証し、実装へ落とし込むか」という思考過程を証明する作品**

として位置づける。

### 1.2 現在のDevex(ステージ4完了時点)

以下の機能まで実現し、本番に反映している。

1. AIチャットによる要件ヒアリング(プロジェクト名の入力、ヒアリング結果のサマリ、完了判定)
2. 要件定義書・外部設計書のAI生成と、生成後の自己診断(3段階)
3. 簡易ドキュメントモード: 内部設計書・実装計画書まで一括生成
4. 詳細設計モード: 段階ごとに人が承認しながら組み立てる
   - ① 機能(処理)一覧 → ② データフロー → ③ データモデル → ④ ソフトウェア構造 → ⑤ 主要処理の手順 → ⑥ 処理ロジックの詳細 → ⑦ 横断事項と実装計画
   - 各段階は、AI の構造化出力 → 意味モデル(Pydantic)→ 人の承認 → md/HTML という流れで作る
   - 処理ID(例: `F-01#4`)による段階間の紐づけ、05↔06 のバッジ、逆引き表、関与表
   - 段階単位の陳腐化の検知と、手動の再生成
   - 図(DFD・ER・構成図)の自動レイアウト、React Flow での編集、draw.io / SVG 出力
5. 文書のバージョン履歴・プロンプトテンプレート・構造化ログ

**まだ無いもの**: 要件定義書・外部設計書は Markdown のままで、要件ID(REQ-xxx)が無い。このため、「要件 → 機能」の上流側の追跡が途切れている。また、ヒアリングの完了判定(5条件)に、非機能要件とセキュリティの観点が無い。

### 1.3 改修の基本方針

今後は「ドキュメントを増やす」こと自体を目的にしない。

以下の方向へ発展させる。

``` text
要件 → 要件定義 → 外部設計 → 内部設計 → 実装計画 → 実装手順 → 実装 → テスト
```

この各段階を、単なるMarkdown文書としてではなく、相互に参照可能な設計情報としてつなげていく。

特に重要なのは、

- 設計情報の構造化
- 設計間のトレーサビリティ
- 漏れの少ないヒアリング(ユーザー自身から要件を引き出す)
- 変更影響分析
- AIによる設計レビュー
- 実装可能性の検証
- 実装計画から実装手順への変換
- 設計と実装・テストの整合性検証

である。

### 1.4 なぜこの方向を目指すのか

「AIに設計書を書かせる」だけでは、既存の生成AIサービスとの差別化が弱い。

Devexの価値は、

> **AIを使って設計作業を効率化することではなく、設計そのものの品質・一貫性・実装可能性を高めること**

に置く。

また、AIがコードを完全自動生成することを最終目的としない。

人間が、

- なぜこの構造になっているのか
- どの責務をどこに持たせるのか
- どの順番で実装するのか
- どの設計変更がどこへ影響するのか

を理解した状態で開発できることを重視する。同じ理由で、セキュリティや非機能要件も AI の提案に頼り切らず、ユーザーが自分で判断できる形で引き出す。

## 2. ステージ一覧

### 完了済みのステージ

詳細は [`docs/implementation_plan.md`](../docs/implementation_plan.md) 4.1節と、各 Phase の教材(`textbook/Phase-<N>/`)にある。

#### ステージ1:MVP ── 【完了・Phase 1〜5】

- **トピック**: チャットによるヒアリングと、4文書(要件定義・外部設計・内部設計・実装計画)の一括生成。
- **目的**: コア機能をエンドツーエンドで動かし、本番(VPS)まで届ける。
- **作ったもの**: JWT 認証、プロジェクト管理、添付ファイルの読み込み、ストリーミングのチャット、バックグラウンドでの4文書生成、プレビュー・ダウンロード、自動デプロイ。

#### ステージ2:機能拡張・品質向上 ── 【完了・Phase 6】

- **トピック**: 運用と使い勝手の改善。
- **目的**: 継続して使える品質にする。
- **作ったもの**: 文書のバージョン履歴(閲覧・比較・復元)、プロンプトテンプレートの選択、構造化ログ・エラー追跡。

#### ステージ3:UML設計図パイプライン ── 【完了・Phase 7〜13】

- **トピック**: 文書から構造化された設計情報(意味モデル)を作り、図にする。
- **目的**: 設計を「文章」ではなく「構造」として扱う土台を作る。
- **作ったもの**: UML 意味モデル(Pydantic)・データ辞書、決定論的なレイアウトエンジン、React Flow でのレビュー・編集、承認フロー、draw.io / SVG 出力。
- **補足**: 簡易モードから設計図を作る機能は、ステージ4 の詳細設計モードが同じ図を作るようになったため、Phase 24 の後に撤回した。図の編集・検証・レイアウト・出力の部品は詳細設計モードが引き継いでいる。

#### ステージ4:詳細設計モード ── 【完了・Phase 14〜24】

- **トピック**: 実務(C4・arc42・日本の詳細設計)に合わせた、段階承認型の詳細設計。
- **目的**: 人がコーディングするのに十分な資料を作る。設計情報を構造化し、段階間の紐づけを持たせる。
- **作ったもの**: 段階1〜7(1.2節)、処理IDによる紐づけ、段階単位の陳腐化の検知、詳細設計書・実装計画の zip(HTML+md+図)、偽 LLM による段階1〜7 の契約テストと E2E。

### これからのステージ

#### ステージ5:実装手順書 + 実装可能性チェック ── 【次】

##### 1. トピック

実装計画・詳細設計から、開発者が実際に作業できる実装手順へ変換する。その変換の中で、設計が実装できる状態かを検証する。

##### 2. 目的

- 「設計書を作る」から「設計を実際の開発作業へ落とし込む」ところまで責任範囲を広げる。
- 「設計は書けているが実装できない」という問題を、手順書を作る過程で表に出す。
- ここで見つかった不足を、ステージ6(ヒアリング改良)の材料にする。

##### 3. 何を作るか

実装タスク(作業単位)ごとに、次を記載した実装手順書を生成する。

- 対象ファイル(依存順)
- 作成・変更対象と責務1行
- 実装順序・実装内容
- 使用する設計情報(処理ID 等)
- インターフェース・依存関係
- 注意事項
- 確認方法・テスト観点

あわせて、次の実装可能性チェックを行う。

- 必要なコンポーネント・インターフェース・DB モデルが定義されているか
- API 仕様が実装可能な粒度か
- トランザクション境界・エラー処理・認証認可が定義されているか
- 外部依存が定義されているか
- 設計間に矛盾がないか
- 実装順序を決められるだけの情報があるか

##### 4. どのように作るかの例示

- **ひな形は CL 教材**: [ゴール3の比較](../textbook/appendix/goal3-comparison.md)で見つけた共通要素「作業単位の表」(作業単位・対象の処理ID・作成・変更するファイル(依存順)・役割1行・確認方法)を手順書の骨格にする。この開発で書いてきた教材を、手順書のサンプルとして使う。
- **実装者が人でも AI でも中身を変えない**([振り返り](../textbook/appendix/overall-retrospective.md)の決定を、手順書の要件として引き継ぐ)。
- **チェックは2層にする**: 決定論的な検証(段階ごとの既存バリデータの延長。例: 手順が参照するモジュールが段階4 に無い)と、LLM による指摘。チェックだけを先に単独で作らず、手順書の生成と一緒に作る。

``` text
TASK-012:ユーザー登録API

1. Userモデルを作成            対応設計:段階3 の users テーブル
2. UserRepositoryを実装         対応設計:段階4 のモジュール一覧
3. UserServiceに登録処理を実装  対応設計:F-03#2〜#5 / 段階6 の関数
4. POST /users APIを実装        対応設計:外部設計の API 一覧
5. 正常系・異常系テストを追加

⚠ 認可条件が未定義です(F-03#1)
⚠ メール重複時のレスポンス仕様が未定義です
```

##### 5. 重要度

**★★★★★(最重要)**

#### ステージ6:ヒアリング改良 + 上流の構造化 ── 【次の次】

##### 1. トピック

ヒアリングの漏れを減らし、ユーザーの潜在的なニーズを引き出す。あわせて、要件定義・外部設計を構造化し、要件IDを振る。

##### 2. 目的

- 聞き漏れを減らし、潜在的なニーズを引き出して、設計後の要件変更を減らす。
- ユーザー視点では考えにくいセキュリティや非機能要件を、AI の提案に頼り切らず、ユーザー自身の判断として引き出して設計に反映する。
- 要件 → 機能 → 作業単位の追跡を、上流までつなげる。

##### 3. 何を作るか

- **観点ごとに状態を記録する**: 観点ごとに状態(ユーザーが決定 / AI の提案をユーザーが採用 / 未決 / 対象外)を持たせる。今の完了判定(5条件)をこの表で置き換える。
- **出どころを記録する**: 要件定義書に、各要件がユーザーの決定か AI の提案かを書く。後で要件が変わったときに原因を辿れるようにする。
- **非機能の観点は実務の基準に合わせる**: IPA の非機能要求グレード(可用性・性能・拡張性・運用保守性・移行性・セキュリティ・システム環境)を観点の一覧の元にし、プロジェクトの規模に合わせて絞る。
- **答えやすい問い方にする**: 「可用性の要件は?」と聞かず、「止まったら何時間まで困らないか」「誰に見られたら困るデータか」のような場面で聞く。選択肢ごとの結果(コスト・手間)も見せて選んでもらう。AI はおすすめを示してよいが、決めるのはユーザーにする。
- **潜在的なニーズを聞く質問の型**: 利用者ごとの1日の流れ、例外の場面(入力を間違えた・取り消したい・権限が無い)、将来の拡張予定。
- **上流の構造化**: 要件定義書・外部設計書を、内部では構造化モデルで持ち、要件ID(REQ-xxx)を振る。詳細設計の処理IDと結ぶ。

``` text
REQ-001
  └─ F-03(処理)
      ├─ 段階2 の DFD
      ├─ 段階3 の users テーブル
      ├─ F-03#2〜#5(手順)
      └─ TASK-012(ステージ5 の作業単位)
```

##### 4. どのように作るかの例示

- **ステージ5 の結果をものさしにする**: 実装可能性チェックで見つかった不足を「ヒアリングで聞くべきだった項目」までさかのぼって分類し、どの観点を足すかを実例で決める。
- **効果を測る**: ヒアリングが原因の不足の件数を、改良の前後で比べる。偽 LLM ではなく実際の LLM で、決まった数件の想定シナリオを流して比べる。
- 最初の Phase は #28 の仕様診断にし、観点の表と問い方をそこで決める。

##### 5. 重要度

**★★★★★(最重要)**

#### ステージ7:変更影響分析・変更管理 ── 【予定】

##### 1. トピック

設計変更による影響範囲を分析し、変更履歴・陳腐化を要素単位で管理する。

##### 2. 目的

設計を「作る」だけでなく「変更に強くする」。

##### 3. 何を作るか

ある設計項目を変更したとき、影響を受ける設計情報・機能・データモデル・コンポーネント・実装タスク・(将来は)テストを示す。今の段階単位の陳腐化検知を、要素単位に細かくする。変更された設計に対して、再生成の候補を示す。

##### 4. どのように作るかの例示

``` text
変更:F-03「ユーザー登録」

直接影響
├─ F-03#2〜#5
├─ users テーブル
└─ TASK-012

間接影響
├─ 外部設計の API 一覧
└─ REQ-001 に紐づくテスト
```

ステージ5・6 で結んだ ID を使った要素のグラフをたどって影響範囲を求める(標準ライブラリの `graphlib` で足りる)。LLM には「影響理由の説明」だけを任せる。

##### 5. 重要度

**★★★★☆(高)**

#### ステージ8:AI設計レビュー + テスト設計 ── 【予定】

##### 1. トピック

生成した設計の品質をAIにレビューさせ、要件・設計からテスト観点・テストケースへつなげる。レビュー結果から再ヒアリングへ戻る流れを作る。

##### 2. 目的

- 「生成するAI」から「設計を成り立たせるAI」へ進める。
- 要件 → 設計 → 実装 → テストの追跡を完成させる。
- 生成の質を測れるようにする。

##### 3. 何を作るか

- **AI 設計レビュー**: 生成とレビューのモデルを分ける。レビューは設計を書き換えず、「問題・重要度・対象ID・理由・改善案」を返す。重要度は #28 の3段階(最重要・中程度・軽微)を使う。今の自己診断を広げる形で作る。
- **再ヒアリング**: レビューで見つかった、ヒアリングが原因の不足を、ステージ6 の観点の表の「未決」に戻し、チャットで聞き直す(今の「修正中(revising)」の流れを広げる)。
- **テスト設計**: 正常系・異常系・境界値・セキュリティ・非機能・結合テスト。日本の実務(単体/結合/総合テスト、テスト仕様書)の形に合わせる。
- **品質評価**: 決まった少数の正解例で、生成物とレビューの指摘の正確さを測る(偽 LLM の契約テストは形の検証であり、質は測れないため)。

``` text
REQ-001 → F-03 → TASK-012 → TEST-021

TEST-021 ユーザー登録API
正常:正常なメールアドレスで登録できる
異常:メールアドレス重複 / パスワード不正 / 必須項目欠落
```

##### 4. 重要度

**★★★★☆(高)**

#### ステージ9:設計・実装の整合性検証 ── 【将来】

- **トピック**: 実際のコードと設計情報のずれを検出する(設計に無い責務、存在しない API、仕様と違うデータモデル)。
- **目的**: Devex を「開発の開始時に使う AI」から「開発中・開発後も使う設計管理の基盤」へ広げる。
- **方針**: 任意のリポジトリの解析は重いので、対象を自分のスタック(FastAPI / Next.js)に絞る。Devex 自身を Devex で設計し、検証するところから始める。
- **重要度**: ★★★☆☆(中長期)

#### ステージ10:GitHub / CI/CD・運用への接続 ── 【将来】

- **トピック**: Pull Request と設計IDの関連付け、CI での設計整合性チェック、設計変更の検知、リリース単位の設計履歴。
- **目的**: 設計情報を実際の開発ライフサイクルに組み込む。
- **方針**: ステージ9 の整合性検証ができてから進める。
- **重要度**: ★★☆☆☆(将来)

#### 設計図について

初版の「Phase 4:設計図・UML等の自動生成」は、新しいステージにしない。図の部品(意味モデル・レイアウト・draw.io 出力)はステージ3・4 で作り済みである。今後は図の種類を増やすより、既存の図を手順書(ステージ5)や影響分析(ステージ7)から参照できるようにする。

### 3.3 なぜこの順序か

- **5 を最初にする**: 手順書を作ろうとすると、設計の不足が実例として出てくる。チェックだけを先に作るより、手順書と一緒に作る方が、何を検証すべきかがはっきりする。
- **6 を 5 の直後にする**: ヒアリングで聞く項目は主に上流の文書の雛形から決まるので、手順書がそろうのを待つ必要はない。一方、5 で見つかった不足は、何を聞き足すべきかを実例で教えてくれる。また、レビュー(8)まで待つと、その間に作る設計書がすべて今のヒアリングの質のままになる。
- **6 で上流も構造化する**: 観点ごとの状態の記録と要件IDの採番は、どちらも要件定義書の構造化であり、同じ仕事である。
- **8 では再ヒアリングの自動化だけを足す**: 自己診断と「修正中(revising)」でチャットに戻る流れはすでにあるので、それを広げる。

## 4. 今後の最優先領域

現在のDevexでは、設計書の種類をさらに増やすことより、

> **現在存在する設計情報を「実装可能な状態」へ変換すること**

を優先する。

そのため、直近では以下の順序を重視する。

``` text
詳細設計 → 実装手順書(+ 実装可能性チェック) → 不足・矛盾の修正 → 人間が実装 → テスト
                                      ↓
                              ヒアリングの改良へ戻す
```

特に実装手順書を生成しようとすると、

- 必要なファイルが分からない
- 責務の所在が不明
- 依存関係が不足
- API仕様が不足
- DB仕様が不足
- エラー処理が未定義
- トランザクション境界が不明

などの設計上の問題が表面化する。

したがって、

> **実装手順書生成は、単なる実装支援機能ではなく、設計の実装可能性を検証するための仕組みでもある。**

そして、その問題の多くは、さかのぼるとヒアリングの漏れに行き着く。ステージ5 の次にステージ6 を置くのはこのためである。

## 5. Devexの最終的なコンセプト

Devexの最終形は、単なるAIドキュメントジェネレーターではない。

``` text
                 ┌─────────────┐
                 │    要件     │ ← ヒアリング(ユーザー自身から引き出す)
                 └──────┬──────┘
                        ↓
                 ┌─────────────┐
                 │   要件定義  │
                 └──────┬──────┘
                        ↓
                 ┌─────────────┐
                 │   外部設計  │
                 └──────┬──────┘
                        ↓
                 ┌─────────────┐
                 │   内部設計  │
                 └──────┬──────┘
                        ↓
                 ┌─────────────┐
                 │   詳細設計  │
                 └──────┬──────┘
                        ↓
                 ┌─────────────┐
                 │   実装計画  │
                 └──────┬──────┘
                        ↓
                 ┌─────────────┐
                 │   実装手順  │ ← 実装可能性チェック
                 └──────┬──────┘
                        ↓
                    人間が実装
                        ↓
                 ┌─────────────┐
                 │    テスト   │
                 └──────┬──────┘
                        ↓
              設計 ↔ 実装 ↔ テスト
                   の整合性検証
                        ↓
                  GitHub / CI/CD
```

この一連の流れを支える中心には、

> **設計情報の構造化とトレーサビリティ**

を置く。

Devexの価値は「AIが大量のコードや文書を生成すること」ではなく、

> **要求から設計、実装、テストまでの論理的なつながりを可視化し、人間が理解・判断しながら開発できる状態を作ること**

にある。

これにより、ポートフォリオとしても「AIアプリを作った」という実績ではなく、

> **「システム設計という問題をどう捉え、その問題をAIと構造化された設計情報によってどう解決しようとしたか」**

を示せる作品になる。

## 6. 「1年後に重宝されるITスキル」とDevexの関係

Devexのロードマップは、単なるアプリ機能の追加計画ではない。

今後のITエンジニアに求められる能力として重視する、

``` text
Software Engineering
        │
        ├─ Requirements(ステージ6)
        ├─ Architecture / Design(ステージ3・4)
        ├─ Traceability(ステージ4・6)
        ├─ Impact Analysis(ステージ7)
        ├─ Review / Testing(ステージ8)
        └─ Maintainability(ステージ9・10)
                │
                ▼
             Devex
                │
                ▼
        AI Engineering
                │
                ├─ LLM
                ├─ Structured Output(ステージ3〜)
                ├─ Workflow(ステージ4〜)
                ├─ Evaluation(ステージ8)
                └─ AI Review(ステージ8)
                │
                ▼
           Production
                │
                ├─ Docker
                ├─ PostgreSQL
                ├─ CI/CD
                ├─ Security
                └─ Cloud / VPS
```

を一つの実システムで実践することを目的とする。

したがって、今後は個別のAI技術を横に広げることだけを目的とせず、

> **Software Engineering × AI Engineering × Production**

をDevexという実システムの中で一貫して実装・検証することを優先する。
