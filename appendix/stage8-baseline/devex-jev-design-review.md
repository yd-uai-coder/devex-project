# DevexにおけるJevを活用した設計レビュー構成

## 1. 目的

Devexでは、チャットによる要件確認を通じて、次のドキュメントを生成する。

1. 要件定義書
2. 外部設計書
3. 内部設計書
4. 実装計画書

これらのドキュメントについて、要件網羅性・設計間の整合性・設計妥当性を継続的に検証できるようにする。

基本方針は、**LLMにドキュメントを生成させるだけでなく、機械的検証・Jevによる基準別判定・レビュワーLLMによる詳細レビュー・人間の承認を組み合わせる**こと。

## 2. 推奨アーキテクチャ

```text
ユーザーとの要件確認チャット
          |
          v
   Gemini：ドキュメント生成
          |
          v
     構造化された設計モデル
          |
          v
  ① 機械的バリデーション
          |
          v
  ② Jev：基準別の判定
          |
          v
  アプリケーションの判定ロジック
       /              \
      v                v
 基準を通過       要確認・不合格
      |                |
      |                v
      |        ③ Claude等のレビュワーLLM
      |                |
      +--------+-------+
               v
       レビュー結果を統合
               |
               v
         人間による承認
               |
               v
       必要に応じて修正・再レビュー
```

### 各コンポーネントの責務

| コンポーネント | 主な責務 |
|---|---|
| Gemini（生成モデル） | 要件定義書・外部設計書・内部設計書・実装計画書の生成 |
| 機械的バリデーション | ID欠落、参照先不存在、必須項目不足、スキーマ違反などの検出 |
| Jev | 定義された評価基準に基づく判定、確率・スコアなどの出力 |
| Claude等のレビュワーLLM | 設計上の矛盾、責務分割、例外処理、セキュリティ、保守性などの深掘りレビュー |
| アプリケーションの判定ロジック | 各検証結果を統合し、追加レビューや人間確認の要否を決定 |
| 人間 | 指摘の妥当性、設計変更の採否、最終承認を判断 |

JevはレビュワーLLMの単純な代替ではなく、基準が明確な判定を担い、詳細な推論が必要なケースをレビュワーLLMへ振り分けるために使う。

## 3. Jevで評価する観点

初期段階では、次の3観点から始める。

### 3.1 要件充足性

- 要件定義書の各要件が外部設計に反映されているか
- 外部設計の機能が内部設計で具体化されているか
- 内部設計の処理が実装計画に反映されているか
- 要件を満たすための設計上の根拠があるか

判定例：

- `SATISFIED`：根拠を確認でき、要件を満たしている
- `PARTIALLY_SATISFIED`：一部不足がある
- `NOT_SATISFIED`：要件を満たしていない
- `INSUFFICIENT_EVIDENCE`：判断材料が不足している

### 3.2 ドキュメント間の整合性

- 外部設計と内部設計に矛盾がないか
- API仕様とデータモデルが整合しているか
- 業務ルールと処理ロジックが一致しているか
- 実装計画が設計内容と一致しているか

例：外部設計ではユーザーが複数のプロジェクトに所属できるのに、内部設計のデータモデルではユーザーに単一の `project_id` しか保持できない。

### 3.3 必要事項の網羅性

- 認証・認可
- 正常系・異常系の処理
- エラー処理
- トランザクション境界
- 非機能要件
- 個人情報・機密情報の保護
- 運用・監視・バックアップなど、要件に応じた運用事項

Jevの判定だけで安全性や妥当性を確定しない。重大なリスクはレビュワーLLMや人間による確認につなげる。

## 4. 機械的バリデーションで検出する項目

LLMに判断させる必要がないものは、可能な限りプログラムで検証する。

- 要件ID・設計IDの重複
- 要件IDの欠落
- トレーサビリティ参照先の不存在
- 必須フィールドの不足
- JSON/Pydantic等のスキーマ違反
- 許可されていないステータス値
- 必須ドキュメントや必須セクションの欠落
- 定義されたルールに基づく対応関係の未設定

例：

```text
FR-001 -> API-001
FR-002 -> API-002
FR-003 -> 対応する設計なし
```

`FR-003` に対応する設計がないことは、トレーサビリティ情報を使って機械的に検出する。一方、設計が存在していても本当に要件を満たしているかは、JevやレビュワーLLMによる評価対象とする。

## 5. レビュワーLLMの責務

Claude等のレビュワーLLMは、Jevや機械的検証で問題が疑われた箇所を中心に、設計上の妥当性を詳しく調査する。

### 主なレビュー観点

- 要件解釈の妥当性
- 要件と設計のトレーサビリティ
- 要件間・設計間の矛盾
- APIとデータモデルの整合性
- モジュールの責務分割、凝集度、結合度
- エラー処理と例外系
- 認証・認可、情報保護
- トランザクションとデータ整合性
- 性能・可用性などの非機能要件
- テスト容易性、変更容易性、保守性
- 実装計画の順序・依存関係・完了条件

### レビュワーLLMにさせないこと

レビュワーは原則として、対象ドキュメントを直接編集しない。

レビュー結果は独立したデータとして出力し、問題箇所・根拠・関連要件・影響・改善案を記録する。修正は別の修正処理で行い、必要に応じて人間の承認を挟む。

## 6. レビュー結果のデータ形式例

```json
{
  "review_id": "REV-023",
  "target_document": "external-design-v3",
  "status": "NEEDS_REVISION",
  "issues": [
    {
      "issue_id": "ISSUE-001",
      "severity": "HIGH",
      "category": "requirement_coverage",
      "requirement_ids": ["FR-012"],
      "design_ids": ["API-003"],
      "description": "FR-012を満たす操作が設計上確認できない",
      "evidence": "API-003の仕様にはFR-012に必要な処理が記載されていない",
      "impact": "要件を満たす機能が実装されない可能性がある",
      "recommendation": "不足している処理と対応するAPI仕様を確認する",
      "reviewer": "claude"
    }
  ]
}
```

上記はデータ形式の例であり、実際のフィールドや列挙値はアプリケーションのスキーマとして定義する。

Jevの結果も別途保存し、モデル名・バージョン、評価基準、入力対象のバージョン、判定値、スコア、実行日時を追跡できるようにする。

## 7. 判定・振り分け方針

Jevの出力をそのまま最終的なPASS/FAILに変換しない。アプリケーション側の判定ロジックで、少なくとも次を考慮する。

- 機械的バリデーションの結果
- Jevの観点別判定とスコア
- 問題の重大度
- 判定の確信度または不確実性
- 要件の重要度
- 必ず人間が確認すべき項目かどうか

初期運用では自動的にレビューを省略せず、Jevの判定を記録するだけのシャドーモードで実績を集める。その後、テストデータに基づいてしきい値を設定する。

### 推奨する初期ルール

- 機械的検証エラー：必ず修正対象
- 重大なセキュリティ・データ整合性リスク：必ず詳細レビューまたは人間確認
- Jevが不足・矛盾を示す：レビュワーLLMへ送る
- Jevが判断材料不足を示す：追加情報の要求または人間確認
- Jevが問題なしと判定：他の必須ゲートを通過していることを確認してから承認候補にする

## 8. 品質評価とテスト

モデルの一般的なベンチマークだけで選定せず、Devex固有の設計レビュー評価セットを用意する。

### テストケース例

1. 要件漏れ
2. API仕様とデータモデルの矛盾
3. 認可条件の漏れ
4. トランザクション境界の不備
5. エラー処理の不足
6. 状態遷移の漏れ
7. 非機能要件への対応不足
8. 責務過多・依存関係の問題
9. 実装計画の依存順序の誤り
10. 問題が存在しない正常ケース

### 評価指標

- **再現率（Recall）**：既知の欠陥をどの程度検出できたか
- **適合率（Precision）**：指摘したもののうち、実際に欠陥だった割合
- **重大度判定の妥当性**
- **根拠の正確性**
- **不確実判定の割合**
- **1レビュー当たりのコストと遅延**
- **人間のレビュー結果との一致度**

見逃しのコストが大きい重大欠陥については、総合スコアよりも再現率や必須チェックの通過状況を重視する。

## 9. 実装ロードマップ

### Phase 1：検証基盤

- 要件・設計に安定したIDを付与する
- 構造化モデルとトレーサビリティ情報を整備する
- ID、参照、必須項目、スキーマの機械的検証を実装する

### Phase 2：Jevによる基準別判定

- 要件充足性・設計間整合性・網羅性を評価する
- 判定結果を構造化して保存する
- まずはシャドーモードで実行し、実際の結果を記録する

### Phase 3：レビュワーLLM連携

- Claude等に関連する要件・設計・検証結果を渡す
- 指摘、根拠、影響、改善案を構造化して受け取る
- レビュワーはドキュメントを直接編集しない

### Phase 4：評価・しきい値調整

- 正解ラベル付きの設計欠陥テストセットを作る
- Jev単独、レビュワーLLM単独、併用構成を比較する
- 見逃し率・誤検出率・コスト・遅延を評価する

### Phase 5：人間承認と修正サイクル

- 指摘の採用・却下・保留を管理する
- 採用された指摘を別の修正処理で反映する
- 修正後に再検証・再レビューする
- ドキュメントの版、レビュー結果、承認履歴を紐付ける

## 10. 設計上の重要原則

1. **Markdownを唯一の正本にしない。** 構造化された要件・設計モデルを保持し、ドキュメントはそこから生成する。
2. **機械で判定できるものはプログラムで検証する。**
3. **Jevは基準別の判定器として利用し、複雑な設計推論を全面的に任せない。**
4. **レビュワーLLMは診断に専念させ、直接編集させない。**
5. **重大な問題を総合スコアで相殺しない。**
6. **人間による承認と、レビュー・修正の履歴を残す。**
7. **自動化の範囲は、実データで精度を検証してから広げる。**

## 結論

Devexでは、次の構成を推奨する。

**機械的バリデーション → Jevによる基準別判定 → Claude等による詳細レビュー → 人間による承認 → 必要に応じた修正・再レビュー**

この構成により、要件網羅性やドキュメント間の整合性を継続的に検証しつつ、LLMによる深い設計レビューと人間による最終判断を維持できる。
