1. **[最重要 / 設計]** テーブル users, backend/core/security.py, DF-1, DF-2, FR-002
   - 問題: users.password の説明が「ログイン時にそのまま照合する」で、パスワードを平文で保存・照合する設計になっている。内部設計書の security.py にはパスワードのハッシュ化があり、両者が食い違う。
   - 理由: 公開サービス(FR-001)のメール+パスワード認証で、DB が漏れるとパスワードがそのまま露出する。3.3 の security.py の責務(ハッシュ化)とも矛盾する。
   - 改善案: password_hash カラムにして、登録時にハッシュ化し、ログイン時はハッシュで照合すると明記する。DF-1・DF-2 の変換欄にもハッシュ化を入れる。
2. **[最重要 / 設計]** POST /api/v1/chat/messages, POST /api/v1/documents/generate, POST /api/v1/projects, NFR-006
   - 問題: チャット送信 API の本文は message だけで、対象プロジェクトを特定できない。chat・documents・projects のどの API にも、プロジェクトの所有者を確認する処理や 401/403/404 の応答が無い。
   - 理由: NFR-006「他人のプロジェクト閲覧を不可」を満たせない。DF-4 は project_id を保存するが、入力に project_id が無い。generate は project_id を受け取るのに、所有者の検証が無い。
   - 改善案: chat の本文かパスに project_id を加える。認証必須とし、project.user_id とログインユーザーを照合する。応答に 401/403/404 を追加する。
3. **[最重要 / 不整合]** FR-010, NFR-006, FR-001
   - 問題: FR-010(共有リンクで未ログインでも閲覧可)と NFR-006(他人のプロジェクト閲覧を不可)が矛盾している。FR-010 の元になるヒアリング項目も無い。
   - 理由: 共有リンクの仕組み(トークン、有効期限、取り消し、対象の範囲)が決まっておらず、機密性の要件と両立するか判断できない。決定的検証の指摘は「画面・API が無い」ことだけで、この矛盾は拾っていない。
   - 改善案: 共有を MVP に入れるか利用者に聞き直す。入れる場合は、URL の推測を防ぐトークン、公開と取り消しの API、閲覧の画面を設計し、NFR-006 に例外として書く。入れない場合は FR-010 を削除する。
4. **[中程度 / 不整合]** 1.3 システム化の範囲, FR-009
   - 問題: In Scope に「Jira連携による課題の自動登録」があり、Out of Scope に「Jira・Notion連携」がある。同じ項目が両方に入っている。
   - 理由: ヒアリングの MVP の範囲では Jira 連携は対象外と決まっており、対応する FR・API・画面も無い。In Scope の記述が誤りと考えられる。
   - 改善案: In Scope から Jira 連携を削除する。
5. **[中程度 / 不整合]** POST /api/v1/auth/login, FR-002, backend/api/v1/auth.py
   - 問題: FR-002 はトークンを HttpOnly Cookie に保存すると定めている。外部設計書のログイン API はトークンを応答の本文で返し、localStorage に保存する設計になっている。内部設計書は「Cookieを設定する」としている。
   - 理由: localStorage に置くと XSS でトークンを盗まれる。HttpOnly Cookie にするという決定事項に反し、外部設計書と内部設計書も食い違う。
   - 改善案: ログイン応答は Set-Cookie(HttpOnly, Secure, SameSite)にし、本文でトークンを返さない。localStorage の記述を削除する。CSRF 対策も記載する。
6. **[中程度 / 不整合]** 3.4 例外処理・ログ設計, NFR-007
   - 問題: 3.4 に「機密情報は一切ログに残さない」とある一方、「AI応答失敗時はチャットの入力内容とプロンプト全文をログに出力する」とも書かれており、互いに矛盾している。
   - 理由: NFR-007 は入力内容を一切ログに残さず、エラーの有無と日時だけを残すと定めている。参考資料やチャット内容は機密になりうる。
   - 改善案: 入力内容とプロンプト全文のログ出力を削除する。エラーコード・日時・リクエスト ID だけを残す。
7. **[中程度 / 設計]** POST /api/v1/documents/generate, POST /api/v1/chat/messages, リスク1, NFR-003
   - 問題: 数分かかる 4 文書の生成と自己診断を、同期の 1 回の POST で処理している。タイムアウト、途中で失敗した場合の扱い、再生成での既存データの扱いが決まっていない。
   - 理由: nginx やブラウザのタイムアウトで切れる恐れがある。documents は project_id と doc_type に一意制約が無く、再生成すると重複する。4 文書のうち一部だけ保存された場合の整合も不明。チャットは最初の文字を数秒で返す要件なのにストリーミング応答が無い。
   - 改善案: 生成を非同期ジョブにして、状態を取得する API を設ける。保存は全件成功時に 1 トランザクションで行う。再生成時は置換か世代管理かを決める。チャットは SSE などのストリーミングにする。
8. **[中程度 / 設計]** SCR-003, FR-006, SCR-002, POST /api/v1/documents/generate
   - 問題: 保存済みの設計書・診断結果・チャット履歴・プロジェクトを取得する API が無い。SCR-003 の「選択した設計書」を表示する手段も無い。FR-006 は付録で API が「—」になっている。
   - 理由: 生成後に再表示や再ログインをした場合に、画面が表示すべきデータを取得できない。generate の応答に何が含まれるかも未定義。
   - 改善案: プロジェクトの取得、設計書の取得、診断結果の取得、チャット履歴の取得の API を追加する。generate の応答の本文も定義する。
9. **[中程度 / 不整合]** FR-002, CON-003, POST /api/v1/auth/login, backend/core/security.py
   - 問題: リフレッシュトークンで更新する API も、ログアウトでトークンを失効させる API も無い。Redis の失効管理は書かれているのに、使う入口が定義されていない。
   - 理由: アクセストークンは 30 分で切れる。更新手段が無いと、リフレッシュトークン(14 日)の要件を実装できない。
   - 改善案: POST /auth/refresh と POST /auth/logout を追加する。Redis に失効リストを持つ処理を内部設計に書く。
10. **[中程度 / 不整合]** NFR-008, POST /api/v1/chat/messages, POST /api/v1/documents/generate, M-01-T01, M-02-T01
   - 問題: 429 のエラー応答が定義されているのは認証 2 API だけで、チャット・生成には無い。Redis によるレート制限を実装するタスクも実装計画に無い。
   - 理由: NFR-008 は、チャットと生成の回数制限も必須としている。ミドルウェアとして共通化すると書かれているだけで、実装の担当が無い。
   - 改善案: チャット・生成 API に 429 を追加する。レート制限の実装タスクと、対象・単位・上限値を決めて実装計画に加える。
11. **[中程度 / 設計]** DF-3, DF-4, DF-5, テーブル projects, FR-003
   - 問題: 参考資料の使われ方が流れから抜けている。DF-5 は chat_messages だけを取得し、projects の reference_file_paths を読まない。DF-4 のチャットにも参考資料が入らない。pdf のテキスト抽出も無い。
   - 理由: アップロードした参考資料が生成結果に反映されず、FR-003 が意味を持たない。ファイルの保存場所もパスだけで、NFR-002 のバックアップは DB しか対象にしていない。
   - 改善案: DF-3 にテキスト抽出と保存先を明記する。DF-4・DF-5 で projects から参考資料の内容を読んでプロンプトに入れる。ファイルまたは抽出テキストも保全の対象にする。
12. **[中程度 / 設計]** 実装計画書 4.2 WBS, SCR-001, SCR-002, SCR-003, NFR-002, CON-005, NFR-009
   - 問題: 実装計画にフロントエンドの画面タスクが無い。nginx・HTTPS・GitHub Actions の自動デプロイ、DB の日次バックアップと VPS 外へのコピー、Redis レート制限、トークン失効のタスクも無い。M-01-T01 の要件欄は「なし」になっている。
   - 理由: フェーズ1 は画面とデプロイまで含むと書かれているのに、画面 3 つ(SCR-001〜003)がどのタスクにも割り当てられていない。非機能要件にも担当が無い。
   - 改善案: 各画面のタスク、CI/CD・nginx のタスク、バックアップのタスク、レート制限のタスクを追加する。要件・画面との対応を付ける。
13. **[中程度 / ヒアリング]** FR-008, NFR-008, NFR-003, 観点 セキュリティ(不正利用)
   - 問題: 具体的な数値が決まっていない。「数千文字まで」の上限、ログイン試行・登録・チャット・生成のレート制限の回数や期間、1 ユーザーあたりのプロジェクト数や生成回数がいずれも未決のまま。
   - 理由: 数値が無いと、API の検証やレート制限を実装できない。生成のコストを LLM の従量課金で受ける公開サービスなので、上限は重要になる。
   - 改善案: 利用者に聞き直す。入力の文字数上限、各操作の回数と期間、ユーザーあたりの生成上限を決めて、要件に数値で書く。
14. **[軽微 / ヒアリング]** FR-001, 観点 規模, 観点 セキュリティ
   - 問題: 公開サービスなのに、メール確認、パスワード再設定、外部 LLM に送る機密情報の取り扱い(利用者への告知)、データの保持期間の方針をヒアリングしていない。
   - 理由: 規模の観点は「AI の提案を採用」のままで、誰でも登録できる前提の運用事項が要件に出てこない。削除・退会は不要と決まっているが、保持期間は決まっていない。
   - 改善案: メール確認の要否、パスワード再設定の要否、LLM への送信に関する告知、データの保持方針を利用者に確認する。
15. **[軽微 / 不整合]** backend/api/v1/auth.py, backend/core/security.py, POST /api/v1/auth/register, POST /api/v1/auth/login, FR-008
   - 問題: auth.py の依存先が ai_service.py になっていて、不自然。security.py の層が「モデル」になっている。register と login の要件欄に、チャット入力の制限である FR-008 が載っている。
   - 理由: レイヤーの依存と要件の対応が実際の責務とずれている。
   - 改善案: auth.py の依存先を security.py とリポジトリ層に直す。security.py の層名を直す。register と login の要件欄から FR-008 を外し、NFR-008 に差し替える。
