1. **[最重要 / 設計]** SCR-004, FR-004, POST /api/v1/projects/{id}/summary/approve
   - 問題: 構造化サマリを取得・生成する API がなく、画面に表示する手段がない。「修正依頼ボタン」に対応する API もない。ヒアリング完了ボタン(SCR-003)に対応する API もない。
   - 理由: 2.6 の API 一覧には、サマリの生成・取得、修正依頼、ヒアリング完了の API が無い。承認 API だけでは、FR-004 の「確認して承認する」を実現できない。
   - 改善案: ヒアリング完了(サマリ生成)、サマリ取得、サマリ修正依頼の API を追加する。サマリのデータ保存先も定義する。
2. **[最重要 / 設計]** POST /api/v1/projects/{id}/summary/approve, FR-005, FR-006, NFR-003, FR-009
   - 問題: 4文書の順次生成と自己診断を同期的な 1 回の API で行う設計になっている。生成には数分かかる。進捗を取得する API、完了を知る API、文書単位の失敗や再生成の API もない。
   - 理由: 応答は「200 OK(生成開始)」で、エラーは「500 生成失敗」だけである。SCR-005 には再生成ボタンがあるが、対応する API がない。FR-009 の「生成失敗時は再生成」を満たせない。
   - 改善案: 非同期ジョブ化し、ジョブ状態取得 API と文書単位の再生成 API(POST .../documents/{type}/regenerate)を追加する。途中失敗時は、生成済みの文書を残す扱いを定める。
3. **[最重要 / 設計]** GET /api/v1/projects/{id}/documents, FR-006, FR-007, FR-008, SCR-005
   - 問題: 自己診断結果を返す API が定義されていない。版を指定して取得する方法もない。
   - 理由: FR-006 の自己診断は承認 API に紐づくだけで、結果の取得先が無い。SCR-005 の版切り替えボタンに対応する版指定のパスやパラメータも無い。FR-008 の直近3件保持を行う削除処理も、どこにも書かれていない。
   - 改善案: documents API の応答に診断結果を含めるか、診断取得 API を追加する。版指定のパス(.../documents/{type}/versions/{n})を設ける。4 版目の保存時に最古の版を削除する処理を定める。
4. **[中程度 / 不整合]** NFR-008, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/summary/approve, POST /api/v1/auth/login, POST /api/v1/auth/register
   - 問題: レート制限の具体値(回数・期間・単位)がなく、超過時のエラー応答(429)がどの API にも定義されていない。
   - 理由: NFR-008 はログイン総当たり、登録の大量作成、チャットや生成の回数上限を要求している。しかし 2.6 のエラー列に 429 が無く、制限値も設計に出てこない。
   - 改善案: 対象ごとの上限値(IP 単位、ユーザー単位など)を決める。各 API に 429 と Retry-After を追加する。無料枠 LLM の上限超過時の応答(503 など)も定義する。
5. **[中程度 / 設計]** POST /api/v1/projects, GET /api/v1/projects, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/documents/upload, GET /api/v1/projects/{id}/documents
   - 問題: 認可の定義がない。{id} のプロジェクトが認証ユーザー本人のものか確認する旨が書かれていない。ほとんどの API に 401/403/404 の定義もない。
   - 理由: 公開サービスで複数ユーザーが使うため、他人のプロジェクトの閲覧や操作(IDOR)を防ぐ必要がある。2.6 のエラー列には 401 が一部にあるだけで、403/404 は GET documents に 404 があるのみ。
   - 改善案: 全 API で、所有者チェックと 401/403/404 を明記する。projects と documents に所有ユーザーの紐づけを持たせる。
6. **[中程度 / 設計]** POST /api/v1/projects/{id}/chat, SCR-003, NFR-003
   - 問題: チャット応答が通常の 200 OK(AI応答)になっている。NFR-003 は「最初の文字を数秒で出力」としており、ストリーミング(SSE など)の定義が必要。チャット履歴を取得する API もない。
   - 理由: SCR-003 はチャット履歴を表示するが、取得手段がなく、画面再訪や再読込で復元できない。ストリーミングの仕様も外部設計に無い。
   - 改善案: SSE などのストリーミング応答を定義する。チャット履歴取得 API を追加する。応答失敗時にメッセージを履歴へ保存しない扱いも明記する。
7. **[中程度 / 設計]** POST /api/v1/projects/{id}/documents/upload, FR-003, SCR-003
   - 問題: アップロードの上限サイズ、PDF のテキスト化失敗(暗号化・画像のみ)の扱い、テキスト化結果の保持方法と LLM のコンテキスト量への収め方が未定義。アップロード済み資料の一覧取得や、再アップロード時の扱いも無い。
   - 理由: FR-003 は「テキスト化して保持する」と定めているが、エラー列は 400 不正形式のみ。サイズ超過(413)や抽出失敗(422)がなく、無料枠 LLM のトークン上限にも影響する。
   - 改善案: サイズ上限、抽出失敗時のエラー、テキストの文字数制限や要約方針を決める。資料一覧 API を追加する。
8. **[中程度 / 設計]** NFR-007, NFR-002, NFR-005
   - 問題: データモデル(内部設計)が与えられておらず、保存するテーブルと項目が不明。パスワードのハッシュ化方式、トークンの種別と有効期限、ログアウト API(Redis の失効)も定義されていない。
   - 理由: CON-003 は「トークン失効用 Redis」としているが、ログアウトや失効の API が無い。NFR-007 の「操作の記録」の項目も未定義。チャット内容はログに残さないが DB には保存するという区別も書かれていない。
   - 改善案: ログアウト API とトークンの有効期限・リフレッシュ方針を追加する。主要テーブルと操作ログの項目を定義する。
9. **[中程度 / ヒアリング]** 規模, セキュリティ, FR-001
   - 問題: 公開サービスなのに、メール確認、パスワードリセット、パスワード要件、登録の可否(招待制か誰でも可か)が聞かれていない。
   - 理由: セキュリティ観点は AI 提案の採用だけで、「ログインを入れる」という内容に留まる。パスワードを忘れた場合の復旧手段は要件にも設計にも無い。
   - 改善案: パスワードリセットとメール確認の要否、パスワード規則を利用者に確認し、要件に追加する。
10. **[中程度 / ヒアリング]** 体制・期間, CON-004, NFR-003
   - 問題: 体制・期間が未決のまま。また、LLM 無料枠の上限(1日あたりの回数・トークン)に対して、想定する同時利用者数と生成量が見合うか確認されていない。
   - 理由: 1回のプロジェクトで、チャットと 4 文書生成と自己診断を行うと、多数の LLM 呼び出しが発生する。無料枠だと十数人の利用で枯渇しうるが、その時の利用者への見せ方も未決。
   - 改善案: 期間・体制を確認する。無料枠上限に達したときの運用(待機表示、翌日再試行など)と、NFR-008 の回数上限の値との関係を決める。
11. **[軽微 / 不整合]** FR-002, SCR-002, FR-005, 付録 要件との対応
   - 問題: SCR-002 のプロジェクト一覧・作成画面が FR-005(文書生成)に紐づいている。FR-002 には「プロジェクト管理」の要件が無い。プロジェクトの作成と一覧が、チャット機能に混在している。
   - 理由: 2.2 の SCR-002 の要件欄と付録の対応表で、プロジェクト作成と文書生成が結びつけられているが、実際には生成を行わない。
   - 改善案: プロジェクト管理を独立した要件にするか、対応関係を整理する。
12. **[軽微 / 不整合]** NFR-003, 性能・拡張性
   - 問題: ヒアリングでは「数秒〜数分」とあるのに、要件では「数分以内」になっている。数値の基準(何分以内か)も曖昧。
   - 理由: 要件定義書の NFR-003 とヒアリングの表で表現が異なる。タイムアウト値の根拠にならない。
   - 改善案: 生成時間の上限値(例: 5分)を明記し、API のタイムアウトやジョブ監視に反映する。
