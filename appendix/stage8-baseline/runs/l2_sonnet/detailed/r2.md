1. **[最重要 / 設計]** SCR-004, FR-004, POST /api/v1/projects/{id}/summary/approve
   - 問題: 構造化サマリを生成・取得する API がなく、SCR-004 の「表示項目: サマリ内容」を取得できない。「ヒアリング完了」操作の API も無い。修正依頼ボタンに対応する API もない。
   - 理由: API一覧には approve しかなく、サマリの作成・取得・修正依頼・ヒアリング完了の API が見当たらない。FR-004 の「確認して承認する」を満たせない。
   - 改善案: ヒアリング完了(サマリ生成)、サマリ取得、修正依頼の API を追加する。サマリを保存するデータの扱いも定義する。
2. **[最重要 / 設計]** POST /api/v1/projects/{id}/summary/approve, FR-005, FR-006, NFR-003, SCR-005
   - 問題: 4文書の逐次生成と自己診断は数分かかるが、approve が 200 で「生成開始」を返すだけ。進捗取得・完了通知・状態確認の API がなく、同期か非同期かも不明。自己診断結果を返す API もない。
   - 理由: NFR-003 は4文書の生成に数分かかるとしている。SCR-005 は自己診断結果を表示するが、GET /documents の応答にそれが含まれるか不明で、生成中や途中失敗の状態を取れない。
   - 改善案: ジョブを非同期で実行し、状態取得 API(または SSE)を設ける。文書ごとの状態(生成中・完了・失敗)と診断結果を返す。
3. **[中程度 / 設計]** SCR-005, FR-009, FR-008, POST /api/v1/projects/{id}/summary/approve
   - 問題: SCR-005 に再生成ボタンと版切り替えボタンがあるが、対応する API がない。再生成は approve の再呼び出しでよいのか、文書単位で行うのかが不明。版の指定取得もできない。
   - 理由: FR-009 は生成失敗時の再生成を求め、FR-008 は直近3件の版管理を求める。API一覧には GET /documents しかなく、文書・版の指定や再生成の経路がない。
   - 改善案: 文書単位の再生成 API(POST /projects/{id}/documents/{type}/regenerate)を追加する。版指定の取得も追加する。再生成と版の増加・3件を超えた版の破棄の規則を定める。
4. **[中程度 / 設計]** POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/documents/upload, POST /api/v1/projects/{id}/summary/approve, GET /api/v1/projects/{id}/documents, GET /api/v1/projects
   - 問題: 認可の仕様がない。{id} のプロジェクトが本人のものかを確認する規定がなく、他人のプロジェクトへのアクセスを防げない。401/403/404 の応答も、多くの API で定義されていない。
   - 理由: 公開サービス(誰でも登録可能)で、プロジェクトはユーザーごとのデータである。chat・upload・approve には 401 がなく、403 はどの API にもない。
   - 改善案: プロジェクトの所有者検査を全 {id} 系 API の共通規則とする。401・403(または404)をエラー欄に追記する。
5. **[中程度 / 不整合]** NFR-008, POST /api/v1/auth/login, POST /api/v1/auth/register, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/summary/approve
   - 問題: 回数上限(レート制限)を要件に挙げているが、API のエラー応答に 429 がなく、具体的な上限値や単位(IP・ユーザー別)も決まっていない。
   - 理由: NFR-008 はユーザーが決定した要件だが、外部設計のどの API にも超過時の応答がない。Gemini 無料枠の上限超過(CON-004)の扱いも画面・API に現れない。
   - 改善案: 各 API に 429(と Retry-After)を追加する。上限の数値と単位をヒアリングして決める。LLM の上限超過時のエラー応答も定義する。
6. **[中程度 / 設計]** POST /api/v1/auth/login, FR-001, CON-003, SCR-001
   - 問題: ログアウトとトークン失効の API がない。トークンの種類(JWT か、有効期限、リフレッシュの有無)や保管場所も未定義である。
   - 理由: CON-003 は「トークン失効用 Redis」を使うとしているが、失効を起こす操作(ログアウト)が API 一覧にない。画面にも無い。
   - 改善案: POST /auth/logout を追加し、トークンの方式と期限、保管方法(Cookie か否か)を定める。
7. **[中程度 / 設計]** POST /api/v1/projects/{id}/chat, SCR-003, NFR-003
   - 問題: チャット応答の形式が「200 OK (AI応答)」のままである。NFR-003 は最初の文字を数秒で出すとしているが、ストリーミング(SSE など)の方式が書かれていない。チャット履歴の取得 API もない。
   - 理由: SCR-003 は再訪時にチャット履歴を表示するが、取得 API がない。FR-009 は失敗時に「メッセージを送らずに再送を促す」とあり、失敗したメッセージを履歴に残さない規則が必要。
   - 改善案: ストリーミング応答の方式を明記する。履歴取得 API を追加する。失敗時は履歴に保存しないと明記する。
8. **[中程度 / 設計]** POST /api/v1/projects/{id}/documents/upload, FR-003, SCR-003
   - 問題: 参考資料のサイズ上限、PDF のテキスト化(スキャン PDF や抽出失敗)の扱い、テキスト化結果が LLM への入力にどう使われるかが定義されていない。アップロード済み資料の一覧取得の API もない。
   - 理由: FR-003 は「テキスト化して保持」を求める。upload のエラーは 400 だけで、サイズ超過(413)や変換失敗がない。長い資料は LLM のコンテキスト制限にも影響する。
   - 改善案: ファイルサイズとページ数の上限、変換失敗時のエラーを定める。保持したテキストをヒアリング・生成にどう渡すか(要約・分割など)を決める。
9. **[中程度 / 設計]** FR-008, NFR-007, FR-003, FR-002
   - 問題: データモデル(内部設計)がなく、チャット履歴・参考資料テキスト・サマリ・版の保存方針が見えない。NFR-007 は入力内容をログに残さないとするが、DB にチャット内容を保存してよいのかは明確でない。
   - 理由: チャット履歴は SCR-003 の表示や文書生成に必要で、DB 保存が前提になる。「ログ」と「業務データ」の区別が書かれていない。
   - 改善案: 保存するデータ(チャット・資料・サマリ・文書の版)と、ログに残さないデータを区別して明記する。
10. **[軽微 / 設計]** SCR-002, FR-002, FR-005
   - 問題: SCR-002 の要件に FR-005 が対応づいているが、プロジェクト一覧画面は文書生成を行わない。プロジェクトの進行状況(どの段階か)も一覧に表示されず、再訪時にどの画面へ遷移するか不明。
   - 理由: 画面遷移は一方向のフロー(SCR-002→003→004→005)だけで、生成済みプロジェクトを開いたときの遷移先が定義されていない。
   - 改善案: プロジェクトの状態(ヒアリング中・サマリ確認・生成済み)を持たせ、状態に応じた遷移先を定義する。
11. **[軽微 / ヒアリング]** 体制・期間, FR-011, NFR-008
   - 問題: 体制・期間が未決のまま。回数上限の具体値、メールアドレス確認やパスワード再設定の要否など、公開サービスで必要な認証まわりの事実が聞けていない。
   - 理由: セキュリティ観点は「ログインをMVPに入れる」の採用だけで内容が浅い。規模が公開サービスなので、パスワード方針やメール確認の要否が要件に出ていない。
   - 改善案: パスワードの強度、メール確認、パスワード再設定の要否、上限値を利用者に聞き直す。
