1. **[最重要 / 不整合]** FR-008, SCR-005, GET /api/v1/projects/{id}/documents
   - 問題: 版管理の直近3件保持の実装根拠が不明確
   - 理由: FR-008は『文書ごとに版を増やして直近3件を保持』と明記しているが、外部設計書の SCR-005 では『版の履歴（直近3件）』、API では単に『生成文書および版一覧取得』と記載されており、どの単位で3件を保持するのか(プロジェクト単位か、文書種別ごとか)が不明確である。特に、4種文書(要件定義・外部設計・内部設計・実装計画)が順次生成される場合、各文書ごとに3件か、それともプロジェクト全体で3件か、の区別がない。
   - 改善案: 版管理の単位を明記する。たとえば『各文書種別ごとに直近3件を保持』など、具体的にどの範囲で3件制限が適用されるかを設計書に記載する。
2. **[最重要 / 設計]** FR-005, FR-004, SCR-004, POST /api/v1/projects/{id}/summary/approve
   - 問題: 4種文書の生成フロー と承認フロー が未定義
   - 理由: FR-005 では『要件定義』『外部設計』『内部設計』『実装計画』の4種文書を『順次生成』と明記されているが、SCR-004 の『承認して文書生成へ進む』と SCR-005 の『生成された4種文書』の間に、4種文書がいつ生成されるのか、誰がいつ承認するのか、生成中の画面遷移や待機時間の扱いが設計されていない。特に、『4文書の生成は数秒〜数分待てる』(性能要件)という記述から、複数の文書が逐次ではなく並行生成される可能性も考えられ、その場合の進捗表示や完了通知の仕組みが明記されていない。
   - 改善案: SCR-004 の承認後、どのタイミングで4種文書が生成開始されるか、生成中の画面(プログレス表示など)をどう扱うか、各文書の生成完了後の遷移を明記する。並行生成か順次生成かも明確にする。
3. **[最重要 / 不整合]** FR-009, SCR-003, POST /api/v1/projects/{id}/chat
   - 問題: AI応答失敗時の処理フローが API 応答に反映されていない
   - 理由: FR-009 では『AIの応答失敗時は理由を表示してメッセージを送らずに再送を促す』と明記されており、SCR-003 の『メッセージ送信時はAI応答またはエラー・再送案内を表示』と対応している。しかし、POST /api/v1/projects/{id}/chat の応答仕様では『500 AI応答失敗』と記載されているだけで、『理由を表示』するためのエラー応答ボディ(エラーメッセージの形式、エラーコード等)が定義されていない。
   - 改善案: POST /api/v1/projects/{id}/chat の 500 エラー応答に、具体的なエラー理由を返すボディ仕様を追加する。例えば『reason: "API quota exceeded"』など。
4. **[最重要 / 設計]** NFR-008, SCR-001, POST /api/v1/auth/login, POST /api/v1/auth/register, POST /api/v1/projects/{id}/chat
   - 問題: レート制限の実装方法と API 応答が未定義
   - 理由: NFR-008 では『ログインの総当たり、登録の大量作成、チャットや生成の回数上限を設けて不正利用を防ぐ』と明記されており、技術スタックでは Redis を『レート制限・トークン失効用』と記載している。しかし、外部設計書の API 一覧には、レート制限に達した場合の応答(429 Too Many Requests など)が定義されていない。また、各エンドポイント(ログイン、登録、チャット送信、文書生成)でレート制限の条件(1時間あたり何回など)が明記されていない。
   - 改善案: 各 API エンドポイントに対して、レート制限に達した際の応答コード(429)と応答ボディ(残り待機時間など)を明記する。また、各エンドポイントのレート制限の閾値(例: ログイン 5回/15分、チャット送信 100回/日)を設計書に記載する。
5. **[最重要 / 不整合]** FR-006, SCR-005, GET /api/v1/projects/{id}/documents
   - 問題: 自己診断結果の取得・表示方法が未定義
   - 理由: FR-006 では『生成後にAIが各文書の不足点を自己診断して提示する』と明記されており、SCR-005 では『AIによる不足点の自己診断結果の確認』と記載されている。しかし、GET /api/v1/projects/{id}/documents の応答仕様には『生成文書および版一覧』としか記載されておらず、自己診断結果(どの要件が不足しているか、どの API が実装されていないかなど)をどのような形式で取得するのかが明記されていない。また、自己診断が各文書生成時に自動実行されるのか、ユーザーが手動で実行するのかも不明確である。
   - 改善案: GET /api/v1/projects/{id}/documents の応答に、自己診断結果を含めるか、別途 API エンドポイント(例: GET /api/v1/projects/{id}/documents/{doc_id}/diagnosis)を設計して、自己診断結果の形式(JSON スキーマ)を明記する。また、自己診断の実行タイミング(自動・手動)も記載する。
6. **[中程度 / 設計]** FR-003, SCR-003, POST /api/v1/projects/{id}/documents/upload
   - 問題: 参考資料の保持と利用方法が不明確
   - 理由: FR-003 では『参考資料(txt、md、PDF)を読み込みテキスト化して保持する』と明記されており、SCR-003 では『参考資料ファイル選択（txt, md, PDF）』と記載されている。しかし、テキスト化した参考資料がどこに保存されるのか(PostgreSQL か外部ストレージか)、チャットや文書生成時にどのように参照されるのか、版の更新時に参考資料がどう扱われるのかが未定義である。また、POST /api/v1/projects/{id}/documents/upload は『参考資料アップロード』とあるが、テキスト化結果をどのような形式で返すのか、アップロード後にそれをどう確認するのかが記載されていない。
   - 改善案: 参考資料の保持場所、テキスト化の方法(OCR・テキスト抽出)、チャットおよび文書生成プロセスでの参考資料の参照方法、版更新時の参考資料の扱いをそれぞれ明記する。POST /api/v1/projects/{id}/documents/upload の応答に、アップロード・テキスト化結果の確認方法を追加する。
7. **[中程度 / 設計]** FR-004, SCR-004, POST /api/v1/projects/{id}/summary/approve
   - 問題: 構造化サマリの生成と内容の定義が不明確
   - 理由: FR-004 では『ヒアリング完了後に構造化サマリを確認して承認する機能』と明記されており、SCR-004 では『構造化されたサマリ内容』と記載されている。しかし、『構造化されたサマリ』がどのような形式・内容(要件の箇条書き、カテゴリ分けなど)で、どのタイミングで生成されるのか、チャットヒアリングから構造化サマリへの変換方法が未定義である。また、SCR-003(チャットヒアリング完了)から SCR-004(サマリ確認)への遷移時に自動生成されると推定できるが、その API が外部設計書に明記されていない(POST /api/v1/projects/{id}/summary など)。
   - 改善案: 構造化サマリの形式・内容を定義する(例: 『ユーザー情報』『機能要件』『非機能要件』『制約条件』のセクション分け)。サマリ生成 API を設計書に追加し、チャットヒアリングからサマリへの変換タイミングを明記する。
8. **[中程度 / 設計]** NFR-003, SCR-003, SCR-005, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/summary/approve

   - 改善案: POST /api/v1/projects/{id}/chat と POST /api/v1/projects/{id}/summary/approve(文書生成)について、ストリーミング対応の有無を明記する。ストリーミング対応の場合、応答形式(Server-Sent Events・WebSocket など)、イベントスキーマ、エラー時の処理を記載する。

   - 改善案: POST /api/v1/projects/{id}/chat の本文に、チャット履歴の ID やセッション ID を含めるべきか、バックエンド側で自動的に文脈を管理するかを明記する。参考資料の LLM への入力方法(プロンプトに埋め込む・ベクトル化など)も設計書に記載する。
