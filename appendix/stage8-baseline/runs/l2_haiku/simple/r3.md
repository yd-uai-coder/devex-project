1. **[最重要 / 設計]** backend/core/security.py, users テーブル
   - 問題: パスワードがプレーンテキストのままデータベースに保存される設計になっている
   - 理由: users テーブルのパスワードカラムについて「ログイン時にそのまま照合する」と記述されており、backend/core/security.py では「パスワードのハッシュ化」が責務に記載されていますが、実装詳細がない。セキュリティ観点で不可欠な要件です。
   - 改善案: パスワード登録時には passlib を使用してハッシュ化し、ログイン時はハッシュの比較を行う設計に明確化してください。
2. **[最重要 / 設計]** POST /api/v1/auth/login, backend/api/v1/auth.py
   - 問題: アクセストークン・リフレッシュトークンがレスポンスボディで返されて localStorage に保存される設計になっている
   - 理由: 外部設計書 2.6 の API一覧では「アクセストークン・リフレッシュトークンを応答の本文で返し、フロントエンドは localStorage に保存する」と記述されていますが、FR-002 では「HttpOnly Cookie に保存する」と規定されています。XSS 攻撃に対する耐性が異なります。
   - 改善案: HttpOnly Cookie にトークンを設定する設計に統一し、ボディでの返却は削除してください。
3. **[最重要 / 不整合]** NFR-007, 3.4 例外処理・エラーハンドリング・ログ設計
   - 問題: AI応答失敗時にチャット入力内容とプロンプト全文をログに出力する方針が、セキュリティ要件 NFR-007 に違反している
   - 理由: NFR-007 では「機密情報や入力内容は一切ログに残さず、エラーの有無や日時だけを残す」と要件が規定されていますが、内部設計書 3.4 では「ただし障害調査のため、AI応答失敗時はチャットの入力内容とプロンプト全文をログに出力する方針とする」と記述され、矛盾しています。
   - 改善案: NFR-007 に従うか、NFR-007 の例外を利用者に確認するかを決定してください。
4. **[中程度 / 設計]** POST /api/v1/projects, SCR-002
   - 問題: 参考資料のアップロードと後続のヒアリングの関係が明確でない
   - 理由: 外部設計書 2.3 では SCR-002 に「参考資料ファイルアップロード(txt, md, pdf、最大3件)、チャットメッセージ入力欄」があり、API一覧では POST /api/v1/projects でファイル、POST /api/v1/chat/messages でメッセージと別の API として分かれています。ファイルアップロード後の project_id がチャットに渡されることは記載されていません。
   - 改善案: SCR-002 のフロー（ファイルアップロード後に project_id を取得し、その後メッセージを送信）を画面遷移図またはシーケンス図で明示してください。
5. **[中程度 / 設計]** POST /api/v1/documents/generate, DF-5
   - 問題: 生成された設計書が複数あるのに、プレビュー・出力画面との関係が不明確である
   - 理由: 4種設計書（要件定義・外部設計・内部設計・実装計画）が一括生成されますが、SCR-003 では「選択した設計書」とあり、どのように選択できるのか、API では単一の設計書ごとの取得 API がありません。DF-5 では documents テーブルに複数レコード挿入されることは示されていますが、フロントエンドでの取得方法が API 一覧に無い。
   - 改善案: 設計書取得用の GET /api/v1/documents/{document_id} や GET /api/v1/projects/{project_id}/documents など、生成済みの設計書を取得する API を外部設計書に追加してください。
6. **[中程度 / 設計]** POST /api/v1/documents/generate, 自己診断
   - 問題: 自己診断結果（diagnostics テーブルのデータ）がクライアントに返却されるかどうかが記載されていない
   - 理由: FR-005 では「AIが各文書の不足点を3段階で自己診断して提示する」と要件があり、SCR-002 では「AIによる各文書の不足点自己診断結果(3段階: 最重要/中程度/軽微)」を表示することになっています。しかし、POST /api/v1/documents/generate のレスポンス仕様（本文・エラー）に自己診断結果を含むかどうかが記載されていません。
   - 改善案: POST /api/v1/documents/generate のレスポンスに自己診断結果（document_id ごとの severity と comment）を含むことを外部設計書で明示してください。
7. **[中程度 / 設計]** NFR-008, POST /api/v1/auth/register, POST /api/v1/chat/messages
   - 問題: レート制限の具体的な条件（1時間あたりの回数上限など）が記載されていない
   - 理由: NFR-008 では「ログインの総当たり、登録の大量作成、チャットと生成の回数制限により不正利用を防ぐ」と要件がありますが、具体的に登録は1IPあたり何回まで、チャットは1ユーザーあたり何回/時間まで、などの上限値が設定されていません。
   - 改善案: NFR-008 を見直し、ユーザーに各 API のレート制限条件（上限値、時間枠、単位）を確認して要件定義書に記載してください。
8. **[中程度 / 設計]** テーブル: projects
   - 問題: プロジェクト情報の中身が参考資料のパスだけで、プロジェクト名などの識別情報がない
   - 理由: projects テーブルは id, user_id, reference_file_paths, created_at のみで、プロジェクトの名前やタイトル、説明などの属性が無い。ユーザーが複数のプロジェクトを管理する場合に識別できません。
   - 改善案: projects テーブルに、プロジェクト名や簡単な説明などを保持するカラムを追加してください。
9. **[中程度 / 設計]** SCR-002, 複数プロジェクト管理
   - 問題: ユーザーが複数のプロジェクトを管理・選択するための画面や操作方法が記載されていない
   - 理由: SCR-002 は「メイン機能画面」として初期入力・ヒアリング・生成が中心ですが、ユーザーが過去に作成したプロジェクト一覧から選択するような画面遷移がありません。初回のみのシステムなのか、複数プロジェクト管理に対応するのか不明確。
   - 改善案: 複数プロジェクト対応か単一プロジェクトオンリーかをユーザーに確認し、複数対応の場合はプロジェクト一覧画面と遷移フローを追加してください。
10. **[中程度 / 設計]** FR-010, SCR-002, SCR-003
   - 問題: 共有リンクで公開された設計書にアクセスするためのエンドポイント・画面が設計されていない
   - 理由: FR-010 では「生成した設計書を共有リンクで公開し、ログインしていない人も閲覧できるようにする」とありますが、既知の検証指摘で指摘済みの通り、画面も API も記載されていません。
   - 改善案: 認証なしで設計書を取得する GET /api/v1/public/documents/{share_token} のような API と、共有リンク生成・取得の仕組みを外部設計書に追加してください。
11. **[中程度 / 設計]** 3.4 例外処理・エラーハンドリング・ログ設計
   - 問題: AI応答失敗時と生成失敗時で、メッセージの扱いが異なるが、その判定基準が不明確である
   - 理由: FR-007 では「AIの応答失敗時はメッセージを保存せず、生成失敗時は再生成できるようにする」とありますが、何を応答失敗、何を生成失敗と判定するのか、またそれに対応する HTTP ステータスコードが設計されていません。
   - 改善案: 応答失敗（例：AI が回答を返さなかった場合）と生成失敗（例：4種設計書生成の途中で失敗した場合）を明確に定義し、それぞれの例外ハンドリングと HTTP レスポンスを内部設計書に記載してください。
12. **[中程度 / 設計]** M-03-T01, M-03-T02
   - 問題: チャットヒアリング完了から設計書生成までの判定が明記されていない
   - 理由: 実装計画書では M-03-T01 でチャットメッセージの実装、M-03-T02 で生成機能の実装が分かれていますが、「いつ、誰が、どのように生成ボタンを押すのか」が不明です。ユーザーが手動で生成ボタンを押すのか、チャットが一定の条件で自動トリガーするのか。
   - 改善案: ユーザーが手動で『生成』ボタンを押す設計なのか、自動判定で生成するのかを要件定義書に明記し、SCR-002 の操作フローを明確化してください。
13. **[軽微 / 設計]** バックエンド処理・モジュール設計
   - 問題: ミドルウェアやルーターの実装仕様が記載されていない
   - 理由: 3.3 では FastAPI のレイヤー構成が示されていますが、レート制限とトークン検証を行う「ミドルウェア」の詳細（どのエンドポイントに適用するか、Redisとの連携方法）が記載されていません。
   - 改善案: レート制限・トークン検証のミドルウェア実装仕様（どのエンドポイントに適用、制限条件など）を内部設計書に追加してください。
14. **[軽微 / 設計]** backend/api/v1/auth.py, ユーザー登録
   - 問題: メールアドレスのバリデーション（フォーマット検証）の仕様が記載されていない
   - 理由: FR-001 と POST /api/v1/auth/register では入力値バリデーション（ファイル形式、件数チェック）の例が示されていますが、メールアドレスのフォーマット検証（RFC 5322 準拠など）は明記されていません。
   - 改善案: メールアドレスのバリデーション基準（RFC 準拠、正規表現など）を内部設計書に記載してください。
15. **[軽微 / 設計]** NFR-003, チャットの最初の文字が数秒
   - 問題: ユーザー入力から AI 応答開始までの時間目標が「最初の文字が数秒」と曖昧である
   - 理由: NFR-003 では性能要件として「チャットの最初の文字が数秒」とありますが、「1文字目の表示が何秒以内」なのか、「ストリーミング表示か」が不明です。ただし、実装の参考値としては曖昧さがあります。
   - 改善案: 「最初の文字が 3 秒以内」など具体的な時間数を利用者に確認するか、ストリーミング表示の有無を決めてください。
