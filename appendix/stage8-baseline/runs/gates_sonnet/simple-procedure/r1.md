## 区切り1: 要件定義書 + 外部設計書 + 内部設計書 + 実装計画書

1. **[最重要 / 設計]** POST /api/v1/chat/messages, DF-4, テーブル chat_messages
   - 問題: チャット送信 API の本文が message だけで、どのプロジェクトへの発言か特定できない。DF-4 では project_id を保存するが、入力のどこからも来ない。
   - 理由: 外部設計書 2.6 の本文は message のみ。内部設計書 DF-4 では chat_graph が project_id を保存する。履歴の取得もプロジェクトを特定できなければ行えない。
   - 改善案: 本文かパスに project_id を入れる(例: POST /api/v1/projects/{id}/messages)。ヒアリング用に履歴を取得するときも project_id を使う。
2. **[最重要 / 不整合]** NFR-006, POST /api/v1/chat/messages, POST /api/v1/documents/generate, POST /api/v1/projects
   - 問題: 他人のプロジェクトを見られない要件(NFR-006)に対応する認可の設計が無い。チャットと生成の API には 401 も 403/404 も無く、project_id の所有者確認も DF に無い。
   - 理由: NFR-006 は Must 相当のセキュリティ要件。generate が project_id を受け取るだけでは、他人の ID を指定して参照や生成ができてしまう。
   - 改善案: 全 API で認証を必須にし、project_id が user_id に属するか確認する処理を DF-4・DF-5 に加える。401/403/404 の応答を API 一覧に追記する。
3. **[最重要 / 設計]** SCR-003, FR-006, SCR-002, FR-002
   - 問題: 画面の操作に対応する取得系 API が無い。プロジェクト一覧・詳細、チャット履歴、生成済み設計書と自己診断の取得、トークン更新(refresh)の API がどれも定義されていない。
   - 理由: SCR-003 のプレビューと SCR-002 の履歴・診断の表示には読み出しが要る。付録で FR-006 の API は「—」。FR-002 のリフレッシュトークン 14 日にも更新 API が無く、30 分のヒアリング中にアクセストークンが切れる。
   - 改善案: GET /projects、GET /projects/{id}、GET /projects/{id}/messages、GET /projects/{id}/documents(診断を含める)、POST /auth/refresh を追加し、FR-006 と対応づける。
4. **[最重要 / 設計]** POST /api/v1/documents/generate, DF-5, NFR-003, 4.4 リスク1
   - 問題: 数分かかる 4 文書の生成と自己診断を、1 回の同期リクエストで 201 を返す設計にしている。進捗や状態の取得、途中失敗時の扱い、再生成時の既存文書の扱いが決まっていない。
   - 理由: NFR-003 では生成に数分かかる。実装計画 4.4 は「非同期処理」としているが、API は同期のまま。nginx やブラウザのタイムアウトを超えるおそれがある。4 件のうち一部だけ保存された場合や、再生成で documents が重複する場合の扱いも無い。
   - 改善案: 生成をジョブ化し(202 とジョブ状態の取得 API)、4 文書と診断を 1 トランザクションで保存する。再生成は上書きか世代管理かを決める。
5. **[中程度 / 不整合]** FR-008, NFR-008, POST /api/v1/chat/messages, POST /api/v1/documents/generate, POST /api/v1/projects
   - 問題: 回数制限(NFR-008)のうち、チャット・生成・プロジェクト作成の 429 がエラー応答に無い。付録では FR-008(チャット入力の長さ)が登録・ログインにも対応づけられている。
   - 理由: 429 があるのは register と login だけ。チャット・生成の回数制限は 3.4 に書かれているが API にも DF にも出てこない。FR-008 の対応づけも趣旨とずれている。
   - 改善案: チャット・生成・アップロードの API に 429 を追加する。付録の FR-008 の対応を chat のみに直し、NFR-008 の対応を別に設ける。
6. **[中程度 / ヒアリング]** NFR-008, FR-008
   - 問題: 回数制限の具体値(ログイン失敗回数、登録数、チャット・生成の回数と単位、ロック時間)と、チャットの「数千文字」の上限が決まっていない。
   - 理由: ヒアリングは「回数制限」「数千文字」までで、数値が無い。公開サービスで Gemini の利用コストにも直結するため、数値が無いと実装も試験もできない。
   - 改善案: 回数制限は 1 ユーザー・1 IP あたり何回/時間かを、文字数は上限を、それぞれ利用者に聞き直して要件に数値で入れる。
7. **[中程度 / 設計]** DF-3, DF-4, DF-5, FR-003, テーブル projects
   - 問題: 参考資料の本文を取り出す処理(pdf のテキスト抽出など)が無い。ファイルパスを保存するだけで、チャットのヒアリングにはまったく渡されない。生成時にもチャット履歴しか取得していない。
   - 理由: DF-3 はファイルを保存してパスを紐付けるだけ。DF-4 は message と履歴だけを使う。DF-5 の取得元は chat_messages のみ。FR-003 の参考資料が設計書に反映されない。
   - 改善案: DF-3 でテキスト抽出と上限サイズの検証を行って保存する。DF-4・DF-5 のプロンプト構築に参考資料の本文を加える。
8. **[中程度 / 不整合]** NFR-002, テーブル projects, reference_file_paths
   - 問題: 参考資料をファイルとして VPS 上に保存するが、バックアップは DB のみが対象で、ファイルの保存先も決まっていない。
   - 理由: NFR-002 は DB の日次バックアップと VPS 外へのコピーを求めている。reference_file_paths は DB 外のファイルを指すため、復元するとパスだけが残って実体が消える。ファイルの保存先ボリュームも Docker Compose の構成に出てこない。
   - 改善案: 本文を DB に保存するか、ファイル用ボリュームもバックアップ対象にする。サイズ上限と保存先も決める。
9. **[中程度 / ヒアリング]** SCR-002, FR-004, chat_graph.py
   - 問題: ヒアリングをいつ終えて生成に進むか(AI が判断するのか、利用者がボタンで指示するのか)が決まっていない。生成ボタンの有無も不明。
   - 理由: SCR-002 には「完了時に設計書を一括生成」とあるが、操作ボタンは送信・再送・再生成のみ。DF-4 に完了判定が無い。ヒアリングで聞くべき項目や質問数も定まっていない。
   - 改善案: 生成開始の操作(「生成する」ボタンなど)と、ヒアリングで聞く項目、ヒアリング終了の条件を決めて要件と SCR-002・DF-4 に反映する。
10. **[中程度 / 設計]** SCR-002, SCR-003, テーブル projects, POST /api/v1/projects
   - 問題: プロジェクトの一覧・再表示の画面がなく、projects にも名称や状態のカラムが無い。過去のプロジェクトを開き直せるかが不明。
   - 理由: 利用場面は「その日のうちに見直して共有」で、画面遷移が SCR-001→002→003 だけでは保存した設計書へ戻る導線が無い。複数プロジェクトの区別もできない。
   - 改善案: プロジェクト一覧画面(または SCR-002 の一覧領域)を加え、projects に title と status を追加する。
11. **[中程度 / 設計]** 実装計画書 4.2, M-01-T01, NFR-002, NFR-007, NFR-008, CON-005
   - 問題: 実装計画に、画面(SCR-001〜003 のフロントエンド)、nginx・HTTPS・GitHub Actions のデプロイ、DB スキーマ作成、バックアップ、レート制限・ログ・認可の各タスクが無い。
   - 理由: タスクはバックエンドのモジュール中心で、フロントエンドのタスクはゼロ。M-01-T01 は要件・処理とも「なし」。4.1 の MVP に VPS へのデプロイが含まれるのに、対応するタスクが無い。FR-006 は M-03-T02 に付いているが、プレビューやコピーの画面実装は含まれない。
   - 改善案: フロントエンド実装(画面ごと)、DB マイグレーション、Redis のレート制限・トークン失効、ログ方針、nginx・デプロイ・バックアップのタスクを追加し、要件に紐付ける。
12. **[軽微 / 設計]** backend/api/v1/auth.py, backend/core/security.py, backend/core/database.py, モジュール一覧
   - 問題: モジュールの依存や層の分類が不自然。auth.py が ai_service.py に依存し、security.py と database.py の層が「モデル」になっている。リポジトリ層がモジュール一覧に無い。トークン失効を行うモジュールも不明。
   - 理由: 3.3 の本文ではルーティング・サービス・リポジトリ・モデルの 4 層とミドルウェアで Redis を使うとしているが、モジュール一覧に反映されていない。
   - 改善案: auth のサービス層とリポジトリ層、レート制限・トークン検証のミドルウェアを一覧に追加し、依存先と層を直す。
13. **[軽微 / ヒアリング]** FR-001, SCR-001
   - 問題: 公開サービスの登録について、パスワードの強度、メール確認、パスワード再設定の方針が決まっていない。
   - 理由: 規模は「AI の提案を採用」で公開サービスになったが、要件には登録とログインしか無い。機密性の高い入力を扱う。
   - 改善案: パスワードの規則、メール確認の要否、再設定の要否を利用者に確認し、MVP に含めるか対象外にするかを要件に書く。

## 区切り2: 要件定義書 + 外部設計書 + 内部設計書 + 実装計画書 + 実装手順書

1. **[最重要 / 設計]** POST /api/v1/chat/messages, POST /api/v1/documents/generate, chat_messages, DF-4, NFR-006
   - 問題: チャット送信APIの本文が message だけで、どのプロジェクトの会話かを特定する project_id がない。DF-4 で chat_messages に保存するには project_id が必要だが、受け取る経路がない。
   - 理由: 外部設計書 2.6 の本文は message のみ。DF-4 では project_id を保存するのに入力元が定義されていない。このままだと会話をプロジェクトに結び付けられず、他人のプロジェクトへの書き込みも防げない。
   - 改善案: リクエスト本文かパスに project_id を加える(例: /projects/{id}/messages)。あわせて、プロジェクトの所有者を確認する処理を明記する。
2. **[最重要 / 不整合]** NFR-006, POST /api/v1/documents/generate, POST /api/v1/chat/messages, POST /api/v1/projects, DF-5
   - 問題: 他人のプロジェクトを閲覧できないという要件に対し、認可の設計がない。generate は project_id を受け取るが、所有者の検証、403/404 の応答、認証エラー(401)の定義がない。chat と generate には 401 もない。
   - 理由: NFR-006 は Must 相当のセキュリティ要件だが、API 一覧で NFR-006 に対応するのは projects だけ。DF-5 に user_id による絞り込みがない。他人の project_id を指定すれば、他人のチャットから設計書を生成できてしまう。
   - 改善案: 認証が必要な全 API に 401 を加える。project_id を受け取る API では、projects.user_id と認証ユーザーを照合して、不一致なら 403 または 404 を返す。DF-4 と DF-5 にもこの照合を入れる。
3. **[最重要 / 設計]** FR-006, SCR-003, POST /api/v1/documents/generate, documents
   - 問題: 保存済みの設計書や自己診断結果を取得する API(GET)がない。SCR-003 のプレビュー・コピー・ダウンロードに必要なデータを取れない。画面を再び開く場合や、生成後に再取得する場合にも対応できない。
   - 理由: 外部設計書 2.6 の API はすべて POST。付録で FR-006 の API は「—」になっている。実装計画でも FR-006 は M-03-T02(バックエンドのみ)に載っているだけで、フロントエンドのタスクがない。
   - 改善案: プロジェクトごとの設計書一覧と、診断を含む設計書の取得 API(GET /api/v1/projects/{id}/documents など)を追加する。チャット履歴の取得 API も同様に追加する。
4. **[最重要 / 設計]** POST /api/v1/projects, SCR-002, FR-003, projects, DF-3
   - 問題: 参考資料の内容が、後の処理で使われる形になっていない。DF-3 ではファイルを保存してパスを持つだけで、pdf のテキスト抽出がない。DF-4 のチャットのプロンプトにも参考資料が入らない。DF-5 の取得元は chat_messages だけで、参考資料は読み込まれない。
   - 理由: FR-003 は「初期入力で読み込む」ことを求めている。DF-5 の変換は「チャット履歴・参考資料取得」と書かれているが、データの流れは chat_messages からしか出ていない。また、ファイルのサイズ上限や、プロジェクトを作成する際に文字数や初期入力を持つかどうかも未定義。
   - 改善案: アップロード時に txt/md/pdf からテキストを抽出して保存する。DF-4 と DF-5 のプロンプトに参考資料を入れる流れを定義する。ファイルのサイズ上限、保存先、プロジェクト作成後に初期の説明文を持つかどうかも決める。
5. **[中程度 / 設計]** POST /api/v1/documents/generate, DF-5, NFR-003, FR-007
   - 問題: 4文書の生成は数分かかるが、同期の POST で 201 を返す設計になっている。nginx やブラウザのタイムアウト、進捗表示、途中失敗の扱いが未定義。
   - 理由: NFR-003 は生成に数分かかることを許容している。DF-5 は生成から診断、保存まで1リクエストで行い、一部の文書だけ保存された場合や再生成時に既存の documents をどうするかが書かれていない。リスク1の対策も「非同期処理」としか書かれていない。
   - 改善案: 生成をジョブ化し、状態取得用の API を用意するか、タイムアウト値を明記する。保存は全体を1トランザクションにするか状態列を持たせる。再生成時は既存の文書を置き換えるのか追加するのかを決める。
6. **[中程度 / 設計]** POST /api/v1/auth/login, FR-002, CON-003, SCR-001
   - 問題: リフレッシュトークンでアクセストークンを更新する API と、ログアウトの API がない。Redis によるトークン失効の対象や、Cookie の属性(Secure、SameSite)、CSRF 対策も未定義。
   - 理由: FR-002 はアクセス30分・リフレッシュ14日を求め、CON-003 は Redis でトークン失効を行うとしている。ところが 2.6 には refresh と logout がない。30分で切れた後に再ログインが必要になる。Cookie 認証の POST には CSRF 対策も要る。
   - 改善案: POST /auth/refresh と /auth/logout を追加する。トークンの失効を Redis でどう行うかと、Cookie の属性、CSRF 対策を決める。
7. **[中程度 / 設計]** NFR-008, POST /api/v1/chat/messages, POST /api/v1/documents/generate, POST /api/v1/projects
   - 問題: 回数制限の具体的な値(回数、期間、単位)と、API 側の 429 の定義が足りない。chat、generate、projects には 429 の応答がない。
   - 理由: NFR-008 はチャットと生成の回数制限を求めているが、2.6 で 429 があるのは register と login だけ。制限値もどの文書にもない。実装計画のタスクにもレート制限の実装がない。
   - 改善案: 各 API の制限値(IP 単位かユーザー単位か)を決める。chat と generate に 429 を追加し、制限用ミドルウェアのタスクを実装計画に加える。
8. **[中程度 / 不整合]** 実装計画書 4.2, NFR-002, NFR-009, CON-005, FR-006, SCR-001, SCR-002, SCR-003, NFR-008
   - 問題: 実装計画書に、フロントエンド(SCR-001〜003)、nginx と GitHub Actions のデプロイ、DB のマイグレーション、バックアップ(NFR-002)、レート制限、ログ制御(NFR-007)に当たるタスクがない。M-01-T01 の要件も「なし」になっている。
   - 理由: 4.1 は「プレビュー・ダウンロード」と「VPS へのデプロイ」を MVP に含めると書いているが、4.2 のタスクはバックエンドの API だけ。Must の要件を実装する単位がなく、Next.js や Tamagui の構築も含まれていない。
   - 改善案: フロントエンド基盤、各画面、テーブル作成とマイグレーション、nginx と CI/CD、バックアップ、レート制限とログ設計のタスクを追加する。要件との紐付けも行う。
9. **[中程度 / 不整合]** backend/api/v1/auth.py, モジュール一覧, backend/core/database.py, backend/core/security.py
   - 問題: auth.py の依存先が ai_service.py になっていて、認証処理と無関係。一方、security.py と database.py は「モデル」層、projects.py と documents.py も依存先が不足している。レート制限やトークン検証のミドルウェアを置くファイルも構成にない。
   - 理由: 3.3 のモジュール一覧では auth.py が ai_service.py に依存するが、DF-1・DF-2 に AI は出てこない。実装ルールは「依存先にだけ依存する」なので、誤った依存がそのまま実装を縛る。documents.py は DF-5 で chat_messages を読むが、リポジトリ層の記載がない。
   - 改善案: auth.py の依存先を security.py と database.py に直す。レート制限・認証ミドルウェアと、リポジトリ層のモジュールをモジュール一覧に追加する。
10. **[中程度 / 設計]** POST /api/v1/chat/messages, DF-4, FR-007, chat_messages
   - 問題: ユーザーのメッセージを保存するタイミングが曖昧。FR-007 は失敗時にメッセージを保存しないとしているが、DF-4 は AI 応答後に保存する流れで、ユーザー発言と AI 応答を一緒に保存するのかが書かれていない。会話の終了判定と、生成へ進む条件もない。
   - 理由: DF-4 で保存するのは project_id, sender, content と一括の記載のみ。ヒアリング完了をどう判断するか、いつ generate を呼ぶのかが SCR-002 にも書かれておらず、チャット履歴の再表示もできない。
   - 改善案: ユーザー発言と AI 応答を成功時に同一トランザクションで保存すると明記する。ヒアリングを終えて生成に進む操作(ボタンなど)と、チャットの入力上限の具体値(文字数)を決める。
11. **[軽微 / ヒアリング]** NFR-002, NFR-007, 運用・保守性(データの保持・削除), セキュリティ(ログ)
   - 問題: アップロードした参考資料ファイルとプロジェクト内容を VPS 上に保存するが、バックアップ対象(DB のみ)との整合や保持期間が決まっていない。ログの「一切残さない」と、不正利用の調査や回数制限用の IP 記録との関係も未確認。
   - 理由: NFR-002 は DB のバックアップだけを対象にしており、reference_file_paths が指すファイルは対象外。NFR-007 は AI の提案を採用した観点で、利用者に確かめた内容ではない。機密性の高い入力を扱うサービスなので、これらは確認が必要。
   - 改善案: バックアップにアップロードファイルを含めるか、保存ファイルの保持期間をどうするか、ログに IP やユーザー ID を残してよいかを利用者に確認する。
