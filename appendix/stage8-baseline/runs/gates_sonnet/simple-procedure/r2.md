## 区切り1: 要件定義書 + 外部設計書 + 内部設計書 + 実装計画書

1. **[最重要 / 設計]** POST /api/v1/chat/messages, DF-4, テーブル chat_messages
   - 問題: チャット送信APIの本文が message だけで、どのプロジェクトへの発言かを特定できない。DF-4 でも project_id の入手元が無い。
   - 理由: chat_messages は project_id が NOT NULL で、履歴を踏まえた応答には対象プロジェクトが必要。2.6 の本文欄に project_id がない。
   - 改善案: project_id をパスまたは本文に含める(例: POST /api/v1/projects/{project_id}/chat/messages)。DF-4 にも project_id の取得元を書く。
2. **[最重要 / 不整合]** NFR-006, POST /api/v1/chat/messages, POST /api/v1/documents/generate, DF-5
   - 問題: 他人のプロジェクトを閲覧できないという要件に対し、project_id を受け取る chat と generate に認証・所有者チェックの設計と 401/403/404 の応答が無い。
   - 理由: NFR-006 の関連付けは POST /projects だけ。generate は project_id を本文で受けるため、他人の ID を指定して履歴や生成物を読める恐れがある。内部設計にも user_id と projects の照合処理が無い。
   - 改善案: 全プロジェクト関連APIで JWT のユーザーと projects.user_id を照合し、不一致は 403/404 を返すと明記する。エラー欄に 401/403/404 を追加する。
3. **[最重要 / 設計]** SCR-003, FR-006, SCR-002, POST /api/v1/documents/generate, 観点 API の完全さ
   - 問題: 生成済み設計書、自己診断結果、チャット履歴、プロジェクト一覧を取得するAPIが無い。SCR-003 のプレビューやログイン後の再表示は、generate の応答に頼るしかない。
   - 理由: 2.2 と 2.3 では SCR-003 で設計書を選んで表示し、SCR-002 でチャット履歴を表示する。付録でも FR-006 の API は「—」。利用者は「その日のうちに見直す」ため、再読み込み後の取得手段が要る。
   - 改善案: GET /projects、GET /projects/{id}/messages、GET /projects/{id}/documents(診断を含む)などの取得APIを追加し、FR-006 と対応付ける。
4. **[最重要 / 設計]** POST /api/v1/documents/generate, NFR-003, リスク1, DF-5
   - 問題: 数分かかる4文書の生成と自己診断を、1回の同期POST(201)で返す設計になっている。進捗・状態・タイムアウトの扱いが無い。
   - 理由: NFR-003 は生成に数分を許容する。nginx やブラウザのタイムアウトで途中切断されうる。リスク1 は「非同期処理」を挙げるが、API は同期型で食い違う。途中失敗時の部分保存の扱いも未定義。
   - 改善案: 生成をバックグラウンドジョブにして 202 + 状態取得APIにするか、同期でも nginx のタイムアウトを明記する。4文書と診断は1トランザクションで保存し、失敗時は全体をロールバックする。
5. **[中程度 / 設計]** テーブル documents, テーブル diagnostics, FR-007, POST /api/v1/documents/generate
   - 問題: 再生成を行うと、同一プロジェクトに同じ doc_type の documents が重複して溜まる。どれが最新かを決める仕組みが無い。
   - 理由: documents に (project_id, doc_type) の一意制約も版・最新フラグも無い。FR-007 は再生成を認めており、版の履歴は将来拡張(FR-009)で対象外。
   - 改善案: 再生成時に既存の documents と diagnostics を置換する(一意制約 + upsert)と決める。または generation 番号か is_latest を持たせる。
6. **[中程度 / 不整合]** NFR-008, POST /api/v1/chat/messages, POST /api/v1/documents/generate, POST /api/v1/projects, FR-008
   - 問題: チャットと生成の回数制限は要件にあるが、chat と generate のエラー応答に 429 が無い。回数や期間の具体値もどこにも無い。付録では register/login を FR-008(入力長)に結び付けており、NFR-008 との対応が混ざっている。
   - 理由: 2.6 で 429 があるのは register/login のみ。3.4 は制限を実装すると言うだけで、閾値(例: 生成は1日何回)が無く、Redis のキー設計もできない。
   - 改善案: chat・generate(必要なら projects)に 429 を追加する。制限値は利用者に確認して NFR-008 に記載する。register/login の対応先は NFR-008 にする。
7. **[中程度 / 設計]** FR-002, CON-003, POST /api/v1/auth/login, 観点 セキュリティ
   - 問題: リフレッシュトークンによる更新、ログアウト、トークン失効のAPIが無い。Cookie 認証の CSRF 対策も書かれていない。
   - 理由: FR-002 はアクセス30分・リフレッシュ14日で、CON-003 は Redis でトークン失効を行うとする。しかし 2.6 に refresh/logout が無く、失効の契機が無い。30分で認証が切れた後の継続方法が不明。
   - 改善案: POST /auth/refresh と /auth/logout を追加し、失効をRedisで管理する流れを DF に書く。Cookie の SameSite 設定や CSRF 方針も明記する。
8. **[中程度 / 設計]** DF-3, DF-4, DF-5, テーブル projects, FR-003
   - 問題: 参考資料が、ヒアリングと生成で使われる流れになっていない。DF-3 は保存パスだけで、pdf のテキスト抽出が無い。DF-4 の LLM 呼び出しは参考資料を使わない。DF-5 は取得元が chat_messages だけで、projects.reference_file_paths を読んでいない。
   - 理由: FR-003 は参考資料を読み込んで初期入力に使うことを求める。受け取ったデータが後段で使われていない。ファイルサイズ上限も未定義。
   - 改善案: DF-3 にテキスト抽出と、サイズ・ページ数の上限を追加する。DF-4/DF-5 で projects の資料内容をプロンプトに含める流れにする。
9. **[中程度 / 設計]** FR-004, SCR-002, POST /api/v1/projects, POST /api/v1/documents/generate
   - 問題: ヒアリングの終了と生成の開始が決まっていない。SCR-002 は「完了時に生成」と書くが、API は generate を別に持つ。ヒアリング前や履歴が少ない状態で generate を呼べるかの条件も無い。projects には、ファイル無しでの作成可否や名前も無い。
   - 理由: 2.3 のアクション記述と 2.6 の API が一致しない。chat_graph の終了判定も内部設計に無い。
   - 改善案: 利用者が生成ボタンで明示的に開始する方式か、AI の完了判定を返す方式かを決める。generate の前提条件(最低限のチャット件数など)と、条件を満たさない場合の 400/409 を定義する。
10. **[中程度 / 設計]** 実装計画書 4.2, SCR-001, SCR-002, SCR-003, CON-001
   - 問題: 実装計画にフロントエンドの画面実装タスクが一つも無い。nginx/HTTPS 設定、GitHub Actions による自動デプロイ、Redis のレート制限・トークン失効、ログ方針、DBバックアップのタスクも無い。

   - 改善案: 画面ごとのフロントエンドタスク(SCR-001〜003)を追加する。nginx/CD、レート制限ミドルウェア、日次バックアップ+外部コピー、ログ制御を基盤タスクとして追加し、各 NFR に紐付ける。
11. **[中程度 / 設計]** NFR-002, テーブル projects, reference_file_paths
   - 問題: バックアップ対象が DB だけで、参考資料ファイルの保存先と保全が決まっていない。
   - 理由: projects は参考資料をファイルパスで持つが、ファイルの実体の置き場所(Docker ボリューム等)が書かれていない。DBを復元してもファイルが失われ、実体の無いパスが残る恐れがある。
   - 改善案: ファイルの保存先を決める。内容を DB に保存する案も含めて検討する。ファイルをバックアップ対象に含めるか、MVP でそれを許容するかを明記する。
12. **[中程度 / ヒアリング]** 観点 セキュリティ, FR-001, NFR-006, 観点 規模

   - 改善案: Gemini へのデータ送信方針(学習への利用の有無、有料APIか)を聞く。メール確認、パスワード強度、再設定を MVP に含めるかを聞いて、要件に記載する。
13. **[軽微 / ヒアリング]** FR-008, NFR-003, NFR-008

## 区切り2: 要件定義書 + 外部設計書 + 内部設計書 + 実装計画書 + 実装手順書

1. **[最重要 / 設計]** POST /api/v1/chat/messages, DF-4, テーブル chat_messages, SCR-002
   - 問題: チャット送信APIの本文が message だけで、どのプロジェクトの会話か特定できない。DF-4 では chat_messages に project_id を保存するが、入力のどこにも project_id がない。
   - 理由: 外部設計書 2.6 の本文は message のみ。DF-4 の保存項目(project_id, sender, content)と食い違う。履歴の取得や文脈の組み立ても、プロジェクトを特定できないと実装できない。
   - 改善案: リクエストに project_id を追加するか、パスを /projects/{project_id}/chat/messages にする。会話履歴の取得元も同じキーで決める。
2. **[最重要 / 設計]** NFR-006, POST /api/v1/chat/messages, POST /api/v1/documents/generate, POST /api/v1/projects, DF-4, DF-5
   - 問題: 他人のプロジェクトを見られないようにする要件(NFR-006)に対し、chat と generate で project_id の所有者確認が設計されていない。chat と generate のエラー応答には 401/403/404 もない。
   - 理由: generate は project_id を受け取るが、DF-5 には user_id と project の所有者を照合する処理がない。チャット送信は認証必須かどうかも不明で、projects だけが 401 を持つ。他人の project_id を指定すると、他人のチャット履歴から設計書が生成され、それが返る恐れがある。
   - 改善案: プロジェクトに紐づく全 API で、アクセストークンの検証と projects.user_id の照合を必須にする。応答は 401、403 または 404 を定義し、DF-4 と DF-5 に所有者確認のステップを入れる。
3. **[最重要 / 不整合]** FR-006, SCR-003, SCR-002, POST /api/v1/documents/generate, 付録 要件との対応
   - 問題: 保存済みの設計書・自己診断・チャット履歴・プロジェクト一覧を取得する API が無い。FR-006 の API 欄は「—」。SCR-003 は「選択した設計書」を表示する設計だが、取得手段が無い。
   - 理由: SCR-003 のプレビューやコピーは、documents と diagnostics を読めないと動かない。generate の応答に本文を全部載せる前提でも、画面を再訪・再読込したときに表示できない。SCR-002 のチャット履歴表示も同様。
   - 改善案: GET /projects、GET /projects/{id}/messages、GET /projects/{id}/documents(診断を含む)などの参照 API を追加し、FR-006 と SCR-003 に対応づける。
4. **[中程度 / 設計]** FR-002, NFR-006, CON-003, POST /api/v1/auth/login, DF-2
   - 問題: アクセストークン 30分・リフレッシュトークン 14日と、Redis でのトークン失効を前提にしているが、リフレッシュ用 API とログアウト(失効)API が無い。Cookie 認証の CSRF 対策や SameSite の方針も無い。
   - 理由: アクセストークンは 30分で切れるが、更新する API が無い。失効を扱う処理も DF や API に無い。Cookie 認証は、CSRF 対策なしでは POST 系 API が攻撃を受けうる。
   - 改善案: POST /auth/refresh と POST /auth/logout を追加し、Redis での失効処理を DF に書く。Cookie の SameSite と CSRF 対策の方針を決める。
5. **[中程度 / 設計]** DF-5, DF-4, FR-003, テーブル projects, POST /api/v1/projects
   - 問題: 参考資料が生成に使われない。DF-5 の取得元は chat_messages だけで、projects.reference_file_paths を読む処理が無い。DF-4 のプロンプトにも参考資料は入らない。pdf からのテキスト抽出と、ファイルのサイズ上限・保存場所も未定。
   - 理由: FR-003 は参考資料を読み込んで使うことが目的だが、保存したパスが設計書生成に渡らない。保存先のボリュームが NFR-002 のバックアップ対象かどうかも不明。
   - 改善案: DF-4 と DF-5 に、参考資料の読み出し・テキスト化・プロンプトへの組み込みを加える。サイズ上限、保存先、バックアップ対象を決める。
6. **[中程度 / 設計]** POST /api/v1/documents/generate, DF-5, NFR-003, FR-007, テーブル documents, テーブル diagnostics
   - 問題: 数分かかる4文書の生成と自己診断を、1回の同期 POST(201)で処理する設計になっている。タイムアウト、途中失敗、再生成時の重複の扱いが無い。

   - 問題: FR-008(チャット入力の長さと空送信の禁止)が register と login に紐づいている。一方、メールの形式やパスワード長などの入力検証ルールはどこにも定義されていない。
   - 理由: FR-008 はチャット入力の要件で、認証 API には当てはまらない。パスワードの規則が決まっていないので、400 の判定条件を実装できない。
   - 改善案: 紐づけを直し、認証の入力検証(パスワードの最小長、メール形式)を別の要件として定義する。
13. **[中程度 / ヒアリング]** 規模, セキュリティ, FR-001, NFR-006, CON-004
   - 問題: 公開サービスで誰でも登録できるのに、メール確認の有無、利用者数やコストの上限、機密情報を外部の Gemini に送ることへの扱い(利用者への告知、参考資料の機密区分)が聞けていない。規模は AI の提案を採用したままで、運用面は深掘りされていない。
   - 理由: 機密性を重視する一方で入力内容を外部 LLM に送る。公開サービスなので、Gemini の API 費用が不正登録で膨らむ恐れもある。要件に反映されておらず、利用者に聞き直さないと決められない。
   - 改善案: メール確認の要否、登録数やトークン量の上限、外部 LLM へ送信する旨の告知とデータの扱いを利用者に確認し、要件に追加する。
