## 区切り1: 要件定義書

1. **[中程度 / ヒアリング]** NFR-008
   - 問題: ログイン失敗回数、登録数、チャット・生成の回数上限が「設ける」とだけあり、具体値(回数・期間・単位がIPかアカウントか)が決まっていない。
   - 理由: ヒアリングの「セキュリティ(不正利用)」は方針のみ。Gemini無料枠(CON-004)の枠を守る水準にも関わる。値がないと Redis の制限設定や超過時の応答を実装できない。
   - 改善案: 各上限の値と単位、超過時の待ち時間やメッセージを利用者に聞いて要件に書く。
2. **[中程度 / ヒアリング]** CON-004, NFR-003, FR-005, NFR-008
   - 問題: Gemini Flash-Liteの無料枠(毎分・毎日のリクエスト数やトークン数)と、同時十数人×4文書生成+チャット+自己診断の呼び出し量が見合うか検討されていない。
   - 理由: CON-004は「上限超過時はエラー処理を挟む」とだけある。公開サービス(規模=public)で枠が尽きると、主機能が全員止まる。数分以内という NFR-003 も満たせなくなる。
   - 改善案: 無料枠の上限と想定の利用量を見積もり、全体の枠を使い切ったときの扱い(待たせる、日次上限を絞る、有料枠にするなど)を利用者と決める。
3. **[中程度 / ヒアリング]** FR-001, 観点 セキュリティ
   - 問題: セキュリティの観点は「ログインをMVPに入れる」だけ採用され、公開サービスのユーザー登録の詳細(メール確認の有無、パスワード規則、パスワード再設定、セッションやトークンの有効期間)が決まっていない。
   - 理由: 規模は公開で誰でも登録できる。メール確認や再設定がないと、大量登録対策(NFR-008)やアカウント回復の挙動が決まらない。FR-001は認証方式も示していない。
   - 改善案: 登録時のメール確認、パスワード再設定、トークン有効期限、ログアウト時の失効の扱いを聞いて要件に加える。
4. **[中程度 / ヒアリング]** FR-003
   - 問題: 参考資料のファイルサイズ・件数・文字数の上限や、スキャンPDF・暗号化PDFなどテキスト化できない場合の扱いが決まっていない。また、テキストを保持する期間やLLMへ渡す量の扱いも決まっていない。
   - 理由: FR-003は「読み込みテキスト化して保持」とだけある。大きな資料はLLMの入力上限と性能(NFR-003)に影響する。失敗時の例外(FR-009)にも資料の読み込み失敗が含まれていない。
   - 改善案: 上限値とテキスト化失敗時の表示、資料内容をどの処理にどう渡すかを決めて要件に加える。
5. **[中程度 / ヒアリング]** 観点 セキュリティ, NFR-005, NFR-007, CON-004
   - 問題: クライアントとの打ち合わせ内容や資料(機密情報を含み得る)を外部LLM(Gemini無料枠)へ送ることへの同意や注意書き、保存データの保持期間が検討されていない。削除機能もないため、利用者は一度入れたデータを消せない。
   - 理由: NFR-007はログだけを扱う。DBに残るチャットや資料の取り扱いと、無料枠では入力が提供元の改善に使われ得る点が要件にない。利用者はSE・コンサルで、守秘義務が絡む。
   - 改善案: 機密情報を外部LLMへ送る旨の利用者への表示、利用規約への記載、DB上のチャットや資料の保持方針を利用者に確認する。
6. **[中程度 / ヒアリング]** FR-002, FR-004, 利用者の1日の流れ
   - 問題: ヒアリングを中断・再開できるか、チャット履歴や構造化サマリをどこまで保存するか、プロジェクトの単位や一覧がどうなるかが決まっていない。
   - 理由: ヒアリングは約30分、その日のうちに見直す流れ(利用者の1日の流れ)。ブラウザを閉じた場合の挙動がないとデータモデルと画面を決められない。プロジェクトの一覧や選択の要件もない。
   - 改善案: プロジェクトの作成・一覧・再開の要件と、チャットとサマリの保存範囲を聞いて追加する。
7. **[中程度 / 設計]** FR-004, FR-005
   - 問題: サマリ確認で内容を修正する・やり直す手段(編集か、チャットで追加ヒアリングか)と、承認後に内容を変えたい場合の扱いが書かれていない。
   - 理由: FR-004は「確認して承認」だけ。サマリが誤っていると4文書すべてが誤るのに、差し戻し手順がない。
   - 改善案: サマリの直接編集、チャットへの差し戻し、承認後の再生成のうち採る方法を要件に書く。
8. **[中程度 / 設計]** FR-005, FR-009, FR-006
   - 問題: 4文書を順次生成する途中で失敗したとき、どこから再生成するか(失敗した文書だけか、後続を作り直すか)と、成功済みの文書の扱いが決まっていない。自己診断の結果をどう反映するかも不明。
   - 理由: FR-009は「再生成できる」とだけある。4文書は数分かかる処理(NFR-003)で、前の文書に後の文書が依存する。版の保持(FR-008)とも関わり、失敗時に版が増えるかも不明。
   - 改善案: 文書単位の状態(生成中・成功・失敗)と再生成の単位、失敗した版を版数に数えるかを決める。自己診断の指摘は提示のみか、再生成に使うかを明記する。
9. **[中程度 / 不整合]** FR-008, FR-011
   - 問題: FR-008は直近3版を保持するが、版の履歴画面はFR-011(Should、将来)に回っている。MVPで利用者が過去の版を見る・取り出す手段がない。
   - 理由: 画面がなければ保持した古い版は使われず、保持の目的が不明になる。最新版だけ見えるのか、版番号の選択だけ置くのかが決まっていない。
   - 改善案: MVPで古い版を取り出せる最小限の手段(版の選択など)を要件に入れるか、保持の目的を明記する。
10. **[軽微 / ヒアリング]** FR-010
   - 問題: チャットの上限が「数千文字」で、具体的な文字数が決まっていない。
   - 理由: 入力検査と画面表示、LLMの入力量の見積もりに具体値が必要。
   - 改善案: 上限の文字数(例:4000字)を決め、超過時の表示を明記する。
11. **[軽微 / 設計]** CON-003, NFR-002, NFR-001
   - 問題: Redisをトークン失効とレート制限に使うが、永続化の有無と、Redis停止・再起動時の挙動(失効済みトークンが復活しないか)が決まっていない。また、生成が数分かかる処理の最中に、mainへのpushによる自動デプロイ(CON-005)で処理が打ち切られる場合の扱いがない。
   - 理由: NFR-002のバックアップはDBだけが対象。デプロイでコンテナが再作成されると、実行中の生成が失敗する。
   - 改善案: Redisの永続化とRedis障害時の方針(拒否か許可か)、生成中のデプロイの扱いを決めて書く。
12. **[軽微 / 設計]** NFR-007, NFR-004
   - 問題: 「操作の記録」として何を、どこに、どれだけの期間残すかが決まっていない。
   - 理由: NFR-007は入力内容を残さないとだけある。エラー追跡はMVP後(NFR-004)なので、不正利用の調査(NFR-008)に使えるかも不明。
   - 改善案: 記録する項目(利用者ID、操作種別、時刻、結果など)と保存先、保持期間を定める。

## 区切り2: 要件定義書 + 外部設計書

2. **[最重要 / 設計]** POST /api/v1/projects/{id}/summary/approve, FR-005, FR-006, NFR-003
   - 問題: 4文書の順次生成と自己診断は数分かかるが、承認 API は同期的な 200 OK(生成開始)としか書かれていない。進捗確認・完了通知・個別文書の失敗と再生成の仕組みが無い。
   - 理由: NFR-003 は4文書生成に数分かかるとしている。FR-009 は生成失敗時に再生成できることを求めるが、再生成 API が無く、承認 API の 500 エラーだけでは途中失敗を扱えない。
   - 改善案: 生成をバックグラウンドジョブにしてジョブ状態取得 API(進捗・文書ごとの成否)を設け、文書単位または全体の再生成 API を追加する。

   - 問題: SCR-005 の再生成・版切り替え・コピー・ダウンロード・自己診断結果の取得に対応する API が無い。一覧 API の応答内容(診断結果を含むか、文書・版の指定方法)も不明である。
   - 理由: 文書や版を特定するパス(例: /documents/{docId}/versions/{n})が無い。FR-006 の自己診断結果を返す API が無く、版管理(直近3件保持)の挙動も定義されていない。
   - 改善案: 文書の種別と版を指定して取得する API、再生成 API、診断結果の取得方法を定義し、3件超過時の古い版の削除ルールも書く。
4. **[中程度 / 不整合]** FR-011, SCR-005, FR-008

   - 理由: FR-011 では版の履歴画面を将来の拡張としているのに、外部設計書の Must 画面には含まれていて、MVP の範囲が食い違っている。
   - 改善案: MVP で版の閲覧・切り替えを提供するかを決め、要件か SCR-005 のどちらかをそろえる。
5. **[中程度 / 設計]** NFR-008, POST /api/v1/auth/login, POST /api/v1/auth/register, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/summary/approve

   - 理由: NFR-008 は Must 級のセキュリティ要件だが、2.6 のエラー欄に 429 が無く、上限値や単位(IP・ユーザー・期間)も決まっていない。無料枠 LLM(CON-004)の上限との関係も不明である。
   - 改善案: 各操作の上限値と単位を決め、429 とそのメッセージを各 API のエラーに追加する。ユーザーへの確認が要る。
6. **[中程度 / 設計]** POST /api/v1/auth/login, GET /api/v1/projects, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/documents/upload, GET /api/v1/projects/{id}/documents
   - 問題: 認証・認可の方針が書かれていない。トークン形式、ログアウト・失効の API、他人のプロジェクト {id} へのアクセスを拒否する 403/404 の扱いが未定義である。401 エラーが定義されているのは一部の API だけである。
   - 理由: CON-003 はトークン失効用の Redis を挙げているが、失効の API が無い。{id} 指定の API は所有者チェックが必須で、公開サービス(規模=public)ではデータ漏えいに直結する。

7. **[中程度 / 設計]** FR-003, POST /api/v1/projects/{id}/documents/upload
   - 問題: 参考資料のテキスト化の処理が定義されていない。ファイルサイズ上限、PDF の抽出失敗やスキャン PDF の扱い、テキスト化結果の用途(LLM への入力にどう使うか)、アップロード済み資料の一覧・削除が決まっていない。

   - 改善案: サイズ・ページ数・文字数の上限、抽出失敗時のエラー、テキストを LLM にどう渡すかを定義する。
8. **[中程度 / 設計]** POST /api/v1/projects/{id}/chat, NFR-003, FR-009
   - 問題: チャット応答は「最初の文字を数秒で出す」ストリーミング前提だが、API は 200 OK (AI応答) の単発応答として書かれている。ストリーミング中に失敗したときの扱いも不明である。

9. **[中程度 / 設計]** SCR-002, GET /api/v1/projects, SCR-003
   - 問題: 画面遷移時に既存プロジェクトの状態(ヒアリング中・サマリ承認済み・文書生成済み)を取得する API が無い。チャット履歴の取得 API も無く、再訪時にどの画面へ進むかが決まらない。

   - 改善案: プロジェクトに状態を持たせ、チャット履歴取得 API を追加する。状態に応じた遷移先を SCR-002 に定義する。
10. **[中程度 / 設計]** 外部設計書 2.6, NFR-002, NFR-007
   - 問題: 内部設計書(データモデル)が無く、バックアップ対象のデータ項目や、チャット内容の保存と NFR-007 の整合が確認できない。チャット履歴を DB に保存しなければサマリ生成ができないが、「入力内容はログに残さない」との線引きが書かれていない。

11. **[軽微 / ヒアリング]** FR-010, SCR-003
   - 問題: チャットの上限が「数千文字」のままで具体的な文字数が決まっていない。
   - 理由: バリデーションと 400 エラーの条件にするには、具体的な数値が要る。

   - 問題: 公開サービスなのに、パスワードの規則、メール確認、パスワード再設定、利用者の本人確認の方針が聞けていない。セキュリティが「AI の提案を採用」のままで、ログインを MVP に入れるという程度の内容しかない。

   - 改善案: パスワード規則、メール確認、再設定の要否を利用者に確認して要件に追加する。

## 区切り3: 要件定義書 + 外部設計書 + 詳細設計書

1. **[最重要 / 設計]** テーブル projects, F-03, F-04, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/documents/upload, POST /api/v1/projects/{id}/summary/approve, GET /api/v1/projects/{id}/documents

   - 理由: 公開サービス(規模=public)で FR-001/NFR-008 のアクセス制御を求めるのに、トークンの検証だけで、他人のプロジェクトのチャット・資料・生成文書を ID を指定して読み書きできる。ER 図の projects と F-03 の処理も食い違っている。

2. **[最重要 / 設計]** FR-008, FR-006, テーブル documents, テーブル summaries, F-07, F-08
   - 問題: 版管理と自己診断を保存する場所がない。documents は project_id と content だけで、参考資料と生成文書が同じ表に入り、文書種別・版番号・作成日時・自己診断結果の列がない。summaries(approved のみ)は「生成文書および版履歴データ」と説明されているが、対応する列がない。
   - 理由: FR-008「文書ごとに直近3件の版を保持」、FR-006「不足点を提示」、F-08「4種文書と直近3件を取得」を、このデータモデルでは実現できない。「直近3件」を残す処理(古い版の削除)もどの処理にも書かれていない。
   - 改善案: 生成文書用に document_versions(project_id, doc_type, version_no, content, created_at)を設け、参考資料は別表(ファイル名付き)に分ける。自己診断結果の保存先を決め、4種×3版を超えた古い版を削除する手順を F-07 に加える。
3. **[最重要 / 不整合]** FR-004, SCR-003, SCR-004, テーブル summaries, F-07
   - 問題: 構造化サマリを生成・保存・表示・修正依頼する API と処理がない。SCR-003 の「ヒアリング完了」、SCR-004 の表示と「修正依頼」に対応する API がなく、summaries は approved だけでサマリ本文を持たない。F-07 手順6 は「構造化サマリデータ」を渡すが、その取得元がない。
