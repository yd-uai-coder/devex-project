1. **[最重要 / 設計]** POST /api/v1/chat/messages, POST /api/v1/documents/generate, DF-4, テーブル chat_messages
   - 問題: チャット送信APIの本文が message のみで project_id がなく、どのプロジェクトのチャットか特定できない。DF-4 は chat_messages に project_id を保存するが、その入力元が無い。
   - 理由: 外部設計書 2.6 のチャット API は本文が message だけ。DF-4 は project_id を保存先に書くが、受け取る経路が無い。
   - 改善案: チャット API に project_id を追加するか、パスを /projects/{project_id}/chat/messages のようにする。
2. **[最重要 / 不整合]** NFR-006, POST /api/v1/chat/messages, POST /api/v1/documents/generate, DF-5, DF-4
   - 問題: 他人のプロジェクトを閲覧できないという要件(NFR-006)に対し、チャットと生成の API には所有者確認の設計が無い。生成APIの本文は project_id だけで、401/403/404 の応答も定義されていない。これらの API は認証要否も不明。
   - 理由: NFR-006 に紐づくのは POST /projects だけ。他人の project_id を指定してチャット履歴や設計書を読み書きできる恐れがある。chat と documents のエラー欄に認証・認可のエラーが無い。
   - 改善案: project の user_id と認証ユーザーを照合する処理を DF-4/DF-5 に加え、全 API に 401/403(または 404)を定義する。
3. **[最重要 / 設計]** FR-006, SCR-003, POST /api/v1/documents/generate, FR-007
   - 問題: 生成済みの設計書と自己診断結果を取得する API(GET)が無い。SCR-003 のプレビュー、リロード後の再表示、一覧表示ができない。プロジェクトやチャット履歴を取得する API も無い。
   - 理由: 外部設計書 2.6 の API は5本の POST だけ。FR-006 の対応表では API が「—」。生成結果は生成 API の応答でしか返らず、本文の形も未定義。
   - 改善案: プロジェクト一覧・履歴取得と、設計書・診断の取得 API(GET /projects/{id}/documents など)を追加し、応答の形を定義する。
4. **[中程度 / 設計]** POST /api/v1/documents/generate, NFR-003, FR-007, DF-5
   - 問題: 数分かかる4文書の生成と自己診断を、同期 API の1回で行う設計になっている。タイムアウト、進捗、途中失敗の扱いが決まっていない。
   - 理由: NFR-003 は生成に数分かかることを許容している。DF-5 は4件分の documents と diagnostics を保存するが、途中で失敗したときの扱い(全保存か全破棄か)が無い。nginx のタイムアウトにも触れていない。リスク1の対策も「非同期処理を活用」と書くだけ。
   - 改善案: 生成をジョブにして状態を取得する API を用意するか、タイムアウト値と保存を1トランザクションにする方針を明記する。
5. **[中程度 / 設計]** POST /api/v1/documents/generate, テーブル documents, FR-007, FR-009
   - 問題: 再生成したときに、既存の documents・diagnostics を上書きするか追加するかが決まっていない。documents は (project_id, doc_type) が一意でなく、世代や状態の列も無い。
   - 理由: FR-007 は再生成を要求し、生成 API は何度でも呼べる。版の履歴は MVP 外なので、最新版の特定方法が必要。
   - 改善案: 再生成時は既存行を置き換える方針にして一意制約を付けるか、世代列を設けて最新を取得する規則を定義する。
6. **[中程度 / 設計]** NFR-008, POST /api/v1/chat/messages, POST /api/v1/documents/generate, POST /api/v1/projects
   - 問題: チャットと生成の回数制限を実装する方針はあるが、上限値・単位(ユーザーか IP か)・期間が決まっていない。chat/documents/projects API には 429 の応答も無い。
   - 理由: NFR-008 は回数制限を求めている。外部設計書 2.6 で 429 があるのは register と login だけ。FR-008 の「数千文字」も具体値が無く、バリデーションを実装できない。
   - 改善案: 回数制限の上限値と単位を決め、該当 API に 429 を定義する。入力文字数も具体値にする。
7. **[中程度 / 不整合]** FR-002, POST /api/v1/auth/login, backend/core/security.py, CON-003
   - 問題: リフレッシュトークンで更新する API と、ログアウト・トークン失効の API が無い。一方で Redis は「トークン失効」に使うと書かれている。
   - 理由: FR-002 はアクセストークン30分・リフレッシュ14日を求めるが、更新エンドポイントが API 一覧に無い。トークン失効の処理も DF にも API にも出てこない。
   - 改善案: POST /auth/refresh と /auth/logout を追加し、Redis の失効の扱いを DF に書く。もしくは失効を MVP 外と明記する。
8. **[中程度 / 不整合]** backend/api/v1/auth.py, モジュール一覧, backend/core/security.py, backend/api/v1/projects.py, backend/api/v1/documents.py
   - 問題: モジュールの依存関係が不整合。auth.py の依存先が ai_service.py になっている。documents.py は DF-5 で chat_messages を直接読むのに、リポジトリ層が構成に無い。projects.py も DB の依存を持たない。レート制限とトークン検証のミドルウェアの置き場所も未定義。
   - 理由: 内部設計書 3.3 の依存先と、3.3 で述べるレイヤー構成(リポジトリ層・ミドルウェア)が合っていない。実装ルールは「依存先だけに依存する」ので、そのままでは実装が設計違反になる。
   - 改善案: auth.py の依存先を security.py と DB 層に直す。リポジトリ層とミドルウェア用のモジュールを追加し、依存先を定義する。
9. **[中程度 / 設計]** テーブル projects, POST /api/v1/projects, DF-3, DF-5, FR-003
   - 問題: 参考資料はファイルパスだけを保存し、保存場所(Docker ボリューム等)は決まっていない。pdf のテキスト抽出・サイズ上限・生成時の LLM への渡し方も設計されていない。DF-5 の取得元も chat_messages だけで、参考資料が出てこない。
   - 理由: DF-3 は保存するだけで内容の抽出が無い。DF-5 の流れは参考資料を使っていない。NFR-002 のバックアップ対象にも、ファイル保管場所が含まれない。
   - 改善案: ファイルの保存先・サイズ上限・テキスト抽出の方法を決め、DF-5 で参考資料を読む処理を明記する。バックアップ対象にも含める。
10. **[中程度 / 設計]** POST /api/v1/projects, SCR-002, テーブル projects, DF-3
   - 問題: プロジェクト作成の API は参考資料の files のみを受け取り、プロジェクト名がない。また、参考資料が無い場合にプロジェクトを作れるかが不明。
   - 理由: projects テーブルには名前・タイトル・状態の列が無い。1人が複数のプロジェクトを持つ設計(1対多)で、一覧から識別する手段が無い。files は「最大3件」のみで、0件の扱いが決まっていない。
   - 改善案: projects に name 列を足し、API の本文に加える。files 0件を許可するか明記する。
11. **[中程度 / 設計]** POST /api/v1/chat/messages, FR-007, DF-4, テーブル chat_messages
   - 問題: AI 応答の失敗時はメッセージを保存しない仕様だが、DF-4 の順序(LLM 呼び出し後に保存)とは、利用者メッセージの保存タイミングが定まっていない。ヒアリングの終了と生成の開始を決める規則も無い。
   - 理由: FR-007 は応答失敗時にメッセージを保存せず再送させる。DF-4 は LLM 後に保存する流れだが、user と ai を同一トランザクションで保存するとは書いていない。また、ヒアリングの完了判定も無い。
   - 改善案: user と ai の2件を、応答成功後に同一トランザクションで保存すると明記する。ヒアリングから生成への遷移の条件も定義する。
12. **[中程度 / 不整合]** M-01-T01, 実装計画書, CON-005, NFR-002, SCR-001, SCR-002, SCR-003, NFR-009
   - 問題: 実装計画書にフロントエンドの実装タスクが無く、基盤タスクも Next.js 基盤・nginx・GitHub Actions・DB マイグレーション・バックアップ・スマホ閲覧対応を含んでいない。
   - 理由: タスクは M-01〜M-03 のバックエンドの API だけ。M-01-T01 は Dockerfile と compose に限られ、要件 CON-005・NFR-002 の担当タスクが無い。FR-006 のプレビュー・コピー・ダウンロードも、API の無いまま M-03-T02 に割り当てられている。M-01 のゴールにも「Next.js の構造」が入っていて、実際の中身と矛盾する。
   - 改善案: 画面(SCR-001〜003)、Next.js 基盤、nginx・CI/CD、マイグレーション、バックアップ、レート制限のタスクを追加する。
13. **[軽微 / ヒアリング]** NFR-007, NFR-004, 観点 運用・保守性, 観点 セキュリティ(ログ)
   - 問題: 「AI の提案を採用」の運用・保守性とログの観点が浅い。エラー追跡と死活監視を MVP 後にする一方、ログは「エラーの有無と日時だけ」に限り、障害原因を調べる手段が無い。ログの保存先や保持期間も決まっていない。
   - 理由: NFR-004 と NFR-007 は AI 提案の採用のみで、利用者に確認していない。不具合の調査や Gemini の失敗の切り分けに必要な情報が残らない。
   - 改善案: 利用者に、エラーコードやリクエスト ID などを残してよいかと、ログの保持期間を確認する。
14. **[軽微 / ヒアリング]** 観点 体制・期間, FR-001
   - 問題: 体制・期間が未決のまま、誰でも登録できる公開サービスとして FR-001 が決まった。パスワード規則、メール確認、利用規約、機密情報を外部 LLM(Gemini)に送ることの周知など、公開サービスで要る事柄が聞けていない。
   - 理由: 規模は AI 提案を採用で、確認が浅い。NFR-006 で機密性を重視する一方、入力が Gemini に送られることが要件に出てこない。
   - 改善案: パスワードの最低要件、メールの確認要否、Gemini へのデータ送信の扱いと同意を利用者に確認する。
