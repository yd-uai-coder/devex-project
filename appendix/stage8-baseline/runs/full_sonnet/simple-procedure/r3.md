1. **[最重要 / 設計]** POST /api/v1/chat/messages, DF-4, テーブル: chat_messages
   - 問題: チャット送信 API の本文が message だけで、project_id がない。どのプロジェクトのチャットか特定できず、履歴の取得や保存先も決まらない。
   - 理由: 外部設計書 2.6 と DF-4 の入力は message のみ。chat_messages.project_id は NOT NULL で、LLM に渡す履歴もプロジェクト単位で必要になる。
   - 改善案: リクエストに project_id を追加する(またはパスを /projects/{project_id}/chat/messages にする)。あわせて対象プロジェクトの所有者チェックを DF-4 に入れる。
2. **[最重要 / 設計]** FR-006, SCR-002, SCR-003, 外部設計書 2.6 API一覧, 付録 要件との対応
   - 問題: 画面が必要とするデータの取得 API がない。チャット履歴、プロジェクト一覧・再開、生成済み設計書の本文、自己診断結果が対象。FR-006 のプレビュー・コピー・ダウンロードも、対応する API が「—」になっている。
   - 理由: SCR-002 はチャット履歴・設計書・自己診断を表示し、SCR-003 は設計書を表示する。しかし API は register / login / projects 作成 / chat 送信 / generate の5本だけ。generate の応答の中身も未定義。1.2 の「その日のうちに見直す」利用では、再ログイン後に再表示できる必要がある。
   - 改善案: GET /projects(一覧)、GET /projects/{id}(履歴を含む)、GET /projects/{id}/documents(本文と診断を含む)を追加する。generate の応答項目を定義する。ダウンロードを API で行うかクライアント側で行うかを決める。
3. **[最重要 / 不整合]** NFR-006, POST /api/v1/documents/generate, POST /api/v1/chat/messages, POST /api/v1/projects, DF-4, DF-5
   - 問題: 他人のプロジェクトを閲覧・操作できないようにする所有者チェックが、chat と generate の API・データフローにない。認証エラー(401)と権限エラー(403/404)の応答も定義されていない。
   - 理由: NFR-006 は Must のセキュリティ要件。generate は client から渡された project_id をそのまま使い、DF-5 には user_id と projects の突合がない。chat と generate のエラー欄に 401 がなく、projects の 401 だけがある。
   - 改善案: JWT の user_id と projects.user_id を照合する処理を DF-4/DF-5 に追加する。他人のプロジェクトは 404 を返す。chat と generate にも 401/404 を明記する。
4. **[中程度 / 設計]** FR-002, POST /api/v1/auth/login, CON-003
   - 問題: リフレッシュトークンでアクセストークンを再発行する API と、ログアウト(トークン失効)の API がない。
   - 理由: FR-002 はアクセス30分・リフレッシュ14日で、CON-003 は Redis でトークンを失効管理するとしている。API 一覧には register と login しかなく、更新と失効の流れがどこにもない。
   - 改善案: POST /auth/refresh と POST /auth/logout を追加する。Redis の失効リストを使う手順(ローテーションするか、jti を何で管理するか)を DF に書く。
5. **[中程度 / 設計]** POST /api/v1/documents/generate, NFR-003, FR-007, テーブル: documents, テーブル: diagnostics, リスク1
   - 問題: 数分かかる4文書の生成を、同期の 201 応答で返す設計になっている。進捗や状態、タイムアウト(nginx・FastAPI)の扱い、途中失敗時の部分保存、再生成時に既存の documents / diagnostics を置換するか追記するかが決まっていない。
   - 理由: NFR-003 は生成に数分かかるとしている。リスク1は「非同期処理を活用」とあるだけで、API・テーブルに状態管理がない。documents に (project_id, doc_type) の一意制約もなく、再生成すると重複しうる。
   - 改善案: 生成をジョブ化する(202 を返し、状態取得 API を設ける)か、同期でタイムアウトを延ばすかを決める。生成の状態を持たせる。4文書と診断はトランザクションで保存し、再生成は置換とする。
6. **[中程度 / 不整合]** DF-5, テーブル: projects, FR-003, FR-004
   - 問題: アップロードした参考資料が生成に使われる流れが書かれていない。pdf のテキスト抽出、保存場所、サイズ上限、プロンプトに入れる長さの上限もない。
   - 理由: DF-5 の「チャット履歴・参考資料取得」の取得元は chat_messages だけで、projects.reference_file_paths を読む行がない。DF-3 は「ファイル保存」とあるだけで、保存先(Docker ボリューム等)は未定義。保存先が NFR-002 のバックアップ対象かも不明。
   - 改善案: DF-5 に projects から参考資料を読む行と抽出処理を追加する。ファイルサイズ上限と保存先を定め、バックアップ対象に含める。参考資料の内容を DF-4 のヒアリングでも使うか決める。
7. **[中程度 / ヒアリング]** NFR-008, POST /api/v1/chat/messages, POST /api/v1/documents/generate, 内部設計書 3.4
   - 問題: 回数制限の具体値(ログイン失敗、登録、チャット、生成の回数と期間)が決まっていない。chat と generate の API には 429 の応答もない。
   - 理由: NFR-008 は「回数制限により防ぐ」と書くだけで数値がない。外部設計書 2.6 の 429 は register と login だけ。公開サービスで Gemini の利用料に直結するため、実装時に決められない。
   - 改善案: ユーザーに上限を聞き直す(例: 1ユーザーあたり1日の生成回数、1分あたりのチャット数、IP とアカウントのどちらで制限するか)。決まった値を NFR-008 と各 API の 429 に反映する。
8. **[中程度 / 不整合]** 実装計画書 4.2 WBS, CON-001, CON-005, NFR-002, SCR-001, SCR-002, SCR-003, FR-006
   - 問題: 実装計画書がバックエンドしか扱っておらず、フロントエンド(Next.js + Tamagui の3画面)、nginx、GitHub Actions による自動デプロイ、DB バックアップのタスクがない。レート制限のミドルウェアのタスクもない。
   - 理由: M-01〜M-03 のモジュールはすべて backend/*。M-01-T01 の環境・設定は Dockerfile と docker-compose.yml だけ。FR-006 は M-03-T02 に割り当てられているが、プレビュー・コピー・ダウンロードを担う画面実装はない。NFR-002、NFR-008、CON-005 を担うタスクもない。
   - 改善案: フロント基盤と SCR-001〜003 の実装、nginx 設定と CI/CD、バックアップ(7世代と VPS 外コピー)、レート制限ミドルウェアのタスクを追加し、要件 ID と結び付ける。
9. **[中程度 / ヒアリング]** DF-4, SCR-002, FR-004, chat_graph.py
   - 問題: ヒアリングをいつ完了とみなして生成に進むかが定義されていない。chat の応答に完了判定の項目がなく、生成は別 API になっている。
   - 理由: SCR-002 は「完了時に設計書を一括生成」とあるが、DF-4 の応答は AI 応答メッセージだけ。ヒアリングで聞く項目、質問の回数、利用者が任意に生成を押せるかが不明で、LangGraph のフロー設計に着手できない。
   - 改善案: 生成の起動を利用者の明示操作(生成ボタン)にするか、AI が充足を判定するかを決める。その場合は chat の応答に状態項目を加える。ヒアリングで聞く観点の一覧も定める。
10. **[中程度 / 設計]** DF-4, FR-007, テーブル: chat_messages
   - 問題: 利用者の発言をいつ保存するかが曖昧。AI 応答が失敗したときの再送で、利用者メッセージが重複したり欠けたりする恐れがある。
   - 理由: DF-4 の保存行は「project_id, sender, content」の1行だけ。ユーザー発言と AI 応答のどちらを保存するか書かれていない。FR-007 は失敗時に「メッセージを保存しない」としている。
   - 改善案: ユーザー発言と AI 応答を成功後に同一トランザクションで保存する、と DF-4 に明記する。再送時は同じ入力を再度受け付ける。
11. **[軽微 / 不整合]** backend/api/v1/auth.py, backend/api/v1/projects.py, backend/core/security.py, 内部設計書 3.3 モジュール一覧
   - 問題: モジュール一覧の依存が不自然または欠けている。auth.py が ai_service.py に依存している。リポジトリ層が構成に無く、projects.py と auth.py から DB へのアクセスが直接書かれている。security.py の層が「モデル」になっている。
   - 理由: 3.3 の本文はルーティング・サービス・リポジトリ・モデルの4層としているが、ファイル構成にリポジトリ層はない。auth と ai_service は無関係。実装ルールが「一覧の依存先にだけ依存する」なので、このままでは実装が矛盾する。
   - 改善案: auth.py の依存先を security.py と core/database.py に直す。リポジトリ層を設けるか、api から DB セッションを直接使うと明記する。security.py の層を core に直す。
12. **[軽微 / ヒアリング]** FR-008, NFR-008, FR-001, POST /api/v1/auth/register
   - 問題: 入力の上限と登録の条件が曖昧。チャット入力は「数千文字」としか書かれていない。パスワードの規則やメール確認の有無も決まっていない。
   - 理由: FR-008 は数値がなく、400 の判定条件を実装できない。公開サービス(FR-001)で誰でも登録できるのに、登録の大量作成対策はレート制限だけ。
   - 改善案: チャット入力の最大文字数を数値で決める。パスワードの最小要件とメール確認の要否を聞き直して、FR-001 に反映する。
