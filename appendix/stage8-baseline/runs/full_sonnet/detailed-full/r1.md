1. **[最重要 / 設計]** テーブル projects, F-03, F-04, POST /api/v1/projects/{id}/chat, GET /api/v1/projects/{id}/documents, POST /api/v1/projects/{id}/summary/approve
   - 問題: projects テーブルに所有者(user_id)の列がありません。F-03 は find_all_by_user_id、F-04 は user_id を保存すると書いていますが、実際には保存できません。{id} 付きの API にも、そのプロジェクトが本人のものかを確かめる手順や 403 の応答がありません。
   - 理由: 公開サービス(規模=public)なので、他人のプロジェクトIDを指定すると、他人のチャット・資料・生成文書を読み書きできる恐れがあります。F-05〜F-08 の verify_token はトークンの検証だけで終わっています。
   - 改善案: projects に user_id(FK)を追加します。{id} を使う全 API で、プロジェクトの所有者とトークンのユーザーが一致するかを確認します。一致しなければ 403 または 404 を返し、API 一覧にもその応答を書きます。
2. **[最重要 / 設計]** テーブル documents, テーブル summaries, FR-008, FR-005, FR-006, F-07, F-08
   - 問題: 生成した4種文書、版番号、文書の種別、自己診断の結果、構造化サマリの本文を保存するテーブルや列がありません。documents は参考資料の content だけで、summaries は approved の真偽値だけです。
   - 理由: F-07 は documents に生成文書を書き込み、F-08 は documents から直近3件の版を読み出すとしています。しかし、参考資料と生成文書の区別も、版・種別・診断結果の列もないため、FR-005・FR-006・FR-008 を満たせません。
   - 改善案: 参考資料(reference_documents)と生成文書(generated_documents: project_id, 種別, version, content, diagnosis, 作成日時)を別テーブルに分けます。summaries に本文を持たせ、直近3件を残す方針を定めます。
3. **[最重要 / 不整合]** FR-004, SCR-003, SCR-004, POST /api/v1/projects/{id}/summary/approve
   - 問題: ヒアリング完了から構造化サマリを作る処理、サマリを表示する API、修正依頼の API がありません。SCR-003 の「ヒアリング完了ボタン」と SCR-004 の「修正依頼ボタン」には対応する API も処理もありません。
   - 理由: 外部設計の API 一覧には approve しかなく、詳細設計の F-01〜F-08 にもサマリの作成・取得・修正はありません。しかし F-07 は「構造化サマリデータ」を入力に使っています。サマリはどこにも作られず、利用者が承認する対象が存在しません。
   - 改善案: サマリ生成の API(POST .../summary)、取得の API(GET .../summary)、修正依頼の API を追加します。対応する処理 F-ID、保存先、実装計画のタスクも追加します。
4. **[最重要 / 設計]** F-07, POST /api/v1/projects/{id}/summary/approve, SCR-005, FR-009, 実装計画書 リスク(タイムアウト)
   - 問題: 文書生成はバックグラウンド処理ですが、状態を保持する場所と状態を取得する API がありません。生成失敗時の記録、再生成の API(SCR-005 の再生成ボタン)、版切り替えの API もありません。F-07 の手順の表では、非同期の手順5のあとに手順6〜7を同期のように並べ、その後で手順8の応答を返しており、順序が矛盾しています。
   - 理由: 実装計画書のリスク欄は「進捗や結果は別APIで取得する」としていますが、API 一覧にその API はありません。FR-009 の「生成失敗時は再生成できる」を満たす手段もありません。4文書を1回の LLM 呼び出しで作るため、途中で失敗すると全部やり直しになります。
   - 改善案: 生成ジョブの状態(待機・生成中・成功・失敗、理由)を持つ列やテーブルと、GET .../generation-status、POST .../regenerate を追加します。F-07 の手順を「承認→ジョブ登録→応答」と「バックグラウンド側」に分けて書き直します。文書単位で生成・失敗を扱い、版の指定取得も定義します。
5. **[中程度 / 不整合]** NFR-008, FR-001, POST /api/v1/auth/login, POST /api/v1/auth/register, POST /api/v1/projects/{id}/chat, POST /api/v1/projects/{id}/summary/approve, 07 レート制限
   - 問題: 回数上限(NFR-008)は横断事項に書かれているだけです。上限の値と単位(IP かユーザーか)、対象 API ごとの扱い、429 の応答が API 一覧にありません。処理を担当するモジュールも app/cache/token.py のみで、F-02 以外の手順にも出てきません。実装計画にもレート制限のタスクがありません。
   - 理由: NFR-008 はユーザーが決めたセキュリティ要件ですが、画面・API・処理・実装タスクのどれにも落ちていません。Gemini 無料枠の保護にも関わります。
   - 改善案: 対象 API ごとに上限値と単位を決め、API 一覧に 429 を追加します。レート制限専用のモジュールを作り、M-01 の基盤タスクまたは独立のタスクとして実装計画に入れます。
6. **[中程度 / 設計]** テーブル tokens, F-02, L-04, 07 認証, FR-001
   - 問題: トークンの設計が食い違っています。tokens テーブルには有効期限・user_id・失効の列がなく、email で紐づけています。F-02 は create_token(ユーザーID)を呼ぶ一方、手順4では Redis 保存と tokens C の両方が書かれています。有効期限は「要決定」のままです。ログアウトや失効の API もありません。
   - 理由: CON-003 は Redis を「トークン失効用」としていますが、期限切れの判定(L-04 手順3)に必要な期限が定義されていません。DB と Redis のどちらが正かも決まっていません。F-02 の「手順2〜4が1つのトランザクション」は Redis を含められません。
   - 改善案: トークンの保存先を Redis か tokens テーブルのどちらかに決め、user_id と expires_at を持たせます。有効期限を数値で決め、ログアウト(失効)API を追加します。
7. **[中程度 / 設計]** F-05, テーブル chats, POST /api/v1/projects/{id}/chat, NFR-003, FR-003
   - 問題: LLM の呼び出しに渡すのは「プロジェクトID・今回のメッセージ」だけで、過去のチャット履歴や、保持した参考資料(documents.content)を文脈に使う手順がありません。chats には発言者・順序・作成日時の列もありません。API の応答は一括の 200 OK で、NFR-003 の「最初の文字を数秒で出す」(ストリーミング)に必要な方式が書かれていません。チャット履歴の取得 API もありません。
   - 理由: 参考資料は FR-003 で保持するだけで、ヒアリングにも文書生成にも使われません。履歴が文脈に入らないと、ヒアリングが会話として成り立ちません。画面を再読み込みしても履歴を表示できません。
   - 改善案: LLM の入力に、履歴と参考資料テキストを加えます。chats に作成日時などを追加します。応答を SSE などのストリーミングにするかを決め、履歴取得の API を追加します。
8. **[中程度 / 不整合]** 実装計画書 M-01〜M-04, SCR-001, SCR-002, SCR-003, SCR-004, SCR-005, NFR-002, CON-005, NFR-009
   - 問題: 実装計画のタスクはバックエンドのみです。5画面のフロントエンド(Next.js + Tamagui)、nginx、GitHub Actions による自動デプロイ、DB の日次バックアップと VPS 外へのコピー(NFR-002)、ブラウザ対応の確認に当たるタスクがありません。
   - 理由: 環境の節で技術スタックを述べているだけで、画面・デプロイ・バックアップの作業が計画に入っていません。「プレビュー・コピー・ダウンロード」(FR-007)にも画面の実装タスクがありません。
   - 改善案: 画面ごとのフロント実装タスク、nginx/CI-CD の構築タスク、バックアップ(cron とオフサイト転送)のタスク、結合・E2E テストのタスクを追加します。
9. **[中程度 / ヒアリング]** FR-003, F-06, POST /api/v1/projects/{id}/documents/upload, 規模(公開サービス), セキュリティ
   - 問題: 参考資料のファイルサイズ上限、1プロジェクトあたりの件数、LLM に渡せるテキスト量の上限が決まっていません。公開サービスなのに、メール確認、パスワードの強度、パスワード再設定、利用規約や入力データの扱いも聞かれていません。セキュリティ観点は AI の提案を採用した「ログインを入れる」だけです。
   - 理由: PDF のテキスト化とアップロードは負荷と悪用の入口になります。Gemini の無料枠にも収まるか不明です。誰でも登録できるため、アカウント周りの方針が要件にないと設計できません。
   - 改善案: サイズ・件数・文字数の上限と、アカウントまわりの方針(メール確認、パスワード規則、再設定の要否)を利用者に聞き直し、要件に追加します。
10. **[軽微 / 不整合]** POST /api/v1/projects/{id}/documents/upload, F-06, POST /api/v1/projects/{id}/chat, L-02, L-05, 07 ログ, NFR-004
   - 問題: 細部の食い違いが複数あります。(1) アップロードの応答が API 一覧では 201、F-06 では 200 です。(2) API 一覧の多くに 401・404 の応答が書かれていません。チャットの失敗応答が 500 だけで、Gemini の上限超過を表す 429/503 がありません。(3) L-02 は「例外なし」としていますが、手順は 401 を返します。L-05 は ValueError、F-04 は AuthError・UnauthorizedError と、例外名がばらばらです。(4) 07 ログは死活監視に活用すると書いていますが、NFR-004 は MVP 後に導入すると定めています。
   - 理由: 外部設計と詳細設計で同じ API の記述が一致しないと、実装とテストの基準が定まりません。
   - 改善案: 応答コードを外部設計に合わせて統一し、401・403・404・429・503 を API 一覧に補います。例外名を共通化し、ログの記述は MVP の範囲に直します。
