# TOP ページと GUIDE(使い方の解説)ページの構成案

> 2026-10-29 にユーザーが承認した構成案(Phase 118 の入力)。経緯は [`textbook/q_a.md`](../textbook/q_a.md)「ステージ14完了後 ── TOP・GUIDE の構成案」。パスはリポジトリ直下から。

## Context

- 今の TOP(`devex-ui/src/app/(pages)/page.tsx`)は、ダミー画像の Hero と「4種類のドキュメントを自動生成」という**ステージ1時点の説明**、メニューのカードだけ。ステージ11〜14 で足した「合意と変更管理」が一切伝わらない。
- メニューの Guide は仮リンク(`/guide` は 404。`devex-ui/src/lib/menu-tree.ts:36-39`)。
- 目的: 偶然このページに来た人が「何のアプリか・何ができるか」を TOP で掴み、使い方は GUIDE で手順どおりに進められるようにする。内容の正本は root の `README.md`(概要・課題・機能)と `docs/external_design.md`(画面・遷移)。

## 1. 見せ方の方針

1. **読者を3つに分ける**: ①偶然来た人(何のアプリか知らない)②使ってみたい人 ③クライアント(共有リンクで来る人)。TOP は①が30秒で掴めることを最優先、GUIDE は②が画面の横に置いて進められること、③には専用ページを置く。
2. **TOP =「何が・なぜ」、GUIDE =「どうやって」**。TOP に手順は書かず、機能カードごとに GUIDE の該当ページへ誘導する。
3. **用語は初出で言い換える**。「CR → 変更要求(仕様を変えたいという申し出)」「束 → 合意済みの版」「トレーサビリティ → 要件からテストまでのつながり」。用語集のページも置く。
4. **画面の表記どおりに書く**(ボタン名・タブ名・見出しを画面と一致させる)。
5. **前提条件を先に言う**: 自分の API キー(Gemini / Claude)が要る・費用は自分持ち、詳細設計モード限定の機能(確認事項・資料・行の合意)はその旨を各所に明記。
6. **流れを図で見せる**: 「ヒアリング → 文書 → 詳細設計 → 実装手順・テスト → 合意済みの版 → 変更要求 → クライアントと合意 → 反映・再検証」を1枚の図(インライン SVG か Tamagui の箱と矢印)にし、TOP と GUIDE 目次で共有する。
7. **ログイン不要で読める**(公開ページ。`(protected)` の外に置く)。
8. **AI に任せきりにしない姿勢**(人が判断・承認する)と「やらないこと」も TOP に短く書き、期待値を合わせる。

## 4. GUIDE のページ構成

```
/guide                     目次: ガイドの読み方・目的別の入口・全体の流れ図
├─ /guide/getting-started  はじめに: 登録/ログイン(メール・Google)、API キーの取得と登録、
│                          用途ごとのモデル選択、費用の目安、キーの扱い(暗号化・削除)
├─ /guide/projects         プロジェクト: ダッシュボード、モードの選び方、テンプレート、検索・削除
├─ /guide/hearing
├─ /guide/documents
├─ /guide/detailed-design
├─ /guide/implementation
├─ /guide/review           設計レビュー・テスト設計・変更の影響
├─ /guide/agreement        合意と変更管理(最も手順が長い。目次つき)
├─ /guide/materials
├─ /guide/for-clients      クライアントの方へ
└─ /guide/glossary         用語集とよくある質問(費用・データの扱い・対応ファイル)
```

**機能ごとのページを、流れでつなぐ**(ユーザーの回答を反映):
- ページは機能ごと(上のツリー)。そのうえで、利用の流れの順番を1本の並びとして定義する:
  はじめに → プロジェクト → ヒアリング → 文書 → 詳細設計 → 実装手順 → レビュー・影響 → 合意と変更管理 → 資料の取り込み(→ クライアントの方へ は合意と変更管理から分岐)。
- 各ページの上に**流れの帯**(全段を横に並べ、今のページを強調。押すとその段へ飛ぶ。スマホ幅では「段 N / 全 M: 名前」の1行+展開)を置く → どのページから読んでも、仕様の流れの中の位置が分かる。
- 各ページの下に**「前へ / 次へ」**(流れの順)と、関係の深いページへの横のリンク(例: ヒアリング ↔ 確認事項、合意 ↔ クライアントの方へ)。
- `/guide` 目次は、流れ図そのものを目次にする(図の各段がそのページへのリンク)+ 目的別の入口。
- 流れの並びはデータ1か所(`features/guide/` の定義)に置き、帯・前後のリンク・目次・TOP のカードが同じ定義を使う。

**各ページの共通の型**(読み手が迷わないよう固定する):
0. 流れの帯(上)
1. この機能でできること(2〜3文)
2. 使う場面
3. 前提(モード・必要な状態・API キー)
4. 手順(番号付き。画面のボタン名どおり)
5. 画面の見方(スクリーンショット + 注記)
6. うまく使うコツ / 注意
7. 次に読む(前後のページへのリンク)

目的別の入口(`/guide` 目次): 「まず試したい → はじめに」「設計書がほしい → ヒアリング・文書」「しっかり設計したい → 詳細設計」「仕様変更をクライアントと合意したい → 合意と変更管理」「共有リンクを受け取った → クライアントの方へ」。

## 5. 実装の方向(承認後に詰める)

- **進め方**: Phase 118 をこの作業(TOP・GUIDE)にし、自動実装モード on。ステージ11〜14 の本番反映は Phase 119 に送り、TOP・GUIDE も一緒に反映する(CLAUDE.md・位置付け 12章・memory の「Phase 118 = 本番反映」の記述を送る)。Phase 118 の開始は別セッション(#18)。
- **スクリーンショット**: 開発環境に確認用のデータ(簡易・詳細の各1プロジェクト、CR・資料つき)を用意し、run-devex-ui の shot.mjs で撮影、`devex-ui/public/guide/*.png` に置く。個人情報・API キーが写らないことを確かめる。ライト/ダークは片方(ライト)で統一。

- 置き場: `devex-ui/src/app/(pages)/guide/**/page.tsx`(公開)、本文と部品は `devex-ui/src/features/guide/`(ページ共通の型のレイアウト部品、流れ図、機能の定義データ)。TOP のカードと GUIDE の目次は同じ機能の定義データを使う。
- 既存の再利用: `components/ui/media/Hero.tsx`、`components/ui/layout-blocks/LayoutGrid.tsx`、`components/ui/primitives/StyledCard.tsx`。
- メニュー: `src/lib/menu-tree.ts` の Guide を `/guide` 目次と主要ページへのリンクに差し替え。
- `metadata`(title・description)をページごとに付け、`layout.tsx` の `lang="en"` を `ja` に直す(検索・読み上げのため)。Next.js の書き方は `devex-ui/node_modules/next/dist/docs/` で確かめる(AGENTS.md)。
- 仕様: `docs/external_design.md` 2.2 の画面一覧に TOP・GUIDE を足す(#40 の CR として q_a に残す)。
- テスト: 各ページのコンポーネントテスト(見出し・GUIDE へのリンク)、menu-tree のテストの更新。
