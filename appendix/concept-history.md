## 1. 改修方針とロードマップ(元: `devex_roadmap.md`)

ChatGPT で作った初版(項目を「Phase 0〜10」と番号付けしていた)を、2026-10-06 に Claude との相談で改訂した。番号を `docs/implementation_plan.md` の「ステージ」にそろえ、完了済みのステージ1〜4を含めて並べ直した。

### 1.1 目指すもの

- 単なる「AI による設計書生成アプリ」ではなく、**要件定義から設計・実装計画・実装手順・テストまでの開発プロセスをつなぎ、設計の一貫性と実装可能性を支援するシステム**にする。
- ポートフォリオとしては、「設計者としてシステムをどう分解し、設計し、検証し、実装へ落とし込むか」という思考過程を示す作品にする。
- 「ドキュメントを増やす」こと自体を目的にしない。要件 → 要件定義 → 外部設計 → 内部設計 → 実装計画 → 実装手順 → 実装 → テストの各段階を、相互に参照できる設計情報としてつなぐ。重要なのは、設計情報の構造化・トレーサビリティ・漏れの少ないヒアリング・変更影響分析・AI による設計レビュー・実装可能性の検証。
- **なぜこの方向か**: 「AI に設計書を書かせる」だけでは既存の生成 AI サービスと差がつかない。価値は、設計そのものの品質・一貫性・実装可能性を高めることに置く。AI がコードを完全に自動生成することは最終目的にしない。人が「なぜこの構造か・どの責務をどこに持たせるか・どの順で実装するか・どの変更がどこへ効くか」を理解した状態で開発できることを重視する。セキュリティや非機能要件も、AI の提案に頼り切らず、利用者が自分で判断できる形で引き出す。

### 1.3 なぜこの順序か

- **5 を最初にする**: 手順書を作ろうとすると、設計の不足(必要なファイルが分からない・責務の所在が不明・API や DB の仕様やエラー処理・トランザクション境界が無い)が実例として出てくる。チェックだけを先に作るより、何を検証すべきかがはっきりする。実装手順書の生成は、設計の実装可能性を検証する仕組みでもある。
- **6 を 5 の直後にする**: 5 で見つかる不足の多くはヒアリングの漏れに行き着く。レビュー(8)まで待つと、その間に作る設計書がすべて今のヒアリングの質のままになる。観点の状態の記録と要件 ID の採番は、どちらも要件定義書の構造化なので同じステージで行う。
- **8 では再ヒアリングの自動化だけを足す**: 自己診断と「修正中」でチャットに戻る流れはすでにあるので、それを広げる。

## 2. UML 製図・レビュー・draw.io 出力システム(元: `uml-review-drawio-requirements-external-design.md`、「UML 文書」)

2026-09-27 に作った、独立したシステムとしての要件定義書・外部設計書(想定実装者は Claude Code)。ステージ3では主仕様として扱い、Devex の中のモジュールとして作った。

### 2.1 考え方

AI に UML 図を draw.io の XML として直接書かせない(生成・検証・レイアウト調整に時間がかかり、利用者が確かめるまでが遅い)。代わりに、AI は UML の**意味構造**を中間モデルとして作り、React Flow で速く表示して利用者がレビュー・修正し、承認した後にだけ同じモデルから draw.io を生成する。

```text
AI → UML Semantic Model → Layout / Style → React Flow のプレビュー → 利用者のレビュー・修正 → 承認 → draw.io Generator → .drawio
```

### 2.2 元の章ごとの要点

| 章 | 要点 |
|---|---|
| 1.4 スコープ | Must: 意味モデルの受け取りと JSON での保持・React Flow への変換とプレビュー・ドラッグでの配置変更・クラス名など要素の編集・保存・承認・承認済みモデルからの draw.io 生成とダウンロード・React Flow と draw.io で意味構造と位置が一致。Should: 自動レイアウト・検証・undo/redo・版の管理・SVG 等の出力・複数の記法。Won't: draw.io の完全再現・AI による draw.io XML の直接生成 |
| 1.5 機能要件 | FR-001(設計モデルの生成)〜 FR-016(図の間の整合性) |
| 1.6 非機能要件 | NFR-001 性能・NFR-002 再現性・NFR-003 保守性・NFR-004 拡張性・NFR-005 AI 依存の分離 |
| 2.2 責務の分離 | 正本は図ではなく共通の Design Model。Semantic(何を表すか)/ Layout(どこに置くか)/ Style(どう見せるか)を分け、記法ごとのモデル(Activity・Sequence・Component・ER など)は Semantic の拡張にする |
| 2.3 設計 JSON モデル | `id`・`view`・`notation`・`version`・`status`・`elements`・`relations` を持つ共通の形 |
| 2.6 API 設計 | `POST /api/uml/diagrams`(生成)・`GET`/`PUT /api/uml/diagrams/{id}`・`/validate`・`/layout`・`/approve`・`/export/drawio` |
| 2.7 React Flow Adapter | `toReactFlow()` と `fromReactFlow()` で意味モデルと React Flow の形を相互に変換する |
| 2.8〜2.9 | Layout Engine と draw.io Generator(決定的・XML のエスケープ) |
| 2.11 状態遷移 | draft → reviewing → approved → exported。承認後に編集すると reviewing に戻る |

| 2.14 設計ビュー | UML 図を作ること自体を目的にせず、人が設計を理解できる図を選ぶ(振る舞いはアクティビティ図、実行時の連携はシーケンス図、構造はコンポーネント図、データは ER 図) |
| 4 配置方針・文書への反映(2026-09-27 の決定) | Devex 本体のリポジトリの中に新しいモジュールとして足す。文書への反映は、該当の節を構造化データから作り直して Markdown を置き換える方式。4.3節の推奨モジュール構成は `devex-api/backend/app/uml/` と `devex-ui/src/features/uml/` |

### 2.3 その後

[ステージ3の要件整理](#stage3)で、主仕様として採用した部分(FR-001〜016・NFR・API・状態遷移・4章)と、採らなかった部分(初期のクラス図の編集を Could に切り分け、元の「Phase 1〜8」の番号は使わずステージ3は Phase 7 から)を分けた。API のパスは `/api/v1/projects/{id}/uml/...` になり、詳細設計モードが段階2〜4の図として引き継いでいる。

## 3. ステージ3の要件整理 ── UML 設計図パイプライン(元: `stage3-requirements-organization.md`)

2026-09-28 に作り、09-29 に D1〜D8 を決めた叩き台。入力は [UML 文書](#uml-document)、要件定義・設計書テンプレートと UML MCP の調査メモ(整理で削除)、別プロジェクトの自作の図生成エンジン(「移植元エンジン」)。

### 3.1 確定した方針

- 入力の役割分担: UML 文書は主仕様。調査メモ(IPA・デジタル庁の要件定義と設計書のテンプレート、UML の MCP)からは3点だけ取り込んだ ── 図の記法と工程の対応表(図と文書の節の対応表の材料)、IPA の非機能要求グレードと LLM アプリに固有の非機能要件(自己診断の観点の追加。従)、「図はテキストで人が読める形で持つ」考え(JSON を正本にしたので直接は採らない)。MCP(開発時の道具であり実行時に入れない)・自作の RAG・デジタル庁のテンプレートの全面採用(個人開発には重い)は採らなかった。
- 主は UML 図のパイプライン、文書テンプレートの拡充は従。図の正本は JSON の意味モデル(Semantic / Layout / Style を分ける)。
- 記法: コンポーネント図・ER 図・**処理別 DFD** を Must(DFD は 09-29 に Should から引き上げ)。
- 最終ビジョン(09-29 共有): ① AI との対話で要件と基本設計を書く(完了) → ② 基本設計から詳細設計を起こす(ステージ3) → ③ 詳細設計の手直しを基本設計へ戻す(ステージ3) → ④ AI の自動コーディングでイメージどおりのシステムができる(最終目標。**スコープ外**。図の粒度の品質指標として置く: 実装者が追加の設計判断をせずにコードへ落とせる水準)。
- 移植元エンジンの調査: Python の DSL(レーンと行を定義側が明示し、矢印だけを自動で経路探索)、1つの定義から `.drawio` と `.svg` を同時に出力、経路の候補を全部挙げてコストで選ぶ、日本語の文字幅の見積もりと禁則処理つきの折り返し。Devex には、レーンと行の割り当て(最長経路法の層分けと循環辺の除去)・幅の上限の検証エラー化・ノード数の上限を新しく足す必要があった。

当時の Phase の案は、7 設計フェーズ / 8 意味モデル・データ辞書・CRUD / 9 レイアウト / 10 AI 生成 / 11 画面 / 12 承認と出力 / 13 文書との連携(M9a) / 13b 手直しの反映(M9b) / 14 activity と統合。

## 4. 詳細設計モードの構想(元: `detailed-design-mode-organization.md`)

2026-09-30、Phase 13 の完了後の相談で出た構想の整理メモ。2026-10-01 に「概要モード」を「簡易ドキュメントモード」に改称した。

### 4.1 背景

コンポーネント図の粒度が粗く(`api-service-model` 程度)、ファイル単位のモジュールの責務が分からない、という指摘があった。原因は図ではなく入力の側にあった(内部設計書のプロンプトがファイル単位の責務を求めていない、図の生成が「入力に無い要素を作らない」、図1枚の要素の上限が30)。いったん「機能ごとの部分図」などで直す方針を立てたが、「一般的な実務と照らして再検討したい」として保留し、公開資料を調べた。

### 4.2 実務の資料から分かったこと

| 観点 | 実務の形 |
|---|---|
| 構造 | 階層になった「概観図 + 部品の表(名前・責務・コードの場所)」。重要な部分だけ書く(arc42 Building Block View) |
| 構造の粒度 | コンポーネント図は責務の単位。コードの図は手で描かない(C4) |
| 振る舞い | 番号付きの手順・アクティビティ図・シーケンス図のどれでもよい。代表的なシナリオだけ(arc42 Runtime View) |
| 日本の詳細設計 | シーケンス図・CRUD 図・テーブル定義・モジュール仕様 |
| DFD | 要件定義〜基本設計で使うのが一般的。詳細な処理ロジックはフローチャートなど |

利用者が示した前提: 実務にできるだけ準拠する。自動コーディングの水準は理想形であり要件ではない(まずは、人がコーディングするのに十分な資料を作る)。シーケンス図に当たるものは欲しいが、まずは番号付きの手順から始める。

### 4.3 構想した形

- **2つのモード**: 簡易ドキュメントモード(チャット → 4文書を一括生成。そのまま残す)と、詳細設計モード(チャット → 要件定義・外部設計 → 段階1〜6を順に作って承認 → 実装計画)。各段階の意味モデルを人が承認してから次の入力にし、文書は承認済みの成果物から組み立てる。
- **詳細設計書の章 = 段階**: 1 機能(処理)一覧 / 2 データフロー(機能グループごとの DFD・データ辞書・処理概要表)/ 3 データモデル(ER・テーブル定義・CRUD 図)/ 4 ソフトウェア構造(構成図・モジュール一覧)/ 5 主要処理の手順(選んだ処理だけ。No・呼び出し元 → 先・渡すデータ・処理内容・結果・DB 操作・分岐と例外)/ 6 処理ロジックの詳細(任意。選んだ関数のモジュール仕様と擬似フロー)/ 7 横断事項。
- **良い点**: 実務の工程に沿う。1回の入力が小さくなり品質が上がる。ステージ3の資産(意味モデル・検証・レイアウト・出力・レビュー画面・承認・データ辞書・陳腐化)の大部分を使える。段階の依存がそのまま陳腐化の伝わる道になる。M9b がほぼ不要になる。
- **懸念**: 規模が大きく、モード・段階の状態・ウィザードの画面が要る。シーケンス図は未解決。

### 4.4 未決事項と決定

元の8章の未決事項(1〜9)は Phase 14 ですべて決めた([Phase 14-1](../textbook/Phase-14/Phase-14-1.md)・[Phase 14-2](../textbook/Phase-14/Phase-14-2.md))。

| # | 未決事項 | 決定 |

| 2 | 段階の状態と承認の持ち方・前の段階を直したとき | `design_stages` と陳腐化の表示(作り直しは人が指示する) |
| 3 | 機能グループの決め方 | API のリソース名で初期値を作り、人が確定する |
| 4 | CRUD のうち DFD から決まらない部分 | R・W は DFD の向き、C/U/D は AI の下書きを人が確定する |
| 5 | 手順の列・シーケンス図に進むか | 列は見本どおり。シーケンス図は運用の後に判断する(その後、ステージ5で段階5の手順から導く形で足した) |

## 5. 実装手順書の作成方針(元: `devex_implementation_procedure_guideline.md`)

ChatGPT との相談で作った初版を、2026-10-06〜07 に Claude との相談で今の Devex(詳細設計モードの段階1〜7、簡易ドキュメントモードの4文書)に合わせて改訂した、ステージ5の方針。初版から直した主な点は、設計の中身を書き写さず参照する・2つのモードを入力にする・実装単位を機能ごとの縦割りにする・実装可能性チェックを入れる・変更の影響を手で書かない、の5つ。

### 5.1 元の章ごとの要点

| 章 | 要点 |
|---|---|
| 1 目的 | 手順書は、コード生成用のプロンプトではなく、設計情報を実装できる粒度へ変える文書。設計の不足・矛盾を、実装に入る前に表に出す(実装可能性チェック)。手順書の生成とチェックは1つの機能として作る |
| 2 位置づけ | 要件 → 要件定義 → 外部設計 → 内部設計 / 詳細設計 → 実装計画 → **実装手順書 + 実装可能性チェック** → 人による実装 → テスト。不足・矛盾は設計の修正とヒアリングの改良へ戻す |
| 3 入力とモード | 詳細設計モードは段階1〜7(単位の元は段階7のタスク、参照先は処理 ID・段階6の関数・段階3のテーブル・段階4のモジュール・07章)。簡易モードは4文書(単位の元は実装計画書の WBS、参照先は `DF-<n>`・API・モジュールのパス・内部設計書 3.2・3.4)。形は共通にし、変わるのは入力と深さだけ。簡易モードは「未定義」が多く出ることにも価値がある |
| 4 実装計画との違い | 実装計画は What / When、手順書は How。手順書は設計を**書き写さず ID で参照**し、固有に書くのはファイル(依存順・責務1行)・順序・確かめ方・設計に無いもの(未定義)の4つだけ |
| 5 基本構成 | 1 実装概要 / 2 前提・制約 / 3 実装単位の一覧(依存順)/ 4 各単位(目的・対象の処理と参照する設計・ファイル・実装の要点・テスト観点・確認方法・未定義)/ 5 未定義・要決定の一覧 / 6 完了条件 |
| 6 実装概要 | 対象と対象外を明示し、AI による不要な実装を防ぐ。要件の MoSCoW とマイルストーンから導く |
| 7 前提・制約 | 実装ルールは一般論で書かず、設計(段階4の層と依存先・07章、簡易モードは内部設計書 3.1・3.3・3.4)から引く。引けないものは未定義に挙げる |
| 8 実装単位 | **機能ごとの縦割り**(層ごとの横割りは途中で確かめられないので採らない)。ID は実装計画から導く(`M-01-T01`)。依存は単位の間に持ち、単位の中のファイルは import の依存順 |
| 9 単位のテンプレート | 目的 / 対象の処理・参照する設計 / 作成・変更するファイル(依存順の表)/ 実装の要点(設計に無いことだけ)/ テスト観点 / 確認方法 / 未定義・要決定 |
| 10 処理・インターフェース・エラー | すべて設計の該当箇所を参照する(処理の流れは段階5の手順・`DF-<n>`、関数の契約は段階6、API は外部設計、エラー・トランザクション・認証は07章・内部設計書 3.4)。設計に無いものは推測で埋めず未定義に |
| 11 テスト | Given/When/Then に加えて、SUT・ドライバ・スタブの関係を書く(スタブが要らないときは理由を書く)。ステージ5は単位ごとの観点まで、体系的なテスト設計はステージ8 |
| 12 完了条件 | Definition of Done(単位のテスト・既存のテスト・lint と型・マイグレーション・起動して確認・未定義がすべて決まり設計に反映) |
| 13 実装可能性チェック | 調べるもの(コンポーネント・API の粒度・トランザクション・エラー・認証・外部依存・矛盾・順序)。**2層**: 決定論的な検証(参照する ID が設計にあるか・依存順が段階4と矛盾しないか・どの単位にも入らない処理が無いか)と、LLM に推測で埋めさせず未定義として挙げさせる指摘。重要度は #28 の3段階。ヒアリングで聞くべきだったものはステージ6の材料に |
| 14 変更時の影響範囲 | 手で書かない(書いた時点から古くなる)。単位と ID の紐づけだけを持ち、影響はステージ7でグラフをたどって計算する |
| 15 AI への渡し方 | 設計書を一括で渡さず、今の単位に必要な情報を中心に渡す。**AI 向けの出力は手順書の1単位を整形したもの**で、別の中身を作らない。参照の展開は Devex が決定的に行い、未定義が残る単位は渡す前に警告する |
| 16 AI による実装の流れ | 単位の提示 → リポジトリの調査 → 整合性の確認 → 差異の報告 → 方針の提示 → 人の確認 → 実装 → テスト → 報告。設計とコードが食い違えば、勝手に直さず報告する |
| 17 プロンプトの基本構造 | プロジェクト概要・実装ルール・今回の単位・ファイル・参照する設計(本文を展開)・テスト観点・完了条件・制約(推測で決めない)を、手順書と設計から機械的に埋める |
| 18 出力 | 詳細設計書・実装計画の zip に `implementation_procedure/`(`index.md` と単位ごとの md。ファイル名は単位の ID)を加える。簡易モードも同じ形 |
| 19 設計原則 | 1 AI の完全自動実装を目的にしない / 2 計画と手順書を分ける / 3 単位を明確に / 4 人と AI の共通言語 / 5 設計変更を実装へ伝える / 6 不整合を検出して報告 / 7 書き写さず参照 / 8 推測で埋めない / 9 形はモードでも実装者でも変えない |
| 20 最終的な価値 | 要件を設計へ、設計を実装計画へ、計画を具体的な手順へ変え、AI Coding Agent による実装まで一貫してつなぐ。開発の速さと、人による設計・実装・保守の理解を両立させる |
| 21 未決事項 | Phase 25 で決定(下) |

### 5.2 その後

21章の未決事項は Phase 25 ですべて決めた([Phase 25-1](../textbook/Phase-25/Phase-25-1.md)): 1 形は共通で簡易モードも作る / 2 実装計画書の WBS を縦割り・ID 付きにする / 3 段階7を改修して `M-01-T01` / 4 実装の要点は自明な作業と順序の理由だけ / 5 検証と AI の2層、直すのは設計の側 / 6 zip と画面の両方 / 7 選んだ単位を上限5 / 8 テストは単位ごとの観点まで。あわせて、段階5の手順から導くシーケンス図を手順書に載せた([Phase 25-5](../textbook/Phase-25/Phase-25-5.md))。簡易モードの手順書は Phase 31 で作った(WBS を決まった書式で書かせて決定的に読む)。

## 6. ステージ9・10 の影響調査と計画(元: `stage9-10-plan.md`)

ステージ8の完了後(2026-10-16)、ロードマップを改めたときに、各ステージの着手前に作った影響調査と計画の案。

### 6.1 新ステージ9: 使い勝手とアカウント・モデル設定(元の1節)

- **要望**: ヘッダーからトップへ / ログアウト / ログイン済みのとき認証ページを飛ばす(汎用のミドルウェアとして作る)/ ダッシュボードの削除・タイトルの検索・モードと進行状態での絞り込み・10件ずつのページ送り / マイページ(表示名・メール・パスワードの変更、用途ごとのモデル、API キーの登録。superuser でなくても自分のキーで使えるように)/ チャットを最下部で表示 / 文書と詳細設計の画面の削除ボタン / グローバルメニューの組み直し(TOP・CONTENTS・Authentication・Guide)。
- **影響調査の主な点**: 認証ページを飛ばすには、Next.js 16 の `src/proxy.ts` と、UI のオリジンに置くログインの印の cookie が要る(アクセストークンはメモリ、refresh cookie は API のオリジンにあるため)。プロジェクトの一覧はレスポンスの形が `{items, total}` に変わる。モデルとキーは新しいテーブル(用途ごとの provider とモデル、provider ごとの API キーを Fernet で暗号化)と静的なカタログが要る。LLM の組み立てを「ユーザーと用途 → LLM」に作り替え、呼び出し箇所の約8か所と provider に固有の処理を両方の provider で通す。
- **決めたこと**: `.env` のモデルとキーはシステムの既定値とし、利用者のキーがあればそちらを優先する(キーが無い利用者も既定の Gemini でチャットと生成ができる。レビューは自分のキーがあれば superuser でなくても使える)/ 絞り込みの「段階」は進行状態 / 認証ページは proxy と印の cookie で飛ばす / 判定のモデルは4つ目の用途にする。
- **Phase の案**: 画面の小さな調整 → 認証ページの proxy → 削除 → 検索と絞り込み → アカウント → モデルとキー → LLM のユーザーごとの解決 → E2E と本番。

### 6.2 新ステージ10: Google 認証(元の2節)

- **影響調査**: `users.hashed_password` を null 可にし、`google_sub` を足す。`POST /auth/google` で ID トークンを検証して自前の JWT と refresh cookie を発行する。マイページでは Google だけの利用者にパスワードの「設定」を出す。本番では Google Cloud の OAuth クライアントと同意画面を用意する。E2E は偽の検証のフラグで流す。
- **2.3 未決事項**: フロー(Authorization Code か ID トークンか)・同じメールの既存アカウントとの紐付け・ライブラリ。
- **2.4 ステージ9の振り返りから**: 本番への反映をステージ10とまとめる。ステージ10の入力として、開発環境のレート制限・削除したプロジェクトの URL の表示・新規作成の後の一覧の cache・押せないボタンの見た目・負荷のときだけ落ちるテスト。

### 6.3 その後
